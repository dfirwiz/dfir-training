학습 범위

넷째 날 6강에서는 Zeek이 패킷을 연결·프로토콜·이벤트와 로그로 바꾸는 흐름, 시그니처와 이벤트의 차이, 단일 프로세스와 클러스터의 역할 분담, 여러 센서의 행동 상관관계를 배웁니다. 예시는 정상 합성 기록이며 실제 운영 센서를 실행한 결과가 아닙니다.

1. 패킷을 전부 저장하는 것과 질문할 수 있는 기록을 만드는 것은 다릅니다

하루치 패킷에서 “어떤 내부 호스트가 새 외부 서비스와 연결했나?”를 매번 원시 바이트부터 찾는다면 시간이 많이 듭니다. Zeek은 네트워크 트래픽을 해석해 연결·DNS·HTTP·TLS 같은 활동을 구조화된 로그와 이벤트로 바꿉니다. 이벤트는 패킷 처리 과정에서 의미 있는 상태나 데이터가 생겼다는 신호이고, 로그는 그 결과를 나중에 검색할 수 있도록 남긴 기록입니다.

도서관에서 책의 모든 글자를 사진으로 보관하는 것과 제목·저자·대출 기록을 색인으로 만드는 차이를 떠올려 보세요. 색인은 질문을 빠르게 답하게 하지만 원문을 대신하지는 않습니다. Zeek 로그도 관측 지점과 분석기가 해석한 범위만 담고, 암호화된 응용 내용·누락 패킷·지원하지 않는 프로토콜은 제한됩니다. 중요한 사건에서는 원시 패킷, 방화벽·단말·서버 로그와 함께 봅니다.

2. 패킷에서 이벤트와 로그가 나오는 처리 순서를 따라갑니다

수집 라이브러리가 프레임을 읽으면 Zeek의 코어가 네트워크·전송 계층을 해석하고 양방향 연결 상태를 만듭니다. TCP라면 순서가 바뀐 세그먼트를 재조립하고, 응용 분석기는 실제 메시지 구조를 보고 프로토콜을 판별합니다. 포트 번호는 단서일 뿐이며 동적 프로토콜 탐지는 내용 구조와 상태를 함께 봅니다.

분석기가 새 연결, DNS 질의, HTTP 요청, TLS 수립처럼 의미 있는 상태를 만나면 이벤트를 스크립트 계층에 전달합니다. 하나의 이벤트를 여러 독립 핸들러가 받을 수 있어요. 스크립트는 로그를 쓰거나 조건을 누적하고, 필요한 경우 notice를 만들어 조사 대상으로 올립니다. 이벤트가 발생했다는 사실과 악성이라는 판단은 같은 말이 아닙니다.

3. 시그니처는 정적 조건을, 이벤트는 상태와 데이터의 도착을 표현합니다

시그니처는 헤더나 페이로드의 정해진 패턴처럼 비교적 정적인 조건을 찾는 데 강합니다. 이벤트는 연결이 만들어짐, TLS 수립이 완료됨, DNS 응답이 관측됨, 프로토콜 위반이 발견됨처럼 분석 과정의 상태 변화를 표현합니다. 이벤트 자체가 경보는 아니며 스크립트가 문맥을 누적해 로그·notice·통계를 만들 수 있습니다.

같은 패킷을 다른 질문으로 읽기
관점시그니처이벤트·스크립트
주요 입력헤더·바이트 패턴·고정 조건연결 상태, 프로토콜 의미, 분석기가 제공한 데이터
시간 범위패킷 또는 재조립 스트림의 정의된 범위한 연결부터 여러 이벤트·시간 구간까지 누적 가능
결과조건 일치 경보로그, 통계, notice 또는 아무 동작도 하지 않음
한계변형·암호화·문맥 부족에 영향상태 메모리·스크립트 오류·센서별 분산과 누락에 영향

예를 들어 new_connection은 새 연결이 관측됐다는 이벤트이고, http_request는 HTTP 요청이 분석됐다는 이벤트입니다. 이름만으로 정상·악성을 나누지 않습니다. 한 이벤트를 여러 스크립트가 독립적으로 처리할 수 있으므로 같은 활동이 연결 로그, 프로토콜 로그와 사용자 정의 통계에 함께 반영될 수 있습니다.

4. 클러스터는 역할을 나눠 처리량과 공통 시야를 확보합니다

작은 환경에서는 한 호스트의 단일 구성으로 패킷 분석과 로그 기록을 함께 할 수 있습니다. 트래픽이나 스크립트 부하가 커지면 여러 Zeek 프로세스로 나눕니다. worker는 패킷을 읽고 프로토콜 분석을 수행합니다. manager는 중앙 관점이 필요한 데이터·이벤트와 notice를 다루며, 별도 logger가 없으면 로그도 모읍니다. logger는 선택적인 역할로 로그 수집 부하를 분리합니다. proxy는 배포한 스크립트가 필요로 하는 데이터 저장·작업과 통신 부하를 나누는 역할을 할 수 있습니다.

오래된 설명처럼 proxy가 모든 worker를 자동으로 하나의 완벽한 센서로 만든다고 생각하면 안 됩니다. 필요한 proxy 수와 역할은 스크립트, 클러스터 백엔드, worker 수와 트래픽 특성에 따라 달라집니다. 현재 문서에서도 작은 클러스터와 큰 클러스터의 요구가 다르다고 설명합니다. CPU·메모리·이벤트 지연과 로그 큐를 측정해 확장합니다.

5. 패킷별 분산보다 흐름 단위 일관성이 먼저입니다

프레임을 worker 1, 2, 3에 차례로 돌리면 요청과 응답이 다른 프로세스에 들어가 TCP 재조립과 응용 상태가 깨질 수 있습니다. 주소·포트·전송 프로토콜로 만든 대칭 흐름 해시처럼 양방향을 같은 worker에 보내는 분배가 필요합니다. 터널·NAT·VLAN이 있으면 해시가 바깥과 안쪽 중 무엇을 보는지 확인합니다.

정상 합성 구간에서 worker 세 대의 처리량이 각각 3.2, 3.0, 2.8Gb/s라면 합은 9.0Gb/s입니다. 평균은 9.0 ÷ 3 = 3.0Gb/s이고 가장 큰 worker는 평균보다 0.2Gb/s, 약 6.7% 높습니다. 하지만 이 합계만으로 무손실을 말할 수 없어요. 한 대에 거대한 흐름이 몰리거나 작은 패킷이 많으면 pps·CPU·드롭이 먼저 한계에 닿을 수 있습니다.

조건을 바꿔 한 worker가 5.8Gb/s, 나머지가 1.7과 1.5Gb/s라면 합은 여전히 9.0Gb/s입니다. 전체 평균은 같아도 첫 worker만 포화될 수 있어요. worker별 수집 드롭, 분석 큐, 이벤트·로그 지연과 흐름 분포를 함께 봅니다. worker 수를 바꾸면 해시 결과가 크게 재배치될 수 있으므로 변경 전후의 가시성 틈도 기록합니다.

6. 여러 이벤트를 묶을 때 같은 주체라는 증거가 필요합니다

어떤 단말에서 인증 실패가 여러 번 있었고, 나중에 여러 파일 서버로 연결했으며, 이후 송신 바이트가 크게 늘었다고 합시다. 각 사건은 정상일 수 있지만 시간·자산 역할·사용자·서버 결과를 연결하면 조사 우선순위를 높일 수 있습니다. Zeek은 네트워크 이벤트와 로그를 제공하지만 실제 사용자의 성공 인증과 파일 접근 권한은 인증·파일 서버 기록이 필요합니다.

센서 A의 192.0.2.40과 센서 B의 같은 주소가 반드시 같은 장치를 뜻하지 않습니다. DHCP 임대, VPN, NAT, 주소 재사용과 센서 시계를 확인하세요. Zeek 연결의 uid는 한 연결을 로그 사이에서 연결하는 식별자이지만 서로 다른 센서의 별개 연결을 같은 사건으로 자동 보장하지 않습니다. 자산 ID·사용자·시간 창과 서버 요청 ID를 보조 키로 사용합니다.

복습과 해설

1. Zeek 이벤트가 발생하면 공격이 확인된 것인가요?
아닙니다. 이벤트는 연결·프로토콜 상태나 데이터가 관측됐다는 신호입니다. 스크립트·로그와 다른 증거가 의미를 부여합니다.
2. 시그니처와 이벤트의 가장 큰 차이는 무엇인가요?
시그니처는 정의된 정적 조건의 일치를 찾고, 이벤트는 분석기가 해석한 상태 변화와 데이터 도착을 스크립트에 전달합니다. 둘은 경쟁 관계가 아니라 질문이 다릅니다.
3. 클러스터에서 worker는 무엇을 하나요?
패킷을 읽고 연결 재조립과 프로토콜 분석의 대부분을 수행합니다. manager·proxy·logger는 중앙 관점, 작업·상태 분산과 로그 수집 역할을 나눕니다.
4. 세 worker 합계가 처리량 목표와 같으면 안전한가요?
아닙니다. 흐름이 한 worker에 치우치거나 작은 패킷이 많으면 개별 포화가 생깁니다. worker별 pps·CPU·드롭·큐와 이벤트 지연을 확인합니다.
5. 여러 센서의 같은 IP를 같은 단말로 묶어도 될까요?
DHCP·NAT·VPN과 시간 차이 때문에 틀릴 수 있습니다. 자산·사용자·임대·서버 기록과 함께 식별해야 합니다.

공식 자료와 확인일

2026-11-25에 Zeek 9.0의 클러스터 역할, 현재 클러스터 아키텍처와 외부 흐름 분배, Zeek 이벤트와 스크립트 기본 구조를 확인했습니다. 실제 Zeek 프로세스·패킷 브로커·캡처 파일은 실행하지 않았습니다.
