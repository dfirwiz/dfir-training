학습 범위

넷째 날 18강은 Zeek 로그 상관분석 종합 실습입니다. 정상 합성 기록으로 연결·DNS·TLS를 읽고, 단순 주기 신호를 조사 후보로 올린 뒤 모니터링·헌팅·사고 대응에서 각각 어떻게 활용할지 연습합니다.

1. 첫 질문은 어떤 주체가 언제 무엇을 했느냐입니다

업무 단말이 낯선 주소에 일정 간격으로 접속했다는 알림이 왔다고 합시다. 출입 기록으로 비유하면 연결 로그는 누가 어느 문으로 언제 들어왔는지 적은 장부입니다. DNS는 목적지를 찾아보는 안내 데스크 기록, TLS 로그는 보호된 연결을 준비한 기록에 가깝습니다. 안내를 받은 사람이 곧바로 그 문에 가는 것은 아니듯 DNS와 다음 연결은 시간과 주체를 대조해야 합니다. 암호화 구간 뒤의 요청 내용이나 실행 프로세스를 알려면 별도 기록도 필요합니다.

조사 시작 전에 센서 위치, UTC 기준 시간 범위, 관심 단말의 주소 할당 기록을 적습니다. 같은 주소가 다른 단말에 다시 할당되거나 NAT·프록시에서 주소가 변할 수 있습니다. 로그가 일부만 있다면 범위 밖인 시간과 실제 누락을 나눠 표시하세요.

2. UID로 같은 연결을 묶고, 서로 다른 연결은 다른 근거로 이어 봅니다

UID는 Zeek가 연결에 부여하는 식별자입니다. 같은 센서의 로그에서 한 TCP 연결의 conn.log와 ssl.log를 UID로 연결할 수 있습니다. DNS의 dns.log는 DNS 통신의 연결 UID를 사용합니다. DNS 질의가 뒤이은 TLS 연결과 관련 있는지 보려면 동일한 시작 주체, 응답 주소와 목적지, 시간차 같은 근거를 더합니다. DNS 응답의 주소만으로 어떤 이름이 실제 사용됐는지 확정하기는 어렵습니다. 주소 공유, 캐시, 프록시, 여러 응답 값이 있기 때문입니다.

문서용 단말 192.0.2.34의 정상 합성 로그 요약
UTC로그와 UID관측 값다음 확인
08:00:00dns.log / D1updates.example 질의, 응답 198.51.100.30같은 단말의 이후 연결
08:00:04conn.log / C1198.51.100.30:443/TCP 연결같은 UID의 TLS 정보

08:10:06conn.log / C3같은 목적지의 세 번째 연결간격 분산과 승인 작업 일정

첫 TLS 연결까지 DNS 응답 후 4초가 지났습니다. 다음 연결은 300초 뒤, 그다음은 302초 뒤 시작했습니다. 관측된 두 간격의 평균은 (300 + 302) ÷ 2 = 301초입니다. 정상 업데이트가 5분마다 상태를 확인할 수 있습니다. 반대로 중간 한 건이 누락되면 10분에 가까운 간격이 보일 수 있습니다. 측정 전에 같은 주체·목적지·방향으로 묶었는지, 로그 시각이 연결 시작 시각인지 확인합니다.

3. 합성 기록을 오프라인에서 한 번 더 검산합니다

아래 코드는 세 연결의 시작 시각을 초로 환산한 목록만 읽습니다. zip(starts, starts[1:])은 인접 시각을 둘씩 묶습니다. later - earlier는 두 번째 시각에서 첫 시각을 뺀 초 단위의 간격입니다. 같은 목적지에 다른 단말이 접속하더라도 먼저 단말별로 나눠 계산합니다.

starts = [4, 304, 606]  # 08:00:00 UTC 이후 초
gaps = [later - earlier for earlier, later in zip(starts, starts[1:])]
print(gaps, sum(gaps) / len(gaps))  # [300, 302] 301.0

실제 로그의 ts는 시각, id.orig_h와 id.resp_h는 연결 시작 및 응답 주소, id.resp_p는 응답 측 포트입니다. TCP의 missed_bytes가 양수이면 비어 있는 페이로드 구간이 있다는 단서입니다. 0이라는 값만으로 센서 사본의 완전성을 보증할 수는 없습니다. ssl.log의 server_name은 관측한 경우의 서버 이름이며, 관측되지 않은 이름을 DNS나 포트로 채워 넣지 않습니다.

4. 모니터링, 헌팅, 사고 대응은 같은 관측을 다르게 활용합니다

지속 모니터링에서는 반복 접속을 검토 후보로 올리고 승인된 자산과 일정에 맞춰 기대되는 근거를 기록합니다. 예를 들어 5분 전후의 주기로 여러 번 접속했다는 값은 후보 조건입니다. 실제 기준은 여러 정상 기간을 확인해 고릅니다. 운영 단위에서 알림을 남긴다면 센서와 시간 범위, 비교한 집단, 수집 공백과 닫기 조건도 포함하세요.

위협 헌팅에서는 시작 단말을 바꿔 같은 시기에 비슷한 목적지나 규칙적 간격이 다른 자산에도 있는지 살펴봅니다. 어떤 대상에서 흔한 연결인지 확인하면 예외 규칙을 만들 근거가 생깁니다. 사고 대응에서는 서버나 프록시의 요청 처리 기록, 종단 프로세스와 소켓, 승인된 변경 일정으로 검증해 관측 범위를 좁힙니다.

5. 타임라인의 결론마다 확인 수준을 적습니다

관측: 단말이 같은 목적지에 세 번 접속했습니다. 첫 연결의 TLS 로그에는 업데이트용 이름이 보였고 두 간격은 300초와 302초였습니다. 가설: 예정된 업데이트 확인일 수 있습니다. 추가 증거: 승인 목록, 종단 프로세스, 서버 요청 기록과 시간대를 비교합니다. 검색 창이 짧거나 센서가 한쪽 방향만 봤다면 그 제한도 남깁니다.

앞 강의의 수집 위치, TLS 관측 범위, Zeek 이벤트와 기준선, 센서와 목적지의 해석 차이가 이 장부에 모두 들어옵니다. Zeek의 Notice는 관측에서 운영 검토가 필요한 결과를 발행하는 데 사용할 수 있습니다. 같은 활동이 반복된다면 기준을 근거와 함께 버전으로 관리하고, 새 표본에서 잘못된 합치기와 빠진 이벤트를 확인합니다.

복습과 바로 읽는 해설

1. C1과 D1의 UID가 다르면 관련이 없나요?
각각 다른 네트워크 연결의 UID입니다. 출발 주체와 DNS 응답, 연결 목적지와 시각으로 관련성을 확인합니다.
2. 표시된 두 간격을 왜 300초와 302초로 적나요?
인접 연결을 각각 뺀 결과입니다. 평균 301초는 차이를 숨기므로 원시 간격도 함께 남깁니다.
3. 443번 연결에서 요청 경로가 없으면 어떻게 조사하나요?
TLS 이름과 연결 시각 등 관측 가능한 범위를 기록하고, 승인을 받은 프록시 또는 서버 기록에서 실제 요청을 찾습니다.
4. 단말에서 승인 프로세스가 관측되면 어떤 점을 더 확인하나요?
그 프로세스가 바로 해당 소켓을 열었는지와 요청 목적지, 예정된 실행 시각을 맞춥니다. 그 뒤에 조사 결론을 업데이트합니다.
