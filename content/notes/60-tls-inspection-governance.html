학습 범위

넷째 날 5강에서는 TLS 종료 프록시가 하나의 암호화 연결을 두 연결로 나누는 원리, 평문을 다룰 때 생기는 보안·개인정보 위험, 선택적 검사와 키 로그를 이용한 안전한 오프라인 검증을 다룹니다. 예시는 관리되는 시험 환경을 가정하며 실제 사용자 통신을 복호화하지 않았습니다.

1. 암호화된 연결을 꼭 열어봐야만 조사할 수 있을까요?

의심스러운 외부 연결이 반복되지만 응용 내용은 TLS 안에 들어 있다고 합시다. 가장 먼저 “전부 복호화하자”고 결정하면 안 됩니다. 연결 시각·주소·방향·바이트·TLS 수립 정보와 관리 리졸버·프록시·단말·서버 로그만으로 질문에 답할 수 있는지부터 봅니다. 내용이 꼭 필요한 경우에도 승인된 목적, 대상, 기간과 접근자를 먼저 정합니다.

봉인된 우편물을 검사하는 상황을 떠올려 보세요. 봉투 겉면과 무게만으로 배송 경로를 확인할 수 있고, 정말 필요한 경우에만 정해진 절차로 열어볼 수 있습니다. TLS 메타데이터도 비슷하지만 이 비유에는 한계가 있어요. 하나의 IP가 여러 서비스를 담을 수 있고 ECH나 암호화 DNS가 이름 단서를 줄이며, 패킷 크기만으로 내용이나 의도를 확정할 수 없습니다.

2. 종료 프록시는 한 연결을 두 개의 TLS 연결로 나눕니다

종료 프록시는 클라이언트가 맺으려던 TLS 연결의 실제 종단으로 동작하고, 외부 서버에는 별도의 TLS 연결을 만듭니다. 클라이언트 쪽 연결과 서버 쪽 연결은 TCP 순서 번호, TLS 키와 인증서 검증 결과가 서로 달라요. 프록시는 두 연결 사이에서 평문을 읽고 정책을 적용한 뒤 다시 암호화합니다.

관리되는 단말은 조직이 배포한 신뢰 앵커를 이용해 프록시가 대상 이름에 맞춰 제시한 인증서를 검증할 수 있습니다. 신뢰 앵커는 인증서 체인의 출발점을 신뢰하도록 둔 인증기관 인증서입니다. 이 구성이 있다고 원래 서버 인증을 건너뛰어도 되는 것은 아닙니다. 프록시는 외부 서버의 이름·인증서·유효기간과 정책을 검증하고, 클라이언트에는 프록시가 확인한 결과와 차단 이유를 일관되게 전달해야 합니다.

3. 프록시 앞뒤 패킷은 같은 바이트 복사본이 아닙니다

프록시 앞에서 본 클라이언트 주소와 외부 서버 주소가 뒤쪽에서도 그대로일 수 있지만, NAT나 라우팅 정책 때문에 달라질 수도 있습니다. 포트와 TCP 순서 번호는 보통 별개의 연결이므로 서로 일치하지 않아요. 복호화한 내용을 분석 도구로 다시 패킷화하면 원래 암호화 패킷의 크기·타이밍·체크섬과 달라질 수 있습니다.

예를 들어 클라이언트가 10:00:02.120에 198.51.100.30:443으로 연결했고, 프록시가 10:00:02.168에 같은 서버로 새 연결을 시작했다고 합시다. 두 시작 시각의 차이는 0.048초, 즉 48ms입니다. 이 수치는 프록시 처리 시간만 뜻하지 않습니다. DNS·정책 조회, 큐, 외부 네트워크와 캡처 시계 오차도 섞일 수 있어요.

조건을 바꿔 프록시가 기존 서버 연결을 재사용하면 클라이언트 연결 하나와 서버 연결 하나를 단순히 1:1로 맞출 수 없습니다. 프록시의 연결 식별자·요청 ID와 양쪽 로그를 사용해야 합니다. “앞쪽 517바이트가 뒤쪽 70바이트로 바뀌었다”는 한 표본만으로 특정 응용이나 변조를 단정하지 않습니다.

4. 복호화 제외는 편의가 아니라 데이터 처리 정책입니다

건강·금융·노무·개인 통신처럼 민감도가 높은 범주는 업무 목적과 법적 근거에 따라 검사 제외가 필요할 수 있습니다. 반대로 악성 파일 탐지처럼 내용 검사가 꼭 필요한 관리 서비스가 있을 수 있어요. 목적지 이름만으로 범주를 정하면 공유 호스팅, CDN, 리디렉션과 ECH 때문에 틀릴 수 있으므로 자산·사용자·응용 정책과 서버 인증 결과를 함께 봅니다.

mTLS는 서버뿐 아니라 클라이언트도 인증서를 제시하는 상호 TLS입니다. 종료 프록시가 클라이언트의 원래 개인키를 대신 가질 수 없으므로 응용이 실패하거나 별도 설계가 필요할 수 있습니다. 인증서 고정, ECH, HTTP/3의 QUIC도 정책 장치의 가시성과 호환성에 영향을 줍니다. 실패했을 때 조용히 평문으로 내리거나 검사 없이 통과시키지 말고, 정한 정책대로 차단·예외·경보 중 무엇이 일어났는지 기록합니다.

5. 키 로그는 전체 프록시보다 좁은 오프라인 검증에 쓸 수 있습니다

관리되는 시험 클라이언트나 서버가 해당 TLS 세션의 비밀을 키 로그로 남길 수 있다면 저장된 캡처를 오프라인에서 복호화할 수 있습니다. Wireshark의 tls.keylog_file은 TLS 해석기에 키 로그 경로를 알려 주는 설정입니다. 파일을 지정했다고 모든 연결이 자동으로 풀리는 것은 아니며, 캡처와 세션 비밀이 같은 연결에 해당하고 수립 패킷과 재조립이 충분해야 합니다.

키 로그는 인증서나 공개키가 아니라 실제 세션의 평문을 드러낼 수 있는 민감한 비밀입니다. 시험 단말·짧은 시간·필요한 연결로 범위를 제한하고 암호화 저장, 최소 권한, 사용 후 파기와 감사 기록을 적용합니다. 실제 사용자 브라우저에 무단으로 설정하거나 외부 시스템의 비밀을 수집하지 않습니다.

서버 개인키 하나로 최신 TLS 1.3 트래픽을 나중에 전부 복호화할 수 있다고 생각하면 안 됩니다. 현대의 임시 키 교환과 전방향 비밀성은 장기 개인키가 나중에 노출돼도 과거 세션 복구 범위를 줄입니다. 목적에 맞는 세션 비밀을 승인된 종단에서 확보하는 방식과 프록시 종료 방식은 서로 다른 선택입니다.

6. 복호화하지 않아도 행동을 가설로 좁힐 수 있습니다

웹 문서 열람은 비교적 작은 요청 뒤 여러 응답이 짧은 시간에 모일 수 있고, 영상 스트리밍은 더 길고 지속적인 서버→클라이언트 바이트가 나타날 수 있습니다. 백업 업로드는 반대로 클라이언트→서버 바이트가 크게 치우칠 수 있어요. 하지만 캐시, 압축, 적응형 비트율, 화상회의, 소프트웨어 업데이트도 비슷한 모양을 만들 수 있습니다.

정상 합성 흐름에서 5분 동안 보낸 바이트가 900MB, 받은 바이트가 30MB라면 송신/수신 비는 900 ÷ 30 = 30입니다. 관측 사실은 이 구간에서 송신 바이트가 수신의 30배였다는 것입니다. 가설은 업로드·백업·동기화 등이고, 추가 증거는 관리 단말의 프로세스·사용자·예약 작업, 프록시 목적지와 서버 수신 기록입니다. 비율 하나만으로 유출이나 침해 성공을 확정하지 않습니다.

복습과 해설

1. 종료 프록시는 암호문을 그대로 전달하는 장치인가요?
아닙니다. 클라이언트와 첫 TLS 연결을 끝내고 외부 서버와 별도의 TLS 연결을 만듭니다. 가운데에서 평문을 다루므로 서버 검증과 민감정보 통제가 필요합니다.
2. 프록시 앞뒤의 TCP 순서 번호가 같아야 하나요?
두 TCP 연결은 독립적이므로 같을 필요가 없습니다. 프록시 요청 ID, 시각과 양쪽 로그를 사용해 대응 관계를 확인합니다.
3. 모든 TLS 트래픽을 복호화하면 조사 품질이 항상 좋아질까요?
내용 가시성은 늘지만 민감정보, 신뢰 경계, 호환성, 성능과 관리 위험도 커집니다. 먼저 메타데이터와 관리 로그로 답할 수 있는지 보고 최소 범위를 선택합니다.
4. 키 로그가 있으면 서버 개인키도 함께 필요한가요?
해당 세션 비밀이 정확히 있고 캡처가 충분하다면 키 로그 방식으로 해석할 수 있습니다. 키 로그 자체가 매우 민감하므로 범위·보존·접근을 통제해야 합니다.
5. 송신/수신 바이트 비가 30이면 유출인가요?
큰 비대칭이라는 관측일 뿐입니다. 승인된 백업·동기화도 가능하므로 단말 프로세스, 사용자·작업 기록과 서버 측 수신 증거를 연결합니다.

공식 자료와 확인일

2026-11-25에 RFC 9325의 현대 TLS 보안 권고와 전방향 비밀성, Wireshark 사용자 안내서의 TLS 세션 키 처리, Wireshark의 TLS 복호화 조건을 확인했습니다. 실제 프록시·키 로그·사용자 트래픽은 구성하거나 복호화하지 않았습니다.
