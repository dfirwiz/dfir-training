이 강의에서 할 일

둘째 날에는 저장된 패킷에서 필드를 찾아 읽었습니다. 이제는 탐지에 필요한 필드를 먼저 정하고, 그 값이 들어 있는 가상 패킷을 만들어 검산합니다. 예제는 문서용 주소와 자체 문자열을 사용하며 파일 안에서만 다룹니다.

1. 경보가 없을 때 무엇부터 확인할까요?

새 UDP 탐지 규칙을 켰는데 하루 종일 경보가 없었다고 해 봅시다. 생각할 수 있는 이유가 여럿입니다. 조건에 맞는 트래픽이 없었을 수도 있고, 센서가 필요한 방향을 못 봤을 수도 있습니다. 규칙이 로드되지 않았거나 내가 다른 바이트를 비교하고 있을 수도 있죠. 셋째 날의 첫 질문은 그래서 “어떤 입력을 주면 어떤 결과가 나와야 하나?”입니다.

편의점에서 바코드 스캐너를 교체했다고 생각해 보세요. 처음에는 품목 코드와 가격을 이미 아는 물건을 찍어 봅니다. 그런 다음 포장이 비슷해도 코드가 다른 물건을 찍어, 원하는 품목만 등록되는지 확인합니다. 패킷 시험도 의도적으로 맞는 표본과 비슷하지만 다른 표본을 함께 마련합니다. 비유의 한계도 있어요. 바코드는 한 자리에서 읽지만, 네트워크 센서는 수집 위치, 방향, 길이, 암호화, 여러 패킷의 재조립 상태에 따라 같은 통신에서 볼 수 있는 정보가 달라집니다.

시그니처는 탐지기가 관측한 데이터에 적용하는 조건입니다. 문자열만 뜻하는 것은 아닙니다. 프로토콜, 주소와 포트, 흐름의 방향, 해석된 응용 필드도 조건에 들어갈 수 있습니다. IDS는 침입 탐지 시스템으로 조건을 만족한 관측을 경보로 남길 수 있습니다. IPS는 배치 방식과 정책에 따라 통과 여부에도 관여할 수 있습니다. 이번에는 alert 규칙으로 경보의 기대 범위를 읽습니다. 차단을 시험하려면 별도의 배치·정책·처리 결과가 필요합니다.

2. 패킷보다 먼저 기대 결과를 적습니다

업무 서비스의 형식을 흉내 내지 않는 작은 시험을 준비해 봅시다. “IPv4의 192.0.2.10에서 198.51.100.20으로 향하는 UDP에서, 목적지 포트가 5514이고 UDP 데이터 첫 여섯 바이트가 정확히 LAB-OK면 경보 후보로 삼는다.” 포트는 가상의 숫자 조건입니다. 이 포트가 실제 어떤 프로그램에 연결됐는지, 앱이 이 데이터를 받아들였는지는 이 문장으로 결정할 수 없습니다.

첫 줄을 보고 코드부터 쓰기 쉬운데, 먼저 예제마다 기대 결과를 붙여 보세요. 조건 한 가지씩만 바꾸면 어떤 조건이 동작했는지 확인하기 훨씬 쉽습니다. 마지막 표본은 뒤에 바이트를 붙여, “접두부 일치”가 메시지 전체 일치와 어떻게 다른지도 보여 줍니다.

3. Scapy에서 계층과 필드를 찾아봅니다

Scapy는 Python에서 패킷을 계층별 객체로 다룰 수 있는 도구입니다. IP는 IPv4 계층을 만드는 클래스 이름이고 IP()는 이를 호출해 사용할 객체 하나를 만드는 표현입니다. ip처럼 소문자로 정한 변수 이름과 대문자 IP 클래스 이름은 Python에서 구별됩니다. 먼저 필드 이름을 발견해 보겠습니다.

from scapy.all import Ether, IP, UDP, Raw, ls, lsc

ls(Ether)
ls(IP)
ls(UDP)
ls(Raw)

from … import …는 오른쪽의 이름을 현재 코드에서 사용할 수 있게 가져옵니다. ls(IP)처럼 계층 클래스를 넘기면 필드와 자료형, 기본값을 확인할 수 있습니다. ls(ip)처럼 만들어 둔 객체를 넘겨 그 객체의 설정을 둘러볼 수도 있습니다. Scapy의 대화형 프롬프트에서 인수 없는 ls()는 계층을 찾고, lsc()는 명령을 찾을 때 사용합니다. 여기서 ls는 디렉터리를 보는 셸 명령과 이름만 같습니다.

이 표본에서 사용하는 객체와 필드
객체대표 필드예제에서 읽는 뜻
Ethersrc, dst, type링크 계층 주소와 바로 안쪽 계층의 종류. 예제의 주소는 로컬 관리 유니캐스트 값입니다.
IPsrc, dst, id, ttl, len, protoIPv4 주소, 16비트 데이터그램 식별자, 홉 제한에 쓰이는 값, 전체 IP 길이와 상위 프로토콜 번호입니다.
UDPsport, dport, len, chksum출발지/목적지 포트, UDP 헤더와 데이터를 합한 길이, 체크섬입니다.
Rawload이 실습에서 임의로 정한 데이터 바이트를 담습니다.

같은 이름인 src라도 Ether에서는 MAC, IP에서는 IP 주소입니다. 캡처에서 바이트 앞으로부터 주소를 찾기 전에 “어느 계층의 주소인가?”를 먼저 정했던 이유가 여기에도 그대로 적용됩니다.

4. 값과 자료형을 함께 지정합니다

ip = IP(src="192.0.2.10", dst="198.51.100.20", ttl=64)
ip.id = 314
udp = UDP(sport=53000, dport=5514)
payload = Raw(load=b"LAB-OK")

ip = IP(...)의 바깥 =는 만든 객체를 이름에 연결합니다. 괄호 안의 src=와 dst=는 필드 이름을 지정합니다. ip.id = 314는 이미 만든 객체의 id 필드를 바꿉니다. 처음에 IP(..., id=314)처럼 넘겨도 같은 값을 지정할 수 있습니다. 여기서 ID는 분석을 위해 고른 IPv4 필드입니다. 연결 번호나 로그의 사건 번호가 아닙니다.

주소는 따옴표 안의 문자열이고 53000과 5514는 정수입니다. b"LAB-OK"의 앞 b는 문자열 모양을 바이트로 쓴다는 뜻입니다. 이 예제의 ASCII 여섯 문자는 각각 한 바이트라 길이도 6바이트입니다. 사람이 보는 글자 수와 인코딩한 바이트 수는 문자가 달라지면 달라질 수 있습니다. 탐지의 위치와 길이는 바이트로 계산하세요.

포트에 실수로 "5514"처럼 따옴표를 붙였다고 가정해 볼까요? 숫자가 똑같아 보여도 Python에서는 자료형이 다릅니다. 어떤 필드는 대입할 때 검사하고, 어떤 필드는 실제 바이트를 만들 때 예외를 드러냅니다. 오류가 나타나는 정확한 시점은 필드와 버전의 구현에 달려 있습니다. 필드 설명에서 타입을 확인하고, bytes(...)로 직렬화해 보고, 다시 해석한 결과의 값을 비교하는 순서가 도움이 됩니다.

5. 바깥 헤더부터 데이터까지 쌓습니다

Scapy에서 객체 사이의 /는 여기서 나눗셈을 하지 않습니다. 왼쪽 계층 안에 오른쪽 계층을 넣는 표현입니다. 이번 구조는 Ether()/IP()/UDP()/Raw()입니다. 이 순서는 이전 강의의 캡슐화와 같습니다. 바깥 Ethernet이 안쪽 IPv4의 종류를, IPv4의 proto가 안쪽 UDP의 종류를 가리킵니다. 라이브러리는 지정된 계층을 조립할 수 있지만, 조립이 가능하다는 사실로 순서가 의도와 일치하는지까지 판정할 수는 없습니다.

예제에는 VLAN 태그와 IPv4 옵션을 넣지 않았습니다. Ethernet 헤더 14바이트에 IPv4 헤더 20바이트를 더하면 UDP 시작은 오프셋 34입니다. UDP 헤더 8바이트를 지나면 데이터는 프레임 오프셋 42에서 시작합니다. UDP 데이터만 따로 읽는 규칙에서는 바로 이 자리가 오프셋 0입니다. 같은 첫 글자도 어느 시작점을 기준으로 세느냐에 따라 숫자가 달라집니다.

Scapy에서 만든 48바이트는 데이터와 세 헤더를 합한 저장 표본입니다. 선 위의 기본 Ethernet 프레임 길이를 이 숫자로 판단할 수는 없습니다. 예를 들어 14바이트 헤더와 4바이트 FCS를 가정한 기본 Ethernet에서 데이터 영역의 최소값 46바이트를 채우려면, IP 전체 34바이트에 46 − 34 = 12바이트의 채움이 필요합니다. 이렇게 계산한 14 + 46 + 4 = 64바이트와 파일에 조립한 바이트를 구분하세요. 실제 수집에는 FCS와 채움이 보이는지, 링크 유형이 무엇인지도 확인합니다.

6. 다섯 표본을 파일로 쓰고 다시 확인합니다

아래 코드를 빈 작업 폴더에서 실행하면 signature-check.pcap이 생깁니다. wrpcap은 파일에 쓰는 함수이며 이 입력에는 명시한 Ethernet 주소를 사용합니다. 실습 파일의 수집 시각도 고정해 같은 예제를 반복할 때 비교하기 쉽게 만들었습니다.

from scapy.all import Ether, IP, UDP, Raw, rdpcap, wrpcap

cases = [(5514, b"LAB-OK"), (5514, b"LAB-NO"),
         (5514, b"XLAB-OK"), (5515, b"LAB-OK"),
         (5514, b"LAB-OK:2")]
frames = []

for index, (port, data) in enumerate(cases):
    frame = (
        Ether(src="02:00:00:00:00:0a", dst="02:00:00:00:00:14")
        / IP(src="192.0.2.10", dst="198.51.100.20", id=314 + index, ttl=64)
        / UDP(sport=53000, dport=port)
        / Raw(load=data)
    )
    frame = Ether(bytes(frame))
    frame.time = 1_700_000_000 + index
    frames.append(frame)

filename = "signature-check.pcap"
wrpcap(filename, frames)
saved = rdpcap(filename)

for frame in saved:
    print(frame[IP].id, frame[UDP].dport, frame[UDP].len, bytes(frame[UDP].payload))

cases에는 포트와 데이터의 쌍을 넣었습니다. enumerate는 0에서 시작하는 index를 각 쌍에 붙이며 314 + index는 표본을 식별할 숫자입니다. bytes(frame)은 계층을 실제 바이트 순서로 조립하고, Ether(...)로 그 바이트를 Ethernet부터 다시 해석합니다. frames.append는 조립한 표본을 목록 끝에 넣습니다. frame.time은 캡처 레코드에 저장할 시각이며 IPv4나 UDP의 헤더 필드가 아닙니다.

rdpcap은 디스크에 저장한 결과를 다시 읽습니다. frame[UDP]는 해석 결과에서 UDP 계층을 고르고, .payload는 그 계층 안쪽 데이터를 가리킵니다. 마지막 print는 IP 식별자·목적지 포트·UDP 길이·데이터를 보여 줍니다. 저장 파일의 이더넷 주소와 표시된 IP/UDP 필드도 분석기에 열어 대조할 수 있습니다. 규칙을 맡은 도구를 실행하기 전에 입력 파일이 기대한 구조로 읽히는지부터 확인하는 습관입니다.

Scapy 2.5.0에서 이 코드를 실행해 확인한 첫 줄은 314 5514 14 b'LAB-OK'입니다. 314로 기본 표본을 찾고, 목적지 포트 5514와 UDP 길이 14, 실제 데이터 여섯 바이트를 차례로 읽습니다. 길이 14는 다음 절에서 헤더와 데이터로 나눠 검산하겠습니다.

7. 객체에서 보인 값과 저장된 값을 구별합니다

만든 직후의 객체에서 길이나 체크섬이 None으로 보이더라도, 도구가 직렬화 과정에서 값을 채우도록 남겨 둔 필드일 수 있습니다. show()는 현재 객체를 계층별로 보여주고 show2()는 조립한 결과를 해석해서 보여 줍니다. 파일에 어떤 값이 실제로 들어갔는지 기록하려면 저장 후 다시 읽은 바이트와 필드를 기준으로 삼으세요.

기본 표본을 손으로 검산해 봅시다. UDP 길이는 자체 헤더 8 + 데이터 6 = 14바이트입니다. IPv4의 Total Length는 IPv4 헤더 20 + UDP 전체 14 = 34바이트입니다. Ethernet의 type은 IPv4를 가리키는 0x0800이고, IPv4의 proto는 UDP인 17입니다. UDP 헤더 안의 Length는 전체 프레임 길이가 아니라 UDP 시작 위치부터의 구간을 나타냅니다.

위치 변경 표본은 앞에 X 한 바이트를 붙였습니다. UDP 길이가 15바이트, IPv4 전체가 35바이트로 늘고, L은 UDP 데이터 오프셋 1로 이동합니다. 뒤에 :2를 붙인 표본은 UDP 길이가 16, IPv4 전체가 36으로 늘지만 L은 오프셋 0에 그대로 있습니다. 이처럼 패킷 길이 변화와 탐지 범위 변화가 꼭 같이 움직이지는 않습니다.

8. 한 줄 규칙을 머리말과 옵션으로 읽습니다

Snort 3 규칙 예시입니다. 보호 구간을 뜻하는 설정 변수를 도입하기 전에 가상의 주소와 포트를 직접 써서 모든 조건이 보이도록 했습니다. 교육 예제의 식별자가 실제 규칙 모음의 식별자와 충돌하지 않도록, 운영 환경에서는 팀의 배정 기준을 따르세요.

alert udp 192.0.2.10 any -> 198.51.100.20 5514 (msg:"LAB offline marker prefix"; content:"LAB-OK",offset 0,depth 6; sid:1000040; rev:1;)

alert는 일치하면 경보를 기록하도록 하는 동작이고, udp는 프로토콜 조건입니다. 화살표 왼쪽은 출발 주소와 포트입니다. any로 출발 포트를 제한하지 않았습니다. 오른쪽은 목적 주소와 포트입니다. 괄호 안의 msg는 사람이 읽을 경보 설명, sid는 규칙 식별자, rev는 그 규칙의 개정 번호입니다. 세미콜론은 옵션을 구분하고, content 뒤 쉼표는 이 콘텐츠 비교에 붙는 수식어를 구분합니다.

content:"LAB-OK"는 여섯 바이트를 비교합니다. offset 0은 이 규칙의 검사 버퍼 맨 앞에서 시작하라는 뜻이고 depth 6은 그 시작점에서 검사할 범위를 여섯 바이트로 제한합니다. 이 UDP 예제에서는 기본 패킷 데이터 버퍼를 대상으로 설명합니다. HTTP처럼 규칙이 특정 해석 버퍼를 선택하면 기준점이 달라집니다. 이 줄은 Snort 3 문법을 기준으로 작성했으므로, 다른 엔진이나 버전에 그대로 옮길 때는 옵션 형식과 버퍼의 선택 기준을 제작사 문서에서 확인하세요.

왜 위치 변경 표본은 빠질까요? 그 표본의 첫 여섯 바이트는 XLAB-O입니다. 전체 데이터 안에 LAB-OK가 있어도, 지금 검사할 여섯 자리에는 그대로 들어오지 않습니다. 뒤에 문자를 붙인 표본의 첫 여섯 바이트는 그대로 LAB-OK입니다. 메시지 전체가 여섯 바이트인 경우만 원했다면 별도의 길이 조건이 필요합니다. 다시 말해 요구사항이 바뀌면 기대 표와 규칙을 함께 고칩니다.

기본 표본을 만들 때 IPv4 ID를 지정했지만 규칙에는 ID 검사가 없습니다. 이 사례에서 ID는 특정 표본을 다시 찾기 위한 표식입니다. 반면 통신 특성에서 TCP 플래그나 순서 번호가 중요하다는 가설을 세웠다면, 어떤 필드를 어떤 조건으로 검사하는지 규칙과 기대 표에 따로 적어야 합니다. 예를 들어 둘째 날에 다룬 TCP 시작 세그먼트의 데이터나 순서 번호 0은 합법적인 문맥에서도 나올 수 있으니, 그 값 하나로 활동의 목적을 판단하지 않습니다.

Snort 3가 설치된 실습 환경에서 확인할 때는 위 규칙을 local.rules에 저장하고, 같은 폴더에 생성한 표본을 아래처럼 오프라인으로 읽습니다. 이 명령의 엔진 결과는 이번 글에서 재현하지 않았습니다.

snort -R local.rules -r signature-check.pcap -A alert_fast

-R은 추가할 규칙 파일, -r은 읽을 캡처 파일, -A alert_fast는 짧은 텍스트 경보 출력 방식입니다. 설치에 따라 별도 snort.lua가 필요하면 -c에 그 설정 파일을 지정합니다. 실습용 설정에서 종료 상태와 읽은 패킷 수, 해당 sid의 경보를 확인하세요. 처음과 마지막 표본이 예상한 일치 후보입니다. 다른 규칙이 함께 로드되면 추가 경보가 생길 수 있으므로, 전체 경보 수를 이 규칙 하나의 결과로 세지 않습니다.

9. 검산, 엔진 결과, 운영 결론의 근거를 남깁니다

세 가지 확인을 따로 적어 두면 팀원이 같은 실험을 반복할 수 있습니다. 첫째, 파일에서 기대한 바이트·길이·방향이 읽히는지 확인합니다. 둘째, 센서나 엔진이 같은 파일을 오프라인으로 읽었을 때 해당 규칙을 실제로 평가했는지 확인합니다. 이때 엔진 버전, 설정, 규칙 파일, 경보 출력 위치를 함께 기록하세요. 규칙 식의 집합을 Python에서 계산한 결과는 두 번째 단계의 근거가 될 수 없습니다.

셋째, 운영 데이터에서 비슷한 경보가 났다면 애초에 어떤 버퍼를 비교했는지, 필요한 방향이 파일에 들어왔는지 확인합니다. 예를 들어 방화벽 안쪽에서는 192.0.2.10으로 보인 주소가 바깥쪽에서는 주소 변환 때문에 달라질 수 있습니다. 복호화되지 않은 통신에서는 비교할 앱 문자열이 보이지 않을 수 있고, 패킷을 짧게 저장하면 검사할 데이터가 빠질 수 있습니다. TCP 내용 탐지에서는 세그먼트 여러 개의 재조립 여부도 결과에 영향을 줍니다.

경보를 받았다면 원본 레코드의 값, 수집 방향과 시각, 해당 규칙 버전을 기록하세요. 업무용 메시지인지 알고 싶으면 그 시각의 단말 프로세스와 송신 기록, 서버가 처리한 요청 로그, 필요하면 방화벽의 주소 변환 기록을 확인합니다. 경보가 없었다면 우선 예상한 긍정 표본을 엔진이 읽고 있는지를 확인하고, 그래도 결과가 다르면 포트, 기준점, 유효 길이, 로드한 구성부터 좁혀 가면 됩니다.

공급사의 규칙 묶음은 출발점입니다. 조직 고유의 메시지 형식과 수집 위치는 해당 환경의 표본으로 확인해야 합니다. 검증이 끝난 표본과 기대 결과를 팀의 규칙 기록에 함께 남기면, 엔진이나 설정을 바꿀 때 같은 조건을 다시 시험할 수 있습니다.

이번 확인 범위. Scapy 2.5.0으로 다섯 가상 프레임을 조립하고 파일을 다시 읽었습니다. 별도의 바이트 검사로 길이, IPv4·UDP 체크섬, 규칙 조건의 기대 집합을 확인했습니다. Scapy 2.7.0은 검증 환경에서 초기화가 막혔습니다. Snort·Suricata 경보 엔진 실행, 실제 센서 수집, IPS 처리 결과는 확인 범위 밖입니다. 다음 강의에서는 저장한 캡처를 다시 읽고, 변경 전후 바이트와 체크섬을 대조하겠습니다.

복습 · 결과를 예측한 뒤 해설을 비교해 보세요

1. 화면에서 IP 목적지와 Ethernet 목적지를 둘 다 보았습니다. 어떤 값이 규칙의 주소 조건에 들어갈까요?

이 예제의 UDP 규칙에는 IPv4의 목적지가 들어갑니다. Ethernet 목적지는 링크 계층의 주소입니다. 둘 다 프레임에 있어도 의미와 쓰는 단계가 다릅니다.

2. IPv4에 4바이트 옵션을 넣으면 데이터 위치는 어떻게 바뀌나요?

Ethernet 14 + IPv4 24 + UDP 8 = 프레임 오프셋 46입니다. IPv4 헤더가 4바이트 늘어 프레임 기준 위치도 4바이트 움직입니다. UDP 데이터를 기준으로 한 첫 글자의 위치는 여전히 0입니다.

3. LAB-OK:2가 일치하면 규칙이 잘못된 건가요?

현재 요구사항은 접두부 일치입니다. 처음 여섯 자리만 비교하므로 의도한 결과입니다. 넓은 기준 때문에 운영에서 원치 않는 일치가 많다면, 앱 구조나 메시지 길이처럼 업무상 필요한 조건을 다시 정의해 검증합니다.

4. UDP 길이 필드가 14이면 데이터가 몇 바이트인가요?

UDP 길이는 8바이트 자체 헤더를 포함하므로 선언된 데이터는 14 − 8 = 6바이트입니다. 저장 파일이 잘렸다면 선언한 만큼 실제 확보했는지도 확인합니다.

5. 표본이 규칙에 맞는다고 계산했는데 경보 파일이 비어 있습니다. 어디부터 확인하나요?

오프라인 엔진이 파일과 규칙을 실제로 읽었는지 먼저 확인합니다. 그다음 출력 위치·버퍼·주소 방향·포트를 확인하세요. 입력 바이트 검산은 장비 안의 규칙 로드나 경보 기록까지 보장하지 않습니다.

6. 같은 안내 문구가 실제 캡처에서도 보였습니다. 어떤 자료가 더 필요할까요?

우선 관측한 문자열과 규칙 조건을 적습니다. 단말에서 어떤 프로세스가 보냈는지, 서버에서 같은 시각에 처리한 요청이 있는지, 방화벽이나 센서가 어느 방향을 봤는지 확인하면 활동 목적과 영향에 대한 판단을 좁힐 수 있습니다.
