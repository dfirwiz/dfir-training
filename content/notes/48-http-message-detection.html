학습 범위

셋째 날 9강에서는 HTTP/1.1의 요청과 응답이 어디에서 나뉘는지 읽고, 같은 문자열을 검색해도 필드와 방향에 따라 결론이 달라지는 이유를 살펴봅니다. 모든 메시지와 규칙은 독립적인 가상 예입니다.

1. 경보에 경로가 보이면 그 주소로 요청했다고 말할 수 있을까요?

운영팀이 /health/ready 요청을 조사하는데 검색 결과에 그 글자가 백 번 나왔다고 해 볼게요. 응답으로 내려온 안내 페이지에도 같은 문자열이 들어갈 수 있습니다. 우선 어떤 기록이 클라이언트가 보낸 요청인지, 어떤 기록이 서버가 돌려준 응답인지 갈라야 실제 호출 수를 셀 수 있습니다.

병원 접수 창구의 신청서에 비유해 보죠. 환자가 적은 방문 목적과 창구가 적은 처리 결과는 같은 종이에 나와도 의미가 다릅니다. HTTP에서는 하나의 연결 위에 요청과 응답이 여러 번 오갈 수 있고, 기존 연결을 그대로 사용해도 매 요청마다 별도의 의미를 가집니다. 쿠키나 토큰을 써 로그인 상태를 이어가는 일은 애플리케이션이 맡습니다. 따라서 “같은 TCP 연결이다”와 “같은 사용자 작업이다”는 별개로 입증해야 합니다.

2. 시작줄과 빈 줄을 기준으로 요청과 응답을 읽습니다

왼쪽이 클라이언트 192.0.2.32, 오른쪽이 서비스 198.51.100.40인 평문 실험을 가정합니다. 화면에서 보이는 줄 끝은 실제 HTTP/1.1에서 CRLF라는 2바이트 줄바꿈입니다. CR(캐리지 리턴)과 LF(라인 피드)를 한 번씩 씁니다. 아래 요청은 헤더 뒤의 빈 줄에서 끝나며, 응답의 본문은 개행을 포함하지 않은 ASCII OK 두 바이트입니다. 코드 상자의 줄바꿈은 읽기 위한 표시입니다.

GET /health/ready?format=plain HTTP/1.1
Host: status.example
Accept: text/plain
Accept-Encoding: gzip

첫 줄은 메서드, 요청 대상, 메시지 버전을 공백으로 나눕니다. GET은 리소스의 표현을 요청합니다. POST는 대상 리소스에 본문 처리를 요청하고 PUT은 지정 대상의 상태를 보내는 표현으로 만들거나 바꾸도록 요청합니다. 이 예제의 /health/ready는 경로이고, 물음표 뒤의 format=plain은 질의입니다. HTTP/1.1의 Host는 같은 주소를 쓰는 서비스 중 요청받을 이름을 전달합니다. Accept는 받아들일 미디어 유형, Accept-Encoding은 받을 수 있는 콘텐츠 인코딩 값을 알립니다. 서버가 실제로 gzip을 썼는지는 응답을 확인해야 합니다.

HTTP/1.1 200 OK
Content-Type: text/plain
Content-Length: 2

OK

응답의 첫 줄은 버전, 3자리 상태 코드, 사람이 읽는 이유 문구로 구성됩니다. 자동 해석의 기준은 숫자 200입니다. Content-Type은 본문의 미디어 유형, Content-Length는 이 경우 본문의 바이트 수입니다. ASCII에서 O 1바이트와 K 1바이트를 더해 2입니다. 빈 줄은 헤더를 끝내므로 이 두 바이트에 포함되지 않습니다. Content-Encoding: gzip 응답이라면 전송 중 콘텐츠는 압축된 형태이며, 평문 내용으로 비교하려면 분석기의 압축 해제가 가능한지와 한도를 확인해야 합니다.

언제나 헤더에 적힌 길이를 읽으면 될까요? HTTP/1.1에서는 청크 단위 전송 코딩이 메시지 끝을 정할 수 있고, HEAD 응답이나 204·304 응답은 본문이 없습니다. 특히 HEAD의 헤더에 나오는 길이는 대응하는 GET의 표현 길이일 수 있습니다. 연속 요청을 처리할 때도 “빈 줄 이후부터 연결 끝까지가 같은 본문”이라고 가정하면 경계를 잘못 짚게 됩니다.

3. 상태 코드는 응답의 종류를 알려 줍니다

상태 코드 첫 자리와 조사에서 확인할 점
범위가상 예해석의 출발점
1xx 안내100 Continue중간 응답입니다. 뒤따르는 최종 응답을 확인합니다.
2xx 성공200 OK, 204 No Content서버가 이 요청을 성공으로 응답했습니다. 후속 업무 결과는 서비스 로그와 대조합니다.
3xx 추가 조치302 Found, 304 Not Modified302의 Location은 이동 후보입니다. 304는 보관된 표현의 재사용을 알립니다.
4xx 요청 관련 오류401, 403, 404인증 정보 요구, 접근 거절, 리소스 미발견 등 이유를 나눕니다.
5xx 서버 관련 오류500, 502애플리케이션 자체 오류인지 중계 서버가 받은 상위 응답 문제인지 살핍니다.

응답을 302로 바꾸고 Location: https://status.example/maintenance가 추가됐다고 해 보죠. 이동 대상이 제시되었다는 점은 관측할 수 있지만, 어떤 클라이언트가 실제로 따라갔는지 알려면 다음 요청과 그 응답을 찾아야 합니다. 200 응답도 화면에 뜬 정상 페이지, 중계 캐시가 돌려준 응답, 업무 처리 결과 등 상황이 다를 수 있습니다. HTTP 상태와 애플리케이션의 처리 성공을 구분해 기록합니다.

4. 패턴, 프로토콜 필드, 행동 통계로 서로 다른 질문을 합니다

문자열 비교는 검사 영역 어딘가에 바이트가 있는지 알려 줍니다. 프로토콜 디코딩은 응용 규약을 따라 메시지를 나누고 경로인지 본문인지 위치를 설명합니다. 행동 기반 검사는 특정 서비스의 요청·오류 비율이나 연결 수가 평소와 달라졌는지 봅니다. 셋을 같이 쓰면 “필드에서 정확히 무엇을 봤고, 얼마나 달라졌으며, 원인을 알려면 무엇이 필요한가”를 나눌 수 있습니다. 합성 표본 20건 중 502가 4건이라면 4 ÷ 20 × 100 = 20%입니다. 분모가 요청인지, 재시도를 포함한 응답인지, 시간과 서비스가 평소 표본과 같은지 확인하세요.

아래는 Snort 3의 요청 필드 조건을 설명하는 옵션 조각입니다. 세미콜론 앞의 http_method와 http_uri:path는 뒤에 나오는 비교가 사용할 버퍼를 바꿉니다. :path는 정규화된 URI 중 경로만 고르고 질의는 제외합니다. offset 0,depth 3은 처음 세 바이트에서 GET을 확인하는 예제입니다. 정확히 메서드 전체가 GET인지 보려면 버퍼 길이도 3으로 제한합니다. bufferlen:3은 현재 버퍼의 바이트 수가 정확히 3이라는 뜻입니다.

http_method; content:"GET",offset 0,depth 3; bufferlen:3;
http_uri:path; content:"/health/ready",offset 0,depth 13; bufferlen:13;

경로의 길이는 / 1 + health 6 + / 1 + ready 5 = 13바이트입니다. bufferlen:13을 뺀다면 /health/ready-old도 접두부 조건에 들어올 수 있습니다. GET /health/ready?format=plain은 경로 조각이 13바이트여서 조건에 들어오고, POST /health/ready는 메서드 조건에서 빠집니다. 응답에서 200을 보려면 상태 코드 버퍼인 http_stat_code를 사용해 별도 방향과 응답 조건을 설계합니다. 같은 문자열이 응답 본문에 나온다는 사실은 요청 경로 조건을 충족시키지 않습니다.

5. 어떤 계층에서 무엇을 볼 수 있는지 적습니다

HTTP는 페이지 외에 API나 파일 전송에도 쓰입니다. 메서드와 포트만 보면 실제 기능을 판단하기 어렵습니다. 요청과 응답을 분리한 뒤, 패킷을 어디서 수집했는지, 재조립에 필요한 데이터가 있었는지, 검사기의 서비스 식별과 본문 검사 깊이가 어땠는지를 기록하세요. TLS가 유지되는 구간에서는 평문 경로·헤더·본문을 관측하지 못하는 것이 일반적입니다. 승인된 프록시나 서버에서 이미 남은 정상 로그, 상태·시간·요청 식별자, 종단 프로세스 기록을 맞춰 조사 범위를 좁힙니다.

조사 메모의 문장을 세 개로 나눠 보세요. 관측은 “프록시에서 특정 시간에 GET과 해당 경로 및 302를 확인했다”입니다. 가설은 “점검 서비스가 유지보수 응답을 보냈다”입니다. 추가 확인은 “서버의 라우팅 로그와 클라이언트의 후속 요청으로 실제 이동 여부를 확인한다”입니다. 서비스 포트, 본문 속 단어, 응답 부재 하나만으로 성공이나 실패를 확정하지 않습니다.

복습과 해설

1. 응답의 글자 OK와 상태 코드 200 중 코드 해석 기준은 무엇인가요?
3자리 숫자인 200입니다. 사람이 읽는 문구는 처리 결과를 판정할 기준으로 쓰지 않습니다.
2. /health/ready-old가 들어오기 시작하면 어떤 조건을 살펴보나요?
접두부 13바이트만 비교하는지, 경로 버퍼의 길이도 13으로 확인하는지 봅니다. 질의가 붙어도 경로만 선택한 버퍼에서는 별개입니다.
3. 302와 이동 주소를 찾았으면 이동까지 증명했나요?
이동 지시를 본 것입니다. 같은 클라이언트가 새 요청을 냈는지와 그 응답을 찾아야 이동을 확인할 수 있습니다.
4. 502 비율만 올랐다면 감염으로 기록할 수 있나요?
그 비율은 변화의 단서입니다. 동일한 집계 범위에서 재시도, 서버 장애, 배포, 상위 프록시 상태를 확인합니다.
5. TLS 캡처에서 URI가 보이지 않으면 어떻게 이어가나요?
그 센서가 평문을 볼 수 있었는지 확인하고 승인된 구간의 프록시·서버 로그와 수집 시간·연결 정보를 맞춥니다.

공식 자료와 확인일

2026-11-20에 RFC 9110의 HTTP 의미와 상태 코드, RFC 9112의 HTTP/1.1 메시지, Snort 3의 메서드, URI, 응답 상태 코드 및 버퍼 길이를 확인했습니다. 예제의 바이트와 조건은 독립 검산했으며 탐지 엔진은 실행하지 않았습니다.
