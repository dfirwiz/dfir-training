1. 발견한 패킷을 통신의 문맥 안에서 읽기

가상의 상황부터 이어 볼까요? 검색에서 filename=notice.pdf를 찾았습니다. 이제 “문서를 받았다”고 보고해도 될까요? 아직은 그 문자열이 어느 방향의 어느 메시지에 있었는지 모릅니다. 요청의 매개변수일 수도, 서버가 제안한 파일명일 수도, 데이터 안의 우연한 문자열일 수도 있죠. 이번에는 발견한 바이트를 관련 대화로 되돌려 놓아 의미를 확인합니다.

잘게 나뉜 편지를 봉투에서 꺼내 문장 순서대로 맞추는 일을 생각해 보세요. 조각 하나에 ‘승인’이라고 적혀 있어도 앞에 ‘미’가 있으면 의미가 달라집니다. TCP 스트림을 읽는 이유도 앞뒤와 방향을 확인하기 위해서입니다. 다만 실제 TCP는 편지 조각의 도착 순서만 따르지 않고 바이트 위치와 연결 상태를 사용합니다. 빠진 조각을 도구가 자동으로 만들어 내거나, 실제 수신 프로그램이 어떻게 처리했는지까지 보증하는 것도 아닙니다.

7강에서는 파일 속성과 통계로 상세 조사할 통신을 골랐습니다. 이번에는 그 통신의 내용을 여러 패킷에 걸쳐 읽습니다. 패킷 하나에 의심스러운 파일명이 보이더라도, 그것이 클라이언트의 요청인지 서버의 응답인지, 본문인지 헤더인지 알아야 의미를 설명할 수 있습니다.

이때 필요한 기능이 Follow TCP Stream입니다. TCP 스트림은 한 연결에서 전달되는 바이트의 흐름입니다. 응용 메시지가 여러 TCP 세그먼트에 나뉘거나 한 세그먼트에 여러 메시지가 들어갈 수 있으므로, 개별 패킷만 읽는 방식으로는 메시지의 앞뒤를 놓치기 쉽습니다. 스트림을 따라가면 관련 데이터를 순서와 방향에 맞춰 읽는 데 도움이 됩니다.

하지만 화면에 이어졌다는 이유로 실제 수신 프로그램의 처리 결과까지 확정되지는 않습니다. 수집 누락, 연결 중간부터의 캡처, 재조립 정책과 암호화가 해석에 영향을 줍니다. 자료를 이어 읽는 기능과 사건의 결과를 입증하는 일을 구별하면서 진행하겠습니다.

2. 선택한 패킷에서 Follow TCP Stream으로 들어가기

관심 TCP 패킷을 목록에서 선택한 뒤 Analyze → Follow → TCP Stream을 사용합니다. 패킷 목록의 우클릭 메뉴에서 Follow 항목으로 들어갈 수도 있습니다. 여기서 고른 패킷은 해당 연결로 들어가는 출발점입니다. 반드시 연결의 첫 패킷을 선택해야 하는 것은 아닙니다. [1]

가령 같은 TCP 연결의 패킷 120, 123, 127에 나뉜 데이터가 있다고 가정해 보겠습니다. 123번에서 시작해도 그 연결의 관련 데이터를 대상으로 스트림을 볼 수 있습니다. 반면 무관한 연결의 패킷을 선택하면 다른 대화가 열립니다. 표시된 종단 주소·포트와 스트림 번호를 먼저 확인하는 습관이 필요합니다.

TCP는 바이트 위치를 시퀀스 번호로 추적하므로 스트림을 재조립할 때는 단순한 캡처 도착 순서대로 문자열을 붙이는 것보다 더 많은 처리가 필요합니다. 재전송된 같은 바이트를 중복된 새 응용 데이터로 읽지 않아야 하고, 빠진 범위나 충돌하는 값도 검토해야 합니다. 5강에서 배운 센서와 수신 구현의 재조립 차이도 여전히 관련됩니다.

예전 설명에서 tcpdump를 ‘개별 패킷’, Wireshark를 ‘스트림’으로 대비한 것은 작업 방식의 차이를 강조한 것입니다. tcpdump로도 관련 패킷을 필터링하고 흐름을 조사할 수 있습니다. 여기서 Wireshark의 장점은 대화형으로 재조립된 양방향 데이터를 읽고 관심 위치로 다시 돌아가기 편리하다는 점입니다. 어느 도구 이름도 분석의 정확성을 자동으로 보증하지 않습니다.

UDP에도 Follow 기능이 있습니다. 관련 데이터그램을 읽기 좋게 모아 보는 기능이지 UDP에 TCP와 같은 전달·순서 보장을 추가하는 것은 아닙니다. 응용 메시지의 경계와 복구 기능은 해당 상위 프로토콜의 규칙까지 확인해야 합니다. [1]

패킷 번호와 바이트 위치는 다른 번호입니다

패킷120·123·127이라는 숫자는 현재 파일에서 고른 기록을 찾아가는 참조입니다. TCP 시퀀스 번호는 한 방향 데이터의 바이트 위치를 추적하는 값입니다. 패킷 번호가3씩 늘었다고 데이터가3바이트씩 이동한 것은 아닙니다. 관련 없는 다른 통신의 기록이 사이에 들어갈 수도 있으므로 기록 순서와 스트림의 위치를 구별하세요.

Follow는 선택 패킷이 속한 연결을 기준으로 읽는 기능입니다. 연결의 중간 패킷에서 열어도 앞부분이 파일에 있으면 함께 검토할 수 있지만, 파일에 없는 연결 시작이나 응용 데이터를 새로 복구하는 것은 아닙니다. 먼저 주소·포트·방향·연결 식별과 수집 범위를 맞춘 뒤, 재조립된 데이터와 관련 원래 패킷을 오가며 확인합니다.

같은 바이트의 재전송을 새 내용으로 두 번 붙이면 메시지가 달라질 수 있습니다. 반대로 같은 위치의 다른 바이트가 오면 어떤 값을 채택했는지 검토해야 합니다. 스트림은 전송된 모든 패킷의 페이로드를 무조건 나열한 것과 다릅니다. 현재 도구의 재조립 결과와 실제 수신 결과가 같다고 판단하려면 수집·설정·대상 구현의 조건까지 확인해야 합니다.

3. 양방향과 한쪽 방향을 구분해 읽는다

Follow 창의 Entire conversation은 양쪽 방향을 함께 보는 선택입니다. 필요하면 클라이언트 → 서버 또는 서버 → 클라이언트만 골라 읽습니다. 클라이언트는 해당 연결에서 통신을 시작하는 쪽, 서버는 그 연결을 받아 서비스를 제공하는 쪽이라는 문맥으로 먼저 이해하면 됩니다. 한 장비가 모든 통신에서 언제나 같은 역할을 갖는 것은 아닙니다.

기본 색상은 방향을 구분하는 보조 수단입니다. 현재 공식 문서는 클라이언트 → 서버를 빨강, 반대 방향을 파랑으로 설명하면서 테마에 따른 색 설정도 명시합니다. 원문의 한쪽 방향 선택 설명에는 이 색상 대응이 뒤바뀐 부분이 있으므로 그대로 외우지 않습니다. 실제 주소·포트와 선택한 방향, 요청·응답의 의미를 함께 확인하세요. [1]

원문의 첫 스트림은 메일 전달 프로토콜인 SMTP 대화입니다. 다음은 원래 주소와 계정을 쓰지 않고 새로 만든 예시입니다. 주소는 예시 도메인을 사용하며, 화면의 줄바꿈은 실제 프로토콜의 CRLF 구분을 읽기 좋게 표현한 것입니다.

서버 → 클라이언트: 220 mail.example ESMTP
클라이언트 → 서버: EHLO sender.example
서버 → 클라이언트: 250-mail.example
서버 → 클라이언트: 250 SIZE 1000000
클라이언트 → 서버: MAIL FROM:<sender@example.org>
서버 → 클라이언트: 250 OK
클라이언트 → 서버: RCPT TO:<recipient@example.net>

220은 SMTP 서비스 준비 응답이고 EHLO는 클라이언트가 자신을 알리면서 확장 기능을 확인하는 명령입니다. 250 계열은 요청 동작에 대한 성공 응답이며, 250-처럼 하이픈이 있으면 여러 줄 응답의 중간 줄일 수 있습니다. MAIL FROM은 SMTP 봉투의 발신자를, RCPT TO는 봉투의 수신자를 지정합니다. 이 값만으로 실제 작성자의 신원을 인증한 것은 아닙니다. [2]

원문 화면에는 SIZE·PIPELINING·VRFY·ETRN 등 서버의 확장 기능 알림도 있습니다. 이번 학습의 초점은 각 확장 기능의 전체 명세가 아니라, 서버의 알림과 클라이언트 명령이 주고받는 대화라는 것을 알아보는 데 있습니다. 예시도 본문 전송과 최종 수락까지 보여 주지 않으므로 수신함 도착이나 사용자의 읽기·클릭까지 확인했다고 말할 수 없습니다.

ASCII는 이런 텍스트 기반 대화를 읽는 데 적합합니다. 표시할 수 없는 데이터는 점으로 보일 수 있으며, 점이 실제 원시 바이트가 0x2E라는 뜻은 아닐 수 있습니다. 바이너리 데이터는 Hex Dump 등 적절한 형식으로 대조합니다. 표시 형식의 변화와 실제 데이터의 변화를 구분해야 합니다.

SMTP의 응답은 어느 단계에 대한 응답일까요?

SMTP는 Simple Mail Transfer Protocol, 즉 메일 전달 프로토콜입니다. 먼저 서버의220 준비 응답을 보고 클라이언트가 EHLO로 대화를 시작하는 흐름을 읽습니다. EHLO는 확장 SMTP 기능을 확인하는 인사 명령이며, ESMTP는 그 확장된 동작을 가리키는 표현입니다. 이 대화는 사용자가 웹메일 화면에서 편지를 작성한 기록과 같은 종류의 자료가 아닙니다.

예시에서 MAIL FROM:<sender@example.org>의 꺾쇠 안 주소는 SMTP 봉투의 발신 주소입니다. RCPT TO는 이 전송에서 받을 봉투 주소를 지정합니다. 메시지 본문 안의 From·To 표시와 봉투는 서로 다른 부분이며, 봉투 주소만으로 실제 작성자를 인증한 것은 아닙니다. 계정 인증과 실제 작성·수신·사용자 열람은 별도의 증거가 필요합니다. [2]

또 MAIL FROM 뒤의250 OK는 그 단계의 동작에 대한 응답입니다. 예시에는 RCPT TO 뒤의 응답과 본문 전송·최종 수락이 없으므로 “메일 전달 완료”로 늘려 쓰지 않습니다. 서버의 SIZE 기능 알림도 허용 크기 같은 기능 정보를 나타내는 것이지, 그 숫자만큼의 파일이 실제 전달되었다는 뜻은 아닙니다. PIPELINING 같은 확장 알림 전체를 이번에 외우기보다, 어떤 쪽이 기능을 알리고 어떤 명령에 답하는지부터 봅니다.

CRLF는 Carriage Return과 Line Feed라는 두 제어 문자의 조합으로, 이 텍스트 프로토콜에서 줄의 끝을 나타냅니다. 읽기 쉬운 화면 줄바꿈과 원래 바이트는 구분해야 합니다. ASCII는 문자를 숫자 코드에 대응시키는 체계이며, 인쇄 가능한 문자만 보고 바이너리 바이트 전체를 읽었다고 생각하면 안 됩니다.

4. Follow를 닫아도 이전 필터가 남을 수 있다

Follow를 실행하면 Wireshark가 해당 스트림에 맞는 표시 필터를 적용합니다. 가령 tcp.stream eq 0은 현재 파일에서 도구가 0번으로 식별한 TCP 스트림을 고르는 표현입니다. tcp.stream == 0처럼 쓰는 표현도 있습니다. 이 숫자는 TCP 헤더에 들어 있는 전 세계 공통 연결 번호가 아닙니다.

스트림 창의 Close는 창을 닫으면서 현재 스트림 필터를 남길 수 있고, Back은 이전 표시 필터를 복원하는 동작입니다. 버전과 UI를 확인하되 ‘창을 닫았으니 모든 패킷이 다시 보인다’고 가정하지 마세요. 상단 필터 입력란과 표시 패킷 수를 확인하고, 전체로 돌아가려면 Clear 버튼으로 조건을 지우고 적용 상태를 확인합니다. [1]

보고서에는 스트림 번호와 패킷 번호를 남기되 원본 파일의 식별 정보, 해시, 버전·설정과 필터도 함께 기록하세요. 파일을 합치거나 일부만 추출하고 다시 읽으면 도구가 매기는 번호가 달라질 수 있습니다. 스트림 0이라는 숫자만 다른 사람에게 전달하면 같은 통신을 재현하기 어려울 수 있습니다.

이전 상태로 돌아가는 것과 전체를 보는 것은 다릅니다

tcp.stream eq 0를 나누어 읽으면 tcp.stream은 도구가 붙인 TCP 스트림 식별 필드, eq는 같다는 비교,0은 찾을 값입니다. ==도 값 비교를 적는 표현입니다. TCP 헤더 안에0번 연결 번호가 적혀 있다는 뜻이 아니므로 다른 파일이나 설정의0번과 자동으로 같은 통신이라고 연결하지 않습니다. [12]

예를 들어 조사 단말 주소만 표시한 상태에서 Follow를 열었다고 해 볼까요? Back으로 돌아오면 이전의 주소 조건이 복원될 수 있습니다. 그러면 “전체 파일로 복귀”한 것이 아니라 “주소로 제한했던 상태로 복귀”한 것입니다. Close로 닫으면 스트림 조건이 남을 수 있습니다. 다음 검색 전에 실제 입력란과 표시 개수를 확인하는 짧은 습관이 검색 실패의 원인을 많이 줄여 줍니다.

표시 필터를 지워도 원래 파일이 이미 추출본이면 제외된 다른 연결은 생기지 않습니다. 또 수집 단계에서 제한했거나 뒤쪽 바이트를 저장하지 않았다면 화면 조건을 바꾸어 복구할 수 없습니다. 지금 열린 파일,그 파일의 원본·파생 관계,표시 필터라는 서로 다른 범위를 확인하세요.

5. Find Packet은 검색할 장소와 방식을 함께 정한다

전체 범위로 돌아온 뒤 Edit → Find Packet 또는 해당 환경의 Ctrl+F로 찾기 도구를 엽니다. 찾기 도구 모음과 표시 필터 입력란은 목적이 다릅니다. 표시 필터는 조건에 맞는 패킷을 화면에 남기고, Find는 조건에 맞는 위치로 이동하는 작업입니다. 둘 다 조건식을 사용할 수 있다고 같은 기능으로 취급하지 마세요. [3]

찾기에는 두 질문이 있습니다. 무엇을 기준으로 찾을 것인가와 어느 표현에서 찾을 것인가입니다. 같은 filename 문자열도 목록의 요약에는 없고 바이트에는 있을 수 있습니다. 기본 설정이 이번 질문에 맞는지 직접 확인해야 합니다.

가상의 단서가 filename=notice.pdf라면 String과 Packet bytes를 선택하는 것이 한 가지 출발점입니다. 대소문자 구분이 필요한지 확인하고, 문자 폭을 고르는 Narrow·Wide·Narrow & Wide 같은 옵션도 살펴봅니다. 단일 바이트 텍스트와 넓은 문자 표현을 구분하는 선택이지 모든 언어·인코딩을 자동으로 해결한다는 뜻은 아닙니다. 단순한 영문 표식도 공백·따옴표·대소문자가 다르면 정확 일치 결과가 달라질 수 있습니다.

검색 기본값을 고정 규칙으로 외우지 않기 · 2026년 11월 2일

원문의 ‘거의 항상 String / Packet Bytes’라는 요령은 당시 파일명 표식 조사에는 유용하지만 모든 질문의 정답은 아닙니다. 필드 조건에는 표시 필터가, 특정 바이트에는 16진수 검색이 더 적절할 수 있습니다. 현재 공식 가이드에는 선택 패킷 내부만 찾는 Find in selected Packet 모드도 설명되어 있습니다. 이 모드는 검색 범위를 해당 패킷의 상세 정보로 제한하므로, 파일 전체를 찾으려는 중 켜져 있지는 않은지 확인합니다. [3]

Help 메뉴나 항목 위의 도움말도 활용하세요. 버전에 따라 도구 모음 배치나 옵션이 달라질 수 있어 과거 화면의 좌표보다 기능 이름과 현재 설명을 기준으로 설정하는 편이 재현하기 좋습니다.

찾을 대상이 문자·바이트·필드 중 무엇인가요?

String은 문자열,Hexadecimal Value는16진수로 적은 바이트 열,Regular Expression은 문자 패턴,Display filter는 해석된 프로토콜 필드 조건이라는 뜻입니다. 예를 들어 영어 파일명 표식 자체를 찾는 것과 HTTP 헤더의 의미를 찾는 것은 같은 질문이 아닙니다. 문자열을 찾았다고 해당 프로토콜의 특정 필드임이 증명되는 것도 아닙니다.

검색 영역도 함께 고릅니다. Packet list는 도구가 만든 요약,Packet details는 해석 트리,Packet bytes는 선택 데이터 소스의 바이트를 대상으로 이해하면 됩니다. 원시 프레임에는 헤더도 있으므로 Packet bytes를 언제나 응용 페이로드라고 부르지 마세요. 서로 다른 영역에서 같은 단서가 다른 모양으로 나타나거나 일부가 표시되지 않을 수 있습니다.

표식을 조금 바꾸어 filename="notice.pdf"라고 쓰면,따옴표 없는 filename=notice.pdf와 실제 문자열이 다릅니다. filename = notice.pdf처럼 공백이 생겨도 정확 일치 검색 결과가 달라질 수 있죠. 대소문자·문자 폭·인코딩과 실제 바이트를 확인한 뒤 적절한 검색 조건을 고릅니다. 유효한 헤더 문법과 문자열 검색의 정확 일치는 별개입니다.

현재의 Find in selected Packet은 한 패킷의 상세 트리 안에서 찾는 모드입니다. 파일 전체의 패킷을 탐색하려는 중 이 모드가 켜져 있으면 질문 자체가 좁아집니다. 공식 문서는 이 모드의 검색 종류가 String과 Regular Expression으로 제한된다고 설명합니다. 버전에 맞는 도움말을 확인하고,모든 검색 옵션 조합이 늘 같은 방식으로 동작한다고 가정하지 않습니다. [3]

6. 못 찾았다는 결과는 무엇을 뜻할까

검색 결과가 없으면 먼저 실패 조건을 나누어 봅니다. 이전 스트림 필터가 남았는지, 목록·상세·바이트 중 맞는 곳을 골랐는지, 선택 패킷 내부 검색으로 제한했는지, 문자열 표기와 인코딩이 맞는지 확인합니다. 그다음 수집 누락·잘림·암호화·다른 연결 가능성을 검토합니다.

문자열이 TCP 세그먼트 경계에서 갈라질 수도 있습니다. 가상 예시로 앞 세그먼트에 filename=not, 다음에 ice.pdf가 있다고 가정하면, 원래 개별 패킷 바이트만 검사하는 검색에서 전체 표식이 안 잡힐 수 있습니다. 두 조각을 재조립해 읽으면 filename=notice.pdf가 됩니다. 이것은 검색할 자료의 단위가 달라지는 문제입니다. [4]

이때 무조건 도구 오류라고 하지 않습니다. 관련 TCP 스트림과 재조립된 데이터, 원래 패킷을 교차 확인합니다. 반대로 재조립 화면의 문자열 하나만 보고 원래 한 패킷에 전부 들어 있었다고 보고해서도 안 됩니다. 패킷 단위 증거와 재구성한 메시지의 관계를 기록해야 합니다.

따라서 신중한 기록은 ‘현재 표시 범위의 원래 패킷 바이트에서 이 문자열을 찾지 못했다’입니다. 모든 파일·모든 경로·복호화한 본문까지 검증하지 않았다면 ‘그 활동은 없었다’로 바꾸지 않습니다. 검색은 가설을 검증하는 한 방법이지 관측 범위 밖을 증명하는 수단이 아닙니다.

검색 실패를 두 단계로 나누어 확인합니다

먼저 선택의 문제를 확인합니다. 잘못된 파일·남은 필터·한 패킷 제한·검색 영역·대소문자·따옴표·공백 때문에 놓쳤을 수 있습니다. 다음에는 자료와 해석의 문제를 봅니다. 수집 시작·종료 시각,한 방향 수집,비대칭 경로,누락·잘림,암호화,재조립·디섹터 설정이 영향을 줄 수 있습니다. 이 둘을 나누면 무조건 검색어만 바꾸거나 도구 오류라고 결론내리는 일을 줄일 수 있습니다.

앞의 두 조각을 길이로 읽어 볼까요? ASCII로 filename=not는12바이트이고 ice.pdf는7바이트입니다. 같은 방향에서 누락 없이 연속했다면 합계19바이트가 filename=notice.pdf를 이룹니다. 각 원래 패킷 안에19바이트 전체가 없더라도 연결해 읽은 데이터에는 표식이 존재할 수 있습니다.

반대로 두 문자열이 다른 연결이나 반대 방향에 있었다면 임의로 붙일 수 없습니다. 같은 파일에서 가까이 보였다는 이유만으로 이어 붙이지 말고,실제 연결·방향·바이트 위치를 확인해야 합니다. 파일 전체의 원시 바이트에서 같은 글자를 발견한 것과 유효한 재조립 메시지 안에서 확인한 것은 다른 근거입니다.

7. 찾은 패킷에서 다시 스트림으로 들어간다

문자열을 찾았다면 해당 패킷이 선택됩니다. 그 위치를 기록하고 우클릭 또는 Analyze 메뉴에서 Follow → TCP Stream으로 들어갑니다. 찾기 → 해당 연결 선택 → 요청·응답 맥락 확인이라는 연결입니다. 발견한 한 줄이 사건의 결론이 아니라 관련 대화로 들어가는 손잡이가 되는 셈입니다.

Follow 창 안의 Find와 Find Next는 현재 스트림의 표시 내용에서 텍스트 위치를 찾는 데 쓰입니다. 메인 화면의 Find Packet과 검색하는 공간이 다르다는 점을 구분하세요. 스트림 선택기 역시 다른 연결로 이동하는 기능이므로, 번호를 바꾼 뒤 이전 통신의 내용처럼 기록하지 않습니다. [1]

찾은 위치는 조사 메모의 닻과 비슷합니다. 패킷 번호·시각·종단과 바이트 위치를 남긴 뒤 Follow 안에서 앞뒤 헤더와 메시지를 읽으면 다른 사람이 같은 자료를 따라가기 좋습니다. 다만 닻 하나가 사건 전체의 위치를 알려 주는 것은 아닙니다. 응답 표식을 찾았으면 그 요청은 무엇이었는지,같은 연결의 다른 메시지와 섞이지 않았는지도 확인하세요.

메인 화면에서 찾는 Find Packet과 스트림 창의 Find는 서로 다른 공간을 검색합니다. 표시 형식이나 방향을 바꾸면 눈에 보이는 텍스트와 검색 범위도 달라질 수 있습니다. “검색 성공”이라고만 적기보다 어느 창·형식·방향·데이터 소스에서 어떤 바이트를 확인했는지 붙이면 근거가 분명해집니다.

8. HTTP 응답의 파일명과 길이는 각각 무엇을 말하는가

다음은 구조를 설명하기 위한 가상의 평문 HTTP/1.1 대화입니다. 실제 서버와 통신한 결과가 아니며 본문 9,000바이트는 제시하지 않은 부분 예시입니다.

클라이언트 → 서버
GET /download?id=notice HTTP/1.1
Host: download.example
User-Agent: ExampleClient/1.0
Accept-Encoding: gzip
Connection: keep-alive

서버 → 클라이언트
HTTP/1.1 200 OK
Content-Type: application/pdf
Content-Length: 9000
Content-Disposition: inline; filename=notice.pdf
Connection: close

[본문은 이 예시에서 생략]

요청의 GET은 자원 조회 메서드이고, Host는 요청 대상 호스트를 나타냅니다. User-Agent는 클라이언트가 자신에 대해 보낸 정보입니다. UA-CPU처럼 CPU 정보를 알리는 추가 요청 헤더가 보이는 경우에도 송신 측이 보낸 주장이라는 점은 같습니다. 그 값만으로 실제 브라우저·운영체제나 공격자의 숙련도를 인증하지는 못합니다. Accept-Encoding은 클라이언트가 받아들일 수 있는 내용 코딩을 알립니다. gzip을 요청에 써 보냈다는 것만으로 이번 응답이 실제 gzip으로 압축되었다고 확정하지 않고 응답의 Content-Encoding 등과 본문을 확인합니다. [5]

정보설명단독으로 확정하지 않을 것

Connection: close이 HTTP/1.1 연결을 계속 유지하지 않겠다는 연결 관리 정보사용자 프로그램 종료나 공격 차단 성공

inline은 일반적인 표시 처리 방식에 관한 값이고, filename은 파일명 제안입니다. 원문 화면에서도 이 표식은 HTTP 서버 응답 헤더에 있습니다. 따라서 같은 표식을 찾았다고 반드시 요청 URL에서 발견했다고 쓰면 안 됩니다. RFC 6266 역시 제공된 파일명을 그대로 신뢰할 사실이 아닌 제안으로 다룹니다. 파일명이 .pdf라고 해서 실제 PDF이거나 무해한 문서라고 결론 내리지 않습니다. [6]

실제 화면에는 Date·Server·X-Powered-By·Accept-Ranges 같은 헤더도 나타날 수 있습니다. Date는 메시지 생성 시각에 관한 서버 측 정보로 캡처 시각과 기준이 다를 수 있습니다. Server와 X-Powered-By는 제품 관련 알림일 수 있지만 그대로 인증된 자산 버전으로 믿지 않습니다. Accept-Ranges: bytes는 바이트 범위 요청 지원에 관한 정보이지 파일의 악성 여부를 알려 주는 값이 아닙니다. 필요한 의미를 공식 명세와 대조하고 실제 바이트·자산 정보로 검증합니다. [5]

요청·응답의 첫 줄과 헤더·본문을 나눕니다

HTTP는 Hypertext Transfer Protocol로 웹에서 요청과 응답을 주고받는 규칙입니다. 이 예시의 요청 첫 줄은 GET이라는 메서드,요청 대상 /download?id=notice,HTTP/1.1이라는 버전으로 읽습니다. 물음표 뒤의 id=notice는 이 가상 서비스가 사용하는 질의 부분이지 실제 다운로드 파일명과 자동으로 같은 값이 아닙니다. Host는 요청 대상 이름을,응답의 첫 줄은 프로토콜 버전과 상태 코드를 나타냅니다.

헤더(header)는 메시지 처리에 필요한 정보를 담는 항목이고,본문(body)은 그 헤더 뒤에 오는 내용입니다. HTTP/1.1 텍스트 예시에서는 빈 줄이 헤더 영역의 끝을 구별합니다. 본문의 안내 문장 [본문은 이 예시에서 생략]은 학습용 생략 표시이며 서버가 보낸 실제 바이트가 아닙니다. 예시의 빈 줄·방향 설명·생략 표시까지 한 덩어리로 세어 실제 응답 길이라고 계산하지 마세요.

Content-Disposition: inline; filename=notice.pdf에서 콜론 앞은 헤더 이름이고,inline은 처리 방식,세미콜론 뒤 filename은 매개변수입니다. 파일명을 제안했지만 실제 저장 위치·최종 이름·형식·실행을 알려 주는 것은 아닙니다. 브라우저가 이름을 바꾸거나 저장하지 않았을 수도 있으므로 응답의 제안과 단말의 결과를 나누어 봅니다. [6]

200 OK는 해당 HTTP 요청의 성공 상태에 대한 정보입니다. 그 응답이 오류 안내 문서나 다른 내용일 가능성,본문이 충분히 확보되지 않은 가능성도 따로 확인해야 합니다. User-Agent·UA-CPU·Server·X-Powered-By 같은 문자열은 송신자가 알린 정보이므로 실제 프로그램·버전·사용자 신원과 일치하는지는 자산·단말·서버 기록으로 검증합니다.

9. 헤더에 적힌 길이와 확보한 내용의 양을 대조한다

앞 예시는 본문을 생략했으므로 Content-Length가 9,000이라고 적혀 있어도 여기에서 9,000바이트를 확보한 것은 아닙니다. 실제 분석에서도 같은 원칙을 적용합니다. 서버가 선언한 값, 캡처에서 확보한 범위, 재조립된 내용과 실제 수신·저장 결과를 각각 나누어 봅니다.

계산을 단순화하기 위해 정상적인 HTTP/1.1 GET 응답이고, Transfer-Encoding과 압축이 없으며 Content-Length 9,000을 기준으로 본문을 읽는 상황이라고 가정하겠습니다. 응답 헤더 뒤에서 본문 3,000바이트만 확보했다면 9,000 - 3,000 = 6,000바이트가 선언된 분량에 비해 아직 확인되지 않은 범위입니다. 이것을 곧바로 ‘서버가 6,000바이트를 전송하지 않았다’고 해석할 수는 없습니다. 캡처가 먼저 끝났거나 일부를 저장하지 않았을 수도 있습니다.

반대로 Follow의 Entire conversation에 9,500바이트가 표시되었다고 그것이 본문 9,500바이트라는 뜻도 아닙니다. 요청과 응답의 헤더, 방향별 데이터, 여러 메시지가 포함될 수 있습니다. 어느 표시 형식과 방향에서 어떤 바이트를 셌는지부터 확인해야 합니다. 숫자가 다르다는 사실만으로 전송 오류를 선언하지 마세요.

HEAD 응답이나 특정 상태 코드처럼 본문 처리 규칙이 다른 경우, chunked 전송이나 압축이 적용되는 경우에는 같은 계산을 기계적으로 적용하면 안 됩니다. RFC 9110의 Content-Length는 내용의 옥텟 수를 다루되 문맥별 규칙이 있으며, HTTP/1.1 메시지 경계는 별도 프레이밍 규칙도 함께 봅니다. 길이는 필드명·단위·문맥을 붙여서 읽는 값입니다. [5] [7]

같은 길이처럼 보여도 무엇을 셌는지가 다릅니다

옥텟(octet)은8비트이며 이번 문맥의 바이트와 같은 크기입니다. Content-Length는 단순 조건에서 메시지 내용의 예상 옥텟 수를 다루는 값입니다. 요청 헤더·응답 헤더·반대 방향 데이터·재전송까지 모두 합한 캡처 통계와 같은 분자가 아닙니다. 길이를 비교하기 전에 메시지 종류와 어느 경계 뒤를 셌는지부터 정해야 합니다.

기존 가상 조건을 유지하면 확보 비율은 3,000 ÷ 9,000 × 100 ≈ 33.33%이고 미확인 분량은6,000바이트입니다. 만약 추가 캡처에서 누락 없이 같은 본문의2,000바이트를 더 확보했다면 현재5,000바이트이고 남은 범위는 9,000 − 5,000 = 4,000바이트입니다. 이것은 확보 범위를 설명하는 계산이지 실제 사용자에게 전달된 양을 검증한 결과는 아닙니다.

조건을 바꾸어 HEAD 요청의 응답이라고 해 보겠습니다. 정상적인 HEAD 응답은 헤더 뒤에 메시지 본문을 보내지 않으며,Content-Length가 있어도 GET이었다면 해당했을 표현의 길이를 나타낼 수 있습니다. 따라서 본문이0바이트라고 자동으로9,000바이트 유실이라 쓰면 틀립니다. 응답 메서드·상태와 적용 규칙을 먼저 읽어야 합니다. [5] [7]

Transfer-Encoding은 HTTP/1.1 전송의 메시지 경계 처리와 관련되고,Content-Encoding은 gzip 같은 내용 코딩과 관련됩니다. 둘을 같은 “압축” 항목으로 처리하지 마세요. chunked이면 조각 크기와 끝 표시에 따라 메시지 경계를 읽고,내용 코딩이 있으면 코딩된 내용 길이와 해제 후 파일 크기가 달라질 수 있습니다. 예시의 단순 뺄셈을 이런 경우에 그대로 강제하지 않습니다. [5] [7]

10. 객체 저장과 현대의 암호화 환경에 연결하기

원문의 이 범위는 문자열 발견 뒤 HTTP 스트림을 읽는 데 초점을 둡니다. 여기에 파일 객체를 별도로 조사하려는 경우의 보충을 연결하겠습니다. File → Export Objects → HTTP는 해석·재조립 가능한 HTTP 객체를 살펴보고 저장하는 방법입니다. 지원 프로토콜과 확보한 데이터, 재조립·복호화 조건에 영향을 받습니다. 이 HTTP 예시를 포함한 원본 파일은 확인되지 않아 객체 추출 성공이나 해시·파일 형식 분석 결과를 제시하지 않습니다. 추가 확보한 첫째 날 파일의 MySQL·IRC 스트림 분석과는 별도입니다. [8]

Follow 창에서 ASCII로 저장한 양방향 대화, Raw 형식의 스트림 저장, HTTP 객체 추출, 패킷을 캡처 형식으로 저장하는 것은 서로 다른 결과물입니다. 텍스트 대화를 저장했다고 원래의 다운로드 파일을 정확히 추출한 것은 아닙니다. 어떤 기능·방향·형식으로 저장했는지와 완전성·인코딩·압축 처리 여부를 기록합니다.

현재도 유효한 원리와 적용 조건

패킷 검색과 대화 재구성은 여전히 유효하지만, 현재의 웹 통신을 모두 평문 HTTP/1.1 텍스트로 기대하면 안 됩니다. TLS에서는 적절한 비밀정보 등 복호화 조건이 필요합니다. HTTP/2는 한 TCP 연결 안에 여러 응용 스트림이 들어갈 수 있고, HTTP/3는 QUIC을 사용하므로 모든 웹 조사에서 TCP Follow 하나만 찾는 방식은 충분하지 않습니다. 현재 Follow 기능의 프로토콜·하위 스트림 구분과 실제 통신 구조를 확인합니다. [11] [1] [9] [10]

암호화로 본문이 안 보여도 접속 주소·시각·길이·방향과 연결 상태는 관측 범위 안에서 분석할 수 있습니다. 반면 어떤 명령이나 파일이었는지는 프록시·서버·단말 자료가 필요할 수 있습니다. 본문이 안 보인다는 것과 통신 자체가 없었다는 것을 구분해야 패킷 분석의 가치와 한계를 동시에 설명할 수 있습니다.

저장 버튼이 같아 보여도 결과물은 다릅니다

ASCII 대화 저장은 사람이 읽을 수 있는 표현을 남기는 선택이고,Raw 스트림 저장은 스트림 데이터를 다른 프로그램에서 조사할 때 쓰는 선택입니다. 현재 공식 문서는 Raw 화면은16진수 문자열로 보이지만 Save As 결과는 추가 줄 구분자를 넣지 않은 바이너리 파일이라고 설명합니다. 화면의16진수 글자를 복사한 텍스트와 Raw 저장 파일을 같은 것으로 취급하지 마세요. 어느 방향을 골랐는지도 함께 기록합니다. [1]

그렇더라도 Raw 스트림은 HTTP 응답 본문만 골라 저장한 객체와 자동으로 같지 않습니다. 요청·응답 헤더나 다른 메시지가 포함되는지,내용 코딩과 전송 프레이밍을 어떻게 처리했는지 확인해야 합니다. HTTP 객체 추출은 해석된 프로토콜 구조를 이용하는 후속 조사이며,원래 패킷 기록을 보존하는 캡처 저장과도 목적이 다릅니다.

추출 결과에는 사용한 캡처·관련 스트림·패킷·방향·기능과 확보 범위를 남깁니다. 실제 추출하지 않았다면 해시·형식·완전성 결과를 만들어 적지 않습니다. 또 파일을 구성했다는 사실과 단말에 같은 이름으로 저장되거나 실행됐다는 사실은 별도로 검증합니다.

HTTP/2의 응용 스트림과 Wireshark의 TCP 스트림 번호도 구별하세요. 한 TCP 연결에서 여러 요청·응답이 다중화될 수 있으므로 TCP 하나를 응용 요청 하나와 같다고 놓으면 안 됩니다. HTTP/3는 QUIC 기반이어서 TCP 헤더와 Follow TCP 메뉴를 전제로 한 절차가 그대로 맞지 않을 수 있습니다. 버전·암호화·하위 스트림과 도구의 지원을 확인하고 관측 가능한 범위부터 설명합니다. [10] [11]

11. 조사 기록을 재현 가능하게 남기기

지금까지의 기능을 하나로 묶어 보겠습니다. 목록은 관심 패킷을 고르고, 상세 패널은 필드를 해석하며, 바이트 패널은 확보한 데이터와 대응시킵니다. 수집·저장 옵션은 자료 범위를 정하고, 통계는 전체에서 후보를 고릅니다. Find로 특정 위치를 찾은 뒤 Follow로 문맥을 읽고, 필요하면 자료를 별도 형식으로 저장합니다. 이 단계들은 서로를 대신하지 않고 연결됩니다.

예를 들어 ‘어떤 스트림에 파일명 제안이 있었다’는 관측은 다음처럼 기록할 수 있습니다. 실제 사건 결과가 아닌 학습용 문장입니다.

확인한 캡처 파일의 패킷 320에서 파일명 관련 문자열을 찾았다. 해당 연결은 현재 해석에서 tcp.stream eq 7로 식별되며, 재조립된 서버 응답의 Content-Disposition 헤더에서 filename=notice.pdf를 확인했다. 이 표식은 서버가 제안한 파일명이며, 실제 파일 저장·실행과 악성 여부는 아직 확인되지 않았다. 요청·응답의 확보 범위, 원본 해시·버전·필터와 관련 패킷 범위를 함께 기록하고 단말·서버 자료를 대조한다.

응답 코드와 문자열을 발견했다는 사실, 관련 본문을 충분히 확보했다는 사실, 실제 단말이 파일을 저장·실행했다는 사실은 별도의 증거 수준입니다. 도구 이름이나 응답 부재만으로 공격자의 실력·무해함·공격 성공을 판단하지 않습니다.

예시 보고서의 번호320과 스트림7은 가상의 참조값입니다. 실제 기록에서는 원본 파일의 해시와 분석 버전·프로필·필터를 붙이고,선택 방향·검색 장소·표시 형식·관련 바이트 위치와 재조립 범위를 함께 남깁니다. 원본을 합치거나 추출본으로 옮긴 뒤 같은 숫자라고 같은 통신을 가리킨다고 생각하지 않습니다.

전체 검토를 마칠 때는 필요한 메모·파생 자료를 저장한 뒤 스트림 창을 닫거나 프로그램을 종료합니다. 창을 닫은 것,이전 표시 조건으로 돌아간 것,현재 분석 자료와 증거 기록을 보존한 것은 서로 다른 작업입니다. 다음 조사자가 어떤 상태에서 무엇을 확인했는지 따라갈 수 있도록 남겨 두세요.

12. 이번 회차의 증거 구분

패킷으로 확인 가능한 사실

확보된 바이트와 검색 위치, 관측된 종단·방향, 해석 가능한 요청·응답과 헤더, 재조립에 사용한 데이터와 확인한 범위입니다. 실제 바이트와 도구가 생성한 해석을 구분합니다.

단독으로 확정할 수 없는 부분

발신자의 신원·숙련도, 미수집 데이터, 암호화 본문의 의미, 파일의 최종 저장·실행과 공격 성공입니다. 파일명·상태 코드·제품 알림만으로 악성·실행 환경을 확정하지 않습니다.

함께 확인할 로그

센서 위치·손실·길이 제한, 원본 파일 해시와 분석 설정, 메일·프록시·웹 서버 기록, 브라우저 다운로드와 단말 파일·프로세스 활동, 필요한 복호화 정보입니다.

응답 표식이 관측됐다는 사실은 관련 통신을 조사할 근거입니다. 그러나 그 표식만으로 발신자 의도나 수신자의 행동을 확정하지 않습니다. 네트워크 자료의 관측과 단말의 저장·열람·프로세스 실행을 별도 단계로 연결해야 합니다. 필요한 경우 브라우저·메일·프록시·서버·인증 기록과 파일 활동을 대조합니다.

자료를 연결할 때는 수집 위치·방향·기간·누락과 시간대·시계 오차부터 맞춥니다. 주소와 시각이 비슷한 기록을 아무렇게나 묶지 말고,실제 연결·요청 식별자·계정·프로세스 등 연결 근거를 찾습니다. 복호화나 재조립에 필요한 자료가 없으면 무엇을 모르는지 그대로 남기는 것이 정확한 보고입니다.

13. 복습 — 검색 범위부터 결과의 의미까지

자체 복습과 미제공 자료

원문의 마지막 페이지는 별도 워크북 연습 안내입니다. 추가 제공된 워크북의 문제·기재 해설은 확인하고 실습 가이드로 연결했습니다. 추가 확보한 첫째 날 PCAP을 오프라인으로 대조했으며, 아래 자체 예시는 원본 파일의 실행 출력과 구분합니다. 아래 문제는 이번 범위의 학습 목표를 연습하도록 새로 구성했으며 원본 연습 완료 기록이 아닙니다.

질문 1: 첫 스트림을 Follow한 뒤 닫았더니 HTTP 표식을 찾지 못했습니다. 무엇부터 볼까요?

해설: 상단 표시 필터와 표시 패킷 수부터 봅니다. Close는 필터를 남길 수 있고 Back은 이전 조건을 복원합니다. 이전 조건이 좁았을 수도 있으므로 필요하면 Clear로 전체 표시를 확인합니다. 그다음 검색 장소·방식·선택 패킷 제한과 실제 자료 범위를 점검합니다.

질문 2: 빨간 글씨는 항상 공격자가 보낸 데이터일까요?

해설: 아닙니다. 기본 색은 방향 구분이며 테마에 따라 달라질 수 있습니다. 클라이언트·서버의 실제 주소와 메시지 역할을 확인해야 합니다. 어느 역할도 자동으로 공격자나 피해자를 뜻하지 않습니다.

질문 3: Packet bytes 검색과 Info 열 검색은 같을까요?

해설: 바이트와 요약 표시는 다릅니다. 요약에는 표식이 생략될 수 있고 상세 패널에는 해석된 값이 보일 수 있습니다. 지금 원하는 것이 실제 바이트인지, 표시된 필드인지, 해석된 프로토콜 조건인지를 먼저 정합니다.

질문 4: 표식이 두 패킷에 나뉘면 없다고 결론 내릴 수 있을까요?

해설: 개별 패킷 바이트 검색의 한계일 수 있습니다. filename=not과 ice.pdf를 TCP 순서에 맞춰 이어야 전체 표식이 나옵니다. 관련 스트림·재조립 데이터와 원래 패킷을 함께 검토하고, 결과를 어떤 단위에서 찾았는지 기록합니다.

질문 5: 200 OK와 filename=notice.pdf를 발견하면 악성 PDF 실행을 확인한 것일까요?

해설: HTTP 응답의 상태와 파일명 제안을 확인한 것입니다. 내용·형식·완전성, 실제 저장과 실행·영향은 별도입니다. 단말 파일·프로세스 기록과 서버·브라우저 자료를 연결해야 합니다.

질문 6: Content-Length 9,000인데 본문 3,000바이트만 확보했습니다. 남은 6,000바이트는 전송되지 않았을까요?

해설: 단순 예제의 선언 분량과 확보 분량의 차이는 6,000바이트입니다. 그러나 수집 중단·누락·잘림 때문에 못 봤을 수도 있습니다. 응답 문맥·프레이밍·압축 조건을 확인한 뒤 실제 전송과 캡처의 완전성을 구분합니다.

질문 7: 보고서에 스트림 7이라고만 쓰면 충분할까요?

해설: 그 번호는 파일과 해석 조건 안에서 의미가 있습니다. 파일 해시·버전·설정·필터와 패킷 번호·시각·종단을 함께 남겨야 다른 사람이 같은 자료로 검토하기 좋습니다. 추출하거나 합친 파일에서 번호가 같을 것이라고 기대하지 않습니다.

질문 8: HTTP 객체를 추출하지 못했다면 통신이 없었던 것일까요?

해설: 지원되는 프로토콜·수집 범위·재조립·암호화와 디섹터 조건을 확인해야 합니다. 추출 기능의 결과와 실제 전송의 존재는 같은 질문이 아닙니다. 보이는 헤더·시간·양과 단말·서버 기록도 함께 검토합니다.

조건을 바꾼 추가 복습

문제 9. Back을 눌렀는데 전체 파일로 돌아온 것이 아닐 수 있나요?

해설: 이전 표시 필터가 이미 주소나 다른 조건으로 제한돼 있었다면 그 상태로 복귀합니다. 실제 필터 입력란·표시 개수와 현재 파일이 원본인지 추출본인지 확인해야 합니다.

문제 10. filename=not과 ice.pdf가 같은 파일에 있으면 언제나 연결할 수 있나요?

해설: 같은 TCP 연결·같은 방향에서 바이트 위치가 연속하고 필요한 자료가 확보됐는지 봅니다. 앞은12바이트,뒤는7바이트로 합계19바이트이지만 다른 연결이나 반대 방향이면 임의로 이어 붙일 수 없습니다.

문제 11. filename="notice.pdf"와 filename=notice.pdf의 문자열 검색은 같나요?

해설: 따옴표가 실제 바이트에 들어간 앞 표현과 뒤 표현은 다릅니다. 공백·대소문자·문자 폭도 확인합니다. 헤더 문법에서 허용되는 표현과 정확 일치 문자열 검색은 다른 질문입니다.

문제 12. MAIL FROM 뒤250 OK면 수신자가 메일을 읽은 것인가요?

해설: 그 단계의 요청에 대한 성공 응답입니다. 수신자 지정·본문 전송·최종 수락·수신함 도착·사용자 열람은 추가 단계입니다. 예시의 일부 대화만으로 그 결과를 확정하지 않습니다.

문제 13. 일반 GET 응답의9,000바이트 중3,000을 보고2,000을 더 확보했다면요?

해설: 같은 본문의 연속 범위를 중복 없이 확보했다는 조건에서 현재5,000바이트,남은 미확인 분량은4,000바이트입니다. 전송량이나 단말 수신량을 직접 검증한 결과로 쓰지 않습니다.

문제 14. HEAD 응답에 Content-Length9000이 있고 본문이 없으면9,000바이트 유실인가요?

해설: 정상 HEAD 응답은 본문을 보내지 않으며 그 길이는 GET이었다면 해당했을 표현 길이일 수 있습니다. 메서드·상태·메시지 경계 규칙을 먼저 확인하고 단순 뺄셈을 적용하지 않습니다.

문제 15. Raw 화면의16진수 글자를 복사하면 Raw Save As와 같은가요?

해설: 현재 공식 문서는 Raw 표시와 Save As 결과를 구별합니다. 화면은16진수 문자열이고 Save As는 추가 줄 구분자 없는 바이너리 파일입니다. 방향·범위·형식을 기록하며 HTTP 객체와도 자동으로 같다고 놓지 않습니다.

문제 16. HTTP/2에서 TCP 스트림 하나면 HTTP 요청 하나인가요?

해설: 한 TCP 연결에 여러 HTTP/2 응용 스트림이 다중화될 수 있습니다. 전송 계층 연결과 응용 스트림의 번호·경계를 구별해야 합니다. HTTP/3는 QUIC 기반이므로 TCP 전제의 절차도 다시 확인합니다.

다음9강에서는 링크 계층과 Ethernet을 배웁니다. 이번에 다룬 스트림·응용 메시지와 별도로,현재 링크의 프레임 주소와 경계를 구분하는 단계로 이어집니다.

워크북 연계 실습

서버 문자열과 명령을 확인하고 요청·응답·실제 성공을 구분합니다. 스트림과 문자열 검색 실습에서 단계별 설명과 복습을 읽을 수 있습니다. 이 페이지의 기존 자체 예시는 그대로 유지하며, 원본 PCAP을 실행한 출력으로 제시하지 않습니다.

본 교재는 검색에서 스트림으로 읽는 원리와 워크북 연습으로 이어지는 범위를 설명합니다. 기존 검토에는 워크북의 탐색·스트림·문자열 학습 목표와 첫째 날 여섯 캡처·621개 기록의 오프라인 대조가 있습니다. 이번 실행의 원문 대조·독립 계산과 과거 실습 검증은 구별합니다. 원본 워크북·PCAP을 이번에 다시 분석하거나 HTTP 객체를 추출하지 않았습니다.

연계 실습에서는 서버 문자열과 명령이 어느 방향·메시지에 있는지 보고,요청·응답·실제 성공의 근거를 구별해 보세요. 이름·기능이 익숙해졌더라도 검색 범위와 원래 패킷으로 돌아가는 습관을 유지합니다. 표시된 텍스트를 실제 프로그램 실행으로 옮겨 쓰기 전에 필요한 단말 증거가 무엇인지 설명하는 것이 목표입니다.
