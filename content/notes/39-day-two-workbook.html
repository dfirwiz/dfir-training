학습 범위와 예제

둘째 날 17강 · 교재의 실습 연결 안내와 기존 워크북 검토 기록을 앞 강의에 연결하는 보충입니다. 인쇄 30~152쪽 전체를 이번에 새로 대조했다는 뜻은 아닙니다. 아래 주소·숫자·흐름은 별도 표시가 없으면 가상 학습 예시입니다. 명령은 분석 절차이며 실제 실행 출력으로 제시하지 않습니다.

1. 문제를 풀기 전에 무엇을 세는지 적습니다

이번 보충은 전자 워크북 둘째 날의 네 실습을 앞 강의와 연결하는 가이드입니다. 2026년 11월 3~4일의 기존 검토에서는 문제와 기재 해설을 확인하고, 제공된 여섯 PCAP 파일의 레코드와 주요 필드를 바이트 단위로 읽었습니다. Wireshark GUI·tcpdump·TShark를 실행한 결과나 당시 VM의 실제 수신 동작을 재현한 것으로 표시하지 않습니다.

파일 확장자가 .pcap이라고 실제 파일 형식이 항상 전통 PCAP인 것은 아닙니다. 제공 자료에는 PCAPNG 형식도 있었습니다. 파일 서명을 보고 형식을 판단한 뒤 레코드를 세었습니다. 전체 프레임 수, 필터로 선택한 패킷 수, 고유 포트 수, 연결 수는 서로 다른 단위입니다. 숫자를 적을 때 이 구별부터 붙여 보세요.

2026-11-18 · 랩 PDF 네 개 직접 대조

새로 제공된 표시 필터·BPF·TCP·UDP/ICMP 랩 PDF 총 53쪽을 OCR과 페이지 이미지로 대조했습니다. 기존 설명을 유지하면서 문제·힌트·기재 해설의 학습 목표를 아래 보충과 연결했습니다. PDF의 화면과 기재 결과를 읽은 것이며 실제 PCAP 여섯 개를 다시 실행한 것은 아닙니다. 아래 기존 파일 수치·레코드 번호는 과거 검토 기록과 구분하고, 새 계산 예제는 별도로 검산했습니다. 이전의 워크북 원문 접근 보류는 해소됐지만 실제 엔진·종단 재실행과 전체 과정의 최종 점검은 별도입니다.

실습 파일을 열었더니 선배가 적어 둔 숫자와 내 화면의 숫자가 다릅니다. 어디부터 고치면 좋을까요? 정답 숫자에 맞춰 필터를 바꾸기 전에 “같은 원본인가, 같은 집합인가, 같은 단위인가”부터 확인해야 합니다. 출석부의 전체 학생 수와 오늘 교실에 들어온 수, 중복 출입 횟수를 섞으면 어떤 숫자도 맞출 수 없겠죠. 패킷 실습도 마찬가지입니다.

다만 출석부 비유가 통신 전체를 설명하지는 않습니다. 캡처는 이미 누락되었거나 길이가 잘렸을 수 있고, 같은 통신이 두 인터페이스에서 중복 저장될 수도 있습니다. 한 파일의 개수만 정확하다고 실제 송수신을 모두 안다는 뜻은 아니지요. 그래서 결과와 함께 원본 해시·수집 위치·시간·도구 설정·집계 단위를 적습니다. 해시는 파일 바이트가 같은지 비교하는 지문이며, 파일 내용의 진실성이나 수집 경위를 혼자 보증하지 않습니다.

전통 PCAP은 전역 헤더와 패킷별 헤더를 따라 읽고, PCAPNG는 블록 종류·길이·인터페이스를 구분해 읽습니다. PCAPNG의 인터페이스 설명 블록을 패킷 하나로 세면 안 됩니다. 캡처 길이와 원래 길이, 인터페이스마다 다른 타임스탬프 단위도 나눠 봅니다. 여기서 기존 여섯 숫자의 합은 108+477+14+256+166+46=1,067레코드입니다. 합산을 다시 계산하는 것과 원본의 1,067레코드를 다시 검증하는 것은 별개의 일입니다.

2. 표시 필터: 주소 방향과 내보낼 집합 확인

첫 실습은 주소·ARP·헤더 길이·DNS를 표시 조건으로 바꾸는 연습입니다. 출발지와 목적지를 OR로 연결해야 하는지, 한 방향만 필요한지 먼저 한국어로 씁니다. ARP 요청은 arp.opcode == 1처럼 프로토콜 내부 필드로 찾습니다. Ethernet 브로드캐스트만 고르면 ARP 이외의 트래픽도 섞일 수 있습니다. 제공 파일의 바이트 검사에서는 ARP 요청 16개를 확인했습니다.

IPv4 옵션이 있는 패킷은 헤더 길이부터 확인합니다. 첫 옵션의 타입을 찾는 문제라면 “옵션 전체 어디엔가 값이 있다”와 “첫 옵션이 그 값이다”를 구별합니다. 구조를 읽는 필터와 바이트 위치를 보는 필터가 같은 질문에 답하는지도 확인하세요. 비초기 조각이나 잘린 데이터는 따로 점검합니다.

DNS를 UDP로 한정하라는 질문에서는 단순 dns만으로 끝내지 않습니다. DNS는 TCP로도 전달될 수 있기 때문입니다. udp and dns로 후보를 고르고 요청·응답 및 해석 상태를 점검합니다. 표시된 패킷만 새 파일에 내보내고, 다시 열어 예상 개수·시간·바이트가 맞는지 확인합니다. 아래 제공 dns.pcap의 14개 레코드는 별도 파일의 검사값이며, 이번에 GUI 내보내기를 실행해서 새로 만든 결과는 아닙니다.

조건을 문장으로 먼저 정하기

새 가상 사례를 보겠습니다. “192.0.2.25가 관여한 IPv4 TCP 통신을 찾고 싶다”면 출발지이거나 목적지라는 두 방향을 OR로 묶고 TCP를 AND로 결합합니다. ip.src는 IPv4 출발 주소, ip.dst는 목적 주소, ==는 같은 값인지 비교하는 기호입니다. or는 둘 중 하나라도, and는 양쪽을 함께 요구합니다. 괄호는 요구를 눈으로 확인할 수 있게 합니다.

(ip.src == 192.0.2.25 or ip.dst == 192.0.2.25) and tcp
arp.opcode == 1
arp.opcode == 1 and arp.src.proto_ipv4 == arp.dst.proto_ipv4
icmp.type == 0 and ip.len < 50
udp and dns

이 필터들은 서로 독립적인 연습입니다. 첫 식의 IPv4 범위는 IPv6까지 조사했다는 뜻이 아닙니다. ARP의 Opcode는 작업 종류이고 1은 요청, 2는 응답입니다. 세 번째 식은 요청 중 송신·대상 IPv4가 같은 후보를 더 좁히지만, 자발적 알림의 모든 구현과 의도를 증명하는 판정식은 아닙니다. 필드가 만들어질 만큼 원본이 있어야 비교할 수 있습니다.

icmp.type == 0은 IPv4 Echo Reply, ip.len은 IPv4 Total Length를 바이트로 표시한 값입니다. < 50은 50바이트 미만이지 Ethernet 프레임 50바이트 미만이 아닙니다. 독립 예제에서 태그 없는 Ethernet 데이터 영역에 IP 31바이트를 실었다면 최소 데이터 영역 46바이트까지 46−31=15바이트의 채움이 필요합니다. IP의 Total Length에는 이 채움을 넣지 않습니다. 실제 저장에는 FCS 유무·추가 채움·링크 형식 차이가 있으므로 이 최소값을 실제 파일의 뒤쪽 0바이트 개수로 단정하지 않습니다.

첫 IPv4 옵션도 기준점을 따져 봅시다. IHL>5인 첫 조각의 IPv4에서 첫 옵션은 기본 헤더 20바이트 뒤에서 시작합니다. “헤더 안에 타입 X가 존재함”은 “처음 옵션 타입이 X임”보다 넓은 질문입니다. 옵션이 없는 데이터의 바이트가 우연히 X와 같아지는 반례를 먼저 만들면 잘못된 필터를 찾기 쉽습니다. 앞 강의의 옵션 존재 조건·초기 조각·읽을 수 있는 길이와 함께 확인하세요.

표시, 표시된 패킷 저장, 화면 텍스트 저장을 나누기

화면에 필터를 타이핑한 것과 그 필터를 적용한 상태도 다릅니다. 표시된 집합을 확인한 뒤 Export Specified Packets의 패킷 범위를 살피고, 저장한 캡처를 다시 열어 개수·첫/마지막 시각·대표 프레임 바이트를 대조합니다. Export Packet Dissections는 해석된 텍스트·CSV 등의 내보내기이므로 원래 캡처 파일 저장과 다릅니다. 현재 메뉴와 범위의 의미는 공식 내보내기 안내를 기준으로 확인하세요.

조건을 바꿔 DNS가 TCP로 오거나 암호화된 DNS가 지나가면 어떨까요? udp and dns는 UDP로 해석된 DNS만 고르는 범위입니다. 포트 53만으로 DNS가 정상 해석된다고 보장하지 않고, 해석되지 않은 트래픽의 부재를 DNS 이용 부재로 바꾸지도 않습니다. 스트림 재조립·Decode As·암호화·수집 위치를 기록하고 리졸버 로그와 맞춰 봅니다.

arp.opcode == 1
ip.hdr_len > 20
udp and dns

3. BPF: 플래그와 DNS 오프셋을 검산합니다

연결 시작은 목적지 포트를, 연결 시작 응답은 출발지 포트를 조사합니다. 제공 int-server 파일에서 플래그 바이트 정확 일치 0x02의 레코드는 13개였지만 고유 목적지 포트는 6개였습니다. 0x12의 레코드는 5개, 고유 출발지 포트는 3개였습니다. “패킷 수가 곧 서비스 수”가 아님을 보여주는 예입니다.

이 숫자는 해당 파일에 대한 정확 일치 조건의 결과입니다. 실제 조사에서는 앞 강의처럼 ECN을 허용하는 마스크와 비교하고 어떤 추가 플래그를 제외했는지 기록합니다. FIN 또는 RST 중 하나라도 찾는 조건은 & 0x05 != 0입니다. 목적지 포트 143에서 PSH·ACK가 모두 켜졌는지는 & 0x18 = 0x18로 비교합니다. 두 식의 != 0과 = 마스크 값을 바꾸어 쓰지 않습니다.

DNS 헤더는 UDP의 8바이트 뒤에서 시작합니다. 따라서 UDP 기준 오프셋 10은 DNS 플래그의 상위 바이트이고, QR은 그 바이트의 0x80 비트입니다. UDP 기준 오프셋 18의 두 바이트는 DNS ARCOUNT입니다. 질의이면서 추가 레코드가 있는 조건을 만들 때 QR=0과 ARCOUNT>0을 함께 검사합니다. 제공 dns 파일에서 이 바이트 조건에 해당한 레코드는 1·4·6·8입니다. 완전한 DNS 의미 검증과 가변 질문 이름의 파싱은 별도 단계입니다.

정확 일치, 모두 포함, 하나라도 포함의 반례

비트는 한 자리의 0 또는 1이고, 0x는 16진수 표시입니다. &는 두 수를 비트별로 AND하여 마스크가 1인 자리만 남깁니다. FIN의 값 1과 RST의 값 4를 합한 마스크는 5, 즉 0x05입니다. 남은 값이 0이 아니면 둘 중 적어도 하나가 있다는 뜻입니다. 반대로 PSH 8과 ACK 16을 더한 마스크 0x18의 두 자리가 모두 있어야 한다면 결과가 0x18과 같아야 합니다.

tcp[13]은 TCP 시작에서 0부터 세는 바이트 13입니다. 여기에 목적지 포트 143을 별도로 결합하고 표본 개수를 제한할 수 있습니다. 아래 가상 파일명은 기존 실습의 실제 실행 출력이 아닙니다. -r은 저장 파일 읽기, -nn은 주소·포트 이름 변환 끄기, -c 5는 일치하는 패킷 다섯 개를 처리하면 끝내는 제한입니다. 파일의 첫 다섯 패킷을 먼저 고른다는 뜻이 아닙니다. 작은따옴표는 셸이 & 등의 기호를 가로채지 않도록 감쌉니다.

tcpdump -nn -r practice.pcap 'ip and (tcp[13] & 0x05) != 0'
tcpdump -nn -r practice.pcap -c 5 'ip and tcp dst port 143 and (tcp[13] & 0x18) = 0x18'

ip를 넣은 이유는 IPv4 바이트 접근 범위를 드러내기 위해서입니다. IPv6 확장 헤더나 비초기 IP 조각까지 이 예제로 검사했다고 쓰지 않습니다. ECN을 고려한 SYN/SYNACK 후보는 앞 16강의 낮은 여섯 자리 조건과 두 자리 조건을 비교하고, 현재 AccECN의 AE도 따로 확인합니다. 정확 02/12의 과거 개수를 오늘의 모든 연결 수로 바꾸지 마세요.

DNS는 “어디서부터 10바이트인가”가 핵심입니다

UDP 헤더는 8바이트이고 그 다음 DNS 고정 헤더는 12바이트입니다. DNS ID는 DNS+0의 2바이트, 플래그는 DNS+2의 2바이트, QDCOUNT·ANCOUNT·NSCOUNT·ARCOUNT는 각각 DNS+4·6·8·10의 2바이트입니다. 따라서 DNS+10인 ARCOUNT는 UDP+18입니다. 같은 10이라는 숫자라도 UDP+10은 DNS 플래그의 상위 바이트입니다.

# 독립적인 DNS 고정 헤더 12바이트 · 실제 파일에서 추출한 값 아님
12 34 01 00 00 01 00 00 00 00 00 01

ID는 0x1234, 플래그는 0x0100입니다. 첫 플래그 바이트 01과 0x80을 AND하면 0이므로 QR=0인 질의 후보이고, ARCOUNT의 00 01은 네트워크 바이트 순서로 1입니다. 이 12바이트만으로는 QDCOUNT=1과 ARCOUNT=1이 요구하는 질문과 추가 레코드가 실제로 존재하는지 확인할 수 없습니다. 아래 비트 검사가 참이어도 완전한 DNS 메시지 판정은 실패할 수 있는 의도적인 반례입니다.

QR은 Query/Response, 즉 질의·응답 구분이고 ARCOUNT는 Additional Resource Record 개수입니다. ARCOUNT>0이 곧 EDNS라는 뜻도 아닙니다. EDNS의 OPT 레코드는 타입 41의 구조와 위치까지 확인해야 합니다. 가변 길이 이름·압축 포인터·잘림·응답 재시도는 별도 파싱 대상입니다. DNS 기본 형식과 EDNS 형식을 연결해 보세요.

tcpdump -nn -r dns.pcap 'udp dst port 53 and (udp[10] & 0x80) = 0 and udp[18:2] > 0'

4. 마스크는 연속된 주소 범위만 고르지 않습니다

마지막 바이트에 (값 & 0xd0) = 0xd0을 적용하면 0xd0의 1인 자리, 즉 128·64·16 자리가 모두 켜져 있어야 합니다. 32 자리와 아래 네 자리는 검사하지 않으므로 두 구간이 선택됩니다. 208~223과 240~255입니다. 그 사이 224~239는 16 자리가 꺼져 있어 빠집니다.

총 선택 값은 32개입니다. 제공 추가 실습 파일은 끝 바이트 0~255를 비교하는 연습에 대응하며 레코드는 256개입니다. 이 마스크가 단일 CIDR 프리픽스와 언제나 같은 집합이라고 외우지 마세요. 검사하지 않는 자리가 중간에 있으면 여러 떨어진 구간이 될 수 있습니다.

직접 경계값을 넣어 볼까요? 207은 이진수 11001111이라 16 자리가 0이어서 제외됩니다. 208은 11010000이라 통과하고, 223은 11011111이라 통과합니다. 224는 11100000이라 16 자리가 다시 0이어서 제외되고, 240은 11110000이라 통과합니다. 검사하지 않는 다섯 자리는 각각 두 값을 가질 수 있어 2×2×2×2×2=32가지입니다. 비트 계산을 “208 이상”이라는 한 범위로 바꾸면 224~239의 거짓 양성이 생깁니다.

실제 주소 조건에서는 같은 /24라는 앞 24비트의 제한도 따로 붙여야 합니다. 끝 바이트만 비교하면 다른 네트워크의 같은 끝 숫자도 들어옵니다. 예를 들어 192.0.2.208과 198.51.100.208은 끝 바이트만 같고 다른 주소입니다. CIDR은 앞에서 연속한 비트를 고정하는 표현이며, 중간 자리를 건너뛰는 이 마스크와 일반적으로 같은 집합이 아닙니다.

5. TCP: 체크섬 오류와 겹치는 바이트를 별도로 봅니다

TCP 실습의 체크섬 질문에서는 IP 체크섬이 맞아도 TCP 체크섬이 틀릴 수 있음을 확인합니다. 제공 TCP 파일을 재계산했을 때 TCP 체크섬이 유효하지 않은 레코드는 121·128이었습니다. 그중 RST가 포함된 흐름에서는 RST를 보았다는 사실과 종단이 실제 종료했다는 판단을 분리합니다. 실제 수신 동작까지 확인하려면 종단 자료가 더 필요합니다.

같은 출발지 포트와 같은 SEQ 범위인데 내용이 다른 두 세그먼트는 단순한 동일 데이터 재전송과 다릅니다. 서로 다른 재조립 정책에서 어떤 바이트를 채택하는지가 달라질 수 있습니다. SYN 데이터도 함께 있을 수 있으므로 현재 기능·유효성·스트림 문맥을 확인합니다. 이 현상을 발견했다고 운영 서버에 공격을 재전송할 필요는 없습니다. 확보한 자료에서 범위와 내용을 비교하면 됩니다.

다른 문제의 여러 SYN은 포트·초기 SEQ·간격을 비교해 같은 시도의 재전송과 새로운 연결 후보를 구별합니다. 비정상 플래그 조합은 SYN/FIN/RST 등 각 의미가 상태에서 충돌하는지 보고, 단순히 모든 플래그가 있다는 이유만으로 실제 침해를 주장하지 않습니다. 외부 SYN/ACK만 보이는 사례는 반사 응답 가설과 수집 범위 가설을 나눕니다.

URG 추가 문제는 첫 세그먼트의 포인터가 그 세그먼트 데이터 바깥을 가리킬 수도 있음을 보여줍니다. 다음 세그먼트까지 바이트 위치를 이어서 계산하고, 응용이 어떤 바이트를 읽었는지는 워크북의 기재 결과와 현재 재현 결과를 구별합니다. 한 구현의 문자가 빠지는 동작을 모든 TCP의 보편 규칙으로 일반화하지 않습니다.

체크섬은 어느 영역을 검사했는지부터 묻습니다

IPv4 헤더 체크섬은 IPv4 헤더를 검사하고, TCP 체크섬은 IP 주소·프로토콜·TCP 길이를 담은 의사 헤더와 TCP 헤더·데이터를 검사합니다. IP 체크섬이 맞아도 TCP 데이터가 달라지면 TCP 체크섬이 틀릴 수 있습니다. 계산할 때는 체크섬 필드를 0으로 놓고 16비트 워드들을 더하며 넘친 자리올림을 다시 접고 비트를 반전합니다. 수신 검사는 저장된 체크섬까지 더한 결과가 0xffff인지 확인하는 방식과 연결됩니다. 자세한 전체 바이트 예제는 8강에서 이어 읽습니다.

합성 예로 워드 0xffff와 0x0002를 더하면 0x10001입니다. 위로 넘친 1을 아래 16비트 0001에 더해 0002, 반전한 체크섬은 fffd입니다. ffff+0002+fffd=1fffe, 다시 접으면 ffff가 됩니다. 이 작은 산술은 TCP 전체 패킷을 구성한 예가 아니라 자리올림 접기 연습입니다. 실제 TCP에는 의사 헤더와 모든 데이터가 포함되어야 합니다.

수집 지점이 송신 호스트라면 체크섬 오프로딩 때문에 캡처 시점의 필드가 아직 완성되지 않았을 수 있습니다. 잘못된 체크섬이라는 표시 하나로 와이어 손상이나 의도적인 공격을 확정하지 말고, 수집 방향·NIC 설정·반대 센서·표본 바이트를 비교합니다. 반대로 제공된 조작 연습 자료의 오류도 오프로딩이라고 자동 면제하지 않습니다.

같은 순서 위치에 다른 데이터가 있을 때

SEQ는 TCP 데이터의 순서 위치이고 ACK는 다음에 기대하는 위치입니다. 독립적인 예로 두 데이터 세그먼트가 같은 SEQ=2001에서 시작해 각각 ALPHA와 ALPXA라는 5바이트를 담았다고 합시다. 범위는 모두 [2001,2006)이고, 끝의 괄호는 2006은 포함하지 않는다는 뜻입니다. 네 번째 바이트 위치 2004가 H와 X로 충돌합니다. 같은 범위라는 이유로 동일 데이터 재전송이라고 쓰면 핵심을 놓칩니다.

여기에 SYN까지 함께 있다면 계산 조건이 바뀝니다. SEQ=2000인 SYN은 한 칸을 쓰므로 첫 데이터는 2001부터이고, 5바이트까지 수용했다는 조건 아래 다음 기대값은 2000+1+5=2006입니다. 하지만 실제로 수용했다는 사실은 별도 증거입니다. TCP Fast Open은 옵션·쿠키·응답·구현 문맥이 필요하며, SYN 데이터가 있다는 이유만으로 기능이나 회피 성공을 단정하지 않습니다.

재조립은 세그먼트들을 순서 위치에 맞춰 하나의 바이트 흐름으로 해석하는 일입니다. 센서와 종단이 겹치는 바이트·잘못된 체크섬·RST를 다르게 처리한다면 서로 다른 흐름을 볼 수 있습니다. 이를 확인하려면 원본 바이트, 센서 설정, 종단 수신 상태와 응용 기록을 비교해야 합니다. 이 강의의 계산이 어떤 제품의 회피 성공을 재현한 것은 아닙니다.

재시도·조작 필드·RST·URG를 한 판단으로 합치지 않기

가상 SYN이 시작 후 0·4·12·28초에 같은 5튜플과 ISN으로 나왔다면 간격은 4−0=4초, 12−4=8초, 28−12=16초입니다. 증가하는 간격은 재시도 가설을 지지하지만 수집 중복·의도적인 재생도 검토합니다. 포트와 ISN이 달라지면 새 시도 후보를 구분하고, 시도 수를 공격 의도나 성공 수로 바꾸지 않습니다.

조작된 헤더는 필드별로 해석하세요. 0x3f는 FIN·SYN·RST·PSH·ACK·URG 여섯 자리의 합 1+2+4+8+16+32=63입니다. 전부 켜졌다는 사실, 포트가 0이라는 사실, 윈도·옵션·URG 값은 서로 다른 검사 항목입니다. MSS는 광고자가 받을 수 있는 데이터 크기와 방향을, 윈도는 연결 단계와 스케일 협상을 고려해 읽습니다. 값 하나가 특이하다는 이유만으로 정상 상대의 처리 결과를 상상해서 채우지 않습니다.

RST는 재설정 신호입니다. 실제 상태·SEQ 검사·체크섬과 수신 구현에 따라 채택 여부가 달라집니다. RST 뒤에 같은 연결 데이터와 그에 맞는 ACK가 이어지면 “이 센서에서는 뒤의 교환도 관측되었다”라고 쓸 수 있습니다. 왜 거부했는지, 어느 종단이 어떤 데이터를 처리했는지는 단말·서버·방화벽 로그와 연결해야 합니다.

URG는 데이터 삭제 명령이 아닙니다. 가상으로 SEQ=1001인 4바이트 ABCD와 SEQ=1005인 4바이트 EFGH가 이어지고 첫 URG 포인터가 6이면 경계는 1001+6=1007입니다. 현재 표준의 경계 바로 앞 위치 1006은 F입니다. 이 경계를 일반 소켓 읽기·별도 OOB 읽기·SO_OOBINLINE 설정이 어떻게 노출하는지는 구현과 API 조건을 확인해야 합니다. 패킷에서 F가 사라졌다는 뜻이 아닙니다. URG 구현 차이를 참고하세요.

6. UDP·ICMP: 잘못된 응답도 학습 자료에 들어 있습니다

UDP·ICMP 실습에서는 브로드캐스트에 대한 오류, 비초기 조각 관련 오류, ICMP 오류에 대한 또 다른 오류를 검토합니다. 패킷 쌍이 존재한다고 그 관계가 표준상 올바르다는 뜻은 아닙니다. 앞 강의의 오류 생성 억제 조건을 적용해 “왜 이 응답이 없어야 하는가”를 설명해 보세요.

TTL이 단계적으로 커지는 Echo들과 Time Exceeded의 인용 원본을 연결하면 경로 탐사 가설을 검토할 수 있습니다. 운영체제는 도구 방식과 페이로드의 단서로 추정하되 확정하지 않습니다. 요청보다 응답이 많거나 적은 묶음은 ID·SEQ·주소·데이터·수집 조건을 다시 맞춥니다.

ICMP 데이터에서 명령과 결과처럼 보이는 내용이 이어지면 일반 도달성 점검 외의 사용을 의심할 수 있습니다. 하지만 프로그램 이름이나 공격자까지 패킷만으로 정하지 않습니다. 원래 프로세스, 업무 목적, 시간대와 종단 기록을 확인합니다. 추가 문제에서 Echo에 대한 “프로토콜 도달 불가”가 돌아오는 모순도 Type/Code와 원래 요청을 비교해 설명합니다.

먼저 바깥 ICMP의 발신자와 인용된 원래 목적지를 별도 열로 적습니다. 독립 예제에서 192.0.2.10:54000이 198.51.100.20:33440으로 UDP를 보내고, 203.0.113.1이 Time Exceeded를 보냈다면 203.0.113.1을 UDP 서비스 서버로 집계하지 않습니다. 오류 안의 원래 주소·포트·식별 정보가 자극과 맞는지 확인해야 합니다. 시간만 가장 가깝다는 이유로 두 패킷을 짝짓지 마세요.

IPv4 ICMP 오류는 일반적으로 ICMP 오류에 대한 응답, 비초기 조각, 브로드캐스트·멀티캐스트 목적지 또는 링크 브로드캐스트 등 억제 조건을 검토해야 합니다. 원본 관계가 맞는지와 표준상 생성 가능한지도 별개입니다. 이런 표본이 저장 파일에 있다고 장비가 실제 송신했다거나 원래 수신자가 처리했다고까지 증명되지는 않습니다. 조작 자료·잘못된 디코딩·누락된 문맥도 가능하니까요. ICMPv6는 별도 예외와 조건이 있으므로 v4 규칙을 그대로 복사하지 않습니다.

Echo Request는 IPv4 Type8·Code0, Reply는 Type0·Code0입니다. ID와 SEQ가 같더라도 NAT·여러 송신자·순번 순환 때문에 다른 교환일 수 있습니다. 주소·데이터·방향·시각·수집 위치까지 묶습니다. TTL은 IP 패킷의 홉 제한 값이며 단계적으로 증가하는 여러 자극은 경로 탐사 가설을 지지합니다. 무응답 홉은 오류 억제·속도 제한·반환 경로·수집 손실도 가능하므로 장비 부재나 차단 성공으로 확정하지 않습니다.

Echo에 대해 “프로토콜 도달 불가”가 돌아오는 표본이라면, 먼저 인용 원본이 정말 그 Echo인지와 바깥 Type/Code를 다시 확인합니다. 예상과 다른 응답을 곧바로 도구나 운영체제의 지문으로 확정하지 않습니다. 명령처럼 보이는 데이터도 관측 문자열·가능한 용도·추가 증거를 나눕니다. 암호화·압축된 데이터나 잘린 캡처에서는 의미 확인이 더 제한되며, 실제 프로세스·인증·서버 처리 기록이 필요합니다.

7. 결론까지 가는 길에 세 개의 문이 있습니다

실습의 마지막 문장은 “필터가 찾았다”에서 멈추지 않아야 합니다. 아래 그림은 계산이 맞는지, 도구가 같은 집합을 선택하는지, 실제 종단이 무엇을 했는지의 세 관문을 구분합니다. 단계가 올라가려면 새 증거가 필요하고, 위 단계의 빈칸을 아래 단계의 숫자로 메울 수 없습니다.

여기에 자료 접근의 관문도 따로 있습니다. 이전 사람이 원본을 검토한 기록과 내가 이번에 원본 문항을 직접 대조한 것은 다릅니다. 이번에는 새 예제의 ①을 확인하지만, 과거 PCAP 관측을 새로 재검증한 것도 아니며 ②·③을 실행한 것도 아닙니다. 전체 워크북 항목을 빠짐없이 대조했다는 판정은 새로 확보한 랩 PDF와 본문을 항목별로 대조해야 합니다. 이번 대조 내용은 아래 보충과 검토 기록에 남겼고, 실제 엔진·종단 검증은 별도로 구분합니다.

8. 새 랩 원문과 대조하며 더 짚어 볼 부분

앞 절의 원리를 실제 학습 목표와 연결해 보겠습니다. 이 절은 새로 받은 네 랩 문서의 준비·본 실습·추가 실습을 모두 확인한 뒤 보강한 내용입니다. 원본 문항·정답·화면을 복제하는 대신, 같은 원리를 새로운 주소와 숫자로 연습합니다. PDF 화면에 쓰인 명령을 읽었다는 사실과 그 명령을 이번에 실행했다는 주장은 다릅니다.

표시 필터: 이름에 문자열이 있다는 것과 질의만 있다는 것은 다릅니다

문서용 이름 lab.example을 찾아야 한다고 합시다. dns.qry.name contains "lab"에서 dns.qry.name은 질문 이름, contains는 부분 문자열 포함 여부, 따옴표 안의 lab은 비교할 문자열입니다. 요청뿐 아니라 질문을 포함하는 응답도 이 조건에 들어올 수 있습니다. 요청만 필요하다면 dns.flags.response == 0을 AND로 추가하고, 적용된 조건과 상세 트리의 실제 질문을 비교하세요. 응답까지 고른 결과가 두 번 실행한 DNS 질의라는 뜻은 아닙니다.

# Wireshark 표시 필터 · 새 독립 예제
dns.qry.name contains "lab"
(dns.qry.name contains "lab") and dns.flags.response == 0
arp.opcode == 1 and arp.isgratuitous == 1

마지막 식의 arp.isgratuitous는 Wireshark가 자발적 ARP로 해석한 불리언 필드입니다. 불리언은 참·거짓을 나타냅니다. 요청 집합 안에서 찾는 질문이므로 Opcode 조건도 함께 남겼습니다. 앞 절의 송신·대상 IPv4 동일 비교와 이 해석 필드가 어떤 표본에서 같은지 확인하고, 그 조건만으로 위조나 장애 원인을 단정하지 않습니다. 매 실습 뒤에는 이전 필터를 해제하고 원본 전체 개수로 돌아왔는지 확인하세요. 조건이 남아 있으면 다음 실습의 검색 공간부터 달라집니다.

기본 Ethernet의 최소 프레임 길이는 헤더 14·데이터 최소 46·FCS 4를 합한 64바이트라는 조건으로 이해합니다. 여기서 짧은 것은 IP Total Length일 수 있으며 IP 헤더 길이와 다릅니다. 패딩이 붙어 정상 길이가 된 프레임을 무조건 손상된 runt라고 부르지 않습니다. 옵션 존재 조건 없이 IP+20을 읽으면 TCP·UDP의 첫 바이트를 옵션으로 오해할 수도 있지요. 새 예제로 옵션 타입 0x83을 찾는다면 타입 한 바이트와 두 바이트 패턴을 혼동하지 말고, 1바이트 값의 표시 문법과 옵션 존재·조각·길이 조건을 각각 확인해야 합니다. 앞 강의의 단일 바이트 slice 예제를 참고하세요.

저장한 캡처 개수를 확인할 때 원문은 셸 파이프로 줄 수를 세는 방법도 안내합니다. |는 앞 명령의 표준 출력을 뒤로 넘기고, wc -l의 마지막 글자는 숫자 1이 아니라 소문자 L입니다. -t는 tcpdump 시각 표시를 생략하고 -n은 주소 이름 해석을 끕니다. 그러나 다중 행 상세 출력·진단·오류·파일 읽기 실패를 확인하지 않으면 줄 수와 패킷 수가 달라질 수 있습니다. 재열기와 패킷 번호 표본 대조를 함께 사용하고, 실제 실행하지 않은 개수를 새 결과로 쓰지 않습니다.

BPF: 표의 축약 표현보다 실제 비트와 상태를 봅니다

ACK는 항상 모든 패킷에 있다는 규칙이 아닙니다. 연결 시작 SYN이나 일부 RST에서는 다른 상태 규칙이 적용됩니다. PSH도 “모든 데이터 패킷”을 고르는 표시가 아니며 PSH 없이 데이터가 전송될 수 있습니다. 따라서 FIN/RST를 고를 때 ACK까지 무조건 요구하거나, 데이터 전송을 모두 찾겠다며 PSH만 고르면 질문과 결과가 어긋날 수 있습니다. 원문의 플래그 요약은 입문용 단서로 보고 현재 TCP 상태 규칙과 앞 절의 추가 비트 허용 조건을 함께 읽습니다.

같은 응답이 여러 번 보이면 호스트 재전송 외에 수집 중복·미러링·링크의 반복 기록도 가설입니다. 원문이 특정 실습 환경의 중복 원인을 설명하더라도 지금 다른 캡처에도 같은 원인이 있다고 옮기지 마세요. 시각·프레임 바이트·SEQ·ACK·캡처 인터페이스와 양쪽 센서로 확인합니다. DNS의 QR/ARCOUNT 검사는 기존 절처럼 고정 필드의 선언을 검사하는 것이고, 추가 레코드가 있다는 사실만으로 EDNS나 이상 통신을 확정하지 않습니다.

TCP 체크섬과 조작 필드: 각 항목의 증거 수준을 다르게 적습니다

IPv4 Protocol 필드는 IP 시작+9에 있고 값 6은 TCP를 가리킵니다. TCP 체크섬은 TCP 시작+16~17의 2바이트이므로 IP+16~17과 혼동하지 않습니다. TCP 체크섬 값 0은 “검사 생략” 표시가 아닙니다. 의사 헤더·전체 TCP를 포함해 실제 합이 맞는지 계산해야 하며, 값이 0이라는 이유만으로 무조건 오류라고 판단할 수도 없습니다. IPv4 UDP의 선택적 체크섬 표기와 섞지 마세요. PDF의 오류 표시는 문서가 보여 준 표본의 결과이고, 이번에 원본 PCAP을 다시 계산한 것은 아닙니다.

TCP 필드별로 나눠 적는 관측·조건·한계
관측 항목먼저 해석할 것곧바로 확정하지 않을 것
포트 0저장된 TCP 헤더 값·방향·응용 역할소켓 API의 포트0 자동할당과 동일 취급하지 않음

예를 들어 캡처의 실제 SEQ가 0이면 화면 상대 SEQ=0과 의미가 같지 않을 수 있습니다. 순서 번호는 32비트 공간에서 순환하므로 0도 표현 가능한 값입니다. ACK 번호는 ACK 비트가 켜졌을 때 상태 문맥에서 읽습니다. 여러 특이 필드가 함께 나타나면 조작 가설의 우선순위가 높아질 수 있지만, 각각의 유효성·수신 결과와 의도까지 같은 문장으로 합치지는 않습니다.

보이지 않는 SYN을 응답에서 어디까지 역추론할까요?

독립 사례에서 외부 198.51.100.80:443이 내부 여러 주소의 55000번 포트로 SYN/ACK를 보내고, ACK가 모두 9001이라고 합시다. 데이터 없는 SYN에 대한 통상적인 응답이라는 조건 아래, 원래 SYN의 출발 포트 후보는 55000, 원래 SEQ 후보는 9001−1=9000입니다. 목적지 포트와 확인 번호가 반복된다는 관측은 자동 생성·주소 위조에 대한 가설을 강화할 수 있습니다. 그러나 원래 SYN이 저장되지 않았으므로 그 필드를 직접 관측한 것으로 적지는 않습니다.

“출발 SYN을 못 봤다”는 사실에는 수집 누락·비대칭 경로·시간 범위·NAT·센서 필터도 영향을 줍니다. 원문에서 모든 출발 통신을 수집한다는 전제를 준 사례와, 그 전제를 확인하지 못한 실제 조사를 구분해야 합니다. 원치 않는 SYN/ACK에 종단이 RST를 만들 수 있지만 상태·방화벽·라우팅·속도 제한에 따라 관측이 달라집니다. 반사 응답 가설이 성립해도 서비스 거부의 성공·보낸 사람·숙련도는 부하·서버 상태·방화벽·종단 증거가 더 필요합니다.

잘못된 체크섬의 RST 뒤에 데이터가 이어지는 경우도 두 단계로 봅니다. 먼저 저장 표본에 어떤 값과 후속 SEQ/ACK가 있는지, 다음으로 센서와 종단이 그 값을 실제로 어떻게 처리했는지입니다. 원문의 당시 센서 가정은 가능한 불일치 사례로 설명하되 모든 현재 IDS/IPS가 같은 방식으로 우회된다고 일반화하지 않습니다. URG 예제의 응용 출력도 일반/OOB 읽기와 인라인 설정을 포함한 당시 구현 결과이며 전송 중 바이트 삭제 규칙이 아닙니다.

UDP·ICMP: 인용 필드와 경로 탐사에서 생기는 두 가지 함정

재조립 시간 초과 오류는 첫 조각 조건까지 봅니다. 원래 IPv4 데이터그램의 오프셋 0인 조각을 받지 못했다면 재조립 실패에 대한 ICMP 오류를 만들지 않아야 하는 조건이 있습니다. 비초기 조각에 대한 오류 억제와 재조립 타이머 만료를 구분하세요. 다만 캡처에 첫 조각이 없다고 수신자도 못 받았다고 자동 결론낼 수는 없습니다. 수집 손실·위치·시간과 수신자 로그를 확인해야 합니다. 오류에 대한 또 다른 오류를 억제하는 이유도 반복 오류의 확산을 막기 위한 것이지, 캡처 두 행만으로 실제 서비스 거부가 발생했다는 뜻은 아닙니다.

인용 IPv4 헤더의 체크섬은 후보를 빨리 찾는 값이 될 수 있지만 패킷 고유 ID는 아닙니다. 값은 16비트라 가능한 값이 2의 16제곱, 즉 65,536개이고 다른 헤더가 같은 결과를 가질 수 있습니다. NAT나 TTL 변화로 원래 송신 지점과 인용 지점의 값이 달라질 수도 있습니다. 바깥 오류 IP 헤더와 인용 IP 헤더 중 어디서 선택했는지 확인한 뒤 주소·프로토콜·식별자·조각 정보·인용 포트·시각을 함께 맞춥니다. “체크섬이 같다”는 한 조건으로 원인을 유일하게 확정하지 않습니다.

TTL이 증가하는 Echo 묶음과 Time Exceeded는 ICMP 방식 경로 탐사와 잘 맞습니다. Windows tracert의 기본 방식과 연결할 수 있지만 다른 운영체제의 도구도 ICMP·UDP·TCP 방식을 선택할 수 있으므로 운영체제 확정 지문은 아닙니다. 오류 발신 주소는 그 시점의 응답 인터페이스 단서이며 장비 전체 목록이나 왕복 경로의 완전한 지도가 아닙니다. 비응답·다중 경로·NAT와 수집 범위를 기록합니다.

Echo 안에서 SSH 식별 문자열과 협상처럼 보이는 내용이 이어지면 ICMP를 다른 통신의 운반 수단으로 사용한 가설을 검토할 수 있습니다. 요청·응답 개수 불균형은 조사 단서일 뿐, 그 자체로 터널을 확정하지 않습니다. 합법적 진단·수집 손실·사용자 지정 데이터도 가능하기 때문입니다. 원문이 이름 붙인 특정 도구를 모든 비슷한 문자열에 적용하지 말고, 여러 프레임의 흐름·페이로드 구조·승인된 업무·종단 프로세스·서버 인증 기록으로 판단을 보강합니다. 암호화된 구간의 내용이나 실제 로그인 성공까지 문자열에서 추정하지 않습니다.

Echo를 인용하며 프로토콜 도달 불가를 보고한 응답은 요청의 프로토콜 번호와 생성한 오류의 의미를 맞춰 보는 연습입니다. ICMP를 생성할 수 있다는 것과 모든 ICMP 질의를 처리하도록 허용했다는 것은 다른 조건입니다. 단순히 “ICMP를 쓰니 전부 지원해야 한다”라고 결론내리지 말고, 정책·조작·기재된 실습 조건을 구분하고 원래 자극·Code·종단 설정을 확인하세요.

9. 확인한 범위와 남은 실행 검증

과거 검토에서는 여섯 파일 총 1067개 레코드의 프레이밍과 주요 헤더를 오프라인으로 읽었고, BPF 마스크의 0~255 값과 길이·ACK 예제를 계산했습니다. 이것은 저장된 바이트의 검산입니다. 실제 캡처 필터 엔진, Wireshark의 재조립 설정과 GUI 내보내기, 대상 운영체제의 수신·캐시·라우팅 동작을 실행 검증한 것과 구별합니다.

이 가이드의 필터를 직접 실행할 때는 설치 버전, 원본 해시, 사용 명령·설정, 선택 레코드 수를 기록하고 표본 패킷을 원본 바이트와 대조하세요. 결과가 다르면 숫자를 억지로 맞추지 말고 파일 버전·필터 의미·오프로딩·중첩 헤더·재조립 차이부터 점검합니다. 그 차이를 설명하는 과정이 실습의 목적입니다.

복습 · 조건을 바꾸어 생각하기

질문 1. SYN 13개면 서비스 13개인가요?

아닙니다. 같은 대상의 재시도가 포함될 수 있고, 제공 파일에서는 고유 목적지 포트가 6개였습니다.

질문 2. 마스크 0xd0 조건은 왜 두 구간인가요?

32 자리를 검사하지 않지만 16 자리는 1이어야 해서 208~223, 240~255가 선택됩니다.

질문 3. DNS 헤더 기준 10과 UDP 기준 10은 같나요?

아닙니다. UDP 헤더가 8바이트이므로 기준점을 명확히 적습니다.

질문 4. 이번 바이트 검산이 VM 실행 검증을 대신하나요?

저장 필드와 계산을 확인한 범위입니다. 수신 구현의 실제 동작과 도구 실행은 별도입니다.

질문 5. 0x10이 (값&0x18)!=0을 통과하면 PSH와 ACK가 모두 있나요?

ACK 하나만 있어도 비영입니다. 모두를 요구할 때는 (값&0x18)=0x18과 비교해야 합니다. 다른 플래그는 이 마스크가 무시합니다.

질문 6. DNS 고정 헤더의 ARCOUNT=1만 있으면 완전한 EDNS인가요?

추가 레코드가 하나 있다고 선언한 것뿐입니다. 실제 레코드 존재·이름 파싱·타입41·필드 길이를 확인해야 하며 짧은 합성 헤더가 이 한계를 보여 줍니다.

질문 7. IP 31바이트이면 이더넷 채움은 항상15바이트인가요?

기본 태그 없는 Ethernet 데이터 최소46이라는 조건 아래 최소 계산이15입니다. 실제 저장 길이·FCS·링크 형식·추가 채움은 별도 측정합니다.

질문 8. 파일 끝 .pcap이면 전통 PCAP으로 읽어도 되나요?

확장자가 아닌 서명과 구조로 판단합니다. PCAPNG의 메타데이터 블록을 패킷으로 세지 않고 인터페이스와 시간 단위도 확인합니다.

질문 9. 동일 SEQ=2001의 ALPHA와 ALPXA는 같은 데이터 재전송인가요?

동일한 [2001,2006) 범위 중 위치2004의 바이트가 충돌합니다. 충돌 관측과 실제 종단이 어떤 값을 채택했는지는 다른 질문입니다.

질문 10. URG 경계1007이면 어떤 바이트가 와이어에서 삭제됐나요?

삭제된 것으로 결론내리지 않습니다. 예제의 경계 앞1006은F지만 일반/OOB 읽기·인라인 설정·구현을 확인해야 응용이 읽은 값을 설명할 수 있습니다.

질문 11. 0·4·12·28초 SYN의 간격과 평균은 무엇인가요?

간격은4·8·16초이고 합28초/간격3개=약9.33초입니다. 일정한 주기라고 표현하지 않으며 같은 시도 여부도 필드와 문맥으로 확인합니다.

질문 12. 체크섬 산술이 맞으면 RST가 실제 연결을 닫았나요?

형식 검증을 뒷받침할 뿐입니다. 수신 상태·SEQ·정책·구현과 후속 통신·단말 기록이 필요합니다.

질문 13. Time Exceeded 발신자가 보이면 그 주소가 UDP 목적 서버인가요?

대개 경로의 오류 발신자 후보입니다. 바깥 발신자와 인용된 원래 목적지·포트를 분리하고 자극과 대응시켜야 합니다.

질문 14. 1,067을 다시 합산했으면 실습 재검증을 완료했나요?

과거 기록 숫자의 산술 확인일 뿐입니다. 현재 원본의 프레이밍·필드·전체 문항, 도구와 종단 검증은 각각 다른 범위입니다.

질문 15. 상세 보강 페이지가 게시됐으면 둘째 날 전체 완료인가요?

아닙니다. 원본 워크북 전체/추가 목표와 누적 미해결 항목을 직접 대조하는 최종 점검이 남았습니다. 게시와 교육 내용의 검토 완료를 구분합니다.

질문 16. 질문 이름 부분 문자열이 두 패킷에서 보이면 질의를 두 번 한 것인가요?

질문을 포함한 응답일 수 있습니다. QR·방향·ID·시각과 질문을 맞춘 뒤 요청 수와 패킷 수를 구분합니다.

질문 17. 같은 체크섬으로 찾은 인용 원본은 유일한가요?

16비트 값은 충돌할 수 있습니다. 바깥/인용 계층을 나누고 주소·식별자·조각·포트·시각을 함께 대조합니다.

질문 18. 반복 SYN/ACK의 ACK가9001이면 원래 SYN을 직접 보았나요?

통상적인 데이터 없는 SYN 응답이라는 전제 아래 SEQ9000을 역추론한 것입니다. 미관측 자극과 위조/수집 누락 가설을 분리합니다.
