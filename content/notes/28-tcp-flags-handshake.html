1. 플래그는 패킷에 붙은 처리 안내입니다

창구에서 번호표를 뽑는 것과 업무를 마쳤다고 알리는 것은 다른 행동이지요. TCP 플래그도 연결의 시작·확인·종료 같은 처리를 알립니다. 플래그는 따로 존재하는 명령 문자열이 아니라 헤더 안의 비트입니다. 여러 비트가 동시에 켜질 수 있으므로 이름 하나만 보고 패킷 전체를 분류하면 중요한 조합을 놓칠 수 있습니다.

SYN은 순서 번호를 동기화하며 연결을 시작할 때 사용합니다. ACK는 확인 번호 필드가 유효하다는 뜻입니다. ACK 비트가 있다는 사실만으로 상대의 어떤 데이터를 확인했는지 알 수 없으므로 반드시 ACK 숫자를 읽습니다. tcpdump는 ACK를 점(.)으로 보여주기도 합니다. [S.]는 SYN과 ACK가 함께 있다는 뜻입니다.

2. 세 번의 교환에서 무엇을 확인하나요?

A가 SYN과 SEQ 3000을 보냅니다. B는 A의 SYN을 받아 ACK 3001을 돌려주면서 자기 SEQ 9000을 SYN으로 알립니다. A는 ACK 9001을 보냅니다. 이렇게 양쪽이 서로의 시작 번호를 알고 확인합니다. 첫 SYN의 ACK 필드에 어떤 숫자가 들어 있더라도 ACK 비트가 없다면 유효한 확인 정보로 취급하지 않습니다.

이때 주소와 포트뿐 아니라 MSS, 윈도 스케일, SACK 허용 등의 옵션도 확인합니다. 분석가는 첫 SYN을 누가 보냈는지로 역할을 추정할 수 있지만, 프록시·중간 장비와 동시 열기 같은 예외를 고려합니다. 작은 포트가 언제나 서버라는 규칙보다 실제 교환 순서가 더 좋은 근거입니다.

“SYN/ACK가 보였다”는 연결 요청에 대한 응답을 관측했다는 뜻입니다. 마지막 ACK가 안 보인다면 연결 완성을 곧바로 주장할 수 없습니다. 응답 경로가 센서를 지나지 않았는지, 캡처가 끝났는지, 이후 데이터가 있는지 확인합니다.

3. ECN 비트가 더 있다고 이상한 SYN일까요?

혼잡한 도로의 안내판처럼 네트워크가 혼잡을 알릴 방법이 ECN입니다. 기본 ECN에서는 IP 헤더의 표시와 TCP의 ECE/CWR 비트가 함께 역할을 합니다. 연결 협상에서의 비트 의미와 이미 데이터를 교환하는 단계의 의미를 나누어 읽어야 합니다. 모든 ECE를 즉시 발생한 혼잡으로 해석하면 안 됩니다.

교재가 다루는 기본 협상에서는 SYN에 ECE/CWR가 함께 나타날 수 있습니다. 따라서 플래그 바이트가 정확히 0x02인 것만 찾으면 이런 시작 요청을 놓칠 수 있습니다. “SYN=1, ACK=0” 조건으로 후보를 찾고 나머지 비트를 확인하는 이유입니다. 여기서 기본 ECN 설명을 모든 최신 확장 방식의 완전한 상태표로 사용하지는 않습니다.

4. PSH와 패킷 수를 오해하지 않습니다

PSH를 “이 패킷은 최고 우선순위로 보낸다”라고 외우면 곤란합니다. IP 경로의 우선순위나 암호화 여부를 뜻하지 않습니다. 또 PSH 경계가 곧 HTTP 메시지 경계인 것도 아닙니다. 하나의 응용 메시지가 여러 TCP 세그먼트로 나뉘거나 여러 메시지가 한 세그먼트에 실릴 수 있습니다.

TCP는 동시 열기처럼 양쪽이 SYN을 시작하는 상태도 처리할 수 있습니다. 교재의 네 번 교환 예제는 정확히 세 패킷만 있어야 정상이라는 가정의 한계를 보여줍니다. 다만 모든 네 패킷 흐름을 동시 열기라고 부르지 말고, 실제 SYN·ACK 관계와 순서 번호를 추적해야 합니다. 관측 패킷 수가 늘어난 원인이 재전송일 수도 있습니다.

복습 · 조건을 바꾸어 생각하기

질문 1. SYN/ACK만 보이면 웹 접속 성공인가요?

연결 시작 응답을 봤을 뿐입니다. 연결 완성과 응용 요청·응답을 확인해야 합니다.

질문 2. PSH가 없으면 데이터가 없나요?

데이터 유무는 길이로 확인합니다. ACK만 켜진 세그먼트에도 데이터가 있을 수 있습니다.

질문 3. ECE가 있는 SYN을 제외해도 되나요?

연결 후보 탐색에서 누락될 수 있습니다. 기본 ECN 협상과 그 외 플래그를 문맥에서 읽습니다.
