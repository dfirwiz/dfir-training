학습 범위

넷째 날 11강에서는 앞 강의의 행동 연쇄를 관측 이벤트 → 제한된 상태 저장 → 다음 이벤트와 비교 → 조사 후보로 구현하는 원리를 배웁니다. 메시지 본문, DNS A 응답, 외부 연결을 예로 들되 실제 메일·캡처는 사용하지 않고, 상태 만료·메모리·허용 목록·IPv6와 프록시 같은 운영 조건을 함께 다룹니다.

1. 코드를 쓰기 전에 증거 문장부터 쪼갭니다

“메시지에 있던 링크의 주소로 단말이 연결하면 알려 줘”라는 요구는 한 문장처럼 보이지만 센서에는 한 번에 도착하지 않습니다. 메시지 내용, DNS 응답, 연결 시작은 서로 다른 시각의 서로 다른 이벤트입니다. 그래서 먼저 의사코드로 관측과 상태를 나눕니다.

1. 승인된 관측 지점에서 메시지의 URL 후보를 얻는다.
2. URL 후보에서 정규화한 호스트 이름을 저장한다.
3. 그 이름에 대한 유효 DNS 응답 주소를 만료 시각과 함께 저장한다.
4. 내부 주체가 저장된 주소로 연결을 시작하면 조사 후보를 만든다.
5. 후보에 URL·DNS·연결의 시각과 센서 한계를 함께 기록한다.

택배 추적표를 떠올리면 쉽습니다. 송장 번호를 받은 뒤 허브 도착과 배송 완료를 같은 번호로 이어 봅니다. 하지만 네트워크에서는 URL, DNS 이름, IP 주소가 일대일 송장 번호가 아닙니다. CDN은 한 이름에 여러 주소를 주고, 공유 호스팅은 한 주소를 여러 이름이 씁니다. 따라서 주소가 같다는 사실은 연결 고리이지 신원 증명이 아닙니다.

각 단계가 만들고 소비하는 상태
단계직접 관측저장할 최소 상태버릴 시점
메시지디코딩된 엔터티 안의 URL 후보정규화한 이름, 관측 시각, 메시지 식별 후보조직의 조사 창·개인정보 정책 종료

2. 이벤트는 순서대로 오지만 한 함수 안에 있지 않습니다

Zeek의 mime_entity_data(c, length, data)는 메일 프로토콜에서 디코딩한 MIME 엔터티 전체를 전달할 수 있습니다. dns_A_reply(c, msg, ans, a)는 A 레코드 하나마다 주소 a를 전달합니다. 연결 이벤트는 그 주소가 응답 측인지 비교할 수 있습니다. 세 처리기는 독립적으로 실행되므로 그 사이를 잇는 전역 set 또는 table이 필요합니다.

set[string]은 중복 없는 문자열 집합이고, set[addr]은 중복 없는 IP 주소 집합입니다. “값이 있나?”만 묻는다면 set이 알맞습니다. 이름마다 여러 주소·만료 시각을 붙여야 한다면 table[string] of set[addr]처럼 키와 값을 가진 table이 더 자연스럽습니다.

3. MIME 데이터에서 URL을 찾는 일은 생각보다 조심스럽습니다

mime_entity_data의 length는 전달된 데이터의 바이트 수이고, data는 디코딩된 엔터티 문자열입니다. 현행 Zeek 문서는 전체 엔터티를 버퍼링하는 이 이벤트보다 조각을 순차 전달하는 mime_segment_data가 메모리 효율적일 수 있다고 설명합니다. 큰 첨부를 모두 모으면 센서 부담이 커집니다.

작은 합성 문자열 Read https://notice.example/report.에서 호스트 이름은 notice.example입니다. 정규식으로 https?:// 뒤를 자르는 작은 데모는 개념 학습에는 좋지만, 괄호·따옴표·국제화 도메인·HTML 엔터티·리디렉션·사용자 정보 표기에서 쉽게 틀립니다. 운영에서는 메일 게이트웨이의 구조화 URL 로그나 검증된 URL 파서를 우선하고, 원문 전체를 불필요하게 보존하지 않습니다.

조건을 바꾸면

링크가 https://notice.example:8443/report라면 포트는 이름에 포함하지 않습니다. https://NOTICE.example./처럼 대문자와 마지막 점이 있으면 DNS 비교용 이름을 소문자·정규형으로 맞춰야 합니다. 화면 표시 문자열과 실제 링크 대상이 다를 수도 있으므로 “사용자가 본 글자”와 “센서가 본 URI”를 구분합니다.

4. DNS 응답은 이름과 주소를 잇되 TTL을 잊지 않습니다

dns_A_reply의 마지막 인자 a: addr는 IPv4 A 답의 주소입니다. IPv6는 별도의 AAAA 응답을 함께 처리해야 합니다. 답이 여러 개면 이벤트도 각 답에 대해 발생할 수 있으므로 “마지막 주소 하나”로 덮어쓰면 누락됩니다. CNAME 연쇄, 캐시된 답, 재귀 리졸버의 외부 질의도 주체를 흐릴 수 있습니다.

예를 들어 이름 상태가 10:00:00에 생기고 DNS TTL이 300초라면 단순 유효 종료는 10:00:00 + 300초 = 10:05:00입니다. 조직이 상관 창을 최대 15분으로 정했더라도 이 예에서는 TTL 5분을 넘겨 같은 주소를 자동 연결하지 않는 편이 보수적입니다. 반대로 TTL을 관측하지 못했다면 임의의 긴 기간을 사실처럼 쓰지 말고 정책상 짧은 상한과 불확실성을 기록합니다.

Zeek의 &create_expire, &read_expire, &write_expire는 각각 생성·마지막 읽기·마지막 쓰기 뒤의 만료를 표현합니다. 이 속성은 변수 이름이 아니라 현재 컨테이너 값에 붙는다는 점이 중요합니다. 컨테이너를 새 값으로 통째로 다시 대입하면 만료 속성이 사라질 수 있어 현행 문서의 주의 사항을 확인해야 합니다.

5. 주소 일치는 경보가 아니라 조사 후보입니다

연결 이벤트에서 c$id$resp_h in related_addresses를 검사하면 응답 측 주소가 상태에 있는지 묻습니다. in은 “집합의 구성원인가?”라는 연산자입니다. 참이라도 실제 웹 요청 성공, 사용자의 클릭, 침해 성공을 뜻하지 않습니다. SYN만 보고 끝났을 수도 있고, 주소가 공유 CDN일 수도 있습니다.

6. 오탐보다 먼저 상태의 수명과 비용을 설계합니다

하루 50,000개의 고유 이름을 저장하고 항목당 이름·주소·시각·컨테이너 오버헤드를 보수적으로 200바이트라고 가정하면 원시 추정은 50,000 × 200 = 10,000,000바이트, 약 10MB입니다. 실제 메모리는 런타임 자료구조와 복제 방식 때문에 더 클 수 있습니다. 만료가 없고 매일 새 이름이 쌓이면 30일 단순 합계는 약 300MB이며, 클러스터 복제까지 더해질 수 있습니다.

허용 목록은 오탐을 줄이지만 “안전 목록”이 아닙니다. 조직이 자주 쓰는 도메인도 계정 탈취·공급망 변경·공유 호스팅 때문에 조사 가치가 생길 수 있습니다. 후보를 완전히 버리기보다 우선순위·억제 기간·예외 근거를 기록하고 주기적으로 재검토합니다. 현행 Notice Framework는 note와 identifier를 이용해 같은 유형·대상의 중복 notice를 일정 기간 억제할 수 있습니다.

현행 구현 차이

2026년 현재도 위 이벤트와 컨테이너 원리는 유효하지만, 운영 구현은 MIME 조각 처리, A와 AAAA, 컨테이너 만료, 클러스터 상태 분배, 구조화 로그를 함께 고려해야 합니다. 오래된 예제 한 파일을 복사해 바로 배치하지 말고 현재 설치 버전의 이벤트 시그니처와 로드 정책을 확인합니다.

복습과 해설

1. 왜 세 이벤트를 한 함수에서 처리하지 않나요?
메시지, DNS, 연결은 서로 다른 시각과 분석기에서 발생합니다. 필요한 최소 상태를 제한된 기간 보존해 독립 이벤트를 이어야 합니다.
2. A 응답 주소가 집합에 있으면 링크 클릭이 확정되나요?
아닙니다. 주소 일치는 상관 후보입니다. 공유 주소, 캐시, 다른 애플리케이션을 배제하고 단말·프록시 증거를 확인해야 합니다.
3. 조건을 IPv6로 바꾸면 무엇이 달라지나요?
A만 처리하면 AAAA 경로를 놓칩니다. IPv4·IPv6 답과 연결을 모두 수집하고, 주소 계열마다 센서 가시성이 같은지 확인해야 합니다.
4. 상태를 영원히 보관하면 더 정확해지나요?
아닙니다. 오래된 이름↔주소 관계가 새 연결과 잘못 이어지고 메모리·개인정보 비용이 커집니다. TTL과 조사 목적에 맞는 만료가 필요합니다.
5. URL 정규식이 한 번 동작했으면 운영에 충분한가요?
아닙니다. URI 문법과 HTML·메일 인코딩의 예외가 많습니다. 구조화된 게이트웨이 로그나 검증된 파서를 우선하고 합성 정상·경계 표본으로 검증합니다.

공식 자료와 확인일

2026-11-25에 Zeek 9.0.0 MIME 이벤트의 전체 엔터티·조각 처리 차이, Zeek 9.0.1 DNS A/AAAA 응답 이벤트 인자, Zeek set·table 타입, 컨테이너 만료 속성과 값 재대입 주의점, Notice Framework의 식별자 기반 중복 억제를 확인했습니다. 코드는 교육용 의사 표현이며 Zeek·메일·캡처·외부 시스템 시험은 실행하지 않았습니다.
