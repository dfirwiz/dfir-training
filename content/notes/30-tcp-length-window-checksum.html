학습 범위와 예제

둘째 날 8강 · 교재 인쇄 86~97쪽의 학습 주제를 자체 예제와 해설로 풀었습니다. 아래 주소·숫자·흐름은 별도 표시가 없으면 가상 학습 예시입니다. 명령은 분석 절차이며 실제 실행 출력으로 제시하지 않습니다.

1. 데이터가 몇 바이트인지 먼저 계산해 봅시다

상자 전체 무게만으로 내용물 무게를 알 수는 없지요. 포장 무게를 빼야 합니다. IPv4 패킷에서 TCP 데이터 길이를 구할 때도 IP 헤더와 TCP 헤더를 빼야 합니다. 두 헤더 모두 옵션 때문에 길이가 달라질 수 있으므로 늘 20바이트씩 빼면 틀릴 수 있습니다.

IPv4 IHL은 ip[0]의 아래 네 비트이고, TCP Data Offset은 tcp[12]의 위 네 비트입니다. 각각 4를 곱합니다. 가상 예시에서 IP Total Length가 120, IHL이 6, TCP Data Offset이 8이면 IP 헤더 24바이트, TCP 헤더 32바이트입니다. 데이터는 120-24-32=64바이트입니다.

IP 전체 길이       120바이트
IP IHL              6 × 4 = 24바이트
TCP Data Offset     8 × 4 = 32바이트
TCP 데이터         120 - 24 - 32 = 64바이트

2. 계산식에 넣기 전에 유효한 입력인지 봅니다

이 계산은 완전한 비단편 IPv4/TCP 패킷을 전제로 한 기본식입니다. IP 조각마다 TCP 헤더가 있는 것은 아닙니다. 캡처가 snaplen 때문에 잘렸다면 헤더에 쓰인 전체 길이와 파일에 실제로 저장된 길이도 다를 수 있습니다. 헤더가 주장하는 데이터 길이와 확보한 데이터 바이트 수를 구별합니다.

헤더 길이가 최소 길이보다 작거나 전체 길이보다 길면, 바로 음수 데이터를 보고할 것이 아니라 손상·잘못된 기준점·불완전 수집·비정상 패킷을 점검합니다. Ethernet의 패딩이나 링크 계층 헤더를 IP Total Length에 다시 더하는 실수도 피합니다. 먼저 시작점을 그림으로 표시하고 길이끼리 관계가 맞는지 검사하세요.

3. 수신 윈도는 “지금 더 받을 수 있는 범위”입니다

식당 창구에서 “주문을 다섯 개 더 받을 수 있습니다”라고 말하는 장면을 떠올려 보세요. TCP의 수신 윈도는 이와 비슷하게 상대에게 수신 여유를 알립니다. 자신의 송신 속도를 직접 적는 필드가 아닙니다. 연결 양방향의 윈도는 따로 읽어야 합니다.

윈도 0은 상대가 당분간 새 데이터를 보내지 않도록 알리는 상태입니다. 곧바로 공격이나 연결 종료를 뜻하지 않습니다. 응용이 읽기를 멈췄거나 처리 속도가 부족할 수 있습니다. 이후 윈도 갱신과 프로브를 보면서 회복 여부를 확인합니다.

수신 윈도만으로 실제 전송 속도가 결정되는 것은 아닙니다. 송신자는 혼잡 제어, 링크 용량, 애플리케이션의 데이터 생성 속도 등의 제한도 받습니다. 수신 흐름 제어와 네트워크 혼잡 제어를 분리해서 생각해야 원인을 정확히 좁힐 수 있습니다.

4. MTU보다 큰 세그먼트가 파일에 보인다면

TSO는 큰 송신 데이터를 나누는 일을 네트워크 장치 쪽에 맡기는 기능입니다. 호스트 안에서 그 처리 전에 캡처하면 실제 선로에서 보낼 프레임보다 큰 단위가 보일 수 있습니다. 반대로 수신 집약 기능은 여러 수신 단위를 합친 모습으로 관측되게 할 수 있습니다. 파일의 한 레코드가 항상 선로의 한 프레임이라는 가정을 주의하세요.

따라서 길이가 유난히 크면 점보 프레임·오프로딩·캡처 지점을 확인합니다. 운영 서버의 설정을 무조건 바꾸기보다, 분석용 수집 지점과 센서 구성의 적합성을 검토하고 필요한 비교 캡처를 얻습니다. 교재의 센서 권고를 운영 서버 전체의 즉시 변경 지시로 받아들이지 않습니다.

5. 체크섬은 IP 주소의 영향도 받습니다

TCP 체크섬은 TCP 헤더와 데이터만으로 계산하지 않습니다. 출발지·목적지 IP 주소, 프로토콜, TCP 길이 같은 가상 헤더 정보도 계산에 참여합니다. 가상 헤더는 독립적인 실제 TCP 앞머리로 전송되는 것이 아니라 계산용 구성입니다. 주소를 바꾸는 NAT나 패킷 편집에서 TCP 체크섬도 고려해야 하는 이유입니다.

체크섬 오류 표시를 보면 실제 손상과 체크섬 오프로딩을 구별합니다. 송신 호스트에서 장치가 최종 값을 채우기 전에 수집했을 수 있습니다. 다른 지점의 같은 트래픽, 수집 방향, 오프로딩 설정, 캡처 잘림을 대조하세요. 실제 와이어의 잘못된 체크섬을 수신 호스트가 어떻게 처리했는지는 유효성 검사와 로그를 함께 확인합니다. 체크섬은 암호학적 무결성이나 송신자 인증 수단도 아닙니다.

복습 · 조건을 바꾸어 생각하기

질문 1. IP 전체 100, IHL 5, TCP Offset 10이면 데이터는?

100-20-40=40바이트입니다. 캡처와 단편 조건도 확인합니다.

질문 2. 윈도 0은 RST와 같은가요?

아닙니다. 수신 여유가 없는 흐름 제어 상태이며 이후 회복할 수 있습니다.

질문 3. 출발지 IP만 바꾸면 TCP 체크섬은 그대로여도 되나요?

가상 헤더에 주소가 포함되므로 TCP 체크섬에도 영향을 줍니다.

질문 4. 큰 세그먼트와 체크섬 오류가 함께 보이면 공격인가요?

오프로딩 전후의 수집 차이도 후보입니다. 수집 조건과 다른 관측 지점을 대조합니다.
