학습 범위

넷째 날 12강에서는 단일 문자열 대신 정상 행위의 범위와 변화를 관찰합니다. HTTP 요청·응답 크기, TLS 인증서 다양성, TCP 특성, 장기 연결, 대용량 흐름과 연결 수를 예로 들어 임계값·기준선·실시간 중간 점검을 설계하고, 이상이 곧 침해는 아니라는 조사 원칙을 익힙니다.

1. 상관분석은 데이터 가까이에서 시작하되 한곳에 가두지 않습니다

센서가 이미 HTTP, TLS, TCP 연결 상태를 해석했다면 일부 요약과 후보화는 센서 가까이에서 수행할 수 있습니다. 원시 패킷을 모두 중앙으로 보낸 뒤 처음부터 다시 해석하는 것보다 빠르게 반응하고 전송량을 줄일 수 있기 때문입니다. 그렇다고 SIEM·데이터 레이크가 필요 없다는 뜻은 아닙니다. 센서는 짧은 시간의 네트워크 문맥에 강하고, 중앙 분석은 여러 센서·자산·사용자·장기간 이력을 연결하는 데 강합니다.

동네 체온계를 비유로 들어볼게요. 방마다 온도를 바로 재면 급격한 변화를 빨리 알 수 있지만, 건물 전체 냉난방 문제는 중앙 기록과 설비 상태를 함께 봐야 합니다. 네트워크 센서도 마찬가지입니다. 패킷 손실, 비대칭 경로, 암호화, 클러스터 분산 때문에 센서 한 대의 값이 전체 진실은 아닙니다.

2. 임계값 하나보다 비교 가능한 기준선을 만듭니다

“연결이 100개 넘으면 이상” 같은 숫자는 간단하지만 사용자·서버·요일·배치 시간에 따라 의미가 달라집니다. 기준선은 정상이라는 보증서가 아니라 같은 조건에서 흔히 보이던 범위입니다. 자산 역할, 업무 시간, 프로토콜, 방향, 소프트웨어 변경 전후를 나눠야 합니다.

합성 예로 한 업무 단말의 5분당 외부 연결 수가 지난 20개 같은 시간대 구간에서 평균 40개이고 표준편차가 10개라고 합시다. 현재 85개라면 단순 z 점수는 (85 - 40) ÷ 10 = 4.5입니다. 평균보다 4.5표준편차 높다는 변화 후보지만, 새 화상회의·업데이트·원격지원 도입일 수 있습니다. 표본이 적거나 분포가 한쪽으로 치우치면 z 점수 자체도 부적절할 수 있습니다.

3. HTTP·TLS·TCP의 단순 규칙은 출발점입니다

일반적인 웹 조회는 작은 요청 뒤 큰 응답이 올 때가 많습니다. Zeek의 HTTP 로그에는 압축 해제 기준의 request_body_len과 response_body_len이 있을 수 있습니다. 합성 흐름에서 요청 본문 800바이트, 응답 본문 48,000바이트라면 응답/요청 비율은 48,000 ÷ 800 = 60입니다. 하지만 파일 업로드는 반대이고, 스트리밍·WebSocket·HTTP/2 다중화·암호화 트래픽은 이 단순 모양을 깨뜨립니다.

TLS 서버가 한 인증서만 제공할 것이라는 가정도 공유 호스팅, 인증서 갱신, 클라이언트 인증, 연결 재개에서 달라집니다. 인증서 수 변화는 “중간자 공격” 판정이 아니라 서버 이름, 체인, 발급자, 배포 변경을 확인할 후보입니다. TCP 옵션도 운영체제·커널·로드밸런서·NIC 오프로딩·경로에 따라 변합니다. 옵션 변화만으로 새 장비나 조작을 확정하지 않습니다.

4. 끝나지 않은 연결은 중간에 살펴봐야 합니다

conn.log의 완성된 요약은 보통 연결이 종료되거나 만료될 때 기록됩니다. 연결이 몇 시간 유지되거나 그동안 많은 바이트를 보낸다면 종료만 기다리는 정책은 늦습니다. 현행 Zeek의 ConnPolling 프레임워크는 연결을 일정 간격으로 확인하고 콜백이 다음 확인 간격을 반환하도록 합니다. 음수 간격을 반환하면 감시를 끝냅니다.

예를 들어 첫 확인을 5분 뒤, 이후 5분마다 한다고 합시다. 10:00에 시작한 연결은 10:05, 10:10, 10:15에 후보 조건을 확인합니다. 실제 알림 시간은 스케줄링·센서 부하·네트워크 시간에 따라 정확히 벽시계 5분과 같지 않을 수 있습니다. 오프라인 캡처에서는 Zeek의 네트워크 시간이 패킷 타임스탬프를 따라가므로 “실시간 5분”과도 다릅니다.

흔한 오해

장기 연결은 곧 터널이나 명령제어가 아닙니다. 메시징, VPN, 데이터베이스 풀, 원격 관리도 오래 유지됩니다. 반대로 짧게 끊어지는 반복 연결도 조사 가치가 있을 수 있습니다. 지속 시간·방향별 바이트·주기·목적지·종단 프로세스를 함께 봅니다.

5. 대용량 흐름과 많은 연결은 단위를 먼저 고정합니다

conn.log의 orig_bytes와 resp_bytes는 전송계층 페이로드 바이트이고, orig_ip_bytes와 resp_ip_bytes는 IP 계층 바이트입니다. 헤더 포함 여부가 다르므로 서로 섞어 임계값을 계산하지 않습니다. missed_bytes가 0이 아니면 센서가 놓친 TCP 바이트가 있어 용량과 재조립 해석이 불완전할 수 있습니다.

합성 흐름의 시작 측 페이로드가 600MB이고 10분 동안 전송되었다고 합시다. 십진 단위 평균 속도는 600MB × 8 = 4,800Mb, 4,800Mb ÷ 600초 = 8Mb/s입니다. 이것은 파일 크기나 반출 성공을 뜻하지 않습니다. 재전송, 압축, 프로토콜 오버헤드, 중간 차단, 목적지 수신 결과를 별도로 확인합니다.

연결 수는 호스트별로 집계할 수 있지만 분모가 중요합니다. 5분에 300개와 1시간에 300개는 다릅니다. 서버와 워크스테이션의 역할도 다릅니다. 클러스터에서 단순한 로컬 set만 세면 worker별 일부만 보일 수 있습니다. 현행 SumStats는 관측값, 키, reducer, epoch을 분리해 단일·클러스터 배포의 구간 집계를 돕습니다.

6. 후보는 억제·설명·피드백까지 설계합니다

후보 규칙에는 숫자만 넣지 말고 “무엇을, 어느 구간에서, 어떤 키로, 왜 보는가”를 적습니다. 예를 들어 “업무 단말별 5분 외부 연결 수가 같은 역할·시간대 기준선보다 크게 증가”처럼 표현합니다. 경보에는 현재값, 기준값, 구간, 센서, UID 예시, 누락 여부를 포함해야 분석가가 다시 계산할 수 있습니다.

Notice Framework의 identifier는 같은 대상의 중복 후보를 억제하는 데 쓸 수 있지만, 너무 긴 억제는 상태 악화를 숨깁니다. 임계값을 넘은 첫 시점, 최고값, 종료 또는 회복 시점을 따로 보존하는 방식이 유용합니다. 허용 목록과 임계값 변경은 변경 사유·소유자·만료일을 남깁니다.

복습과 해설

1. 데이터 가까이에서 상관하면 SIEM은 필요 없나요?
아닙니다. 센서는 빠른 프로토콜 문맥에, 중앙 분석은 여러 데이터 원천과 장기 이력에 강합니다. 두 계층의 역할을 나눕니다.
2. 평균보다 4.5표준편차 높으면 침해인가요?
아닙니다. 비교 조건 안에서 큰 변화라는 뜻입니다. 분포·표본·업무 변경을 확인하고 종단 증거로 가설을 검증합니다.
3. 600MB가 외부로 향했으면 600MB 유출이 확정되나요?
아닙니다. 어느 계층의 바이트인지, 재전송·손실·차단·수신 결과를 확인해야 합니다. 흐름 바이트는 파일 반출 결과와 같지 않습니다.
4. 장기 연결을 conn.log 종료 뒤에만 보면 어떤 문제가 있나요?
오래 지속되는 동안의 변화를 늦게 알게 됩니다. 중간 polling이나 주기 집계를 사용하되 정상 장기 세션과 센서 비용을 함께 고려합니다.
5. 조건을 클러스터로 바꾸면 로컬 집계가 왜 위험한가요?
부하 분산으로 worker마다 일부 흐름만 볼 수 있습니다. 클러스터 투명 집계 프레임워크나 중앙 결합을 사용하고 어떤 범위를 센 값인지 기록합니다.

공식 자료와 확인일

2026-11-25에 Zeek 9.0.1 SumStats의 관측·reducer·epoch과 클러스터 집계, ConnPolling의 연결 중간 점검 방식, conn.log의 방향별 바이트·패킷·상태 필드, HTTP 요청·응답 본문 길이 필드, Notice Framework의 중복 억제 원리를 확인했습니다. 수치와 흐름은 정상 합성 예제이며 Zeek 스크립트·캡처·외부 시스템 시험은 실행하지 않았습니다.
