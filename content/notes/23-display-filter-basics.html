시작하며 — 패킷이 너무 많습니다

첫째 날에는 패킷을 열어 보고, 그 안에 어떤 정보가 들어 있는지 살펴봤습니다. 이더넷 주소도 있었고, IP 주소도 있었지요. 이제 화면에 보이는 숫자들이 조금씩 의미를 갖기 시작했을 겁니다.

그런데 실제 분석에서는 다른 문제가 기다리고 있습니다.

패킷이 너무 많습니다.

패킷이 열 개라면 하나씩 눌러 보면 됩니다. 백 개까지도 어떻게든 해볼 수 있겠지요. 하지만 백만 개라면 어떨까요?

그 안에서 특정 컴퓨터가 보낸 DNS 요청을 찾으려고 처음부터 끝까지 내려가다 보면, 정작 무엇을 찾고 있었는지 잊어버릴 수도 있습니다.

이럴 때 필요한 것이 필터입니다. 우리가 찾으려는 조건을 도구에 알려 주고, 그 조건에 맞는 패킷부터 살펴보는 것이지요.

이번 시간에는 필터 문장을 외우기 전에, 내가 알고 싶은 것을 어떻게 조건으로 바꾸는지부터 익혀 보겠습니다.

이번 시간의 목표

표시 필터와 캡처 필터를 구별하고, 주소·프로토콜·문자열 조건을 조합해 원하는 패킷을 찾습니다. 찾은 결과로 무엇을 말할 수 있는지, 필터 밖에서 무엇을 더 확인해야 하는지도 함께 생각합니다. 주소와 도메인은 학습용 예시이며, 아래 표와 그림은 실제 캡처의 실행 출력이 아닙니다.

1. 필터를 걸면 나머지 패킷은 없어질까요?

휴대전화 사진첩을 떠올려 보세요.

사진이 수천 장 있는데 작년에 찍은 사진만 보고 싶습니다. 날짜로 범위를 좁히면 작년 사진들만 화면에 나타나지요. 그렇다고 올해 찍은 사진이 삭제된 것은 아닙니다. 날짜 조건을 풀면 다시 나타납니다.

Wireshark의 표시 필터(Display Filter)도 비슷합니다.

이미 확보한 패킷 중에서 조건에 맞는 것을 화면에 보여 줍니다. 조건에 맞지 않는 패킷은 잠시 가려집니다.

예를 들어 표시 필터 입력란에 다음과 같이 적습니다.

dns

그러면 Wireshark가 DNS로 해석한 패킷들이 표시됩니다. 필터를 지우면 다른 패킷도 다시 보입니다. 표시 필터를 적용하는 것만으로 원본 캡처 파일의 패킷이 삭제되지는 않습니다. [1]

여기서 함께 구별해야 하는 것이 캡처 필터(Capture Filter)입니다.

화면에서 고르기와 수집할 때 고르기의 차이
구분표시 필터캡처 필터
조건을 적용하는 단계확보한 패킷을 화면에서 볼 때패킷을 수집할 때
하는 일보여 줄 패킷을 선택수집할 패킷을 선택
조건 밖의 패킷원본에 남아 있어 다시 볼 수 있음해당 수집에서는 확보되지 않음
예시 문법ip.addr == 192.0.2.10host 192.0.2.10

분석하다가 “아, DNS뿐 아니라 다른 통신도 봐야겠는데?”라는 생각이 들 수 있습니다.

표시 필터였다면 조건을 바꾸면 됩니다. 하지만 캡처할 때부터 다른 통신을 제외했다면, 그 캡처 파일에는 조사에 필요한 패킷이 없을 수 있습니다.

화면에서 가리는 것과 처음부터 수집하지 않는 것은 결과가 다릅니다.

또 두 필터는 문법도 다릅니다. 표시 필터에 사용하던 문장을 캡처 필터 입력란에 그대로 넣으면 동작하지 않을 수 있는 이유가 여기에 있습니다. 캡처 필터 문법은 다음 단계에서 별도로 다룹니다.

2. Wireshark는 어떻게 ‘DNS에서 물어본 이름’만 찾아낼까요?

이번에는 이런 질문을 해보겠습니다.

“DNS 통신 중에서 backup이라는 글자가 들어간 이름을 찾아보고 싶어요.”

패킷 전체에서 backup이라는 글자를 검색하면 될까요?

그렇게 찾을 수도 있습니다. 하지만 패킷 어디에서 발견된 글자인지가 중요합니다. 우리가 찾고 싶은 것은 DNS에서 질의한 이름인데, 다른 데이터에 들어 있는 글자가 검색될 수도 있으니까요.

택배 송장을 떠올려 보겠습니다.

송장에는 보내는 사람, 받는 사람, 주소, 배송 요청 사항이 적혀 있습니다. 우리가 받는 사람의 이름을 찾는다면, 종이 전체에서 비슷한 글자를 찾는 것보다 ‘받는 사람’ 칸을 확인하는 편이 정확하겠지요.

Wireshark도 패킷의 구조를 해석해서 각각의 칸에 이름을 붙입니다.

이처럼 프로토콜의 구조를 해석하는 기능을 디섹터(Dissector)라고 부릅니다. 처음에는 ‘패킷의 각 부분이 무엇인지 구별해 주는 해석기’ 정도로 이해하면 됩니다.

DNS를 해석한 결과에는 다음과 같은 필드가 있습니다.

dns.qry.name

여기서 필드는 특정 정보를 담는 칸입니다. dns.qry.name은 DNS의 질문 부분에 들어 있는 질의 이름을 가리킵니다.

이제 우리가 원하는 조건을 적을 수 있습니다.

dns.qry.name contains "backup"

말로 읽으면 다음과 같습니다.

“DNS 질의 이름에 backup이라는 문자열이 들어 있는 패킷을 보여 주세요.”

필터 문장이 낯설 때는 이렇게 우리말로 읽어 보세요. 조건이 의도와 맞는지 확인하기가 훨씬 쉬워집니다.

헤더에 실린 값과 도구가 계산한 정보

Wireshark가 보여 주는 정보가 모두 헤더에 그대로 쓰여 있는 것은 아닙니다. 일부는 여러 조각이나 패킷을 분석하면서 도구가 알아낸 정보입니다. 예를 들어 ip.fragment.overlap은 IPv4 조각의 구간이 겹친다는 분석 결과를 선택하는 데 쓰입니다. ‘디섹터가 제공하는 필드와 분석 정보’를 바탕으로 필터가 동작한다는 점을 기억하세요.

필드 이름만 적으면 그 필드의 존재를 검사하는 경우도 있습니다. 특히 참·거짓 필드에서는 ‘필드가 있다’와 ‘값이 참이다’를 구별해야 합니다. 예를 들어 tcp.flags.syn만으로 SYN 값이 1인 패킷만 고른다고 생각하면 안 됩니다. 실제로 SYN이 설정된 것을 찾을 때는 tcp.flags.syn == 1처럼 값을 비교합니다. TCP의 의미는 이후 강의에서 더 자세히 다룹니다. [2]

3. 필터의 기본 모양을 알아봅시다

많이 사용하는 필터는 다음 모양입니다.

어느 필드를 볼 것인가   어떻게 비교할 것인가   무엇과 비교할 것인가

실제 문장으로 바꿔 보겠습니다.

ip.src == 192.0.2.10

세 부분으로 나누면 어렵지 않습니다.

필터 한 문장을 세 부분으로 나누어 읽기
부분뜻
ip.srcIPv4 출발지 주소를 보겠습니다

따라서 이 필터는 출발지 IPv4 주소가 192.0.2.10인 패킷을 찾습니다.

그럼 이 컴퓨터가 받은 패킷은 어떻게 찾을까요?

ip.dst == 192.0.2.10

src를 dst로 바꾸었습니다. 목적지 주소를 비교하는 것입니다.

이번에는 이 컴퓨터가 보내거나 받은 패킷을 모두 보고 싶습니다.

ip.addr == 192.0.2.10

기본적인 IPv4 통신에서 ip.addr를 사용하면 출발지나 목적지 주소에 해당 값이 있는 패킷을 찾을 수 있습니다.

어느 방향의 통신을 찾는지에 따라 필드 선택하기
알고 싶은 것필터
이 컴퓨터가 보낸 패킷ip.src == 192.0.2.10
이 컴퓨터가 받은 패킷ip.dst == 192.0.2.10
이 컴퓨터가 보내거나 받은 패킷ip.addr == 192.0.2.10

단어 하나가 바뀌었지만, 조사 대상은 달라졌습니다.

“이 컴퓨터와 관련된 통신”을 찾으면서 출발지 조건만 사용하면 응답을 놓칠 수 있습니다. 필터를 입력하기 전에 통신의 어느 방향을 보고 싶은지 먼저 생각해야 합니다.

주소와 장비의 신원은 구별합니다

위 예제는 단순한 IPv4 통신을 가정합니다. 실제 분석에서는 NAT나 터널, ICMP 오류에 인용된 내부 패킷 때문에 주소의 해석이 달라질 수 있습니다. ip.addr가 선택한 주소가 어느 계층에 있는지 상세 창에서 확인하고, IP 주소 하나만으로 실제 사용자나 프로그램까지 확정하지 않습니다. IPv6 주소에는 ipv6.addr 등 별도 필드를 사용합니다.

ip.len은 IPv4 헤더를 포함한 전체 길이입니다. 프레임 전체 길이나 응용 데이터 길이와 혼동하지 마세요. 연산자를 선택할 때도 ‘어떤 단위의 값을 비교하는가’를 함께 생각하면 실수를 줄일 수 있습니다.

4. 조건이 두 개라면 어떻게 할까요?

조금 더 구체적인 질문을 해보겠습니다.

“192.0.2.10이 보낸 패킷 중에서 DNS만 보고 싶어요.”

조건이 두 개입니다.

첫 번째는 출발지 주소입니다.

ip.src == 192.0.2.10

두 번째는 DNS라는 조건입니다.

dns

두 조건을 모두 만족해야 하므로 and로 연결합니다.

ip.src == 192.0.2.10 and dns

이제 질문을 바꿔 보겠습니다.

“DNS나 ICMP 패킷을 보고 싶어요.”

이번에는 둘 중 하나만 해당해도 됩니다.

dns or icmp

and는 모두 만족해야 하고, or는 하나 이상 만족하면 됩니다.

괄호도 유용합니다. 다음 질문을 보세요.

“이 컴퓨터와 관련된 통신 중에서 TCP 또는 UDP를 보고 싶어요.”
ip.addr == 192.0.2.10 and (tcp or udp)

괄호 안의 tcp or udp를 하나의 묶음으로 읽으면 됩니다.

필터가 길어질수록 머릿속으로만 조건을 연결하지 말고, 함께 판단할 조건을 괄호로 묶어 의도를 드러내는 습관을 들이세요.

and는 &&, or는 ||, not은 !로도 적을 수 있습니다. 처음에는 읽기 쉬운 단어 형태로 익혀도 충분합니다.

5. contains와 matches는 무엇이 다를까요?

앞에서 사용한 contains는 특정 문자열이 들어 있는지 찾습니다.

dns.qry.name contains "backup"

다음 이름들이 있다고 가정해 보겠습니다. 실제 캡처의 출력이 아닌 학습용 예시입니다.

포함 여부와 시작 위치 패턴의 차이 · 모두 소문자로 작성한 가상 질의 이름
질의 이름contains "backup"matches "^backup"
backup.example예예
files-backup.example예아니요
oldbackup.example예아니요
portal.example아니요아니요

backup이 앞에 있든 중간에 있든, 해당 문자열이 들어 있으면 contains 조건에 맞습니다.

그런데 이번에는 이름이 backup으로 시작하는 경우만 보고 싶습니다.

이때는 문자열의 모양을 표현하는 정규표현식과 matches를 사용할 수 있습니다.

dns.qry.name matches "^backup"

여기서 ^는 문자열의 시작을 나타냅니다.

따라서 위 예시에서는 backup.example이 해당합니다. files-backup.example에는 backup이라는 글자가 있지만, 그 글자로 시작하지는 않으므로 해당하지 않습니다.

처음에는 이렇게 구별하면 됩니다.

  • contains: 이 글자가 들어 있나요?
  • matches: 이 패턴에 맞나요?

현재 Wireshark에서 contains는 대소문자를 구별하며, matches는 기본적으로 대소문자를 구별하지 않습니다. 두 조건을 비교할 때는 이 차이도 살펴야 합니다. [2]

현재 문법으로 보충 · 대소문자와 정규표현식

소문자 검색어로 대소문자 차이를 무시하고 포함 여부를 찾고 싶다면 lower(dns.qry.name) contains "backup"처럼 필드를 소문자로 바꿔 비교할 수 있습니다. 단순 문자열 검색이면 먼저 contains를 사용하고, 위치·반복 같은 패턴이 필요할 때 정규표현식을 사용하세요. 정규표현식에 역슬래시가 들어가면 문자열 해석과 패턴 해석의 두 단계를 고려해야 하므로, 복잡한 식은 작은 예시로 먼저 검증하는 편이 좋습니다. [2]

그런데 질의 이름을 찾았는데 응답도 보이네요?

다음 필터를 적용했는데 DNS 응답까지 나타날 수 있습니다.

dns.qry.name contains "backup"

필터가 잘못된 것일까요?

DNS 응답에도 원래 질문한 이름이 들어 있을 수 있습니다. 따라서 질의 이름 필드가 있다는 사실만으로 그 패킷이 요청이라는 뜻은 아닙니다.

요청만 찾으려면 조건을 하나 더 붙입니다.

dns.flags.response == 0 and dns.qry.name contains "backup"

dns.flags.response는 응답 여부를 나타내는 필드이며, 값이 0이면 요청입니다. [3]

이 차이는 패킷 수를 셀 때 중요합니다.

필터 결과가 열 개라고 해서 곧바로 “DNS 요청을 열 번 보냈다”고 적으면 안 됩니다. 요청과 응답이 함께 선택되었을 수 있으니까요.

무엇을 골랐는지 이해한 다음에 개수를 해석해야 합니다.

6. 표시 필터가 있는데 ‘패킷 찾기’는 왜 필요할까요?

첫째 날에 사용한 Find Packet을 기억하시나요?

문자열을 찾을 수 있는데, 표시 필터에서도 contains를 쓸 수 있습니다. 비슷해 보이지만 사용하는 목적이 조금 다릅니다.

문서에서 특정 단어를 검색하는 상황을 생각해 보세요.

하나는 그 단어가 들어 있는 문장만 따로 모아 보는 방법입니다. 다른 하나는 원래 문서에서 해당 위치로 이동해서 앞뒤 문단을 함께 읽는 방법이지요.

표시 필터는 조건에 맞는 패킷들을 모아 보는 데 유용합니다.

Find Packet은 현재 표시된 목록에서 조건에 맞는 패킷으로 이동하므로, 그 주변 흐름을 살피는 데 유용합니다.

이때 DNS 필터만 계속 적용해 놓으면 뒤이어 발생한 TCP 통신은 가려져 있을 수 있습니다.

필터는 필요한 것을 찾게 해 주지만, 필터 밖의 정보도 있다는 사실은 분석자가 기억해야 합니다.

Find Packet도 이미 걸려 있는 표시 필터 밖의 정보를 저절로 모두 보여 주는 기능은 아닙니다. 문맥을 넓히려면 현재 표시 조건부터 확인합니다. 이전에 배운 스트림 분석과도 연결해 보세요.

7. 과거의 설명을 현재 버전에 맞춰 읽어야 하는 부분

이전 버전의 학습 자료에는 다음과 같은 형태의 필터를 주의하라는 설명이 나옵니다.

ip.addr != 192.0.2.10

의도는 “이 주소와 관련된 패킷을 제외하겠다”는 것입니다.

그런데 구버전에서는 여러 주소 중 하나라도 비교 대상과 다르면 조건에 맞을 수 있었습니다. 예를 들어 출발지가 192.0.2.10이어도 목적지 주소가 다르기 때문에 패킷이 남는 식입니다.

여기에는 버전에 따른 변화가 있습니다.

Wireshark 3.6부터 !=의 의미가 바뀌었습니다. 따라서 구버전 동작을 현재 버전에서도 그대로 발생하는 문제로 외우면 안 됩니다. 현재 !=는 해당 필드의 모든 값이 비교 대상과 다른지를 검사합니다. [2]

산술 연산에 관한 과거 설명도 그대로 적용하지 않습니다. 현재 표시 필터는 숫자 필드의 덧셈·뺄셈 등도 지원합니다. 다만 이런 연산과, 여러 패킷을 해석해 조각 중첩이나 재전송을 판단하는 분석 기능은 구별해야 합니다. 필터 한 줄이 모든 상태 분석을 대신하는 것은 아닙니다. [2]

의도를 풀어 적는 방법도 알아두겠습니다.

not (ip.addr == 192.0.2.10)

말로 읽으면 다음과 같습니다.

“그 주소가 들어 있는 패킷이라는 조건을 뒤집겠습니다.”

여기서 한 가지 더 생각해 볼까요?

이 조건만 사용하면 IPv4 주소 필드 자체가 없는 패킷도 남을 수 있습니다. 우리가 원하는 것이 IPv4 패킷 중에서 해당 주소와 관련된 것을 제외하는 것이라면 범위까지 적어 주면 됩니다.

ip and not (ip.addr == 192.0.2.10)

앞의 ip는 IPv4 패킷이라는 범위를 정하고, 뒤의 조건은 특정 주소를 제외합니다.

이 예제에서 기억할 것은 기호 하나보다 질문의 정확성입니다.

“그 주소를 제외한다”는 말에 더해, 어떤 패킷 집합에서 제외하는지까지 생각하면 필터가 명확해집니다.

8. 작은 조사에 연결해 봅시다

다음은 학습용 가상 상황입니다.

한 컴퓨터가 backup이라는 문자열을 포함한 DNS 이름을 질의했다는 제보가 들어왔습니다. 컴퓨터의 IPv4 주소는 192.0.2.10입니다.

처음부터 복잡한 필터를 완성하려고 하지 말고, 질문을 조금씩 구체화해 보겠습니다.

먼저 해당 컴퓨터와 관련된 패킷을 살펴봅니다.

ip.addr == 192.0.2.10

그다음 이 컴퓨터가 보낸 DNS로 좁힙니다.

ip.src == 192.0.2.10 and dns

이제 DNS 요청 중에서 질의 이름에 backup이 들어 있는 것을 찾습니다.

ip.src == 192.0.2.10 and dns.flags.response == 0 and dns.qry.name contains "backup"

이렇게 패킷을 찾았다면 무엇을 확인한 것일까요?

확인한 사실은 확보한 캡처에서 해당 출발지 주소를 가진 DNS 요청이 관측되었고, 질의 이름에 그 문자열이 있었다는 것입니다.

그 컴퓨터가 악성코드에 감염되었다고 확정한 것은 아닙니다. backup은 정상적인 이름에도 들어갈 수 있습니다. DNS 질의가 있었다고 해서 해당 서비스에 실제로 접속했다는 뜻도 아닙니다.

다음으로는 응답과 후속 통신을 살펴볼 수 있습니다. 필요하면 단말 기록을 확인해 어떤 프로그램이 해당 통신을 만들었는지도 조사합니다.

필터로 패킷을 찾는 단계와, 그 패킷의 의미를 판단하는 단계가 이렇게 이어집니다.

9. 최신 보충 — 결과가 없는 이유와 분석 도구의 보안

암호화된 DNS는 질의 이름 필터만으로 찾을 수 없을 수 있습니다

dns.qry.name으로 검색했는데 아무것도 나오지 않았다고 합시다. 그렇다면 “이 컴퓨터는 DNS를 사용하지 않았다”고 결론내려도 될까요?

아직은 어렵습니다. DNS over HTTPS(DoH)는 DNS 질의와 응답을 HTTPS 안에 실어 보냅니다. 복호화에 필요한 정보가 없는 캡처에서는 질의 이름이 DNS 필드로 드러나지 않을 수 있습니다. 이는 필터 문장을 더 복잡하게 만든다고 해결되는 문제가 아닙니다. [4] [5]

사진첩 비유로 돌아가 볼까요? 이름표가 없는 사진에 ‘이름표에 backup이 적힌 사진’이라는 조건을 걸면 결과가 없을 수 있습니다. 그 사람이 사진에 없다는 것과 이름표를 읽을 수 없다는 것은 다른 이야기이지요.

분석에서는 캡처 위치와 수집 시간, IPv4·IPv6 범위, 잘림이나 재조립 상태, 암호화 여부를 확인합니다. 질의 내용을 알아야 한다면 해당 환경에서 확보 가능한 단말·리졸버 기록과 대조합니다. 단순히 443번 포트를 썼다는 사실만으로 DoH라고 확정하지도 않습니다.

표시 필터를 걸어 두었다고 해서, 보이지 않는 프로토콜의 해석까지 모두 막는 것은 아닙니다. 표시 필터를 보안 경계로 생각하면 안 됩니다. PCAP이나 설정 프로파일을 읽는 분석 도구 자체도 업데이트가 필요합니다.

2026년 11월 1일 확인한 공식 권고에는 조작된 PCAPNG 파일을 읽을 때 프로그램이 비정상 종료될 수 있는 문제가 있습니다. 권고 문서 wnpa-sec-2026-84는 2026년 8월 12일 발표되었고, 수정 버전은 4.6.8과 4.4.18입니다. [7]

별도의 권고 wnpa-sec-2026-106은 2026년 9월 23일 발표되었으며, 조작된 설정 프로파일을 가져올 때 비정상 종료 또는 임의 코드 실행이 가능할 수 있는 문제를 다룹니다. 이 문제의 수정 버전은 4.6.9와 4.4.19입니다. 캡처 파일을 읽는 동작과 프로파일을 가져오는 동작은 서로 다른 입력 경로입니다. [8]

10. 이해했는지 확인해 봅시다

질문 1. dns 표시 필터를 적용한 뒤 TCP 패킷이 보이지 않습니다. 삭제된 것일까요?

아닙니다. 현재 표시 조건에서 가려진 것입니다. 필터를 지우면 다시 볼 수 있습니다. 단, 처음 수집할 때 캡처 필터로 제외했다면 해당 파일에는 없을 수 있습니다.

질문 2. dns.qry.name contains "backup"의 결과가 여섯 개입니다. DNS 요청이 여섯 번 있었다고 말해도 될까요?

아직은 어렵습니다. DNS 응답에도 질의 이름이 들어 있을 수 있습니다. 요청 횟수를 조사하려면 요청 조건을 추가하고, 반복 요청이나 캡처 중복 여부도 확인해야 합니다.

질문 3. 192.0.2.10이 받은 패킷도 보고 싶은데 ip.src == 192.0.2.10만 사용했습니다. 충분할까요?

충분하지 않습니다. 일반적인 직접 통신에서 그 컴퓨터로 돌아오는 응답은 해당 주소가 목적지에 들어갑니다. 양방향을 보려면 ip.addr == 192.0.2.10을 사용할 수 있습니다.

질문 4. 필터 결과에 의심스러운 이름이 나타났습니다. 다음에 무엇을 해야 할까요?

먼저 질의 이름과 요청·응답 여부를 직접 확인합니다. 이후 필터 범위를 조절해 관련 응답과 후속 통신을 살펴봅니다. 악성 여부나 실제 영향은 다른 증거와 연결해 판단합니다.

질문 5. IPv4 이외의 패킷을 제외하면서 특정 주소도 빼고 싶다면?

ip and not (ip.addr == 192.0.2.10)처럼 IPv4라는 범위와 제외 조건을 함께 적습니다. 조건을 부정하는 것만으로 필드의 존재 조건까지 생긴다고 가정하지 않습니다.

질문 6. Backup.example을 소문자 검색어 backup으로 찾고 싶다면?

대소문자 차이를 무시한 포함 검색에는 lower(dns.qry.name) contains "backup"을 사용할 수 있습니다. 원래의 contains와 기본적으로 대소문자를 구별하지 않는 matches의 차이도 떠올려 보세요.

질문 7. 질의 이름 검색 결과가 0이면 DNS를 쓰지 않았다는 뜻일까요?

그 결론은 이릅니다. 캡처 범위·필터 조건·프로토콜 해석과 암호화된 DNS 가능성을 확인해야 합니다. 확보한 자료에서 해당 필드의 일치를 찾지 못했다는 사실을 먼저 기록합니다.

질문 8. 표시 필터를 DNS로 설정해 두면 악성 PCAP의 다른 해석기 취약점도 막을 수 있을까요?

표시 필터를 그런 보안 경계로 사용하면 안 됩니다. 파일·프로토콜 해석의 취약점은 도구의 보안 수정으로 대응해야 합니다. 설정 프로파일의 가져오기 역시 별도 권고를 확인합니다.

다음 학습에서는 필드 이름을 아직 외우지 못했을 때 메뉴와 상세 창에서 필터를 만드는 방법, 관심 있는 패킷을 모아 내보내는 방법을 이어서 다룹니다.
