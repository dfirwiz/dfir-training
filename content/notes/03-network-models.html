1. 도구의 해석을 검증하려면 구조부터

가상의 상황부터 볼까요? 서버 쪽 로그에는 요청이 도착했다고 남았는데, 분석 화면에서는 HTTP 요청이 보이지 않습니다. 이때 “도구가 틀렸네”라고 끝내면 원인을 찾기 어렵습니다. 지금 보고 있는 것이 프레임 하나인지, IP 조각인지, TCP 스트림의 일부인지부터 알아야 합니다. TLS로 보호된 바이트라면 HTTP 문장이 직접 보이지 않는 것도 자연스럽습니다.

경고 화면은 사건의 책갈피와 비슷합니다. 책갈피가 꽂힌 문장만 읽으면 앞뒤 이야기를 놓치듯, 경고에 딸린 패킷만으로는 이전 연결이나 뒤의 활동을 알기 어렵습니다. 장비와 설정에 따라 경고 관련 일부 패킷만 보존할 수도 있으므로, 전체 캡처가 있는지와 보존 범위를 확인해야 합니다. 앞 강의의 ICMP 속 다른 통신이나 경고 이후의 활동도 이런 맥락에서 다시 봅니다.

다만 패킷이 있어야만 사건이 존재하는 것은 아닙니다. 단말 기록이나 서버 감사 로그가 독립적인 증거가 될 수 있죠. 패킷은 네트워크에서 관측한 사실을 보강하는 자료이며, 센서는 보통 실제 수신 프로그램의 내부 상태를 그대로 보지 못합니다. 재조립 정책과 구현 차이 때문에 센서가 구성한 데이터와 단말이 처리한 데이터가 달라질 수도 있습니다. 그래서 구조를 배우고, 필요한 지점에서는 다른 기록과 맞춰 보는 것입니다.

앞선 두 노트에서 경고와 실제 발생 사실을 구별했습니다. 이제 도구가 ‘TCP’나 ‘HTTP’라고 표시한 근거를 직접 따라가 보겠습니다. 패킷 분석기는 바이트를 읽고, 프로토콜의 규칙에 따라 헤더와 데이터를 나누며, 그 안에 있는 다음 프로토콜을 해석합니다.

이 과정에는 수집된 정보와 구현의 한계가 있습니다. 캡처 밖의 활동이나 실제 응용 프로그램 내부 상태까지 모두 알 수는 없습니다. 분석 결과를 검증한다는 것은 도구를 불신하는 것이 아니라, 그 결과가 어떤 구조와 증거에서 나왔는지 확인하는 일입니다.

이번 회차의 목표

TCP/IP의 네 계층을 구별하고, 캡슐화와 역캡슐화를 설명하며, 프로토콜 식별자와 길이 필드로 다음 데이터의 위치를 찾습니다.

예를 들어 특정 웹 서버의 취약점을 노리는 요청이 관측됐지만 그 제품을 운영하지 않는다고 해도, 그 이유만으로 요청 탐지가 오탐인 것은 아닙니다. 공격 시도의 존재와 해당 자산에 미칠 영향을 따로 판단합니다.

2. TCP/IP 계층은 통신 역할을 나눈 지도

한 회사의 여러 담당자가 협력한다고 생각해 보세요

편지를 쓰는 사람은 내용에 집중하고, 우편 분류 담당자는 주소를 읽고, 배달 담당자는 지금 맡은 구간에서 다음 장소로 옮깁니다. 통신도 메시지 의미·프로그램 사이 전달·네트워크 사이 전달·현재 링크 전송이라는 역할을 나누면 이해하기 쉽습니다. 여기서 프로토콜은 서로 같은 방식으로 메시지를 만들고 해석하기 위한 규칙입니다. 헤더는 그 처리에 필요한 정보를 담는 앞부분이고, 필드는 헤더 안의 개별 항목입니다.

비유에는 한계가 있습니다. 실제 패킷은 편지처럼 한 장씩 완성된 메시지를 그대로 운반하지 않을 수 있고, 장비 하나가 여러 계층을 함께 해석하기도 합니다. 계층의 독립성은 다른 계층의 존재를 전혀 모른다는 뜻보다, 역할과 접점을 나누어 구현을 바꿀 수 있다는 뜻에 가깝습니다. 예를 들어 IP 버전이 달라져도 TCP의 포트와 순서 관리라는 역할은 이어집니다. 주소 체계와 체크섬 계산에 연결되는 세부 조건까지 모두 같다는 뜻은 아닙니다.

“그럼 송신 TCP와 수신 TCP가 직접 선으로 이어졌나요?” 논리적으로는 같은 계층의 규칙으로 대화하지만 실제 데이터는 송신 호스트의 아래 계층으로 내려가 링크를 통과한 뒤 수신 호스트에서 올라갑니다. 이를 같은 계층 사이의 논리적 통신이라고 이해하세요. 계층별 담당을 나누면 어느 부분의 문제를 확인할지 질문도 구체적으로 바뀝니다.

MAC·IP·포트는 같은 종류의 주소가 아닙니다

MAC은 Media Access Control의 약자로, Ethernet에서는 현재 링크의 인터페이스 주소를 나타냅니다. 라우터는 서로 다른 IP 네트워크 사이에서 패킷을 전달하는 장비이며, 다음 홉은 그 전달에서 바로 다음으로 넘겨줄 지점입니다. 포트는 TCP나 UDP에서 통신 접점을 구분하는 번호입니다. DNS는 이름과 관련 정보를 질의하는 규칙이고, HTTP는 웹 요청·응답, SMTP는 메일 전달에 쓰이는 규칙입니다. 이름이 낯설다면 지금은 각 프로토콜의 담당 역할부터 연결하면 됩니다.

가령 문서용 클라이언트 192.0.2.20이 다른 네트워크의 서버 198.51.100.10으로 보낸다고 해 보겠습니다. NAT 같은 주소 변환이 없는 단순 경로에서는 IP 목적지는 서버지만, 첫 Ethernet 프레임의 목적지 MAC은 게이트웨이의 인터페이스일 수 있습니다. 라우터를 지나 다음 링크로 나갈 때 링크 헤더는 새로 만들어집니다. 첫 구간의 MAC을 서버의 실제 사용자나 최종 장비 신원이라고 보고하면 안 되는 이유입니다.

브라우저에서 웹 서버로 요청을 보내는 장면을 떠올려 보겠습니다. 브라우저는 요청 메시지의 의미를 알아야 하고, 운영체제는 어떤 통신 상대와 프로그램에 데이터를 보낼지 구분해야 합니다. 다른 네트워크를 지나가려면 IP 주소를 이용한 전달이 필요하고, 지금 연결된 링크에서는 그 링크에 맞는 형식으로 전송해야 합니다.

웹 브라우저가 데이터를 보낼 때 모든 일을 한 가지 프로토콜이 처리하지 않습니다. 응용 프로그램의 메시지를 만들고, 통신 상대의 서비스를 구분하고, 다른 네트워크로 전달하고, 현재 링크로 전송하는 역할을 나눕니다. 이 노트에서는 TCP/IP를 네 계층으로 설명합니다. [1]

주소에도 역할의 차이가 있습니다. IP 주소는 IP 통신의 출발지와 목적지를 표현하고, Ethernet의 MAC 주소는 현재 링크에서 프레임을 전달하는 데 사용합니다. 다른 네트워크에 있는 서버로 보내는 경우에는 현재 링크의 다음 전달 지점이 라우터일 수 있습니다. 그래서 ‘프레임의 목적지’와 ‘최종 응용 서버’를 같은 것으로 취급하면 안 됩니다. 이 차이는 링크 계층을 배울 때 다시 자세히 다룹니다.

계층 모델은 역할을 이해하는 지도입니다. 모든 구현이 네 개의 독립된 상자로만 움직인다는 뜻은 아닙니다. 실제 방화벽이나 분석기는 여러 계층의 정보를 함께 사용합니다.

3. 송신할 때는 데이터를 차례로 감싼다

포장을 벗겨 보면 무엇이 데이터일까요?

배송 상자에는 받는 곳을 적은 겉면과 내용물이 있습니다. 내용물로 넣은 작은 봉투에도 자체 주소와 문서가 있을 수 있죠. 바깥 상자의 담당자는 그 봉투 전체를 내용물로 취급합니다. 마찬가지로 TCP 헤더는 TCP에게는 제어 정보이지만, 그것을 담는 IP에게는 페이로드의 일부입니다. 페이로드(payload)는 해당 계층이 운반하는 데이터라는 뜻입니다.

이름도 함께 익혀 둡시다. Ethernet 단위를 프레임(frame), IP 단위를 패킷 또는 데이터그램(datagram), TCP 단위를 세그먼트(segment)라고 부릅니다. 일상 대화에서는 모두 패킷이라고 부르기도 하니 문맥을 확인하세요. UDP도 데이터그램이라는 말을 사용합니다. 같은 단어가 등장한다고 같은 계층이나 같은 헤더를 뜻하지는 않습니다.

응용 데이터 100바이트를 TCP가 운반하고 TCP 헤더가 20바이트라면, IP가 받는 덩어리는 20 + 100 = 120바이트입니다. IP 헤더가 20바이트라면 Ethernet이 담을 IP 패킷은 20 + 120 = 140바이트입니다. 태그 없는 Ethernet II의 헤더 14바이트까지 더하면 FCS를 제외한 프레임은 14 + 140 = 154바이트가 됩니다. 각 덧셈에서 어느 계층의 헤더를 추가했는지 말할 수 있으면 원리를 이해한 것입니다.

실제 Ethernet에는 끝부분의 FCS(Frame Check Sequence), 즉 오류 검사용 값과 최소 길이를 맞추는 패딩 같은 요소도 있습니다. 캡처 장치가 FCS를 파일에 남기지 않는 경우도 있습니다. 따라서 여기의 단순 덧셈을 모든 파일 길이나 회선에서 사용한 전체 전송량으로 확대하면 안 됩니다. 아래 도식은 포함 관계를 설명하는 그림이며 실제 비율이나 모든 부가 요소를 그린 것은 아닙니다.

응용 프로그램의 데이터를 보내려면 각 계층에서 필요한 정보를 붙입니다. 이 과정을 캡슐화라고 합니다. 배송 상자 안에 작은 상자를 넣듯, 한 계층에서 만든 헤더와 데이터 전체가 아래 계층의 페이로드가 됩니다.

단순한 TCP over IPv4 over Ethernet 예시에서는 TCP가 응용 데이터를 운반하고, IPv4가 TCP 헤더와 데이터를 운반하며, Ethernet이 IP 패킷 전체를 운반합니다. 페이로드라는 말은 항상 어느 계층을 기준으로 하는지 함께 생각해야 합니다.

송신 과정을 순서대로 풀어 보면 다음과 같습니다.

  1. 응용 프로그램이 보낼 데이터를 준비합니다. 예를 들어 HTTP 요청의 내용입니다. HTTPS라면 TCP가 운반할 데이터를 준비하는 과정에서 TLS가 응용 데이터를 보호합니다.
  2. TCP가 자신의 헤더를 붙입니다. 포트와 순서·확인 응답에 필요한 정보 등이 들어갑니다. TCP가 운반하는 데이터 앞에 TCP용 정보가 추가됩니다.
  3. IPv4가 IP 헤더를 붙입니다. IP 주소와 다음 프로토콜을 나타내는 값 등이 들어갑니다. 이 단계에서는 TCP 헤더까지 포함한 덩어리가 IP의 데이터입니다.
  4. Ethernet이 IP 패킷을 프레임에 담습니다. 현재 링크에서 전달하기 위한 주소와 유형 정보 등이 붙습니다. 실제 프레임의 세부 구성은 링크 종류에 따라 달라집니다.

IP 페이로드는 응용 데이터와 같은 말이 아닙니다. 이 예시의 IP 페이로드에는 TCP 헤더도 포함됩니다. TCP 페이로드를 볼 때 비로소 그 TCP 헤더 뒤의 데이터를 가리킵니다.

패킷 하나가 메시지 하나는 아닙니다

TCP는 바이트 스트림을 제공합니다. 응용 메시지 하나가 여러 TCP 세그먼트에 걸칠 수도 있고, 세그먼트 하나에 메시지가 여러 개 포함될 수도 있습니다. 개별 패킷에 문자열이 없다는 이유만으로 전체 통신에도 없다고 판단하지 마세요. [3]

4. 수신할 때는 종류와 길이를 따라 읽는다

먼저 출입구를 찾고, 다음 담당자를 고릅니다

분석기는 아무 바이트나 IP로 읽기 시작하지 않습니다. 먼저 캡처 파일이 알려 주는 링크 형식을 확인해야 합니다. Ethernet 캡처인지, 무선 링크의 부가 정보가 있는지, 운영체제가 제공한 다른 캡처 형식인지에 따라 시작점이 달라집니다. PCAP 파일 자체의 저장용 헤더도 회선의 Ethernet 헤더와는 별개입니다. 파일 맨 앞 14바이트를 무조건 건너뛰는 방법은 맞지 않습니다.

EtherType은 Ethernet의 뒤에 담긴 종류를 나타내는 값입니다. 0x는 뒤의 숫자를 16진수로 썼다는 표기입니다. 예를 들어 0x0800과 IPv4 Protocol의 십진수 6은 서로 다른 위치의 서로 다른 식별자입니다. 전자는 IPv4를, 후자는 이 IPv4 데이터의 상위 프로토콜인 TCP를 가리킵니다. 이름과 값을 외우기 전에 “어느 헤더에서 읽었나”를 붙여 보세요.

종류를 알았다고 경계까지 저절로 아는 것은 아닙니다. “IPv4다”와 “IPv4 헤더가 24바이트다”는 다른 정보입니다. 반대로 길이만 알아도 다음 것이 TCP인지 UDP인지 알 수 없죠. 그래서 종류와 길이를 함께 확인합니다. 일부 프로토콜은 자기 안에 버전·식별 정보를 담기도 하지만, 눈에 띄는 문자열 하나만으로 구조 전체를 확정해서는 안 됩니다.

포트 80으로 받은 데이터는 그 포트에서 수신하는 프로그램이 처리합니다. 수신 대기한다는 것은 해당 접점에서 도착하는 통신을 받을 준비를 했다는 뜻입니다. 분석기의 HTTP 해석은 포트 관례·바이트 구조·설정 등에 따른 해석이지, 그 서버에서 어느 실행 파일이 실제 처리했다는 증명은 아닙니다. 서버 설정과 프로세스의 연결 기록을 대조하면 그 간격을 좁힐 수 있습니다.

수신 측은 바깥쪽 헤더를 해석하고 내부 데이터를 해당 처리기로 넘깁니다. 이를 역캡슐화라고 합니다. 영어 문서에서는 decapsulation 또는 de-encapsulation이라는 표기를 만날 수 있습니다. 분석 도구도 이 구조를 따라가며 다음 두 질문에 답합니다.

  1. 다음에는 어떤 프로토콜이 오는가? 프로토콜 식별자를 확인합니다.
  2. 현재 헤더는 어디에서 끝나는가? 정해진 길이나 길이 필드로 경계를 계산합니다.

EtherType 0x86dd는 IPv6를 가리킵니다. Ethernet의 Type/Length 필드가 길이를 나타내는 IEEE 802.3 프레임은 LLC 등 추가 구조를 고려해야 합니다. 이번 계산은 VLAN 태그가 없는 Ethernet II를 가정합니다. [2]

예를 들어 분석기가 Ethernet II의 EtherType을 보고 IPv4로 들어갔다면, 다음에는 IP 헤더의 형식과 길이가 맞는지 확인합니다. IPv4 Protocol 값이 6이면 TCP가 전달된다는 뜻이지만, IP 단편이라면 TCP를 해석하기 전에 재조립이 필요한 경우가 있습니다. TCP에 도달하면 TCP 헤더의 길이를 읽어 그 뒤의 데이터를 찾습니다.

수신 호스트에서는 포트 등을 이용해 관련 소켓으로 데이터를 전달합니다. 소켓은 프로그램이 통신을 주고받는 접점이라고 먼저 이해하면 됩니다. 패킷을 보는 분석기는 수신 프로그램과 동일한 위치에 있지 않으므로, 포트를 단서로 삼되 실제 프로그램이나 메시지를 추가 증거로 확인해야 합니다.

목적지 포트 80은 HTTP를 예상할 단서지만 보장하지는 않습니다. 실제 바이트와 통신 흐름을 보고 해석이 맞는지 확인합니다. 반대로 암호화된 데이터에서는 응용 메시지를 직접 검증하기 어려울 수 있습니다.

5. 헤더 길이는 외우는 값과 읽어야 하는 값이 다르다

고정 길이의 헤더도 있지만 옵션 때문에 길이가 달라지는 헤더도 있습니다. IPv4나 TCP를 항상 20바이트라고 가정하면 옵션을 데이터로 잘못 읽게 됩니다.

이번 회차에서 사용하는 길이 기준 [2] [3] [4]

여기에는 세 가지 길이 해석이 섞여 있습니다. Ethernet II의 기본 헤더는 구조에서 길이를 알 수 있는 고정 길이입니다. IPv4와 TCP 헤더는 필드 값을 읽어야 하는 가변 길이입니다. TCP 데이터 길이는 다른 길이를 빼서 구하는 계산된 길이입니다. 무엇을 읽었고 무엇을 계산했는지 구별하면 해석 과정을 설명하기 쉬워집니다.

32비트는 4바이트입니다. 따라서 IHL이나 Data Offset의 원래 값은 그대로 바이트 수가 되지 않습니다. IPv4 헤더와 TCP 헤더는 각각 기본 20바이트이며, 해당 길이 필드로 표현하는 일반적인 최대 헤더 길이는 각각 60바이트입니다. 옵션과 헤더 패딩이 포함되면 길이가 늘어납니다. [3] [4]

Wireshark가 계산된 길이를 바이트로 보여 주는 경우와 원래 필드 값을 읽는 경우도 구별하세요. 예를 들어 원래 IHL 값이 6이면 헤더는 6바이트가 아니라 6 × 4 = 24바이트입니다.

원래 필드 값과 화면의 환산값을 구별해 봅시다

IHL은 Internet Header Length, 즉 IPv4 헤더 길이입니다. Data Offset은 TCP 시작에서 실제 데이터 시작까지의 거리를 표현합니다. 이 둘은 32비트 단위를 세므로 32비트 ÷ 8비트/바이트 = 4바이트로 환산합니다. 1바이트는 8비트이고, 비트는 0 또는 1을 담는 가장 작은 단위라고 이해하면 됩니다. 비트와 16진수는 다음 강의에서 더 천천히 연습합니다.

두 길이 필드는 각각 4비트이므로 표현 가능한 가장 큰 원래 값은 15입니다. 일반적인 헤더 길이 범위는 5 × 4 = 20바이트부터 15 × 4 = 60바이트까지입니다. 4비트라서 헤더가 4바이트라는 뜻이 아닙니다. 필드 자체의 크기, 필드가 담는 숫자, 그 숫자를 환산한 길이는 서로 구별하세요.

Total Length는 전체 길이라는 뜻으로, IPv4에서는 IP 헤더와 그 데이터의 합을 바이트로 담습니다. TCP에는 이와 똑같은 의미로 TCP 페이로드 길이를 직접 알려 주는 기본 헤더 필드가 없습니다. 그래서 IP 전체 길이와 두 헤더 길이에서 계산합니다. Wireshark 화면에서 계산된 TCP 길이를 보더라도 실제 패킷 안에 같은 이름의 길이 필드가 있다고 가정하지 마세요.

6. 옵션의 경계도 규칙에 따라 읽는다

헤더 전체의 끝을 찾았다고 해서 그 안의 옵션 구조를 모두 이해한 것은 아닙니다. 옵션이 여러 개 있다면 어디에서 하나가 끝나고 다음 것이 시작하는지도 알아야 합니다.

많은 옵션은 종류, 길이, 값으로 구성되어 자신이 차지하는 범위를 알려 줍니다. 그러나 모든 옵션에 같은 형식을 기계적으로 적용하면 안 됩니다. 예를 들어 TCP의 End of Option List와 No-Operation은 한 바이트짜리 형식이며, 다른 옵션에서 사용하는 길이·데이터 구조와 다릅니다. TCP 헤더 길이에는 옵션 뒤의 패딩도 포함될 수 있습니다. [3]

따라서 ‘기본 20바이트 다음의 12바이트’를 봤다고 해서 그 안이 반드시 하나의 12바이트 옵션이라고 해석하지 않습니다. 여러 옵션과 패딩의 조합일 수 있습니다. 전체 경계를 먼저 확인하고, 각 옵션의 종류와 길이 규칙을 따라 읽어야 합니다.

여기서 옵션은 기본 헤더 뒤에 붙는 선택적 제어 정보입니다. 패딩(padding)은 정해진 경계에 맞추기 위해 채우는 바이트입니다. 옵션의 “길이”가 값 부분만인지, 종류·길이 필드까지 포함하는지는 해당 규칙을 봐야 합니다. TCP의 일반적인 길이 포함 옵션은 종류와 길이 자체도 길이에 포함합니다. [3]

가상의 TCP 옵션 바이트 01 01 02 04 05 b4를 읽어 볼까요? 01은 No-Operation, 즉 한 바이트짜리 정렬용 옵션이므로 다음 바이트가 곧 다음 옵션입니다. 두 번째 01도 마찬가지입니다. 다음 02는 MSS(Maximum Segment Size, 최대 세그먼트 크기) 옵션의 종류이고, 04는 종류 1바이트·길이 1바이트·값 2바이트를 합친 총 4바이트라는 뜻입니다. 여기서는 MSS 값을 해석하기보다, 여섯 바이트가 하나의 옵션이 아니라 세 옵션이라는 점을 확인합니다.

이 여섯 바이트만으로 전체 TCP 헤더가 완성됐다고 볼 수도 없습니다. 헤더 전체는 4바이트 단위여야 하므로 다른 옵션이나 패딩까지 확인해야 하죠. 길이 값이 남은 헤더를 넘거나 필요한 바이트가 없으면 억지로 다음 옵션을 읽지 말고, 저장 누락·구조 오류·해석 설정을 구별합니다.

7. 예제로 데이터가 시작되는 위치 계산하기

다음은 학습을 위해 새로 구성한 예시입니다. 실제 PCAP을 실행한 결과가 아닙니다. VLAN 태그 없는 Ethernet II 안에 단편화되지 않은 IPv4/TCP 패킷이 온다고 가정합니다.

  • IPv4 Total Length: 1,000바이트
  • IPv4 IHL: 6 → IP 헤더 24바이트
  • TCP Data Offset: 8 → TCP 헤더 32바이트

먼저 IP 헤더 길이를 바이트로 환산합니다. IHL이 6이므로 6 × 4 = 24바이트입니다. 다음으로 TCP 헤더 길이를 환산하면 Data Offset이 8이므로 8 × 4 = 32바이트입니다.

IP Total Length 1,000바이트에는 IP 헤더와 TCP 헤더, TCP 데이터가 모두 들어 있습니다. 그러므로 TCP 데이터를 남기려면 그 안에 포함된 두 헤더를 빼야 합니다. Ethernet 헤더 14바이트는 애초에 IP Total Length에 포함되지 않았으므로 이 뺄셈에서 다시 빼지 않습니다.

TCP 페이로드 길이는 IP 전체 길이에서 두 헤더 길이를 빼면 됩니다.

TCP 페이로드 = IPv4 Total Length - IPv4 헤더 길이 - TCP 헤더 길이
             = 1000 - 24 - 32
             = 944바이트

Ethernet II 헤더 시작을 0으로 둔 바이트 오프셋
IPv4 헤더 시작 = 14
TCP 헤더 시작  = 14 + 24 = 38
TCP 데이터 시작 = 14 + 24 + 32 = 70

데이터의 시작 위치는 반대로 앞에 있는 길이를 더해서 찾습니다. Ethernet II 헤더가 0번 위치에서 시작한다면 14바이트 뒤에서 IPv4가 시작합니다. 다시 24바이트를 지나면 TCP가 시작하고, TCP 헤더 32바이트를 더 지나면 70번 위치에서 데이터가 시작합니다. 여기서 오프셋은 ‘기준점에서 몇 바이트 떨어졌는가’를 뜻합니다.

여기서 944바이트는 해당 TCP 세그먼트의 페이로드입니다. 파일 전체 크기나 읽을 수 있는 HTTP 본문 길이를 뜻하지 않습니다. TLS를 사용한다면 암호화된 레코드의 일부일 수 있습니다.

IP 단편화, 잘린 캡처, 재조립이 필요한 경우에는 이 단순 계산만으로 캡처된 바이트를 모두 설명할 수 없습니다. 표시된 길이와 실제 확보한 데이터가 맞는지도 함께 확인해야 합니다.

조건을 하나 바꾸면 왜 답이 달라질까요?

앞의 예시에서 TCP Data Offset만 5로 바꿔 보겠습니다. TCP 헤더는 5 × 4 = 20바이트가 됩니다. IP 전체 길이 1,000바이트와 IP 헤더 24바이트는 그대로이므로, TCP 데이터는 1000 − 24 − 20 = 956바이트입니다. 데이터 시작은 프레임 기준 14 + 24 + 20 = 58입니다. 헤더가 12바이트 짧아진 만큼 시작이 12바이트 앞당겨지고, 같은 전체 길이 안의 데이터는 12바이트 늘었죠.

이번에는 원래 값으로 돌아가 단일 VLAN 태그 4바이트가 추가되는 조건만 생각해 봅니다. 해당 구조의 링크 헤더가 18바이트라면 IP 기준 TCP 데이터 길이 944바이트는 그대로이지만, 프레임 기준 데이터 시작은 18 + 24 + 32 = 74가 됩니다. 링크의 앞부분이 바뀐 것과 IP 내부 길이가 바뀐 것을 분리할 수 있어야 합니다.

다른 길이도 연습해 볼까요? 단편화되지 않은 IPv4 패킷의 Total Length가 1,500바이트, IP 헤더가 20바이트, TCP 헤더가 40바이트라면 1500 − 20 − 40 = 1440바이트가 TCP 데이터입니다. TCP 헤더의 기본 부분 20바이트를 빼면 옵션·패딩 영역은 40 − 20 = 20바이트입니다. 이것이 반드시 하나의 옵션이라는 뜻은 아닙니다.

오프셋은 0에서 센 거리입니다. 원래 예시의 IP 헤더는 위치 14~37, TCP 헤더는 38~69, 데이터는 70~1013에 해당합니다. 마지막 바이트가 1013이므로 총 길이는 1014바이트입니다. “1014번 바이트까지 데이터가 있다”라고 쓰면 한 바이트가 늘어나니, 끝 위치가 포함되는지 제외되는지도 분명히 적으세요.

8. 계산한 길이와 실제 캡처가 다르면

패킷 헤더에 적힌 길이는 캡처 파일에 실제로 남은 데이터의 양과 다를 수 있습니다. 수집 도구가 패킷의 앞부분만 저장하도록 설정되어 있다면, 뒤의 내용은 파일에 없습니다. Wireshark는 프레임 길이와 캡처된 길이를 구분하며, SnapLen은 각 프레임에서 저장할 최대 분량을 제한하는 설정입니다. [12]

앞의 가상 예시에서 프레임 길이는 1,014바이트이지만 캡처 파일에는 앞의 128바이트만 저장되었다고 가정해 보겠습니다. 헤더들은 모두 확보했고 TCP 데이터는 70번 위치에서 시작합니다. 이 파일에 남아 있는 TCP 데이터는 128 - 70 = 58바이트입니다. IP·TCP 헤더에서 계산한 페이로드 944바이트 전체를 읽을 수 있는 것이 아닙니다.

같은 예시에서 서로 다른 길이의 의미
값의미
944바이트헤더의 길이 값에서 계산한 해당 TCP 세그먼트의 페이로드 길이
58바이트앞의 128바이트만 저장한 이 캡처에 실제로 남은 TCP 데이터 분량
미확인남은 데이터를 포함한 실제 메시지의 전체 의미와 응용 프로그램의 처리 결과

이 차이만으로 실제 통신에서 데이터가 사라졌다고 결론 내리지 않습니다. 수집 단계에서 저장하지 않은 것일 수 있기 때문입니다. 반대로 헤더 길이를 더했는데 전체 IP 길이보다 커지는 등 구조 자체가 맞지 않는다면, 계산 단위·링크 형식·디코딩 기준·캡처 손상·실제 비정상 패킷 가능성을 다시 확인해야 합니다.

또한 TCP는 여러 세그먼트의 데이터를 이어서 응용 프로그램에 제공합니다. Wireshark의 Follow TCP Stream은 관련 스트림을 읽는 데 도움이 되지만, 수집하지 못한 바이트를 만들어 주거나 암호화를 자동으로 풀어 주지는 않습니다. 필요한 구간이 빠졌는지와 복호화 정보가 있는지를 별도로 확인합니다. [11]

SnapLen은 스냅샷 길이(snapshot length)의 줄임말입니다. 가령 저장 한도를 128바이트로 정했다면, 뒤의 내용은 수집 도구가 저장하지 않았을 수 있습니다. 도구가 원래 프레임 길이를 메타데이터로 기록해도, 그것이 저장하지 않은 본문까지 보유한다는 뜻은 아닙니다. 반대로 센서가 아예 놓친 프레임은 이 길이 비교만으로 발견할 수 없으므로 수집 손실 통계도 봐야 합니다.

IP 단편에도 주의하세요. Protocol이 6인 뒤쪽 IP 조각이라고 해서 그 조각의 데이터 시작에 새 TCP 헤더가 있는 것은 아닙니다. 원래 TCP 세그먼트의 중간 부분일 수 있습니다. 앞의 길이 공식은 단편화되지 않은 IPv4/TCP라는 전제를 붙였기 때문에 사용할 수 있었습니다. 나중에 단편화 강의에서는 조각 위치와 재조립 범위를 따로 계산합니다.

추가 조사를 할 때는 원래 캡처의 링크 유형·SnapLen·시간 범위·방향·손실 기록을 먼저 적습니다. 그다음 재조립에 필요한 앞뒤 패킷이 있는지, 표시 필터가 일부를 숨겼는지 확인합니다. Follow TCP Stream은 관련 바이트를 읽기 좋게 연결하는 기능이지 서버가 실제로 받아 처리한 결과를 대신하는 것은 아닙니다.

9. 최신 보충 — 계층은 유효하지만 조합은 다양하다

캡슐화와 길이 확인 원리는 여전히 유효합니다. 현재 환경에서는 ‘웹이니까 항상 TCP’ 또는 ‘IP니까 항상 IPv4’처럼 특정 조합을 전제로 하지 않는 것이 중요합니다.

기초 예시를 현재 환경에 적용할 때
상황해석에 반영할 내용
HTTP/3와 QUICHTTP/3는 QUIC을 사용하고 QUIC 패킷은 UDP 데이터그램으로 전달됩니다. TCP 헤더나 SYN 플래그를 찾는 방식으로 해석하지 않습니다. [5] [6]
IPv6기본 헤더는 40바이트이고 Next Header로 다음 헤더를 가리킵니다. 확장 헤더가 있으면 그 구조를 따라가야 합니다. IPv4의 IHL·Total Length 공식을 그대로 쓰지 않습니다. [7]
호스트에서 직접 수집체크섬 계산이나 분할이 NIC에 위임되어 있으면 캡처에서 체크섬 오류나 예상보다 큰 데이터 단위가 보일 수 있습니다. 실제 회선의 패킷도 같았다고 단정하지 않습니다. [8]
표준과 관측 조건 확인

TCP 표준을 확인할 때는 2022년의 RFC 9293도 참고합니다. 이 문서는 RFC 793을 대체하며 TCP의 명세와 누적 변경 사항을 정리합니다. IPv6의 길이·확장 헤더나 QUIC처럼 다른 구조를 만났다면 그 프로토콜의 표준으로 돌아가 확인하세요. [3]

Wireshark에서 체크섬 경고가 보이면 먼저 캡처 위치와 오프로딩 여부를 확인합니다. 가능한 경우 다른 관측 지점의 캡처와 비교해 실제 전송 오류인지 구분합니다. 경고를 일괄적으로 무시하거나 모두 공격으로 분류하지 않습니다. [8]

새 프로토콜을 만나도 질문은 같습니다

HTTP/3의 경우 웹 통신이라는 응용 목적은 익숙해도 그 아래에는 QUIC과 UDP가 있습니다. UDP 자체에 TCP의 순서 번호와 재전송 구조가 없다는 사실과, 위에서 동작하는 QUIC이 연결·스트림·손실 복구를 제공한다는 사실은 함께 성립합니다. “웹이면 TCP 헤더를 빼면 된다”는 방법 대신, 실제 다음 프로토콜을 확인해야 하는 이유입니다.

IPv6의 Next Header는 다음 헤더의 종류를 나타내는 값입니다. 기본 헤더 뒤에 확장 헤더가 이어질 수 있으므로, 기본 40바이트만 건너뛰면 항상 TCP라는 뜻은 아닙니다. 계층의 역할은 비슷해도 길이 필드와 연결 방식은 해당 표준을 따라야 합니다. [7]

NIC는 Network Interface Card, 즉 네트워크 인터페이스 장치입니다. 오프로딩(offloading)은 원래 호스트가 할 계산이나 분할 일부를 장치에 맡기는 것입니다. 호스트 내부에서 수집한 시점에는 체크섬이 아직 완성되지 않았거나, 나중에 여러 세그먼트로 나갈 큰 데이터가 보일 수도 있습니다. 센서 위치와 설정을 확인한 뒤 가능한 경우 회선 쪽 관측과 비교하세요. 의심스러운 표시가 모두 정상이라는 뜻도 아니므로, 실제 오류 가능성까지 함께 검토합니다.

10. 클라우드에서도 관측 범위를 먼저 정한다

클라우드라고 패킷 분석이 불가능한 것은 아닙니다. 다만 ‘클라우드의 모든 패킷을 제한 없이 확보할 수 있다’고 이해하면 안 됩니다. 서비스, 지원되는 수집 소스, 권한, 경로와 필터를 확인해야 합니다.

예를 들어 AWS VPC Traffic Mirroring은 소스·타깃·필터로 세션을 구성하며 모든 인스턴스 유형에서 지원되는 것은 아닙니다. 공식 제한 문서에는 ARP·DHCP 등 미러링할 수 없는 트래픽과 MTU에 따른 잘림, 대역폭 제약에 따른 손실 가능성도 설명되어 있습니다. [9] [10]

클라우드에서 수집되는 미러링본에는 원래 패킷을 옮기기 위한 바깥쪽 캡슐화가 더 붙을 수 있습니다. AWS Traffic Mirroring의 VXLAN 전달이 그 예입니다. 이때 바깥쪽 IP·UDP 정보는 수집 전달을 위한 정보이고, 안쪽에는 조사하려던 원래 프레임과 통신이 들어 있습니다. 바깥쪽 주소만 보고 업무 통신의 상대라고 기록하지 않도록 원본이 어느 위치에 들어 있는지 확인합니다. [13]

이것이 캡슐화를 배우는 실무적인 이유 중 하나입니다. ‘IP가 두 번 보인다’는 현상이 곧 공격을 뜻하지는 않습니다. 정상적인 수집 터널이나 다른 캡슐화 구조일 수 있으므로 어떤 계층을 보고 있는지 먼저 구별해야 합니다.

따라서 조사를 설계할 때는 ‘어느 지점에서 어떤 통신을 수집했는가’를 기록합니다. 직접 캡처할 수 없는 활동은 서비스의 감사 로그와 응용 로그 등으로 보완합니다. 비용도 수집량·전송·분석·보존 조건에 따라 검토해야 하므로, 무조건 저렴하거나 비싸다고 일반화하지 않습니다.

안 보이는 이유도 조사 대상

암호화로 내용이 숨겨진 것, 수집 대상이 아니어서 없는 것, 필터로 제외된 것, 캡처가 잘리거나 누락된 것은 다른 문제입니다. 무엇이 원인인지 구분해야 올바른 다음 증거를 선택할 수 있습니다.

바깥 주소는 누구의 주소일까요?

미러링(mirroring)은 원래 통신의 복사본을 분석 지점으로 보내는 방식입니다. VXLAN은 여기서 원래 프레임을 다른 네트워크를 통해 운반하는 캡슐화에 사용됩니다. AWS의 미러링 형식이라면 바깥 Ethernet·IP·UDP·VXLAN 안에 원래 Ethernet 프레임이 들어갑니다. 따라서 IP가 두 번 보여도 같은 주소 두 개를 중복 기록한 것이 아닐 수 있습니다. 바깥 IP는 복사본 전달 경로, 안쪽 IP는 조사할 통신을 나타내는지 구별하세요. [13]

생활 비유로는 편지 봉투를 운송용 큰 봉투 안에 다시 넣는 경우와 비슷합니다. 큰 봉투의 수취인은 중계 센터이고 작은 봉투의 수취인은 실제 업무 상대일 수 있죠. 하지만 이 비유만으로 모든 터널의 구조가 VXLAN과 같다고 생각하지는 마세요. 터널 프로토콜마다 헤더·길이·암호화 조건이 다릅니다.

“그럼 모든 클라우드 서버에 도구를 설치하면 되나요?” 설치 권한이 있는 가상머신과, 내부 운영체제에 접근할 수 없는 관리형 서비스를 구별해야 합니다. 지원되는 미러링 소스인지, 어떤 통신이 제외되는지, 어디에서 수집 권한이 있는지를 먼저 확인합니다. 하이브리드 환경이라면 사내 구간·VPN 뒤·클라우드 구간 중 어느 지점의 관측인지도 남깁니다. VPN은 여러 네트워크 사이에 보호된 통신 경로를 만드는 방식이며, 관측 지점에 따라 바깥 터널 또는 안쪽 통신을 보게 됩니다.

수집한 패킷을 모두 사내로 보내는 방식과 클라우드 안에서 분석하고 필요한 구간만 가져오는 방식은 전송량과 보존 비용이 다릅니다. 여기서는 특정 요금이나 모든 제공자의 기능을 단정하지 않습니다. 현재 서비스의 수집 범위와 정책을 확인하고, 보이지 않는 요청은 서버·인증·서비스 감사 기록으로 보완하세요. 시간대·시계 오차·요청 식별자를 맞춰야 서로 다른 자료를 같은 사건으로 연결할 수 있습니다.

11. 이번 회차의 증거 구분

패킷으로 확인

관측된 링크 형식, EtherType, IP 프로토콜 식별자, 헤더 길이와 전체 길이, 확보된 데이터의 경계.

패킷만으로 확정 불가

포트만으로 응용 프로그램의 정체, 암호화된 본문의 의미, 관측 밖 활동, 캡처의 체크섬 경고만으로 실제 회선 오류 여부.

함께 확인할 자료

캡처 지점과 링크 유형, 미러링 필터·수집 손실 기록, NIC 오프로딩 설정, 단말 프로세스·연결 기록, 서버와 클라우드 감사 로그.

조사 메모도 한 번 써 보겠습니다. 관측: 수집 파일의 Ethernet II 안에서 IPv4 Protocol 6을 확인했고, 헤더 길이로 계산한 TCP 데이터 시작은 프레임 기준 70바이트였다. 가설: 목적지 포트와 일부 데이터가 특정 웹 통신 해석을 지지할 수 있다. 미확인: 해당 프로그램의 정체·서버의 실제 처리·공격 성공은 현재 자료만으로 확인하지 못했다. 추가 확인: 누락 여부, 재조립 상태, 단말 프로세스와 서버 요청 기록을 대조한다.

헤더를 정확히 계산해도 내용과 영향의 결론까지 자동으로 따라오지는 않습니다. 반대로 응용 내용을 못 읽어도 주소·시각·방향·길이·연결 진행 같은 단서를 기록할 수 있습니다. 경계 계산은 어느 바이트를 무엇으로 해석했는지 설명하는 출발점입니다.

12. 복습과 경계 계산 연습

질문: IP 페이로드와 TCP 페이로드는 같을까요?

해설: 이번 TCP over IPv4 예시에서는 다릅니다. IP 페이로드에는 TCP 헤더와 TCP 데이터가 들어 있습니다. TCP 페이로드는 TCP 헤더 뒤의 데이터입니다. 페이로드라고 할 때는 어느 계층을 기준으로 하는지 먼저 확인합니다.

질문: IPv4 IHL이 5이고 TCP Data Offset이 8입니다. IP Total Length가 900바이트라면 TCP 데이터는 몇 바이트일까요?

해설: 단편화되지 않은 완전한 IPv4/TCP 패킷을 가정하면 IP 헤더는 5 × 4 = 20바이트, TCP 헤더는 8 × 4 = 32바이트입니다. 따라서 900 - 20 - 32 = 848바이트입니다. Ethernet 헤더 길이를 이 계산에서 다시 빼지 않습니다.

질문: Ethernet II의 IP 시작 위치는 언제나 14일까요?

해설: 이번처럼 VLAN 태그가 없는 단순 구조에서는 14바이트 뒤입니다. VLAN이나 다른 캡처 링크 형식에서는 위치가 달라지므로 실제 구조를 확인해야 합니다. 프레임 시작 기준인지 IP 헤더 시작 기준인지도 함께 적습니다.

질문: 헤더에서 계산한 TCP 데이터가 944바이트인데 파일에는 58바이트만 보입니다. 통신 오류일까요?

해설: 곧바로 그렇게 판단하지 않습니다. SnapLen 등으로 캡처가 잘렸는지, 실제 저장된 길이는 얼마인지 확인합니다. 캡처 파일에 없는 것과 실제로 전송되지 않은 것은 다른 상황입니다.

조사 메모에는 계산의 전제를 함께 적어 보세요.

VLAN 태그 없는 Ethernet II 및 단편화되지 않은 IPv4/TCP 구조로 해석하였다. IHL과 Data Offset을 바이트로 환산해 TCP 데이터 시작 위치를 계산했다. 캡처 길이와 예상 데이터 길이를 비교했으며, 응용 프로토콜과 처리 결과는 추가 검증이 필요하다.

조건을 바꾼 추가 복습

문제 5. 서버가 사용하는 제품과 다른 공격 경고가 떴습니다. 오탐이라고 끝내도 될까요?

해설: 규칙이 공격 시도를 찾는 것이라면 해당 시도가 정확히 탐지됐을 수 있습니다. 탐지의 정확성, 대상에 대한 적용 가능성, 실제 영향은 나누어 판단합니다. 경고가 없더라도 다른 기록에 활동이 있으면 규칙·설정·수집 범위를 조사합니다.

문제 6. TCP/IP 네 계층의 두 번째 칸이 곧 OSI L2인가요?

해설: 아닙니다. 모델의 계층 수와 번호를 섞으면 안 됩니다. 실무의 L2는 보통 링크, L3는 IP, L4는 TCP·UDP를 가리킵니다. 어떤 모델과 역할을 말하는지 확인합니다.

문제 7. 다른 네트워크 서버로 보내는데 프레임 목적지 MAC이 게이트웨이입니다. 잘못 보낸 것일까요?

해설: NAT 없는 단순 라우팅 예시에서는 자연스럽습니다. IP 목적지는 최종 서버여도 첫 링크의 다음 홉은 게이트웨이일 수 있습니다. 링크의 목적지와 최종 응용 상대를 구별합니다.

문제 8. TCP 옵션 12바이트를 찾았습니다. 길이 12인 옵션 하나일까요?

해설: 여러 옵션과 패딩의 조합일 수 있습니다. 종류·길이 규칙을 하나씩 읽어야 합니다. No-Operation과 End of Option List처럼 한 바이트 형식도 있으므로 모든 두 번째 바이트를 길이로 읽지 않습니다.

문제 9. 원래 예시에서 TCP Data Offset만 5로 바뀌면 데이터 길이와 시작은요?

해설: TCP 헤더는 5×4=20바이트입니다. 데이터는 1000−24−20=956바이트이며 태그 없는 Ethernet II 프레임 기준 시작은 14+24+20=58입니다. 단편화되지 않았고 필요한 바이트가 있다는 전제를 함께 남깁니다.

문제 10. 프레임 기준 오프셋이 70인데 단일 VLAN 태그 4바이트가 앞에 추가되면 IP 안의 데이터도 줄까요?

해설: IP 전체 길이가 그대로라면 TCP 데이터 길이는 줄지 않습니다. 프레임 기준 시작 위치만 70+4=74로 이동합니다. 링크 구조 변화와 IP 내부 길이를 따로 계산합니다.

문제 11. 캡처의 TCP 체크섬 경고 하나로 실제 회선 오류라고 보고할까요?

해설: 호스트 수집 시점과 NIC 오프로딩을 확인하고 가능한 다른 지점과 비교합니다. 오프로딩 가능성이 있다는 이유만으로 모든 경고를 무시하지도 않습니다. 실제 오류와 수집 표현의 차이를 구별할 증거가 필요합니다.

문제 12. IP가 두 겹이면 악성 터널인가요?

해설: 정상 미러링이나 VPN의 캡슐화일 수 있습니다. 링크 형식과 각 헤더의 종류·길이를 따라 안쪽과 바깥쪽의 역할을 구별하고 승인된 수집 경로와 대조합니다. 중첩 자체로 의도를 확정하지 않습니다.

문제 13. HTTP/3 통신에서 TCP SYN이 안 보입니다. 연결 실패일까요?

해설: HTTP/3는 QUIC을 사용하고 QUIC은 UDP로 전달됩니다. TCP 플래그가 없는 구조에서 TCP 연결 설정을 찾는 질문 자체가 맞지 않습니다. 실제 프로토콜과 수집 범위를 먼저 확인합니다.

문제 14. 헤더 길이 합이 IP 전체 길이보다 큽니다. 공격 패킷이 확실한가요?

해설: 먼저 원래 값과 환산값, 캡처 링크 유형, 시작점, 단편 상태, 저장 누락과 디코딩 설정을 확인합니다. 그 뒤 실제 비정상 구조 가능성을 평가합니다. 계산 모순은 재검토의 단서이지 의도나 침해 성공의 증명은 아닙니다.

다음 4강에서는 이 길이와 식별자에 사용한 비트·바이트·16진수를 직접 읽습니다. 지금은 외운 숫자보다 기준 계층·길이 단위·관측 범위를 함께 말하는 습관을 남겨 두세요.

워크북 연계 실습

Ethernet Type, IPv4 Protocol, 상위 데이터의 단서를 구분해 다음 구조를 찾는 연습입니다. 계층을 바꾸어 같은 패킷 읽기에서 단계별 설명과 복습을 읽을 수 있습니다. 이 페이지의 기존 자체 예시는 그대로 유지하며, 원본 PCAP을 실행한 출력으로 제시하지 않습니다.

접근 자료의 역할도 나누어 둡시다. 본 교재는 계층과 캡슐화의 원리를 설명하고, 전자 워크북은 어떤 순서로 도구를 조작하며 관찰할지 연결합니다. 캡처 파일은 저장된 실제 바이트의 근거입니다. 기존 검토에서는 첫째 날 여섯 캡처의 621개 기록을 오프라인으로 대조했습니다. 이것은 이번 강의에서 tcpdump나 Wireshark를 다시 실행했다는 뜻은 아닙니다.

연계 실습에서는 먼저 이름 변환이 적용된 이름과 원래 숫자 주소·포트를 구별하고, 같은 패킷의 Ethernet Type·IP Protocol·전송 계층을 차례로 확인하세요. 표시된 길이의 기준점이 프레임인지 IP인지도 적습니다. 명령의 옵션과 화면 조작은 연결된 가이드에서 따라가되, 여기의 독립 계산 예제를 원본 캡처의 출력으로 옮겨 적지는 마세요.
