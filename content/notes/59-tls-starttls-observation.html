학습 범위

넷째 날 4강에서는 TLS 1.2와 1.3의 연결 수립을 관측 관점에서 비교하고, 재개·0-RTT·SNI와 ECH의 한계, SMTP STARTTLS 업그레이드와 강제 정책을 해석합니다. 메시지는 안전한 정상 합성 예제이며 실제 메일이나 외부 시스템을 시험하지 않았습니다.

1. 자물쇠가 보인다고 업무 결과까지 보이는 것은 아닙니다

센서에서 외부 서버로 향하는 TLS 연결이 보였습니다. 이 사실로 말할 수 있는 것은 관측 지점과 시간에 암호화된 연결 수립이 진행됐다는 정도입니다. 사용자가 로그인했는지, 파일을 내려받았는지, 서버가 요청을 성공 처리했는지는 암호문 바깥의 메타데이터만으로 확정할 수 없어요.

택배 상자를 떠올려 보세요. 겉면의 출발지·도착지와 크기·도착 시각은 보이지만 봉인된 안쪽의 물건은 열쇠 없이 알 수 없습니다. TLS도 IP 주소, 전송 계층의 흐름, 패킷 길이와 시간, 일부 연결 수립 정보는 관측될 수 있지만 응용 데이터는 보호합니다. 이 비유의 한계는 최신 TLS가 상자 겉면의 일부 정보까지 줄이거나 암호화할 수 있고, 여러 이름이 같은 전달망 주소를 공유할 수 있다는 점입니다.

2. TLS 1.2와 1.3은 메시지 이름보다 보호 시점이 다릅니다

ClientHello는 클라이언트가 지원하는 버전·암호 조합과 확장을 제안하는 첫 TLS 수립 메시지입니다. ServerHello는 서버가 선택한 조건을 답합니다. TLS 1.2의 일반적인 인증서 기반 수립에서는 서버 인증서와 키 교환 메시지가 뒤따르고, 양쪽이 키 계산과 검증을 마친 후 응용 데이터를 암호화합니다. 실제 메시지는 선택한 키 교환·인증 방식에 따라 달라집니다.

TLS 1.3은 오래된 알고리즘과 여러 왕복을 줄이고, ServerHello 뒤의 많은 수립 메시지를 수립 트래픽 키로 보호합니다. 그러므로 TLS 1.2에서 보던 순서와 필드를 TLS 1.3에 그대로 대입하면 안 됩니다. 패킷 분석기는 레코드와 수립 메시지를 해석하지만, 캡처가 중간부터 시작했거나 TCP 재조립이 깨졌다면 버전과 메시지를 잘못 읽을 수도 있어요.

정상 합성 캡처를 분석한다면 tls.handshake.type == 1 같은 표시 필터로 ClientHello를 찾을 수 있습니다. tls.handshake.type은 해석된 TLS 수립 메시지 종류 필드이고, == 1은 값이 ClientHello인 항목과 같다는 조건입니다. 이 필터는 캡처 자체를 바꾸지 않으며, 분석기가 TLS로 해석한 패킷만 보여 줍니다. 비표준 포트나 불완전한 재조립에서는 먼저 해당 흐름이 TLS로 해석됐는지 확인합니다.

3. 재개와 0-RTT를 “항상 빠른 같은 연결”로 묶지 않습니다

TLS 1.3에서 서버는 연결 뒤 NewSessionTicket을 보내 재개에 쓸 수 있는 정보를 제공할 수 있습니다. 이후 클라이언트는 사전 공유 키(PSK) 방식으로 새 연결을 재개할 수 있어요. PSK는 양쪽이 공유한 비밀에서 키를 만드는 방식입니다. 재개는 이전 TCP 연결을 계속 쓰는 것이 아니라 새 TLS 연결 수립의 일부 계산을 줄이는 절차입니다.

0-RTT early data는 허용된 재개에서 클라이언트가 첫 비행에 응용 데이터를 함께 보낼 수 있는 선택 기능입니다. RTT는 요청이 상대에게 갔다가 응답이 돌아오는 왕복 시간입니다. 이름 때문에 모든 TLS 1.3 연결이 0-RTT라고 오해하기 쉬운데, 서버와 응용이 명시적으로 허용해야 하며 거부될 수도 있습니다. 0-RTT 데이터는 연결 사이 재전송에 대한 보호가 일반 1-RTT 데이터보다 약하므로, 재실행해도 안전하지 않은 작업에는 사용하면 안 됩니다.

패킷에서 첫 서버 응답 전에 암호화된 레코드가 보인다고 곧바로 중복 업무 처리를 선언하지 마세요. 관측 사실은 클라이언트가 early data를 제안·전송한 정황입니다. 서버가 수락했는지와 응용이 처리했는지는 TLS 상태와 서버 로그가 필요합니다. 같은 요청이 다시 보이면 네트워크 재전송, 클라이언트 재시도, 서버의 0-RTT 거부 후 1-RTT 전송을 구별합니다.

4. SNI가 보이지 않을 때도 관측 가능한 단서는 남지만 결론은 좁아집니다

SNI(Server Name Indication)는 여러 이름을 한 서버 주소에서 제공할 때 클라이언트가 원하는 서버 이름을 ClientHello 확장으로 알려 주는 기능입니다. 전통적인 SNI는 평문 ClientHello에서 보일 수 있지만, 이것은 URL 전체가 아닙니다. 경로·검색어·응용 내용은 HTTPS 안에서 보호됩니다. IP 주소 하나에도 여러 도메인이 있을 수 있으므로 주소를 도메인 하나로 단정하지 않습니다.

ECH(Encrypted Client Hello)는 TLS 1.3에서 민감한 ClientHello 내부를 서버의 공개 키로 암호화해 SNI와 ALPN 같은 필드를 보호합니다. 바깥 ClientHello와 제공자 주소 등 일부 외부 정보는 남을 수 있어도, 관측 센서가 내부 SNI를 직접 읽지 못할 수 있습니다. 암호화 DNS까지 쓰면 센서 앞의 평문 DNS 질의도 없을 수 있어요. 그렇다고 조사가 끝나는 것은 아닙니다. 조직이 관리하는 리졸버·프록시·종단·인증 기록, 서버 주소와 인증된 자산 목록, 시간·방향·바이트 같은 메타데이터를 적법한 범위에서 연결합니다.

복호화가 승인된 환경에서는 클라이언트가 남긴 TLS 세션 비밀을 키 로그 파일로 분석기에 제공해 저장된 캡처를 오프라인 해석할 수 있습니다. 키 로그는 매우 민감하며 해당 세션의 평문을 드러낼 수 있으므로 최소 권한, 짧은 보존, 감사 가능한 전달 경로가 필요합니다. TLS 1.3을 서버 개인키만으로 사후 복호화할 수 있다고 가정하면 안 됩니다.

5. STARTTLS는 같은 연결을 평문 협상에서 TLS로 올립니다

STARTTLS는 처음부터 별도 TLS 포트로 접속하는 대신, 기존 응용 프로토콜 연결에서 서버가 TLS 업그레이드를 지원한다고 알리고 클라이언트가 전환을 요청하는 방식입니다. SMTP에서는 서버의 확장 응답에 STARTTLS가 보이고, 클라이언트가 STARTTLS 명령을 보낸 뒤 성공 응답을 받으면 같은 TCP 연결에서 TLS 수립이 시작됩니다. 그 뒤 SMTP 상태는 새 보안 계층 위에서 다시 이어집니다.

여기서 “STARTTLS를 지원한다”와 “반드시 TLS로 전달한다”를 구분해야 합니다. 기회적(opportunistic) 전송은 상대가 지원하면 TLS를 쓰되 실패하면 평문으로 계속할 수 있습니다. 이 경우 중간자가 광고를 지우거나 협상을 방해하면 다운그레이드가 일어날 수 있어요. 메일 제출·접근과 서버 간 전송은 정책과 포트가 다르므로 한 문장으로 묶지 않습니다.

6. 다운그레이드는 패킷 한 장보다 정책과 장기 기록으로 확인합니다

정상적으로 늘 TLS를 쓰던 도메인의 SMTP 세션에서 어느 날 STARTTLS 광고가 보이지 않고 평문 전달이 이어졌다고 합시다. 관측 사실은 그 수집점에서 광고와 TLS 수립을 보지 못했다는 것입니다. 가설은 중간 장비의 제거, 서버 설정 변경, 다른 MX 선택, 캡처 누락 또는 능동적 다운그레이드입니다. 발신 MTA 로그, DNS와 MX 결과, 수신 서버 설정, 중간 장비 변경, 같은 시간대의 여러 세션과 TLS 보고를 대조해야 원인을 좁힐 수 있습니다.

MTA-STS는 수신 도메인이 TLS와 인증된 MX를 기대한다는 정책을 HTTPS와 DNS로 알리고, 강제 모드에서는 조건을 만족하지 못한 전달을 거부하게 합니다. DANE for SMTP는 DNSSEC으로 인증한 TLSA 레코드를 이용해 다운그레이드에 강한 정책을 제공합니다. TLSRPT는 STARTTLS·MTA-STS·DANE 적용 실패 통계를 수신 도메인에 보고합니다. 각각 배포 전제가 다르며, 한 번의 패킷만으로 정책 적용 성공을 판단하지 않습니다.

복습과 해설

1. TLS 연결이 보이면 로그인 성공도 확인된 것인가요?
아닙니다. TLS 수립과 암호화 레코드는 연결의 존재를 보여 줍니다. 로그인 결과는 서버·인증·응용 로그 또는 승인된 복호화 자료가 필요합니다.
2. TLS 1.3에서는 왜 TLS 1.2의 인증서 순서를 그대로 찾으면 안 될까요?
ServerHello 뒤의 많은 수립 메시지가 수립 키로 보호되며 메시지 구성이 달라졌기 때문입니다. 버전·재개·클라이언트 인증 조건을 먼저 확인하세요.
3. 모든 TLS 1.3 연결이 0-RTT인가요?
아닙니다. 이전 연결에서 얻은 PSK와 서버·응용의 명시적 허용이 필요한 선택 기능입니다. 거부와 재전송 가능성, 재생 위험을 함께 봅니다.
4. SNI가 보이지 않으면 조사를 멈춰야 하나요?
ECH나 캡처 조건으로 SNI가 보이지 않을 수 있습니다. 관리 리졸버·프록시·단말·서버 로그와 주소·시간·방향·바이트를 연결하되 도메인을 추측으로 확정하지 않습니다.
5. STARTTLS 광고가 사라진 한 세션만으로 공격이라고 결론 내릴 수 있나요?
아닙니다. 설정 변경, 다른 서버, 중간 장비, 캡처 누락도 가능합니다. MTA 로그와 DNS·MX·정책·TLSRPT의 장기 기록을 대조합니다.

공식 자료와 확인일

2026-11-25에 RFC 8446의 TLS 1.3 수립·재개·0-RTT, RFC 9849의 Encrypted Client Hello, RFC 3207의 SMTP STARTTLS, RFC 8461의 MTA-STS, RFC 8460의 TLS Reporting, RFC 7672의 DANE SMTP, Wireshark 사용자 안내서의 TLS 키 로그를 확인했습니다. 실제 메일 전송·복호화·외부 시스템 시험은 수행하지 않았습니다.
