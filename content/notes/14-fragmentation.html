1. 단편화는 정상 기능이면서 중요한 조사 대상이다

IP 단편화, fragmentation는 하나의 IP 데이터그램을 더 작은 여러 IP 조각으로 나누어 전달하는 기능입니다. 경로의 링크마다 운반할 수 있는 크기가 다를 수 있기 때문에 필요해졌습니다. 수신 측에서는 관련 조각을 원래 위치에 놓아 IP 데이터를 재조립합니다. 먼저 정상 구조를 이해해야 손실·오류·악의적인 조작을 구분할 수 있습니다.

현대에도 이 원리를 배워야 하는 이유는 두 가지입니다. 정상 업무에서도 큰 UDP 메시지·터널·MTU 조건 때문에 조각이 생길 수 있고, 조각 처리와 재조립은 장비의 자원·구현·탐지 방식에 영향을 주기 때문입니다. 다만 ‘조각이 보였다’와 ‘공격이 확인되었다’는 다른 결론입니다. 원문의 숨김·오구성·공격이라는 조사 방향은 가설로 사용하고, 정상적인 생성 조건도 함께 검증합니다.

이번에는 MTU, 조각을 묶는 정보, DF·MF·Offset과 첫째·중간·마지막 조각을 판별하는 원리를 다룹니다. 원문의 뒤에 이어지는 긴 덤프의 전체 길이·오프셋 계산은 다음 회차에서 충분한 분량으로 진행합니다. 설명을 줄여 한 회차에 몰아넣지 않고 개념 경계에서 나눴습니다.

예시와 확인 범위

별도 실습 PCAP은 제공되지 않았습니다. 아래 주소·필드·길이·표·도식은 문서용 주소로 자체 구성한 가상 예시입니다. 원본 도구의 실행 출력이나 실제 사건의 관측 결과가 아닙니다. 검산한 계산과 실제 네트워크에서 확인한 결과를 구분합니다.

2. MTU는 현재 링크에서 운반할 IP 크기의 한도다

MTU, Maximum Transmission Unit는 해당 링크에서 한 번에 운반할 수 있는 데이터 단위의 최대 크기입니다. 일반적인 Ethernet의 IP MTU1500은 Ethernet 헤더와 FCS까지 합한 전체 프레임 크기가 아니라, 그 안에 담기는 IP 패킷의 한도입니다. 구성에 따라 다른 MTU도 있으므로 모든 링크가 언제나1500이라고 가정하지 않습니다.

가상 경로 A→R→B에서 A 쪽 링크의 IP MTU가2000, R의 B 방향 출력 링크 MTU가1500이라고 하겠습니다. A가 IP 전체 길이1800인 IPv4 데이터그램을 만들었다면 첫 링크에서는 운반할 수 있어도 R의 출력 링크에는 그대로 넣을 수 없습니다. R은 출력 링크의 한도와 DF 등 처리 조건을 확인해야 합니다. 라우터의 입력 링크에 들어왔다는 사실이 다음 링크에도 들어간다는 보장은 아닙니다.

송신 호스트가 메모리에서 만든 IP 패킷이 자기 출력 인터페이스보다 클 때도 관련 처리가 필요합니다. 그러나 ‘메모리에 크게 보인다’는 현상만으로 실제 회선의 IP 단편화를 확정하지 않습니다. 호스트의 분할 오프로딩·수집 위치 때문에 큰 데이터 단위를 관측하는 경우도 있고, 실제 송신 단계에서 전송 계층의 분할이 이루어질 수도 있습니다. 회선의 조각 여부는 IP의 MF·Offset 등과 수집 조건으로 확인합니다.

DF가0이고 필요한 조건이 맞으면 IPv4 송신자나 라우터가 데이터를 나누어 각 조각에 맞는 IP 헤더를 붙일 수 있습니다. 반대로 DF가1이면 그 원래 데이터그램을 전달 중 단편화하는 경로를 선택할 수 없습니다. MTU 초과라는 원인과 단편화·폐기라는 실제 결과를 나누어 보세요. [1] [2]

3. 무엇을 나누고 무엇을 다시 붙이는가

IPv4 단편화에서 나누는 대상은 원래 IP 헤더 뒤의 데이터입니다. 이 영역에는 TCP·UDP·ICMP의 헤더도 포함됩니다. IP 입장에서 그 위의 프로토콜 헤더 역시 자신이 운반하는 데이터이기 때문입니다. 원래 IP 헤더 자체를 앞부분·뒷부분으로 쪼개 각 조각에 나누어 싣는 것은 아닙니다.

대신 각 조각에는 독립적으로 해석할 수 있는 IP 헤더가 있습니다. 따라서 ‘원래 헤더의 사본’이라는 설명은 기본 구조와 관련 필드를 이어받는다는 뜻으로 읽습니다. 각 조각의 Total Length·MF·Offset·체크섬은 달라질 수 있고, 옵션은 복사 규칙에 따라 모든 조각에 똑같이 들어가지 않을 수도 있습니다. 서로 다른 경로를 거쳤다면 TTL 등도 같다고 기대하지 않습니다.

또한 모든 조각에 TCP·UDP 헤더가 다시 붙는 것은 아닙니다. 일반적인 원본의 앞부분에 있던 전송 헤더는 앞 조각의 데이터에 포함되고, 뒤 조각은 원래 데이터의 이어지는 부분을 운반합니다. 뒤 조각의 Protocol이 UDP라고 표시되어도 그 조각의 첫 데이터 바이트를 곧바로 새 UDP 헤더라고 해석하면 안 됩니다.

이는 TCP 세그먼트 분할과도 다릅니다. 여러 TCP 세그먼트는 각각 TCP 헤더와 순번 정보를 가진 전송 단위입니다. 하나의 IP 데이터그램이 여러 IP 조각으로 나뉜 경우에는 IP 재조립 이후에 그 안의 원래 전송 단위를 해석합니다. 큰 파일 하나, TCP 세그먼트 하나, IP 데이터그램 하나, IP 조각 하나를 같은 크기나 경계로 취급하지 마세요.

4. 단편화를 줄이려는 이유와 공격 판정은 구분한다

조각마다 IP 헤더가 추가되므로 전송량과 처리량에 부담이 생깁니다. 수신자는 조각이 모일 때까지 상태와 메모리를 유지해야 하고, 중간 방화벽·NAT·분석기도 필요한 처리를 해야 합니다. 한 조각이 빠지면 원래 IP 데이터를 완성할 수 없을 수 있습니다. 단편화가 기능상 가능하다고 성능과 안정성에 언제나 좋은 선택은 아닙니다. RFC8900은 이런 취약한 전달 조건을 정리합니다. [3]

가상 상황에서 조각 세 개 중 둘만 도착했다면, 나머지 둘의 데이터가 일부 보이더라도 원래 데이터그램을 완성했다고 할 수 없습니다. IP 자체가 빠진 조각을 알아서 재전송하는 것도 아닙니다. TCP나 응용 프로토콜이 손실을 알아차려 필요한 데이터를 다시 보낼 수 있지만, 그때 재전송·재분할되는 단위와 크기는 해당 구현·경로에 따라 달라집니다. ‘원래와 정확히 같은 IP 패킷이 반드시 다시 단편화된다’고 일반화하지 않습니다.

정상 흐름에서 조각이 생겼다면 먼저 MTU·터널 오버헤드·UDP 메시지 크기·PMTU 학습 상태를 확인합니다. 비정상적으로 자원을 쓰거나 규칙의 예상과 다르게 재조립되는 흐름은 별도의 공격 가설로 검증합니다. 드물다는 사실만으로 악성 의도나 공격자의 수준을 확정하지 않습니다.

5. 원문의 취약점 사례는 ‘현재 감염 증거’가 아니라 처리 위험의 역사다

원문은 조각·옵션·재조립 구현에 결함이 생길 수 있다는 점을 과거 취약점으로 보여 줍니다. 그 학습 포인트는 여전히 중요하지만, 2021년 당시의 ‘최근’을 현재 사건으로 옮기거나 모든 단편 패킷을 해당 취약점 시도로 이름 붙이면 안 됩니다. 실제 제품·버전·수정 상태와 일치하는 입력·영향 증거를 확인해야 합니다.

6. DNS와 EDNS는 정상적인 단편화의 배경이 될 수 있다

EDNS(0)는 DNS 기능을 확장하는 체계이며 UDP 수신 용량을 알리는 정보도 포함합니다. 이때 알리는 크기는 수신 측의 지원 용량이지, 모든 응답이 반드시 그만한 길이로 나간다는 뜻이 아닙니다. 또한 DNS 메시지 크기, UDP 데이터그램 길이, IP 전체 길이, 링크 MTU는 서로 다른 경계입니다. [8]

원문은 큰 EDNS 용량을 사용하는 구현과 DNS 응답이 단편화되는 경우를 소개합니다. 오늘날의 모든 Microsoft DNS가 고정된 같은 값으로 항상 단편화를 만든다고 일반화하지 않습니다. 요청자가 알린 용량과 실제 응답 크기, 서버 설정·버전, 경로 MTU를 확인해야 합니다. DNSSEC 등으로 응답이 커지거나 경로 한도가 작을 때도 이 문제를 만날 수 있습니다.

2021년 이후 보충 · 2026년 11월 1일 확인

2025년의 Informational RFC9715는 DNS over UDP에서 IP 단편화를 피하고 필요한 경우 TCP로 전환하는 방향을 설명합니다. 이 문서는 기본 최대 DNS/UDP 페이로드로1400을 권고하고 더 작은 값도 허용하며,1232를 사용해 온 배경도 별도로 다룹니다. 이를 모든 환경의 단 하나의 절대값으로 바꾸지 않습니다. 실제 MTU·추가 헤더·구현 정책을 확인해야 합니다. [9]

1232라는 예시의 계산은 IPv6 최소 MTU1280에서 기본 IPv6 헤더40과 UDP 헤더8을 빼는 1280 - 40 - 8 = 1232입니다. 이 값은 DNS 메시지를 담을 예산을 설명하며 IPv4 단편의 오프셋 단위나 Ethernet 프레임 길이와 같은 숫자가 아닙니다. 확장 헤더·터널 등으로 조건이 달라지면 다시 계산해야 합니다.

정상 DNS가 단편화될 수 있다는 사실이 조각을 무조건 허용하라는 뜻도, 조각을 무조건 공격으로 차단하라는 뜻도 아닙니다. 메시지 크기를 줄이거나 전송을 바꾸는 정책, TCP 도달성, DNS 서버·리졸버의 재시도와 실패 로그를 함께 검토합니다. UDP 응용의 메시지 크기와 경로 한도를 고려하라는 일반 지침도 유효합니다. [17]

7. 조각들을 묶을 때 ID 하나만 보지 않는다

한 원래 IP 데이터그램에서 나온 관련 조각 묶음을 원문은 fragment train이라고 부릅니다. 기본적으로 조각들의 출발지·목적지 IP와 Protocol, IP Identification을 함께 보아야 합니다. 같은 묶음의 IP ID는 같아야 하지만, ID만 같다고 모두 같은 묶음은 아닙니다. 제한된16비트 값이므로 다른 흐름·다른 시점에서도 같을 수 있습니다.

가상으로192.0.2.10→198.51.100.20, Protocol17, ID4242인 조각들을 조사한다고 하겠습니다. 같은 ID4242라도 반대 방향이거나 다른 목적지·프로토콜이면 별도 후보입니다. 같은 네 값이 맞더라도 수집 시각·인터페이스·터널 문맥과 중복 수집·ID 재사용 가능성을 함께 확인해야 합니다. 이 기본 키가 실제 자산이나 사용자를 인증하는 것도 아닙니다.

12강에서 본 RFC6864의 구분도 유지합니다. 단편화될 수 없는 atomic 데이터그램의 ID를 재조립용 고유값처럼 활용하지 않습니다. 반대로 실제 조각이나 단편화가 허용된 데이터그램의 ID 제약까지 사라진 것은 아닙니다. ID·Offset·MF를 서로 연결해서 읽어야 하는 이유입니다. [14]

8. DF는 단편화하지 말라는 뜻이지 도착 보장은 아니다

DF, Don't Fragment가1이면 전달 중 그 IPv4 데이터그램을 단편화해서 작은 링크에 맞추는 동작은 허용되지 않습니다. 가상 IP 패킷1800바이트가 MTU1500인 출력 링크를 만나 DF1이라면, 라우터는 이를1800 그대로 내보내거나 임의로 조각내지 않고 폐기해야 합니다. 일반적인 조건에서는 ICMP Type3·Code4, 단편화가 필요하지만 DF가 설정되었다는 오류를 돌려보냅니다.

IPv4 PMTUD, Path MTU Discovery는 경로에서 사용할 수 있는 크기를 알아내는 방식입니다. DF가 설정된 패킷에 관한 오류와 다음 홉 MTU 정보를 이용해 송신 측의 크기 추정을 줄일 수 있습니다. PMTU는 개별 인터페이스 MTU와 달리 그 경로에서 통과할 수 있는 한도를 뜻합니다. [10]

원문의 ‘발견 후 모든 미래 패킷은 그 MTU 이하’라는 설명은 목표 동작으로 이해하되 고정된 영구 보장으로 읽지 않습니다. 경로·터널·인터페이스가 바뀔 수 있고, 캐시·재탐색·구현 정책이 있습니다. 또한 ICMP가 도착하지 않는다고 큰 패킷이 목적지에 도달했다고 증명되는 것은 아닙니다. 오류가 차단·제한·누락되어 큰 통신만 멎는 현상도 조사해야 합니다.

PMTU 오류의 출발지·인용 정보가 실제 송신과 연결되는지도 확인해야 합니다. 패킷 하나에 적힌 MTU를 무조건 신뢰해 적용되었다고 하거나, ICMP가 보였다는 이유만으로 송신자의 실제 크기 조절까지 완료되었다고 하지 않습니다. 이후 패킷 크기·재시도·단말 상태로 넘어갑니다.

9. 현재의 PMTU 학습과 IPv6를 구분한다

PLPMTUD 계열은 패킷을 만드는 계층에서 탐침과 도달 확인 등을 활용해 사용할 크기를 알아내는 관점입니다. 데이터그램 전송을 위한 RFC8899의 DPLPMTUD는 ICMP에만 의존하지 않는 방식과 손실·확인 신호의 처리를 다룹니다. 이 문서는2020년에 이미 나왔으므로 단순히2021년 이후에 새로 생긴 기능이라고 소개하지 않습니다. [11]

그렇다고 모든 응용이 이 기능을 구현했다는 뜻은 아닙니다. 조각이 보이지 않고 ICMP도 없다는 관찰만으로 ‘DPLPMTUD가 정상 작동했다’고 쓰지 않습니다. 어떤 전송 프로토콜·버전·설정이 탐침과 확인을 지원하는지, 실제로 크기를 바꾸었는지 확인해야 합니다.

IPv6 라우터는 IPv4처럼 전달 중 단편화하지 않습니다. 필요한 경우 송신 측이 IPv6의 단편화 구조를 사용하며, 큰 패킷을 전달할 수 없는 라우터는 조건에 맞게 ICMPv6 Packet Too Big을 알립니다. IPv4의 DF/MF/13비트 필드를 IPv6 기본 헤더에 그대로 찾으면 안 됩니다. [12]

원문의 ‘IPv6에서는 MTU 발견이 필수’라는 표현도 구체화해야 합니다. RFC8201은 IPv6 노드에 PMTUD 구현이 반드시 요구되는 것은 아니라고 명시하며, 해당 기능을 구현한 경우의 동작을 설명합니다. 최소 한도와 선택한 패킷 크기 전략, 송신 측 단편화·오류 처리의 규칙을 나누어 보아야 합니다. [13]

10. MF는 뒤쪽 데이터의 존재이며 도착 순서가 아니다

MF, More Fragments가1이면 원래 데이터 안에서 더 큰 오프셋에 해당하는 조각이 있다는 뜻입니다. 정상적인 한 묶음에서 데이터 끝을 담은 마지막 조각은 MF0이고, 그 앞의 조각들은 MF1입니다. MF1이 보인다는 것 자체가 해당 패킷도 조각이라는 단서입니다.

하지만 ‘더 있다’는 말은 현재 시각 이후에 반드시 도착한다는 예약이 아닙니다. 뒤쪽 조각이 먼저 도착했거나, 다른 경로를 거쳐 늦거나, 아예 손실될 수 있습니다. 원문의 줄지어 선 그림은 데이터의 이어짐을 이해하는 비유로 보고 실제 수집 순서로 옮기지 않습니다.

MF0인 조각을 먼저 봤다면 원래 데이터의 끝 위치를 계산할 단서가 생긴 것입니다. 앞부분까지 모두 확보했다는 뜻은 아닙니다. 마지막 위치의 조각을 읽은 일과 전체 데이터그램이 완성된 일은 다릅니다. 수신자가 완성했다고 판단하려면 필요한 구간이 모두 채워졌는지 확인해야 합니다.

따라서 보고서에서 ‘마지막 패킷이 도착했다’를 쓸 때는 마지막 수집 레코드인지, 원래 데이터의 끝을 가진 조각인지 구분합니다. 보통 이 회차에서 말하는 마지막은 데이터 위치 기준입니다.

11. Offset의 기준점은 원래 IP 데이터의 시작이다

Fragment Offset은 이 조각의 데이터를 원래 IP 데이터 영역의 어디에 놓을지 알려 줍니다. 기준0은 원래 IPv4 헤더 바로 뒤입니다. 현재 조각의 IP 헤더 시작이나 Ethernet 프레임 시작이 아닙니다. 따라서 오프셋 바이트 위치를 구한 뒤 원래 IP 헤더20을 더해 ‘앞에 이미 온 데이터’라고 계산하지 않습니다.

필드의 단위는8바이트이므로 바이트 위치 = 원시 Offset 값 × 8입니다. 원시 값5라면 5 × 8 = 40으로, 이 조각의 데이터가 원래 데이터의40번 바이트부터 놓인다는 뜻입니다. 원시 값10은80바이트 위치입니다. 원시 필드 숫자와 도구가 바이트로 환산한 표시를 혼동하지 마세요.

한 조각이 원래 데이터의40~79번을 담으면 길이는 79 - 40 + 1 = 40바이트입니다. 이 조각의 오프셋은40을8로 나눈5입니다. 구간을 반열린 표기 [40,80)로 쓰면 끝80은 포함하지 않으므로 길이는 80 - 40 = 40으로 계산할 수 있습니다. 본문 표와 도식에서는 어느 표기인지 함께 적습니다.

오프셋은 위치이지 시간 순번이 아닙니다. Offset10을 보았다고 반드시 앞에10개의 조각이 있었다는 뜻도 아닙니다. 앞의80바이트가 한 조각이었는지 여러 조각이었는지는 길이·MF·다른 조각을 확인해야 합니다.

12. 왜 8을 곱하고, 최대값은 왜 8192가 아닐까

전체 길이는16비트이므로 2¹⁶ = 65,536가지를 표현하고 값의 범위는0~65,535입니다. Offset은13비트이므로 2¹³ = 8,192가지, 원시 값의 범위는0~8,191입니다. 원문의 설명에서 값의 개수와 최대값을 분리해 읽어야 합니다. 원시 Offset의 최대값은8,192가 아니라8,191입니다.

두 필드의 비트 수 차이는3이므로 2³ = 8 단위를 사용하면 적은 비트로 큰 위치 범위를 나타낼 수 있습니다. 계산 관점에서는 원시 값을 왼쪽으로3비트 옮기는 것과 같습니다. 예를 들어5는2진수101이고, 뒤에0 세 개를 붙인101000은40입니다.

표현상 최대 바이트 위치는 8,191 × 8 = 65,528입니다. 그러나 이 값이 모든 조각에서 유효한 시작 위치라는 뜻은 아닙니다. 실제로는 재조립할 IP 전체 길이·헤더·데이터 끝이 규격의 한도 안에 들어야 합니다. ‘필드에 넣을 수 있다’와 ‘다른 길이 조건까지 맞는 유효한 패킷이다’는 별도 질문입니다.

끝이 아닌 조각의 데이터 길이는 다음 조각의 시작을8바이트 단위로 표현할 수 있도록8의 배수가 되어야 합니다. 마지막 조각의 데이터 길이는8의 배수일 필요가 없습니다. 따라서 원문의 ‘최소 데이터8바이트’를 모든 마지막 조각까지 적용하지 않습니다. 다음 절의 작은 가상 예제에서는 마지막 데이터를3바이트로 두어 이 차이를 보여 줍니다.

‘모든 조각 길이가8의 배수’라는 말도 헤더까지 포함한 Total Length에 무조건 적용하면 안 됩니다. 이 정렬 조건은 조각이 운반하는 IP 데이터 길이에 대한 것입니다. IP 헤더가20이면 데이터40인 조각의 IP 전체 길이는60입니다. 길이의 범위를 다시 나누어 보아야 합니다.

13. 두 바이트에서 Flags와 Offset을 분리한다

IP 시작 기준6번 바이트의 상위3비트가 예약·DF·MF이며, 나머지5비트와7번 바이트 전체가13비트 Offset입니다. 두 바이트를 네트워크 순서의16비트 값으로 읽은 뒤 구분하면 계산이 분명해집니다.

자체 계산을 위한 비트 마스크는 예약 0x8000, DF 0x4000, MF 0x2000, Offset 부분 0x1fff입니다. AND 연산은 지정된 비트만 남기는 데 사용합니다. 예를 들어0x2005에서 Offset을 구하면 0x2005 AND 0x1fff = 0x0005이고, MF 부분은0이 아니므로 설정된 상태입니다.

따라서0x2005 전체를10진수8197로 바꾸어8을 곱하면 안 됩니다. 그 숫자에는 MF가 섞여 있습니다. 위치는 원시 Offset5에8을 곱한40바이트입니다. 두 바이트를 먼저 정확히 분해한 뒤 단위를 바꾸는 순서를 지키세요.

14. 첫째·중간·마지막 조각을 판별한다

기본 판별은 MF=1 또는 Offset>0이면 조각이라는 관계입니다. MF0만 보고 비단편 패킷이라고 끝내지 말고 Offset도 봅니다. 아래는 정상적인 구조를 전제로 한 기본 분류이며 예약 비트·DF 모순·잘림·잘못된 길이 등은 별도 검증 대상입니다.

MF와 원시 Offset의 네 가지 조합
MFOffset기본 분류증명하지 않는 것
00단편화되지 않은 데이터그램DF·정상 처리·공격 여부는 별도
10원래 데이터의 첫 조각가장 먼저 수집되었다는 뜻 아님
10보다 큼첫째도 끝도 아닌 중간 조각앞 조각 개수·수집 완료는 모름
00보다 큼원래 데이터의 마지막 조각앞부분까지 모두 도착했다는 뜻 아님

원문의 비트 그림 문제도 이런 방식으로 MF와 Offset을 따로 보아야 합니다. 다음은 같은 원리를 새 값으로 연습하는 가상 예제입니다. A·B·C라는 표시는 패킷 캡처의 실제 번호가 아니라 데이터 위치를 설명하기 위한 이름입니다.

자체 구성한 작은 조각 묶음 — 주소·Protocol·ID는 같다고 가정
조각·필드6~7해석IP 데이터 구간·길이IP 헤더20일 때 전체
A · 0x2000MF1,Offset0 · 첫째[0,40) · 40바이트60바이트
B · 0x2005MF1,Offset5×8=40 · 중간[40,80) · 40바이트60바이트
C · 0x000aMF0,Offset10×8=80 · 마지막[80,83) · 3바이트23바이트

C가 먼저 도착해도 마지막 조각이라는 분류는 변하지 않습니다. C를 통해 원래 IP 데이터 끝이83이라는 단서가 생기지만 A·B의80바이트가 아직 없다면 완성되지 않습니다. A·B·C를 모두 확보하고 겹침·빈 구간이 없다면 데이터 합계는 40 + 40 + 3 = 83, 기본 헤더20을 가진 원래 IP 전체 길이는 20 + 83 = 103바이트입니다.

전달된 세 조각의 IP 길이를 더하면 60 + 60 + 23 = 143바이트입니다. 원래103보다40이 큰 것은 헤더20이 두 개 더 붙었기 때문입니다. 작은 조각은 원리를 보이기 위한 자체 예시이며 실제 네트워크의 일반적인 생성 크기나 공격 증거로 제시한 것이 아닙니다.

15. 마지막 조각을 알아도 재조립 완료는 따로 확인한다

수신 측은 관련 조각을 묶고 오프셋과 길이로 채워진 구간을 관리합니다. 마지막 조각의 Offset과 데이터 길이로 전체 데이터 끝을 알더라도, 그 앞에 빈 구간이 있으면 완성이 아닙니다. 이처럼 구간의 채워짐과 빈틈을 생각하면 순서가 달라도 조립할 수 있는 이유가 이해됩니다. RFC815는 이런 재조립 알고리즘의 관점을 설명합니다. [15]

일반적인 IP 전달에서 원래 데이터그램으로 재조립하는 곳은 최종 목적지입니다. 경유 라우터가 매 홉마다 모두 재조립한 뒤 다시 나누는 것이 기본 절차는 아닙니다. 다만 터널 종단·보안 장비·NAT·분석기의 상태 관리 등 실제 구성은 따로 확인해야 합니다.

원문의 ‘마지막을 제외하면 같은 크기’라는 설명은 최대 크기로 채워 나누는 흔한 예제를 이해하는 데 유용합니다. 그러나 같은 크기여야 한다는 보편 규칙은 아닙니다. RFC791도 더 작은 크기를 만드는 대안을 설명하며, 경로에서 다시 단편화될 수도 있습니다. 길이 불균일만으로 악성이라고 단정하지 말고 정렬·위치·길이·경로 조건을 검증합니다.

IDS·IPS의 조각 재조립이 대상과 다르면 탐지의 해석 범위가 달라질 수 있습니다. 이 문제를 검증하려면 센서가 본 모든 관련 조각, 수집 손실·재조립 설정·제한과 대상 처리 결과를 대조해야 합니다. 캡처 파일에서 재조립한 것과 실제 호스트가 받아들여 응용에 전달한 것은 동일한 증거가 아닙니다.

암호화된 TLS 데이터를 담은 IP 조각을 모두 합쳤다고 TLS 본문까지 평문으로 읽을 수 있는 것도 아닙니다. IP 재조립·TCP 스트림 재구성·TLS 복호화·응용 처리의 증거를 단계별로 구별합니다. 패킷 분석은 여전히 가치가 있지만 각 단계가 답하는 질문을 정확히 유지해야 합니다.

16. 이번 회차의 증거 구분과 조사 메모

실제 자료에서는 먼저 출발지·목적지·Protocol·ID와 수집 문맥을 연결하고, 각 조각의 IHL·Total Length·MF·Offset을 읽습니다. 그다음 데이터 구간을 계산해 중복·빈틈·끝 위치를 검토합니다. 실제 수신·재조립·응용 결과는 다음 증거로 확인합니다. 필드와 계산을 확인하지 않은 채 공격 이름부터 붙이지 않습니다.

Wireshark에서는 ip.flags.mf == 1 || ip.frag_offset > 0 같은 표시 필터로 IPv4 조각 후보를 고를 수 있습니다. ||는 둘 중 하나라도 참이라는 뜻입니다. MF1만 찾으면 MF0인 마지막 조각을 놓칩니다. 필터는 조각을 선택할 뿐 관련 묶음의 완전성·정상성·공격 성공을 판정하지 않습니다. [16]

패킷으로 확인 가능한 사실

관측된 IP 주소·Protocol·ID·DF/MF·원시Offset·길이, 계산된 데이터 위치·범위, 확보한 조각의 시간 관계와 관측된 ICMP 오류입니다.

단독으로 확정할 수 없는 부분

앞 조각 개수·모든 경로·실제 PMTU 학습 성공, 보이지 않는 조각의 원인, 대상 재조립·취약점 악용·응용 처리 성공, 공격 의도·도구·숙련도와 암호화 본문의 의미입니다.

함께 확인할 자료

출력·경로 MTU와 터널 오버헤드, 송신·수신·센서의 수집 위치 및 손실, PMTU·ICMP·재조립 기록과 자원 상태, DNS/UDP 크기·재시도·TCP 전환, 자산 버전·패치와 단말·서버 로그입니다.

가상 묶음의 조각 C는 MF0·원시Offset10·데이터3바이트로 끝 위치83을 알린다. C가 먼저 수집되었어도 데이터 위치상 마지막이다. A·B를 확보하기 전에는 전체 데이터의 재조립 완료를 주장할 수 없다. 이 예제는 계산 검증이며 실제 네트워크 수신 결과는 제공되지 않았다.

17. 복습 — 단위와 순서의 함정을 피하기

이번 범위의 원문 비트 판별 문제는 첫째·중간·마지막 조각의 분류를 익히는 것이 목표입니다. 아래는 독립적인 값과 문맥으로 만든 복습입니다. 실제 PCAP을 실행한 정답이라고 표시하지 않습니다.

질문 1: IP 길이1800이 MTU1500 링크를 만나면 무조건 조각이 생길까요?

해설: DF와 처리 조건을 확인해야 합니다. IPv4에서 DF1이라면 전달 중 단편화 대신 폐기·조건부 ICMP 오류가 문제입니다. 호스트 수집의 큰 데이터 단위가 실제 회선의 조각인지도 별도 확인합니다.

질문 2: 원래 UDP 헤더는 각 IP 조각에 다시 붙을까요?

해설: 원래 IP 데이터의 일부로 나뉩니다. 각 조각에는 자체 IP 헤더가 있지만 뒤 조각마다 새 UDP 헤더가 생기는 것은 아닙니다. Protocol17만 보고 뒤 조각의 처음을 UDP 헤더로 읽지 않습니다.

질문 3: MF0이면 비단편 데이터그램일까요?

해설: Offset도 봅니다. MF0·Offset>0이면 마지막 조각입니다. MF0·Offset0이 기본적인 비단편 조합입니다. 실제 형식의 일관성은 별도로 검증합니다.

질문 4: Offset5는 원래 데이터의5번 바이트나 다섯 번째 조각일까요?

해설: 원시 값5×8=40바이트 위치입니다. 시간 순서나 앞 조각 개수를 뜻하지 않습니다. IP 헤더20을 여기에 더해 앞선 데이터 길이로 계산하지 않습니다.

질문 5: 13비트 Offset의 최대값은8192이고 최대 위치는65536일까요?

해설:8192는 값의 개수입니다. 최대 원시 값8191×8=65528이 표현상의 위치 한도입니다. 실제 유효성은 전체 IP 길이·헤더·끝 위치 조건까지 확인합니다.

질문 6: 마지막 조각의 데이터가3바이트면8의 배수가 아니므로 무조건 오류일까요?

해설: 마지막 데이터에는 그 정렬 조건을 적용하지 않습니다. 끝이 아닌 조각의 데이터 길이와 IP 전체 길이의 구분도 필요합니다. 사례의 A·B 데이터40은8의 배수이고 C의 끝 데이터3은 나머지입니다.

질문 7: 0x2005를 그대로8배 하면 위치일까요?

해설: MF가 섞인 전체 값이므로 먼저0x1fff로 Offset 부분만 남깁니다. 결과5를8배 해40을 얻고, MF1이므로 중간 조각으로 분류합니다.

질문 8: C→A→B 순서로 캡처했는데 C가 마지막 조각이라는 설명은 모순일까요?

해설: 마지막은 데이터 위치 기준입니다. C가 끝83을 알리더라도 앞80바이트가 채워져야 완성입니다. 수집 순서와 재조립 위치를 구분합니다.

질문 9: EDNS 용량4096을 보았으면 DNS 응답이4096바이트로 조각났다고 확정할까요?

해설: 수신 용량 광고와 실제 응답 길이는 다릅니다. UDP·IP·MTU 경계와 서버 정책, 실제 응답·TCP 전환을 확인해야 합니다. 광고 숫자 하나는 단편화 관측이 아닙니다.

질문 10: 조각마다 길이가 다르면 공격이거나 높은 숙련도의 증거일까요?

해설: 그렇지 않습니다. 생성 방식·재단편화·헤더 옵션과 경로 한도를 확인합니다. 악성 가설은 재조립 모순·자원 영향·정책과 전후 활동으로 검증하고 과거 CVE 이름만으로 확정하지 않습니다.

추가 연습: 가상 묶음에서 B를 지운 뒤 조사 메모를 다시 써 보세요. A와 C의 총 데이터는43바이트이지만 원래 끝은83이고 [40,80) 구간40바이트가 비어 있습니다. ‘끝 조각이 있다’는 사실과 ‘전체를 확보했다’는 결론을 분리하는 연습입니다. 다음 회차에서는 같은 사고 과정을 실제 헤더 덤프 형식의 길이·오프셋 계산으로 확장합니다.
