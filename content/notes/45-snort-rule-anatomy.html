학습 범위

셋째 날 6강에서는 정상 상태 알림을 고르는 규칙을 한 줄씩 읽습니다. 주소는 문서용이고 메시지와 규칙은 독립적인 교육 예제입니다. 경보가 나와야 하는 경우와 빠져야 하는 경우를 함께 정합니다.

1. 규칙 파일을 열기 전에 탐지 의도를 한 문장으로 씁니다

업무용 상태 점검 앱이 보낸 정상 메시지를 교육용 캡처에 넣었습니다. “UDP로 지정한 방향과 포트에 도착했고 데이터가 NOTE: READY로 시작하는 경우를 찾아 주세요.” 여기에는 프로토콜, 주소 방향, 목적지 포트, 검사할 데이터의 시작점이라는 독립된 조건이 있습니다. 각 조건을 문장으로 적어야 코드로 옮길 때 한 가지를 빠뜨려도 알아챌 수 있어요.

창고에서 물건을 분류할 때 먼저 배송 구역과 받는 곳을 확인하고, 상자 안의 라벨을 읽는 일과 닮았습니다. 하지만 네트워크에서는 한 메시지가 여러 세그먼트에 걸쳐 있거나 검사기가 라벨을 원래 바이트와 다른 형태로 꺼내 줄 수 있습니다. “어디에서 찾기 시작하는지”를 함께 지정해야 합니다.

공급하는 기본 규칙이 있더라도, 왜 경보가 나왔는지 확인하려면 헤더와 옵션을 읽어야 합니다. 조직의 정상 도구가 우연히 같은 문자열을 보낼 수도 있고, 필요한 필드가 받는 센서에서 보이지 않을 수도 있습니다. 취약점 권고나 위협 보고서는 어떤 방어 관측이 필요한지 알려 주지만, 규칙은 실제 수집 환경에서 검증 가능한 조건으로 다시 써야 합니다.

2. 규칙의 머리말과 괄호 안을 나눠 봅니다

다음은 Snort 3에서 파일로 검사할 수 있도록 작성한 가상 예입니다. 목적은 정상 표식을 검증하는 것이며, 생산 규칙을 배포하는 예는 아닙니다.

alert udp 192.0.2.60 any -> 198.51.100.70 5514 (msg:"LAB status message"; content:"NOTE|3a 20|READY",offset 0,depth 11; sid:1000045; rev:1;)
규칙을 왼쪽부터 읽는 순서
구간예제 값이 조건이 묻는 것
머리말 동작alert조건이 맞으면 어떤 종류의 이벤트를 처리하나요?
머리말 프로토콜udp어떤 전송 프로토콜을 대상으로 하나요?
출발 주소·포트192.0.2.60 any어느 주소에서 왔나요? 출발 포트는 제한하나요?
방향·목적 주소와 포트-> 198.51.100.70 5514어느 쪽으로, 어느 목적 포트로 향했나요?
괄호 안 검사 조건content, offset, depth어느 검사 영역의 어떤 바이트를 비교하나요?
괄호 안 기록 정보msg, sid, rev일치 결과를 나중에 어떤 규칙 개정으로 찾나요?

머리말에 있는 any는 출발 포트를 제한하지 않는 자리입니다. 같은 단어가 주소 자리에 있으면 주소 범위를 제한하지 않습니다. ->는 왼쪽에서 오른쪽인 한 방향입니다. <>는 양쪽을 비교하는 방향 연산자이므로, 한 방향만 관찰하려는 규칙에서 기호만 바꾸면 선정되는 표본의 범위가 달라집니다. 검색 결과를 늘리기 위해 바꾸기보다 조사 질문에 맞춰 선택하세요.

$HOME_NET과 같은 이름은 설정에서 정의하는 주소 집합을 참조합니다. 미리 지정한 내부 주소라는 뜻을 의도하더라도, 변수의 실제 정의와 센서가 본 NAT 전후 주소를 확인해야 합니다. 이번 예제에서 주소를 직접 쓴 이유는 방향과 포트에 초점을 두기 위해서입니다. 규칙은 여러 줄로 들여쓰기해 읽을 수도 있습니다. 문법과 저장 형식, 팀의 검토 규칙은 설치한 버전과 배포 경로에 따라 확인하세요.

3. 옵션의 값과 비교 위치를 바이트 단위로 풉니다

괄호 안은 여러 옵션으로 이루어집니다. msg:처럼 이름과 인수 사이는 콜론, 옵션을 끝내는 기호는 세미콜론입니다. content의 뒤에 붙은 offset 0,depth 11은 쉼표로 연결한 수식어입니다. Snort 3 예제를 Snort 2나 다른 엔진의 규칙 파일에 넣을 때는 같은 기호와 옵션이 지원되는지 별도로 확인해야 합니다.

인용부호 안에서 NOTE와 READY는 ASCII 글자입니다. |3a 20|에서 세로줄은 16진수 바이트 표현의 시작과 끝이고, 3a는 콜론, 20은 공백입니다. 왼쪽 4바이트 + 가운데 2바이트 + 오른쪽 5바이트 = 11바이트입니다. 대소문자 변경이나 앞에 붙은 한 바이트가 결과를 바꿀 수 있으므로, 사람이 읽는 의미와 검사한 바이트를 함께 확인하세요.

offset 0은 이 검사 영역의 시작부터, depth 11은 그 시작에서 최대 11바이트 안을 보겠다는 가정입니다. 패킷 전체의 프레임 오프셋 0을 가리키는 표현이 아닙니다. 이 단순 UDP 예제에서는 데이터의 첫 위치로 읽습니다. content에 부정 기호를 쓰거나 정규식 옵션을 쓰는 경우에도, “어느 범위에서 일치하지 않는가” 또는 “어느 범위에서 패턴을 평가하는가”부터 적으세요. 암호화나 수집 누락으로 비교할 내용 자체가 없을 때는 해당 활동이 없었다고 판정할 수 없습니다.

4. 포트 조건과 해석된 서비스 조건을 비교합니다

포트 80을 쓴 패킷이라고 언제나 HTTP라는 뜻은 아닙니다. 반대로 정상 HTTP가 다른 포트를 사용할 수도 있습니다. Snort 3의 서비스 머리말은 해석기가 알려 준 서비스로 평가 범위를 정합니다. 아래는 상태 확인용 HTTP 경로의 단순한 접두부를 읽는 의도입니다.

alert http (
    msg:"LAB HTTP health path";
    flow:to_server,established;
    http_uri:path;
    content:"/health/ready",offset 0,depth 13;
    sid:1000046;
    rev:1;
)

alert http는 이 규칙이 HTTP로 식별된 서비스에 적용된다는 뜻입니다. 이 머리말에는 특정 주소와 포트가 없으므로 자산 범위가 필요한 규칙에서 주소 제약을 자동으로 만족한다고 보지 않습니다. flow:to_server,established는 이 예제에서 서버로 향하는 확립된 흐름을 검사하도록 범위를 정합니다. http_uri:path는 이후 비교를 HTTP URI의 경로 부분에 적용합니다. 이런 검사 영역은 선택된 뒤의 콘텐츠 비교에 이어서 적용되기 때문에 고정된 검사 버퍼라고도 부릅니다.

/health/ready는 13바이트입니다. 질의 문자열이 뒤에 있어도 경로가 같으면 검사 영역은 동일할 수 있습니다. 또 /health/ready-extra처럼 경로 자체에 뒤가 붙으면 앞 13바이트는 일치합니다. 정확한 경로만 필요한 업무라면 전체 일치라는 요구를 별도로 표현하고 경계 반례를 추가해야 합니다. TLS를 권한 있게 해석할 수 없거나 서비스 검사기가 경로를 제공하지 않으면 이 버퍼를 볼 수 없습니다.

여러 세그먼트에 문자열이 나뉜 경우도 생각해 볼까요? 한 패킷씩만 검사하는 조건과, 해석기가 재조립해서 제공하는 서비스 버퍼 조건은 동작 범위가 다릅니다. 서비스·방향·재조립 설정, 양방향 가시성, 원래 세그먼트와 버퍼의 차이를 확인하면 결과 설명이 쉬워집니다.

5. 부정 표본에서 어떤 이유로 빠졌는지 검산합니다

첫 번째 UDP 규칙의 기대 결과 · 엔진 출력 아님
표본방향·목적 포트UDP 데이터기대와 이유
A정방향 · 5514NOTE: READY일치 · 모든 조건
B정방향 · 5514XNOTE: READY불일치 · 시작 위치가 1
C정방향 · 5515NOTE: READY불일치 · 목적 포트 다름
D역방향 · 5514NOTE: READY불일치 · 주소 방향 다름
E정방향 · 5514NOTE: READY!일치 · 앞 11바이트는 그대로

여기서 정방향은 192.0.2.60 → 198.51.100.70입니다. 역방향 비교를 위해서는 두 주소만 바꾸고 같은 목적 포트를 유지한 별도 표본을 상정했습니다. 이렇게 한 가지 조건만 바꾸면 어느 조건이 결과를 달리했는지 설명할 수 있습니다. 위 표본은 독립 바이트 비교로 A와 E만 통과한다고 검산했습니다. 실제 Snort 경보를 실행해 얻은 숫자로 읽지 마세요.

6. 경보 정보는 추적에 쓰고, 판정은 증거로 합니다

msg는 읽기 쉬운 경보 설명입니다. sid는 규칙 식별자이고 rev는 같은 규칙의 개정 번호입니다. 자체 규칙의 식별자는 운영 규칙 묶음의 값과 충돌하지 않도록 조직의 번호 체계에서 배정합니다. 조건을 바꿨다면 버전과 날짜를 기록하고, 개정 전후의 시험 결과를 나란히 남겨 두세요.

classtype은 로드된 분류 정의를 가리킵니다. 규칙에서 분류나 우선순위를 정할 수 있지만, 그 값은 조사 순서를 돕는 메타데이터입니다. 어떤 프로세스가 통신했고 수신 측이 어떤 작업을 했는지는 패킷과 단말·서버·방화벽 기록을 봐야 합니다. alert는 이번 파일의 의도이며, 인라인에서만 의미 있는 처리 동작을 운영 센서의 실제 결과로 옮겨 쓰지 않습니다.

현장에서 규칙을 검토할 때는 먼저 5강의 설정·입력·출력 점검을 하고, 시험 환경의 긍정·부정 표본을 각각 확인하세요. 규칙이 동작하지 않았다면 누락한 범위와 변경한 설정을 기록합니다. 예측과 일치했다면 로드한 SID·개정, 검사 영역, 양방향 수집 범위와 비교한 원래 패킷을 남깁니다.

복습 · 어느 조건이 결과를 바꿨나요?

1. 목적 포트가 맞고 데이터도 같았는데 주소 방향이 반대입니다. 첫 규칙에 일치할까요?

한 방향 화살표의 조건을 충족하지 않습니다. 왕복을 다루려면 요구사항에 맞게 방향을 명시하고 별도 반례로 확인합니다.

2. 전체 데이터가 12바이트인 E가 11바이트 조건에 들어가는 이유는?

길이 전체가 11이라는 조건을 쓴 것이 아닙니다. 시작 11바이트에 패턴이 모두 들어가는지 확인합니다.

3. |3a 20|은 문자 몇 글자를 검사할까요?

텍스트 네 글자와 공백을 찾는 표현이 아니라, 16진수로 표시한 두 바이트를 검사합니다. 콜론 하나와 공백 하나입니다.

4. 서비스 규칙이 TCP 8080의 HTTP에도 적용될 수 있나요?

엔진이 해당 흐름을 HTTP로 식별하고 검사 영역을 제공하면 적용될 수 있습니다. 포트만 보고 해석 결과를 단정하지 않습니다.

5. rev가 다른 경보 두 개를 비교할 때 무엇이 필요할까요?

같은 SID라도 조건 변경이 있을 수 있습니다. 개정별 규칙 내용과 센서 설정, 입력을 함께 대조합니다.

6. 표에서 일치 예상인 두 표본을 센서가 모두 놓쳤습니다. 첫 조사는?

구성에서 규칙이 로드됐는지 확인하고, 캡처에서 필요한 방향·포트와 바이트가 있는지 확인합니다. 실제 경보 출력 위치와 검사 버퍼도 맞춰 봅니다.
