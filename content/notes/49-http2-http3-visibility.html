학습 범위

셋째 날 10강에서는 같은 HTTP 요청이 HTTP/2와 HTTP/3에서 어떻게 들어오는지 비교합니다. 정상적인 상태 페이지의 가상 프레임을 사용해 길이·스트림·암호화가 조사에 미치는 영향을 살펴봅니다.

1. 한 연결에서 여러 요청이 오가면 어떻게 짝을 찾을까요?

상태 화면과 아이콘을 한꺼번에 가져오는 브라우저를 떠올려 보세요. 분석 화면에 응답 조각이 세 개 보인다고 첫 조각 다음에 온 것이 반드시 같은 응답은 아닙니다. HTTP의 메서드와 상태 코드는 앞 강의와 같은 의미를 가지지만, 메시지를 담는 형식에는 차이가 있어요.

한 작업대에서 접수번호를 붙인 두 주문을 번갈아 처리한다고 생각해 보죠. 네트워크에서는 접수번호 역할을 스트림 ID가 맡습니다. 다만 이 번호는 연결별로 쓰이고, ID 자체로 사용자의 신원이나 데이터 순서를 알아낼 수는 없습니다. HTTP/2에서는 같은 TCP 바이트 흐름을 공유하므로 앞선 데이터가 빠지면 여러 요청의 데이터가 읽히기까지 기다릴 수 있습니다. HTTP/3에서는 QUIC이 독립적인 스트림을 제공하므로 한 스트림의 누락이 다른 스트림의 순서 전달을 반드시 막지는 않습니다. 같은 연결의 혼잡 제어와 헤더 상태 같은 공통 의존성은 여전히 있습니다.

2. HTTP/2의 프레임과 스트림을 나눠 읽습니다

프레임은 HTTP/2가 TCP 위에서 보내는 단위이고, 스트림은 한 연결에서 프레임들을 교환하는 논리 채널입니다. 예를 들어 클라이언트가 스트림 1에서 상태 페이지, 스트림 3에서 아이콘을 요청할 수 있습니다. 서버가 1번의 헤더, 3번의 헤더와 데이터, 1번의 데이터를 차례로 돌려줘도 각 프레임의 ID를 보고 짝을 맞출 수 있어요. 주소·포트만 보면 이 두 요청이 같은 연결로 보입니다.

HTTP/2 프레임은 9바이트 고정 머리말을 사용합니다. 처음 24비트(3바이트)는 뒤따르는 프레임 내용의 길이, 다음 8비트(1바이트)는 유형, 다음 8비트는 플래그입니다. 마지막 32비트(4바이트)는 예약 비트 1개와 스트림 식별자 31비트로 나뉩니다. 스트림 0은 연결 수준의 프레임에 쓰입니다. 예를 들어 SETTINGS는 연결 설정이고, HEADERS와 DATA는 해당 스트림의 헤더와 데이터를 담습니다. 긴 헤더 블록은 CONTINUATION으로 이어질 수 있습니다. 프레임 하나가 TCP 세그먼트 하나 안에 다 있어야 하는 것은 아닙니다.

스트림 1의 가상 응답 끝에 READY가 들어왔다고 하죠. 문자가 각각 1바이트여서 내용은 5바이트입니다. 아래 머리말에서 00 00 05가 길이 5, 그다음 00이 DATA, 01이 DATA에서 이 방향의 끝을 뜻하는 END_STREAM입니다. 마지막 네 바이트의 최상위 예약 비트를 제외하면 스트림 번호는 1입니다. 전체 프레임은 9 + 5 = 14바이트이며 길이 필드 값에는 고정 머리말이 포함되지 않습니다.

가상 HTTP/2 DATA 프레임 · 16진수
머리말  00 00 05  00  01  00 00 00 01
내용    52 45 41 44 59  (ASCII READY)

3. HTTP/2의 시작과 헤더가 보이는 조건을 확인합니다

TLS 연결에서는 응용 계층 프로토콜을 협상하는 ALPN을 사용해 h2를 선택합니다. TLS를 쓰지 않고 서버 지원을 사전에 알고 접속한다면, 연결의 시작을 알리는 프리페이스와 SETTINGS 프레임으로 시작할 수 있습니다. 오래된 캡처에서 평문 HTTP/1.1의 Upgrade: h2c와 101이 보일 수 있지만 RFC 9113에서는 이 시작 방식을 폐기했습니다. 101만으로 현재 브라우저의 HTTP/2 사용을 추정하지 않습니다. 서버 푸시를 지원하는 경우 서버가 요청될 리소스를 미리 제시할 수 있으나, 허용 여부는 설정과 구현에 달려 있습니다.

HTTP/2의 :method, :path, :authority, :status처럼 콜론으로 시작하는 이름은 메시지의 역할 정보를 전달하는 의사 헤더입니다. 앞 강의에서 읽은 GET /health/ready 한 줄이 그대로 나타날 필요는 없어요. 헤더 블록은 HPACK으로 인코딩되므로 텍스트 검색 결과와 디코딩된 필드가 다를 수 있습니다. 또한 중간부터 캡처하면 헤더 참조에 필요한 상태를 놓칠 수 있어, 복호화할 수 있는 파일이라도 모든 헤더가 복원된다고 단정할 수 없습니다.

Wireshark의 http2.streamid == 1는 HTTP/2 해석 결과에 스트림 ID 1이 포함된 패킷을 고릅니다. ==는 같다는 뜻입니다. 패킷 하나에 다른 스트림의 프레임도 함께 있을 수 있고, 스트림 번호 1은 여러 연결에서 재사용됩니다. 특정 연결의 tcp.stream과 함께 좁히고 패킷 상세에서 각 프레임을 펼쳐 확인하세요. 경로나 상태 코드는 해석 가능한 경우에만 비교할 수 있습니다.

4. HTTP/3에서는 UDP, QUIC 패킷, 스트림을 구별합니다

HTTP/3는 QUIC 위에 HTTP 의미를 실어 보냅니다. QUIC은 UDP를 쓰면서도 자체 순서 전달, 손실 복구, 혼잡 제어와 TLS 1.3 기반 보호를 제공합니다. 응용 헤더 압축에 HTTP/3가 쓰는 방식은 QPACK입니다. UDP라는 이름만으로 연결 상태가 없다거나 대화 내용을 평문으로 읽을 수 있다고 결론 내리면 안 됩니다.

UDP 데이터그램 안에는 QUIC 패킷이 들어가며 조건에 따라 패킷이 함께 실릴 수 있습니다. 프레임 유형은 UDP 바로 뒤가 아니라 QUIC 패킷의 프레임 영역에서 읽습니다. QUIC 표준의 프레임 유형과 스트림 ID는 가변 길이 정수입니다. 정수가 항상 1바이트나 8바이트로 고정되는 것은 아니며 앞쪽 비트가 인코딩 길이를 표시합니다. ACK 프레임은 패킷 수신 확인을, CRYPTO는 핸드셰이크 데이터를, STREAM은 스트림에 실린 데이터를 전달합니다.

가상으로 복호화되고 해석된 QUIC의 한 방향에서 스트림 ID 4의 처음 4바이트가 STAT, 오프셋 4부터 2바이트가 US였다고 해 보죠. 오프셋은 데이터의 바이트 위치이므로 0~3과 4~5가 이어져 6바이트의 STATUS가 됩니다. 두 번째 조각이 오프셋 5라면 4번 자리가 비어 있어 바로 붙일 수 없습니다. STREAM 유형 계열인 0x08~0x0f의 비트는 오프셋 필드, 길이 필드의 포함 여부와 방향의 종료 표시를 알려 줍니다. 오프셋이 생략되면 0이라는 뜻입니다. 스트림 ID의 하위 두 비트는 누가 열었는지와 양방향 여부를 구분합니다. ID 4는 하위 두 비트가 0이어서 클라이언트가 만든 양방향 스트림입니다. 이것만으로 지금 프레임이 어느 쪽에서 왔는지 판단하지는 않습니다.

예전 자료에 “QUIC를 지원하는 도구가 거의 없다”고 적혀 있어도 현재 지원 범위를 제품과 버전별로 다시 확인하세요. Wireshark는 IETF QUIC의 필드 목록을 제공하고, Suricata 8.0.1 공식 문서에는 quic.version과 같은 QUIC 규칙 필드가 있습니다. 이 사실이 HTTP/3 요청 본문까지 읽을 수 있다는 뜻은 아닙니다. QUIC Initial의 보호와 연결 성립 이후 응용 데이터의 보호도 서로 다릅니다. 초기 트래픽에서 확인되는 항목만으로 뒤이어 전송된 경로와 본문을 짐작하지 않습니다.

예를 들어 센서에서 UDP 443의 QUIC 후보 흐름을 봤다면 포트와 대상, 시간, 양방향 여부, 해석기가 실제로 인식한 버전을 적으세요. HTTP/3 사용 여부와 업무 결과를 확인하려면 서버나 프록시의 프로토콜·요청 식별자 로그를 비교합니다. 중간 데이터가 없거나 암호화 때문에 파서가 필드를 내놓지 못해도, 요청이 없었다고 결론 내리지 않습니다.

복습과 해설

1. HTTP/2 DATA 내용이 5바이트면 전체는 몇 바이트인가요?
고정 머리말 9바이트를 더해 14바이트입니다. TCP와 IP 머리말은 이 계산과 별개입니다.
2. 서로 다른 연결의 스트림 1은 같은 요청인가요?
스트림 ID는 연결 안에서 해석합니다. 먼저 연결을 좁히고, 방향과 프레임 및 헤더를 함께 읽습니다.
3. GET이 원시 바이트 검색에 안 나오면 요청이 없었나요?
HTTP/2와 HTTP/3의 헤더 인코딩이나 암호화 때문에 보이지 않을 수 있습니다. 해석된 메서드 필드나 서버 기록을 확인합니다.
4. QUIC에서 오프셋이 4 대신 5이면?
앞 조각이 0~3을 채웠다는 가정에서 4가 빠집니다. 다른 프레임이나 캡처에 누락 바이트가 있는지 확인해야 합니다.
5. UDP 443을 봤는데 무슨 URL이었는지 알고 싶습니다.
포트는 조사 범위를 좁힐 단서입니다. 해석된 QUIC·HTTP/3 여부, 수집 방향, 권한을 갖춘 서버·프록시의 요청 기록을 비교합니다.

공식 자료와 확인일

2026-11-20에 RFC 9113 HTTP/2, RFC 7541 HPACK, RFC 9114 HTTP/3, RFC 9000 QUIC, RFC 9001 QUIC의 TLS, RFC 9204 QPACK을 확인했습니다. 도구 범위는 Wireshark HTTP/2·QUIC 필드와 Suricata 8.0.1 QUIC 규칙을 참고했습니다. 예제는 독립 바이트 검산이며 엔진으로 캡처를 재생하지 않았습니다.
