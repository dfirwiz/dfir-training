1. 조각을 읽는 것에서 같은 데이터로 재조립하는 것까지

앞선 회차에서는 조각의 데이터 길이와 원래 위치를 계산했습니다. 이제 한 단계 더 나아가 보겠습니다. 같은 위치를 가리키는 조각이 두 개이고 내용이 서로 다르다면, 어느 내용을 원래 데이터로 보아야 할까요? 보안 센서와 목적지 호스트가 서로 다른 답을 선택한다면 탐지 결과는 어떻게 달라질까요?

이번에는 중첩 조각 → 재조립 정책의 차이 → 큰 ICMP 메시지의 세 조각 → tcpdump와 Wireshark의 표시 → 길이와 체크섬 검증 순서로 공부합니다. 숫자를 계산하는 능력을 실제 조사에서 무엇을 확인했고 무엇이 남았는지 설명하는 능력으로 연결하는 것이 목표입니다.

자료와 회차 경계

아래 주소·조각·바이트 배열·도식은 학습을 위해 독립적으로 구성한 가상 예시입니다. 첫째 날 PCAP 여섯 개를 추가로 확보해 오프라인으로 해석하고 주요 필드·기록 수·시간을 독립 도구로 교차 검증했습니다. 자체 배열의 계산 검산과 실제 네트워크 실행을 구별하며, 특정 운영체제나 IDS/IPS에서 재현했다고 주장하지 않습니다. VPN의 MTU·DF·MSS와 단편화 종합 복습은 설명을 줄이지 않도록 다음 회차로 나눕니다.

패킷 분석에서 중요한 것은 분석기가 붙인 이름만 옮기는 것이 아닙니다. 그 이름이 개별 조각을 읽은 결과인지, 여러 조각을 합친 결과인지, 실제 목적지의 처리까지 확인한 것인지 구별해야 합니다.

2. 중첩은 조각의 개수가 아니라 데이터 구간으로 찾는다

중첩(overlap)은 같은 원래 IP 데이터 위치를 둘 이상의 조각이 덮는 상황입니다. 조각의 IP 전체 길이가 같다는 것만으로는 중첩이 아닙니다. 각 조각에서 데이터 길이 = Total Length − IHL×4, 시작 = 원시 Offset×8, 끝 = 시작+데이터 길이를 구한 뒤 구간이 겹치는지 비교합니다.

다음은 출발지 192.0.2.10, 목적지 198.51.100.20, Protocol 1, IP ID 0x6100이 같은 것으로 가정한 가상 묶음입니다. 각 IP 헤더는 20바이트입니다. A~D는 설명용 이름이며, 실제 캡처 기록이 아닙니다.

가상 묶음에서 B와 C가 같은 32바이트 위치를 덮는 사례
조각IP 전체 / 데이터MF · 원시 Offset원래 IP 데이터 구간내용에 관한 설정
A52 / 32바이트1 · 0[0,32)메시지의 시작 부분
B52 / 32바이트1 · 4[32,64)LEFT 8회
C52 / 32바이트1 · 4[32,64)RGHT 8회
D44 / 24바이트0 · 8[64,88)메시지의 나머지

B와 C는 전체 길이 52에서 헤더 20을 뺀 데이터 32바이트를 가집니다. 원시 Offset 4를 바이트로 바꾸면 4×8=32, 끝은 32+32=64입니다. 두 조각의 구간이 완전히 같으므로 전체 중첩입니다. 문자열은 각각 4바이트를 8번 반복해 32바이트이며, 서로 다른 내용을 구분하기 위한 표식입니다. 표식 자체가 정상·악성을 뜻하지 않습니다.

시작 위치가 다르더라도 중첩할 수 있습니다. B의 [32,64)와 다른 조각의 [48,80)을 비교하면 공통 구간은 [48,64), 길이는 64−48=16바이트입니다. 이것은 부분 중첩입니다. 두 구간의 시작 중 큰 값과 끝 중 작은 값을 골라, 앞의 값보다 뒤의 값이 클 때 그 차이가 겹친 길이가 됩니다.

반대로 [0,32)와 [32,64)는 32라는 경계에서 이어질 뿐 겹치지 않습니다. 대괄호는 시작을 포함하고 오른쪽 소괄호는 끝을 제외한다는 뜻입니다. 그래서 첫 구간은 0~31번 바이트를, 다음 구간은 32~63번 바이트를 나타냅니다.

3. 같은 내용의 중복과 서로 다른 내용의 충돌

두 조각의 위치와 길이가 같더라도 데이터를 비교하는 단계가 남습니다. 같은 위치에 같은 바이트가 다시 보인 경우와, 같은 위치에 다른 바이트가 들어온 경우는 분석의 의미가 다릅니다. 후자는 어느 내용을 채택하느냐에 따라 재조립 결과가 달라질 수 있습니다.

앞 예제에서 C도 LEFT를 8번 담았다면 데이터 관점에서는 동일한 중복 후보입니다. 실제 자료에서는 미러링 경로 중복이나 수집 파일 병합, 네트워크에서의 중복 등 다른 원인을 확인합니다. IP가 손실 복구를 위해 알아서 같은 조각을 재전송했다고 가정하지 않습니다.

반면 B가 LEFT, C가 RGHT라면 [32,64)의 바이트가 충돌합니다. 이때는 같은 주소·Protocol·ID 및 시간·관측 위치를 올바르게 연결했는지도 확인해야 합니다. 긴 시간에 걸친 IP ID 재사용이나 다른 관측 영역의 패킷을 잘못 묶으면, 서로 다른 데이터그램을 충돌 조각으로 오인할 수 있습니다.

따라서 조사 기록은 ‘조각 두 개가 있다’에서 끝나지 않습니다. ‘같은 묶음으로 판단한 근거는 무엇인가, 구간은 얼마나 겹치는가, 그 구간의 바이트는 동일한가, 어떤 수집 지점에서 어떤 순서로 보였는가’를 남깁니다. Wireshark의 ip.fragment.overlap과 ip.fragment.overlap.conflict도 겹침과 내용 충돌을 구분하는 분석 필드입니다. 경고 하나를 곧바로 공격 성공 판정으로 사용하지 않습니다. [7]

4. 재조립 결과가 달라지면 왜 탐지 회피 문제가 생길까

IDS는 의심스러운 통신을 탐지하는 시스템이고, IPS는 통신 경로에서 정책에 따라 차단할 수 있는 시스템입니다. 조각으로 나뉜 상위 메시지를 정확히 검사하려면 관련 데이터를 연결하거나 정규화하는 처리가 필요합니다. 여기서 정규화는 뒤에서 해석이 갈릴 수 있는 모호한 입력을 일관된 형태로 처리하는 접근을 뜻합니다.

가상 상황을 하나 두겠습니다. 센서가 충돌한 [32,64)에서 B의 바이트를 채택했지만 목적지는 C의 바이트를 채택했습니다. 그러면 센서가 검사한 메시지와 목적지가 처리한 메시지가 달라질 수 있습니다. 센서가 놓친 탐지 조건이 목적지에서 선택한 내용에 있었다면 탐지 회피 가능성을 검토할 이유가 됩니다. 같은 문서를 두 사람이 서로 다른 수정본으로 조립해 읽는 상황과 비슷합니다.

다만 이것은 정책 차이의 위험을 설명하는 조건부 예시입니다. 특정 운영체제가 항상 먼저 온 내용이나 나중 내용을 고른다는 실제 측정 결과가 아닙니다. 구현에 따라 겹친 모양·길이·순서·프로토콜과 설정이 결과에 영향을 줄 수 있고, 묶음 전체를 버릴 수도 있습니다. ‘선착순/후착순’이라는 두 가지 규칙만으로 모든 구현을 설명하지 않습니다.

회피 성공을 주장하려면 센서와 대상이 각각 어떤 데이터를 확보하고 어떻게 처리했는지, 대상이 상위 체크섬과 형식을 받아들였는지, 탐지 조건이 실제로 어디에서 달라졌는지까지 확인해야 합니다. 페이로드에 특정 단어를 두 개 넣은 예제만으로는 이런 결과가 증명되지 않습니다. 다른 바이트를 선택했어도 체크섬 검증이나 응용 처리에서 거부될 수 있습니다.

중첩 관측은 조사할 사건입니다. 실제 회피·취약점 악용·응용 명령 실행은 추가 증거로 확인할 결론입니다. 도구 이름, 드문 조각 모양, 응답 부재만으로 공격자의 숙련도나 공격 성공을 단정하지 않습니다.

5. 현재 기준으로 구분하기: IPv4, IPv6, 운영체제의 실제 동작

‘조각은 겹치면 안 된다’는 문장은 분석기가 모호한 데이터를 경계해야 한다는 출발점으로 유용합니다. 하지만 이를 ‘중첩은 어떤 경우에도 존재할 수 없으며 모든 수신기가 똑같이 처리한다’는 뜻으로 확대하면 안 됩니다.

공식 표준 대조 — 2026년 11월 1일 확인

IPv4의 RFC1122 §3.3.2에는 재조립 과정에서 조각이 겹칠 수 있다는 논의가 있습니다. 이 역사적 논의를 근거로 현재의 모든 IPv4 호스트가 충돌 내용을 같은 방식으로 받아들여야 한다거나, 버리는 구현은 무조건 잘못되었다고 단정하지 않습니다. 표준의 논의, 보안 정책, 구현과 실제 버전의 동작을 따로 확인합니다. [2]

IPv6의 RFC8200 §4.5는 재조립 중 중첩을 발견하면 해당 패킷의 재조립을 포기하고 받은 조각들을 버리는 처리를 규정합니다. 이때 ICMP 오류를 보내지 않는다는 조건도 있습니다. 동시에 정확히 같은 조각의 중복을 식별해서 중복본만 버리고 다른 조각은 유지하는 선택도 설명합니다. 따라서 ‘IPv6에서 중복된 조각 하나가 보이면 언제나 전체 폐기’라는 표현도 지나칩니다. IPv4와 IPv6의 헤더 구조를 같은 것으로 계산하지 않는 것은 물론입니다. [3]

과거의 Windows 설명이나 아직 출시되지 않은 후속 버전에 대한 추정을 현재의 모든 Windows 동작으로 옮기지 않습니다. 이번 작업에서는 특정 Windows 빌드의 중첩 처리 실험을 수행하지 않았습니다. 현재 조사 대상의 결과가 필요하면 버전·패치·방화벽·가상화·수집 위치를 기록하고, 대상의 수신·폐기 증거와 센서 설정을 대조해야 합니다. 과거 서술만으로 현재 구현을 확정하지 않는 것이 보완점입니다.

이 구분은 단편화 필드가 2021년 이후 모두 바뀌었다는 뜻이 아닙니다. 위치와 길이 계산은 그대로 유효합니다. 오래된 예제를 사용할 때 현재에도 성립하는 규칙과 특정 구현·조건에 의존하는 설명을 구별하는 것입니다.

6. 중첩을 볼 때 필요한 tcpdump 옵션과 해석 순서

PCAP이 준비되어 있다면 먼저 상세 헤더에서 위치·길이를 읽고, 그다음 겹친 데이터의 실제 바이트를 비교합니다. 다음은 사용법을 위한 명령 예시입니다. 설명용 파일명을 사용하며 이번 작업에서 실행한 결과가 아닙니다.

tcpdump -r sample-overlap.pcap -ntv
tcpdump -r sample-overlap.pcap -ntvA

-r은 저장된 파일 읽기, -n은 주소 등의 이름 변환 억제, -t는 시각 숨김, -v는 상세 출력입니다. -ntvA는 여기에 대문자 -A를 더해 링크 헤더를 제외한 내용을 ASCII로 보여 줍니다. -A는 16진수가 아니며, 실제 바이트와 위치를 정밀하게 확인할 때는 -x나 -X를 함께 이해해야 합니다. -X는 16진수와 ASCII를 표시합니다. [4]

ASCII 출력에는 IP 헤더의 바이트도 포함되며 읽을 수 없는 값은 점 등으로 보일 수 있습니다. 출력에서 사람이 읽는 단어만 따로 정리한 교육용 표시는 원시 덤프와 다릅니다. 앞의 표에서 LEFT·RGHT만 골라 쓴 것도 데이터 관계를 설명하기 위한 정리이지 실제 tcpdump 화면을 재현한 것이 아닙니다. 문자열만 보고 ‘이 조각은 무해하다’고 판단하지 않습니다.

순서는 다음과 같습니다. 먼저 IHL과 Total Length로 실제 조각 데이터 길이를 구합니다. 다음에 바이트 Offset으로 구간을 놓고 같은 위치의 바이트를 비교합니다. 마지막으로 시각·센서와 대상의 처리 증거를 대조합니다. 실제 도착 순서가 중요하다면 -t 대신 날짜·시각을 표시하는 -tttt를 사용할 수 있습니다. 표시 시간대도 확인합니다.

tcpdump IPv4 상세 줄의 offset은 이미 바이트 위치로 환산된 값입니다. 앞 가상 예제에서 원시 값 4에 8을 곱하면 32이며, 상세 출력의 offset 32를 다시 8배 하지 않습니다. 공식 IPv4 해석 소스의 처리와 대조했습니다. [5]

7. 현재의 센서에서는 정책과 자원 제한도 조사한다

보안 장비가 단편을 처리한다고 해서 모든 대상과 항상 같은 결과를 보장하는 것은 아닙니다. 대상 정보가 오래되었거나, 센서가 일부 경로만 보거나, 조각을 유지할 자원이 부족하면 분석 범위가 달라질 수 있습니다. IDS/IPS의 존재와 해당 묶음의 검사 완료를 구별해야 하는 이유입니다.

예를 들어 Suricata 공식 구성 문서는 host-os-policy로 대상별 재조립 처리 문맥을 설명하고, defrag에서 IP 조각 재조립의 자원과 제한을 다룹니다. timeout은 조각을 기다리는 시간, memcap은 사용할 메모리 한도, trackers와 max-frags는 추적하는 묶음·조각 수 관련 제한입니다. 실제 값과 적용 범위는 설치 버전과 구성에서 확인합니다. [6]

IPS에서 메모리 한도에 닿았을 때의 처리 정책도 확인 대상입니다. 정책에 따라 검사·전달·폐기의 결과가 달라질 수 있으므로 ‘경고가 없었다’는 것만으로 모든 조각을 검사했다고 보고하지 않습니다. 이 노트는 운영 설정을 바꾸라는 처방이 아니라, 사건을 설명할 때 확인해야 할 조건을 짚는 것입니다.

공식 8.0.2 문서와 현재 개발 문서를 대조했으며, 개발 문서를 배포 중인 안정 버전으로 소개하지 않습니다. 특정 문서의 기본값을 모든 센서·호스트의 공통 타이머나 한도로 옮기지도 않습니다. 조사 메모에는 실제 센서의 버전·정책·자원 통계·수집 손실과 대상 자산 정보를 남깁니다.

8. 큰 Echo 메시지 하나를 세 조각으로 나눠 본다

중첩의 위험을 이해했으니 이번에는 겹침 없는 분할을 처음부터 끝까지 계산하겠습니다. 다음은 각 조각을 MTU 한도까지 채워 나눈 가상 예제입니다. Echo 데이터가 큰 것은 단편을 여러 개 만들기 위한 학습 조건이며, 크기 하나만으로 악성이라고 분류하지 않습니다.

문서용 출발지 192.0.2.25에서 목적지 198.51.100.40으로 보내는 IPv4 ICMP Echo Request를 가정합니다. IP 헤더는 옵션 없는 20바이트, Echo 헤더는 8바이트, Echo 데이터는 4000바이트입니다. 출력 링크 MTU는 IP 전체 기준 1500바이트, DF는 0이며 여기서 단편화를 허용하는 것으로 둡니다. 실제 IPv4에서 DF나 경로 조건이 다르면 같은 결과가 보장되지 않습니다.

ICMP 메시지 전체 = Echo 헤더 8 + Echo 데이터 4000 = 4008바이트
원래 IP 전체    = IP 헤더 20 + ICMP 메시지 4008 = 4028바이트
조각당 최대 IP 데이터 = MTU 1500 − IP 헤더 20 = 1480바이트
1480 ÷ 8 = 185 → 끝이 아닌 조각의 정렬 조건에도 맞음

MTU가 임의의 값이라면 끝이 아닌 데이터의 8바이트 정렬 때문에 남은 공간을 전부 채울 수 없는 경우도 있습니다. 이번에는 1500−20=1480이 정확히 8의 배수이므로 최대로 채우는 계산이 간단합니다. 같은 크기의 분할이 모든 상황의 의무 규칙이라는 뜻은 아닙니다.

공통 IP ID는 자체 값 0x5a16을 사용합니다. 5×4096 + 10×256 + 1×16 + 6 = 20480+2560+16+6 = 23062이므로 16진수 0x5a16과 10진수 23062는 같은 값입니다. 관련 묶음인지는 ID만이 아니라 주소·Protocol·시간·수집 문맥까지 함께 확인합니다.

9. 첫 조각에는 Echo 헤더와 데이터 일부가 함께 들어간다

첫 조각 F1은 원래 IP 데이터 위치 0에서 시작합니다. 헤더 20바이트를 제외한 공간 1480바이트 중 앞 8바이트가 Echo 헤더입니다. 따라서 Echo 데이터가 들어갈 공간은 1480−8=1472바이트입니다. 전체는 20+8+1472=1500바이트입니다.

F1의 Protocol은 1(ICMP), IP ID는 23062, 원시 Offset은 0, MF는 1입니다. MF1은 원래 데이터의 뒤가 더 있다는 뜻이며 다음 조각이 얼마나 남았는지는 알려 주지 않습니다. 데이터 구간은 [0,1480)입니다. 이 구간의 처음 8바이트가 Echo 헤더이고 다음 1472바이트가 Echo 데이터라는 포함 관계를 유지하세요.

이 자체 예제의 Echo 헤더는 Type 8, Code 0, Identifier 0x0102, Sequence Number 1로 정의합니다. Type·Code로 Echo Request를 구별할 수 있고, Identifier·Sequence Number는 요청과 응답을 대응시키는 데 쓰입니다. IP ID 23062와 ICMP Identifier 258은 서로 다른 계층의 필드입니다. [8]

F1에 Echo 헤더가 있다고 해서 이 조각만으로 전체 메시지의 체크섬이나 실제 응답을 검증할 수 있는 것은 아닙니다. 나머지 Echo 데이터가 아직 뒤 조각에 남아 있습니다. 도구가 첫 조각에 Echo Request라고 표시하는 근거와 전체 메시지 검증의 범위를 구별합니다.

10. 둘째와 마지막 조각의 위치는 1480과 2960이다

F1이 원래 IP 데이터 1480바이트를 운반했으므로 F2는 위치 1480에서 시작합니다. 새 IP 헤더 20바이트 뒤에 Echo 데이터 1480바이트를 넣으면 전체는 다시 1500바이트입니다. F2의 데이터에는 새로운 Echo 헤더가 없으며 구간은 [1480,2960)입니다.

이때 원시 Offset은 1480÷8=185=0x00b9이고, 아직 뒤가 남았으므로 MF1입니다. Flags·Offset 두 바이트를 함께 적으면 MF 부분 0x2000과 Offset 0x00b9가 합쳐진 0x20b9입니다. IP 전체 길이 1500을 그대로 Offset으로 사용하지 않습니다. 위치 계산에서 각 조각의 자체 IP 헤더를 빼야 하기 때문입니다.

F3의 시작은 앞 두 데이터 길이의 합인 1480+1480=2960바이트입니다. 앞 두 조각이 각각 1048바이트라고 읽으면 이 합이 나오지 않습니다. 1048은 마지막에 남는 데이터 길이이며, 2960을 만드는 앞 두 데이터는 각각 1480바이트입니다.

남은 IP 데이터 = 4008 − 1480 − 1480 = 1048바이트
F3의 IP 전체  = 20 + 1048 = 1068바이트
원시 Offset    = 2960 ÷ 8 = 370 = 0x0172
끝 위치        = 2960 + 1048 = 4008바이트
MF             = 0 → 원래 데이터 위치상 마지막 조각

F3은 [2960,4008)을 운반합니다. Protocol은 여전히 ICMP지만 Echo의 Type·Code가 새로 붙지 않습니다. 뒤 조각 하나만 보고 Echo Request라고 확정할 수 없는 이유입니다. 공통 IP ID는 F1·F2와 같은 23062이고, MF0과 Offset>0의 조합이 마지막 조각을 나타냅니다.

세 구간은 경계에서 이어지고 빈틈·중첩이 없습니다. 마지막 조각이 먼저 도착하더라도 데이터 위치상 마지막이라는 의미는 같습니다. 실제 재조립 완료는 나머지 구간이 모두 채워졌는지, 같은 묶음인지, 필요한 바이트가 잘리지 않았는지를 추가로 확인해야 합니다.

11. 4000, 4008, 4028, 4068은 각각 무엇의 길이인가

이 예제에서 혼동하기 쉬운 것은 서로 비슷한 네 숫자가 가리키는 범위입니다. Echo 데이터만 세면 4000바이트입니다. Echo 헤더 8을 포함한 ICMP 메시지, 즉 원래 IP 데이터는 4008바이트입니다. 원래 IP 헤더 20을 더한 데이터그램 전체는 4028바이트입니다.

조각을 보낼 때는 각 조각에 IP 헤더가 필요합니다. 첫 헤더 하나만 합계에 넣고 끝낼 수 없습니다. 세 조각의 IP 전체 길이는 1500+1500+1068=4068바이트입니다. 원래 전체와의 차이 4068−4028=40바이트는 IP 헤더 20바이트가 두 개 더 생긴 양입니다.

Echo 데이터 확인: 1472 + 1480 + 1048 = 4000바이트
IP 데이터 확인:   1480 + 1480 + 1048 = 4008바이트
원래 IP 전체:     20 + 4008 = 4028바이트
조각 IP 합계:     3×20 + 4008 = 4068바이트

4068은 세 조각의 IP 계층 길이 합계입니다. Ethernet 프레임 헤더·FCS·패딩, 프리앰블과 프레임 간 간격까지 포함한 실제 회선 점유량이라고 부르면 안 됩니다. 수집 파일이 raw IP 형식이라면 Ethernet 헤더가 없을 수도 있습니다. 화면에서 ‘프레임’이라고 부르는 기록의 길이에 항상 14를 더하거나 빼지 말고 실제 캡처 링크 형식을 확인합니다.

이처럼 합계가 맞는지 점검하면 표의 숫자를 외우지 않아도 계산 오류를 찾을 수 있습니다. 중첩된 조각이나 같은 기록의 중복을 모두 더하면 원래 데이터 양을 과대평가할 수 있으므로, 전송량 합산과 중복을 제거한 재조립 길이도 구별합니다.

12. tcpdump는 각 조각에서 무엇을 읽는가

실제 파일을 가지고 있다면 tcpdump -nvt -r sample-three.pcap처럼 상세 정보를 읽을 수 있습니다. -nvt와 -ntv는 같은 세 짧은 옵션의 조합입니다. 다음은 이 자체 예제의 필드 관계를 압축한 가상 표기이며, 특정 버전의 tcpdump를 실행해 얻은 출력이 아닙니다.

F1: id 23062, offset 0,    flags [+],    proto ICMP (1), length 1500
F2: id 23062, offset 1480, flags [+],    proto ICMP (1), length 1500
F3: id 23062, offset 2960, flags [none], proto ICMP (1), length 1068

상세 정보에서 +는 MF가 설정되었다는 표시입니다. none은 여기서 표시할 단편화 플래그가 없다는 뜻이지, 비단편 패킷이라는 뜻이 아닙니다. F3은 MF0이지만 Offset2960이므로 마지막 조각입니다. 원시 370과 바이트 Offset2960을 구별하고, length1068에는 F3의 IP 헤더20도 들어 있음을 확인합니다.

F1에 대해서는 Echo 헤더의 Type8·Code0으로 Echo Request라는 해석을 할 수 있습니다. F2·F3은 Protocol1을 물려받지만 독립적인 Echo 헤더가 없으므로, tcpdump는 보통 프로토콜 이름·번호 중심의 짧은 설명을 합니다. 실제 문구는 버전·옵션에 따라 달라집니다. 공식 소스는 Offset0인 경우와 Offset이 0이 아닌 조각의 상위 프로토콜 해석을 구분합니다. [5]

따라서 F3 줄에 Echo Request라는 단어가 없다고 해서 다른 프로토콜로 변했거나, 패킷이 무해하거나, 암호화되었다고 결론 내리지 않습니다. 필드 자체가 말하는 ICMP와 전체 메시지를 재조립해서 확인하는 Echo 종류의 차이를 이해해야 합니다.

13. Wireshark가 재조립을 마친 프레임에 ICMP를 표시하는 이유

같은 가상 묶음을 Wireshark가 IP 재조립을 사용해 분석한다고 가정해 보겠습니다. F1·F2·F3이 순서대로 들어오면 F3을 읽는 시점에 모든 구간이 채워질 수 있습니다. 이때 F3의 기록 아래에 재조립된 데이터와 ICMP 해석이 표시될 수 있습니다.

이것은 ICMP 헤더가 실제로 F3의 회선 바이트로 옮겨 갔다는 뜻이 아닙니다. 캡처된 현재 조각과 여러 조각에서 구성한 가상 데이터가 같은 분석 화면에 함께 표시되는 것입니다. Wireshark 공식 설명은 재조립이 가능한 시점까지 상위 프로토콜 해석을 미루는 동작을 설명하며, 현재 IPv4 해석 소스도 재조립 데이터와 개별 조각의 처리 경로를 구분합니다. [9] [10]

F3 자체의 IP Total Length는 여전히 1068바이트입니다. 재조립된 IP 데이터 길이는 4008바이트이고, 그 안의 Echo 데이터는 4000바이트입니다. ‘현재 프레임이 1068인데 재조립한 데이터가 4008이니 계산 오류’라고 판단하지 않습니다. 어떤 데이터 소스와 어떤 계층의 길이를 선택했는지 먼저 봅니다.

Wireshark에는 ip.reassembled_in, ip.reassembled.length, ip.reassembled.data처럼 재조립 관계와 데이터를 나타내는 필드가 있습니다. 개별 프레임의 바이트와 재조립된 데이터 소스를 구별해 확인하세요. 오래된 화면과 현재 필드 이름·기본 설정이 완전히 같다고 가정하지 않습니다. [7]

도구 비교를 해석하는 기준 — 2026년 11월 1일 확인

tcpdump의 개별 조각 해석과 Wireshark의 재조립 후 해석은 서로 다른 관점을 제공합니다. 상위 해석이 뒤 프레임에 있다는 이유만으로 Wireshark가 잘못 읽었다고 보지 않습니다. 현재 소스의 IP 재조립 기본값은 활성화이지만, 실제 설치본·프로파일에서 바뀔 수 있습니다. 과거 Wiki의 비활성 기본값 설명을 현재 고정값으로 옮기지 않고 실행 환경의 설정을 확인합니다. [10]

필요한 마지막 위치 조각이 반드시 재조립을 완성한 마지막 도착 조각인 것도 아닙니다. F3→F2→F1 순서라면 처음 위치를 담은 F1이 늦게 들어오면서 빈틈이 채워질 수 있습니다. 어떤 프레임에 상위 해석이 나타나는지는 도구 버전·재방문 처리·재조립 설정도 확인해야 하며, 이 예제의 특정 프레임 번호를 실제 실행 결과로 보장하지 않습니다.

파일이 있다면 wireshark sample-three.pcap으로 열 수 있습니다. POSIX 계열 셸에서 명령 뒤의 &는 프로그램을 백그라운드로 실행하라는 셸 문법이지 Wireshark 옵션이 아닙니다. 이 노트에서는 GUI 실행을 수행하지 않았으며, 다른 셸에서는 같은 문법이라고 가정하지 않습니다. [11]

14. 상위 헤더로 고르면 왜 조각을 놓칠 수 있을까

이 ICMP 예제에서는 첫 조각만 완전한 Echo 헤더를 가지고 있습니다. TCP의 통상적인 분할에서도 첫 조각에 TCP 헤더가 있고 뒤 조각에는 TCP 데이터만 있을 수 있습니다. 그러므로 포트나 Type 같은 상위 필드로 모든 관련 조각을 모을 수 있다고 가정하면 안 됩니다.

libpcap의 IPv4 tcp dst port 80 같은 포트 조건은 비단편 패킷이나 첫 조각에서 해당 포트를 읽습니다. 원시 패킷을 고르는 이 조건만으로 뒤 조각을 모두 선택하지 못합니다. 포트80도 HTTP의 확정 표시는 아닙니다. 실제 관련 조각은 IP 주소·Protocol·ID와 시간 문맥으로 넓혀 찾아야 합니다. [12]

앞의 가상 ICMP 묶음에 대한 파일 읽기 예시는 다음과 같습니다. IP Protocol1을 사용해 ICMP의 뒤 조각도 조사 후보에 넣고, 실제 표시되는 ID와 위치를 대조합니다. 이 명령은 설명용이며 파일을 실행한 결과가 아닙니다.

tcpdump -n -tttt -v -r sample-three.pcap 'ip proto 1 and src host 192.0.2.25 and dst host 198.51.100.40'

and는 조건을 모두 만족해야 한다는 뜻입니다. 이 명령은 지정 방향의 ICMP 후보를 고르며 같은 주소 사이의 다른 메시지도 포함할 수 있습니다. 여전히 ID·시간·길이를 확인해야 하고, 응답 방향까지 보려면 주소 조건도 그 목적에 맞게 조정합니다. 터널 안쪽·바깥쪽, 링크 형식과 수집 필터의 적용 위치도 확인합니다.

Wireshark의 표시 필터는 이미 파일에 있는 패킷과 분석 결과를 대상으로 합니다. 재조립이 켜져 있으면 상위 필드가 재조립을 완성한 프레임에 연결될 수 있으므로, ‘모든 도구에서 포트 필터는 첫 조각만 보인다’고 똑같이 일반화하지 않습니다. 원시 패킷 선택과 재조립 후 표시 조건은 다릅니다.

# Wireshark 표시 필터 예시 — 위 tcpdump 명령의 필터 문법과 다름
ip.src == 192.0.2.25 && ip.dst == 198.51.100.40 &&
ip.proto == 1 && ip.id == 0x5a16

# 모든 IPv4 단편 후보를 찾는 표시 필터
ip.flags.mf == 1 || ip.frag_offset > 0

&&는 모두 참, ||는 하나 이상 참이라는 뜻입니다. MF1만 고르면 마지막 조각을 놓치고, Offset>0만 고르면 첫 조각을 놓칩니다. 이 필터도 묶음의 완전성·공격 여부를 판정하지 않으며, 수집에서 빠진 바이트를 되살리지 않습니다. [7]

‘첫 조각에 상위 헤더’라는 설명의 전제

이번 Echo 헤더는 8바이트이고 첫 조각에 모두 들어 있습니다. 그러나 IPv4의 아주 작은 조각에서는 TCP 헤더 일부가 뒤 조각으로 넘어갈 수 있습니다. RFC1858·RFC3128이 이런 필터 문제를 다룹니다. 따라서 모든 IPv4 조각에서 상위 헤더 전체와 체크섬 필드가 무조건 첫 조각에 있다고 확대하지 않습니다. 상위 헤더가 조각마다 새로 생성되는 것은 아니라는 원칙은 그대로입니다. [13] [14]

15. IP 체크섬은 조각별로, ICMP 체크섬은 원래 메시지 전체로

체크섬은 정해진 범위의 바이트를 계산해 오류를 검출하는 값입니다. 어느 범위를 검사하는지 모르고 ‘체크섬이 맞다’고만 쓰면 증거를 과장하기 쉽습니다. IPv4 헤더 체크섬은 IP 헤더만 대상으로 하며, 그 조각의 데이터 전체를 보호하는 값이 아닙니다.

각 조각은 자신의 Total Length·MF·Offset 등으로 헤더가 달라지므로 그 헤더에 맞게 IP 체크섬을 계산해야 합니다. ‘헤더를 복제한다’는 것은 IP 헤더를 바이트 단위로 완전히 똑같이 복사해도 된다는 뜻이 아닙니다. 헤더 옵션의 복사 규칙과 길이도 실제로 확인해야 합니다. 체크섬은 16비트 값이므로 서로 다른 헤더의 값이 우연히 같을 수 있으며, 조각마다 반드시 전 세계적으로 유일한 체크섬을 가진다는 의미도 아닙니다. [1]

반면 이 예제의 ICMP 체크섬은 Echo 헤더 8과 Echo 데이터 4000을 합친 4008바이트에 대해 계산됩니다. 그 결과 필드는 F1의 ICMP 헤더 안에 있고, IP 분할만으로 3개짜리 ICMP 체크섬이 새로 생기지 않습니다. F1에 필드가 보인다는 것과 F1만으로 그 값을 검증할 수 있다는 것은 다릅니다. 전체 ICMP 메시지가 필요합니다. [8]

종류검사 대상단편화와 관련한 주의
IPv4 헤더각 조각의 IP 헤더조각별 변경된 헤더에 맞게 계산, 데이터 완전성·진위를 증명하지 않음

IPv4 UDPUDP 헤더·데이터와 의사 헤더체크섬0은 미사용을 나타낼 수 있음. IPv6 등에 같은 가정을 그대로 적용하지 않음

의사 헤더(pseudo-header)는 TCP·UDP 체크섬 계산에 출발지·목적지 주소, 프로토콜과 길이 같은 IP 정보를 포함하는 논리적인 구성입니다. 각 조각 뒤에 새로 전송되는 별도 헤더라는 뜻은 아닙니다. TCP는 현재 RFC9293, IPv4 UDP는 RFC768로 범위를 확인할 수 있습니다. [15] [16]

의사 헤더의 TCP·UDP 길이도 원래 해당 세그먼트·데이터그램의 길이를 기준으로 합니다. 각 IP 조각의 Total Length를 그 자리에 넣어 새 체크섬을 만드는 것이 아닙니다. 주소·포트 등을 다른 장비가 변경하는 문제와, 내용 그대로의 IP 분할만 수행하는 문제도 구별합니다. 첫 조각의 일부만 확보했으면 전체 상위 메시지는 ‘검증 미완료’로 남기고, 부족한 범위를 검사한 결과를 전체 체크섬 오류나 악성 증거로 취급하지 않습니다.

자체 검산을 구체적으로 남기기 위해, 앞의 Echo 데이터를 0x41 바이트 4000개로 정의했습니다. Echo의 나머지 필드는 앞에서 정한 Type8·Code0·Identifier0x0102·Sequence1입니다. 이 메모리 배열에서 계산한 ICMP 체크섬은 0x292f이고, 8바이트 헤더는 0800 292f 0102 0001입니다. 이는 원본 PCAP 출력이 아니라 직접 정의한 배열에 대한 계산 결과입니다.

# 가상 F1·F2·F3의 IPv4 헤더 20바이트씩 — 데이터는 여기서 생략
F1: 4500 05dc 5a16 2000 4001 0e96 c000 0219 c633 6428
F2: 4500 05dc 5a16 20b9 4001 0ddd c000 0219 c633 6428
F3: 4500 042c 5a16 0172 4001 2ed4 c000 0219 c633 6428

각 IP 헤더의 체크섬은 차례로 0x0e96, 0x0ddd, 0x2ed4입니다. 자체 배열을 세 구간으로 잘라 다시 연결해 원래 4008바이트와 같은지, IP 헤더와 ICMP 메시지의 1의 보수 합이 맞는지 검산했습니다. 이것은 네트워크로 보내거나 특정 호스트가 수신한 실험이 아닙니다.

체크섬은 암호학적 인증이 아니며, 값이 맞는 패킷도 악성 내용을 담을 수 있습니다. 반대로 호스트 수집에서는 오프로딩 때문에 표시되는 검사 상태가 실제 회선의 값과 다를 수 있습니다. 따라서 ‘각 IP 체크섬이 맞으니 전체 조각도 완전하고 공격이 아니다’라는 결론을 내리지 않습니다. [17]

16. 관측한 사실에서 결론까지, 무엇을 더 확인할까

실제 분석의 첫 단계는 주소·Protocol·ID·시간과 관측 영역을 연결해 관련 조각을 모으는 것입니다. 그다음 각 IHL·전체 길이·MF·Offset을 읽고 구간을 계산합니다. 빠진 구간, 같은 데이터의 중복, 서로 다른 데이터의 충돌을 나누어 기록합니다. 분석기의 재조립 결과와 대상의 수신 결과를 비교하는 것은 그 이후입니다.

패킷으로 확인 가능한 사실

확보한 헤더 필드·시각·데이터 바이트, 계산한 위치와 길이, 관측된 중복·중첩·충돌, 파일에 실제 저장된 분량과 분석기가 표시한 재조립 관계입니다. 묶음으로 연결한 근거와 사용 도구·설정도 기록합니다.

단독으로 확정할 수 없는 부분

분석기의 결과만으로 대상의 최종 바이트 선택, 경고 부재만으로 검사 완료·무해함, 응답 부재만으로 차단·실패, 특정 운영체제·생성 도구·숙련도, 응용 처리나 침해 성공, 암호화된 본문의 의미입니다.

함께 확인할 로그와 자료

송신·센서·수신 지점의 캡처와 손실 통계, SnapLen·미러링·파일 병합 조건, 센서 재조립 정책·자원 제한·폐기 기록, 대상 OS 빌드·IP 재조립 통계·방화벽 기록, 단말 프로세스·서버 응용 로그와 필요한 복호화 정보입니다.

다음은 첫 중첩 예제에 대한 가상 조사 메모입니다. 실제 탐지 회피 결과를 보고하는 문장이 아닙니다.

같은 묶음으로 가정한 B와 C는 원시 Offset4와 IP 데이터32바이트로 모두 [32,64)를 가리킨다. 해당32바이트는 LEFT 반복과 RGHT 반복으로 서로 다르게 정의되어 내용 충돌이 있다. 센서와 대상이 서로 다른 바이트를 채택하면 검사 내용이 달라질 수 있다. 현재 예제에서는 두 구현의 실제 선택, 전체 ICMP 검증, 대상 수신과 응용 처리를 확인하지 않았으므로 회피 성공은 확정하지 않는다.

이와 달리 세 조각 예제에서 F2가 빠졌다면, F1·F3이 있어도 [1480,2960)의 1480바이트가 비어 있습니다. 끝4008을 알았다는 것과 전체4008을 확보했다는 결론을 구별합니다. 조각을 못 본 이유가 실제 전송 손실인지, 경로 차이인지, 필터·저장 누락인지는 추가 증거로 판단합니다.

현대에도 패킷 분석이 중요한 이유가 여기에 있습니다. 암호화된 통신에서도 조각의 크기·위치·수집 누락과 경로 문제를 조사할 수 있습니다. 하지만 IP 재조립은 TLS 복호화나 응용 성공 판정이 아닙니다. 필요한 비밀정보가 없으면 암호화 본문을 자동으로 읽을 수 없고, 단말·서버 로그로 활동의 의미와 결과를 보완해야 합니다. [18]

17. 복습 — 계산, 도구 해석, 판단의 한계를 함께 설명하기

질문 1: IP 전체 길이가 같은 두 조각은 중첩일까요?

해설: 전체 길이만으로는 모릅니다. IHL을 빼 데이터 길이를 구하고 원시 Offset×8로 시작을 구한 뒤 구간을 비교합니다. [0,32)와 [32,64)는 이어지지만 겹치지 않습니다.

질문 2: B의 [32,64)와 E의 [48,80)은 얼마나 겹칠까요?

해설: 시작 중 큰 값48, 끝 중 작은 값64를 고릅니다. 공통 구간[48,64)의 길이는16바이트입니다. 그 구간에서 바이트가 같은지도 따로 비교합니다.

질문 3: 중첩 경고를 보았으니 탐지 회피가 성공했을까요?

해설: 중첩·내용 충돌은 관측이고 회피 성공은 추가 결론입니다. 센서와 대상의 선택, 전체 메시지 검증과 실제 처리 결과를 확인해야 합니다. 같은 바이트 중복이나 수집 병합 같은 다른 원인도 검토합니다.

질문 4: IPv6에서 정확히 같은 조각이 한 번 더 왔다면 무조건 전체 묶음을 버릴까요?

해설: RFC8200은 중첩 시 재조립 포기와 폐기를 규정하면서 정확한 중복을 식별해 중복본만 버리는 선택도 설명합니다. 충돌과 정확한 중복을 구별하고 실제 구현의 처리는 별도로 확인합니다.

질문 5: Echo 데이터4000, Echo 헤더8, IP 헤더20이면 원래 IP 전체는 얼마일까요?

해설: ICMP 메시지4008에 IP 헤더20을 더해4028바이트입니다. 옵션 없는 헤더와 이 메시지 구성을 전제로 합니다. 데이터4000과 IP 전체4028은 같은 범위가 아닙니다.

질문 6: MTU1500에서 첫 조각의 Echo 데이터는 왜1480이 아닌1472일까요?

해설: IP 데이터 공간은1500−20=1480이지만 그 안에 Echo 헤더8이 들어갑니다. 따라서 순수 Echo 데이터 일부는1480−8=1472입니다. 둘째 조각에는 Echo 헤더가 다시 붙지 않아1480을 모두 Echo 데이터에 사용할 수 있습니다.

질문 7: 셋째 조각의 시작2960은 무엇을 더한 값일까요?

해설: 앞 두 조각의 IP 데이터1480+1480입니다. IP 전체1500+1500도, 마지막 데이터1048+1048도 아닙니다. 원시 Offset은2960÷8=370, 16진수0172입니다.

질문 8: 세 조각의 IP 길이 합4068에서 무엇이 늘었을까요?

해설: 원래 IP 전체4028보다40바이트 큽니다. IP 헤더20이 두 번 더 붙었습니다. 이는 IP 계층 합계이고 링크 헤더·FCS·패딩·회선 간격까지 모두 포함한 값은 아닙니다.

질문 9: Wireshark의 F3 아래에 Echo Request가 보이면 Echo 헤더가 F3에 있을까요?

해설: 재조립된 가상 데이터의 해석일 수 있습니다. F3 자체는IP 전체1068, 재조립IP 데이터는4008입니다. 개별 바이트와 재조립 데이터 소스를 나누어 봅니다. 이 표시 위치만으로 분석기가 틀렸다고 결론 내리지 않습니다.

질문 10: 포트 조건을 걸었더니 뒤 조각이 없습니다. 실제로 전송되지 않았을까요?

해설: 먼저 필터의 단계와 문법을 확인합니다. libpcap 원시 패킷의 포트 조건은 뒤 조각을 고르지 못할 수 있고, Wireshark 재조립 후 표시 조건은 다른 프레임에 상위 필드를 연결할 수 있습니다. 주소·IP Protocol·ID·시간으로 범위를 넓히고 수집 조건을 검토합니다.

질문 11: 모든 조각의 IP 체크섬이 맞으면 ICMP 전체도 검증되었을까요?

해설: IP 체크섬은 각 IP 헤더만 검사합니다. ICMP 체크섬은 이 예제에서 전체4008바이트를 필요로 합니다. 체크섬 일치도 암호학적 인증이나 응용의 성공 증거가 아닙니다.

질문 12: 첫 조각에는 언제나 TCP 헤더와 체크섬이 완전히 있을까요?

해설: 이번의 일반적인 분할과 달리 IPv4의 작은 조각은 TCP 헤더 일부를 뒤 조각으로 나눌 수 있습니다. 헤더가 조각마다 새로 생성되지 않는다는 원칙과 모든 헤더 바이트가 첫 조각에 들어 있다는 가정을 구별합니다.

추가 연습: 세 조각 예제에서 F2를 지우고 메모를 써 보세요. 확보한 IP 데이터 합은1480+1048=2528바이트지만 원래 끝은4008이고, [1480,2960)의1480바이트가 비어 있습니다. 센서에서만 빠진 것인지 목적지에서도 빠진 것인지는 별도 확인해야 합니다. 다음 회차에서는 VPN 캡슐화가 만드는 길이 변화와 단편화 문제를 이 관점으로 분석합니다.

워크북 연계 실습

ICMP 시작 조각의 검색에서 IP 묶음 조건으로 돌아가 후속 조각을 찾습니다. 중첩과 필터의 한계 실습에서 단계별 설명과 복습을 읽을 수 있습니다. 이 페이지의 기존 자체 예시는 그대로 유지하며, 원본 PCAP을 실행한 출력으로 제시하지 않습니다.
