이번 실습 범위

셋째 날 4강에서는 가상의 정보 유출 신고를 바탕으로 Wireshark 통계, TCP 대화, HTTP, DNS와 메일 단서를 연결합니다. 아래 표는 직접 만든 관측 장부입니다. 실제 조직의 주소·메시지나 도구 출력은 포함하지 않습니다.

1. 신고를 받으면 어떤 문장부터 검증할까요?

“고객 자료가 외부에 올라간 것 같아요. 지금 당장 알 수 있나요?” 이때 필요한 답은 확신에 찬 추측보다 조사할 수 있는 질문입니다. 어느 단말에서, 어느 외부 서비스로, 어떤 데이터가 관측됐나요? 다음으로 서버가 받았는지, 파일을 저장했는지, 허가되지 않은 자료인지를 따로 확인합니다. 한 번에 다 답할 수 없더라도 어떤 근거까지 확보했는지 알려 줄 수 있습니다.

CCTV의 여러 화면을 돌려보는 것과 비슷합니다. 현관 영상에 상자를 든 사람이 보이면 엘리베이터와 출입 기록을 찾아 움직임을 맞춰 봅니다. 다만 여러 네트워크 로그는 시계와 기록 범위가 다르고, 프록시나 NAT가 주소를 바꿀 수도 있습니다. 화면에 먼저 찍혔다는 이유만으로 뒤 사건의 원인이라고 판단하지 않습니다.

시작하기 전에 캡처 원본, 센서 위치, 필터 설정, 타임존과 수집 시간대를 기록합니다. 캡처 프레임 시각, HTTP의 Date, 메일의 Date와 서버 수신 기록은 의미가 서로 다릅니다. 아래 가상 장부에서는 확인된 센서와 서버 시각을 UTC로 표시합니다. 운영 조사라면 원시 시각을 보존하고 보정 방법과 추정 오차도 함께 남기세요.

2. 프로토콜 분포로 방향을 잡고 대화 표로 좁힙니다

Wireshark의 Statistics → Protocol Hierarchy는 캡처에서 해석한 프로토콜을 계층별로 보여 줍니다. DNS·HTTP·TLS가 어느 정도 보이는지 읽어 조사 출발점을 정할 수 있습니다. 한 프레임은 Ethernet, IP, TCP, HTTP 같은 여러 계층으로 나타날 수 있으므로 줄마다 표시한 비율을 독립적으로 더하지 않습니다. 표시 필터를 적용한 상태라면 통계가 어느 집합을 집계하는지도 확인하세요.

Statistics → Conversations → TCP에서는 주소와 포트 쌍, 패킷 수, 바이트, 시작 시각, 방향별 수치를 비교합니다. 표의 A와 B를 내부·외부라고 자동으로 정하지 말고 관리 중인 주소 목록과 비교합니다. 다음 표는 가상의 요약입니다. 바이트는 센서에서 같은 기준으로 집계한 크기입니다. 실제 화면에서는 어떤 열이 프레임 바이트를 세는지, 전송 데이터인지, 재전송이 포함되는지 설치 버전과 선택 범위에서 확인합니다.

조사할 대화를 고르는 가상 예제 · 바이트
대화단말 → 서버서버 → 단말첫 판단
192.0.2.20 → 198.51.100.441,7208,540받는 쪽이 큽니다. 응답 본문과 요청을 확인합니다.
192.0.2.20 → 203.0.113.8018,4001,200보내는 쪽이 큽니다. 정상 업로드도 가능하므로 우선 내용을 봅니다.
192.0.2.21 → 198.51.100.441,6008,300같은 서버와 통신했지만, 같은 객체인지는 별도 확인합니다.

두 번째 대화의 방향 차이는 18,400 − 1,200 = 17,200바이트입니다. 이 숫자는 이 표에 잡힌 두 방향의 차이를 뜻합니다. 업로드 파일 크기나 유출 바이트를 뜻하지 않습니다. 여러 요청을 같은 TCP 연결로 보냈을 수 있고, 프레임 헤더·ACK·재전송이 섞일 수 있기 때문입니다.

3. 큰 대화 하나에서 요청과 응답으로 돌아갑니다

관심 대화의 프레임을 고르고 Follow → TCP Stream으로 방향을 나누어 봅니다. 예를 들어 POST /diagnostics HTTP/1.1가 보인다면 요청 경로와 메서드를 기록하고, 구분 빈 줄 뒤의 본문이 얼마나 확보됐는지 확인합니다. 한 줄에 보이는 주소나 포트는 이 요청을 찾기 위한 단서입니다. HTTP 200이 있다면 같은 요청의 응답으로 연결되는지 확인한 뒤 응답의 의미와 서버 기록을 비교합니다.

가상 요청에서 확인한 본문은 아래 문자열과 마지막 LF입니다. diag= 5 + sample 6 + & 1 + count= 6 + 3 1 + LF 1 = 20바이트입니다. 앞 표는 TCP 대화 전체의 요약이고, 여기서는 그중 하나의 응용 요청 본문만 셌습니다.

diag=sample&count=3

텍스트를 확인한 뒤에는 “이 요청에서 학습용 진단 문자열 20바이트를 보았다”라고 기록할 수 있습니다. 이를 외부 서비스가 영구 저장했다고 확정하려면 서버나 프록시의 요청 ID, 완료 기록, 저장 항목이 필요합니다. 제품의 정당한 진단 기능인지, 내용이 실제 고객 자료인지도 앱과 데이터 소유자의 기록에서 확인합니다.

4. 의심 시각 이전으로 돌아가 다운로드를 확인합니다

수집에서 가장 눈에 띈 업로드보다 앞서 같은 단말에서 무엇이 있었는지 살펴봅니다. 가상 사례에서는 192.0.2.20이 198.51.100.44에서 /notice.txt를 요청했습니다. 이 요청이 들어 있는 스트림을 열어 보면 파일명과 서버가 보낸 MIME 유형이 실제 바이트와 맞지 않는 사례를 만날 수 있습니다. 앞 강의의 추출물 검증 절차처럼 원래 응답과 저장한 사본의 길이·해시를 기록합니다.

예를 들어 응답이 application/pdf라고 표시되어도 확보한 본문 시작이 TRAINING NOTE라면, “제공된 구간에서 PDF의 기대 바이트가 보이지 않는다”라고 적습니다. 범위 응답이나 부분 수집이라면 파일의 앞부분 자체가 없을 수도 있습니다. 원래 자료가 PDF 구조를 담고 있고 스크립트 관련 문자열이 보이더라도, 그 문자열로 코드 실행·악성 여부·유출 원인을 확정할 수 없습니다. 분석한 파일 식별자와 제공한 응답을 먼저 맞추고 단말의 저장·프로세스·경고를 확인하세요.

두 번째 내부 단말에서도 같은 서버를 연결했다면 조사 범위를 넓힙니다. 서버 IP가 같아도 가상 호스트, 경로, 객체, 수집 범위가 다를 수 있습니다. 요청 대상과 응답 본문의 해시, 단말 로그를 비교해 동일한 자료를 읽었다고 말할 수 있는지 판단하세요.

5. 주소에서 DNS 이름으로, 이름에서 메일로 이동합니다

dns.a == 198.51.100.44로 해당 IPv4 주소를 답변에 담은 DNS 후보를 찾습니다. 여기서 dns.a는 A 레코드의 IPv4 주소 필드입니다. 보이는 이름이 하나라는 이유로 그 주소를 오직 그 이름만 쓴다고 결론내리지 않습니다. 응답의 질문 이름, 요청·응답 방향, 질의 ID, 클라이언트와 리졸버 시각을 맞추고, 다른 이름이나 캐시·프록시가 관계되는지 확인합니다.

이름 docs.example이 단서라면 메일 메시지나 HTTP 호스트처럼 해석된 필드에서 먼저 찾아보세요. 패킷 안에서 문자열을 검색할 수 있지만, DNS 이름은 전송 중에 길이가 붙은 레이블로 나뉘며 문자열의 점까지 그대로 저장되지 않을 수 있습니다. 메일의 링크도 인코딩되거나 여러 프레임에 걸칠 수 있습니다. 그 때문에 패킷 검색 결과가 비었다고 이름이 없다고 확정하지 않고 스트림이나 메일 서버의 사본을 대조합니다.

메일 본문에 같은 링크가 있었다면 수신 시각과 메시지 식별자, 실제 봉투 수신자와 메일 보안 로그를 봅니다. 전달된 사실과 클릭한 사실은 다릅니다. 메일의 보이는 To: 헤더만으로 실제로 전달된 모든 단말을 확정하지 않습니다. 클릭 로그, 브라우저 기록, 단말 이벤트와 같은 흐름이 맞아 들어가면 메일·이름 해석·HTTP 요청 사이의 연결을 더 잘 설명할 수 있습니다. 두 번째 단말의 DNS가 보이지 않은 경우에는 캐시, DNS 암호화, 센서 범위를 먼저 확인합니다.

6. 사건의 시간순서와 가설을 한 표에 담습니다

가상 장부 · 확인된 시계 기준 UTC · 증거는 독립 교육 예시
시각관측이 기록으로 확인한 범위다음 검증
09:20:00메일 서버가 두 계정으로 docs.example 링크가 들어 있는 메시지를 전달함전달과 본문 링크수신 로그·메시지 식별자·클릭 기록
09:20:12단말 .20이 해석 서버에 docs.example을 질의하고 A 응답을 받음같은 질의의 응답에 198.51.100.44단말·리졸버 시각과 브라우저 사용 증거
09:20:17단말 .20의 GET /notice.txt와 응답 본문 일부요청·응답은 관측됨본문 경계, 파일 해시, 단말 쓰기 이벤트
09:20:38단말 .21도 같은 서버에 연결TCP 종단 일부가 일치함경로·파일의 실제 일치, 그 단말의 DNS·메일 기록
09:21:08단말 .20의 POST /diagnostics에 20바이트 가상 문자열이 요청의 본문이 센서에서 관측됨앱 프로세스와 승인된 업무, 서버 요청 로그
09:21:09위 요청 뒤에 같은 교환의 HTTP 200 응답이 관측됨응답 상태가 확인됨서버 보관과 처리 결과, 실제 데이터의 분류

첫 DNS 응답이 기록된 시점부터 HTTP 요청까지는 5초이고, HTTP 요청부터 POST까지는 09:20:17 → 09:21:08, 즉 43 + 8 = 51초입니다. 이 시간 차이는 좁은 범위에서 함께 조사할 이유를 줍니다. 원인까지 주장하려면 파일 쓰기·파일을 읽은 프로세스와 POST를 만든 프로세스가 같은 사건에 연결되는지 증거를 더 봐야 합니다.

만약 수신 메일에서 링크가 확인되어도 클릭 기록이 없다면 판단 문장이 바뀝니다. “메일에 같은 URL이 있었다. 단말이 이 URL을 메일에서 열었는지는 미확인이다.” DNS 응답이 프록시에서만 보였다면 그 질의를 단말에 직접 귀속할 수 있는지도 따로 기록합니다.

7. TShark로 후보를 좁히고 원래 프레임으로 돌아갑니다

아래는 설치한 TShark에서 권한 있는 저장 파일을 조사할 때의 공식 옵션을 대조한 예입니다. practice-timeline.pcap은 분석자가 준비할 파일의 예시 이름입니다. 아랫줄의 출력 필드는 나중에 원본에서 다시 찾기 위한 최소 항목입니다.

tshark -r practice-timeline.pcap -Y 'dns.a == 198.51.100.44' -T fields -e frame.number -e frame.time_epoch -e dns.qry.name -e dns.a
tshark -r practice-timeline.pcap -Y 'ip.src == 192.0.2.20 and http.request.method == "POST"' -T fields -e frame.number -e tcp.stream -e http.host -e http.request.uri

-r은 저장 파일, -Y는 Wireshark와 같은 표시 필터입니다. 작은따옴표 안의 조건을 셸에서 한 인수로 넘깁니다. and는 출발 주소와 메서드 조건이 모두 충족되어야 한다는 뜻입니다. -T fields는 지정한 필드를 출력 형식으로 쓰고, -e는 출력할 필드를 하나씩 추가합니다. frame.time_epoch는 1970년 1월 1일 00:00:00 UTC부터의 초, tcp.stream은 분석기가 그 파일에서 붙인 대화 번호입니다. 다른 캡처 파일의 번호와 바로 대응시키지 않습니다.

첫 식은 DNS 답변의 A 레코드를 찾습니다. DNS 자체가 IPv6로 운반돼도 답변에 IPv4 주소가 들어갈 수 있습니다. 두 번째 식은 출발 IPv4 주소를 제한하므로 IPv6 단말의 HTTP를 찾을 때는 주소 필드를 다시 정하세요. 암호화됐거나 캡처에 공백이 있어 HTTP가 해석되지 않으면 메서드 필드가 나오지 않을 수 있습니다. 필드가 비어 있으면 응용 로그와 캡처 위치를 먼저 확인하고, 번호를 바탕으로 후보 프레임과 대화를 다시 엽니다. 이 페이지에서는 명령을 실행한 출력이 아니라 조사 절차를 설명합니다.

8. 조사 결과를 세 문장으로 나눠 씁니다

관측. “단말 .20의 DNS 응답, HTTP 요청과 응답, 뒤이은 진단 POST를 센서에서 확인했다. POST에서 확보한 본문은 20바이트 교육용 문자열이다.”

가설. “메일의 링크와 단말의 요청이 연관됐을 수 있다. 다만 시각과 이름의 일치가 그 링크가 클릭됐거나, 앞선 파일이 POST를 만들었다는 증거를 제공하지는 않는다.”

다음 확인. “메일 전달·클릭 기록, 단말 브라우저·파일·프로세스 이벤트, 프록시와 최종 서버의 처리 결과를 시간과 식별자로 대조한다. 개인정보나 업무 자료가 실제로 외부에 저장됐는지는 그 근거로 판단한다.”

이 흐름은 고정된 정답 순서가 아닙니다. DNS 기록부터 확인해야 풀리는 사례도 있고, 암호화 때문에 애초에 서버 기록에서 시작해야 하는 사례도 있습니다. 조사표에는 어떤 근거를 먼저 찾았는지와 가설이 바뀐 이유를 남기세요. 운영 조치는 확인된 링크·객체·단말 범위를 바탕으로 조직의 절차와 담당자에게 연결합니다.

복습 · 어떤 근거까지 연결됐나요?

1. TCP 통계에서 외부로 18,400바이트가 나갔습니다. 유출량으로 보고해도 될까요?

집계 범위부터 읽습니다. 대화 전체의 바이트와 특정 요청의 본문은 다릅니다. 실제 본문과 데이터 분류, 서버 응답을 확인한 뒤 판단합니다.

2. 메일에 링크가 있고 단말이 같은 이름을 곧 질의했습니다. 누른 사람이 확인됐나요?

시간과 이름이 일치하는 단서입니다. 자동 검사나 미리 불러오기도 가능하므로 브라우저 이벤트, 메일 클릭 기록이나 단말 프로세스를 확인합니다.

3. HTTP 응답 유형은 PDF인데 본문 일부가 텍스트입니다. 바로 악성으로 분류하나요?

먼저 본문의 실제 시작과 범위, 압축·잘림을 확인합니다. 형식 불일치는 조사할 단서이며 악성이나 실행 여부에는 별도 근거가 필요합니다.

4. 서버에서 200이 왔습니다. 데이터가 외부에 저장됐다는 결론인가요?

해당 요청에 어떤 HTTP 응답이 돌아왔는지를 보여 줍니다. 앱이 무엇을 저장했는지, 저장이 완료됐는지는 서버의 처리 결과와 데이터 기록에서 확인합니다.

5. 두 번째 단말에서 DNS가 보이지 않습니다. 다른 파일이었다고 판단할 수 있나요?

캐시나 다른 수집 위치 때문에 DNS가 빠졌을 수 있습니다. HTTP의 요청 대상과 추출한 객체의 바이트·해시를 비교하고 단말 자료를 맞춥니다.

6. 표시 필터 결과에 프레임이 없었습니다. 무엇부터 다시 검토할까요?

파일과 시간 범위, 필터 문법과 주소 계열, 필요한 방향과 세그먼트, 실제 프로토콜 해석 여부를 확인합니다. 필요한 정보가 암호화됐다면 관련 앱·서버 기록을 찾아봅니다.
