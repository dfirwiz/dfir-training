2. 계층을 바꾸어 같은 패킷 읽기

준비한 파일을 practice-concepts.pcap이라고 가정합니다. 먼저 요약을 읽고, 같은 기록을 바이트와 링크 계층으로 다시 읽습니다. 옵션은 관측 대상을 바꾸는 것이 아니라 보여 주는 정보와 이름 변환 동작을 바꿉니다.

tcpdump -nn -r practice-concepts.pcap
tcpdump -nn -t -c 2 -r practice-concepts.pcap
tcpdump -nn -t -x -c 1 -r practice-concepts.pcap
tcpdump -nn -t -e -v -c 1 -r practice-concepts.pcap

-r 다음에는 파일명, -c 다음에는 처리 개수가 옵니다. -nn은 주소와 포트 이름 변환을 막고, -t는 시각을 숨기며, -x는 링크 계층 헤더를 제외한 16진수, -e는 링크 계층 정보, -v는 더 자세한 해석을 보여 줍니다. 시각을 숨긴 출력만 보고 보고서의 시간 관계를 복원하려 하지 마세요. [1]

가상의 IPv4 헤더 첫 바이트가 0x46이라면 상위 4비트의 4는 버전, 하위 4비트의 6은 IHL입니다. IHL의 단위는 4바이트이므로 헤더 길이는 24바이트입니다. IPv4 헤더 시작에서 오프셋 8의 값이 0x3f라면 TTL은 63, 오프셋 9가 0x11이라면 다음 프로토콜은 UDP입니다. 전체 길이가 0x0044라면 68바이트이고 IP 데이터는 68−24=44바이트입니다.

확인 질문: Ethernet 헤더까지 바이트로 출력하도록 바꾸면 IPv4 TTL의 절대 위치도 그대로일까요? 해설: IPv4 시작을 기준으로 한 오프셋 8은 같지만 프레임 시작에서의 위치는 앞 헤더 길이를 더해야 합니다. VLAN 태그·링크 유형·IP 옵션을 확인하고 기준점을 먼저 고정합니다.

가상 첫 바이트 0x46을 읽는 순서부터 확인해 볼게요. 16진수 한 자리는 4비트이므로 왼쪽 4와 오른쪽 6을 나눕니다. 버전4, IHL6이며 6×4=24바이트가 IPv4 헤더입니다. 전체68에서 헤더24를 빼면 IP가 운반한 데이터44바이트가 남습니다. UDP 헤더가8바이트이고 그 부분까지 모두 확보했다면 UDP 뒤의 데이터는 다시 44−8=36바이트입니다. 질문이 IP 데이터인지 UDP 데이터인지에 따라 답이 달라집니다.

태그 없는 Ethernet II 헤더14바이트를 가정하면 프레임 시작에서 TTL은 14+8=22번 위치입니다. VLAN 태그 하나가 실제 캡처에 보이면 IPv4 시작이18로 밀려 TTL도 18+8=26이 됩니다. IHL이24로 늘어나도 TTL은 IP 고정 부분의8번이고, 바뀌는 것은 뒤 상위 헤더가 시작하는 위치입니다. VLAN 메타데이터나 오프로딩 때문에 태그가 파일에 어떻게 남았는지도 확인해야 합니다.

-c 2는 이 예시에서 처리할 기록을 제한하므로 전체 파일을 다 조사한 결과가 아닙니다. -t는 시간을 숨길 뿐 원래 기록의 시각을 바꾸지 않습니다. 출력 옵션과 조사 범위를 나누어 적고, 같은 패킷을 비교하는지 확인하세요. 이름 변환을 껐다는 것도 주소를 익명화했다는 뜻은 아닙니다.

옵션을 조금씩 바꿔 비교할 때는 셸에서 위쪽 화살표로 이전 명령을 불러와 필요한 부분만 고칠 수 있습니다. 실행 전에 -r 뒤 파일명과 -c 뒤 개수가 맞게 붙어 있는지 다시 읽으세요. 옵션을 한데 묶거나 순서를 바꾸더라도 각 옵션의 인자를 떼어 놓으면 다른 의미로 해석되거나 오류가 납니다. 명령 이력은 입력을 돕지만 분석 근거를 대신하지 않으므로 보고서에는 실제 실행한 전체 명령을 남깁니다.

3. Wireshark에서 통계와 스트림 연결하기

가상의 캡처에 IP 주소 다섯 개와 TCP 대화 여섯 개가 있다고 해 봅시다. 주소 수·대화 수·응용 프로토콜 수는 같은 단위가 아닙니다. 한 주소 쌍 사이에 여러 TCP 연결이 있을 수 있고, 한 TCP 연결의 서버 배너가 응용의 정체를 더 구체적으로 보여 줄 수도 있습니다.

  1. Protocol Hierarchy: 전체 계층에서 응용 프로토콜 후보를 기록합니다. 계층별 수치를 모두 더해 전체 패킷 수로 만들지 않습니다. 같은 패킷이 여러 계층에 포함될 수 있습니다. [2]
  2. Endpoints와 Conversations: 고유 주소 수는 Endpoints에서, 주소 쌍·포트 쌍별 대화는 Conversations에서 봅니다. 바이트 수와 Duration을 정렬하고 표시 필터의 적용 여부를 기록합니다. 캡처에서 관측한 지속 시간과 서비스의 실제 가동 시간은 다릅니다. [3]
  3. 헤더와 바이트: 같은 패킷의 Ethernet Type, TTL, Protocol, TCP 헤더 길이를 선택하고 강조되는 바이트를 확인합니다. TCP 마지막 바이트를 찾을 때 기본 20바이트라고 가정하면 옵션이 있는 패킷에서 틀립니다.
  4. Follow TCP Stream: 조사할 대화의 패킷을 선택해 양방향 데이터를 읽습니다. 가상의 배너 demo-db/3.2와 명령 INSERT INTO audit_events가 보였다면 서버가 주장한 문자열과 요청한 테이블 이름을 구별해 적습니다. 배너만으로 실제 설치 버전이나 명령 성공을 확정하지 않습니다. 스트림 창을 닫은 뒤 표시 필터가 남았는지도 확인합니다. [4]

특정 문자열을 찾을 때는 Find Packet의 검색 대상을 확인합니다. 패킷 바이트·해석된 상세 내용·목록 문구는 같은 입력이 아닙니다. 가령 바이트 검색에서 orange가 기록 210과 389에 있다면 마지막 일치는 389입니다. 검색이 끝에서 다시 처음으로 돌아갈 수 있으므로 한 바퀴의 범위와 현재 필터를 확인하세요. 두 패킷 경계에 나뉜 문자열은 패킷별 검색만으로 놓칠 수 있습니다.

심화 연습은 TCP 옵션의 코드·길이·값을 분리하는 것입니다. 가상 MSS 옵션 02 04 04 b0는 4바이트 전체가 MSS 값이라는 뜻이 아닙니다. 코드 02, 길이 04, 값 0x04b0=1200으로 나눕니다. NOP는 한 바이트 패딩이고 옵션 배치 하나만으로 운영체제를 확정하지 않습니다.

확인 질문: 스트림에 SQL 요청이 보이면 데이터가 저장되었다고 보고할까요? 해설: 요청 전송과 서버 처리 성공은 다릅니다. 응답 상태와 데이터베이스 감사 로그를 연결하고, 암호화·수집 누락으로 확인하지 못한 부분을 남깁니다.

통계에서 고른 후보를 원래 바이트로 되돌려 확인합니다

대화 여섯 개 중 바이트가 가장 많은 항목을 골랐다면 먼저 분모를 적어 보세요. 전체 파일인지 현재 표시 필터 범위인지, 두 방향을 합친 값인지 한 방향인지가 필요합니다. 동일 주소 쌍에도 포트와 시간 문맥이 다른 대화가 있을 수 있습니다. 통계는 후보 선택의 근거이고, 실제 응용 메시지의 처리 결과는 다음 확인 단계입니다.

MSS 옵션의 값도 자리별로 검산할 수 있습니다. 04b0는 4×256+11×16+0=1200입니다. 앞의02는 종류,04는 옵션 전체 길이이므로 이 네 바이트 전체를 숫자 하나로 읽지 않습니다. 그 값은 연결에서 광고한 수신 조건의 단서이지, 모든 관측 TCP 데이터가 반드시1200바이트라는 뜻도 아닙니다. 옵션·경로·실제 전송 크기를 함께 확인합니다.

스트림에서 요청을 발견하면 시각과 방향을 붙여 기록하고 응답·오류·다음 요청을 확인합니다. 재전송·누락·수집 시작점에 따라 문자열이 어디까지 복원되는지 달라질 수 있습니다. 화면에 표시된 문자열과 원래 패킷 바이트, 별도 데이터 소스를 같은 것으로 합쳐 적지 않는 습관이 도움이 됩니다.

실습 보완 · 통계에서 기록 번호와 마지막 검색 결과까지

동료가 ‘관심 통신은 기록 240 부근’이라고 알려 줬다고 해 볼게요. 파일을 열고 끝없이 스크롤하는 것보다 Go → Go to Packet에서 240을 입력해 이동할 수 있습니다. 이 번호는 현재 파일의 기록 번호이며 TCP 시퀀스 번호가 아닙니다. 다른 추출본의 240번과 같은 패킷이라고 가정하지 말고 파일·주소·시각을 먼저 맞춥니다. 그 패킷을 고른 뒤 상세 트리와 Follow TCP Stream으로 들어가세요. [19]

통계에서도 창의 숨은 부분 때문에 답을 놓칠 수 있습니다. Conversations에서 IP와 TCP 탭을 바꾼 뒤 Bytes와 Duration 열을 확인합니다. Duration이 보이지 않으면 창을 넓히거나 표 안의 가로 스크롤을 오른쪽으로 옮겨 열을 찾습니다. 없는 열과 화면 밖 열을 구분하세요. 표시 필터와 제한 옵션을 확인하고 Duration을 내림차순으로 정렬해 최댓값을 읽습니다. 주소 수는 Endpoints에서 세거나 Conversations 양쪽 주소를 중복 제거해야 하며, 대화 행 수를 주소 수로 대신하지 않습니다.

선택 패킷에서 세 패널 중 하나가 안 보이면 창 크기·구분선·View의 패널 표시 설정을 확인합니다. Ethernet II를 펼쳐 Type, IPv4를 펼쳐 TTL과 Protocol을 선택하면 해당 바이트를 교차 확인할 수 있습니다. TCP 헤더 전체를 선택할 때는 Data Offset이 가리키는 끝까지 강조되는지 봅니다. 예를 들어 시작 위치가 프레임의 34이고 헤더가 28바이트라면 마지막 위치는 34+28−1=61입니다. 옵션이 없다는 가정으로 53에서 멈추면 헤더 뒤쪽을 놓칩니다.

이제 가상 문자열 orange를 찾겠습니다. Edit → Find Packet에서 String과 Packet bytes를 고르고, 한 패킷 내부만 찾는 모드가 아닌지 확인합니다. 첫 일치를 기록한 뒤 현재 버전의 Find Next 동작으로 다음 일치를 반복합니다. 메뉴에 표시된 단축키를 따르고, 마지막에서 처음으로 순환했는지도 확인하세요. 가상 일치 번호가 210·389라면 최댓값은 389입니다. ‘마지막’이 번호 기준인지 시간 기준인지도 적습니다. Close 뒤 남은 스트림 필터는 Clear로 해제하고, 표시 수와 원본 범위를 다시 확인합니다. [20]

조건을 바꾸면: 가상 배너가 sample-db/4.1-build7인데 4.1만 적으면 빌드 식별 정보가 빠집니다. 또 요청이 INSERT INTO audit_events (...)라면 대상 이름은 INSERT INTO 뒤의 식별자에서 읽습니다. 두 경우 모두 응답·서버 로그를 확인하기 전에는 실제 설치 상태나 저장 성공까지 주장하지 않습니다.

복습: 문자열을 한 번 찾은 뒤 더 없다고 써도 될까요? 해설: 한 번의 발견은 존재만 보여 줍니다. 검색 대상·방향·필터·순환을 확인해 나머지 일치를 조사해야 마지막 위치를 설명할 수 있습니다. 위 예시는 새로 구성한 값이며 실제 프로그램 실행 화면이 아닙니다.

실습 보완 · TCP 옵션의 길이와 NOP 정렬

TCP 옵션을 읽다가 값 앞의 작은 숫자까지 MSS에 넣으면 전혀 다른 크기가 됩니다. 책의 쪽수와 본문을 나누듯 옵션도 Kind·Length·Value를 나누어 읽습니다. 아래는 송신하지 않은 독립적인 옵션 배열입니다.

02 04 04 b0 | 01 | 03 03 06
MSS 4바이트 | NOP 1바이트 | Window Scale 3바이트

첫 옵션의 02는 MSS 종류, 04는 옵션 전체 길이, 04 b0는 값 1200입니다. 마지막 옵션의 03은 Window Scale 종류, 다음 03은 전체 길이, 06은 시프트 값입니다. NOP는 No Operation으로, 종류 바이트 01 하나가 전부이며 별도 길이 바이트가 없습니다. IP 옵션의 NOP와 TCP 옵션의 NOP는 서로 다른 헤더에서 읽는 항목입니다. [15] [16]

이 배열은 4+1+3=8바이트입니다. 기본 TCP 헤더 20에 더하면 28바이트, Data Offset은 28÷4=7입니다. NOP를 빼고 다른 패딩도 없다고 가정하면 27바이트여서 4바이트 단위의 Data Offset으로 그 끝을 표현할 수 없습니다. 이 예제에서는 세 바이트 Window Scale과 한 바이트 NOP가 함께 마지막 네 바이트를 채웁니다.

얇은 책갈피를 끼워 전체 묶음의 폭을 맞추는 비유가 도움이 되지만, 모든 옵션 하나하나가 반드시 네 바이트여야 한다는 뜻은 아닙니다. RFC 9293은 옵션이 단어 경계에서 시작하지 않을 때도 수신자가 처리할 수 있어야 한다고 설명합니다. NOP의 위치·개수·옵션 순서는 구현별 단서가 될 수 있지만 운영체제를 인증하는 지문은 아닙니다. SYN에서도 모든 가능한 옵션이 반드시 들어가는 것은 아닙니다. [15]

조건을 바꾸면: NOP 두 개와 Window Scale만 두면 옵션 합은 5바이트입니다. 기본20에 더한25만으로 끝났다고 쓰면 안 됩니다. 실제 Data Offset이 가리키는 끝과 나머지 패딩·EOL을 확인해야 합니다. 복습: 길이 04를 MSS 값의 일부로 더할까요? 해설: 아닙니다. 종류·길이·값과 전체 헤더 정렬을 각각 계산합니다.

4. ARP 대응 변화와 스위치 관측 분석하기

가상의 호스트 192.0.2.20이 같은 링크의 192.0.2.1을 찾는다고 합시다. 일반 ARP 요청의 Ethernet 목적지는 ff:ff:ff:ff:ff:ff이고 ARP 내부 Target Hardware Address는 아직 모르는 값을 나타내는 0일 수 있습니다. 두 값은 다른 헤더의 필드입니다. ARP의 Ethernet Type은 0x0806이며 IPv4 헤더를 안에 넣어서 전송하는 형식이 아닙니다.

새로 구성한 ARP 관측 기록
순서내용판단
A192.0.2.20이 192.0.2.1의 MAC 요청주소 해석 시작
B192.0.2.1 → 02:00:00:00:00:01 주장기존 대응 후보
C같은 IP → 02:00:00:00:00:99 주장서로 다른 대응 발견

C는 캐시 오염을 의심할 단서이지만, 그 프레임만으로 피해자가 새 대응을 받아들였는지는 모릅니다. 주소 중복·장비 교체·고가용성 전환도 검토합니다. 대상의 이웃 캐시, 스위치의 MAC 학습 표, 승인된 장비 목록, 전환 로그와 이후 실제 전달 경로를 확인해야 합니다.

짧은 구간에서 같은 출발지 IP와 수많은 출발지 MAC이 관측되면 관측 위치부터 확인하세요. 라우터를 지난 프레임, 가상화·중계·주소 이동에서는 대응이 단순하지 않을 수 있습니다. 같은 링크의 동일 장비라는 전제와 함께 MAC 생성 속도·스위치 학습 실패·포트별 카운터가 맞아야 테이블 고갈 가설이 강해집니다. 학습 실패 뒤의 전달 범위는 VLAN·포트 정책·장비 동작에 좌우되므로 스위치가 언제나 모든 프레임을 전 포트에 뿌린다고 설명하지 않습니다.

자발적 ARP 공지도 살펴봅니다. 요청 형식의 ARP도 주소 대응을 알릴 수 있으므로 응답만 검사하면 놓칩니다. 정상 주소 충돌 검사와 공지에도 ARP가 쓰인다는 점을 함께 보아야 합니다. [5] arpwatch의 주소 변경 경고는 변화의 기록이지 공격 성공 판정은 아닙니다.

확인 질문: 출발지 IP가 같은데 MAC이 다르면 항상 위조일까요? 해설: 아닙니다. 먼저 수집 위치와 네트워크 역할을 고정하고 정상 이동·이중화 가능성을 검토합니다. 그 뒤 승인되지 않은 대응과 피해 호스트의 수용 여부를 분리해 검증합니다.

주소 주장, 호스트 수용, 실제 전달을 세 칸으로 나눕니다

관측표C에서 다른 MAC이 같은 IP를 주장한 것은 첫 칸의 사실입니다. 두 번째 칸은 대상이 그 주장을 캐시에 반영했는가이고, 세 번째는 실제 다음 프레임을 그 MAC으로 보냈는가입니다. 한 ARP 프레임으로 세 칸을 모두 채울 수는 없습니다. 캐시를 바꾸지 않아도 요청이 보일 수 있고, 바뀌었어도 당시 통신이 없으면 사용 여부는 아직 모릅니다.

물품 배송 주소록 비유를 다시 쓰면, 누군가 새 주소를 알려 준 것과 주소록을 고친 것, 실제 물품이 그 주소로 도착한 것은 다른 사건입니다. 네트워크에서는 중계·가상화·위조 때문에 주소가 곧 사람의 신분이라는 전제도 성립하지 않습니다. 승인된 변경 기록과 단말 상태를 함께 확인해야 하는 이유입니다.

실습 보완 · ARP 요청과 주소 변경 로그를 연결하기

주소 오염을 찾을 때 Reply만 살펴보면 Request 형식의 주소 공지를 놓칠 수 있습니다. 예를 들어 Opcode1인 가상 공지에서 Sender IP와 Target IP가 모두 192.0.2.70이고 Sender MAC이 이전과 다르다면, ‘이 주소는 이 MAC을 사용한다’는 새 주장을 검토합니다. 보통의 다른 호스트 주소 질의와 목적이 다르며, Request라는 이름만으로 무해함을 판단하지 않습니다. 정상 주소 충돌 검사·이중화 전환도 함께 확인합니다.

다음은 실제 arpwatch 출력이나 원본 로그를 복제한 것이 아니라, 변화의 의미를 설명하기 위해 정규화한 가상 기록입니다. 감시 도구가 남긴 관측 시각·주소·새 값·이전 값을 나누어 읽어 보세요.

10:00:02 binding-added   ip=192.0.2.70 mac=02:00:00:00:00:10
10:00:04 binding-changed ip=192.0.2.70 mac=02:00:00:00:00:20 previous=02:00:00:00:00:10

첫 줄은 그 도구가 새 대응을 관측한 기록입니다. 두 번째는2초 뒤 같은 IP의 주장이 :10에서 :20으로 달라졌다는 뜻입니다. 이 IP의 실제 소유자가 누구인지, 누가 변경을 허용했는지, 피해 호스트가 캐시를 갱신했는지는 이 두 줄에 없습니다. 장비 교체·가상 머신 이동·승인된 전환 기록을 먼저 대조하고, 원래 ARP의 Opcode·Sender·Target·Ethernet 주소와 연결합니다.

같은 시각의 Request 공지가 :20을 주장했다면 변화와 메시지의 시간상 대응을 설명할 수 있습니다. 그래도 감시 로그의 변화와 대상 호스트의 캐시 수용은 별도입니다. 대상의 이웃 캐시와 이후 프레임 목적지, 스위치·단말 기록까지 연결해야 실제 전달이 바뀌었다는 판단이 강해집니다.

조건을 바꾸면: 이전 값이 없이 첫 줄만 있다면 ‘주소가 공격자 MAC으로 바뀌었다’고 쓸 수 없습니다. 새로 관측한 대응이 있을 뿐입니다. 복습: 변경 로그와 ARP 공지가 같은 주소를 가리키면 공격 성공인가요? 해설: 관측한 주장·감시 기록의 변화까지만 확인했습니다. 정상 변경 여부와 피해자의 수용·실제 전달은 추가 증거가 필요합니다.

5. IPv4 필드와 이상값을 바이트로 확인하기

IPv4 헤더 시작을 0으로 잡으면 TTL은 8, Protocol은 9, 헤더 체크섬은 10~11, 출발지 주소는 12~15, 목적지 주소는 16~19바이트에 있습니다. 버전·IHL은 첫 바이트를 반씩 나누어 읽습니다. Ethernet 프레임 시작과 혼동하지 마세요. [6]

가상 주소 바이트 c0 00 02 14는 192.0.2.20입니다. 헤더 첫 바이트 45는 IPv4와 20바이트 헤더를 뜻합니다. Total Length가 84라면 헤더 뒤의 데이터는 64바이트입니다. Protocol이 ICMP라면 이 64에는 ICMP 헤더도 포함되며, 모두 응용 데이터라고 쓰지 않습니다.

잘못된 버전 값 때문에 도구가 상세 해석을 멈추어도 바이트 확인은 계속할 수 있습니다. 다만 뒤의 바이트를 IPv4 구조로 해석하는 것은 제작 의도나 주변 문맥을 전제로 한 분석입니다. 체크섬 필드가 0이라는 이유만으로 모든 패킷을 불량이라고 단정하지도 않습니다. 해당 헤더 전체의 계산값, 수집 위치, 송신 체크섬 오프로딩 여부를 구분합니다. 이 가이드에서는 원본 패킷의 장비 수신 결과를 확인한 것으로 표시하지 않습니다.

단편 데이터도 이어서 확인합니다. 같은 묶음의 조각이 같은 위치에 서로 다른 내용을 담는다면 중첩의 증거가 됩니다. IP 전체 길이가 수집 링크에서 설정한 MTU보다 크면 점보 설정·오프로딩·수집 지점을 확인합니다. Ethernet이라는 이름만으로 모든 관측 패킷의 IP 길이가 항상 1500 이하라고 가정하지 않습니다.

확인 질문: IHL 6, Total Length 76이라면 헤더 뒤 길이는? 해설: 76−6×4=52바이트입니다. IHL을 그대로 6바이트로 빼거나 ICMP 헤더까지 다시 빼면서 질문의 단위를 바꾸지 않습니다.

선언한 길이와 실제 확보한 길이를 따로 씁니다

가상 헤더가 IHL6·Total Length76이라고 선언했더라도 IP 시작부터 저장된 바이트가40개뿐이라면 전체76개를 읽은 것이 아닙니다. 헤더24개는 확보했지만 뒤 데이터는 40−24=16바이트만 확인할 수 있습니다. 선언한 데이터52개와 비교하면 52−16=36바이트가 저장 범위 밖입니다. 이 차이를 회선에서 패킷이36바이트 손실됐다고 바로 부르지 않고 캡처 잘림·파일 상태를 확인합니다.

체크섬은 검사 범위를 적은 뒤 계산합니다. IPv4 헤더 체크섬이 맞았다는 것과 ICMP 데이터 전체가 맞았다는 것은 다릅니다. 또 계산이 맞았어도 송신자의 정당성이나 응용 처리 성공이 보장되지 않습니다. 실제 수신자가 폐기했는지의 질문에는 수집 위치와 수신·방화벽·서버 기록이 더 필요합니다.

6. 단편을 구간표로 배치하기

조각을 묶을 때는 IPv4 출발지·목적지·Protocol·Identification과 시간 문맥을 확인합니다. ID 하나만 같다고 같은 메시지로 합치지 않습니다. 각 조각의 데이터 길이는 Total Length−IHL×4, 원래 데이터의 시작 위치는 원시 Fragment Offset×8입니다. tcpdump의 출력처럼 이미 바이트 단위로 변환된 위치에는 8을 다시 곱하지 않습니다.

A와 B는 경계에서 이어지고 C는 B의 뒤 8바이트와 중첩합니다. D가 전체 끝을 48로 알려 주더라도 [32,40)은 비어 있습니다. C와 B의 내용이 같은지 다른지 확인하고, 중복 수집·재전송 가능성과 충돌하는 내용을 구별합니다. 순서가 A→D→C→B였어도 데이터 위치는 바뀌지 않습니다.

끝 조각이 없으면 전체 길이를 확정하기 어렵고, 시작 조각이 없으면 상위 헤더를 확인하지 못할 수 있습니다. IPv4 재조립 시간 초과 알림은 첫 조각 수신 여부 등 생성 조건을 확인해야 합니다. 오류가 없다는 이유로 성공을 확정하지 않습니다. 조각이 올 때마다 모든 구현이 타이머를 무조건 새로 시작한다고 외우지 말고 고정 재조립 제한과 실제 구현을 확인합니다. [7]

작거나 서로 다른 크기의 조각은 조사 단서이지만 그 사실 하나가 반드시 규격 위반이나 공격을 뜻하지는 않습니다. 마지막이 아닌 조각의 데이터는 8바이트 배수인지 확인합니다. IP 옵션의 복사 비트가 설정된 옵션은 다른 조각에도 실리는지 확인하며, 조각마다 IHL이 같다고 가정하지 않습니다. [6]

# 사용법 예시: Echo Request의 시작 조각 후보
tcpdump -nn -v -r practice-fragments.pcap 'icmp[0] = 8'
# 같은 관측 구간의 한 묶음 후보를 IPv4 헤더로 다시 선택
tcpdump -nn -v -r practice-fragments.pcap 'src host 192.0.2.20 and dst host 192.0.2.1 and ip proto 1 and ip[4:2] = 42000'

첫 명령은 ICMP Type을 읽으므로 같은 Echo Request의 후속 조각을 모두 보여 주지 않습니다. 후속 조각에는 ICMP 헤더가 다시 실리지 않기 때문입니다. 두 번째 명령은 IP 헤더의 묶음 조건으로 돌아갑니다. ID 재사용과 시간 범위를 확인해야 하며, 이 명령을 실행한 결과가 위 표라고 주장하지 않습니다. [8]

중첩 심화 문제에서는 수신자가 돌려준 Echo Reply 데이터를 요청의 여러 후보와 대조합니다. 한 구간의 일치만 보고 모든 중첩에서 선착 또는 후착을 우선한다고 결론내리지 않습니다. 도착 순서·겹친 위치·완전 중첩과 부분 중첩에 따라 증거를 나누고, 이것은 해당 관측의 결과이지 모든 운영체제의 공통 정책이 아닙니다.

확인 질문: B의 전체 길이가 36이고 헤더가 24로 바뀌면? 해설: 데이터는 12바이트이고 구간은 [16,28)입니다. MF1인 조각의 데이터 길이가 8바이트 배수가 아니라는 추가 이상도 확인합니다. 이전 [16,32)를 그대로 쓰면 안 됩니다.

누락과 중첩을 숫자로 나누어 확인해 볼게요

가상 조각의 저장 데이터 길이는 A16·B16·C8·D8바이트라서 단순 합계는48입니다. 그러나 C8개가 B의구간에 다시 놓이므로 고유하게 확보한 원래 데이터 위치는 48−8=40바이트입니다. 끝 위치48과 비교하면8바이트가 비어 있습니다. 합계48만 보고 완전하다고 판단하면 중첩이 누락을 가려 버립니다.

분실한 페이지가 있는 책에 같은 페이지가 한 장 더 끼어 있는 상황과 비슷합니다. 장수는 맞아 보여도 빠진 내용이 채워진 것은 아닙니다. 실제 패킷에서는 같은 위치의 바이트 값이 같은지까지 비교해야 하므로 페이지 번호 비유만으로 중복과 내용 충돌을 같게 취급하지 않습니다.

두 번째 필터의 src host와 dst host는 방향을, ip proto 1은 IPv4의 ICMP 종류를 제한합니다. ip[4:2]는 IP 시작4번부터2바이트의 Identification을 읽고42000과 비교합니다. 이는 IPID이지 ICMP Echo의Identifier가 아닙니다. and로 네 조건을 모두 요구해도 ID 재사용과 시간·터널 문맥까지 자동 해결되는 것은 아닙니다. 반대 방향 응답은 별도 조건으로 찾아야 합니다.

실습 보완 · IP 옵션의 복사 비트를 직접 판독하기

옵션이 보이면 ‘첫 조각에 있었으니 뒤에도 똑같이 있겠지’라고 추측하기 쉽습니다. IPv4 옵션 Type의 최상위 한 비트는 조각을 만들 때 그 옵션을 각 조각에 복사하는지를 나타냅니다. 이 비트와 옵션 전체 길이는 다른 정보입니다. 옵션 전체를 각 조각에 복사한다는 것이 원래 데이터까지 다시 복제한다는 뜻도 아닙니다. [6]

비트 판독만 위한 가상 Type
0x92 = 1001 0010 → 0x92 & 0x80 = 0x80 → 복사 비트 1
0x12 = 0001 0010 → 0x12 & 0x80 = 0x00 → 복사 비트 0

&는 두 값에서 모두 1인 비트만 남기는 AND입니다. 0x80은 맨 왼쪽 비트만 남기는 마스크입니다. 오른쪽 일곱 비트를 지워 복사 여부를 따로 읽는 것이죠. 위 패턴에 실제 등록 옵션 이름이나 허용 정책을 부여한 것은 아닙니다. 알려진 옵션을 분석할 때는 실제 Type 정의와 길이·데이터도 확인합니다.

일반 다중 바이트 IP 옵션은 Type 한 바이트, 그 둘을 포함하는 Length 한 바이트, 나머지 내부 데이터로 읽습니다. EOL과 NOP는 한 바이트 예외입니다. 옵션의 길이를 따라 다음 경계를 찾고, 전체 IHL 끝을 넘지 않는지 검사합니다. 자세한 필드 구조는 13강의 IP 옵션 해설과 연결됩니다.

Wireshark에서는 IP의 Options와 Type 세부 비트를 펼쳐 해당 바이트를 확인한 뒤 같은 묶음의 후속 조각과 비교합니다. 예를 들어 첫 조각 IHL7에는 복사할 옵션4·첫 조각에만 남길 옵션4가 있고, 후속 조각에는 앞의4만 있다고 가정하면 헤더 길이는 28에서24로 달라질 수 있습니다. 따라서 각 조각의 데이터 길이는 각자의 IHL로 다시 빼야 합니다. 이 숫자는 길이 계산을 위한 독립 가정이며 원본 패킷의 옵션 구성을 재현한 것이 아닙니다.

복습: 복사 비트가 1이면 라우터가 그 패킷을 반드시 허용할까요? 해설: 조각 생성의 복사 규칙과 장비의 옵션 지원·차단 정책은 다릅니다. 실제 옵션의 존재와 반복을 바이트로 확인하고, 처리 성공은 장비 기록과 분리해 검증합니다.

퍼즐의 조각 수만 세지 않고 맞물리는 경계와 완성 테두리까지 확인하는 작업과 비슷합니다. 다만 패킷은 중복 수집이나 별개 메시지의 ID 재사용도 있어, 같은 퍼즐이라는 전제를 먼저 검증해야 합니다. 위 다섯 관점 중 작은 크기·크기 차이는 문맥적 단서이고, 충돌하는 데이터·종료 모순·실제 누락은 별도로 구체적인 근거를 적습니다.

조건을 바꾸면: Q를 다른 ID의 조각으로 분리하면 이 묶음의 조기 종료 모순은 사라지지만 P·R·S·T에는 MF0이 없어 최종 끝을 확정할 수 없습니다. 복습: 조각이 작은 이유를 모르면 나머지 검사를 멈출까요? 해설: 크기 원인은 보류하되 길이·중첩·빈틈·종료 표시는 확보한 필드로 각각 검증합니다.

한 겹침에서는 먼저 온 A가, 다른 겹침에서는 나중에 온 B가 가상 응답과 맞습니다. 그래서 이 입력을 ‘무조건 선착 우선’이나 ‘무조건 후착 우선’ 한 문장으로 설명할 수 없습니다. 행마다 후보·도착 순서·일치 바이트를 남기고, 실제 캡처라면 반대 방향의 Echo Identifier·Sequence·주소·시각으로 응답이 같은 요청에 연결되는지도 확인합니다.

대안 표식은16비트 묶음의 순서만 바꾼 것입니다. 예를 들어 EFGHEFGH와 GHEFGHEF는 같은 EF·GH 묶음을 같은 개수로 가져1의 보수 합을 유지합니다. 따라서 여기서는 어느 대안이 선택되어도 전체 ICMP 체크섬이 같도록 독립 배열을 구성할 수 있습니다. 계산이 같다는 사실로 선택된 바이트를 알아내거나 내용의 진위를 인증할 수는 없습니다. IP 헤더 체크섬은 별도 범위입니다. ASCII 표시·16진수 대조와 체크섬 범위는 16강의 덤프 읽기와 체크섬 해설에서 이어집니다.

복습: 가상 응답의 [24,32)만 GHEFGHEF로 바뀌면 무엇을 고칠까요? 해설: 그 구간의 일치 후보만 B로 바꿉니다. 다른 위치까지 같은 선택이었다고 넓히지 않습니다. 실제 응답이 없다면 이 표의 수신 결과 칸은 확인 불가로 남겨야 합니다.

7. IPv6의 기본 헤더와 이웃 탐색 익히기

IPv6는 주소 표기만 길어진 IPv4가 아닙니다. 기본 헤더는 40바이트이고 Payload Length는 그 기본 헤더 뒤 길이를 나타냅니다. IPv4의 Total Length처럼 기본 헤더까지 포함하는 값과 구분하세요. 기본 헤더에는 IPv4식 IHL과 헤더 체크섬이 없고 TTL의 역할에는 Hop Limit이 대응합니다.

Next Header는 바로 뒤 구조를 가리킵니다. 다음 구조가 상위 프로토콜일 수도 있고 다른 확장 헤더일 수도 있어 연결을 끝까지 따라가야 합니다. IPv6에서는 경유 라우터가 IPv4처럼 패킷을 조각내지 않으며 출발지가 Fragment 헤더를 사용합니다. [9]

실습에서 구분할 이웃 탐색 메시지

Router Solicitation133라우터에게 광고를 요청

Router Solicitation을 단순히 ‘IPv4 ARP와 같은 MAC 질의’로 외우지 마세요. 라우터 광고를 요청하는 절차와 이웃 주소 해석은 목적이 다릅니다. IPv6의 이웃 탐색은 ICMPv6 위에서 동작하며 Ethernet ARP를 그대로 쓰지 않습니다. [10]

주소가 길어진 만큼 헤더도 같은 방식으로 계산할까요?

IPv6 기본 헤더40바이트 뒤에 UDP 헤더8바이트와 데이터24바이트만 있다고 가정하면 Payload Length는 8+24=32바이트이고 IPv6 전체는 40+32=72바이트입니다. 링크 헤더는 포함하지 않습니다. 확장 헤더가 있으면 그것도 기본 헤더 뒤에 있으므로 Payload Length 쪽에 포함됩니다. IPv4의 Total Length와 포함 범위를 바꾸어 외우지 마세요. [9]

이웃 탐색의 약자는 먼저 역할과 연결해 둡시다. RS는 라우터 광고 요청, RA는 그 광고, NS는 이웃 질의, NA는 이웃 정보 알림입니다. 이 네 가지를 ‘MAC을 묻는 한 종류의 메시지’로 합치면 기본 경로 찾기와 이웃 주소 확인을 혼동합니다. 특히 주소 중복 검사 DAD도 NS를 사용하며, 아직 사용하는 주소가 없는 경우 출발지 ::를 사용할 수 있습니다. 그 값 하나만으로 위조라고 단정하지 않고 Target과 절차를 확인합니다. [12]

8. 라우터 광고와 확장 헤더를 분석하기

가상의 호스트가 RS를 보낸 뒤 라우터 A의 RA와 승인되지 않은 것으로 의심되는 B의 RA를 관측했다고 합시다. 먼저 각 RA의 출발지 IPv6 주소, Ethernet 출발지, Source Link-Layer Address 옵션이 있으면 그 값, Router Lifetime, 프리픽스·플래그를 나누어 기록합니다. MAC 두 개를 보았다는 사실만으로 B가 악성이라거나 호스트의 기본 경로가 바뀌었다고 확정하지 않습니다. 승인된 라우터 목록, 단말 경로·이웃 캐시와 이후 전달 경로가 필요합니다. [10]

다음은 새로 만든 헤더 연결 예입니다. 화살표 왼쪽 괄호 안 숫자는 그 헤더의 Next Header 값이며, 바로 오른쪽 헤더를 식별합니다.

IPv6 (NH=0)
  → Hop-by-Hop Options (NH=44)
  → Fragment (NH=17)
  → UDP

0은 Hop-by-Hop Options, 44는 Fragment, 17은 UDP입니다. Fragment 뒤를 무조건 새로운 IPv6 헤더로 해석하지 않습니다. 첫 조각과 후속 조각에서 Fragment 앞에 반복되는 부분을 비교하고, 상위 헤더는 어디까지 실제로 확보했는지 확인합니다. 기본 IPv6 헤더 하나의 Next Header만 보고 UDP가 없다고 결론내리면 확장 헤더 안쪽을 놓칠 수 있습니다. [9]

중첩 처리도 IPv4 사례와 분리해야 합니다. IPv6 중첩 조각을 발견하면 해당 데이터그램 전체를 폐기하도록 정해져 있으므로 IPv4에서 관측한 중첩 우선순위를 IPv6의 정상 처리 규칙으로 옮기지 않습니다. [11]

IPv4와 IPv6 주소의 관계를 찾는 연습에서는 같은 시각·같은 링크에서 관측한 MAC을 연결 단서로 삼습니다. 가상 ARP 응답의 192.0.2.44 → 02:00:00:00:00:44와 NA의 2001:db8::44 → 같은 MAC이 맞으면 같은 인터페이스라는 가설을 세울 수 있습니다. NA에서는 외부 IPv6 출발지뿐 아니라 Target Address와 Target Link-Layer Address 옵션을 확인해야 합니다. 프록시 응답·가상 MAC·위조·주소 변경이 있으므로 동일 MAC만으로 사람이나 물리 호스트의 신원을 확정하지 않습니다.

# 자신이 준비한 파일에 적용하는 MAC 후보 검색 예시
tcpdump -nn -e -r practice-ipv6.pcap 'ether src 02:00:00:00:00:44'
# Wireshark 표시 필터
eth.src == 02:00:00:00:00:44

확인 질문: RA의 외부 Ethernet 출발지와 링크 계층 주소 옵션을 하나의 값으로 기록해도 될까요? 해설: 각각 프레임 전달과 메시지 내부의 주장입니다. 같은지 확인하는 것은 유용하지만 필드를 합쳐 버리면 위조·중계·프록시 상황을 조사할 근거가 사라집니다.

라우터 광고를 받은 뒤 실제 상태가 달라졌는지 확인합니다

RA의 Router Lifetime이0이면 그 발신자를 기본 라우터로 사용하는 유효 기간은0이라는 뜻입니다. 그렇다고 RA의 프리픽스 정보 등 모든 옵션이 무효가 되었다는 뜻은 아닙니다. 기본 경로 선택과 주소 구성 정보를 나누어 읽어야 합니다. RA의 출발지 링크 로컬 주소·Hop Limit255·Code0·체크섬 등 수신 유효성 조건도 함께 확인하되, 이런 형식 조건이 승인된 라우터라는 신원 인증은 아닙니다. [10]

확장 헤더는 ‘바로 다음이 무엇인가’를 연달아 읽습니다

작은 독립 계산도 해 보겠습니다. 반복되는 부분을 IPv6 기본40·Hop-by-Hop8바이트로, Fragment 헤더를8바이트로 가정합니다. 그 뒤의 원래 UDP 헤더와 데이터32바이트를16씩 둘로 나누면 각 조각은 40+8+8+16=72바이트이고 각 Payload Length는 32입니다. 원시 Offset 0과 2는 각각 0과 16바이트 위치이며 M값은 1과 0입니다. 첫 조각에는 UDP 헤더 8과 데이터 8이, 후속에는 나머지 데이터 16만 놓입니다.

재조립 뒤 Fragment헤더는 제거되고 원래 구성은 40+8+32=80바이트입니다. 단순히 두 조각72+72를 응용 크기로 더하면 중복 헤더까지 포함하게 됩니다. 이 값들은 구조를 설명하기 위한 가정으로 실제 캡처·송수신·UDP 체크섬 결과가 아닙니다.

IPv6에서 서로 다른 조각의 구간이 중첩되는 경우의 폐기 규칙은 유지하되, 정확히 같은 조각의 중복 복사본을 따로 버리고 다른 조각은 보존할 수 있다는 RFC8200의 예외도 구분합니다. Offset0·M0인 atomic fragment는 다른 조각과 독립적으로 처리하는 별도 경우입니다. 이 예외를 내용 충돌을 허용하는 일반 규칙으로 확대하지 않습니다. [9] [13]

MAC 후보 필터의 ether src와 표시 필터의 eth.src ==는 바깥 Ethernet 출발지 기준입니다. 주소 옵션이 가리키는Target Link-Layer Address를 대신 검색하는 식은 아닙니다. 같은 MAC 후보를 찾은 뒤 해당 ARP/NA의 내부 필드·시간·링크를 다시 확인해야 합니다. [14]

실습 보완 · Routing 헤더와 조각마다 반복되는 부분

두 IPv6 조각의 맨 앞에 같은 확장 헤더가 보인다면 무엇을 알 수 있을까요? 이름이 같다는 사실에서 멈추지 말고 Fragment 헤더의 앞인지 뒤인지 확인해야 합니다. Routing 헤더는 지정된 노드의 경로 처리와 관련된 확장 헤더이며, 모든 종류의 확장 헤더를 모든 경유 라우터가 똑같이 처리한다는 뜻은 아닙니다. [9]

이 값은 바로 다음 구조를 식별합니다. Routing 헤더의 Next Header가44라고 해서 Routing의 자기 종류가44인 것은 아닙니다. 뒤에 Fragment가 온다는 뜻입니다. 연결도의 각 화살표를 한 칸씩 읽고, 최종 상위 프로토콜을 확인합니다. 번호의 등록 의미와 실제 장비의 지원·허용 여부는 별개입니다. [18]

새로운 독립 구조를 IPv6 → Routing → Fragment → TCP로 가정하겠습니다. 첫 조각과 후속 조각 모두 IPv6 다음에 Routing이 있고 그 다음에 Fragment가 놓입니다. 이때 IPv6와 Routing은 Per-Fragment 부분, 즉 각 조각 앞에서 유지되는 부분에 속합니다. Fragment 뒤에서 나누는 원래 부분과 좌표를 분리해야 합니다. Routing이 있는 구성에서는 그 Routing 헤더까지가 Per-Fragment 부분에 들어간다는 RFC8200의 규칙과 연결됩니다. [9]

서류 묶음을 나눌 때 각 묶음에 배송 안내를 다시 붙이는 비유를 떠올려 보세요. 반복되는 안내는 원래 본문 데이터가 중복되었다는 뜻이 아닙니다. 다만 이 비유를 ‘모든 안내를 모든 사람이 읽는다’는 규칙으로 넓히면 틀립니다. 실제 처리 대상·헤더 종류·현재 목적지와 정책이 있습니다. 후속 조각의 Fragment Next Header가 TCP여도 그 조각의 첫 데이터가 새 TCP 헤더라는 뜻은 아닙니다.

조건을 바꾸어 Routing 앞뒤에 다른 확장 헤더가 있다면 헤더 이름만으로 분류하지 말고 실제 순서와 Fragment 경계를 확인합니다. 그리고 오래된 자료의 Routing Type0은 RFC5095에서 폐기된 기능입니다. 과거 바이트를 해석하는 일과 새 네트워크에서 그 기능을 사용하도록 권하는 일은 구분해야 합니다. [17]

복습: 두 조각에서 Routing이 반복되면 재조립도 완성됐나요? 해설: 헤더 배치의 관측과 데이터 완전성은 다릅니다. Fragment Identification·Offset·M·실제 데이터 길이로 구간표를 따로 만들고 빈틈·중첩을 검사합니다. 헤더 연결만 맞아도 데이터는 빠져 있을 수 있습니다.

9. 관측과 해석을 분리한 종합 복습

질문 1: 이름 변환을 껐는데 질의 이름이 보이면 실패인가요? 해설: 아닙니다. 패킷 데이터에 이미 실린 이름과 분석 중 새로 수행하는 이름 조회를 구분합니다.

질문 2: IP 주소 다섯 개면 TCP 연결도 다섯 개인가요? 해설: 아닙니다. 주소·주소 쌍·포트 쌍별 연결은 서로 다른 집계 단위입니다.

질문 3: ARP 요청의 Ethernet 목적지와 Target MAC이 다른 이유는? 해설: 하나는 프레임을 전달할 주소이고 다른 하나는 아직 알아내려는 주소입니다.

질문 4: 헤더 뒤 52바이트면 응용 데이터도 52바이트인가요? 해설: 상위 프로토콜의 헤더가 포함될 수 있습니다. 질문이 어느 계층 길이를 묻는지 먼저 확인합니다.

질문 5: 마지막 조각이 있으면 완전한가요? 해설: 끝 위치를 알 수 있을 뿐입니다. 모든 구간의 누락·중첩·잘림과 같은 묶음 조건을 확인해야 합니다.

질문 6: 크기가 다른 조각은 모두 공격인가요? 해설: 아닙니다. 재단편화와 헤더 길이 차이도 가능하므로 배수 조건과 전체 구간·경로를 함께 판단합니다.

질문 7: Echo Request 필터가 모든 조각을 보여 주지 않는 이유는? 해설: 후속 조각에는 ICMP Type 위치의 헤더가 반복되지 않습니다. 시작 조각에서 묶음 조건을 얻어 IP 헤더로 다시 선택합니다.

질문 8: 라우터 광고를 받았으면 기본 경로도 바뀌었나요? 해설: 수신과 채택은 다릅니다. 수신자의 설정·정책·경로 상태와 실제 전달을 확인합니다.

질문 9: IPv4 중첩 실습의 결과를 IPv6에 그대로 적용하나요? 해설: 아닙니다. IPv6의 중첩 조각 폐기 규칙을 적용해 따로 판단합니다.

질문 10: 같은 MAC으로 IPv4·IPv6를 연결하면 충분한가요? 해설: 시간·링크·프록시·가상화와 메시지의 Target 필드를 확인하고 단말 자료로 가설을 검증합니다.

각 연습의 마지막에는 ‘어느 입력에서 어떤 필드를 보았는지, 그 값이 어떤 해석을 지지하는지, 무엇은 아직 확인하지 못했는지’를 한 문단으로 적으세요. 개념 풀이를 읽은 것, 계산을 검산한 것, 실제 PCAP을 실행한 것, 수신 장비의 동작을 확인한 것은 서로 다른 완료 단계입니다.

조건을 바꾼 추가 복습

질문 11: 조각 데이터 길이 합이 48바이트이면 원래 48바이트를 전부 확보했나요? 해설: C의 8바이트가 B에 중첩되어 고유 확보는 40이고 [32,40)의 8이 비어 있습니다. 중첩을 제외한 구간의 합으로 검산합니다.

질문 12: IPv6 Payload Length 32는 IPv6 전체 32바이트인가요? 해설: 기본 헤더 40을 제외한 뒤 길이입니다. 이번 기본 예제의 전체는 72바이트이며 확장 헤더가 있으면 Payload Length 안에서 다시 나누어 읽습니다.

질문 13: IPv6 조각 두 개가 각 72바이트면 재조립 뒤 144바이트일까요? 해설: 자체 가정에서는 반복된 기본·확장 헤더와 Fragment 헤더를 구분해야 합니다. 원래 구성은 40+8+32=80이며 후속 데이터에는 UDP 헤더가 다시 실리지 않습니다.

질문 14: RA의 Router Lifetime 0은 모든 프리픽스 옵션도 무효라는 뜻인가요? 해설: 기본 라우터로서의 유효 기간과 다른 옵션의 조건은 별도입니다. 수신과 설정 변경·실제 전달도 구별합니다.

질문 15: 정확히 같은 IPv6 조각의 중복도 내용 충돌과 똑같이 판정하나요? 해설: RFC8200은 정확한 중복만 버리고 나머지 조각을 유지하는 처리를 허용합니다. 같은 구간의 다른 내용 및 atomic fragment의 독립 처리와 분리해 판단합니다.

질문 16: eth.src 필터로 MAC을 찾았으면 NA의 Target 주소 대응까지 확인했나요? 해설: 바깥 프레임 출발지를 찾은 것입니다. NA의 Target Address·주소 옵션과 당시 단말 상태를 별도로 읽어야 하며 같은 MAC만으로 사람을 식별하지 않습니다.

10. 실제 캡처 대조에서 확인한 분석 습관

이전 검토에서는 첫째 날의 여섯 캡처를 파일 내용으로 읽고, 기록 수·시각·Ethernet·ARP·IPv4·TCP·IPv6 필드를 독립 패킷 라이브러리와 교차 검증했습니다. 확장자가 같아도 일부는 PCAP, 일부는 PCAPNG였습니다. 파일 이름이나 확장자만으로 형식과 동일성을 판단하지 말고 헤더와 파일 해시를 기록하세요.

통계의 반올림된 표시는 정확한 바이트·시간과 다를 수 있습니다. 대화의 시작과 끝 시각을 원래 정밀도로 계산한 뒤 화면 단위에 맞춰 비교하면 불일치처럼 보이는 차이를 설명할 수 있습니다. 문자열 검색 결과와 스트림 재구성도 조사 범위가 다르므로 어느 입력에서 찾았는지 기록합니다.

기재 출력과 일부 실제 조각 플래그가 다른 대목은 실제 바이트를 기준으로 구분했습니다. IPv4 헤더 체크섬과 전체 ICMP 응답 체크섬도 따로 검사했습니다. 이 검증은 저장된 파일을 읽은 결과이며 tcpdump·TShark 명령이나 Wireshark 메뉴를 직접 실행한 기록, 실제 스위치·라우터·피해 호스트에서 공격을 재현한 결과는 아닙니다. 앞의 가상 예시는 실제 파일 출력으로 바꾸어 표시하지 않습니다.

11월 2일의 독립 계산과 과거 파일 검증 기록은 그대로 구분합니다. 11월 3일에는 원본 워크북 여섯 실습의 전체 항목을 직접 대조하고 PCAP 여섯 개를 새로 읽었습니다. 총621개 저장 기록의 주요 필드·시각·길이를 독립 라이브러리와 교차 검증했고, 기재 출력과 실제 플래그의 차이 및 조각의 빈 구간도 확인했습니다. 이것은 Wireshark GUI나 tcpdump·TShark 명령을 실행한 기록, 실제 대상 장비에서 공격을 재현한 결과는 아닙니다.
