1. 도구의 해석을 검증하려면 구조부터

앞선 두 노트에서 경고와 실제 발생 사실을 구별했습니다. 이제 도구가 ‘TCP’나 ‘HTTP’라고 표시한 근거를 직접 따라가 보겠습니다. 패킷 분석기는 바이트를 읽고, 프로토콜의 규칙에 따라 헤더와 데이터를 나누며, 그 안에 있는 다음 프로토콜을 해석합니다.

이 과정에는 수집된 정보와 구현의 한계가 있습니다. 캡처 밖의 활동이나 실제 응용 프로그램 내부 상태까지 모두 알 수는 없습니다. 분석 결과를 검증한다는 것은 도구를 불신하는 것이 아니라, 그 결과가 어떤 구조와 증거에서 나왔는지 확인하는 일입니다.

이번 회차의 목표

TCP/IP의 네 계층을 구별하고, 캡슐화와 역캡슐화를 설명하며, 프로토콜 식별자와 길이 필드로 다음 데이터의 위치를 찾습니다.

예를 들어 특정 웹 서버의 취약점을 노리는 요청이 관측됐지만 그 제품을 운영하지 않는다고 해도, 그 이유만으로 요청 탐지가 오탐인 것은 아닙니다. 공격 시도의 존재와 해당 자산에 미칠 영향을 따로 판단합니다.

2. TCP/IP 계층은 통신 역할을 나눈 지도

브라우저에서 웹 서버로 요청을 보내는 장면을 떠올려 보겠습니다. 브라우저는 요청 메시지의 의미를 알아야 하고, 운영체제는 어떤 통신 상대와 프로그램에 데이터를 보낼지 구분해야 합니다. 다른 네트워크를 지나가려면 IP 주소를 이용한 전달이 필요하고, 지금 연결된 링크에서는 그 링크에 맞는 형식으로 전송해야 합니다.

웹 브라우저가 데이터를 보낼 때 모든 일을 한 가지 프로토콜이 처리하지 않습니다. 응용 프로그램의 메시지를 만들고, 통신 상대의 서비스를 구분하고, 다른 네트워크로 전달하고, 현재 링크로 전송하는 역할을 나눕니다. 이 노트에서는 TCP/IP를 네 계층으로 설명합니다. [1]

주소에도 역할의 차이가 있습니다. IP 주소는 IP 통신의 출발지와 목적지를 표현하고, Ethernet의 MAC 주소는 현재 링크에서 프레임을 전달하는 데 사용합니다. 다른 네트워크에 있는 서버로 보내는 경우에는 현재 링크의 다음 전달 지점이 라우터일 수 있습니다. 그래서 ‘프레임의 목적지’와 ‘최종 응용 서버’를 같은 것으로 취급하면 안 됩니다. 이 차이는 링크 계층을 배울 때 다시 자세히 다룹니다.

계층 모델은 역할을 이해하는 지도입니다. 모든 구현이 네 개의 독립된 상자로만 움직인다는 뜻은 아닙니다. 실제 방화벽이나 분석기는 여러 계층의 정보를 함께 사용합니다.

3. 송신할 때는 데이터를 차례로 감싼다

응용 프로그램의 데이터를 보내려면 각 계층에서 필요한 정보를 붙입니다. 이 과정을 캡슐화라고 합니다. 배송 상자 안에 작은 상자를 넣듯, 한 계층에서 만든 헤더와 데이터 전체가 아래 계층의 페이로드가 됩니다.

단순한 TCP over IPv4 over Ethernet 예시에서는 TCP가 응용 데이터를 운반하고, IPv4가 TCP 헤더와 데이터를 운반하며, Ethernet이 IP 패킷 전체를 운반합니다. 페이로드라는 말은 항상 어느 계층을 기준으로 하는지 함께 생각해야 합니다.

송신 과정을 순서대로 풀어 보면 다음과 같습니다.

  1. 응용 프로그램이 보낼 데이터를 준비합니다. 예를 들어 HTTP 요청의 내용입니다. HTTPS라면 TCP가 운반할 데이터를 준비하는 과정에서 TLS가 응용 데이터를 보호합니다.
  2. TCP가 자신의 헤더를 붙입니다. 포트와 순서·확인 응답에 필요한 정보 등이 들어갑니다. TCP가 운반하는 데이터 앞에 TCP용 정보가 추가됩니다.
  3. IPv4가 IP 헤더를 붙입니다. IP 주소와 다음 프로토콜을 나타내는 값 등이 들어갑니다. 이 단계에서는 TCP 헤더까지 포함한 덩어리가 IP의 데이터입니다.
  4. Ethernet이 IP 패킷을 프레임에 담습니다. 현재 링크에서 전달하기 위한 주소와 유형 정보 등이 붙습니다. 실제 프레임의 세부 구성은 링크 종류에 따라 달라집니다.

IP 페이로드는 응용 데이터와 같은 말이 아닙니다. 이 예시의 IP 페이로드에는 TCP 헤더도 포함됩니다. TCP 페이로드를 볼 때 비로소 그 TCP 헤더 뒤의 데이터를 가리킵니다.

패킷 하나가 메시지 하나는 아닙니다

TCP는 바이트 스트림을 제공합니다. 응용 메시지 하나가 여러 TCP 세그먼트에 걸칠 수도 있고, 세그먼트 하나에 메시지가 여러 개 포함될 수도 있습니다. 개별 패킷에 문자열이 없다는 이유만으로 전체 통신에도 없다고 판단하지 마세요. [3]

4. 수신할 때는 종류와 길이를 따라 읽는다

수신 측은 바깥쪽 헤더를 해석하고 내부 데이터를 해당 처리기로 넘깁니다. 이를 역캡슐화라고 합니다. 분석 도구도 이 구조를 따라가며 다음 두 질문에 답합니다.

  1. 다음에는 어떤 프로토콜이 오는가? 프로토콜 식별자를 확인합니다.
  2. 현재 헤더는 어디에서 끝나는가? 정해진 길이나 길이 필드로 경계를 계산합니다.
Ethernet II → IPv4 → TCP를 해석하는 예시
현재 읽는 곳다음 종류를 알려 주는 정보해석
Ethernet II 헤더EtherType 0x0800다음 데이터를 IPv4로 해석합니다.
IPv4 헤더Protocol 6다음 데이터를 TCP로 해석합니다.
TCP 헤더출발지·목적지 포트수신 호스트가 관련 소켓과 프로그램으로 전달하는 데 사용합니다. 응용 프로토콜의 확정 표시는 아닙니다.

EtherType 0x86dd는 IPv6를 가리킵니다. Ethernet의 Type/Length 필드가 길이를 나타내는 IEEE 802.3 프레임은 LLC 등 추가 구조를 고려해야 합니다. 이번 계산은 VLAN 태그가 없는 Ethernet II를 가정합니다. [2]

예를 들어 분석기가 Ethernet II의 EtherType을 보고 IPv4로 들어갔다면, 다음에는 IP 헤더의 형식과 길이가 맞는지 확인합니다. IPv4 Protocol 값이 6이면 TCP가 전달된다는 뜻이지만, IP 단편이라면 TCP를 해석하기 전에 재조립이 필요한 경우가 있습니다. TCP에 도달하면 TCP 헤더의 길이를 읽어 그 뒤의 데이터를 찾습니다.

수신 호스트에서는 포트 등을 이용해 관련 소켓으로 데이터를 전달합니다. 소켓은 프로그램이 통신을 주고받는 접점이라고 먼저 이해하면 됩니다. 패킷을 보는 분석기는 수신 프로그램과 동일한 위치에 있지 않으므로, 포트를 단서로 삼되 실제 프로그램이나 메시지를 추가 증거로 확인해야 합니다.

목적지 포트 80은 HTTP를 예상할 단서지만 보장하지는 않습니다. 실제 바이트와 통신 흐름을 보고 해석이 맞는지 확인합니다. 반대로 암호화된 데이터에서는 응용 메시지를 직접 검증하기 어려울 수 있습니다.

5. 헤더 길이는 외우는 값과 읽어야 하는 값이 다르다

고정 길이의 헤더도 있지만 옵션 때문에 길이가 달라지는 헤더도 있습니다. IPv4나 TCP를 항상 20바이트라고 가정하면 옵션을 데이터로 잘못 읽게 됩니다.

이번 회차에서 사용하는 길이 기준 [2] [3] [4]
대상길이를 확인하는 방법주의할 점

여기에는 세 가지 길이 해석이 섞여 있습니다. Ethernet II의 기본 헤더는 구조에서 길이를 알 수 있는 고정 길이입니다. IPv4와 TCP 헤더는 필드 값을 읽어야 하는 가변 길이입니다. TCP 데이터 길이는 다른 길이를 빼서 구하는 계산된 길이입니다. 무엇을 읽었고 무엇을 계산했는지 구별하면 해석 과정을 설명하기 쉬워집니다.

32비트는 4바이트입니다. 따라서 IHL이나 Data Offset의 원래 값은 그대로 바이트 수가 되지 않습니다. IPv4 헤더와 TCP 헤더는 각각 기본 20바이트이며, 해당 길이 필드로 표현하는 일반적인 최대 헤더 길이는 각각 60바이트입니다. 옵션과 헤더 패딩이 포함되면 길이가 늘어납니다. [3] [4]

Wireshark가 계산된 길이를 바이트로 보여 주는 경우와 원래 필드 값을 읽는 경우도 구별하세요. 예를 들어 원래 IHL 값이 6이면 헤더는 6바이트가 아니라 6 × 4 = 24바이트입니다.

6. 옵션의 경계도 규칙에 따라 읽는다

헤더 전체의 끝을 찾았다고 해서 그 안의 옵션 구조를 모두 이해한 것은 아닙니다. 옵션이 여러 개 있다면 어디에서 하나가 끝나고 다음 것이 시작하는지도 알아야 합니다.

많은 옵션은 종류, 길이, 값으로 구성되어 자신이 차지하는 범위를 알려 줍니다. 그러나 모든 옵션에 같은 형식을 기계적으로 적용하면 안 됩니다. 예를 들어 TCP의 End of Option List와 No-Operation은 한 바이트짜리 형식이며, 다른 옵션에서 사용하는 길이·데이터 구조와 다릅니다. TCP 헤더 길이에는 옵션 뒤의 패딩도 포함될 수 있습니다. [3]

따라서 ‘기본 20바이트 다음의 12바이트’를 봤다고 해서 그 안이 반드시 하나의 12바이트 옵션이라고 해석하지 않습니다. 여러 옵션과 패딩의 조합일 수 있습니다. 전체 경계를 먼저 확인하고, 각 옵션의 종류와 길이 규칙을 따라 읽어야 합니다.

7. 예제로 데이터가 시작되는 위치 계산하기

다음은 학습을 위해 새로 구성한 예시입니다. 실제 PCAP을 실행한 결과가 아닙니다. VLAN 태그 없는 Ethernet II 안에 단편화되지 않은 IPv4/TCP 패킷이 온다고 가정합니다.

  • IPv4 Total Length: 1,000바이트
  • IPv4 IHL: 6 → IP 헤더 24바이트
  • TCP Data Offset: 8 → TCP 헤더 32바이트

먼저 IP 헤더 길이를 바이트로 환산합니다. IHL이 6이므로 6 × 4 = 24바이트입니다. 다음으로 TCP 헤더 길이를 환산하면 Data Offset이 8이므로 8 × 4 = 32바이트입니다.

IP Total Length 1,000바이트에는 IP 헤더와 TCP 헤더, TCP 데이터가 모두 들어 있습니다. 그러므로 TCP 데이터를 남기려면 그 안에 포함된 두 헤더를 빼야 합니다. Ethernet 헤더 14바이트는 애초에 IP Total Length에 포함되지 않았으므로 이 뺄셈에서 다시 빼지 않습니다.

TCP 페이로드 길이는 IP 전체 길이에서 두 헤더 길이를 빼면 됩니다.

TCP 페이로드 = IPv4 Total Length - IPv4 헤더 길이 - TCP 헤더 길이
             = 1000 - 24 - 32
             = 944바이트

Ethernet II 헤더 시작을 0으로 둔 바이트 오프셋
IPv4 헤더 시작 = 14
TCP 헤더 시작  = 14 + 24 = 38
TCP 데이터 시작 = 14 + 24 + 32 = 70

데이터의 시작 위치는 반대로 앞에 있는 길이를 더해서 찾습니다. Ethernet II 헤더가 0번 위치에서 시작한다면 14바이트 뒤에서 IPv4가 시작합니다. 다시 24바이트를 지나면 TCP가 시작하고, TCP 헤더 32바이트를 더 지나면 70번 위치에서 데이터가 시작합니다. 여기서 오프셋은 ‘기준점에서 몇 바이트 떨어졌는가’를 뜻합니다.

여기서 944바이트는 해당 TCP 세그먼트의 페이로드입니다. 파일 전체 크기나 읽을 수 있는 HTTP 본문 길이를 뜻하지 않습니다. TLS를 사용한다면 암호화된 레코드의 일부일 수 있습니다.

IP 단편화, 잘린 캡처, 재조립이 필요한 경우에는 이 단순 계산만으로 캡처된 바이트를 모두 설명할 수 없습니다. 표시된 길이와 실제 확보한 데이터가 맞는지도 함께 확인해야 합니다.

8. 계산한 길이와 실제 캡처가 다르면

패킷 헤더에 적힌 길이는 캡처 파일에 실제로 남은 데이터의 양과 다를 수 있습니다. 수집 도구가 패킷의 앞부분만 저장하도록 설정되어 있다면, 뒤의 내용은 파일에 없습니다. Wireshark는 프레임 길이와 캡처된 길이를 구분하며, SnapLen은 각 프레임에서 저장할 최대 분량을 제한하는 설정입니다. [12]

앞의 가상 예시에서 프레임 길이는 1,014바이트이지만 캡처 파일에는 앞의 128바이트만 저장되었다고 가정해 보겠습니다. 헤더들은 모두 확보했고 TCP 데이터는 70번 위치에서 시작합니다. 이 파일에 남아 있는 TCP 데이터는 128 - 70 = 58바이트입니다. IP·TCP 헤더에서 계산한 페이로드 944바이트 전체를 읽을 수 있는 것이 아닙니다.

같은 예시에서 서로 다른 길이의 의미
값의미
944바이트헤더의 길이 값에서 계산한 해당 TCP 세그먼트의 페이로드 길이
58바이트앞의 128바이트만 저장한 이 캡처에 실제로 남은 TCP 데이터 분량
미확인남은 데이터를 포함한 실제 메시지의 전체 의미와 응용 프로그램의 처리 결과

이 차이만으로 실제 통신에서 데이터가 사라졌다고 결론 내리지 않습니다. 수집 단계에서 저장하지 않은 것일 수 있기 때문입니다. 반대로 헤더 길이를 더했는데 전체 IP 길이보다 커지는 등 구조 자체가 맞지 않는다면, 계산 단위·링크 형식·디코딩 기준·캡처 손상·실제 비정상 패킷 가능성을 다시 확인해야 합니다.

또한 TCP는 여러 세그먼트의 데이터를 이어서 응용 프로그램에 제공합니다. Wireshark의 Follow TCP Stream은 관련 스트림을 읽는 데 도움이 되지만, 수집하지 못한 바이트를 만들어 주거나 암호화를 자동으로 풀어 주지는 않습니다. 필요한 구간이 빠졌는지와 복호화 정보가 있는지를 별도로 확인합니다. [11]

9. 최신 보충 — 계층은 유효하지만 조합은 다양하다

캡슐화와 길이 확인 원리는 여전히 유효합니다. 현재 환경에서는 ‘웹이니까 항상 TCP’ 또는 ‘IP니까 항상 IPv4’처럼 특정 조합을 전제로 하지 않는 것이 중요합니다.

기초 예시를 현재 환경에 적용할 때
상황해석에 반영할 내용
HTTP/3와 QUICHTTP/3는 QUIC을 사용하고 QUIC 패킷은 UDP 데이터그램으로 전달됩니다. TCP 헤더나 SYN 플래그를 찾는 방식으로 해석하지 않습니다. [5] [6]
IPv6기본 헤더는 40바이트이고 Next Header로 다음 헤더를 가리킵니다. 확장 헤더가 있으면 그 구조를 따라가야 합니다. IPv4의 IHL·Total Length 공식을 그대로 쓰지 않습니다. [7]
호스트에서 직접 수집체크섬 계산이나 분할이 NIC에 위임되어 있으면 캡처에서 체크섬 오류나 예상보다 큰 데이터 단위가 보일 수 있습니다. 실제 회선의 패킷도 같았다고 단정하지 않습니다. [8]
표준과 관측 조건 확인

TCP 표준을 확인할 때는 2022년의 RFC 9293도 참고합니다. 이 문서는 RFC 793을 대체하며 TCP의 명세와 누적 변경 사항을 정리합니다. IPv6의 길이·확장 헤더나 QUIC처럼 다른 구조를 만났다면 그 프로토콜의 표준으로 돌아가 확인하세요. [3]

Wireshark에서 체크섬 경고가 보이면 먼저 캡처 위치와 오프로딩 여부를 확인합니다. 가능한 경우 다른 관측 지점의 캡처와 비교해 실제 전송 오류인지 구분합니다. 경고를 일괄적으로 무시하거나 모두 공격으로 분류하지 않습니다. [8]

10. 클라우드에서도 관측 범위를 먼저 정한다

클라우드라고 패킷 분석이 불가능한 것은 아닙니다. 다만 ‘클라우드의 모든 패킷을 제한 없이 확보할 수 있다’고 이해하면 안 됩니다. 서비스, 지원되는 수집 소스, 권한, 경로와 필터를 확인해야 합니다.

예를 들어 AWS VPC Traffic Mirroring은 소스·타깃·필터로 세션을 구성하며 모든 인스턴스 유형에서 지원되는 것은 아닙니다. 공식 제한 문서에는 ARP·DHCP 등 미러링할 수 없는 트래픽과 MTU에 따른 잘림, 대역폭 제약에 따른 손실 가능성도 설명되어 있습니다. [9] [10]

클라우드에서 수집되는 미러링본에는 원래 패킷을 옮기기 위한 바깥쪽 캡슐화가 더 붙을 수 있습니다. AWS Traffic Mirroring의 VXLAN 전달이 그 예입니다. 이때 바깥쪽 IP·UDP 정보는 수집 전달을 위한 정보이고, 안쪽에는 조사하려던 원래 프레임과 통신이 들어 있습니다. 바깥쪽 주소만 보고 업무 통신의 상대라고 기록하지 않도록 원본이 어느 위치에 들어 있는지 확인합니다. [13]

이것이 캡슐화를 배우는 실무적인 이유 중 하나입니다. ‘IP가 두 번 보인다’는 현상이 곧 공격을 뜻하지는 않습니다. 정상적인 수집 터널이나 다른 캡슐화 구조일 수 있으므로 어떤 계층을 보고 있는지 먼저 구별해야 합니다.

따라서 조사를 설계할 때는 ‘어느 지점에서 어떤 통신을 수집했는가’를 기록합니다. 직접 캡처할 수 없는 활동은 서비스의 감사 로그와 응용 로그 등으로 보완합니다. 비용도 수집량·전송·분석·보존 조건에 따라 검토해야 하므로, 무조건 저렴하거나 비싸다고 일반화하지 않습니다.

안 보이는 이유도 조사 대상

암호화로 내용이 숨겨진 것, 수집 대상이 아니어서 없는 것, 필터로 제외된 것, 캡처가 잘리거나 누락된 것은 다른 문제입니다. 무엇이 원인인지 구분해야 올바른 다음 증거를 선택할 수 있습니다.

11. 이번 회차의 증거 구분

패킷으로 확인

관측된 링크 형식, EtherType, IP 프로토콜 식별자, 헤더 길이와 전체 길이, 확보된 데이터의 경계.

패킷만으로 확정 불가

포트만으로 응용 프로그램의 정체, 암호화된 본문의 의미, 관측 밖 활동, 캡처의 체크섬 경고만으로 실제 회선 오류 여부.

함께 확인할 자료

캡처 지점과 링크 유형, 미러링 필터·수집 손실 기록, NIC 오프로딩 설정, 단말 프로세스·연결 기록, 서버와 클라우드 감사 로그.

12. 복습과 경계 계산 연습

질문: IP 페이로드와 TCP 페이로드는 같을까요?

해설: 이번 TCP over IPv4 예시에서는 다릅니다. IP 페이로드에는 TCP 헤더와 TCP 데이터가 들어 있습니다. TCP 페이로드는 TCP 헤더 뒤의 데이터입니다. 페이로드라고 할 때는 어느 계층을 기준으로 하는지 먼저 확인합니다.

질문: IPv4 IHL이 5이고 TCP Data Offset이 8입니다. IP Total Length가 900바이트라면 TCP 데이터는 몇 바이트일까요?

해설: 단편화되지 않은 완전한 IPv4/TCP 패킷을 가정하면 IP 헤더는 5 × 4 = 20바이트, TCP 헤더는 8 × 4 = 32바이트입니다. 따라서 900 - 20 - 32 = 848바이트입니다. Ethernet 헤더 길이를 이 계산에서 다시 빼지 않습니다.

질문: Ethernet II의 IP 시작 위치는 언제나 14일까요?

해설: 이번처럼 VLAN 태그가 없는 단순 구조에서는 14바이트 뒤입니다. VLAN이나 다른 캡처 링크 형식에서는 위치가 달라지므로 실제 구조를 확인해야 합니다. 프레임 시작 기준인지 IP 헤더 시작 기준인지도 함께 적습니다.

질문: 헤더에서 계산한 TCP 데이터가 944바이트인데 파일에는 58바이트만 보입니다. 통신 오류일까요?

해설: 곧바로 그렇게 판단하지 않습니다. SnapLen 등으로 캡처가 잘렸는지, 실제 저장된 길이는 얼마인지 확인합니다. 캡처 파일에 없는 것과 실제로 전송되지 않은 것은 다른 상황입니다.

조사 메모에는 계산의 전제를 함께 적어 보세요.

VLAN 태그 없는 Ethernet II 및 단편화되지 않은 IPv4/TCP 구조로 해석하였다. IHL과 Data Offset을 바이트로 환산해 TCP 데이터 시작 위치를 계산했다. 캡처 길이와 예상 데이터 길이를 비교했으며, 응용 프로토콜과 처리 결과는 추가 검증이 필요하다.

워크북 연계 실습

Ethernet Type, IPv4 Protocol, 상위 데이터의 단서를 구분해 다음 구조를 찾는 연습입니다. 계층을 바꾸어 같은 패킷 읽기에서 단계별 설명과 복습을 읽을 수 있습니다. 이 페이지의 기존 자체 예시는 그대로 유지하며, 원본 PCAP을 실행한 출력으로 제시하지 않습니다.
