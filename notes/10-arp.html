시작하며 — IP를 아는데 왜 첫 프레임을 못 보낼까요?

같은 사무실의 서버에 접속하려고 합니다. 서버의 IPv4 주소도 맞고 프로그램도 실행 중인데, 캡처에는 웹 요청 대신 “누가 이 주소를 쓰나요?”라는 질문이 먼저 보입니다. 왜 바로 요청을 보내지 않을까요? 프로그램이 아는 최종 목적지 주소와, 지금 연결된 링크에서 프레임을 넘길 상대의 주소가 서로 다른 역할을 하기 때문입니다.

큰 건물에서 문서를 전달하는 상황을 떠올려 보세요. 문서에 적힌 최종 수신 부서와, 현재 층에서 봉투를 맡길 담당 창구는 같을 수도 다를 수도 있습니다. 같은 층이라면 담당자에게 직접 주고, 다른 건물이라면 외부 배송 창구에 맡기겠지요. 먼저 “어느 쪽으로 맡길까?”를 정하고, 그다음 “그 창구는 어디인가?”를 알아내야 합니다. 네트워크에서는 앞의 질문이 경로 선택, 뒤의 질문이 이번 링크에서 쓸 주소 대응과 연결됩니다.

비유에는 한계가 있습니다. ARP는 건물 전체의 공식 직원 명부도, 사람을 인증하는 절차도 아닙니다. 같은 링크에 “이 IPv4 주소의 링크 주소를 알려 주세요”라고 묻고, 응답자가 주장하는 대응을 얻는 프로토콜입니다. 그 주장이 진짜인지와 수신자가 실제 사용했는지는 추가로 확인해야 합니다.

이번에는 경로를 정한다 → 필요한 다음 홉의 대응을 확인한다 → 없으면 요청한다 → 응답을 검토·학습한다 → 이후 데이터 프레임에 쓴다는 흐름으로 읽어 보겠습니다. 다음 홉은 현재 링크에서 패킷을 다음으로 넘겨받을 지점입니다. 본문의 주소·바이트·요약은 모두 독립적으로 만든 학습 예시이며 실제 PCAP 실행 출력이 아닙니다.

1. IP 주소를 MAC 주소로 ‘변환한다’는 말의 의미

9강에서 Ethernet 프레임은 목적지 MAC과 출발지 MAC을 담는다고 배웠습니다. 그렇다면 프로그램이 상대의 IP 주소를 알고 있을 때, 프레임에 넣을 MAC은 어떻게 알아낼까요? IPv4 over Ethernet의 일반적인 환경에서는 ARP, Address Resolution Protocol이 이 주소 대응을 알아내는 역할을 합니다.

여기서 ‘변환’은 IP 숫자를 어떤 공식에 넣어 MAC을 계산한다는 뜻이 아닙니다. 선택한 다음 전달 지점의 IPv4 주소에 대응하는 링크 주소를 알아내고 저장하는 일입니다. IP 헤더가 MAC 헤더로 바뀌어 사라지는 것도 아닙니다. 이후 데이터를 보낼 때는 IP 패킷을 해당 MAC 주소가 들어 있는 Ethernet 프레임에 담습니다.

NIC는 Network Interface Card, 즉 네트워크 인터페이스 장치를 뜻합니다. 운영체제의 네트워크 코드와 드라이버가 인터페이스를 통해 링크로 데이터를 내보냅니다. 이 예제의 Ethernet MAC은 6바이트 × 8 = 48비트이고, 16진수 두 자리씩 여섯 묶음으로 표시합니다. IPv4는 4바이트 = 32비트, IPv6는 16바이트 = 128비트입니다. 주소의 크기와 역할이 다르므로 서로 단순 대체되는 값이라고 생각하지 마세요.

MAC의 앞 3바이트를 OUI, Organizationally Unique Identifier로 소개하는 경우가 많습니다. 전역적으로 할당된 일반적인 주소에서는 조직 등록 정보를 알아볼 단서가 될 수 있습니다. 그러나 등록 주소의 종류와 로컬 관리 주소를 구분해야 하고, 앞부분만으로 실제 제품·사용자·실행 프로그램을 확정할 수는 없습니다. 예제에는 RFC 9542의 문서용 MAC 주소를 사용합니다. [1]

MAC의 고정성에 대한 보완 · 2026년 11월 2일 확인

‘하드웨어에 기록되어 있으므로 MAC은 변하지 않고, 바뀌면 NIC 교체뿐’이라는 설명은 일반화할 수 없습니다. 가상 인터페이스, 주소 설정과 프라이버시 기능 등으로 관측 주소가 바뀔 수 있습니다. Apple의 현재 공식 안내도 고정·순환 방식의 비공개 Wi-Fi 주소를 구분합니다. 반대로 가상 머신이라고 매번 부팅할 때 반드시 주소가 달라지는 것도 아닙니다. 실제 장비·가상화·네트워크 설정을 확인합니다. [2]

주소의 길이가 다르다는 것과 역할이 다르다는 것을 함께 봅시다

MAC은 Media Access Control의 약자입니다. 여기서는 현재 Ethernet 링크에서 프레임 전달에 쓰는 주소로 읽으면 됩니다. IP는 Internet Protocol의 주소이고, 경로를 따라 최종 IP 목적지로 전달하는 데 사용합니다. 6바이트짜리 MAC과 4바이트짜리 IPv4는 자릿수부터 다르지만, 핵심은 길이 차이보다 답하려는 전달 질문이 다르다는 점입니다.

가령 하나의 인터페이스가 IPv4 주소 둘을 사용하면 같은 MAC에 여러 IP가 대응할 수 있습니다. 반대로 장애조치로 같은 서비스 IP를 다른 인터페이스가 맡으면 그 IP에 대해 관측되는 MAC이 바뀔 수 있지요. “한 IP는 영원히 한 MAC”이라는 일대일 명부로 외우면 이런 정상 동작도 공격으로 오해하기 쉽습니다. 변경 이유는 DHCP 할당·가상화·장애조치 이력과 함께 살펴봅니다.

MAC을 여섯 묶음으로 표시할 때 콜론은 읽기 쉽게 나눈 표기이며 전송되는 주소 바이트 사이에 콜론 문자가 들어가는 것은 아닙니다. 앞 24비트를 조직 접두부로 읽을 수 있는 등록 방식도 있지만, 로컬 관리 주소나 다른 할당 방식을 무시하고 앞 세 바이트를 제조사 인증서처럼 사용하면 안 됩니다. 문서용 주소도 실제 장비의 신원을 나타내지 않습니다. [1]

2. 먼저 ‘누구의 MAC이 필요한가’를 정한다

ARP를 보내기 전에 먼저 경로 선택이 있습니다. 목적지가 같은 링크에서 직접 전달할 대상인지, 게이트웨이에 넘길 대상인지에 따라 알아낼 MAC이 다릅니다. ARP가 인터넷 전체에서 최종 서버의 MAC을 찾아다니는 것은 아닙니다.

다음은 단순한 가상 구성입니다. A는 192.0.2.10/24, 같은 링크의 B는 192.0.2.20/24, 기본 게이트웨이는 192.0.2.1입니다. 더 구체적인 경로나 정책 라우팅은 없다고 가정합니다. /24는 주소의 앞 24비트가 네트워크 부분이라는 뜻이며 마스크는 255.255.255.0입니다.

A와 B에 마스크를 적용하면 둘 다 네트워크 값 192.0.2.0이 나옵니다. 이 단순 예제에서는 B를 같은 링크에서 직접 찾습니다. 반면 198.51.100.20에 같은 마스크를 적용하면 198.51.100.0이므로 다른 네트워크입니다. A는 기본 경로를 선택해 게이트웨이 192.0.2.1에 보냅니다. 그때 알아낼 대상은 외부 서버가 아니라 게이트웨이의 MAC입니다.

상황알아낼 MAC의 IP이후 데이터 프레임의 목적지
A → 같은 링크 B192.0.2.20B의 MAC
A → 외부 198.51.100.20192.0.2.1게이트웨이의 MAC. IP 목적지는 외부 주소 유지

실제 운영체제는 라우팅 테이블 등을 조회해 출력 인터페이스와 다음 홉을 정합니다. 마스크 비교만으로 모든 환경의 경로를 설명하지 않습니다. 게이트웨이·경로 정보는 수동 설정, DHCP 등의 구성이나 라우팅 학습으로 얻을 수 있고 ARP가 기본 게이트웨이를 임의로 골라 주는 것은 아닙니다.

또한 사용할 수 있는 캐시가 이미 있다면 새로운 ARP 요청 없이 데이터를 보낼 수 있습니다. ‘통신을 시작했으니 반드시 바로 앞에 ARP가 한 번 보여야 한다’는 가정은 틀릴 수 있습니다. 경로를 정하는 일과 링크 주소를 알아내는 일, 기존 대응을 재사용하는 일을 나누어 보아야 합니다.

조건을 하나 바꾸면 ARP 대상도 바뀝니다

앞의 A와 B는 마지막 숫자가 10과 20으로 다릅니다. /24 마스크를 적용한다는 것은 각 주소 비트에 마스크 비트와의 AND를 수행하는 것입니다. AND는 두 비트가 모두 1일 때만 1을 남기는 연산입니다. 255는 이진수 11111111이므로 앞 세 바이트는 그대로 두고, 0은 00000000이므로 마지막 바이트는 모두 0으로 만듭니다. A의 마지막 값 10은 00001010이고, 00000000과 AND하면 00000000입니다. B의 20도 같은 연산 뒤 0이 됩니다. 그래서 둘의 연결 경로가 192.0.2.0/24라는 단순 구성에서는 B를 직접 찾는 것이죠.

이번에는 목적지 B를 192.0.2.200으로 바꿔 보세요. 같은 /24에서는 여전히 직접 찾습니다. 그런데 A의 연결 경로를 192.0.2.0/25로 바꾸고, 나머지 구성도 그에 맞게 설정했다고 합시다. /25의 마지막 마스크 바이트 128은 10000000입니다. 10은 00001010이므로 AND 결과 0, 200은 11001000이므로 결과 128입니다. A는 192.0.2.0/25 쪽이고 B는 192.0.2.128/25 쪽이지요. 기본 경로를 쓴다면 이번에는 게이트웨이의 MAC이 필요합니다. “앞 세 숫자가 같으니 직접 ARP”라는 암기 규칙이 깨집니다.

이 계산은 연결 경로를 이해하는 예제입니다. 실제 호스트에 특정 목적지로 가는 더 구체적인 경로가 있거나 다른 인터페이스·정책을 선택한다면 결과가 달라집니다. 같은 주소처럼 보이는가보다 실제 선택된 출력 경로와 다음 홉을 먼저 확인하세요. DHCP는 Dynamic Host Configuration Protocol로, 주소·게이트웨이 같은 설정을 제공할 수 있는 프로토콜입니다. DHCP가 설정을 준다는 것과 ARP가 그 다음 홉의 MAC을 알아낸다는 것은 별개의 단계입니다.

반대 방향도 생각해 봅시다. 외부에서 온 IP 패킷을 라우터가 A에게 전달하려고 하는데 A의 대응을 모릅니다. 이때 ARP 요청자는 라우터이고 질의 대상은 A입니다. 외부 서버가 원격에서 A의 MAC을 직접 물어보는 것이 아닙니다. 이미 유효한 대응이 있다면 이 방향에서도 새 질문 없이 전달할 수 있습니다.

3. ARP 요청은 무엇을 묻는가

A가 B의 MAC을 아직 모른다고 가정하겠습니다. A의 MAC은 문서용 주소 00:00:5e:00:53:10, B의 MAC은 00:00:5e:00:53:20으로 두겠습니다. A는 ‘192.0.2.20을 사용하는 장치는 누구이며 그 MAC은 무엇인가’를 묻는 ARP Request를 보냅니다.

이 일반적인 최초 요청의 Ethernet 목적지는 ff:ff:ff:ff:ff:ff입니다. 찾으려는 장치의 MAC을 모르므로 로컬 브로드캐스트 범위에 질문하는 것입니다. VLAN으로 나뉜 환경에서는 그 논리적 범위와 전달 설정도 확인해야 합니다. 브로드캐스트라는 말이 인터넷 전체에 퍼진다는 뜻은 아닙니다.

ARP 요청 안에는 질문만 있는 것이 아닙니다. Sender 필드에는 ‘나는 192.0.2.10이며 이 MAC을 사용한다’는 정보가 함께 들어 있습니다. 수신자는 이 정보를 주소 대응 학습에 사용할 수 있습니다. 다만 이 값이 패킷 안에 있다는 것과 그 주장이 인증되었다는 것은 다릅니다. [3]

같은 브로드캐스트를 본 다른 장치가 항상 새 ARP 항목을 생성한다고 단정하지 않습니다. 기존 항목의 유무, 자신이 질의 대상인지, 구현과 설정에 따라 학습 조건이 달라집니다. 이 부분은 캐시 절에서 더 구체적으로 설명하겠습니다.

같은 질문을 들었다고 모두 같은 일을 하는 것은 아닙니다

Request는 요청이라는 뜻입니다. A는 Ethernet 브로드캐스트로 질문을 내보내고, 요청 내부의 Sender에는 자신의 MAC과 IPv4를 적습니다. B 외의 장치 C도 같은 범위에서 그 프레임을 받았을 수 있습니다. 그러나 전달받음·ARP 처리·캐시 갱신·새 항목 생성은 서로 다른 동작입니다. 보안 정책이나 구현 조건이 각각 영향을 줍니다.

여기서 Target은 “이번 ARP 메시지가 대상으로 삼는 주소 자리”입니다. 처음 요청에서는 B를 찾으므로 Target IP가 B입니다. 뒤의 응답에서는 요청자 A에게 답하므로 Target IP가 A가 됩니다. 두 메시지에서 Target을 항상 ‘최종 서버’라는 고정 이름으로 읽지 않으면 Sender와 Target을 뒤집는 실수를 줄일 수 있습니다.

그럼 질문을 받기만 해도 A가 진짜라는 뜻일까요? 그렇지 않습니다. Sender가 기록되었다는 것은 그 대응을 알렸다는 관측 사실입니다. ARP 기본 형식에는 그 주장을 확인할 전자서명이나 인증서가 붙지 않습니다. 실제 A의 자산 정보·스위치 연결·단말 상태와의 일치 여부는 따로 검증합니다.

4. 응답 뒤에는 데이터를 보낼 수 있는 대응이 생긴다

B가 자신의 IPv4 주소를 묻는 요청을 처리하면 ARP Reply로 MAC을 알려 줍니다. 이 일반적인 요청·응답 예제에서 응답의 Ethernet 출발지는 B의 MAC, 목적지는 요청자 A의 MAC입니다. 질문을 들은 모두에게 다시 알리는 방식과 달리, 응답은 보통 요청자에게 유니캐스트로 전달됩니다.

응답 안의 Sender는 B의 MAC·IP이고 Target은 A의 MAC·IP입니다. A가 그 대응을 사용할 수 있게 되면 IPv4 패킷의 목적지를 192.0.2.20으로 두고, 그 바깥 Ethernet 목적지에 B의 MAC을 넣어 보낼 수 있습니다. ARP 패킷이 IP 데이터 패킷으로 변하는 것이 아니라, ARP로 알아낸 정보를 이후 데이터 프레임에 사용하는 것입니다.

다른 네트워크로 나가는 상황도 같은 원리입니다. 게이트웨이의 대응을 알아낸 다음, IP 목적지는 외부 서버로 둔 채 Ethernet 목적지는 게이트웨이로 설정합니다. 라우터는 다음 링크로 나갈 때 새 링크 프레임을 만듭니다. 일반적인 라우팅 예제에서는 출발지 MAC뿐 아니라 출력 링크의 출발지·목적지 MAC 모두를 그 링크에 맞게 구성합니다. NAT·터널 등 별도 처리가 없는 예제라는 전제도 함께 둡니다.

ARP 요청은 보았는데 응답이 안 보인다면 실제 무응답인지, 센서가 유니캐스트 반환 경로를 못 보는지 먼저 확인합니다. 스위치가 모든 유니캐스트 프레임을 모든 포트에 전달하는 것은 아닙니다. 센서의 수집 위치와 미러링 설정이 가시성을 정합니다. 응답 부재만으로 대상이 꺼졌거나 차단에 성공했다고 확정하지 않습니다.

응답이 알려 주는 것은 ‘다음 프레임에 쓸 후보’입니다

Reply는 응답이라는 뜻이고 유니캐스트는 여기서 특정 MAC을 목적지로 지정한 전달입니다. B가 A의 질문을 처리해 답하는 일반 예제에서는 A의 MAC을 이미 요청의 Sender에서 읽을 수 있으므로, 응답을 보내기 위해 반드시 별도의 역방향 ARP 질문부터 할 필요는 없습니다. 다만 실제 캐시 생성·사용 조건은 운영체제에 달려 있습니다.

“응답 뒤 데이터를 보낼 수 있다”는 말도 전제를 포함합니다. A가 응답을 받아들였고 적절한 경로와 사용 가능한 인터페이스가 있어야 합니다. A가 그 MAC으로 다음 프레임을 보냈다면 대응 사용의 증거가 늘지만, B가 해당 프레임을 정상 수신하고 응용 요청까지 처리했는지는 여전히 별도 질문입니다. 서버 접근·응용·인증 기록과 방화벽 기록을 연결할 때도 같은 시각·방향·대상 통신인지 확인합니다.

예를 들어 센서가 C의 일반 스위치 포트에 있다면 브로드캐스트 질문은 보아도 A에게만 돌아가는 응답은 못 볼 수 있습니다. A 포트 양방향 미러에서는 둘 다 보일 수 있지요. “같은 LAN에서 캡처했다”는 말보다 정확한 포트·VLAN·방향·미러링 설정과 수집 시작·종료 시각이 더 유용한 설명입니다. 반복 요청만 보일 때도 대상 고장, 반환 경로 누락, 요청자의 학습 거부를 분리해 조사합니다.

5. Ethernet과 ARP의 필드를 나누어 읽는다

Wireshark에서 Ethernet II와 Address Resolution Protocol을 각각 펼칩니다. Ethernet의 Type이 0x0806이면 뒤에 ARP가 온다는 뜻입니다. 그런데 ARP 내부의 Protocol type에는 0x0800이 보일 수 있습니다. 이것은 이번에 주소 대응을 알아내는 프로토콜이 IPv4라는 뜻입니다. ARP 내부의 값 뒤에 곧바로 IPv4 헤더가 들어 있다는 뜻이 아닙니다.

숫자가 같아 보여도 어떤 자리의 값인지 먼저 물어보세요

필드란 메시지 안에서 정해진 뜻과 폭을 가진 자리입니다. Opcode의 op는 operation, 즉 동작을 가리키며 이 예제의 1과 2는 순서 번호가 아니라 요청·응답 종류입니다. 앞의 Hardware type 1도 숫자 1이지만 Ethernet이라는 주소 형식을 뜻합니다. 같은 1이 보인다고 두 필드가 같은 의미는 아니죠.

SHA·SPA·THA·TPA에서 S는 Sender, T는 Target, H는 Hardware, P는 Protocol, A는 Address입니다. SHA는 보내는 쪽 하드웨어 주소, TPA는 대상 프로토콜 주소처럼 조합하면 됩니다. 하드웨어 주소는 이번 예제의 MAC, 프로토콜 주소는 이번 예제의 IPv4입니다. 크기 필드 6과 4는 이 뒤의 주소를 각각 몇 바이트씩 읽을지 알려 줍니다.

ARP Probe의 경우도 조건을 풀어 봅시다. 아직 주소를 사용하기 전에 중복 여부를 검사하려는 장치는 SPA를 0.0.0.0으로 두고 TPA에 검사할 주소를 넣을 수 있습니다. 이는 “0.0.0.0이라는 일반 호스트에게 통신한다”는 뜻도, 출발지를 숨겼다는 확증도 아닙니다. RFC 5227의 Probe는 브로드캐스트 ARP Request이며 THA는 수신 시 무시하고 송신 시 0으로 두도록 권고합니다. 이후 주소 사용을 알리는 Announcement는 SPA와 TPA에 같은 알릴 주소를 넣는 Request입니다. 기본 주소 질의·중복 검사·주소 알림은 목적이 다릅니다. [4]

보통의 질의 응답이 유니캐스트라는 설명은 유지하되 모든 Reply가 반드시 유니캐스트라는 판정 규칙으로 만들지 않습니다. RFC 5227은 브로드캐스트 Reply를 쓰는 문맥도 별도로 다룹니다. 주소 필드·동작 종류·발생 시점과 네트워크 구성을 함께 읽어야 합니다. 자세한 충돌·위조 판별과 방어는 다음 강의에서 이어갑니다.

6. ARP 28바이트와 프레임의 위치 계산

이번 조합에서 고정된 앞부분은 2 + 2 + 1 + 1 + 2 = 8바이트입니다. 주소 부분은 Sender MAC 6 + Sender IP 4 + Target MAC 6 + Target IP 4이므로 20바이트입니다. 따라서 ARP 메시지는 8 + 20 = 28바이트입니다.

VLAN 태그 없는 Ethernet II에서는 ARP가 프레임 오프셋 14에서 시작합니다. 다음은 앞의 요청을 자체 구성한 42바이트의 헤더·메시지 예시입니다. 패딩과 FCS를 넣지 않은 배열이며 실제 송신·캡처 출력이 아닙니다.

예를 들어 SPA의 첫 바이트 c0는 12 × 16 + 0 = 192, 마지막 0a는 십진수 10입니다. TPA의 마지막 14는 1 × 16 + 4 = 20입니다. Opcode 00 01은 이 필드의 높은 바이트부터 읽어 1로 해석합니다. 필드 위치·폭·바이트 순서·진법을 함께 확인하는 과정입니다.

Ethernet 14 + ARP 28 = 42는 전체 회선 프레임의 최소 길이가 42라는 뜻이 아닙니다. 일반적인 태그 없는 Ethernet의 데이터·패딩 최소가 46바이트이므로 ARP 뒤에는 46 - 28 = 18바이트의 패딩이 필요하고, FCS까지 포함하면 14 + 28 + 18 + 4 = 64바이트입니다. FCS를 제공하지 않는 예시 캡처라면 60바이트입니다. [5]

분석 화면이나 기록에 42바이트가 보인다면 확보된 헤더·ARP 길이와 회선의 실제 전송 길이를 구분해야 합니다. 수집 위치, 길이 잘림, NIC·드라이버가 패딩·FCS를 어느 단계에서 제공하는지 등을 검토합니다. 이 예시의 42바이트는 42 × 8 = 336비트입니다. 이 숫자 역시 저장·표시된 기록의 길이로 해석해야 합니다. 프로그램의 ‘on wire’라는 열 이름만 보고 호스트 수집 기록이 항상 물리 신호의 모든 바이트를 직접 측정했다고 가정하지 않습니다. 태그가 있으면 ARP 시작도 14로 고정되지 않습니다.

기준점을 바꿔도 바이트가 바뀌는 것은 아닙니다

오프셋은 기준점에서 몇 바이트 떨어졌는지 나타내는 위치입니다. 첫 바이트를 0으로 세므로 28바이트짜리 ARP 메시지의 마지막 바이트는 ARP 기준 27입니다. 프레임 기준에서는 시작 14를 더해 41이지요. SHA의 ARP 기준 위치는 8~13, 프레임 기준은 22~27입니다. 어떤 기준인지 말하지 않은 “8번째 바이트”는 조사 메모로 불충분합니다.

4바이트 VLAN 태그 하나가 링크 헤더에 있으면 ARP 시작은 18이 됩니다. ARP 내부의 상대 위치나 28바이트 길이는 그대로지만 프레임 기준 위치는 4씩 뒤로 갑니다. 따라서 “오프셋 20의 값이 1인지 보자”는 규칙을 태그·링크 형식 확인 없이 적용하면 엉뚱한 바이트를 읽을 수 있습니다. 실제 캡처에서 태그가 보존됐는지도 확인하세요.

주소 길이로 표현한 일반식도 써 볼까요? H를 하드웨어 주소의 바이트 수, P를 프로토콜 주소의 바이트 수라고 하면 ARP 길이 = 8 + 2×H + 2×P바이트입니다. Sender와 Target에 같은 종류의 주소 자리가 하나씩 있으므로 각각 두 번 셉니다. H=6, P=4일 때 8 + 12 + 8 = 28입니다. 이 식은 필드 배치를 읽는 계산이지, 길이 값이 어떤 수여도 현재 구현이 그 메시지를 정상 처리한다는 보증은 아닙니다.

태그 없는 최소 프레임의 18바이트 패딩은 ARP 필드가 아닙니다. 이더넷이 작은 메시지를 담을 때 길이 조건을 맞추는 공간입니다. 헤더 14와 ARP 28만 만든 예시 배열, NIC 처리 뒤 저장된 캡처, FCS 포함 회선 프레임을 같은 길이라고 부르면 안 되는 이유가 여기에 있습니다. IP의 Total Length나 TCP 포트는 이 ARP 메시지 안에 존재하지 않으므로 그런 필드를 끼워 넣어 해석하지 마세요.

7. 캐시는 브로드캐스트를 줄이지만 영구적 진실은 아니다

ARP 캐시는 최근에 알아낸 IPv4와 링크 주소의 대응을 다시 쓸 수 있게 저장하는 표입니다. 다음 데이터 패킷마다 같은 질문을 브로드캐스트하면 불필요한 트래픽이 늘기 때문에 일정 기간 대응을 재사용합니다. 그래서 PCAP에서 데이터 통신만 보이고 직전 ARP가 없더라도 이상하다고 할 수 없습니다.

캐시 항목은 만료·재검증·상태 변화나 설정에 따라 바뀔 수 있습니다. RFC 1122는 오래된 캐시 대응을 없애거나 유효성을 판단하는 메커니즘을 요구합니다. 모든 운영체제가 정확히 같은 고정 시간에 같은 방식으로 삭제한다고 설명하지 않습니다. 정적 항목과 동적 학습도 구별합니다. [6]

원문처럼 ‘수신한 모든 장치가 모든 새로운 IP/MAC 대응을 무조건 추가한다’고 단순화하면 안 됩니다. RFC 826의 기본 수신 알고리즘은 이미 있는 Sender 대응의 갱신과, 자신이 Target일 때 새 대응을 추가하는 조건 등을 구분합니다. 실제 구현은 추가적인 수신·학습 정책을 가질 수 있습니다. 요청을 봄 → 수신자가 받아들임 → 캐시에 반영됨은 각각 확인할 단계입니다.

Linux 공식 문서의 arp_accept 같은 설정도 특정 gratuitous ARP에 대한 항목 생성과 기존 항목 갱신의 조건을 구분합니다. 이 설정 하나가 모든 일반 ARP 수신 동작을 설명하는 것은 아니며 여기서 실제 설정을 변경하지도 않습니다. 다양한 캐시 정책이 존재한다는 보충 근거로 읽습니다. [7]

MAC이 바뀌면 공격이라고 먼저 결론 내리지 마세요. 인터페이스·가상화·장애조치·주소 설정 등 정상 원인이 있을 수 있습니다. 반대로 캐시에 값이 들어 있다는 것만으로 진짜 소유자가 인증되었다고 보지도 않습니다. 단말의 실제 캐시와 변화 시각, 자산 정보, 후속 프레임의 목적지를 대조해야 합니다.

기존 항목 갱신과 새 항목 추가를 나누면 모순이 풀립니다

받은 정보를 적어 두는 개인 수첩을 떠올려 보세요. 이미 적힌 사람의 연락처를 고치는 일과, 모든 낯선 사람을 새로 등록하는 일은 다릅니다. RFC 826의 기본 알고리즘도 기존 Sender 대응이 있으면 갱신하는 단계와, 자신이 Target이고 기존 항목이 없으면 추가하는 단계를 나눕니다. 이 설명은 표준 알고리즘을 읽는 연습이며 모든 현대 운영체제에서 그대로 재현했다고 주장하는 것이 아닙니다. [3]

가상 장치 C가 A의 질문을 받았다고 합시다. C가 이미 A의 IP 대응을 갖고 있다면 갱신을 검토하는 경우와, C에 항목이 없고 C 자신도 Target이 아닌 경우는 다릅니다. “모두가 들으니 모두가 새 항목을 만든다”는 결론이 나오지 않지요. 반대로 “응답만 캐시 학습에 쓰이고 요청은 절대 쓰이지 않는다”는 결론도 틀립니다. 요청에도 Sender의 주소 대응이 들어 있습니다.

Linux 문서의 arp_accept는 아직 표에 없는 장치의 gratuitous ARP를 받아 새 항목을 만들지에 관한 설정입니다. gratuitous는 여기서 통상적인 질문을 기다리지 않고 자기 주소를 알리는 자발적 ARP 문맥으로 이해하세요. 문서상 0은 새 항목을 만들지 않음, 1은 생성, 2는 수신 인터페이스에 설정된 주소와 같은 서브넷의 Sender일 때 생성입니다. 기존 항목의 갱신은 별도로 기술됩니다. 이를 모든 ARP의 일괄 차단 스위치라고 부르거나 운영 환경에 곧바로 변경을 권하지 않습니다. 실제 커널 버전과 다른 수신 정책도 확인해야 합니다. [7]

수첩 비유도 한계가 있습니다. 컴퓨터의 이웃 표에는 인터페이스·상태·재검증 정책이 있고, 동적 항목이 재사용 가능한지의 판단이 단순한 “수첩에 있다/없다”보다 복잡할 수 있습니다. 현재 표만 확보했다면 과거에 어느 응답을 받아 언제 바뀌었는지까지 복원한 것은 아닙니다. 가능하면 변화 시각과 패킷을 함께 기록합니다.

8. ARP 캐시와 스위치 MAC 테이블은 다르다

원문의 응답 설명에서는 스위치의 CAM 테이블을 IP와 MAC의 대응 저장소처럼 설명하는 부분이 있습니다. 여기에는 중요한 구분이 필요합니다. 일반적인 L2 스위치의 MAC 테이블은 MAC·VLAN과 전달 포트의 관계를 다루고, ARP 캐시는 IPv4와 링크 주소의 대응을 다룹니다.

ARP·이웃 대응 표IPv4, MAC과 인터페이스·상태이 출력 링크의 다음 전달 지점에는 어떤 MAC을 쓸까?

CAM은 Content Addressable Memory라는 저장·검색 기술 이름으로 스위치의 MAC 테이블을 설명할 때 자주 사용됩니다. CAM이라는 이름 자체가 IP/MAC 대응을 뜻하는 것은 아닙니다. L3 기능을 가진 스위치나 관리용 IP 인터페이스가 있는 장비는 별도의 ARP 정보도 가질 수 있으므로 ‘스위치에는 ARP 표가 절대 없다’는 반대 방향의 일반화도 피합니다. Cisco의 공식 설명도 브리지의 MAC 표와 라우터·L3 스위치의 ARP 캐시를 구분합니다. [8] [9]

스위치는 일반적으로 들어온 프레임의 출발지 MAC과 포트 등을 이용해 전달 정보를 학습할 수 있습니다. 이때 ARP 메시지의 내부 IPv4 대응을 인증한 것은 아닙니다. 따라서 출발지 MAC을 배운 스위치가 존재한다는 사실을 ‘모든 ARP 주장이 검증되었다’는 보안 기능으로 오해하지 않습니다. 캐시 오염과 방어의 차이는 다음 회차에서 다룹니다.

스위치는 프레임을 전달하고, 호스트는 다음 홉 주소를 정합니다

작은 예로 확인해 보죠. VLAN 10에서 A의 프레임이 포트 1로 들어오면 스위치는 출발지 MAC A를 그 VLAN의 포트 1과 연결해 학습할 수 있습니다. 이후 B의 응답이 포트 2에서 오면 B의 출발지 MAC을 포트 2와 연결합니다. 반면 A의 ARP 캐시에 필요한 항목은 “192.0.2.20에 대해 00:00:5e:00:53:20을 쓸 수 있다”는 대응입니다. 같은 왕복 교환 중에도 각 장비는 서로 다른 질문에 답할 정보를 다룹니다.

같은 숫자 주소가 다른 VLAN이나 다른 가상 네트워크에서 재사용될 수도 있습니다. 그래서 조사 메모에는 IP·MAC뿐 아니라 어느 인터페이스·VLAN·포트의 어느 시점인지 적어야 합니다. 특정 포트에서 프레임이 들어온 사실은 유용하지만, 그 포트 뒤에 가상 스위치나 다른 장비가 있다면 바로 한 사용자까지 특정해 주지는 않습니다. 스위치 표만으로 ARP 수신·인증·응용 처리를 모두 입증할 수 없다는 뜻입니다.

실제 캡처가 준비되었다면 다음 명령을 사용할 수 있습니다. sample-arp.pcap은 예시 파일명이며 이 노트에서 원본 PCAP을 실행한 것이 아닙니다. 첫 명령은 원문의 결합 옵션 표기와 같은 형태입니다. [10]

요약만 보고 정상이라고 종결하지 않습니다. 특히 원문의 요청·응답이 첫째·둘째 레코드였다는 것은 그 실습 자료의 배치입니다. 다른 파일에서도 요청이 항상 첫 패킷이고 관련 응답이 바로 다음 패킷일 것이라고 기대하지 말고, 주소·대상·시각과 관측 범위로 연결합니다.

명령을 먼저 해석하고 결과의 단위를 읽습니다

-tne는 하나의 긴 옵션명이 아니라 짧은 옵션 -t, -n, -e를 묶은 표기입니다. 시각을 빼고, 이름 변환을 억제하고, 링크 헤더 정보를 보여 달라는 뜻입니다. 질문의 대상과 링크 방향을 읽기에는 편하지만 반복 간격을 재려면 시각이 있는 두 번째 예제를 선택해야 합니다. -tttt는 t를 네 번 쓰는 시각 출력 옵션이며 “네 패킷을 보라”는 뜻이 아닙니다.

2026년 11월 2일 직접 확인한 tcpdump 4.99.5 공식 매뉴얼은 -n을 호스트 주소·포트 번호 등을 이름으로 변환하지 않는 옵션으로 설명합니다. 그래서 모든 버전에서 “-n은 호스트만, -nn만 포트까지”라고 구분하지 않습니다. -nn은 n 반복 표기로 예제를 유지하되 실제 설치 버전의 도움말과 매뉴얼을 확인하세요. ARP에는 TCP·UDP 포트가 없으므로 포트 열이 비어 있다는 이유로 잘못된 패킷이라고 판단하지 않습니다. [12]

-r 뒤의 파일명은 읽을 입력입니다. sample-arp.pcap을 타이핑한다고 그 파일이 생기거나 자동으로 실습 입력을 찾아 주지는 않습니다. wireshark 뒤의 파일명도 열 대상이며, 끝의 &는 해당 셸에서 백그라운드 작업으로 실행하는 기호입니다. 프로그램이 설치됐는지와 그래픽 환경이 있는지도 별개입니다. 이 개정에서 두 도구를 실행하거나 이 명령의 실제 출력을 얻지는 않았습니다.

읽는 순서는 간단하게 유지합시다. 먼저 Ethernet Type이 ARP를 가리키는지 확인합니다. 다음으로 Opcode와 Sender·Target의 IP·MAC을 읽고, 관련 요청과 응답의 방향을 비교합니다. 끝으로 후속 데이터와 단말 캐시·스위치 표를 연결합니다. ARP에는 TCP의 스트림 번호처럼 이 요청과 응답을 암호학적으로 묶거나 식별하는 거래 번호가 없습니다. 같은 대상 질의가 반복되면 “바로 다음 줄”보다 주소·시각·관측 범위로 관련성을 판단해야 합니다.

10. 패킷에서 관측한 주장과 실제 처리 결과를 구분한다

A가 B의 MAC을 묻는 요청과 B의 주소라고 주장하는 응답을 보았다면, 우선 요청·응답의 필드와 방향을 확인한 것입니다. A가 실제로 그 대응을 받아들였는지는 단말 캐시나 이어지는 데이터 프레임의 목적지로 더 검증합니다. B의 실제 소유자와 맞는지는 자산·스위치·단말 정보가 필요합니다.

예를 들어 응답 뒤 A가 B의 MAC을 목적지로 하는 프레임을 보냈다면 그 대응을 사용한 정황이 됩니다. 그래도 응용 요청의 성공이나 파일 전송·명령 실행까지 입증한 것은 아닙니다. 같은 시간대의 IP·전송·응용 계층과 서버·단말 기록으로 넘어가야 합니다.

ARP에는 일반적인 기본 메시지 자체로 발신자의 주장을 암호학적으로 인증하는 기능이 없습니다. 이 점은 다음 회차의 캐시 오염 분석과 연결됩니다. 이번에는 공격 성공을 가정하지 않고, ‘관측된 대응’, ‘캐시에 반영된 대응’, ‘실제 자산 정보’를 나누어 쓰는 습관을 익힙니다.

192.0.2.10이 192.0.2.20의 링크 주소를 질의했고, 이에 대응하는 ARP Reply가 관측되었다. 응답은 192.0.2.20이 문서용 MAC 00:00:5e:00:53:20을 사용한다고 알렸다. 이 가상 사례에서 단말 캐시의 반영과 실제 자산 소유자는 별도 확인 대상이다. 관측한 필드와 후속 프레임, 캐시·포트·자산 정보를 대조한다.

ARP는 기본적으로 같은 링크의 주소 해석이며 라우터가 일반 IP 패킷처럼 원래의 ARP 요청을 인터넷 경로로 계속 전달하지 않습니다. 그러나 프록시 ARP나 L2 확장 같은 구성을 무시하고 물리적으로 한 방에 있는 장치만 영향받는다고 단정할 수도 없습니다. 실제 브로드캐스트 범위와 전달 구성을 확인합니다. [8]

조건을 바꾸며 보고 문장을 다듬어 봅시다

가상 캡처에서 요청 두 개와 응답 한 개를 보았다고 해 보세요. 첫 요청에는 응답이 없었고 두 번째에만 답했다고 바로 셀 수 있을까요? 캡처 손실이나 시간 범위, 반복 요청 사이의 지연, 반환 경로를 확인해야 합니다. 요청 하나와 응답 하나가 화면에서 인접하다는 이유만으로 처리 순서나 원인을 확정하지 않습니다.

여기에 A의 같은 시각 캐시가 B의 MAC을 가리켰다는 자료를 추가하면 “해당 시점의 캐시에 이 대응이 있었다”는 사실을 쓸 수 있습니다. 뒤이어 A가 그 MAC으로 IPv4 데이터를 보냈다면 “후속 프레임에서 대응을 사용한 정황”도 보강됩니다. 그래도 패킷을 만든 프로그램과 실제 사용자의 신원은 단말 활동·인증 기록이 필요하고, HTTPS 서버가 요청을 정상 처리했는지는 서버 기록이나 합법적으로 확보한 복호화 정보가 필요합니다. 증거가 하나 늘 때마다 어떤 질문에 답했는지를 분명히 합시다.

프록시 ARP는 다른 장치가 대신 답해 프레임을 받아 전달하는 구성입니다. 그래서 응답의 MAC이 예상한 최종 호스트의 MAC과 다르다고 즉시 공격이라고 할 수 없습니다. 실제 프록시 설정과 경로, 예상 전달 결과를 확인해야 합니다. 반대로 가능한 정상 원인이 있다는 이유만으로 위조 의심을 종결하지도 않습니다. 관측 사실·가능한 원인·확인할 설정을 나누어 남기면 됩니다. [8]

11. IPv6는 ARP를 사용하지 않는다

IPv6에서는 Neighbor Discovery가 이웃의 링크 주소 확인과 라우터 발견, 도달성 관리 등의 기능을 수행합니다. 주소 확인에는 Neighbor Solicitation, NS와 Neighbor Advertisement, NA가 쓰이며 각각 ICMPv6의 메시지 종류 135와 136입니다. NDP 전체를 하나의 ICMPv6 타입이라고 설명하면 부정확합니다. [11]

ARP의 ‘누가 이 IPv4 주소를 쓰는가’와 비슷한 학습 질문이 있지만 패킷 형식과 수신 범위는 다릅니다. IPv6의 이웃 확인에서는 멀티캐스트가 사용될 수 있고, IPv4 ARP의 브로드캐스트 프레임·Opcode·Sender/Target 형식을 그대로 적용하지 않습니다. NS·NA를 발견했다고 모든 IPv6 이웃 동작이 단순히 ARP와 같다고 가정하지 마세요.

암호화된 응용 통신에서도 이런 링크·이웃 정보는 경로와 관측 범위를 이해하는 데 도움이 됩니다. 그러나 ARP나 NS·NA를 읽는 것으로 HTTPS 본문의 의미를 복원할 수는 없습니다. 단말·스위치·서버 기록과 연결하여 어느 계층의 질문에 답했는지 분명히 합니다.

이번 단계에서는 IPv4의 주소 해석을 이해한 뒤 “같은 문제를 IPv6가 다른 메시지 체계로 푼다”는 연결만 잡으면 충분합니다. NDP는 Neighbor Discovery Protocol을 가리키는 이름으로도 쓰입니다. Router Solicitation·Advertisement처럼 라우터를 찾는 메시지도 그 체계에 들어 있으므로 NS·NA 두 종류만으로 전체 기능을 설명하지 않습니다. IPv6의 구체적인 헤더·수신 주소·옵션·관측 한계는 첫째 날 실습과 IPv6 분석에서 이어갑니다. [11]

12. 이번 회차의 증거 구분

패킷으로 확인 가능한 사실

관측된 Ethernet 방향과 ARP Opcode, Sender·Target 필드, 확보된 바이트와 길이, 요청·응답의 시간·대상 관계, 이후 관측된 프레임의 MAC 사용입니다.

단독으로 확정할 수 없는 부분

MAC과 실제 사용자·프로그램의 신원, 수신자가 캐시에 반영했는지, 주장의 진위, 보이지 않는 응답과 경로, 암호화 본문과 응용 처리 성공입니다.

함께 확인할 자료

단말 ARP·이웃 표와 경로 설정, 스위치 MAC·VLAN·포트 정보, DHCP·자산·가상화 이력, 수집 위치·손실·NIC 처리, 서버·단말 활동 로그입니다.

13. 복습 — 누구에게 무엇을 묻고 있는가

아래는 자체 구성한 복습 문제입니다. 교재 원리를 확인하는 자체 복습이며, 워크북 연계는 뒤의 실습 링크에서 따로 다룹니다. 원본 PCAP을 실행한 결과가 아닙니다.

질문 1: A가 외부 서버 198.51.100.20에 보낼 때, 같은 링크의 기본 게이트웨이를 선택했다면 누구의 MAC을 찾을까요?

해설: 출력 링크에서 사용할 게이트웨이의 MAC입니다. 이후 프레임 목적지 MAC은 게이트웨이이고 IP 목적지는 외부 서버입니다. 실제 환경에서는 라우팅 테이블과 정책을 먼저 확인합니다.

질문 2: 요청에서 Ethernet 목적지는 ff:ff:ff:ff:ff:ff인데 ARP Target MAC은 모두 0입니다. 서로 모순일까요?

해설: 아닙니다. 바깥 프레임의 배달 대상과 안쪽 질의 필드는 역할이 다릅니다. THA는 아직 모르는 주소의 자리이며 이 일반 요청 예제에서 0을 사용했습니다. 모든 ARP 요청의 유일한 정상값으로 일반화하지 않습니다.

질문 3: Ethernet Type 0x0806과 ARP Protocol type 0x0800은 왜 다를까요?

해설: 전자는 뒤에 ARP 메시지가 온다는 뜻이고, 후자는 그 ARP가 IPv4 주소의 대응을 다룬다는 뜻입니다. 두 필드를 같은 계층의 같은 질문으로 읽지 않습니다.

질문 4: Ethernet/IPv4 ARP의 길이는 어떻게 계산할까요?

해설: 고정 부분 8 + Sender MAC 6 + Sender IP 4 + Target MAC 6 + Target IP 4 = 28바이트입니다. 태그 없는 Ethernet 헤더 14까지 합치면 42이고, 최소 회선 프레임에는 패딩 18과 FCS 4를 더해 64바이트가 됩니다.

질문 5: 데이터 패킷 바로 앞에 ARP가 없다면 위조되었을까요?

해설: 캐시를 재사용했거나 이전 수집 구간·다른 관측 위치에서 해석이 끝났을 수 있습니다. 정적 항목도 가능합니다. 캐시와 경로·수집 조건을 확인하기 전에 공격이라고 단정하지 않습니다.

질문 6: 응답을 본 스위치가 MAC을 배웠다면 그 IP 소유자가 인증되었을까요?

해설: MAC 전달 표의 포트 학습과 ARP의 IPv4/MAC 대응은 다른 기능입니다. 해당 값이 진짜 자산인지와 수신 단말의 캐시 반영은 별도 증거로 확인해야 합니다.

질문 7: MAC이 바뀌면 NIC를 교체했거나 공격이 발생한 것일까요?

해설: 주소 설정·프라이버시·가상화·장애조치 같은 다른 원인도 있습니다. OUI나 주소 변화 하나만으로 사용자의 신원·원인·공격자 수준을 확정하지 않고 이력과 자산 자료를 대조합니다.

질문 8: IPv6에서도 ARP Opcode 1과 2를 찾으면 될까요?

해설: IPv6는 Neighbor Discovery의 ICMPv6 메시지를 봅니다. NS·NA의 타입과 옵션, 대상·수신 범위는 ARP와 다릅니다. 이름만 바꾼 동일 형식이라고 해석하면 안 됩니다.

질문 9: A는 192.0.2.10/25이고 목적지는 192.0.2.200입니다. 다른 구체 경로는 없고 같은 링크의 기본 게이트웨이를 사용한다면 누구에게 ARP하나요?

해설: /25의 마지막 마스크 값은 128입니다. 10 AND 128은 0, 200 AND 128은 128로 연결 경로가 다릅니다. 기본 게이트웨이의 MAC을 알아냅니다. 앞 세 바이트가 같다는 이유만으로 목적지에 직접 ARP하지 않습니다.

질문 10: 단일 VLAN 태그가 보존된 Ethernet에서 ARP Opcode와 TPA의 프레임 기준 위치는 어디인가요?

해설: ARP 시작은 18입니다. Opcode의 상대 위치 6~7에 18을 더해 24~25, TPA의 상대 위치 24~27에 18을 더해 42~45가 됩니다. 주소 크기는 H=6, P=4라고 가정했습니다. 태그 없는 값 20~21과 38~41을 그대로 쓰면 안 됩니다.

질문 11: C는 A의 요청을 보았지만 기존 A 항목도 없고 질의 대상도 아닙니다. 모든 수신자가 새 항목을 만든다고 쓸 수 있나요?

해설: 그렇게 일반화할 수 없습니다. RFC 826 기본 알고리즘은 기존 대응 갱신과 자신이 Target일 때의 추가를 구분합니다. 실제 C의 정책과 캐시를 확인해야 합니다. 요청을 들었다는 관측을 새 항목 생성이라는 결과로 바꾸지 않습니다.

질문 12: ARP Sender IP가 0.0.0.0이면 악성인가요?

해설: 그 값만으로 판단할 수 없습니다. 주소 사용 전 충돌 검사를 하는 Probe는 SPA를 0으로, TPA를 검사할 주소로 둘 수 있습니다. Opcode·브로드캐스트 여부·앞뒤 주소 설정 시점과 관련 기록을 확인합니다. 정당한 형식이라는 사실도 모든 발신 의도를 보증하지 않습니다.

질문 13: 응답자가 알린 MAC을 A가 사용한 프레임을 보았습니다. 웹 로그인이 성공했다고 보고할 수 있나요?

해설: 이 관측은 링크 대응 사용을 지지합니다. 로그인 성공은 응용·인증 단계의 결과이므로 서버·인증 기록이나 읽을 수 있는 관련 응답이 필요합니다. 같은 통신과 시각인지도 맞춰야 합니다. 링크 전달과 응용 성공을 구별합니다.

질문 14: tcpdump -r sample-arp.pcap -tne의 각 부분과 시간 분석의 한계는 무엇인가요?

해설: tcpdump는 도구, -r 다음은 저장 입력, -tne는 -t·-n·-e입니다. 시각을 숨기고 이름 변환을 억제하며 링크 정보를 출력합니다. 시각이 없으므로 그 요약만으로 지연을 계산할 수 없습니다. -tttt를 쓰는 예제와 시간대·수집 기준을 확인합니다. 이 답은 실제 실행 출력이 아닙니다.

질문 15: 센서 C에서 브로드캐스트 요청만 보이고 응답이 없습니다. B가 꺼져 있다고 확정할 수 있나요?

해설: 현재 범위에서 응답을 찾지 못했다고 씁니다. 유니캐스트 반환 경로가 C를 지나지 않거나 미러 방향·수집 시간·손실 때문에 빠졌을 수 있습니다. A 포트의 양방향 수집과 단말 캐시·장비 상태를 대조해 실제 무응답과 관측 누락을 나눕니다.

질문 16: 스위치 표에 B의 MAC과 포트가 있고 A의 ARP 캐시에 B의 IP와 MAC이 있습니다. 두 표는 같은가요?

해설: 서로 다릅니다. 전자는 해당 VLAN의 목적지 MAC 프레임을 어느 포트로 보낼지, 후자는 출력 인터페이스에서 해당 IPv4 이웃에 어떤 MAC을 쓸지에 답합니다. 각각 관측한 시점과 문맥을 남기고 자산·가상화 정보로 소유자를 검증합니다.

워크북 연계 실습

브로드캐스트 목적지와 아직 모르는 Target MAC을 별도로 읽습니다. ARP 요청과 응답 비교에서 단계별 설명과 복습을 읽을 수 있습니다. 이 페이지의 기존 자체 예시는 그대로 유지하며, 원본 PCAP을 실행한 출력으로 제시하지 않습니다.

2026년 11월 1일의 기존 검토에는 첫째 날 워크북과 PCAP 여섯 개, 총 621기록을 오프라인 대조한 기록이 있습니다. 이번 개정은 그 기록을 참고했지만 원본 PCAP 재분석이나 Wireshark·tcpdump 실행을 반복하지 않았습니다. 교재 페이지의 설명 대조, 기존 오프라인 검토, 실제 장비·GUI 재현은 서로 구분합니다. 원본 입력은 공개 페이지에 포함하지 않습니다.
