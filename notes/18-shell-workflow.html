1. 명령줄의 목표는 관심 있는 자료를 반복해서 찾는 것

캡처가 커지면 모든 패킷을 화면에서 하나씩 읽기는 어렵습니다. 명령줄에서는 조건으로 범위를 좁히고, 필요한 정보를 추출한 뒤, 같은 절차를 다시 실행할 수 있습니다. 이번 목표는 긴 명령을 암기하는 것이 아니라 각 단계가 무엇을 받아 무엇을 내보내는지 설명하는 능력입니다. 이 능력은 패킷 외에 서버·인증 로그를 정리할 때도 사용할 수 있습니다.

GUI는 흐름을 시각적으로 탐색하고 선택한 패킷을 자세히 읽는 데 유용합니다. 명령줄은 큰 자료의 반복 추출·집계를 자동화하는 데 유용합니다. GUI는 큰 파일을 전혀 처리할 수 없다거나 tcpdump가 언제나 가장 빠르다고 일반화하지 않습니다. 파일 형식·필터·디스크·해석 옵션·재조립·메모리 조건에 따라 성능이 달라집니다.

예를 들어 메타데이터에서 외부 방향 전송량 증가를 발견했다면 파일 반출을 가설로 세울 수 있습니다. 그러나 전송량이나 포트 하나만으로 FTP 업로드·피싱·악성코드 전달을 확정하지 않습니다. 관련 패킷, DNS·메일·단말·서버 로그를 찾아 가설을 검증합니다. 암호화되었거나 수집하지 않은 내용은 명령줄로도 새로 만들어 낼 수 없습니다.

이번 회차의 범위와 실행 구분

파이프·페이저·cut·awk·sort·uniq·head·wc를 다룹니다. 이 회차의 tcpdump·TShark 명령은 사용법 예시입니다. 추가 확보한 첫째 날 PCAP은 별도 오프라인 해석으로 검증했으며 해당 명령을 실행한 출력과 혼동하지 않습니다. 대신 문서용 주소로 만든 가상 텍스트 여섯 줄을 실제 텍스트 도구에 넣어 추출·집계 결과를 검산했습니다. 이는 실제 네트워크 사건이나 원본 PCAP의 실행 결과가 아닙니다. 바이너리 패킷 스트림과 검색·치환 도구는 다음 회차로 나눕니다.

“이 파일에서 무엇을 찾고 싶나요?”부터 시작해 볼게요

서버의 외부 통신이 갑자기 늘었다고 해 봅시다. 화면을 오래 내려 보는 대신 “어떤 출발지 포트 표기가 자주 등장했는가?”라는 작은 질문부터 정할 수 있습니다. 필요한 항목을 고르고 같은 값끼리 모은 뒤 개수를 세면 됩니다. 다만 질문이 “어떤 프로그램이 파일을 보냈는가?”라면 포트 빈도만으로는 답할 수 없겠죠. 명령을 연결하기 전에 답하려는 질문과 필요한 자료를 정하는 것이 첫 단계입니다.

우편물을 정리하는 작업을 떠올려 보세요. 봉투에서 주소표를 떼어 모으는 일은 추출, 같은 주소끼리 놓는 일은 정렬, 주소별 장수를 세는 일은 집계에 가깝습니다. 하지만 봉투 장수가 곧 사람 수나 물건 수는 아닙니다. 같은 사람이 여러 번 보냈을 수도 있으니까요. 텍스트에서도 한 줄이 패킷인지, 연결인지, 추출한 항목인지 먼저 알아야 숫자의 뜻을 설명할 수 있습니다. 실제 파이프는 봉투를 물리적으로 옮기지 않으며 프로그램 사이에 바이트를 전달한다는 점에서 비유와 다릅니다.

이번에는 인쇄 144~154쪽의 학습 범위와 그림을 직접 대조했습니다. 정규표현식은 뒤 회차에서 이어지고, 이번 목표는 파이프·필드·정렬·빈도의 관계입니다. 기존 워크북과 PCAP 오프라인 검증 기록은 참고했지만 이번에 원본 PCAP이나 워크북을 다시 실행하지 않았습니다. 아래 자체 텍스트는 이번에도 실제 도구에 넣어 재검산했습니다.

2. 파이프는 화면을 복사하는 장치가 아니다

프로그램에는 입력을 받는 표준 입력(stdin), 일반 결과를 쓰는 표준 출력(stdout), 진단·오류를 쓰는 표준 오류(stderr)라는 통로가 있습니다. Bash 같은 셸에서 A | B라고 쓰면 A의 표준 출력을 B의 표준 입력에 연결합니다. B는 화면의 그림이 아니라 전달된 데이터를 읽습니다. [1]

셸은 명령을 실행하고 연결을 해석하는 프로그램입니다. 세로 막대 |는 셸의 문법이며 tcpdump나 cut의 옵션이 아닙니다. 여러 명령이 데이터를 주고받으며 동작할 수 있으므로, 앞 프로그램이 파일을 전부 화면에 쓴 후 사람이 다음 명령을 실행하는 것과도 다릅니다.

tcpdump가 파일 형식을 알리는 진단을 화면에 보여도 그 문장이 반드시 파이프의 다음 명령으로 전달되는 것은 아닙니다. 반대로 오류를 결과와 합쳐 전달하면 필드 추출이나 행 수에 섞일 수 있습니다. 입력 파일이 없어서 해석에 실패한 결과를 ‘관심 패킷0개’로 보고하지 않도록 오류와 성공 상태를 확인합니다.

이 노트의 명령은 Unix 계열의 텍스트 처리와 Bash 문맥을 사용합니다. 현대 PowerShell도 파이프를 널리 활용하며, cmdlet 사이에는 객체를 전달할 수 있습니다. Windows에서는 파이프를 거의 쓰지 않는다는 과거 평가를 현재의 일반 규칙으로 옮기지 않습니다. 같은 기호가 보여도 셸·명령·자료형이 같다는 뜻은 아닙니다. [2]

같은 화면에 보인 두 줄도 서로 다른 통로일 수 있습니다

표준 출력과 표준 오류는 자료의 형식 이름이 아니라 프로그램이 사용할 수 있는 별도 통로입니다. 일반 출력의 파일 설명자는 1, 오류 통로는 2입니다. 파일 설명자는 운영체제가 열린 입출력 통로를 구분하는 번호라고 생각하면 됩니다. 터미널에 둘 다 연결되어 있으면 사람이 보기에는 한 화면에 섞여 나타납니다. 그렇다고 다음 명령도 둘을 모두 받는 것은 아닙니다.

다음은 PCAP을 읽지 않고 Bash가 두 통로로 각각 한 줄을 쓰게 만든 독립 예제입니다. printf는 지정한 형식으로 텍스트를 출력하고 \n은 이 형식 안에서 줄바꿈을 만듭니다. 중괄호는 명령을 묶으며 >&2는 해당 출력을 표준 오류로 보냅니다.

# Bash에서 실행하는 합성 텍스트 예제
{ printf 'data\n'; printf 'diagnostic\n' >&2; } | wc -l
# wc의 표준 출력: 1
# diagnostic은 별도의 표준 오류로 남음

진단을 없앴거나 집계에 합친 예제가 아닙니다. 오른쪽 wc가 받은 것은 data와 그 줄바꿈뿐입니다. 입력 통로와 별개로 각 명령의 성공 여부도 확인해야 하며, 뒤에서 실패를 의도적으로 만든 예제로 다시 살펴보겠습니다. [1]

3. 많은 출력을 읽기: more와 less

디렉터리 목록을 길게 출력하는 ls -al에서 -a는 점으로 시작하는 항목도 포함하고 -l은 상세 목록을 요청합니다. 출력이 길면 ls -al | more처럼 페이저로 연결해 읽을 수 있습니다. 페이저는 텍스트를 화면 단위로 탐색하는 프로그램입니다.

# PCAP이 있을 때의 사용법 예시 — 이 노트에서 실행한 PCAP 결과가 아님
tcpdump -r sample.pcap -n
tcpdump -r sample.pcap -n -c 10
tcpdump -r sample.pcap -n -X | less

-r은 저장 파일 읽기, -n은 주소 등의 이름 변환 억제, -c 10은 처리할 패킷 수 제한입니다. -X는 보통 링크 헤더를 제외한 바이트를16진수와ASCII로 표시합니다. 패킷 열 개가 출력 열 줄이라는 뜻은 아닙니다. 1500바이트 패킷의 덤프는 여러 줄이 될 수 있어 개수 제한과 페이지 탐색은 서로 다른 문제를 해결합니다. [3]

페이저의 기본 탐색 — 실제 키 동작은 설치 도움말도 확인
키용도주의
Space / Enter다음 화면 / 다음 한 줄읽는 위치를 이동할 뿐 패킷을 다시 수집하지 않음
/문자열앞으로 검색표시된 텍스트에서 찾는 것이며 패킷 구조 검색과 다름
less의 b이전 화면저장·버퍼 조건과 구현에 따른 제한 확인
less의 ?문자열뒤로 검색정규표현식의 의미는 다음 학습과 연결
less의 q종료끝에 도달해도 실행 상태가 남을 수 있음

less를 GNU가 more를 다시 쓴 도구라고 단순히 설명하지 않습니다. 독립적인 페이저이며 공식 도움말과 프로젝트 설명을 확인합니다. 또한 ‘more는 어떤 환경에서도 뒤로 갈 수 없다’는 주장도 피합니다. 구현·파일/파이프 입력에 따라 기능이 달라질 수 있습니다. 이 환경에서는 less의 공식 내장 도움말로 위 키를 대조했으며, 원본 PCAP을 화면에서 탐색한 것은 아닙니다. [4]

출력을 줄이는 것과 읽는 속도를 조절하는 것은 다릅니다

-c 10은 tcpdump가 읽거나 받는 패킷 개수를 제한하고, less는 전달받은 텍스트를 탐색하게 합니다. -X처럼 한 패킷이 여러 줄이 되는 출력이라면 둘을 함께 쓸 이유가 있습니다. 반면 전체 파일에서 포트 빈도를 계산하려는데 먼저 10개로 잘라 버리면, 결과의 분모도 최대 그 범위로 줄어듭니다. 화면을 편하게 보려고 넣은 옵션이 조사 범위까지 바꾸지 않았는지 확인하세요.

페이저에서 찾은 단어는 표시 텍스트에서 발견한 단서입니다. 예를 들어 ASCII 덤프에서 문자열을 찾았다고 응용의 완성된 메시지 전체를 재조립한 것은 아닙니다. 텍스트가 끊겨 있거나 암호화되었다면 검색 범위도 달라집니다. 앞의 스트림·객체 분석에서 배운 범위 구분을 그대로 적용할 수 있습니다.

4. 검산할 가상 텍스트를 먼저 정의한다

아래는 tcpdump 요약과 비슷한 모양을 가진 자체 구성 텍스트입니다. 실제 패킷을 해석해 얻은 출력이 아닙니다. 각 줄 끝에는 줄바꿈이 있고, 항목 사이는 하나의ASCII 공백입니다. 이 여섯 줄을 example.txt에 저장했다고 가정합니다.

12:00:00.000001 IP 192.0.2.10.50000 > 198.51.100.20.443: Flags [S], length 0
12:00:00.000002 IP 192.0.2.10.443 > 198.51.100.20.443: Flags [S], length 0
12:00:00.000003 IP 192.0.2.10.50000 > 198.51.100.20.443: Flags [S], length 0
12:00:00.000004 IP 192.0.2.10.53 > 198.51.100.20.443: Flags [S], length 0
12:00:00.000005 IP 192.0.2.10.443 > 198.51.100.20.443: Flags [S], length 0
12:00:00.000006 IP 192.0.2.10.443 > 198.51.100.20.443: Flags [S], length 0

첫째 항목은 시각, 둘째는 IP, 셋째는 출발지 표기, 넷째는 화살표, 다섯째는 목적지 표기입니다. 마지막 점 뒤의 숫자를 포트로 읽을 수 있도록 만든 제한된IPv4 형식입니다. 목적지 끝의 콜론은 표기의 일부이며 주소나 포트 값 자체와 구분합니다.

50000·443·53이라는 숫자는 이 텍스트에 넣은 출발지 포트 표식입니다. 443이 있다고 HTTPS를,53이 있다고 DNS를 확정하지 않습니다. 같은 출발지 포트가 반복되어도 연결 수·사용자 수·공격 횟수와 같지 않습니다.

첫 줄을 다섯 칸으로 읽어 보겠습니다

192.0.2.10.50000은 이 예제에서 IPv4 주소 192.0.2.10과 포트 표식 50000을 붙인 항목입니다. >는 표시상의 방향 기호이고, 뒤의 198.51.100.20.443:은 목적지 항목입니다. 여기서 콜론을 포함한 문자열과 프로토콜의 숫자 필드는 다릅니다. 표기를 통째로 센 것인지 숫자 값만 정리해 센 것인지 기록해 두세요.

여섯 줄에는 출발지 주소 하나와 포트 표식 세 종류를 넣었습니다. 따라서 “주소별 빈도”로 묶으면 하나의 묶음에 6개, “출발지 포트 표식별 빈도”로 묶으면 세 묶음에 3·2·1개가 됩니다. 같은 입력에서도 무엇을 묶음의 기준으로 삼았는지에 따라 답이 달라집니다. 이 예제를 실제 연결 여섯 개나 공격 여섯 번이라고 부르지는 않습니다.

5. cut -c: 문자 위치를 고르면 구조를 아는 것은 아니다

cut은 각 텍스트 줄에서 지정한 부분을 추출합니다. cut -c 17-40 example.txt는1부터 세는 문자 위치에서17번째부터40번째까지를 선택합니다. 양끝을 포함하므로 길이는 40−17+1=24자리입니다. 여기서는ASCII만 사용해 문자·바이트·화면 폭의 혼동을 피합니다. 탭·한글·결합 문자까지 화면의 고정 열과 같다고 생각하지 않습니다. [5]

가상 텍스트의 시각15자리 뒤 공백 한 자리가 있으므로 IP가17번째에서 시작합니다. 첫 줄에 대해 실제 텍스트 도구로 검산한 추출값은 다음과 같습니다.

IP 192.0.2.10.50000 > 19

끝의 19는 목적지 주소의 앞부분입니다. 출발지 표기가 짧은 네 번째 줄에서는 IP 192.0.2.10.53 > 198.5가 됩니다. cut은 출발지가 어디서 끝나는지 몰라 같은24자리를 기계적으로 잘랐습니다. 명령이 성공 종료했다고 원하는 필드를 정확히 얻었다는 뜻은 아닙니다.

고정 위치 추출은 형식이 정말 고정되어 있을 때 유용합니다. 주소 길이·시간 출력·IPv6·상세 옵션이 바뀌면 위치도 바뀔 수 있습니다. 중간 결과를 보기 전에 큰 파일 전체의 통계로 넘어가지 않는 이유입니다.

문자 위치와 화면의 칸도 구별해 주세요

탭 한 개는 화면에서 여러 칸처럼 보일 수 있고, 한글 한 글자도 UTF-8에서는 여러 바이트입니다. 이 환경의 GNU Coreutils 9.7에서는 가를 cut -c 1에 넣었을 때 완전한 한글 대신 첫 바이트만 남았습니다. 현재 공식 문서의 문자 설명과 설치 구현의 지원 범위가 같다고 가정하지 않는 이유입니다. 이 회차의 위치 예제는 ASCII로 제한했고, 한글 문자열 처리에 그대로 적용하지 않습니다. 도구 버전·인코딩을 확인한 뒤 목적에 맞는 문자 처리 방법을 선택하세요.

6. cut -f와 -d: 구분자를 정하고 필드를 선택한다

필드는 구분자로 나눈 항목입니다. cut의 기본 필드 구분자는 탭이므로 이 텍스트의 공백과 다릅니다. -d ' '로 공백 한 문자를 지정하고, -f 3,5로 셋째·다섯째 필드를 고릅니다. 따옴표는 공백을 셸에서 사라지거나 분리되지 않는 하나의 인수로 전달하기 위해 씁니다.

cut -d ' ' -f 3,5 example.txt
# 첫 줄에 대한 텍스트 검산 결과
192.0.2.10.50000 198.51.100.20.443:

첫 줄에서는 원하는 주소·포트 표기가 나옵니다. 하지만 공백이 두 개면 빈 필드가 생길 수 있고, 탭이 섞이면 다른 결과가 됩니다. 구분자가 없는 줄은 기본적으로 그대로 출력될 수 있습니다. cut의 -s는 구분자가 없는 줄을 제외하는 옵션이지만, 올바른 패킷 줄인지 검증하는 기능은 아닙니다.

원문의 순서 설명 수정 — 2026년 11월 2일 재확인

GNU cut은 필드 목록에 어떤 순서로 번호를 쓰더라도 선택된 내용을 입력에 등장하는 순서로 한 번씩 출력합니다. -f 5,3으로 적는다고 목적지·출발지 순서로 뒤집히지 않습니다. -f 3-5처럼 범위도 지정할 수 있지만 항목 재배열 기능과 다릅니다. 순서를 바꾸려면 awk처럼 그 기능을 갖춘 도구를 사용합니다. [5]

공백을 하나만 바꾸어도 “셋째 필드”가 달라집니다

이번에는 패킷처럼 보이는 긴 줄 대신 항목 이름만 둔 짧은 텍스트로 비교해 볼게요. 아래 표의 ␠는 ASCII 공백 한 개, ⇥는 탭 한 개를 눈에 보이게 적은 기호입니다. 실제 입력에는 이 그림 기호를 넣지 않고 공백이나 탭을 넣었습니다.

합성 입력의 공백·탭을 바꾼 실제 텍스트 검산
입력을 보이게 적은 것cut -d ' ' -f 3기본 awk의 $3
time␠IP␠src␠>␠dstsrcsrc
time␠␠IP␠src␠>␠dstIPsrc

두 번째 줄에서 cut은 time 뒤의 두 공백 사이에 빈 필드를 하나 만듭니다. 그러면 IP가 셋째 필드가 됩니다. 세 번째 줄에는 지정한 공백 구분자 자체가 없어서 기본 cut이 줄 전체를 통과시켰습니다. 같은 화면처럼 보이는 입력도 실제 바이트가 다르면 결과가 달라집니다. [5]

printf 'ERROR\n' | cut -d '.' -f 5도 ERROR를 그대로 통과시킵니다. 점이 없는 줄이기 때문입니다. cut -s -d '.' -f 5로 바꾸면 그 줄은 제외되지만, 점이 다섯 항목을 올바르게 구분하는지까지 확인한 것은 아닙니다. “원치 않는 줄이 사라졌다”와 “남은 값이 올바른 포트다” 사이에는 검증 단계가 더 있습니다.

7. cut을 두 번 연결해 포트만 추출한다

먼저 셋째 필드를 얻고, 그 결과를 점으로 다시 나누겠습니다. 192.0.2.10.50000을 점으로 나눈 다섯 항목은 192, 0, 2, 10, 50000입니다. 그래서 두 번째 cut의 -d '.' -f 5가 마지막 포트 표식을 고릅니다.

cut -d ' ' -f 3 example.txt | cut -d '.' -f 5
# 자체 텍스트에 대한 검산 결과
50000
443
50000
53
443
443

한 명령이 출발지 필드를 만들고 다음 명령이 그 필드 안의 항목을 고릅니다. 파이프가 길어져도 단계별 입력·출력을 확인하면 이해할 수 있습니다. 실제 PCAP에서는 tcpdump -r sample.pcap -n의 텍스트를 앞에 연결할 수 있지만, 그것을 실행한 결과가 위 목록이라는 뜻은 아닙니다.

이 방법에는 강한 전제가 있습니다. IPv4의 네 옥텟 뒤에 점과 포트를 붙인 형식이어야 하고, 해당 줄에 포트가 있어야 하며, 셋째 필드가 출발지여야 합니다. ICMP·ARP·IPv6·단편·다른 타임스탬프·옵션·터널에서는 성립하지 않을 수 있습니다. 점 구분 결과 하나를 프로토콜 구조를 해석한 포트와 같은 증거로 취급하지 않습니다.

두 번째 cut은 이미 줄어든 자료만 받습니다

첫 cut이 출발지 표기만 남겼다면 두 번째 cut은 원래 시각·방향·목적지를 알 수 없습니다. 원본 PCAP이 바뀌는 것은 아니지만, 이 파생 출력만 보관하면 시간 순서나 상대 주소를 다시 연결하기 어려워집니다. 포트 빈도로 관심 항목을 찾은 뒤 원래 기록으로 돌아갈 수 있도록 파일 식별 정보와 추출 조건을 함께 남기는 이유입니다.

만약 출발지가 포트 없는 주소 192.0.2.10뿐이라면 점으로 나눈 다섯째 항목이 없습니다. 결과의 빈 줄을 포트 0으로 바꾸지 마세요. 원래 포트가 없는 프로토콜인지, 요약 형식이 바뀌었는지, 필드를 잘못 고른 것인지부터 확인합니다. 누락·없음·숫자 0은 서로 다른 상태입니다.

8. awk는 ‘조건에 맞는 줄에서 무엇을 출력할까’를 적는다

awk는 Aho·Weinberger·Kernighan의 이름에서 따온 텍스트 처리 언어입니다. 단순한 추출부터 조건·계산·집계까지 표현할 수 있습니다. 이번에는 패턴 { 동작 }이라는 기본 형태만 사용합니다.

awk '/ IP / { print $3 }' example.txt

/ IP /는 공백·IP·공백을 포함하는 줄에 적용할 조건이고, 중괄호 안의 print $3은 셋째 필드를 출력하는 동작입니다. $3은 이 문맥에서 awk의 필드 참조입니다. 작은따옴표로 프로그램을 감싸 셸이 먼저 $3을 확장하지 않게 합니다. $0은 줄 전체이며, NF는 필드 개수를 나타냅니다. [6]

기본 awk는 연속된 공백과 탭을 필드 구분에 사용하고 앞뒤 공백도 처리합니다. 공백 한 문자마다 필드를 나누는 cut과 차이가 있습니다. awk -F ':' '{ print $1 }'처럼 -F로 구분자를 지정할 수도 있습니다. awk '{ print $5, $3 }' example.txt라면 출력 순서를 목적지·출발지로 직접 지정합니다.

그러나 awk도 여기서는 IP 패킷 해석기가 아닙니다. / IP /가IPv6를 포함한다고 보장하지 않고, 페이로드에 우연히 같은 문자열이 있을 수도 있습니다. awk로 공백 문제를 줄였다고 필드 위치의 모든 가정이 사라지는 것은 아닙니다. 실제 입력과 조건을 먼저 검토해야 합니다.

조건과 동작을 각각 소리 내어 읽어 보세요

awk '/ IP / { print $3 }' example.txt는 “공백-IP-공백이 있는 줄을 만나면, 그 줄의 셋째 필드를 출력한다”로 읽으면 됩니다. 여기서 패턴은 정규표현식이라는 텍스트 조건이고 동작은 print입니다. print는 결과 뒤에 기본적으로 줄바꿈도 붙입니다. 조건을 만족한 줄이 여섯 개라면 이 예제의 출력도 여섯 줄입니다.

작은따옴표 안의 $3은 awk에 도착해서 해석되어야 합니다. 큰따옴표로 무심코 바꾸면 Bash가 자신의 셋째 위치 매개변수로 먼저 해석할 수 있습니다. 두 프로그램이 같은 기호를 다른 의미로 쓰기 때문입니다. 명령을 복사할 때는 줄바꿈과 따옴표도 문법의 일부로 읽어 주세요.

공백 두 칸에서도 awk가 src를 고른 것은 기본 필드 구분이 연속 공백을 하나의 구분 구간으로 다루기 때문입니다. 하지만 IP나 시각 항목이 추가되는 출력 형식까지 자동으로 보정하지는 않습니다. 구분 규칙이 편리하다는 것과 의미를 검증했다는 것은 따로 확인해야 합니다. [6]

9. sort: 숫자순과 문자순을 구별한다

sort는 줄을 정렬합니다. 텍스트의 기본 비교에서는 숫자처럼 보이는 문자열도 수치의 크기로 비교되는 것은 아닙니다. C 로캘에서 2, 10, 100을 문자순으로 정렬하면10·100·2가 되지만, sort -n으로 숫자 비교를 요청하면2·10·100이 됩니다.

-r은 비교 방향을 뒤집고, -u는 정렬 비교에서 같은 항목을 하나로 줄입니다. -k 1,1은 첫 필드를 정렬 키로 지정합니다. 예를 들어 빈도와포트 두 항목이 있는 출력에서 sort -k1,1nr은 첫 필드를 숫자로 내림차순 비교하라는 뜻입니다. -k 1처럼 끝을 생략하면 첫 필드부터 줄 끝까지 키에 포함되므로 의도가 달라질 수 있습니다. [7]

로캘은 문자 비교·숫자 표현 등 지역별 처리 규칙입니다. 재현성을 위해 로캘을 명시하고 도구 버전을 기록할 수 있습니다. 다만 파이프의 앞 명령에만 환경 변수를 붙였다고 뒤의 모든 명령이 같은 설정을 상속하는 것은 아닙니다. 각 실행 환경과 셸 범위를 확인합니다. 이번ASCII 텍스트 검산은 C.UTF-8 환경에서 수행했습니다.

정렬은 모든 입력을 읽고 임시 저장 공간을 사용할 수 있습니다. 따라서 파이프라고 항상 적은 메모리로 즉시 한 줄씩 끝나거나, 수TB 파일이 순식간에 처리된다고 보장하지 않습니다. 원래 순서가 조사에 필요하면 원본을 보존하고, 정렬한 출력이 시각 순서의 증거를 유지하는지도 구별합니다.

로캘을 적용할 범위도 명령의 일부입니다

LC_ALL=C sort라고 적으면 그 sort에 비교 환경을 지정합니다. 뒤에 파이프로 연결한 uniq까지 같은 값이 설정됐다고 가정할 수는 없습니다. 여러 단계를 같은 환경에서 비교하려면, 예를 들어 Bash의 괄호로 묶은 실행 범위 안에서 export LC_ALL=C를 먼저 실행할 수 있습니다. 아래는 example.txt의 ASCII 포트 표식을 대상으로 실행한 완전한 명령입니다.

(
  export LC_ALL=C
  cut -d ' ' -f 3 example.txt |
    cut -d '.' -f 5 |
    sort -n |
    uniq -c |
    sort -k1,1nr -k2,2n |
    head -n 2
)
# 검산: 3 443 / 2 50000 (각각 한 줄, 앞 여백 생략)

괄호 안의 설정은 그 실행 범위와 자식 명령에 적용됩니다. 마지막 sort는 첫 필드인 빈도를 큰 순서로 비교하고, 동률이면 둘째 필드인 포트 숫자를 작은 순서로 비교합니다. 입력이 전부 숫자라는 이번 전제가 필요합니다. 새 표현을 배웠다고 기존 명령이 틀린 것은 아니고, 재현에 필요한 조건과 동률 규칙을 더 분명하게 적은 것입니다. [7]

10. uniq는 이웃한 같은 줄만 묶는다

uniq는 기본적으로 바로 이웃한 같은 줄을 하나로 줄입니다. 파일 전체를 기억해 모든 중복을 제거하는 도구가 아닙니다. 같은 값을 모아 전체 빈도를 알고 싶다면 먼저 적절히 정렬해야 합니다. uniq -c의 -c는 묶인 줄의 개수를 앞에 붙입니다. [8]

앞의 포트 표식 목록은 50000,443,50000,53,443,443 순서입니다. 정렬하지 않고 uniq에 넣으면 마지막443 두 줄만 인접하므로 다섯 묶음이 남습니다. 정렬 후에는 53,443,443,443,50000,50000이 되어 세 묶음으로 집계됩니다.

# 텍스트 추출 뒤에 연결하는 단계
... | sort -n | uniq -c

# 자체 입력을 이용한 검산 결과
      1 53
      3 443
      2 50000

위의 ...는 앞 단계가 있다는 설명용 생략 표시이며 그대로 실행할 셸 명령이 아닙니다. 실제 전체 명령은 다음 절에 적습니다. 각 빈도의 합은 1+3+2=6으로 원래 여섯 항목과 일치합니다. 이처럼 합계와 중간 결과를 대조하면 추출 단계에서 항목이 사라지거나 오류 문구가 섞인 문제를 찾는 데 도움이 됩니다.

sort -u는 고유 목록을 얻는 데 쓸 수 있지만 출현 빈도를 함께 남기지는 않습니다. 또한 숫자 표기가 0443과 443처럼 섞여 있으면 숫자 비교와 원문 문자열 비교의 ‘같음’이 달라질 수 있습니다. 이번 예제는 동일한10진수 표기만 사용합니다. 데이터의 정규화·비교 기준을 먼저 정합니다.

같은 숫자와 같은 줄은 다를 수 있습니다

0443과 443을 각각 한 줄씩 넣어 보겠습니다. 이번 환경에서 sort -nu는 같은 수치 443으로 비교해 한 줄만 남겼습니다. 반면 sort -n | uniq -c는 숫자순으로 놓은 다음 서로 다른 문자열 두 개를 각각 1회로 셌습니다. 숫자 정렬 옵션을 사용했다고 uniq까지 숫자 비교를 하는 것은 아닙니다. [7]

printf '0443\n443\n' | sort -nu
# 검산: 0443 한 줄
printf '0443\n443\n' | sort -n | uniq -c
# 검산:
      1 0443
      1 443

“그럼 앞의 0을 지우면 되겠네요?” 먼저 그 항목이 정말 10진수 포트인지 확인해야 합니다. 식별자나 문자열이면 0도 의미가 있을 수 있습니다. 원본은 남기고, 파생 결과에서 어떤 정규화를 했는지 기록하세요. 이번 여섯 줄은 처음부터 같은 숫자 표기를 사용해 이 문제가 없도록 정의한 것입니다.

11. 긴 집계 명령을 여섯 단계로 풀어 읽기

이제 실제로 검산한 전체 텍스트 명령을 보겠습니다. 단계마다 무엇을 세고 있는지 말로 설명할 수 있어야 합니다.

cut -d ' ' -f 3 example.txt | cut -d '.' -f 5 | sort -n | uniq -c | sort -rn | head

# 자체 텍스트 처리 검산 결과
      3 443
      2 50000
      1 53

sort -rn은 -r -n의 조합입니다. 이 출력에서는 줄 앞의 개수로 숫자 비교해 큰 빈도를 위로 올립니다. 동일 빈도끼리 어느 순서인지까지 보고서가 요구한다면 명시적인 키와 동률 규칙을 정해야 합니다. 포트 자체를 내림차순 정렬하는 단계라고 오해하지 않습니다.

head는 기본적으로 앞10줄을 출력합니다. head -n 2라면 이 예제에서 위의 두 항목만 보입니다. 입력을 끝까지 평가하기 전 종료할 수 있으므로 ‘상위 목록을 봤다’와 ‘전체 처리가 모두 정상 완료되었다’를 구별합니다. 이번처럼 sort가 앞에 있으면 sort는 입력 전체를 읽어야 합니다. head를 붙였다고 원본 패킷 열 개만 읽는 것이 아닙니다. 이 환경의 공식 내장 도움말에서 기본10줄과 -n을 확인했습니다. [9]

출발지443의 빈도가 가장 높다는 결과는 이 여섯 텍스트 항목에서443이 세 번 있었다는 뜻입니다. 실제 자료에서도 방향을 바꾸거나 요청·응답을 함께 집계하면 의미가 달라집니다. 서비스 응답의 출발지 포트일 수도 있고, 재전송·중복 수집일 수도 있습니다. 빈도 순위를 공격·유출의 위험도 순위로 바로 옮기지 않습니다.

명령을 왼쪽에서 읽되, 검사는 중간에서도 멈춰 봅니다

처음에는 첫 cut까지만 실행해 의도한 출발지가 나오는지 봅니다. 그다음 둘째 cut까지 연결해 여섯 포트 표식을 확인합니다. 정렬 후에도 6개가 남는지, uniq 뒤 빈도의 합이 6인지, head가 몇 항목을 숨겼는지 차례로 확인하면 어느 단계에서 뜻이 달라졌는지 좁힐 수 있습니다. 한 번에 긴 명령만 실행하면 잘못된 추출도 그럴듯한 상위 목록으로 바뀔 수 있습니다.

이 입력에서 상위 두 표식의 빈도 합은 3+2=5이고 전체는 6입니다. 따라서 선택한 표식에 속한 텍스트 항목의 비율은 5/6≈83.3%입니다. 고유 표식 두 개를 세 개 중 골랐다는 2/3≈66.7%와는 분모가 다릅니다. 둘 다 계산은 맞아도 답하는 질문이 다르므로, 어느 비율인지 문장으로 적어 주세요. 이 비율은 실제 네트워크의 트래픽 점유율이 아닙니다.

12. wc: 무엇의 개수를 세고 있는지 먼저 적는다

wc는 줄바꿈·단어·바이트 등의 개수를 셉니다. 데이터에서 한 줄이 어떤 단위를 의미하는지 정했을 때 유용합니다. 같은 명령을 어느 단계에 붙이느냐에 따라 전혀 다른 질문에 답합니다.

# 원래 포트 표식의 항목 수
cut -d ' ' -f 3 example.txt | cut -d '.' -f 5 | wc -l
# 검산값: 6

# 정렬·집계 뒤의 고유 포트 표식 수
cut -d ' ' -f 3 example.txt | cut -d '.' -f 5 | sort -n | uniq -c | sort -rn | wc -l
# 검산값: 3

두 번째는 uniq -c가 고유 값마다 한 줄을 만들었다는 조건 아래3을 얻습니다. 빈도의 합6을 얻은 것이 아닙니다. 바로 앞에 head -n 2를 넣으면2가 되므로 더 이상 전체 고유 값 수라고 부를 수 없습니다.

wc -l은 줄바꿈 수, -w는 단어 수, -c는 바이트 수, -m은 로캘에 따라 해석한 문자 수입니다. 옵션 없는 기본 출력은 줄바꿈·단어·바이트 순서입니다. 원문의 -c를 문자 수라고 설명한 부분을 바로잡습니다. 한글 등 다중 바이트 문자에서 두 숫자가 다를 수 있습니다. [10]

예를 들어UTF-8의 가 한 글자 뒤에 줄바꿈 하나를 둔 입력은 바이트4개, 문자2개, 줄바꿈1개입니다. 문자 수2에는 줄바꿈도 포함됩니다. 줄바꿈 없는 마지막 부분은 wc -l에서 한 줄로 더해지지 않습니다. 실제 검산에서는 인코딩과 로캘을 명시해 이런 차이를 확인했습니다.

tcpdump 텍스트가 여러 줄을 만들면 tcpdump … | wc -l은 패킷 개수와 다를 수 있습니다. 이 회차에서는 텍스트 변환의 단위를 배웁니다. 바이너리 캡처 기록을 직접 세는 방법은 다음 회차에서 따로 다루며, 원본 PCAP의 총 패킷 수를 추정해 채우지 않습니다.

줄바꿈 수가 달라졌다면 자료가 늘었다는 뜻일까요?

printf '443' | wc -l은 0을 냅니다. 텍스트 443은 있지만 줄바꿈이 없기 때문입니다. 그런데 printf '443' | sort | wc -l은 이 GNU 환경에서 1이 됩니다. sort가 끝의 줄바꿈을 보충하기 때문입니다. 포트나 패킷이 하나 새로 생긴 것이 아니라 출력 형식의 줄 끝 처리가 달라진 것입니다. 이런 경우를 생각하면 wc의 숫자를 곧바로 기록 수라고 부르기 어렵다는 점이 보입니다. [7] [10]

13. 현재의 분석에서는 구조화된 필드와 오류 상태도 확인한다

텍스트 처리 원리는 여전히 유효하지만, 사람이 읽는 요약 문자열이 영구적인 데이터 인터페이스는 아닙니다. 자동화를 계속 운영하려면 요약의 몇 번째 글자인지보다 프로토콜 해석기가 제공하는 필드를 선택하는 편이 더 명확한 경우가 있습니다. 가령 TShark에서는 다음과 같이 선택한 필드를 출력할 수 있습니다.

# 파일이 준비되어 있을 때의 사용법 예시, 실행 결과가 아님
tshark -r sample.pcap -Y 'ip and tcp' -T fields -e ip.src -e tcp.srcport

-r은 파일 읽기, -Y는 표시 필터, -T fields는 필드 출력 방식, 반복하는 -e는 출력 필드 지정입니다. 이 예시는IPv4와TCP로 범위를 제한합니다. IPv6를 포함하지 않고, 터널·반복 필드·재조립·빈 필드의 처리도 요구에 맞게 확인해야 합니다. 구조화된 필드라고 대상 사용자·프로그램이나 공격 성공까지 자동으로 확정되는 것은 아닙니다. [11]

반복 실행에서는 원본 파일 식별 정보·수집 지점·시간대·필터·도구 버전·로캘과 명령을 함께 남깁니다. 자료의 전송·저장·해석 실패를 구별하고, 예상치 못한 빈 출력이나 줄 수 변화를 검토합니다. 원본을 읽기 전용으로 두고 파생 결과와 구분하면 다른 분석가가 같은 조건으로 확인하기 쉽습니다.

Bash의 기본 파이프 성공 상태는 마지막 명령의 상태에 영향을 받으므로, 앞 단계 실패가 뒤의 wc 성공에 가려질 수 있습니다. pipefail 같은 기능은 이를 점검하는 데 도움이 되지만 모든 오류를 해결하는 스위치는 아닙니다. head나 페이저가 일찍 종료하면 앞 프로그램이 닫힌 파이프를 만나 종료하는 경우도 있습니다. 종료 상태·진단·기대한 처리 범위를 함께 해석합니다. [1]

이 회차에서 검산한 것은 합성 텍스트에 대한 cut·awk·sort·uniq·head·wc의 동작입니다. 실제 PCAP을 실행하지 않았고, GUI 화면을 탐색하거나 특정 공격을 재현한 것으로 표시하지 않습니다. 문법 검증과 실제 수집 자료의 정확성을 분리합니다.

입력 실패가 ‘0건’처럼 보이는 경우를 직접 만들어 보겠습니다

아래의 missing.txt는 검산용 디렉터리에 의도적으로 만들지 않은 파일입니다. 첫 단계가 입력을 열지 못해도 wc는 빈 입력에서 줄바꿈 0개를 정상적으로 셀 수 있습니다. 기본 Bash 파이프의 종료 상태만 보면 마지막 wc가 성공했으므로 0이 됩니다.

# Bash에서 실행, missing.txt는 의도적으로 존재하지 않음
(
  set +o pipefail
  cut -f 3 missing.txt | wc -l
  printf 'status=%s\n' "$?"
)
# stdout: 0, status=0 (각각 한 줄)
# stderr: cut의 파일 열기 실패 진단

(
  set -o pipefail
  cut -f 3 missing.txt | wc -l
  printf 'status=%s\n' "$?"
)
# stdout: 0, status=1 (이번 GNU cut/Bash 검산값)
# stderr: 같은 파일 열기 실패 진단

$?는 바로 앞 명령의 종료 상태를 뜻합니다. 보통 0은 성공, 0 이외 값은 실패 등 추가 해석이 필요한 상태입니다. 두 경우 모두 화면의 집계값은 0이지만 두 번째는 pipefail 덕분에 앞 단계의 실패도 파이프 상태에 반영됩니다. 그렇다고 pipefail이 잘못 고른 필드를 찾아 주지는 않습니다. 문법적으로 성공한 추출이 의미상 틀릴 수도 있으니까요. [1]

Bash의 PIPESTATUS는 각 단계 상태를 배열로 제공합니다. 같은 실패 예제 직후 printf 'stages=%s\n' "${PIPESTATUS[*]}"를 실행한 검산값은 stages=1 0이었습니다. cut은 실패하고 wc는 성공한 관계입니다. 상태는 다른 명령을 실행하면 바뀌므로 관심 파이프 직후 읽어야 합니다. 이는 Bash 기능이며 모든 셸에 같은 문법이 있다고 가정하지 않습니다. [12]

숫자·진단·종료 상태를 함께 읽는 세 가지 상황
상황확인할 것보고할 의미
입력이 정상 처리되고 조건에 맞는 기록이 없음입력 범위·필터·단계 상태·진단확인한 범위에서 0건
파일 열기·해석이 실패했는데 wc가 0 출력앞 단계 비정상 상태와 오류분석 실패, 대상 부재로 해석하지 않음
head나 페이저가 먼저 종료요청한 범위·닫힌 파이프·단계 상태예상된 조기 종료인지 별도 판단

구조화된 TShark 필드도 같은 점검이 필요합니다. -e로 필드를 골랐더라도 한 프레임에서 같은 필드가 여러 번 나오는 터널, 빈 필드, 설정에 따른 해석 차이가 있을 수 있습니다. 한 줄을 ‘한 연결’로 부르기 전에 출력의 행과 필드 발생 횟수를 확인하세요. 이번 TShark 명령은 공식 매뉴얼을 확인한 사용법 예시이며 실행 결과는 제시하지 않습니다. [11]

14. 집계 결과에서 조사 판단까지

패킷으로 확인 가능한 사실

실제 자료가 있을 때 확보한 주소·포트·시각·방향·길이·바이트와 필터 조건에 맞는 기록입니다. 이 노트의 검산에서는 패킷을 확인한 것이 아니라 정의한 텍스트 여섯 줄과 변환 결과를 확인했습니다.

단독으로 확정할 수 없는 부분

포트 이름만으로 응용 정체, 행 수만으로 패킷·연결·공격 횟수, 반복 빈도만으로 바이트량·반출 성공·사용자 신원, 빈 출력만으로 무해함·차단 성공, 도구 이름만으로 공격자 숙련도입니다.

함께 확인할 자료

원본 캡처·수집 손실·출력 형식과 오류, 양방향 연결·재전송·중복, 단말 프로세스·사용자 기록, 서버·인증·메일·DNS·클라우드 로그, 암호화 통신에 필요한 복호화 정보입니다.

가상 텍스트에 대한 조사 메모는 다음처럼 씁니다.

문서용 주소로 만든 여섯 줄에서 셋째 필드의IPv4 출발지 포트 표식을 추출했다.443은3회,50000은2회,53은1회이고 고유 표식은3개이다. 이는 합성 텍스트의 빈도이며 실제 패킷·연결·파일 반출 결과를 뜻하지 않는다. 실제 자료에서는 추출 형식·누락·중복·방향과 관련 호스트 로그를 추가 확인한다.

현대에도 패킷 분석과 명령줄은 통신의 빈도·크기·시점과 관측 범위를 검토하는 데 가치가 있습니다. 그러나 암호화된 본문을 단순 문자열 처리로 평문으로 만들 수는 없습니다. 집계는 조사할 대상을 찾는 단계이고 활동의 의미와 결과는 필요한 로그·복호화 정보로 검증해야 합니다.

빈도표를 보고 다음 조사 대상을 고릅니다

실제 자료에서 특정 표식이 많이 보였다면 먼저 원래 패킷과 추출 조건으로 돌아갑니다. 서버 응답을 센 것인지 요청을 센 것인지, 같은 패킷을 여러 지점에서 수집한 것인지, 재전송이 포함됐는지 확인합니다. 그 뒤 단말의 프로세스·소켓 기록과 서버 처리 기록을 연결하면 “무엇이 통신했는가”와 “작업이 완료됐는가”에 가까워질 수 있습니다.

명령과 입력 파일이 같아도 도구 버전·시간 표시·이름 변환·로캘이 다르면 중간 문자열이 달라질 수 있습니다. 결과만 저장하기보다 어떤 범위에서 어떤 단위를 세었는지 함께 남겨 보세요. 다른 사람이 결과를 재현할 수 있고, 자신도 며칠 뒤 ‘이 3은 고유 표식 수였구나’ 하고 근거를 되짚을 수 있습니다.

15. 복습 — 명령의 결과와 의미를 함께 말하기

질문 1: 파이프는 화면에 보인 모든 내용을 다음 명령에 전달할까요?

해설: 기본 |는 표준 출력을 표준 입력으로 연결합니다. 표준 오류는 별도입니다. 오류를 결과와 합치면 집계에 섞일 수 있고, 오류를 무시하면 실패를0개 결과로 오해할 수 있습니다.

질문 2: -c 10이면 화면에 딱 열 줄이 나올까요?

해설: tcpdump의 패킷 처리 수 제한입니다. 상세·바이트 출력은 패킷 하나가 여러 줄일 수 있습니다. 페이저의 화면 단위와도 다릅니다.

질문 3: cut -c 17-40은 출발지 주소만 알고 고를까요?

해설: 구조를 모르고24자리를 선택합니다. 이번 합성 입력에서도 목적지 앞부분이 섞입니다. 주소 길이와 출력 옵션이 변하면 같은 열 위치가 같은 필드라는 보장은 없습니다.

질문 4: cut -f 5,3으로 출력 순서를 바꿀 수 있을까요?

해설: GNU cut은 입력에 나타난 순서로 선택 내용을 한 번씩 출력합니다. awk의 print $5,$3처럼 재배열 동작을 명시해야 합니다.

질문 5: 공백 cut과 기본 awk의 필드 나누기는 같을까요?

해설: 공백 한 문자 구분은 연속 공백에 빈 필드를 만들 수 있습니다. 기본 awk는 연속 공백·탭과 앞뒤 공백을 다르게 처리합니다. 어떤 경우든 그 필드가 실제 프로토콜 의미와 맞는지 확인합니다.

질문 6: uniq만 실행하면 파일 전체의 중복이 모두 제거될까요?

해설: 이웃한 같은 줄만 묶습니다. 이번 목록은 정렬 전5묶음, 정렬 후3묶음입니다. 전체 빈도는 같은 표기·비교 기준으로 정렬한 뒤 집계합니다.

질문 7: uniq -c | sort -rn은 포트 크기 순인가요?

해설: 이 결과에서는 맨 앞에 붙은 빈도 숫자로 내림차순 비교합니다.443이3회로 위에 있어도 포트 번호·전송 바이트량·위험도 순위와 같지 않습니다.

질문 8: 집계 뒤 wc값3은 총 출현 수일까요?

해설: 고유 값마다 한 줄이 되었다는 조건에서 고유 값 수3입니다. 빈도 합은3+2+1=6입니다. head로 둘만 남긴 뒤 세면2가 되어 전체 고유 값 수도 아닙니다.

질문 9: wc -c는 한글 글자 수일까요?

해설: 바이트 수입니다. UTF-8의 ‘가+줄바꿈’은4바이트·2문자·줄바꿈1개입니다. 문자수에는 -m, 줄바꿈에는 -l을 사용하고 인코딩·로캘을 확인합니다.

질문 10:443이 많이 보이면HTTPS 유출이나 공격 성공을 확정할까요?

해설: 방향·서비스 정체·중복·재전송·바이트량·실행 프로세스와 활동의 정당성을 확인합니다. 텍스트 빈도 하나는 연결 수나 전송 내용을 입증하지 않습니다. 암호화와 관측 한계도 함께 남깁니다.

추가 연습: 합성 입력의 첫 줄에서 공백 하나를 두 개로 바꾸고 cut과awk의 셋째 필드를 비교해 보세요. 또 -f 3,5와 -f 5,3을 비교해 출력 순서가 같은지 확인하세요. 마지막으로 줄바꿈 없는 한 줄의 wc -l을 관찰하고, ‘명령이 센 단위’를 한 문장으로 설명해 보세요. 원본 실습 PCAP의 정답이 아니라 직접 정의한 텍스트의 학습 문제입니다.

조건을 바꾼 추가 복습

질문 11: time과 IP 사이의 공백만 두 개로 바꾸었습니다. cut의 셋째 필드는 왜 IP가 될까요?

해설: 공백 한 문자마다 나누므로 두 공백 사이가 빈 둘째 필드입니다. IP는 셋째가 됩니다. 기본 awk는 연속 공백을 구분 구간으로 다루어 같은 입력의 셋째로 src를 고릅니다. 둘 중 하나가 무조건 정확한 것이 아니라 입력 규칙과 목적에 맞는지 확인합니다.

질문 12: 점이 없는 ERROR가 두 번째 cut을 통과했습니다. 다섯째 포트라는 뜻일까요?

해설: 구분자가 없는 줄은 기본 cut이 그대로 출력할 수 있습니다. -s로 제외할 수 있지만 남은 문자열의 포트 의미까지 검증되지는 않습니다. 빈 값과 숫자 0도 구분해야 합니다.

질문 13: 0443과 443에서 sort -nu와 sort -n | uniq -c가 다른 이유는 무엇일까요?

해설: 전자는 숫자 비교에서 같은 것으로 묶어 하나만 남기고, 후자는 정렬 뒤 서로 다른 전체 문자열을 따로 셉니다. 무엇을 같은 값으로 볼지 정해야 합니다. 원본은 보존하고 정규화 조건을 남깁니다.

질문 14: 존재하지 않는 파일을 cut으로 읽어 wc에 연결했더니 0과 성공 상태가 나왔습니다. 대상이 없었다고 보고해도 될까요?

해설: 입력 실패를 먼저 확인해야 합니다. 기본 Bash에서는 마지막 wc의 성공이 앞 단계 실패를 가릴 수 있습니다. 진단과 단계 상태를 보고 pipefail·PIPESTATUS로 보완하되, 의미가 틀린 추출까지 자동 검증한다고 생각하지 않습니다.

질문 15: 줄바꿈 없는 443을 wc -l에 넣으면 0인데 sort 뒤에는 왜 1일까요?

해설: wc -l은 줄바꿈을 세고 GNU sort는 마지막 줄바꿈을 보충합니다. 새로운 패킷이 생긴 것이 아닙니다. 입력·출력 형식과 집계 단위를 먼저 확인합니다.

질문 16: 상위 두 표식의 빈도가 3과 2입니다. 5/6과 2/3 중 어느 비율이 맞을까요?

해설: 5/6은 전체 항목 여섯 개 중 선택된 항목 다섯 개의 비율이고, 2/3은 고유 표식 세 종류 중 선택된 두 종류의 비율입니다. 분모가 다릅니다. 실제 패킷 점유율·전송량·위험도를 입증한 수치는 아닙니다.

워크북 연계 실습

파일 읽기·이름 변환·시각·개수·바이트·링크 계층 출력을 연결합니다. tcpdump 옵션 복습에서 단계별 설명과 복습을 읽을 수 있습니다. 이 페이지의 기존 자체 예시는 그대로 유지하며, 원본 PCAP을 실행한 출력으로 제시하지 않습니다.
