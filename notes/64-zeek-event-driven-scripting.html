학습 범위

넷째 날 9강에서는 Zeek 스크립트가 패킷을 위에서 아래로 한 줄씩 처리하는 프로그램이 아니라, 관측된 사건을 이벤트로 받아 필요한 코드만 실행하는 정책 계층이라는 점을 배웁니다. zeek_init, new_connection, connection 레코드, $ 필드 접근, signature_match 연결을 안전한 오프라인 예제로 읽습니다.

1. 패킷보다 이벤트를 먼저 생각해야 합니다

센서에서 “새 연결을 보았을 때만 자산 정보를 덧붙이고 싶다”고 해볼게요. 패킷마다 같은 코드를 실행하면 SYN, 재전송, ACK, 응답처럼 서로 다른 조각을 매번 직접 정리해야 합니다. Zeek은 패킷과 스트림을 먼저 분석한 뒤 new_connection, dns_request, ssl_established 같은 이벤트를 스크립트 계층에 전달합니다. 이벤트는 “관심 있는 일이 관측됐다”는 알림이지, 공격 판정이 아닙니다.

식당의 주문 벨을 떠올리면 쉬워요. 주방 직원이 손님이 움직일 때마다 반응하는 대신 “주문 접수”, “조리 완료” 같은 벨에 맞춰 일을 나눕니다. 다만 비유의 한계가 있습니다. 네트워크 이벤트는 센서 위치·패킷 손실·분석기 활성화 상태에 따라 아예 발생하지 않거나 불완전한 문맥을 가질 수 있습니다.

2. 시작·관측·종료 이벤트는 실행 시점이 다릅니다

zeek_init()은 입력 처리 직전에 한 번 발생해 초기 설정에 적합합니다. new_connection(c: connection)은 Zeek이 새 흐름을 인식할 때마다 발생하며 TCP뿐 아니라 UDP·ICMP의 흐름 개념도 포함합니다. zeek_done()은 정상적인 입력 종료 시점의 집계 출력에 쓸 수 있습니다. 같은 파일의 첫 줄부터 마지막 줄까지 직선으로 실행된다고 생각하면 이 순서를 놓치기 쉽습니다.

이벤트별로 답할 수 있는 질문
이벤트발생 시점적합한 작업주의점
zeek_init()정상 입력 처리 직전테이블 초기화, 정책 준비아직 패킷 기반 네트워크 시간이 준비되지 않았을 수 있음
new_connection(c)새 연결·흐름을 처음 인식끝점·서비스 후보 기록연결 성공이나 악성 여부를 뜻하지 않음
signature_match(...)로드한 시그니처 조건 일치일치 문맥을 후속 정책에 전달일치 데이터는 전체 스트림이 아니라 마지막 조각일 수 있음
zeek_done()정상적인 입력 종료 전누적 건수·요약 출력비정상 종료 방식에 따라 호출되지 않을 수 있음

하나의 이벤트를 여러 스크립트가 독립적으로 처리할 수도 있습니다. 실행 순서가 중요한 핸들러는 우선순위를 명시해야 하며, 단순히 파일에 먼저 적었다고 먼저 실행된다고 가정하면 안 됩니다.

3. 작은 스크립트를 문장처럼 분해해 봅니다

다음 코드는 문서용 주소가 포함된 승인된 저장 캡처를 읽는 상황을 설명하기 위한 예시입니다. 이번 실행에서는 Zeek 명령이나 캡처를 실행하지 않았습니다.

event new_connection(c: connection)
    {
    local origin: addr = c$id$orig_h;
    local responder: addr = c$id$resp_h;
    print fmt("flow candidate %s -> %s", origin, responder);
    }

event는 이벤트 처리기를 선언하는 키워드, new_connection은 받을 이벤트 이름입니다. 괄호 속 c: connection은 이름이 c이고 형식이 connection인 인자를 받는다는 뜻입니다. 중괄호는 이 이벤트 때 실행할 코드 블록, 세미콜론은 한 문장의 끝입니다.

local 변수는 현재 처리기 안에서만 쓰입니다. addr는 IP 주소 형식이고, fmt의 두 %s 자리에 뒤의 값이 순서대로 들어갑니다. 이 출력은 “연결 후보를 관측했다”는 사실만 남깁니다. 연결이 성공했는지, 허용됐는지, 사용자가 누구였는지는 추가 증거가 필요합니다.

4. connection 레코드는 상자 안의 작은 상자입니다

connection은 연결에 관한 이름 붙은 값들의 묶음인 레코드입니다. c$id$orig_h를 왼쪽부터 읽으면 “연결 레코드 c 안의 끝점 식별자 id 안에 있는 시작 측 호스트 orig_h”입니다. 달러 기호($)는 중첩된 레코드의 필드를 찾아가는 연산자입니다.

문서용 흐름 192.0.2.24:53000 → 198.51.100.80:443의 필드
필드예시 값뜻
c$id$orig_h192.0.2.24Zeek이 정한 연결 시작 측 주소
c$id$orig_p53000/tcp시작 측 포트와 전송 프로토콜
c$id$resp_h198.51.100.80응답 측 주소
c$id$resp_p443/tcp응답 측 포트와 전송 프로토콜

originator/responder는 매 패킷의 source/destination과 다릅니다. 보통 첫 패킷을 보낸 쪽이 originator지만, 캡처 손실과 프로토콜 의미에 따라 분석기가 역할을 바로잡을 수 있습니다. 따라서 한 패킷 헤더와 연결 레코드의 역할을 같은 말로 바꾸지 않습니다.

확장 레코드에는 &optional 필드가 있을 수 있습니다. 존재를 보장할 수 없는 필드는 c?$http처럼 ?$로 확인한 뒤 접근해야 합니다. 확인 없이 없는 필드를 읽으면 표현식 오류가 생길 수 있습니다.

5. 시그니처 일치는 스크립트의 시작점이 될 수 있습니다

앞 강의의 시그니처가 일치하면 signature_match 이벤트가 발생할 수 있습니다. 현재 Zeek 문서는 세 인자 형식과 일치 종료 위치를 추가한 네 인자 형식을 함께 설명합니다. state$sig_id는 어떤 시그니처였는지, state$conn은 관련 연결 문맥을 찾는 데 쓰입니다.

event signature_match(state: signature_state, msg: string, data: string)
    {
    if ( state$sig_id == "training-policy-marker" )
        print fmt("review candidate on %s", state$conn$uid);
    }

여기서 ==는 같은지 비교하고, if는 조건이 참일 때만 다음 문장을 실행합니다. data를 전체 요청이나 전체 스트림이라고 가정하면 안 됩니다. 현재 문서상 일치를 촉발한 최근 입력 조각일 수 있으므로, 자세한 해석은 원시 패킷·재조립 상태·같은 UID의 로그와 연결합니다.

조건을 바꾸면

시그니처 이름이 다르면 이 처리기는 출력하지 않습니다. 시그니처가 로드되지 않았거나 암호화·누락 때문에 일치하지 않으면 이벤트 자체가 없습니다. 출력이 없다는 사실만으로 대상 행위가 없었다고 결론 내리지 않습니다.

6. 스크립트 결과도 관측·가설·추가 증거로 나눕니다

한 줄 출력 뒤의 조사 순서
구분말할 수 있는 것함께 볼 증거
관측특정 이벤트와 조건이 센서에서 발생함센서 시각, UID, 원시 캡처, 관련 로그
가설새 외부 서비스 또는 정책 위반 가능성자산 역할, 변경 기록, 허용 목록, 사용자 활동
결론 전 확인연결 성공·업무 영향·침해 여부방화벽 허용 결과, 종단 프로세스, 서버·인증 로그

고속 링크에서 new_connection마다 콘솔에 출력하면 처리 비용과 저장량이 커질 수 있습니다. 초당 5,000개 이벤트가 각각 평균 120바이트 한 줄을 만들면 5,000 × 120 = 600,000바이트/초, 약 0.6MB/초입니다. 60초에는 약 36MB가 됩니다. 운영에서는 구조화 로그, 필터링, 집계와 센서 성능 지표를 함께 설계합니다.

복습과 해설

1. 이벤트는 경보와 같은 말인가요?
아닙니다. 이벤트는 관측된 활동이나 상태를 스크립트에 전달하는 진입점입니다. 정책 코드가 문맥을 더한 뒤 로그나 notice로 만들 수 있습니다.
2. new_connection이 발생하면 TCP 연결이 성공했다는 뜻인가요?
아닙니다. Zeek이 새 흐름을 인식했다는 뜻입니다. 성공 여부는 연결 상태, 응답, 방화벽과 종단 로그를 확인해야 합니다.
3. c$id$orig_h의 달러 기호는 무엇을 하나요?
중첩 레코드의 이름 붙은 필드를 따라갑니다. c 안의 id, 그 안의 orig_h를 읽습니다.
4. 조건을 바꿔 캡처가 중간부터 시작되면 무엇이 달라질까요?
연결 역할과 프로토콜 상태가 불완전할 수 있고 기대한 이벤트가 누락될 수 있습니다. 센서 위치·패킷 손실·분석기 상태를 함께 기록합니다.
5. 스크립트가 한 줄을 출력했으면 침해가 확정되나요?
아닙니다. 처리기가 정의한 조건을 만족했다는 관측입니다. UID, 원시 패킷, 자산·사용자·종단 결과로 가설을 검증합니다.

공식 자료와 확인일

2026-11-25에 Zeek 9.0.1 Scripting 튜토리얼, 이벤트·connection 레코드·선택 필드의 현행 설명, Signature Framework의 signature_match 인자와 데이터 범위를 확인했습니다. 예시 스크립트와 명령은 이번 회차에서 실행하지 않았습니다.
