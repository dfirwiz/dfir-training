1. 길이는 ‘얼마나’, 오프셋은 ‘어디에’를 알려 준다

앞선 회차에서는 IPv4 단편화가 필요한 이유와 MF·Offset의 조합을 배웠습니다. 이번에는 16진수 헤더를 직접 읽어, 조각 하나에 들어 있는 데이터의 양과 원래 데이터에서 차지하는 위치를 계산합니다. 이 두 가지를 알면 ‘마지막 조각이 보였다’는 관찰을 ‘전체 데이터가 모였다’는 결론과 구별할 수 있습니다.

종이 문서를 여러 봉투에 나누어 보냈다고 생각해 보세요. 봉투 전체 무게가 내용물 무게와 다르듯, IP 전체 길이에는 그 조각의 IP 헤더도 포함됩니다. 또 ‘이 봉투에는 원문 1480바이트 지점부터 들어 있다’는 표시는 앞에 봉투가 몇 개 있었는지 알려 주지 않습니다. 한 봉투로 앞부분을 보냈을 수도 있고 여러 봉투로 보냈을 수도 있습니다.

학습 범위와 자료의 한계

첫 조각의 전체 길이, 마지막 조각의 전체 길이, 원시 오프셋의 바이트 환산, 작은 조각을 이용한 계산 문제를 차례로 다룹니다. 별도 실습 PCAP은 제공되지 않았습니다. 아래 주소·헤더·표·그림은 독립적으로 구성한 가상 예시이며, tcpdump를 실행해 얻은 결과나 실제 장비의 재조립 결과가 아닙니다.

계산 자체와 프로토콜 규칙, 실제 도구 실행은 구별합니다. 이 노트의 헤더 바이트와 체크섬은 자체 계산으로 검산했지만, 그것이 실제 통신의 발생이나 공격 성공을 입증하지는 않습니다.

2. 헤더를 읽기 위한 명령과 각 옵션의 역할

PCAP은 수집한 패킷을 담는 파일 형식입니다. 파일이 준비되었다면 tcpdump로 저장된 내용을 읽고 상세 헤더와 16진수를 함께 살펴볼 수 있습니다. 다음의 sample-fragments.pcap은 설명용 파일명입니다. 실제 파일이 있어야 명령을 실행할 수 있습니다.

# 사용법 예시: 이 노트에서 실행한 명령이나 출력이 아닙니다.
tcpdump -r sample-fragments.pcap -ntxv -c 1
tcpdump -r sample-fragments.pcap -ntxv

-ntxv는 네 개의 짧은 옵션 -n -t -x -v를 묶어 쓴 것입니다. 첫 명령은 한 패킷만 보고 멈추고, 둘째는 개수 제한 없이 파일을 읽습니다. 파일의 첫 기록이 반드시 원래 데이터의 첫 조각인 것은 아닙니다. 실제로 어느 조각인지는 MF와 Offset으로 판단해야 합니다.

파일 읽기와 출력 옵션 — 공식 매뉴얼 확인 [2]
옵션무엇을 바꾸는가사용할 때의 의미
-r 파일저장된 패킷 파일을 읽음인터페이스에서 새로 수집하는 명령과 구별
-n주소 등을 이름으로 변환하지 않음숫자 주소를 서로 비교하기 편함
-t출력의 타임스탬프를 숨김헤더 계산에는 간결하지만 시간 관계 조사에는 불리함
-x보통 링크 계층 헤더를 제외한 내용을 16진수로 표시IP 시작 위치를 확인한 뒤 필드를 찾음
-v더 상세한 헤더 정보를 표시IPv4 길이·ID·오프셋·플래그 등을 함께 대조
-c 1한 패킷을 처리한 뒤 종료표본 확인용이며 전체 조각 확보를 보장하지 않음

-x와 -X는 다릅니다. 대문자 -X는 16진수와 ASCII를 함께 표시하고, -xx는 링크 계층 헤더도 포함해 16진수를 출력합니다. 또한 -x의 출력 끝에 Ethernet 패딩이 포함될 수 있고, 잘린 패킷에서는 출력 동작에 예외가 있습니다. ‘화면에 보이는 모든 바이트 수’가 곧 IP Total Length라고 세지 말고 링크 형식과 길이 필드로 경계를 확인합니다.

사건의 시간 관계까지 조사할 때는 -t 대신 날짜와 시각을 보이는 -tttt를 선택할 수 있습니다. 예를 들어 tcpdump -n -tttt -r sample-fragments.pcap -x -v입니다. 이 명령도 사용법 예시입니다. 표시 시간대, 도구 버전과 수집 지점을 함께 기록해야 다른 로그와 맞출 수 있습니다.

3. 16진수에서 필드를 찾는 기준점

이제 링크 헤더를 제외하고 IPv4 헤더의 첫 바이트를 위치 0으로 둡니다. 4500이라는 네 자리 묶음은 한 바이트가 아니라 45와 00, 두 바이트입니다. 각 바이트는 16진수 두 자리로 표시합니다. 두 바이트 정수는 높은 자리 바이트가 먼저 오는 네트워크 바이트 순서로 읽습니다. 따라서 05 dc는 0x05dc이며 순서를 뒤집은 0xdc05가 아닙니다.

이번 계산에 사용하는 IPv4 헤더 위치 [1]
IP 시작 기준 바이트필드읽는 방법
0Version·IHL0x45: 위 4비트는 IPv4, 아래 4비트 IHL은 5
2~3Total Length이 조각의 IP 헤더와 IP 데이터 전체 길이, 단위는 바이트
4~5Identification관련 조각을 묶을 때 주소·Protocol·시간 문맥과 함께 확인
6~7Flags·Fragment Offset상위 3비트와 하위 13비트를 나누고 Offset만 8배
8 / 9TTL / Protocol이번 예시는 0x40=64 / 0x01=1(ICMP)
10~11 / 12~19헤더 체크섬 / 출발지·목적지 주소헤더 일관성 및 관련 조각 연결에 사용

IHL은 헤더 길이를 4바이트 단위로 나타냅니다. IHL 5라면 5 × 4 = 20바이트입니다. 반면 원시 Fragment Offset은 8바이트 단위입니다. 둘 다 숫자에 곱셈이 필요하지만 단위가 다릅니다. ‘IHL은 4, Offset은 8’을 적용한 뒤 결과에 바이트를 붙여 쓰세요.

첫 두 바이트의 45 00 중 두 번째 00은 현재 DSCP·ECN으로 나누어 읽는 영역이 모두 0인 설정입니다. DSCP는 전달 처리 분류, ECN은 혼잡 알림에 사용하는 부분입니다. 예전 tcpdump의 tos 0x0과 연결해 볼 수 있습니다. 이번 A·B는 예약 비트와 DF가 0이고 MF만 다릅니다. TTL 64는 관측한 헤더 값이며 운영체제나 통과한 홉 수를 단독으로 확정하는 표시는 아닙니다. [14] [15]

계산의 기본 순서는 IP 헤더 길이 H = IHL × 4 → 조각 데이터 길이 D = Total Length − H → 시작 S = 원시 Offset × 8 → 끝 E = S + D입니다. 여기서 ‘조각 데이터’는 IP 헤더 뒤의 내용입니다. ICMP·TCP·UDP 헤더가 포함될 수도 있으므로 응용 데이터 길이와 같다고 생각하면 안 됩니다.

아래 가상 헤더는 모두 출발지 192.0.2.10, 목적지 198.51.100.20이라는 문서용 주소를 사용합니다. A와 B는 IP ID 0x4242=16962, Protocol 1이 같은 하나의 묶음이라고 가정합니다. 주소나 ID가 같다는 사실만으로 실제 캡처의 관계를 무제한으로 연결하지는 않습니다. 특히 긴 시간에 걸친 ID 재사용과 NAT·터널의 관측 위치를 구분합니다. [6]

4. 첫 조각: 0x05dc가 왜 1500바이트인가

다음은 자체 구성한 A의 IPv4 헤더 20바이트입니다. 전체 IP 길이는 1500으로 설정했지만, 여기에는 헤더만 보여 주며 뒤의 1480바이트를 실제 덤프로 제시하지 않습니다. 이 짧은 코드 블록의 표시 길이와 헤더에 설정한 패킷 길이는 다른 값입니다.

# 가상 예제 A: IP 헤더만 표시, 뒤의 데이터는 생략
4500 05dc 4242 2000 4001 268d c000 020a c633 6414

IP 시작의 2~3번 바이트에 05dc가 있습니다. 16진수에서 d=13, c=12입니다. 각 자리의 무게를 풀면 다음과 같습니다.

0x05dc = 0×16³ + 5×16² + 13×16¹ + 12×16⁰
         = 0 + 1280 + 208 + 12
         = 1500바이트
IHL       = 5 → 헤더 5×4 = 20바이트
IP 데이터 = 1500−20 = 1480바이트

6~7번 바이트는 0x2000입니다. MF 비트 0x2000가 설정되어 있고 Offset 부분은 0입니다. 따라서 정상적인 형식을 전제로 하면 원래 IP 데이터의 첫 조각이며 뒤의 데이터가 더 있다는 뜻입니다. 1480 ÷ 8 = 185로 나누어떨어지므로 끝이 아닌 조각의 데이터 정렬 조건에도 맞습니다. Total Length 1500 자체가 8의 배수여야 하는 것은 아닙니다.

표준 Ethernet MTU 1500에 맞추어 최대한 채운 흔한 상황이라면, 헤더 20과 데이터 1480이라는 모양을 자연스럽게 설명할 수 있습니다. 다만 1500을 보았다는 사실만으로 실제 링크 MTU가 정확히 1500이라고 증명한 것은 아닙니다. 더 큰 MTU에서도 이 크기로 보낼 수 있고, 패킷을 의도적으로 구성했을 수도 있습니다. MTU는 인터페이스·경로 설정과 다른 관측으로 확인합니다.

MF1은 뒤의 데이터가 남았다고 알리지만, 그 양을 알려 주지는 않습니다. A만으로 원래 전체 IP 길이나 조각 총개수를 구할 수 없습니다. 정상적으로 분할된 큰 데이터그램이라는 가설을 세우고, 같은 묶음의 뒤 조각을 찾아야 합니다.

5. 두 줄의 length가 같은 범위를 뜻하지 않는다

첫 조각을 해석하는 tcpdump 형식의 예에서는 IPv4 설명 줄에 length 1500, ICMP Echo 설명 줄에 length 1480이 나올 수 있습니다. 앞의 것은 IP 헤더를 포함한 길이이고, 뒤의 것은 이 사례에서 ICMP 처리기에 전달된 첫 조각의 IP 데이터 범위입니다. 여기서 1480을 Echo의 순수 진단 데이터 길이라고 읽으면 안 됩니다.

ICMP Echo의 기본 헤더는 Type 1바이트, Code 1바이트, Checksum 2바이트, Identifier 2바이트, Sequence Number 2바이트로 합계 8바이트입니다. 이 헤더가 A의 맨 앞에 온다고 가정하면 A에는 1480−8=1472바이트의 Echo 데이터 일부가 있습니다. ID와 seq라는 ICMP 필드도 IPv4 헤더의 Identification과 별개입니다. [7]

이 시점에는 아직 뒤의 Echo 데이터가 얼마나 남았는지 모릅니다. 따라서 ‘ping 데이터가 1472바이트였다’고 전체 요청의 크기로 보고할 수도 없습니다. 첫 조각에 담긴 일부와 재조립된 전체 메시지를 구별해야 합니다.

실제 출력 문구는 tcpdump 버전과 옵션, 캡처의 완전성에 따라 달라집니다. 이 노트는 특정 실행 문자열을 재현한 것이 아니라 length의 계층별 범위를 설명합니다. 숫자를 옮길 때는 ‘IP 전체’, ‘이 조각의 IP 데이터’, ‘ICMP 전체’, ‘Echo 데이터’ 중 무엇인지 함께 적으세요.

6. 마지막 조각: 0x0030에서 데이터 28바이트까지

이제 같은 가상 묶음의 B를 봅니다. 다음 역시 IPv4 헤더만 표시하며 데이터는 생략한 예제입니다.

# 가상 예제 B: IP 헤더만 표시, 뒤의 28바이트는 생략
4500 0030 4242 00b9 4001 4b80 c000 020a c633 6414

Total Length 위치의 0x0030은 3×16 + 0 = 48바이트입니다. 처음이 0x45이므로 이번에도 IHL 5, 헤더 20바이트입니다. 조각의 데이터는 48−20=28바이트입니다. 여기서 Ethernet 헤더 14바이트를 다시 빼지 않습니다. 애초에 IP Total Length에 포함되지 않은 영역이기 때문입니다.

0x00b9는 MF가 0이고 Offset이 0보다 큽니다. 따라서 원래 데이터의 끝을 담은 마지막 조각입니다. 28은 8의 배수가 아니지만 마지막 조각의 데이터는 남은 분량을 담으므로, 이 사실만으로 잘못된 형식이라고 판단하지 않습니다. 반대로 마지막 조각이 반드시 작아야 하는 것도 아닙니다. 원래 데이터의 나머지 양에 따라 마지막도 최대 크기를 채울 수 있습니다.

각 조각에는 자체 IP 헤더가 있지만 뒤 조각마다 새 ICMP Echo 헤더가 붙지는 않습니다. B의 IP 데이터는 원래 ICMP 메시지 중간 이후의 내용입니다. 그러므로 Protocol이 1이라고 해서 B의 데이터 첫 바이트를 Type, 다음 바이트를 Code로 해석하면 엉뚱한 값을 얻습니다.

분석기가 뒤 조각을 짧게 icmp 또는 프로토콜 번호 중심으로 표시하고 Echo의 ID·seq를 보여 주지 않을 수 있는 이유도 여기에 있습니다. 자세한 ICMP 설명이 없다는 사실만으로 손상·공격·암호화를 판정하지 않습니다. 공식 tcpdump 소스도 Offset이 0인 조각과 뒤 조각의 상위 프로토콜 해석을 구분합니다. [3]

7. 0x00b9는 185이고, 실제 위치는 1480이다

Flags와 Offset이 함께 있는 16비트 전체에서 하위 13비트만 남기려면 0x1fff와 AND 연산을 합니다. AND는 선택한 비트 위치만 남기는 연산입니다. B에서는 0x00b9 AND 0x1fff = 0x00b9입니다. MF가 들어 있는 A의 0x2000 전체를 위치로 읽지 않는 것도 같은 이유입니다.

원시 Offset = 0x00b9
            = 11×16 + 9
            = 176 + 9 = 185   ← 단위: 8바이트 블록
실제 시작 S = 185×8 = 1480바이트
데이터 길이 D = 48−20 = 28바이트
끝 위치 E   = 1480+28 = 1508바이트

오프셋의 기준 0은 원래 IP 데이터의 시작입니다. 프레임 시작도, 현재 조각의 헤더 시작도, 앞서 캡처한 조각의 끝도 아닙니다. 원래 IP 데이터에는 ICMP 헤더도 들어 있으므로 1480에 ICMP 헤더 8을 또 더하지 않습니다.

구간은 [1480,1508)로 쓰겠습니다. 왼쪽은 포함하고 오른쪽은 포함하지 않으므로 실제 바이트 번호는 1480부터 1507까지이며 길이는 1508−1480=28입니다. 끝 번호에 1을 잘못 더하거나 빼는 실수를 줄이는 표기입니다.

현재 도구 구현과 대조 — 2026년 11월 1일 확인

tcpdump의 IPv4 상세 출력은 Offset 부분을 추출한 뒤 이미 ×8하여 바이트 위치를 표시합니다. 따라서 화면에 offset 1480이라고 나오면 그 1480을 또 8배 하지 않습니다. 원시 필드 185와 출력의 바이트 위치 1480은 같은 위치를 다른 단위로 표현한 것입니다. 공식 소스의 (off & IP_OFFMASK) * 8 처리와 대조했습니다. [3]

‘Offset에 8을 곱한다’만 외우면 이중 환산하기 쉽습니다. 먼저 내가 읽는 것이 원시 13비트 값인지, 분석기가 바이트로 환산한 표시인지 확인합니다. 다른 도구나 내보낸 필드에서도 이름이 같다는 이유로 단위를 추측하지 마세요.

8. 두 조각을 합치면 원래 무엇이 몇 바이트였을까

A와 B가 같은 원래 데이터그램에 속하고, 헤더가 일관되며, 해당 데이터가 모두 확보되었다고 가정해 보겠습니다. A는 위치 0에서 데이터 1480바이트를 운반합니다. 따라서 구간은 [0,1480)입니다. B의 구간은 [1480,1508)이므로 A의 끝에 정확히 이어집니다. 이 두 구간 사이에는 빈틈이나 겹침이 없습니다. 이런 구간과 빈틈의 관리가 재조립을 이해하는 출발점입니다. [5]

가상 A·B의 길이와 위치를 같은 기준으로 비교
조각IP 전체 / 헤더 / 데이터MF·원시 Offset원래 IP 데이터 구간
A1500 / 20 / 1480바이트1 · 0[0,1480)
B48 / 20 / 28바이트0 · 185[1480,1508)

마지막 조각은 끝 1508을 알려 줍니다. 앞 구간까지 채워졌다는 가정하에 원래 IP 데이터는 1480+28=1508바이트입니다. 원래 헤더도 IHL 5였다고 두면 원래 IP 전체 길이는 20+1508=1528바이트입니다. 반면 두 조각의 IP 전체 길이를 단순 합산하면 1500+48=1548바이트입니다. 차이 1548−1528=20바이트는 조각이 하나 더 생겨 IP 헤더가 한 번 더 붙은 양입니다.

원래 IP 데이터가 하나의 정상 ICMP Echo 메시지라면 그 전체 메시지는 1508바이트이고, Echo 헤더 8을 빼면 1508−8=1500바이트의 Echo 데이터입니다. 숫자 1500이 다시 나오지만, A의 IP 전체 1500과 원래 Echo 데이터 1500은 서로 다른 범위에서 우연히 같은 숫자입니다. 이 예시를 ‘1500바이트 ping’이라고만 기록하면 어떤 길이인지 모호해집니다.

IPv4 옵션이 있는 실제 자료에서는 각 조각의 IHL을 따로 읽어 데이터 길이를 구하고, 원래 전체 길이를 계산할 때는 원래 헤더의 길이를 사용해야 합니다. 뒤 조각의 헤더가 원래 헤더와 언제나 동일한 길이라고 가정하지 않습니다. 실제 파일에서는 헤더만 보이는 것이 아니라 전체 데이터가 확보되었는지도 확인해야 합니다.

9. 앞에 1480바이트가 있다는 것과 앞 조각 하나는 다르다

B의 바이트 오프셋 1480은 원래 데이터의 앞 1480바이트 다음에 이 조각을 놓으라는 지시입니다. 앞부분의 분할 방식은 기록하지 않습니다. A처럼 1480바이트를 한 번에 보냈다는 설명이 가능한 동시에, 앞부분을 여러 조각으로 나눈 설명도 가능합니다.

예를 들어 같은 데이터그램의 앞부분을 첫 조각 데이터 800바이트, 다음 조각 데이터 680바이트로 나누어 보냈다고 가정해 보겠습니다. 첫 구간은 [0,800), 다음은 [800,1480)입니다. 둘째 조각의 원시 Offset은 800÷8=100이고, 두 데이터 길이 모두 8의 배수입니다. 여기에 B의 [1480,1508)이 이어져도 위치 계산은 모순되지 않습니다. B 하나만 보면 앞부분이 한 조각인지 두 조각인지 구분할 수 없습니다.

일반화 수정 — 2026년 11월 1일 확인

‘끝을 제외하면 항상 MTU까지 채워 같은 크기로 만든다’는 설명은 흔한 최대 충전 예제의 조건입니다. 모든 IPv4 단편의 의무 규칙은 아닙니다. RFC791은 최대 크기보다 작은 조각을 생성하는 대안도 설명하고, RFC1812는 여러 분할 전략을 다룹니다. 경로 중 재단편화도 크기 분포를 바꿀 수 있습니다. 따라서 조각 크기가 서로 다르다는 관찰만으로 악성 생성이나 공격자 숙련도를 판정하지 않습니다. [1] [4]

그렇다고 차이를 무시하는 것도 아닙니다. 끝이 아닌 데이터 길이의 정렬, 끝 위치의 일관성, 중복·겹침과 서로 다른 내용, 재조립 자원 상태, 경로 MTU와 수집 손실을 살펴봅니다. ‘평소와 달라서 조사한다’와 ‘표준상 불가능하므로 공격이다’는 근거의 강도가 다릅니다.

여기서 보완한 내용은 2021년 이후 필드 형식이 바뀌어서 생긴 수정이 아닙니다. 당시에도 존재했던 표준의 예외와 대안을 현재 해석에 분명히 반영한 것입니다. 오래된 계산 원리는 유지하되, 조건이 있는 예시를 보편 법칙으로 확대하지 않는 것이 핵심입니다.

10. 직접 풀기: 길이 0x001c, Offset 0x0002

다음 C는 앞의 A·B와 다른 ID를 사용하는 독립적인 가상 계산 문제입니다. 작은 오프셋을 쉽게 계산하도록 만든 예제이며, 일반적인 경로의 단편 크기를 대표하지 않습니다. 다음 28바이트를 보고 IP 전체 길이, 헤더 길이, 조각 데이터 길이, 바이트 시작·끝 위치, 마지막 조각 여부를 먼저 적어 보세요.

# 가상 예제 C: IP 헤더 20 + 데이터 8, 실제 캡처 아님
4500 001c 4243 0002 4001 4c4a c000 020a c633 6414
4343 4343 4343 4343

풀이 1 — 전체 길이: IP 시작의 2~3번 바이트는 0x001c입니다. c는 12이므로 1×16+12=28바이트입니다. ‘1c를 112처럼 읽기’나 ‘28이 순수 데이터라고 보기’를 피합니다.

풀이 2 — 데이터 길이: IHL 5를 먼저 5×4=20바이트로 바꿉니다. 그 뒤 28−20=8바이트입니다. 코드 블록에서도 IP 헤더 뒤의 43이 여덟 개 있으므로 표시한 데이터와 일치합니다.

풀이 3 — 위치: Flags·Offset의 0x0002에는 MF가 없고 원시 Offset은 2입니다. 바이트 위치는 2×8=16입니다. 데이터 8을 더한 끝 위치는 16+8=24이므로 C는 원래 IP 데이터의 [16,24)를 운반합니다.

풀이 4 — 분류와 한계: MF0·Offset>0이므로 마지막 조각입니다. 원래 데이터의 끝이 24라는 단서는 있지만 앞의 [0,16)을 확보했다는 증거는 없습니다. 원래 헤더가 20바이트라는 가정 아래 예상 원래 전체 길이는 20+24=44바이트입니다. 이것을 ‘44바이트 재조립 완료’라고 쓰면 안 됩니다.

‘첫 조각 뒤로 16바이트’라는 말은 기준이 모호합니다. 정확히는 원래 IP 데이터 시작으로부터 16바이트 떨어진 위치입니다. 바로 앞에 수집한 조각의 끝에서 16을 더하지 않습니다. 데이터에 보이는 43은 ASCII 문자 C에 해당하지만, 이 뒤 조각의 첫 43을 ICMP Type 67로 읽지도 않습니다.

이 문제의 학습 목표는 작은 패킷을 공격이라고 분류하는 것이 아니라, 필드 위치를 찾고 길이와 단위를 바꾸며 관측 범위를 제한해 설명하는 것입니다. 미제공 PCAP의 실제 패킷 순서나 앞 조각의 내용은 이 예제로 확인할 수 없습니다.

11. 계산이 맞아도 캡처가 완전한지 따로 확인한다

Total Length는 헤더가 선언한 IP 길이입니다. 캡처 파일에 그만큼 저장되어 있다는 보증이 아닙니다. SnapLen은 프레임마다 저장할 최대 분량을 제한하는 설정입니다. 수집 도구가 앞부분만 보존했다면 길이 필드는 읽혀도 뒤 데이터는 없을 수 있습니다. Wireshark의 프레임 길이와 캡처된 길이, 잘림 표시와 수집 설정을 함께 확인합니다. [8] [13]

태그 없는 Ethernet II의 14바이트 헤더 뒤에 A가 있고, FCS를 저장하지 않은 가상 수집 상황을 생각해 보겠습니다. 프레임 길이는 14+1500=1514바이트인데 앞 96바이트만 저장했다면, 남은 IP 부분은 96−14=82바이트입니다. IP 헤더 20을 빼면 A의 데이터 중 실제 확보한 것은 82−20=62바이트뿐입니다. 선언된 데이터 길이 1480과 확보한 62는 다릅니다.

이때 B가 온전하게 있더라도 앞부분이 모두 채워진 것은 아닙니다. 분석기가 조각을 제대로 붙이려면 필요한 데이터가 있어야 하며, 재조립 설정과 제한도 맞아야 합니다. 도구가 재조립한 PDU를 표시하는 것과 대상 호스트가 실제로 같은 바이트를 받아들였다는 결론 역시 구별합니다. PDU는 해당 프로토콜이 처리하는 데이터 단위라는 뜻입니다. [10]

체크섬도 범위를 구별합니다. IPv4 헤더 체크섬이 맞는 것은 그 헤더에 대한 계산의 일관성이지, 조각 데이터의 완전성이나 악성·정상 판정이 아닙니다. 이 노트의 A·B·C 헤더는 자체 체크섬을 검산했지만, 생략한 전체 ICMP 메시지의 체크섬이나 실제 수신 동작을 검증했다고 주장하지 않습니다.

12. 현대의 조사에 연결하기: 조각 선택과 암호화 가시성

2026년 11월 1일 공식 문서와 대조했을 때, 이번의 IPv4 길이·위치 계산은 그대로 사용할 수 있습니다. 현대적인 보충은 필드를 새로 외우는 것보다 관측 도구의 단위, 조각 누락, 상위 프로토콜 해석과 실제 처리 결과를 구분하는 데 있습니다.

Wireshark에서는 ip.flags.mf == 1 || ip.frag_offset > 0이라는 표시 필터로 IPv4 단편 후보를 볼 수 있습니다. ||는 둘 중 하나라도 참이라는 뜻입니다. MF1만 고르면 마지막 조각을 놓치고, Offset>0만 고르면 첫 조각을 놓칩니다. 공식 IPv4 필드 목록에는 조각의 겹침·충돌·여러 끝 조각 등에 관한 분석 필드도 있습니다. 다만 분석 필드의 존재나 경고 하나는 공격 성공 판정이 아닙니다. [9]

표시 필터는 이미 저장된 패킷 중 무엇을 볼지 고르는 기능입니다. 수집 단계에서 제외했거나 잘려 저장되지 않은 바이트를 되살리지 않습니다. TCP·UDP의 포트로만 범위를 좁히면 상위 헤더를 담지 않은 뒤 조각의 관계를 놓칠 수 있으므로, IP 단위의 관련 조각과 원래 수집 필터를 함께 검토합니다. 링크 형식·터널·재조립 설정에 따라 필터 해석이 달라질 수 있어, 표시 필터를 라이브 캡처 명령에 그대로 복사하지 않습니다.

RFC8900은 단편화가 중간 장비의 처리·필터링과 손실에 취약할 수 있음을 설명합니다. 이는 2020년 문서이므로 ‘2021년 이후에야 드러난 문제’라고 소개하지 않습니다. 지금도 단편을 읽는 능력은 통신 실패와 탐지의 관측 범위를 조사하는 데 필요합니다. 그렇다고 단편이라는 이유만으로 공격이라고 판단할 근거가 되는 것은 아닙니다. [11]

앞선 사용자 질문인 ‘현대에는 패킷 분석이 의미 없는가’도 여기와 연결됩니다. TLS 같은 암호화가 있어도 IP 조각의 크기·위치·누락 정황을 살피는 가치는 남습니다. 그러나 IP 재조립은 TLS 복호화가 아닙니다. 전체 IP 데이터를 모았어도 그 안의 암호화된 요청·명령·파일 의미를 자동으로 읽는 것은 아니며, 필요한 비밀정보와 단말·서버 로그를 추가로 확인해야 합니다. [12]

13. 관측한 필드에서 조사 메모까지

실제 분석에서는 먼저 링크·IP 기준점을 정하고 IHL·Total Length·Flags·Offset을 읽습니다. 주소·Protocol·ID 및 시간·수집 위치를 연결한 뒤 각 데이터 구간을 계산합니다. 다음에는 빈 구간과 겹침, 실제 확보한 바이트를 확인하고 마지막으로 대상 처리와 응용 결과의 증거를 대조합니다. 계산 결과에서 바로 ‘침해 성공’으로 건너뛰지 않습니다.

패킷으로 확인 가능한 사실

확보한 IPv4 헤더의 IHL·전체 길이·MF·원시 Offset, 계산한 데이터 길이와 원래 위치, 관측한 주소·Protocol·ID·시각, 파일에 실제 저장된 바이트입니다. 같은 묶음이라는 전제와 수집 위치도 함께 적습니다.

단독으로 확정할 수 없는 부분

오프셋만으로 앞 조각 개수, 길이만으로 정확한 경로 MTU, 마지막 조각만으로 완전한 재조립, 응답 부재만으로 차단·무해함, 공격자 도구·숙련도, 대상의 수신·응용 처리 성공과 암호화 본문의 의미입니다.

함께 확인할 로그와 자료

송수신 양단 및 다른 지점의 캡처, 수집 필터·SnapLen·손실 통계, 인터페이스와 터널 MTU, 방화벽·IDS/IPS 재조립 설정과 폐기·자원 기록, 호스트 IP 재조립 통계, 단말 프로세스·연결 기록과 서버 응용 로그입니다.

다음은 A·B에 대한 가상 분석 메모입니다. 실제 사건의 실행 결과를 보고하는 문장이 아닙니다.

같은 주소·Protocol·IP ID를 사용하는 것으로 가정한 A와 B의 헤더를 읽었다. A는 IP 전체 1500, 헤더 20, MF1·원시 Offset0으로 데이터 [0,1480)를 나타낸다. B는 전체 48, 헤더 20, MF0·원시 Offset185로 [1480,1508)를 나타낸다. 두 구간의 길이 계산에는 빈틈이 없다. 원래 헤더가 20바이트라면 예상 전체 길이는 1528바이트이다. 여기 제시된 것은 자체 구성한 헤더 계산이며, 전체 페이로드 확보·대상 재조립·Echo 응답 여부는 확인하지 않았다.

실제 자료에서 B만 보았다면 메모도 바뀌어야 합니다. ‘끝 위치 1508인 마지막 조각을 관측했으나 [0,1480)의 확보 여부는 미확인’이라고 씁니다. 원시 필드·단위·가정을 남기면 다른 분석가도 판단 과정을 검토할 수 있습니다.

14. 복습 — 정답뿐 아니라 근거와 한계까지

질문 1: 0x05dc가 1500인 과정을 설명해 보세요.

해설: 16진수 d는 13, c는 12입니다. 5×256 + 13×16 + 12 = 1280+208+12=1500입니다. 이 필드가 Total Length라면 IP 헤더를 포함한 바이트 수입니다.

질문 2: IHL 5, IP 전체 1500이면 Echo 데이터는 무조건 1480바이트일까요?

해설: 1480은 이 조각의 IP 데이터입니다. ICMP Echo 헤더가 들어 있는 첫 조각이라면 헤더 8을 포함하므로 Echo 데이터 일부는 1472바이트입니다. 전체 Echo 데이터 길이는 뒤 조각까지 알아야 합니다.

질문 3: tcpdump 상세 줄의 offset 1480에 8을 곱해 11840으로 놓아야 할까요?

해설: 아닙니다. 해당 IPv4 상세 출력은 바이트 위치로 환산되어 있습니다. 헤더의 원시 0x00b9=185를 읽었다면 그때 8을 곱해 1480을 얻습니다. 단위를 먼저 적습니다.

질문 4: B의 IP 전체 48에서 20과 14를 빼면 데이터가 14바이트일까요?

해설: IP Total Length에는 Ethernet 헤더가 포함되지 않습니다. IHL 5라면 48−20=28바이트가 IP 데이터입니다. 서로 다른 계층의 기준을 섞어 빼지 않습니다.

질문 5: B의 바이트 Offset이 1480이므로 앞 조각은 정확히 하나일까요?

해설: 위치만으로 개수는 알 수 없습니다. 앞 데이터가 한 조각의 1480일 수도, 800과 680으로 나뉘었을 수도 있습니다. 같은 크기 생성이라는 추가 가정과 실제 관측을 구별합니다.

질문 6: A와 B의 IP 전체 길이 합계 1548이 원래 IP 길이일까요?

해설: 헤더가 중복됩니다. 데이터는 1480+28=1508, 원래 헤더 20이라는 전제에서 원래 전체는 1528입니다. 1548에는 추가 헤더 20이 들어 있습니다. 실제 전체 재조립 여부는 별도 확인합니다.

질문 7: C의 원시 Offset 2는 두 번째 바이트나 두 번째 조각이라는 뜻일까요?

해설: 8바이트 단위이므로 원래 IP 데이터의 16바이트 위치입니다. 전체 28−헤더 20으로 데이터 8, 따라서 [16,24)입니다. 앞부분이나 조각 개수는 이 값만으로 확인하지 못합니다.

질문 8: 마지막 조각을 확보했으면 재조립은 끝났을까요?

해설: 끝 위치를 알았을 뿐입니다. 필요한 앞 구간이 실제로 저장되어 있고 빈틈·충돌이 없는지, 분석기와 대상의 처리 조건이 어떤지 확인해야 합니다. SnapLen으로 앞 조각이 잘렸다면 헤더가 있어도 완전한 데이터는 없습니다.

질문 9: Protocol 1인 뒤 조각의 맨 앞 바이트를 ICMP Type으로 읽어도 될까요?

해설: 비영 오프셋의 데이터는 원래 ICMP 메시지 중간일 수 있습니다. 조각마다 ICMP 헤더가 새로 붙지 않습니다. IP Protocol과 조각 위치를 함께 읽어야 합니다.

질문 10: 조각 크기가 다르고 응답도 보이지 않습니다. 공격 실패나 낮은 숙련도를 결론 내릴까요?

해설: 크기 차이는 분할 전략·재단편화 등으로도 설명될 수 있습니다. 응답 부재는 수집 누락·경로·정책 등과 구별해야 합니다. 승인 여부와 전후 활동, 대상 처리 로그 없이 도구·숙련도·무해함·공격 성공 여부를 단정하지 않습니다.

추가 연습: A·B 중 A가 앞 62바이트의 IP 데이터만 남도록 잘렸다고 가정하고 메모를 다시 써 보세요. 헤더가 선언한 구간 [0,1480)과 확보된 구간 [0,62)는 다릅니다. B가 온전하면 [1480,1508)은 있지만 [62,1480)의 1418바이트가 빠져 있습니다. 숫자로 남은 빈틈을 설명하는 연습입니다. 다음 회차는 이 계산을 더 넓은 단편 분석 사례에 적용합니다.
