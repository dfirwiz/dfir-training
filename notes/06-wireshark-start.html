1. Wireshark는 패킷의 해석 과정을 보여 주는 도구다

가상의 조사 상황부터 볼까요? 서버에서 연결 지연 신고가 들어와 저장된 캡처를 열었습니다. 화면에는 수천 줄이 있고 일부는 색이 다릅니다. 어디부터 읽어야 할까요? 처음부터 모든 줄을 해석하려 하기보다 파일의 범위를 확인하고, 질문과 관계있는 패킷 하나를 골라 그 해석이 어느 바이트에서 나왔는지 따라가면 됩니다. 이번 강의에서는 그 작은 왕복을 익힙니다.

도서관의 목록 카드, 책의 목차, 실제 본문을 생각해 보세요. 목록은 찾을 대상을 고르고, 목차는 구조를 보여 주고, 본문은 내용을 확인하게 해 줍니다. Wireshark의 목록·상세·바이트도 비슷한 관계입니다. 다만 바이트가 있다고 사건의 모든 사실이 적혀 있는 것은 아닙니다. 수집하지 않은 통신과 실제 프로그램 내부 동작까지 이 화면이 대신 보여 주지는 않으므로, 각 영역이 제공하는 근거의 범위를 구별해야 합니다.

앞선 회차에서 계층, 바이트와 표준을 배웠습니다. 이제 그 지식을 실제 분석 화면에 연결하겠습니다. Wireshark는 네트워크 데이터를 수집하거나 저장된 캡처 파일을 열고, 프로토콜 구조에 따라 바이트를 해석하는 도구입니다. 단순히 ‘TCP 패킷이 있다’고 알려 주는 데서 끝나지 않고, 어떤 필드를 읽어 그렇게 해석했는지 따라가게 해 줍니다.

처음에는 메뉴가 많아 부담스러울 수 있습니다. 모든 기능을 외우기보다 ‘전체 흐름에서 관심 패킷을 고르고 → 그 패킷의 계층과 필드를 펼치고 → 해당 바이트를 확인한다’는 흐름부터 익히면 됩니다. 이 과정은 목록, 상세 정보, 원시 바이트라는 세 화면을 오가는 일입니다.

이번 회차의 목표는 저장된 파일을 열고, 화면의 각 영역이 무엇을 보여 주는지 이해하며, 도구가 해석한 필드와 확보된 바이트를 연결하는 것입니다. 스트림·통계·객체 추출 기능의 역할도 살펴보되, 모든 기능을 완전히 익혔다고 가정하지 않습니다. 아래 예시와 도식은 독립적으로 구성한 학습 자료입니다. 추가 확보한 첫째 날 PCAP의 오프라인 검증은 연계 실습 가이드에서 구분해 설명합니다. 실제 파일을 실행한 결과나 원본 화면의 재현이 아닙니다.

2. 어떤 질문에 어떤 기능을 사용할까

Wireshark에는 실시간 수집과 저장 파일 읽기, 프로토콜 분석, 조건에 맞는 패킷 표시, 통신 통계, 스트림 따라가기, 객체 내보내기 등 여러 기능이 있습니다. 기능 이름보다 지금 답하려는 질문에 연결하면 사용 순서를 정하기 쉽습니다.

프로토콜을 해석하는 구성요소를 디섹터(dissector)라고 합니다. 예를 들어 HTTP 디섹터가 요청을 해석하면 메서드 같은 필드로 나누어 볼 수 있습니다. 그 결과 평문 HTTP GET 요청을 찾는 http.request.method == "GET" 같은 표시 필터를 사용할 수 있습니다. [13] 이것은 단순히 모든 바이트에서 GET이라는 세 글자를 찾는 것과 다릅니다. 해당 데이터가 HTTP 요청 필드로 해석되어야 합니다.

따라서 결과가 없을 때는 ‘GET 요청이 절대로 없었다’고 바로 쓰지 않습니다. 다른 통신 구간을 보고 있거나, 데이터가 누락되었거나, HTTP로 해석되지 않았거나, TLS 안에 암호화되어 있을 수 있습니다. 도구의 기능은 강력하지만, 해석 가능한 데이터와 조건이 있어야 그 기능의 결과도 의미가 있습니다. [1] [2]

분석한 패킷을 다시 캡처 파일로 저장하는 기능도 있습니다. Wireshark는 pcap과 pcapng를 읽고 쓸 수 있습니다. 파일로 저장하는 것, 스트림 내용을 텍스트로 저장하는 것, 응용 객체를 추출하는 것은 서로 다른 결과물이므로 목적에 맞는 기능을 선택합니다. 확장자만 보고 어떤 데이터를 저장했는지 단정하지 않습니다. [4]

기능을 누르기 전에 질문을 한 문장으로 씁니다

“이 파일에서 서버와 통신한 기록을 보고 싶다”, “길이 값이 어느 바이트인가”, “HTTP 요청의 메서드가 GET인 것만 보고 싶다”처럼 질문을 구체적으로 적어 보세요. 첫 질문은 주소나 통계, 두 번째는 상세·바이트, 세 번째는 필드 기반 필터와 연결됩니다. 하나의 검색 기능이 이 세 질문을 같은 방법으로 해결하는 것은 아닙니다.

HTTP는 웹의 요청·응답 형식을 정의하는 프로토콜이고, 메서드(method)는 요청이 하려는 동작을 나타내는 항목입니다. http.request.method == "GET"를 나누어 읽으면 http.request.method는 요청 메서드 필드, ==는 같은지 비교하는 연산자, "GET"는 비교할 문자열입니다. 따옴표는 문자열이라는 문법 표시이며 실제 요청에 그 따옴표까지 들어 있다는 뜻은 아닙니다. [13] [14]

조건을 바꾸어 파일 내용에 GET이라는 글자만 들어 있다고 해 봅시다. 그것이 HTTP 메서드 필드로 해석되지 않았다면 위 식에는 맞지 않을 수 있습니다. 반대로 이 식으로 찾은 요청도 승인된 조회인지 공격 시도인지까지 알려 주는 것은 아닙니다. 디섹터가 만든 필드와 업무상의 의미를 나누어 확인하세요.

또 GUI(Graphical User Interface)는 버튼과 창을 사용하는 화면 인터페이스라는 뜻입니다. 같은 분석 목적에 GUI와 명령줄을 함께 사용할 수 있지만, 화면에서 보기 좋게 연결한 결과가 항상 원래 패킷 한 개와 같은 데이터 단위는 아닙니다. 어떤 결과를 저장하거나 보고하는지까지 이름을 붙이면 혼동을 줄일 수 있습니다.

3. tcpdump와 Wireshark는 함께 쓸 수 있다

두 도구 중 하나만 골라야 하는 것은 아닙니다. 명령줄에서 반복적으로 조건을 적용하거나 큰 파일에서 관심 범위를 추리는 데 tcpdump가 편리할 수 있습니다. 선택한 자료의 계층과 필드를 펼쳐 비교하고 대화형으로 탐색하는 데에는 Wireshark가 편리합니다. 특정 환경에서 한 도구만으로 충분할 수도 있고, 두 도구를 연결하는 편이 효율적일 수도 있습니다.

예를 들어 매우 큰 캡처에서 조사 대상 주소가 이미 정해졌다고 가정해 보겠습니다. 전체를 바로 화면에 올리기 어려우면 해당 주소가 출발지 또는 목적지인 패킷을 별도 파일로 저장한 뒤 열 수 있습니다. 다음은 사용법을 설명하는 예시이며, 이 환경에서 실제 실행하거나 원본 자료를 분석한 명령이 아닙니다. 파일명과 문서용 주소는 실제 조사 조건으로 바꿔야 합니다. 출력 파일은 새 이름을 사용합니다. [3]

tcpdump -r original.pcap -w focus.pcap 'host 192.0.2.10'
wireshark -r focus.pcap

첫 명령의 -r original.pcap은 저장 파일을 입력으로 읽습니다. -w focus.pcap은 선택한 패킷을 새 캡처 파일로 씁니다. 뒤의 host 192.0.2.10은 그 주소가 출발지이거나 목적지인 패킷을 선택하는 조건입니다. 두 번째 명령은 만들어진 파일을 Wireshark에서 엽니다. -w로 패킷을 저장하는 것과 화면의 요약 문장을 텍스트 파일로 저장하는 것은 다릅니다. [3] [4]

이때 중요한 비용이 있습니다. 범위를 좁히면 읽기 쉬워지지만 맥락도 빠질 수 있습니다. 특정 주소의 통신만 남기면 그 전에 다른 주소와 주고받은 인증·이름 조회·프록시 통신은 제외될 수 있습니다. 특정 포트나 페이로드 조건을 너무 일찍 적용하면 연결의 일부만 남을 수도 있습니다. 원본을 유지하고, 파생 파일을 만든 명령과 선택 이유를 기록해야 다시 범위를 넓힐 수 있습니다.

또한 ‘큰 파일은 항상 tcpdump가 처리하고 Wireshark는 못 한다’는 절대적인 규칙은 아닙니다. 파일 크기, 메모리, 디섹터와 설정, 실제 분석 작업에 따라 처리 부담이 달라집니다. 도구의 우열보다 필요한 정보를 잃지 않고 검토할 수 있는 작업 흐름을 만드는 것이 목적입니다.

추출은 돋보기인 동시에 선택입니다

큰 상자에서 관심 서류만 새 폴더에 옮기면 읽기 쉬워집니다. 하지만 앞뒤 결재 문서를 두고 왔다면 그 폴더만으로 전체 경위를 설명할 수 없겠죠. 관심 패킷을 새 파일에 쓰는 작업도 같습니다. 복사본을 만들었다는 사실과 그 복사본이 조사에 충분하다는 판단은 다릅니다.

예시 명령에서 작은따옴표는 Bash가 필터 표현식을 한 덩어리로 전달하도록 하는 표기입니다. host는 주소를 기준으로 선택하는 필터 항목이며, 방향을 따로 지정하지 않아 출발지 또는 목적지가 해당 주소인 패킷을 고릅니다. -r와 -w 뒤는 각각 입력·출력 파일명입니다. 이 예시에는 패킷을 네트워크로 보내거나 원본 파일을 고치는 명령이 없습니다. 다만 출력 이름에 기존 파일을 지정하면 덮어쓸 수 있으므로 실제 작업에서는 새 파일명을 사용합니다. [3] [15]

문서용 주소 192.0.2.10의 패킷을 선택했다고 해서 그 사용자와 관련된 모든 활동을 모았다고 표현하지 마세요. 프록시가 다른 연결을 만들거나 주소 변환이 일어나면 다른 주소의 기록에 단서가 있을 수 있습니다. 필터를 적용하기 전 원본의 시간 범위·관측 위치와 주소 대응을 적고, 파생 파일에는 선택 조건과 만든 시점을 남깁니다.

tcpdump는 사람이 읽는 요약을 출력할 수도 있지만 -w는 선택한 패킷 데이터를 캡처 형식으로 기록합니다. 터미널 화면의 문장을 복사한 텍스트와 같은 결과가 아닙니다. Wireshark에서 열 파일이 무엇인지 확인할 때도 확장자뿐 아니라 실제 파일 형식과 저장한 내용을 봅니다.

4. 시작 화면과 파일 열기를 구분하기

Wireshark를 시작하면 수집 인터페이스, 최근 파일과 도움말 등으로 접근할 수 있습니다. 인터페이스는 유선·무선·루프백 등 패킷을 관측할 통로라고 이해하면 됩니다. 목록에 인터페이스가 보인다는 것과 조사 대상 트래픽이 그곳을 지나간다는 것은 다른 사실입니다. 기존 파일을 분석하려는 경우에는 수집부터 시작할 필요 없이 File → Open에서 캡처 파일을 선택합니다.

명령줄에서 실행 파일을 찾을 수 있는 환경이라면 다음처럼 시작할 수도 있습니다. GUI를 표시할 수 있는 환경이 필요하며, 운영체제와 설치 경로에 따라 실행 방법이 다를 수 있습니다. 여기서는 Bash 같은 셸의 예시를 사용합니다. [4]

wireshark
wireshark &
wireshark -r sample.pcap
wireshark sample.pcap &

wireshark는 프로그램을 실행합니다. 끝의 &는 Wireshark의 옵션이 아니라 셸에서 작업을 백그라운드로 실행하는 표기입니다. 터미널에서 다음 명령을 입력할 수 있게 하지만, GUI를 없애거나 원격 환경에 화면을 자동으로 만들어 주지는 않습니다. 이 표기가 모든 셸에서 똑같이 동작한다고 가정하지 않습니다.

-r sample.pcap은 열 파일을 명시하는 방법입니다. 공식 매뉴얼은 파일명을 위치 인자로 주는 방법도 지원하므로 마지막 줄처럼 쓸 수도 있습니다. 파일명에 공백이 있으면 셸에 맞게 인용해야 합니다. 이 명령들은 사용법이며 실행 성공이나 캡처 내용을 확인한 결과로 제시하지 않습니다. [4]

2021년 화면과 현재 환경의 아이콘·메뉴 배치가 완전히 같다고 기대하지 마세요. 공식 사용자 가이드에서도 메뉴, 도구 모음, 표시 필터, 패킷 목록·상세·바이트, 상태 표시줄이라는 기본 역할은 유지됩니다. 화면 위치를 외우기보다 영역의 이름과 역할로 찾아가는 편이 좋습니다. 수집 필터와 표시 필터의 입력 위치는 특히 구분해야 합니다. [5]

파일을 읽는 일과 새로 관측하는 일을 분리합니다

인터페이스(interface)는 여기서 패킷을 수집할 네트워크 접점입니다. 유선·무선 외에 컴퓨터 안의 통신을 관측하는 루프백(loopback)도 있을 수 있습니다. 현재 파일을 읽는다면 그 파일을 만들 때의 인터페이스가 중요하고, 새 캡처라면 지금 고른 접점에 조사할 통신이 흐르는지가 중요합니다. 화면에 작은 활동 그래프가 움직인다는 사실만으로 필요한 방향과 경로를 모두 수집한다는 뜻은 아닙니다.

기존 파일을 열었다면 먼저 파일명을 확인하고, 표시 필터가 남아 있는지와 어떤 프로필을 사용하는지 살펴보세요. 프로필(profile)은 분석 설정을 묶어 관리하는 단위입니다. 같은 파일인데 동료의 화면과 열·색·해석이 다르다면 파일이 다른지뿐 아니라 버전과 프로필·디섹터·재조립 설정도 비교할 필요가 있습니다. 화면 차이를 곧바로 데이터 차이라고 단정하지 않습니다.

wireshark sample.pcap &를 예로 들면 프로그램명, 파일명 인자, 셸 제어 기호라는 세 부분입니다. Bash는 끝의 &를 보고 작업을 비동기로 실행해 다음 명령을 받을 수 있게 합니다. Wireshark가 열릴 그래픽 세션이 없으면 이 기호만 붙여 해결되지 않습니다. 이번 글의 명령은 사용법이며 해당 GUI 실행에 성공했다는 기록이 아닙니다. [16]

도움말과 사용자 가이드는 메뉴를 찾지 못할 때 돌아갈 지도입니다. 오래된 교재의 아이콘 모양이나 버튼 위치가 다르더라도 이름·역할을 기준으로 찾아보세요. 모든 메뉴를 이번에 다 외우기보다 파일 열기, 선택 패킷의 구조 확인, 필터 적용과 해제라는 기본 작업을 설명할 수 있게 만드는 것이 목표입니다.

5. 세 패널은 같은 패킷을 다른 수준으로 보여 준다

상단 메뉴는 File에서 파일을 열고 저장하거나, Capture에서 수집을 제어하고, Analyze와 Statistics에서 분석·통계 기능을 여는 출발점입니다. 도구 모음은 자주 쓰는 동작에 빠르게 접근하는 버튼입니다. 모든 기능이 첫 화면에 보이는 것은 아니므로 메뉴와 공식 도움말을 함께 사용합니다.

파일을 연 뒤에는 위에서 아래로 읽는 흐름을 익혀 보세요. Packet List에서 관심 있는 한 줄을 선택하면, Packet Details가 그 패킷의 프로토콜 구조를 보여 주고, Packet Bytes가 해당 데이터의 바이트를 보여 줍니다. 서로 다른 세 증거 파일이 아니라 같은 선택을 다른 수준으로 보는 것입니다. [5]

목록의 Time은 시각, Source와 Destination은 표시된 출발지·목적지, Protocol은 도구가 해석한 프로토콜, Length는 해당 열의 프레임 길이 정보, Info는 요약 설명입니다. 표시 열과 시각 형식은 설정에 따라 달라질 수 있습니다. 주소가 이름으로 표시된다면 실제 숫자 주소와 혼동하지 않도록 확인합니다. [6]

처음에는 한 패킷을 선택하고 ‘왜 이 프로토콜이라고 표시했을까’를 질문해 보세요. 상세 패널에서 계층 옆의 펼침 표시를 누르면 관련 필드가 나옵니다. Ethernet II의 유형 값이 IPv4를 가리키고, IPv4의 Protocol 값이 ICMP를 가리키는 식으로 해석의 연결을 따라갈 수 있습니다. 목록의 Info 문장만 읽는 것보다 판단 근거가 구체적이 됩니다.

한 패킷을 골라 세 번 묻습니다

첫째, 목록에서 “어느 기록을 선택했는가”를 확인합니다. 둘째, 상세에서 “어느 계층의 어떤 필드를 읽는가”를 확인합니다. 셋째, 바이트에서 “그 값이 어느 위치와 폭으로 저장돼 있는가”를 확인합니다. 예를 들어 목록에 ICMP라고 나왔다면 IPv4의 Protocol 값과 이어지는 ICMP 구조를 펼쳐 보고, 관심 필드를 선택해 바이트와 대조합니다.

목록 한 줄은 파일의 패킷 기록 하나에 대응합니다. 응용 요청 하나, 사용자 행동 하나, 파일 하나와 항상 일대일로 대응하지는 않습니다. TCP의 한 메시지가 여러 패킷에 나뉘거나, 한 패킷에 여러 메시지 일부가 함께 담길 수 있습니다. 색상과 Info 문장은 탐색에 도움이 되지만 색 하나를 공격 성공의 증거로 취급하지 않습니다.

상세 트리는 운영체제의 파일 폴더처럼 항목을 펼쳐 안쪽을 보는 구조입니다. Ethernet II를 펼치는 것과 IP 아래의 길이 필드를 펼치는 것은 서로 다른 계층을 자세히 보는 작업입니다. 선택 패킷을 바꾸면 아래 두 패널의 대상도 바뀌므로, 다른 패킷을 누른 뒤 이전 필드의 값으로 메모하지 않도록 기록 번호·시각·주소를 함께 확인하세요. [6] [7]

6. 상세 패널의 해석과 바이트의 존재를 구별하기

Packet Details는 선택한 패킷을 프로토콜 트리로 보여 줍니다. Frame, Ethernet II, Internet Protocol, ICMP 같은 항목이 보인다면 한 패킷 안에서 서로 다른 계층과 캡처 정보를 보는 것입니다. Frame의 수집 메타데이터 전체가 Ethernet 헤더 안에 들어 있다는 뜻은 아닙니다.

필드를 선택하면 바이트 패널에서 관련 위치를 대조할 수 있습니다. 예를 들어 IPv4 Total Length를 골랐다면 앞서 배운 두 바이트 필드와 표시된 값이 연결되는지 확인합니다. 다만 상세 패널에 보이는 모든 정보가 회선에서 온 헤더 필드는 아닙니다. Wireshark가 계산하거나 분석해 추가한 정보도 있습니다. 공식 가이드는 생성된 정보를 대괄호로 표시하며 응답 시간, TCP 분석, 체크섬 검증 등을 예로 듭니다. 이를 원래 패킷에 적혀 있던 값과 구분해야 합니다. [7]

Packet Bytes의 기본 덤프에는 오프셋과 16진수 바이트, 문자 표현이 나옵니다. 오프셋은 그 데이터 소스의 시작 기준 위치이고, 문자 영역의 점은 표시하기 어려운 바이트일 수 있습니다. 점이 많다는 이유만으로 암호화나 악성을 확정하지 않습니다. [8]

현재 바이트 패널에는 재조립되거나 복호화된 데이터 등 여러 데이터 소스 탭이 나타날 수도 있습니다. 그러므로 ‘이 패널의 오프셋 0은 항상 원래 Ethernet 프레임 시작이다’라고 생각하면 안 됩니다. 지금 어떤 탭과 어떤 데이터 소스를 보고 있는지 먼저 확인하세요. 다음 절은 원래 프레임 바이트를 선택했다는 전제로 읽습니다. [8]

생성된 설명과 저장된 바이트는 다른 근거입니다

Frame은 선택 기록의 캡처 정보를 읽는 출발점이고, Ethernet은 링크의 전달 형식입니다. 둘이 트리에서 함께 보인다는 이유로 Frame의 파일 기록 시각이나 수집 인터페이스 정보가 Ethernet 헤더의 일부라고 생각하면 안 됩니다. 패킷 자체의 필드, 캡처 파일의 메타데이터, 분석기가 계산한 정보를 구별하세요.

가령 응답 시간은 요청과 응답을 연결해 분석기가 계산한 정보일 수 있습니다. 계산값이 유용하다고 해서 같은 숫자가 응답 패킷의 헤더에 적혀 있다는 뜻은 아닙니다. 계산에 어떤 기록이 사용됐고 누락이나 다른 시계 기준이 영향을 주는지 확인해야 합니다. 공식 가이드가 설명하는 대괄호 표시는 이런 생성 정보의 단서입니다. [7]

Packet Bytes의 한 줄에는 기본적으로 바이트 위치와 16진수·문자 표현이 나옵니다. 16진수 두 자리가 한 바이트이며, 문자 쪽의 한 글자가 언제나 사람이 읽는 문자 하나를 뜻하지는 않습니다. 표시할 수 없는 바이트는 점으로 대체될 수 있고, 문자 인코딩과 출력 형식에 따라 보이는 모양도 달라집니다.

특히 탭을 바꾸면 출발점도 바뀝니다. 원래 프레임의 오프셋14와 재조립 데이터의 오프셋14는 같은 바이트라고 보장되지 않습니다. 하나는 링크 헤더를 포함한 기록 안의 위치, 다른 하나는 도구가 구성한 데이터 소스 안의 위치일 수 있죠. “바이트14를 봤다”보다 “원래 프레임 탭의 0 기준 오프셋14를 봤다”라고 쓰면 재검토하기 쉽습니다. [8]

7. IPv4 첫 바이트가 맨 앞에 보이지 않는 이유

IPv4를 배울 때 처음 바이트로 45를 보았다고 해서 프레임의 첫 바이트도 45라고 기대하면 안 됩니다. 0x45는 상위 니블이 버전 4, 하위 니블이 IHL 5인 IPv4 헤더의 첫 바이트입니다. IPv4가 시작되는 곳과 현재 덤프가 시작되는 곳이 같아야 맨 앞에 보입니다.

다음은 VLAN 태그 없는 Ethernet II 안에 IPv4/ICMP가 들어 있는 자체 구성 예시입니다. FCS는 캡처에 포함하지 않고 IP 옵션도 없다고 가정합니다. 바이트는 앞부분만 보여 주며, 완전한 프레임이나 실행 출력이 아닙니다.

14               IPv4 첫 바이트 0x45
16~17            IPv4 Total Length · 0x003c = 60바이트

Ethernet II 헤더는 이 전제에서 6 + 6 + 2 = 14바이트입니다. 0부터 세므로 0~13이 헤더이고, 다음 위치인 오프셋 14에서 IPv4가 시작합니다. ‘14번째 바이트’라는 표현은 세는 방식에 따라 혼동될 수 있으므로, 여기서는 정확히 ‘0 기준 오프셋 14, 즉 순서로는 15번째 바이트’라고 구분합니다.

IPv4 Total Length는 IP 시작 기준 오프셋 2~3입니다. 프레임을 기준으로 옮기면 14 + 2 = 16부터 두 바이트입니다. 값 0x003c는 3 × 16 + 12 = 60입니다. IHL 5는 5 × 4 = 20바이트이므로, ICMP는 14 + 20 = 34 위치에서 시작합니다. IP 데이터인 ICMP 메시지는 60 - 20 = 40바이트입니다.

같은 예시에서 FCS를 제외한 프레임 길이는 14 + 60 = 74바이트이고 비트 수는 74 × 8 = 592비트입니다. ICMP Echo를 헤더 8바이트와 데이터로 나눈다면 데이터는 40 - 8 = 32바이트입니다. 이는 가정한 구조에서 계산한 값이며 실제 캡처의 길이나 응답 결과를 확인한 것은 아닙니다.

14와 45를 무조건 외우지 않기

VLAN 태그나 다른 링크 유형, 터널과 다른 데이터 소스에서는 IP 시작 위치가 달라집니다. IPv4도 옵션이 있으면 IHL이 5가 아닐 수 있어 첫 바이트가 45로 고정되지 않습니다. 바이트 배열 어디에서든 45를 찾아 IP 시작이라고 선언하는 대신 링크 형식과 프로토콜 식별자, 헤더 길이를 따라가야 합니다.

값이 같아 보이는 것보다 구조의 연결을 먼저 봅니다

MAC은 Media Access Control의 약자로 Ethernet에서 링크 주소를 나타냅니다. EtherType은 뒤에 담긴 프로토콜 종류를 알려 주는 필드입니다. 예시에서는 목적지6바이트와 출발지6바이트 뒤의 08 00이 IPv4를 가리키기 때문에 그다음에서 IPv4를 해석합니다. 프레임 어딘가에 45가 나타났다는 이유로 그곳부터 읽는 방법과는 근거가 다릅니다.

IHL은 Internet Header Length, 즉 IPv4 헤더 길이 필드입니다. 0x45의 하위 니블5를 읽고 4바이트 단위를 곱해20바이트라고 계산합니다. ICMP는 Internet Control Message Protocol이며, 이 예시의 Echo 요청·응답은 진단에 사용하는 메시지 종류입니다. 여기서는 IP 데이터40바이트 안에 ICMP Echo 헤더8바이트와 데이터32바이트가 들어 있다고 가정한 것입니다. 모든 ICMP 유형의 전체 구조를8바이트로 단순화하지 마세요.

이번에는 IP 옵션이 생겨 첫 바이트만 46인 가상 조건을 보겠습니다. IP 전체 길이60바이트는 그대로라고 가정하면 IHL6×4=24바이트입니다. 태그 없는 Ethernet II의 IP 시작14는 같지만 ICMP 시작은 14 + 24 = 38로 옮겨집니다. IP 데이터는 60 − 24 = 36바이트이며 Echo의8바이트를 빼면28바이트입니다. 이 변화는 실제 완성 패킷을 수정·전송한 결과가 아니라 경계 계산 연습입니다.

다른 조건으로 원래 IP 헤더20바이트를 유지하고 단일 VLAN 태그4바이트가 추가되면 링크 헤더는18바이트입니다. IP 시작18, Total Length는20~21, ICMP 시작38이 됩니다. 앞의 IHL 변경과 ICMP 시작값이 우연히 같아도 원인은 다릅니다. 프레임 기준 위치만 보지 말고 링크와 IP 각 헤더 길이를 함께 확인해야 합니다.

또 원래74바이트 프레임 중 앞의50바이트만 저장됐다고 해 볼까요? 필요한 헤더34바이트가 모두 저장돼 있고 원래 프레임 바이트를 본다는 전제에서, 파일에 남은 ICMP 메시지 부분은 50 − 34 = 16바이트입니다. 그 안의 Echo 데이터는 16 − 8 = 8바이트뿐입니다. 헤더가 가리키는 데이터32바이트 전체를 확보했다는 뜻은 아닙니다. 저장 길이와 원래 길이를 대조하고 잘림과 실제 전송 손실을 구별하세요.

8. 표시 필터는 지우는 기능이 아니다

패킷이 많으면 상단의 표시 필터 입력란으로 화면을 좁힐 수 있습니다. 예를 들어 icmp를 입력하고 Enter 또는 적용 버튼을 사용하면 ICMP로 해석되는 패킷에 집중할 수 있습니다. ip.addr == 192.0.2.10은 해당 IPv4 주소가 출발지 또는 목적지인 패킷을 고르는 표시 필터 예시입니다. 입력만 한 상태와 실제로 적용한 상태를 구분하세요. [1]

표시 필터는 관심 없는 패킷을 현재 화면에서 숨깁니다. 파일에서 삭제하지 않으므로 필터를 지우면 다시 보입니다. 반대로 수집 필터는 수집 단계에서 어떤 패킷을 받아들일지 제한합니다. 애초에 수집하지 않은 내용을 나중에 표시 필터를 지워 되살릴 수는 없습니다. 두 필터는 언어도 달라 tcpdump의 host 192.0.2.10과 Wireshark 표시 필터의 ip.addr == 192.0.2.10을 입력란 구분 없이 옮기면 안 됩니다. [1] [3]

상태 표시줄은 현재 파일의 패킷 수와 표시된 수, 선택한 설정 프로필 등을 확인하는 데 도움이 됩니다. 가령 파일 안의 패킷 1,000개 중 25개가 보인다면 현재 화면의 비율은 25 ÷ 1000 × 100 = 2.5%입니다. 이 가상 수치는 필터 결과의 비율이지 ‘네트워크 전체의 공격 비율’이 아닙니다. 원래 수집 범위와 필터 조건이 분모를 정하기 때문입니다. [9]

패킷 번호가 중간중간 건너뛰어 보인다면 표시 필터로 다른 패킷이 숨겨졌을 수 있습니다. 반대로 상태 표시줄에 손실 정보가 없거나 손실 0으로 보인다고 네트워크 전 구간의 완전한 수집이 증명되는 것도 아닙니다. 센서가 관측하지 않는 경로의 통신은 그 숫자에 포함되지 않을 수 있습니다.

짧은 식도 각 부분의 뜻을 알고 씁니다

icmp는 프로토콜이 해석되어 존재하는지를 고르는 식입니다. ip.addr == 192.0.2.10에서 ip.addr는 IPv4 주소 필드, ==는 값 비교, 오른쪽은 문서용 주소 상수입니다. 표시 필터는 실제 필드의 해석 결과를 대상으로 하므로 단순 문자열 찾기와 같지 않습니다. 이 예시들은 문서로 문법을 대조한 것이며 이번 실행에서 GUI에 적용한 출력은 아닙니다. [14]

25개 중 일부가 요청이고 일부가 응답이라면, 표시 비율2.5%와 특정 행위의 비율도 달라집니다. 패킷 수, 연결 수, 요청 수, 바이트 합계는 서로 다른 단위입니다. 분모를 현재 파일의 기록 수로 썼는지, 필터가 적용된 통신 수로 썼는지 남기세요. 정밀해 보이는 백분율도 수집과 선택 범위를 벗어나 일반화할 수는 없습니다.

9. 대화·통계·객체 기능이 보여 주는 범위

Conversations는 두 종단 사이의 통신을 묶어 수량과 시간을 살펴보는 기능입니다. Statistics → Conversations에서 계층별 주소, 패킷과 바이트 수, 지속시간 등을 확인할 수 있습니다. IP 주소 쌍으로 묶은 통계와 포트를 포함한 TCP 통계는 묶는 단위가 다릅니다. 필터에 맞는 통신만 제한해 보는 설정도 있으므로, 통계 값을 기록할 때 선택 탭과 필터 범위를 함께 남깁니다. [10]

Follow Stream은 선택한 통신의 데이터를 양방향 또는 방향별로 이어서 보는 데 도움이 됩니다. 패킷을 선택하고 Analyze → Follow 아래에서 지원되는 항목을 고릅니다. TCP는 순서 있는 바이트 스트림이므로 재조립이 중요합니다. UDP에도 Follow 기능이 있지만, 이는 관련 데이터그램을 모아 읽는 도구의 기능입니다. UDP 자체가 TCP 같은 전달·순서 보장 기능을 얻는 것은 아닙니다. 관련 메뉴가 없으면 선택 패킷에서 해당 프로토콜이 식별되었는지 확인합니다. [11]

이어진 화면이라고 해서 내용이 완전하다는 보증은 없습니다. 캡처 누락, 세션 중간 수집, 충돌하는 바이트의 처리와 암호화가 영향을 줍니다. 특히 TLS 데이터를 순서대로 보았다는 것과 평문 HTTP를 읽었다는 것은 다릅니다. 적절한 세션 비밀정보 등 복호화 조건이 갖추어져야 내용 분석을 더 진행할 수 있습니다. [2]

Export Objects는 지원되는 프로토콜에서 재구성한 객체를 파일로 꺼내 별도로 조사하는 기능입니다. 예를 들어 해석 가능한 HTTP 전송에 포함된 문서나 이미지가 대상일 수 있습니다. 모든 통신에서 임의의 원본 파일을 복원하는 기능은 아닙니다. 지원 프로토콜, 확보된 바이트, 재조립·복호화 조건을 확인하고, 추출한 결과가 무엇을 근거로 만들어졌는지 기록해야 합니다. 이 절의 HTTP 객체 추출은 사용법 설명입니다. 추가 확보한 첫째 날 실습 파일의 오프라인 검증을 HTTP 객체 추출 성공으로 표시하지 않습니다. [12]

이런 기능이 있기 때문에 암호화 환경에서도 Wireshark 학습은 유용합니다. 주소·길이·시점과 연결 흐름을 검증하고, 관측 가능한 필드와 가려진 내용을 구분할 수 있습니다. 다만 응용 프로그램이 실제로 무엇을 실행했는지는 서버·단말 로그와 연결해야 합니다. 도구의 해석 화면이 공격 성공 판정을 자동으로 대신하지는 않습니다.

대화를 묶는 기준과 데이터를 읽는 기준을 구별합니다

같은 두 IP 사이에 웹·이름 조회·다른 서비스가 함께 있을 수 있습니다. IP Conversations에서 하나로 묶인 주소 쌍이 TCP 탭에서는 서로 다른 포트 조합의 여러 항목으로 보일 수 있죠. 종단(endpoint)은 선택 계층에서 통신의 한 끝을 뜻합니다. 어느 계층·어느 필터·어느 시간 범위인지 적지 않은 통계는 다른 사람이 같은 수치를 재현하기 어렵습니다.

Follow에서 방향별 데이터를 보면 요청과 응답을 구별하는 데 도움이 됩니다. 하지만 화면의 색상만 외워 누가 보냈는지 정하지 말고, 해당 창에 표시된 주소·포트·방향과 원래 패킷을 확인하세요. TCP는 바이트 위치에 맞추어 데이터를 연결하지만, 누락·겹침·재조립 정책에 따라 실제 수신 프로그램의 해석과 차이가 있을 수 있다는 앞 강의의 조건도 유지합니다.

객체(object)는 여기서 프로토콜이 운반한 문서·이미지 같은 재구성 대상을 말합니다. 캡처 파일 저장은 패킷 기록을, 스트림 저장은 이어 본 데이터나 그 표현을, 객체 내보내기는 해석한 전송 대상물을 남깁니다. 세 파일이 서로를 그대로 대체하지 않습니다. 추출 파일을 조사할 때는 원본 캡처·관련 연결·재구성 조건을 함께 기록하고, 추출 성공만으로 서버 실행이나 사용자 열람까지 증명했다고 쓰지 않습니다.

TLS(Transport Layer Security)는 통신 내용을 보호하는 프로토콜입니다. 암호화 데이터를 이어 놓는 작업과 필요한 세션 정보를 이용해 평문을 얻는 작업은 다릅니다. 내용이 안 보여도 주소·시각·길이·방향 같은 관측 가능한 단서는 남을 수 있지만, 읽지 못한 명령이나 파일 내용을 그 단서만으로 채워 넣지는 않습니다. [2]

10. 화면에서 확인한 사실과 남는 질문

패킷으로 확인 가능한 사실

선택 파일에 확보된 패킷과 바이트, 해석한 계층·필드·길이, 적용 필터에 따른 표시 결과와 관측 범위의 통계입니다. 계산·생성 정보는 원래 필드와 구분합니다.

단독으로 확정할 수 없는 부분

수집 밖의 응답과 경로, 프로그램·사용자 신원, 암호화 본문의 의미, 공격 의도와 성공 여부입니다. 패킷이 안 보인다는 이유만으로 무해하거나 완전히 차단되었다고 확정하지 않습니다.

함께 확인할 자료

수집 지점·인터페이스·링크 유형·손실 기록, 원본과 추출 명령, Wireshark 버전·프로필·필터, 단말 프로세스·연결 기록, 서버·프록시·방화벽 로그입니다.

예를 들어 “현재 파일의 ICMP 표시 필터에서25개를 보았다”는 관측이고, “서버 진단 작업일 수 있다”는 가설입니다. “모두 승인된 점검이며 침해는 없다”는 결론에는 자산·작업 승인·단말 프로세스·관련 로그 같은 근거가 더 필요합니다. 도구가 메시지 유형을 올바르게 표시했더라도 그 활동의 의도와 최종 영향까지 자동으로 따라오지는 않습니다.

응답이 없으면 수집 시간·방향·다른 경로·누락·잘림·필터를 먼저 확인하고, 실제 차단 여부는 방화벽 조치와 서버 측 기록으로 좁힙니다. 자료를 연결할 때도 주소와 시각만 비슷하다는 이유로 합치지 말고, 연결·요청 식별자·계정·프로세스 등 연결 가능한 근거와 시계 기준을 맞추세요.

11. 복습 — 화면을 읽는 순서를 설명해 보기

다음은 자체 구성 문제입니다. 실제 파일이 준비되면 같은 순서로 따라가 볼 수 있지만, 이번 노트가 제공되지 않은 실습의 실행 결과를 대신하지는 않습니다.

질문 1: 목록에서 한 패킷을 클릭한 뒤 무엇을 확인하면 좋을까요?

해설: 상세 패널에서 어떤 계층으로 해석했는지 펼친 뒤, 관심 필드를 선택하고 바이트 패널의 해당 위치와 비교합니다. 표시된 값이 어떤 바이트와 단위에서 나왔는지 확인합니다. 분석기가 생성한 값이라면 원시 헤더 필드와 구분해서 적습니다.

질문 2: Ethernet II 프레임 덤프의 첫 바이트가 45가 아닙니다. IPv4가 아니라고 판단해도 될까요?

해설: 아닙니다. VLAN 태그 없는 Ethernet II 예시에서는 앞의 14바이트가 Ethernet 헤더입니다. EtherType이 IPv4를 가리키는지 확인한 뒤 오프셋 14에서 IP 헤더를 읽습니다. IPv4 자체도 IHL에 따라 첫 바이트가 달라질 수 있습니다. 임의의 45 검색보다 구조를 따라갑니다.

질문 3: 표시 필터를 적용해 1,000개 중 25개만 보입니다. 975개가 파일에서 지워졌을까요?

해설: 표시 필터라면 숨긴 것입니다. 필터를 해제하면 다시 볼 수 있습니다. 현재 표시 비율은 2.5%이지만, 이를 전체 네트워크의 사건 비율로 해석하지 않습니다. 처음 수집한 범위와 선택 조건을 함께 기록합니다.

질문 4: wireshark sample.pcap &의 &는 캡처 옵션일까요?

해설: 여기서는 Bash 같은 셸의 백그라운드 실행 표기입니다. 파일을 여는 인자는 sample.pcap이고, 공식적으로 -r로 명시할 수도 있습니다. &는 GUI를 없애거나 캡처를 자동으로 시작한다는 뜻이 아닙니다.

질문 5: UDP Follow 화면이 열렸다면 UDP도 TCP처럼 재전송과 순서 보장을 할까요?

해설: 도구가 관련 데이터를 읽기 좋게 모아 보여 주는 기능과 프로토콜 자체가 제공하는 보장은 다릅니다. UDP의 상위 프로토콜이 별도 기능을 구현할 수는 있지만, Follow 메뉴가 열렸다는 사실로 그런 기능의 존재나 통신 완전성을 확정하지 않습니다.

질문 6: 대상 주소만 추출한 파일에서 관련 응답이나 HTTP 객체가 없습니다. 조사를 끝내도 될까요?

해설: 추출 조건으로 맥락이 빠졌는지 원본으로 돌아가 확인합니다. 다른 경로, 프록시 연결, 암호화, 수집 누락과 디섹터의 해석 조건도 검토합니다. 확보된 자료에 없다는 관측을 실제 활동이 없었다는 결론으로 바꾸지 않습니다.

선택한 파일에서 대상 주소의 패킷을 표시했다. 관심 패킷의 계층과 필드를 상세 패널에서 확인하고 원래 프레임 바이트를 대조했다. 적용한 필터·데이터 소스·캡처 범위를 기록했으며, 응용 처리 결과와 관측 밖 활동은 추가 로그로 확인한다.

조건을 바꾼 추가 복습

문제 7. http.request.method == "GET"은 바이트 어디에나 GET이 있으면 일치하나요?

해설: 아닙니다. 해당 데이터가 HTTP 요청 메서드 필드로 해석되고 그 값이 GET과 같아야 합니다. 해석되지 않음·누락·암호화·다른 구간을 구별하고, 일치 자체를 악성 판단으로 바꾸지 않습니다.

문제 8. 원래 프레임 탭과 재조립 탭의 오프셋0은 같은 출발점인가요?

해설: 보장되지 않습니다. 각 데이터 소스의 시작 기준입니다. 원래 링크 헤더가 포함된 프레임인지, 여러 패킷에서 구성한 데이터인지 탭을 확인하고 기준점을 기록합니다.

문제 9. IP전체60바이트에서 IHL만6인 예시의 ICMP 시작과 Echo 데이터는요?

해설: 태그 없는 Ethernet II를 가정하면 IP헤더6×4=24바이트, ICMP시작14+24=38입니다. IP데이터60−24=36, Echo헤더8을 빼면28바이트입니다. 계산 연습이며 실제 완성 패킷의 실행 결과는 아닙니다.

문제 10. 원래 IP헤더20바이트에 단일 VLAN태그4바이트가 붙으면요?

해설: 링크 헤더가18바이트인 그 조건에서 IP시작18, Total Length20~21, ICMP시작18+20=38입니다. 앞 문제와 같은38이어도 원인은 다릅니다. 링크와 IP길이를 각각 확인합니다.

문제 11. 74바이트 프레임 중 앞50바이트만 저장됐다면 Echo데이터32바이트를 읽을 수 있나요?

해설: 원래 프레임 탭에서 필요한 헤더가 모두 저장됐다는 전제에서 ICMP부분은50−34=16바이트, Echo데이터는16−8=8바이트만 남습니다. 원래 길이를 안다는 것과 본문을 확보했다는 것은 다릅니다.

문제 12. 상세 패널의 응답시간 숫자는 응답 헤더의 원래 필드인가요?

해설: 분석기가 관련 패킷을 연결해 계산한 생성 정보일 수 있습니다. 원시 필드·캡처 메타데이터·생성 정보를 구분하고, 계산에 사용한 기록과 누락·시각 조건을 확인합니다.

문제 13. 추출본을 열고 표시필터를 지웠는데 다른 주소 통신이 안 보입니다. 없었던 통신인가요?

해설: 추출 단계에서 제외됐다면 현재 파일의 표시필터 해제로 되살아나지 않습니다. 보존한 원본과 추출 명령으로 돌아가 시간·주소·포트·경로 범위를 검토합니다.

문제 14. IP대화1개와 TCP대화1개의 바이트 수를 같은 단위로 바로 비교할까요?

해설: 묶는 계층·주소/포트·필터 범위가 같은지 먼저 확인합니다. 한 IP주소 쌍에 여러 TCP연결이나 다른 프로토콜이 있을 수 있습니다. 어느 통계를 무엇의 분모로 썼는지 남깁니다.

문제 15. 파일에서 객체를 추출했다면 사용자가 그 파일을 실행한 것인가요?

해설: 추출은 확보된 통신을 해석해 파일을 구성한 결과입니다. 실제 수신·저장·열람·실행 여부는 별도 단말·서버 기록으로 검증해야 합니다. 캡처 누락과 재구성 조건도 함께 남깁니다.

문제 16. 동료와 같은 파일인데 화면이 다릅니다. 누구 분석이 틀렸나요?

해설: 파일·선택 패킷·필터·버전·프로필·데이터 소스·재조립·표시 설정을 먼저 맞춥니다. 조건이 다른 화면만 비교해 정답을 고르면 원인을 놓칠 수 있습니다. 필요한 경우 원래 바이트와 명세로 돌아갑니다.

다음7강에서는 파일 속성과 프로토콜·대화 통계로 조사 범위를 정합니다. 이번에 익힌 “어느 파일·필터·계층·데이터 소스인가”라는 질문이 통계의 분모와 의미를 확인하는 기준이 됩니다.

워크북 연계 실습

통계·세 창·헤더 강조·검색을 순서대로 연결합니다. Wireshark 탐색 실습에서 단계별 설명과 복습을 읽을 수 있습니다. 이 페이지의 기존 자체 예시는 그대로 유지하며, 원본 PCAP을 실행한 출력으로 제시하지 않습니다.

교재는 화면 역할과 탐색 원리를, 전자 워크북은 같은 자료를 도구로 읽는 순서를, PCAP은 저장된 관측 바이트를 제공합니다. 기존 검토에서는 첫째 날 여섯 캡처의621개 기록을 오프라인으로 대조했습니다. 그것은 이번 실행에서 Wireshark GUI나 tcpdump/TShark를 다시 실행했다는 뜻은 아닙니다.

연계 연습에서는 목록에서 패킷을 고르고, 상세에서 Ethernet Type·IP Protocol·헤더 길이를 펼친 뒤 해당 바이트를 확인하세요. 검색이나 통계로 옮기기 전에 필터·데이터 소스·기준점부터 메모합니다. 원본 화면과 버전이 다르면 가이드의 기능 이름을 따라가며 차이를 확인하고, 없는 결과를 예상 답에 맞추어 꾸미지는 마세요.
