둘째 날 5강 · TCP의 연결과 바이트 순서

교재 인쇄 59~69쪽의 TCP 기초·포트·순서 번호·확인 번호·상대 번호를 항목별로 대조했습니다. TCP 워크북의 재시도 구별 문제와 순서가 겹치는 문제의 기초 분석을 연결합니다. 별도 표시가 없는 흐름과 주소는 가상 학습 예제입니다. 실제 제공 파일의 저장 바이트 검산과 tcpdump·Wireshark·VM 실행은 구별합니다.

1. 여러 봉투로 나눈 문서를 순서대로 읽으려면

긴 문서를 여러 봉투에 나누어 보낸다고 해봅시다. 봉투가 순서대로 도착한다는 보장이 없고, 하나가 늦게 오거나 같은 내용이 두 번 올 수도 있습니다. 받는 사람은 내용을 순서대로 정리하고 비어 있는 부분을 알아야 합니다. 보내는 사람은 어디까지 도착했는지 알아야 다음 내용을 관리할 수 있습니다. TCP의 순서 번호와 확인 번호는 이런 문제를 해결하는 데 사용됩니다.

하지만 봉투 번호를 1·2·3으로 붙인다는 비유를 그대로 외우면 곧 혼동하게 됩니다. TCP는 패킷마다 하나씩 증가하는 번호를 붙이지 않습니다. 한 방향의 바이트 흐름에 위치를 정하고, 그 세그먼트가 어느 위치부터 시작하는지 헤더에 적습니다. 100바이트를 한 세그먼트에 넣어 보내든 두 세그먼트에 나누어 보내든 같은 데이터의 바이트 위치는 이어져야 합니다.

이 차이를 알면 “패킷이 또 보인다”는 사실에서 더 구체적인 질문으로 나아갈 수 있습니다. 같은 바이트 범위를 다시 보낸 것인지, 다음 범위를 처음 보낸 것인지, 같은 범위인데 내용이 바뀌었는지 살펴볼 수 있습니다. 반대로 패킷 개수만 세면 전송량과 재전송을 구별하기 어렵습니다.

이번 강의에서는 먼저 하나의 TCP 연결 안에 두 방향의 번호 공간이 있다는 점을 이해합니다. 그다음 포트와 연결 식별자, SEQ와 ACK의 계산, 상대 번호 표시를 차근차근 연결합니다. 플래그의 모든 역할과 상태 전이는 다음 강의로 이어가되, 여기서는 SYN·FIN이 번호 공간을 하나씩 쓴다는 계산에 필요한 사실부터 사용합니다.

2. 신뢰성은 끝없이 성공한다는 보장이 아닙니다

TCP는 응용 프로그램에 순서가 있는 바이트 스트림을 제공하는 신뢰성 있는 전송 프로토콜입니다. 받은 범위를 알리는 ACK, 손실에 대응하는 재전송, 순서가 바뀐 데이터의 정리 같은 장치가 있습니다. 신뢰성이라는 말은 연결이 언제나 성립하고 아무리 오래 장애가 나도 반드시 전달을 끝낸다는 약속이 아닙니다. 통신을 계속할 수 없으면 오류나 시간 초과로 끝날 수 있습니다.

또한 보내는 응용 프로그램의 쓰기 호출이 성공했다고 원격 응용 프로그램이 데이터를 처리하거나 저장한 것은 아닙니다. 보통은 로컬 전송 버퍼에 데이터가 받아들여졌다는 단계와 구별해야 합니다. 이후 TCP ACK가 왔다고 해도 원격 TCP의 수신 범위를 알려주는 것이지 파일 저장·결제·로그인 성공을 직접 확인하는 것은 아닙니다. 어느 계층의 성공인지 문장에 붙여 주세요.

수신자가 감당할 수 있는 속도도 중요합니다. 보내는 쪽이 너무 많은 데이터를 밀어 넣으면 수신 버퍼와 응용 처리가 따라가지 못할 수 있습니다. TCP는 수신자가 알리는 윈도 같은 정보를 통해 수신 여유를 고려하는 흐름 제어를 합니다. 이것은 길을 공유하는 다른 트래픽과 네트워크의 혼잡을 다루는 혼잡 제어와 관련은 있지만 같은 기능은 아닙니다. 구체적인 윈도 계산은 뒤 강의에서 다루며, 지금은 수신 확인과 수신 여유가 서로 다른 질문이라는 점을 구별합니다.

원문에서 빠진 데이터를 즉시 알아내고 즉시 재전송을 요청하는 것처럼 읽히는 설명도 조심해야 합니다. 뒤쪽 데이터가 먼저 도착하면 수신 공백을 알 수 있지만, 통신이 조용한 상태에서 마지막 세그먼트가 사라졌다면 다음 번호를 보고 알아챌 기회도 없을 수 있습니다. 송신자는 ACK의 흐름과 타이머 등 여러 근거로 손실을 다룹니다. 매 손실마다 수신자가 별도 재전송 요청 메시지를 즉시 보내는 단일 방식은 아닙니다.

UDP 자체에는 TCP와 같은 순서·누적 ACK·재전송 기능이 없습니다. 그러나 UDP를 사용하는 상위 프로토콜이 그런 기능을 구현할 수 있습니다. 예를 들어 QUIC은 UDP 위에서 신뢰성 있는 스트림을 제공합니다. 따라서 UDP가 보인다고 데이터가 반드시 유실되거나 신뢰성 기능이 전혀 없다고 결론 내리면 안 됩니다. “인터넷의 일정 비율 이상은 항상 TCP”라는 과거 수치도 측정 시기·대상·바이트/패킷 집계가 없으면 현재의 보편 사실로 옮기지 않습니다. [1] [8]

3. 연결은 하나, 관리할 바이트 방향은 둘입니다

A가 B에게 요청을 보내고 B가 A에게 답을 보내면 데이터는 양방향으로 흐릅니다. TCP는 이를 지원하는 하나의 전이중 연결입니다. 전이중은 양쪽이 데이터를 보낼 수 있다는 뜻입니다. 한 방향이 상대의 이야기가 끝날 때까지 차례를 기다려야만 하는 구조가 아닙니다.

기본 TCP 연결은 두 종단 사이의 유니캐스트 통신입니다. 유니캐스트는 특정 한 상대에게 보내는 주소 방식이며, 하나의 TCP 연결을 여러 수신자에게 동시에 뿌리는 멀티캐스트나 브로드캐스트 연결로 이해하지 않습니다. 방송처럼 여러 사용자에게 같은 내용을 전달하는 서비스도 각 사용자와 별도 TCP 연결을 만들거나 다른 전달 계층을 사용할 수 있습니다. 응용 서비스가 여러 사람에게 보인다는 사실과 전송 연결의 상대 수를 구별해야 합니다.

다만 각 방향에서 보낸 바이트 수와 다음에 기대하는 위치는 별도로 관리합니다. A의 데이터 첫 위치가 1001이고 B의 데이터 첫 위치가 7001이어도 정상입니다. A가 100바이트 보냈다고 B 자신의 SEQ가 100 증가하는 것은 아닙니다. B는 ACK 필드로 A의 수신 범위를 알리면서, 자기 데이터가 있으면 자기 SEQ 공간에서 보냅니다.

교재는 이 구별을 강조하려고 두 개의 독립적인 반이중 연결로 생각하라고 설명합니다. 방향별 상태를 나누어 보는 비유로는 도움이 되지만, 실제 TCP 연결이 두 개 만들어지고 서버가 클라이언트의 별도 수신 포트로 새 연결을 거는 것으로 이해하면 틀립니다. SYN/ACK는 같은 연결에서 상대의 시작 번호를 확인하면서 자기 시작 번호도 알리는 세그먼트입니다. 두 번째 별도 연결을 여는 패킷이 아닙니다.

이 구별은 종료 때도 중요합니다. A가 더는 보낼 데이터가 없다고 알린 뒤에도 B가 보내는 방향은 이어질 수 있습니다. 반쪽 닫기라는 동작은 한 연결 안의 방향별 상태로 설명할 수 있습니다. 지금은 “연결 하나”라는 큰 틀과 “번호 공간 둘”이라는 계산 틀을 함께 기억하세요. 구체적인 FIN 교환은 뒤의 종료 강의에서 다룹니다.

4. 스트림·세그먼트·IP 조각은 다른 단위입니다

응용 프로그램이 보낸 바이트 흐름을 스트림이라고 부릅니다. TCP 헤더와 해당 TCP 데이터를 합한 전송 단위는 세그먼트입니다. 한 IP 패킷 안에 TCP 세그먼트가 실릴 때 IPv4 Protocol 값은 6이고, IPv6에서도 TCP를 나타내는 Next Header 값은 6입니다. IPv6 확장 헤더가 있으면 기본 헤더의 Next Header가 바로 6이 아니라 다음 확장 헤더를 가리킬 수도 있습니다.

응용 프로그램이 한 번에 1000바이트를 썼다고 한 개의 TCP 세그먼트가 그대로 만들어진다고 보장되지는 않습니다. TCP는 바이트 스트림을 제공하므로 응용 프로그램의 쓰기 경계와 네트워크 세그먼트 경계가 같을 필요가 없습니다. 여러 쓰기를 합치거나 하나의 쓰기를 나누어 보낼 수 있고, 받는 쪽의 읽기 호출 경계도 다를 수 있습니다. 메시지의 구분은 길이·구분자 같은 응용 규칙으로 따로 처리해야 합니다.

TCP 세그멘테이션과 IP 단편화도 구별합니다. TCP가 스트림을 여러 세그먼트로 나누는 일과, IP가 하나의 데이터그램을 여러 조각으로 나누는 일은 계층과 재조립 대상이 다릅니다. IP 조각마다 완전한 TCP 헤더가 새로 붙는 것도 아닙니다. 두 작업을 모두 단순히 조각이라고 부르면 오프셋과 길이를 읽을 때 기준점이 섞입니다.

호스트에서 캡처하면 오프로딩 때문에 실제 선로에서 보이는 크기와 다른 큰 데이터 단위가 관측될 수도 있습니다. 이를 무조건 잘못된 거대 패킷이나 공격으로 분류하지 않습니다. 캡처 위치와 네트워크 인터페이스의 동작을 확인한 뒤, 저장된 프레임·IP 데이터그램·TCP 세그먼트·고유 스트림 바이트 중 무엇을 세는지 기록해야 합니다.

5. 헤더에서 포트와 두 번호의 자리를 찾기

TCP 시작점을 0으로 두면 첫 2바이트는 출발지 포트, 그다음 2바이트는 목적지 포트입니다. 오프셋 4~7은 SEQ, 8~11은 ACK 번호입니다. 두 번호는 각각 32비트이며 네트워크 바이트 순서로 저장됩니다. 주소는 TCP 헤더에 다시 쓰이지 않고 IP 헤더에서 가져옵니다. 그래서 연결을 식별할 때 두 계층의 정보를 함께 읽습니다.

앞 강의에서 다룬 Data Offset은 tcp[12]의 위 니블입니다. 그 값에 4를 곱하면 TCP 헤더 길이가 되고 옵션이 있으면 20바이트보다 길어집니다. 플래그 바이트는 tcp[13]입니다. ACK 번호는 tcp[8:4]에 숫자로 존재하고, 그 숫자를 확인 번호로 유효하게 읽을지는 ACK 플래그와 연결 맥락을 함께 봅니다. “ACK 비트”와 “ACK 번호”는 같은 필드가 아닙니다.

예를 들어 ACK 비트가 꺼진 SYN에 ACK 번호 필드의 원시 값이 0이 아닌 수로 채워져 있어도, 그 수를 상대가 받은 범위로 사용하지 않습니다. 필드가 물리적으로 있다는 사실과 프로토콜상 의미가 유효하다는 사실을 나누는 것입니다. 뒤에서 보는 실제 실습 표본에도 이런 경우가 있습니다.

표의 오프셋은 TCP 기준입니다. Ethernet 시작에서 무조건 같은 숫자만큼 건너뛰는 식으로 읽으면 IPv4 옵션·링크 유형·VLAN 등에 따라 잘못된 자리를 볼 수 있습니다. 이번 저장 바이트 검산에서는 파일 형식과 링크 타입을 확인한 뒤 IP 헤더 길이로 TCP 시작을 찾고 각 필드를 읽었습니다.

6. 포트 443이 프로그램의 신분증은 아닙니다

IP 주소를 건물에 비유하면 포트는 그 안의 통신 창구에 비유할 수 있습니다. TCP의 출발지·목적지 포트는 각각 16비트여서 비트로 표현할 수 있는 값은 0~65535입니다. 포트가 많기 때문에 한 호스트가 여러 서비스를 제공하고 여러 상대와 동시에 통신하는 데 도움이 됩니다. 그러나 이 숫자만으로 사용자의 이름이나 프로그램의 파일명을 알 수 있는 것은 아닙니다.

IANA는 System Ports 0~1023, User Ports 1024~49151, Dynamic/Private Ports 49152~65535로 구간을 나눕니다. 이것은 등록과 할당의 분류입니다. 실제 운영체제가 자동으로 출발지 포트를 고르는 범위와 항상 일치한다는 뜻은 아닙니다. 또한 1024 이상이라고 서버용 포트가 될 수 없는 것도 아닙니다. [2]

목적지 443을 보면 HTTPS 계열 서비스를 먼저 검토할 수는 있습니다. 그러나 포트 번호 자체가 실제 응용 프로토콜을 인증해 주지는 않습니다. 다른 프로그램이 그 포트에서 동작할 수 있고, 중간 프록시나 포트 전달 때문에 관측 지점의 포트가 종단의 내부 포트와 달라질 수도 있습니다. 반대로 암호화되어 응용 내용을 볼 수 없다면 해당 한계까지 적어야 합니다.

클라이언트가 서비스에 처음 접근할 때 목적지 포트를 알고 시작하는 경우가 흔합니다. 그 뒤 서버의 응답에서는 그 서비스 포트가 출발지로 나타납니다. “출발지 포트는 언제나 임시 포트, 목적지 포트는 언제나 서비스 포트”라는 식으로 모든 패킷을 읽으면 응답 방향을 뒤집어 해석하게 됩니다. 역할은 연결 시작과 양방향 맥락에서 판단하세요.

7. 임시 포트의 선택·재사용·0번을 구별하기

임시 포트는 보통 운영체제가 연결을 시작하는 소켓에 잠시 배정하는 로컬 포트입니다. 선택 방식과 범위는 운영체제·버전·설정에 따라 달라질 수 있습니다. 현재 확인한 Linux 커널 문서는 ip_local_port_range의 기본 경계를 32768과 60999로 설명합니다. 교재의 오래된 범위 표를 모든 현재 호스트의 규칙으로 쓰지 않고 실제 설정을 확인할 출발점으로 삼으세요. [3]

출발지 포트가 매 시도마다 반드시 1씩 증가하거나, 다른 새 연결이면 반드시 다른 값이어야 한다는 일반화도 피합니다. 포트 선택과 재사용에는 목적지, 연결 상태, 할당 정책 같은 조건이 관여합니다. 다른 목적지를 향하는 연결에 같은 로컬 포트가 보일 수 있고, 시간이 지난 뒤 같은 번호가 재사용될 수도 있습니다. 따라서 포트 하나의 변화만으로 재전송인지 새 연결인지 결정하지 않습니다.

일반적인 소켓 API에서 bind의 포트 값으로 0을 주는 것은 “커널이 사용 가능한 포트를 골라 달라”는 요청입니다. 그대로 0번을 서버의 실제 서비스 포트로 쓰라는 뜻이 아닙니다. IANA에서 포트0은 예약되어 있습니다. 하지만 헤더의 16비트 공간에는 0을 담을 수 있으므로 조작된 패킷이나 비정상 트래픽의 저장 파일에서 0을 관측할 수는 있습니다. “정상 서비스에서 쓰지 않는다”와 “어떤 캡처에서도 절대 나타나지 않는다”는 다른 주장입니다.

NAT를 지나는 경우에는 외부에서 본 출발지 포트가 내부 소켓의 포트와 달라질 수 있습니다. 포트의 증가 패턴만 보고 특정 운영체제나 사용자 수를 확정하면 변환·공유·재사용을 놓칠 수 있습니다. 패킷과 호스트 소켓 기록을 연결할 때는 관측 위치와 시각, 변환 로그가 필요합니다.

8. 두 주소와 두 포트, 그리고 시간으로 연결 묶기

가상 클라이언트 192.0.2.10:51000이 198.51.100.20:443으로 접속한다고 해봅시다. 한 방향의 네 요소는 출발지 IP·출발지 포트·목적지 IP·목적지 포트입니다. TCP라는 프로토콜까지 포함하면 흔히 다섯 요소라고 부릅니다. 같은 숫자의 포트를 쓰는 UDP는 TCP와 다른 전송 계층 통신입니다.

응답 방향은 198.51.100.20:443에서 192.0.2.10:51000으로 주소와 포트가 뒤집힙니다. 이것을 반대 방향이니까 무조건 다른 TCP 연결이라고 분리하면 하나의 교환을 잃습니다. 연결 단위로 묶되 각 패킷의 방향을 열에 따로 적으면, SEQ는 자기 방향, ACK는 반대 방향을 가리킨다는 규칙을 적용하기 쉬워집니다.

네 요소가 같다고 무한한 시간에 걸쳐 같은 연결은 아닙니다. 연결이 닫힌 뒤 같은 조합이 재사용될 수 있습니다. SYN·종료·시각·번호 공간을 함께 봐야 이전 연결의 늦은 패킷과 새 연결을 구별할 수 있습니다. 캡처가 중간부터 시작했거나 여러 센서의 파일을 합쳤다면 이 경계가 더 불분명해질 수 있습니다.

Wireshark의 tcp.stream은 그 파일을 분석하면서 붙이는 스트림 식별자입니다. 세계적으로 고유한 연결 번호나 헤더에 저장된 필드가 아닙니다. 다른 파일에서 스트림7이라고 해서 같은 연결이라는 뜻도 아닙니다. 다른 분석자가 결과를 재현할 수 있도록 파일·시간·주소/포트와 도구가 부여한 스트림 번호를 구분해 남기세요.

9. SEQ는 패킷 순번이 아니라 바이트 위치입니다

각 방향은 연결을 시작할 때 ISN, 즉 Initial Sequence Number를 정합니다. 실제 헤더의 SEQ는 32비트 번호 공간에서 세그먼트가 시작하는 위치입니다. ISN을 1000으로 정했다면 그 숫자가 초기 기준이 됩니다. 실제 헤더 숫자가 처음부터 0으로 적힌다는 뜻은 아닙니다. 상대 표시에서 초기 기준을 0으로 바꿔 볼 수 있을 뿐입니다.

SYN은 그 번호 공간에서 한 자리를 차지합니다. 데이터 없는 SYN의 SEQ가 1000이면 다음 새 데이터는 1001부터 시작합니다. 그 데이터가 100바이트라면 실제 바이트 위치는 1001~1100이고 다음 새 범위의 시작은 1101입니다. 끝의 다음 위치를 쓰는 반개구간으로는 [1001,1101)이라고 적습니다. 여기서 오른쪽 값1101은 포함하지 않습니다.

만약 그 100바이트를 40바이트와 60바이트로 나누면 두 데이터 세그먼트의 SEQ는 1001과1041입니다. 다음 새 데이터는 여전히1101입니다. 패킷을 두 개 보냈다고1003이 되는 것도 아니고, 패킷 수가 늘었다고 응용 데이터가 더 많아지는 것도 아닙니다. 세그먼트 경계가 달라도 바이트 위치의 연결은 유지됩니다.

다시 보낸 데이터는 원래의 바이트 위치를 가리킬 수 있습니다. 같은 SEQ가 두 번 나왔다고 무조건 잘못된 번호는 아닙니다. 다만 같은 범위의 데이터가 동일한지, 부분적으로 겹치는지, 다른 내용인지 확인해야 재전송 후보와 충돌하는 겹침을 구별할 수 있습니다. 이 차이는 뒤의 실제 실습에서 다시 계산합니다.

10. 데이터와 SYN·FIN만 번호 공간을 소비합니다

세그먼트가 점유하는 번호 공간의 길이는 데이터 바이트 수 N에 SYN이 있으면1, FIN이 있으면1을 더한 값입니다. 다음 새 위치를 계산할 때는 SEQ + N + SYN + FIN을 사용하고32비트 경계를 넘으면 순환합니다. 여기서 SYN·FIN은 켜졌으면1, 꺼졌으면0으로 생각합니다. 계산은 그 세그먼트가 받아들여질 수 있다는 의미까지 보장하지 않습니다.

순수 ACK는 데이터가 없고 SYN·FIN도 없으므로 길이0입니다. 자기 방향의 번호를 하나 새로 소비하지 않습니다. 그래서 A가 데이터를 보내지 않고 여러 ACK만 보내면 A의 SEQ가 그대로일 수 있습니다. 원문의 “재전송이 아닌 새 세그먼트이면 SEQ가 바뀐다”는 문장을 모든 순수 ACK까지 적용하면 오탐을 만들 수 있습니다.

FIN은 실제 응용 데이터 한 바이트가 실린다는 뜻이 아니지만 번호 공간에서는 한 자리를 씁니다. 예를 들어 SEQ1101에서 데이터20바이트와 FIN이 함께 있다면 데이터는1101~1120이고 FIN이1121을 사용하므로 다음 위치는1122입니다. ACK만 받은 것과 FIN까지 받아들인 것을 숫자로 구별할 수 있게 되는 것입니다.

반대로 PSH·URG·ACK·RST 같은 비트 자체를 켰다는 이유로 이 계산에1씩 더하지 않습니다. 플래그 이름이 여러 개 보인다고 모두 같은 방식으로 번호 공간을 소비하는 것은 아닙니다. 특별한 동작의 수용 여부는 상태·윈도·체크섬 등 다른 검증과 함께 판단해야 합니다. 이번 계산에서는 점유 길이와 정상성 판정을 분리합니다.

11. 세 번의 시작 교환을 두 번호 공간으로 계산하기

가상 A의 ISN은1000, B의 ISN은7000이라고 하겠습니다. A가 보낸 첫 SYN의 SEQ는1000입니다. 아직 ACK 비트가 없으므로 ACK 번호를 상대 수신 범위로 해석하지 않습니다. 데이터가 없는 이 SYN은 A의 번호 공간 하나를 사용합니다.

B의 SYN/ACK는 두 가지 일을 함께 합니다. 자기 SYN으로 B의 SEQ7000을 제시하고, ACK1001로 A의 SYN 다음 위치를 기대한다고 알립니다. 숫자7000과1001을 같은 방향의 연속 값이라고 읽으면 연결이 이해되지 않습니다. 전자는 B가 보내는 방향, 후자는 A에서 받은 방향을 가리킵니다.

A는 SEQ1001, ACK7001인 ACK를 보냅니다. 이 예에서는 데이터가 없어서 A의 다음 새 위치는1001 그대로입니다. B의 SYN 한 자리는 확인됐지만, 이 ACK 자체가 A의 번호 공간을 한 칸 더 사용한 것은 아닙니다. 이후 A가100바이트를 보내면 SEQ1001에서 시작하고 B는 연속 수신 조건에서 ACK1101을 보낼 수 있습니다.

이 표는 기본 계산을 분리한 가상 흐름입니다. 실제 환경에는 시작 교환 중 데이터, 재시도, 동시 열기 같은 조건도 있으므로 모든 TCP 연결의 화면이 반드시 이 네 줄처럼 보인다고 보장하지 않습니다. 다음 강의에서 플래그와 연결 상태를 더 자세히 살펴보겠습니다. 교재의 시작 설명 중 첫 클라이언트 세그먼트를 SYN/ACK라고 부른 부분은 여기서 SYN으로 바로잡습니다.

12. ACK는 마지막 받은 번호가 아니라 다음 기대 위치입니다

SEQ1001에서100바이트를 연속으로 받았다면 마지막 데이터 바이트는1100입니다. ACK 번호는1101입니다. “1101까지 받았다”라고 쓰면1바이트가 어긋납니다. 정확한 문장은 “그 앞의 연속 범위를 받았고 다음에는1101을 기대한다”입니다. 원문에는 마지막 바이트라고 쓴 부분과 다음 기대값이라고 설명한 부분이 혼용되어 있으므로 다음 기대 위치로 통일합니다.

일반적인 데이터 교환에서 누적 ACK는 그 값보다 앞의 연속 범위를 확인합니다. 아직1101~1200이 비어 있다면 더 뒤의 데이터가 일부 도착해도 ACK는1101에 머무를 수 있습니다. 따라서 ACK가 같다고 같은 패킷 하나만 계속 확인하는 것이거나 이후 바이트가 전혀 도착하지 않은 것이라고 단정하지 않습니다.

반대로 ACK가 한 번에200바이트 증가했다고 수신자가 바로 직전에200바이트짜리 패킷 하나를 받았다는 뜻도 아닙니다. 여러 세그먼트를 누적해 확인했거나, 앞의 공백이 메워지면서 보관해 둔 뒤 범위까지 연속으로 연결될 수 있습니다. ACK 증가량은 수신 연속 위치의 전진을 보여주고, 실제 패킷 경계는 별도로 봅니다.

ACK 비트는 ACK 번호를 유효한 확인 값으로 사용할 수 있음을 나타냅니다. 비트가 켜져 있다는 사실만으로 몇 바이트를 새로 받았는지 알 수는 없습니다. 어느 방향의 번호인지, 이전 ACK는 무엇인지, 데이터·SYN·FIN이 어떻게 번호를 사용했는지 함께 계산해야 합니다. RFC9293의 번호 공간과 확인 규칙을 기준으로 읽으세요.

13. 뒤쪽 데이터가 먼저 도착해도 누적 ACK는 멈출 수 있습니다

A의 다음 데이터 위치가1001이라고 해봅시다. A가 보낼 세 범위는 [1001,1101), [1101,1201), [1201,1301)이고 각각100바이트입니다. B가 첫 범위를 받으면 다음 기대 위치는1101입니다. 그런데 가운데 범위가 늦어지고 세 번째가 먼저 도착하면 어떻게 될까요? B는1101에서 시작하는 공백을 아직 채우지 못했습니다.

이때 세 번째 범위를 임시 보관할 수 있더라도 누적 ACK는1101에 머물 수 있습니다. SACK가 협상되어 사용된다면 [1201,1301) 같은 뒤쪽 수신 범위를 별도로 알려줄 수 있습니다. 누적 ACK와 SACK는 서로 모순된 정보가 아닙니다. 전자는 앞에서부터 이어지는 범위, 후자는 그 밖의 선택적 수신 정보를 나타냅니다. 옵션의 구체적인 형식은 뒤 강의에서 다룹니다. [4]

이후 빠졌던 [1101,1201)이 도착하고 보관해 둔 뒤 범위와 연결되면 누적 ACK는1301로 전진할 수 있습니다. 마지막으로 새로 도착한 세그먼트는100바이트인데 ACK는200만큼 움직였습니다. 따라서 “ACK는 언제나 바로 직전 패킷의 SEQ에 그 패킷 길이를 더한 값”이라는 식은 조건 없는 규칙이 아닙니다. 앞에 공백이 없고 새 범위가 연속으로 이어지는 간단한 경우에서만 그렇게 계산할 수 있습니다.

반대로 수신 ACK가 오지 않았다고 데이터가 원격에 반드시 도착하지 않았다고 단정할 수도 없습니다. 데이터는 도착했지만 ACK가 손실되었거나, 관측 센서가 반대 방향을 못 봤을 수 있습니다. 누가 어느 지점에서 무엇을 보았는지를 구분해야 합니다. 수신자의 번호 공간, 송신자의 재전송 판단, 분석자의 캡처는 같은 정보의 완전한 복사본이 아닙니다.

14. 데이터 길이를 계산한 뒤 ACK의 전제를 확인하기

IPv4 Total Length에서 IPv4 헤더 길이와 TCP 헤더 길이를 빼면 온전한 데이터그램의 TCP 데이터 길이를 구할 수 있습니다. 예를 들어 전체 IP 길이160, IHL5, TCP Data Offset10이면 IP 헤더20바이트, TCP 헤더40바이트이므로 데이터는100바이트입니다. Ethernet 헤더는 IP Total Length에 포함되지 않으므로 다시 빼지 않습니다.

가상 데이터 세그먼트의 SEQ가2001이고 이100바이트가 앞의 공백 없이 수신되었다면 다음 누적 ACK는2101입니다. SYN·FIN도 없다면 점유 길이는 데이터 길이와 같습니다. FIN이 함께 있다면 다음 위치는2102입니다. SYN·FIN의 한 자리를 빼먹으면 응용 데이터가 없는 시작·종료 패킷을 계산할 때도1씩 틀리게 됩니다.

하지만 IP 조각 하나를 완전한 원래 TCP 세그먼트처럼 계산하거나, 저장 길이가 짧은 파일에서 헤더 선언만 보고 데이터가 모두 관측됐다고 하면 안 됩니다. 헤더 길이가 유효한지, 합이 전체 길이를 넘지 않는지, 해당 바이트가 실제로 저장되어 있는지 확인해야 합니다. 음수 길이나 비정상적인 길이는 정상적인 데이터 범위 계산을 멈추고 원인을 살펴볼 신호입니다.

이 길이로 확인한 것은 전송 계층 바이트 수입니다. TLS가 실렸다면 암호화 관련 바이트도 포함되고, HTTP 같은 응용 프로토콜의 헤더와 내용이 함께 있을 수도 있습니다. TCP 데이터100바이트를 파일 내용100바이트나 업무 데이터100바이트로 곧바로 바꾸어 부르지 않습니다. 어느 계층의 길이인지를 붙여서 말하면 분석 보고서가 더 정확해집니다.

15. 상대 번호는 바이트를 바꾸는 것이 아니라 기준을 바꿉니다

큰 숫자가 계속 나오면 작은 차이를 읽기 어렵습니다. A의 ISN을4000000000, B의 ISN을1500000000으로 정한 가상 예를 보겠습니다. A의 첫 데이터 SEQ4000000001을 A의 ISN 기준으로 표현하면 상대 SEQ1입니다. B가 그 데이터를517바이트 연속으로 확인한 ACK4000000518은 A의 번호 공간에서 상대 ACK518입니다.

B가 보내는 패킷의 SEQ는 B 자신의 기준을 사용합니다. 예를 들어1500000001이면 상대 SEQ1입니다. 같은 패킷의 ACK4000000518은 A 기준의518입니다. 두 필드 모두 상대 숫자로518과1처럼 작게 보이더라도 기준이 같다는 뜻이 아닙니다. SEQ 열과 ACK 열 옆에 어느 방향의 기준인지 적어 두면 서로 다른 ISN을 잘못 빼는 실수를 줄일 수 있습니다.

tcpdump는 기본 출력에서 상대 번호를 사용할 수 있고 시작 구간에서는 원시값이 보이다가 이후 상대값으로 바뀌는 형태도 만날 수 있습니다. -S 옵션은 절대 번호를 표시합니다. Wireshark도 상대 SEQ·ACK 표시를 사용할 수 있으며 tcp.seq_raw·tcp.ack_raw는 원시 번호 필드입니다. 도구마다 화면에 보이는 표현이 같을 것이라고 가정하지 말고 설정·열·원시 필드를 확인하세요. [5] [6]

상대 seq 1:518은 보통 시작1부터 끝의 다음 위치518까지, 즉517바이트를 나타내는 반개구간으로 읽습니다. 마지막 데이터 바이트의 상대 위치는517입니다. 원시값으로는 [4000000001,4000000518)이고 마지막은4000000517입니다. “1부터518까지 모두 포함해518바이트”라고 읽으면 길이가1 늘어납니다. 범위 표기의 오른쪽 경계를 포함하는지부터 확인하세요.

16. 32비트 순환 때문에 0도 합법적인 위치입니다

32비트 번호는0~4294967295의 범위를 갖고 그다음은0으로 돌아옵니다. 이를 모듈로 2의32승, 즉4294967296 연산이라고 표현합니다. 가상 SEQ4294967293에서5바이트를 보내면 다음 새 위치는2입니다. 4294967293·4294967294·4294967295·0·1이 다섯 바이트의 위치이기 때문입니다.

숫자2가4294967293보다 작다고 해서 이 예에서 더 오래된 데이터인 것은 아닙니다. 단순 정수 대소 관계만으로 새롭고 오래된 위치를 판단하면 순환 부근에서 틀립니다. 실제 TCP는 제한된 윈도와 번호 공간의 모듈로 비교를 사용합니다. 여기서는 짧은 예제로 순환의 존재를 이해하고, 무한히 큰 파일의 총량을 두 숫자만 빼서 추정하지 않는 데 집중합니다.

가상 현재 SEQ에서 ISN을 빼면 기준부터의 위치 차이를 구할 수 있지만, 여러 번 순환한 횟수는 두 값만으로 복원할 수 없습니다. SYN이 사용한1, 재전송·겹침·수신 공백·캡처 시작점도 별도로 봐야 합니다. 원문에서 초기 번호와 현재 번호를 빼면 전송량이 나온다는 설명은 이런 전제가 빠져 있고 뺄셈 방향도 혼동을 줄 수 있습니다. 작은 연속 구간의 위치 차이와 고유 응용 바이트 총량을 구분합니다.

따라서 원시 SEQ가0이라는 사실 하나만으로 비정상 패킷이라고 할 수 없습니다. 초기 선택이나 순환에서0이 나타날 수 있고, 상대0은 기준점 표시일 수 있습니다. 워크북의 조작된 패킷에 여러 이상 필드가 동시에 있더라도 “번호가0이면 언제나 불법”이라는 규칙으로 단순화하면 안 됩니다. 플래그·포트·옵션·연결 상태를 함께 검토해야 합니다.

17. 도구에서 원시 번호와 표시 번호를 나란히 확인하기

재현할 때는 먼저 입력 파일과 연결 범위를 고릅니다. 원시 번호가 필요한 tcpdump 예제에서는 -S를 붙입니다. -nn은 주소와 포트의 이름 변환을 억제하고, -r은 저장 파일을 읽습니다. 시간 간격을 비교할 때는 시각을 숨기는 -t를 빼고 원래 시각도 남겨야 합니다. 같은 순서 번호를 보는 일과 재시도 간격을 확인하는 일에 필요한 출력 정보가 다릅니다.

Wireshark에서는 tcp.seq와 tcp.ack가 표시 설정의 영향을 받을 수 있다는 점을 생각하며 tcp.seq_raw·tcp.ack_raw·tcp.len·tcp.flags를 함께 봅니다. ACK 비트가 꺼진 패킷에서는 원시 ACK 필드가 있더라도 수신 확인 값으로 사용하지 않습니다. tcp.stream을 후보 묶기에 쓰되 연결 식별의 유일한 근거로 삼지 않습니다.

표시 필터 tcp.srcport == 4545와 BPF tcp src port 4545는 서로 다른 입력란의 언어입니다. 번호 필드는 헤더에 저장된 값이고, tcp.analysis.retransmission 같은 분석 표시는 여러 패킷의 관측 순서와 상태에서 도구가 추론한 값입니다. 센서에서 빠진 패킷이나 파일 합치기의 영향을 받을 수 있으므로 분석 표시를 종단의 내부 상태를 직접 읽은 결과처럼 보고하지 않습니다. [7]

19. 워크북: 같은 시작을 다시 시도하는 네 레코드

TCP 워크북의 재시도 구별 문제는 두 SYN 집합을 비교하라고 요구합니다. 첫 집합은10.254.1.8에서 목적지 포트21로 향하는 활동입니다. 우선 주소와 포트로 범위를 고른 뒤, 그 안에서 출발지 포트·ISN·시간 간격·플래그를 나란히 확인합니다. 서버 포트21이라는 숫자만으로 반복 시도의 정체를 판단하지 않습니다.

원래 저장 시각으로 인접 간격을 계산하면2.999920초, 6.000169초, 12.001114초였습니다. 약3·6·12초로 늘어나는 간격은 재시도의 지수적 후퇴와 일관됩니다. 그러나 이 표본의3초를 모든 현재 운영체제의 고정 초기값이라고 외우면 안 됩니다. 타이머는 구현·상태·측정에 따라 달라지고, RFC6298은 타이머 관리와 후퇴 규칙을 별도로 설명합니다.

번호와 간격은 재시도 가설의 근거이지만, 어떤 장비가 어디서 응답을 막았는지까지 증명하지는 않습니다. 호스트 꺼짐, 경로 문제, 방화벽, 응답이 센서에 보이지 않는 조건 등은 추가로 구분해야 합니다. 수집 중복도 시각·IP ID·동일 바이트·센서 위치와 함께 살펴볼 후보입니다. 이 예에서는 적어도 포트 하나만 보고 결론을 내린 것이 아니라 여러 관측을 결합했다는 점이 중요합니다.

20. 다른 포트와 다른 ISN은 새 시도 후보, 성공 확인은 별도입니다

두 번째 집합은10.114.187.126에서 목적지 포트143으로 향하는 활동입니다. 저장 프레임42~45의 출발지 포트는1859·1860·1866·1881이고 원시 SEQ도 각각 다릅니다. 첫 집합처럼 같은 포트와 같은 번호를 일정하게 재사용하는 형태가 아니므로, 서로 다른 시작 시도 후보라는 해석에 맞습니다.

다만 이를 “성공한 연결 네 개”라고 표현하면 증거를 넘어갑니다. SYN 후보 네 개의 포트와 번호가 다르다는 사실은 연결 시작 시도가 구별된다는 근거입니다. 서버의 SYN/ACK와 뒤의 확인, 응용 교환을 함께 보지 않았다면 연결 성립이나 로그인 성공까지 확정할 수 없습니다. 워크북 힌트의 성공이라는 표현은 이 단계에서는 별도 검증 대상으로 제한해 읽습니다.

이 네 저장 레코드에는 ACK 비트가 꺼져 있는데 원시 ACK 필드에는0이 아닌 값이 들어 있었습니다. 그 수를 상대가 받은 바이트 위치라고 해석하지 않습니다. 헤더에 있는 모든 정수가 현재 상태에서 유효한 의미를 갖는 것은 아니라는 앞의 설명을 실제 표본에서 확인할 수 있는 부분입니다. 이 사실 하나가 공격자의 신원이나 종단의 수용 결과를 확정하는 것도 아닙니다.

필터도 범위를 명확히 괄호로 묶으세요. TCP이면서 두 주소/포트 조건 중 하나라는 의도를 tcp and ((첫 조건) or (둘째 조건))로 적었습니다. 숫자 비교의 정확성뿐 아니라 양방향 여부, 프로토콜, 주소 조건의 묶음이 분석 집합을 바꿉니다. 서로 다른 도구의 필터 언어를 바꾸어 쓸 때도 같은 집합을 의도했는지 확인해야 합니다.

21. 워크북: 같은 번호와 같은 길이인데 내용이 다르다면

다음은 출발지 포트4545인 두 레코드의 비교입니다. 저장 프레임122·123은 같은 주소/포트 방향이며 원시 SEQ76148922, TCP 데이터12바이트, 플래그0x02입니다. IP 전체 길이52에서 IP 헤더20과 TCP 헤더20을 빼도12가 나와 길이를 교차 검산할 수 있습니다. 두 레코드의 위치와 길이만 보면 같은 바이트 범위를 다시 제시하는 모습입니다.

그러나 데이터 바이트를 직접 비교하니12바이트 중 처음 네 바이트가 달랐습니다. 같은 위치에 서로 다른 내용을 제시한 것입니다. 정상적인 동일 데이터의 재전송이라고 간단히 정리할 수 없고, 충돌하는 겹침 후보로 검토해야 합니다. 공개 노트에는 원본 실습 페이로드나 전체 덤프를 복제하지 않고 위치·길이·차이의 집계만 설명합니다.

이 표본은 SYN이 있으므로 원시 SEQ76148922는 SYN이 쓰는 위치입니다. 번호 공간 규칙으로 데이터의 첫 위치는76148923이고,12바이트를 모두 포함한 데이터의 다음 위치는76148935입니다. SYN까지 합친 점유 길이는13입니다. 단순히 원시 SEQ에12만 더한76148934를 모든 의미에서 다음 ACK라고 부르면 SYN 한 자리를 빠뜨립니다. 이는 저장 헤더와 표준에 따른 산술이며 해당 세그먼트를 종단이 실제로 받아들였다는 뜻은 아닙니다.

SYN에 데이터가 있다는 이유만으로 언제나 잘못됐다고 단정하지도 않습니다. 기본 TCP의 데이터 전달 시점과 TCP Fast Open 같은 동작을 구분해야 합니다. RFC7413은 SYN 데이터와 초기 응용 전달의 조건을 설명합니다. 이 표본의 핵심 의심점은 같은 범위에서 서로 다른 내용이 있다는 점이며, 옵션·상태·구현에 대한 검토는 뒤 강의와 연결합니다.

22. 관측한 번호를 조사 결론으로 바꾸는 순서

이제 기록을 세 층으로 나누어 볼 수 있습니다. “같은5요소와 같은 SYN 번호가 약3·6·12초 간격으로 보였다”는 관측입니다. “같은 연결 시작의 재시도와 일관된다”는 해석입니다. “방화벽이 막아서 재시도했다”는 원인 가설입니다. 마지막 문장에는 방화벽·경로·종단 로그 같은 별도 증거가 필요합니다.

수신 ACK가 보이면 어디까지의 전송 계층 수신 범위를 알리는지 계산하고, 응용 성공은 별도로 확인합니다. 결제 요청 데이터가 ACK됐다는 사실만으로 결제 완료를 보고하거나, 파일 전송 데이터가 ACK됐다는 이유로 디스크의 최종 파일까지 검증됐다고 하면 안 됩니다. 암호화 여부에 따라 응용 내용을 직접 읽을 수 있는지도 달라집니다.

전송량을 집계할 때도 목적을 먼저 정하세요. 관측한 TCP 데이터 길이를 모두 합하면 재전송과 겹침이 중복으로 포함될 수 있습니다. 고유 바이트 범위를 원한다면 방향별 구간을 합쳐 중복을 구분해야 하고, 파일 내용의 총량을 원하면 응용 프로토콜까지 해석해야 합니다. 순서 번호는 이런 분석의 근거이지만 두 숫자 뺄셈 하나가 모든 총량을 자동으로 주지는 않습니다.

이번 회차는 TCP 워크북 전체 완료가 아닙니다. 재시도/새 시도 구별은 상세히 풀었고, 충돌 겹침 문제는 원시 번호·길이·내용 차이와 한계까지 다뤘습니다. SYN 데이터의 수용과 옵션, 비정상 RST와 체크섬, 조작된 플래그·윈도·URG·서비스 응답은 관련 후속 강의에 남깁니다. 다음 강의는 이번에 계산에 사용한 제어 비트를 실제 연결 시작의 상태와 연결합니다.

23. 복습 · 번호를 외우기보다 조건을 바꾸어 계산하기

질문 1. TCP의 신뢰성이 모든 전송의 성공을 보장하나요? 아닙니다. 손실·순서·중복을 다루는 장치가 있다는 의미입니다. 통신을 복구할 수 없으면 실패할 수 있고, TCP의 수신 확인은 업무 처리 성공과 다릅니다.

질문 2. 한 TCP 연결의 양방향 SEQ가 같은 기준을 쓰나요? 아닙니다. 각 방향은 독립적인 ISN과 번호 공간을 사용합니다. 연결은 하나이고, 한 패킷의 SEQ는 자기 방향, ACK는 반대 방향을 가리킵니다.

질문 3. 100바이트를 두 패킷으로 나누면 번호가2만 증가하나요? 아닙니다. 데이터가 쓰는 번호 공간은100입니다. 패킷 경계가 아니라 바이트 위치를 셉니다. 재전송을 포함한 관측 패킷 수와 고유 데이터 크기를 혼동하지 않습니다.

질문 4. SEQ2001의 데이터300바이트를 연속 수신하면 다음 ACK는?2301입니다. 마지막 데이터 위치는2300이고 다음 기대 위치가2301입니다. SYN·FIN과 수신 공백이 없는 조건의 계산입니다.

질문 5. SEQ2001에 데이터300바이트와 FIN이 있으면 다음 위치는?2302입니다. 데이터300에 FIN이 쓰는1을 더합니다. FIN을 응용 데이터 한 바이트로 세는 것은 아니지만 번호 공간에서는 한 자리입니다.

질문 6. 순수 ACK가 계속 나와도 SEQ가 같을 수 있나요? 가능합니다. 데이터와 SYN·FIN이 없으면 자기 방향에서 번호 공간을 소비하지 않습니다. 같은 SEQ라는 사실만으로 재전송으로 분류할 수 없습니다.

질문 7. ACK1101인데 [1201,1301)도 받았을 수 있나요? 있습니다. 앞의 [1101,1201)이 비어 있으면 누적 ACK는1101에 머물 수 있습니다. SACK 같은 추가 정보와 공백을 함께 살펴봅니다.

질문 8. ACK가200 증가하면 바로 직전 세그먼트 길이도200인가요? 아닙니다. 누적 확인과 공백 메우기로 더 큰 범위가 연결될 수 있습니다. ACK 전진과 패킷 경계는 다른 정보입니다.

질문 9. 상대 SEQ1과 원시 SEQ4000000001이 모순인가요? A의 ISN4000000000을 기준으로 했다면 같은 위치입니다. 어떤 방향의 ISN을 뺐는지 확인해야 합니다.

질문 10. 원시 SEQ4294967293에서5바이트 뒤는?32비트 순환을 적용하면2입니다. 이 예의 데이터 위치는 큰 수 세 개와0·1이고 그다음이2입니다. 단순한 정수 대소만으로 순서를 판단하지 않습니다.

질문 11. 출발지 포트가 달라진 SYN 네 개는 성공한 연결 네 개인가요? 그 정보만으로는 새 시작 시도 후보까지입니다. 연결 성립과 응용 성공은 반대 방향과 후속 교환으로 추가 확인해야 합니다.

질문 12. 같은 SEQ·같은 길이면 항상 동일 데이터 재전송인가요? 아닙니다. 내용도 비교해야 합니다. 같은 범위에서 다른 바이트가 보이면 충돌하는 겹침 후보입니다. 그 관측만으로 실제 회피 성공을 확정하지 않습니다.

질문 13. SYN의 원시 SEQ가500이고 데이터12바이트면 첫 데이터와 다음 위치는? SYN이500을 사용하므로 첫 데이터는501, 데이터 끝 다음 위치는513입니다. SYN을 포함한 점유 길이는13입니다. 종단 수용 여부는 별도입니다.

질문 14. 포트0을 bind에 주면0번 서비스가 선로에서 열리나요? 보통 자동 포트 할당 요청입니다. 예약된 포트0의 헤더 관측과 API 요청의 뜻을 구분합니다. 비정상·조작 패킷에서0이 나타나는 것까지 불가능한 것은 아닙니다.

질문 15. 저장 바이트 검산을 tcpdump 실행이나 VM 수신 검증이라고 불러도 되나요? 안 됩니다. 파일에서 읽은 필드와 산술 관계만 확인했습니다. 도구의 표시·필터 실행과 종단의 실제 수용·재조립은 별도로 검증할 항목입니다.
