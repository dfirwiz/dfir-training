학습 범위와 예제

둘째 날 12강 · 교재 인쇄 128~141쪽의 학습 주제를 자체 예제와 해설로 풀었습니다. 아래 주소·숫자·흐름은 별도 표시가 없으면 가상 학습 예시입니다. 명령은 분석 절차이며 실제 실행 출력으로 제시하지 않습니다.

1. ICMP는 ping만을 위한 프로토콜이 아닙니다

택배가 도착하지 못했을 때 반송 사유가 있으면 어디에서 문제가 생겼는지 조사하기 쉽겠지요. ICMP는 IP 통신의 오류와 제어 정보를 알리는 역할을 합니다. Echo 요청·응답은 그 기능 중 하나입니다. TCP나 UDP 포트를 사용하는 대신 Type과 Code로 메시지를 분류합니다.

ICMPv4는 IPv4 Protocol 값 1, ICMPv6는 Next Header 값 58을 사용합니다. 이름이 비슷해도 타입 번호와 기능을 그대로 바꾸어 읽을 수 없습니다. Echo만 해도 v4 요청은 8, 응답은 0이고 v6 요청은 128, 응답은 129입니다.

2. ping은 되는데 웹은 안 될 때 무엇을 알 수 있나요?

서버에 ping은 되는데 웹 접속이 안 된다는 연락을 받았다고 해 봅시다. “살아 있으니 네트워크는 정상”이라고 답하면 어디까지 확인한 걸까요? Echo 응답은 그 시점에 해당 요청과 응답이 오갈 수 있었다는 단서입니다. TCP 포트의 수신 대기, TLS 교환, 웹 응용이나 사용자 인증 성공은 별도 단계입니다. 반대로 ping이 안 돼도 서비스는 응답할 수 있습니다. Echo에만 다른 정책이 적용될 수 있기 때문이지요.

ICMP는 Internet Control Message Protocol입니다. 반송 안내 비유로 보면 Echo는 “이 쪽지를 받았으면 같은 내용을 돌려주세요”, 오류 메시지는 “이 물건은 이런 사유로 전달하지 못했어요”에 가깝습니다. 비유와 달리 모든 실패가 반드시 반송되는 것은 아닙니다. ICMP 자체에도 TCP 같은 확인·재전송의 신뢰성 장치가 없고, 오류나 응답이 제한·손실·수집 누락으로 보이지 않을 수 있습니다.

전달 실패 보고와 정보성 교환을 나눠 보세요. IPv4에서 큰 패킷이 더 작은 MTU 경로로 가는데 DF(Don't Fragment)가 설정되어 분할할 수 없다면, Type3 Code4인 단편화 필요 보고를 볼 수 있습니다. 닫힌 UDP 포트는 Type3 Code3인 Port Unreachable로 보고될 수 있습니다. 전자는 IP 전달 크기, 후자는 상위 계층 포트와 관련된 사유입니다. 오류의 인용 패킷은 다음13강에서 더 자세히 읽습니다.

교재의 “일시적이지 않은 문제를 보고한다”는 표현을 영구 장애 판정으로 읽지는 마세요. 이후 경로·정책·서비스 상태가 바뀔 수 있고 모든 비트 손상마다 ICMP를 발송하는 것도 아닙니다. 보고한 시각과 장비, 원래 요청을 연결하는 것이 먼저입니다. ICMPv6는 이웃 탐색 같은 다른 제어 기능에도 쓰이므로 “ping 차단”과 “모든 ICMPv6 차단”도 같은 결정이 아닙니다.

3. 번호의 의미는 Type과 Code를 함께 찾아봅니다

Type과 Code는 각각1바이트, 즉8비트입니다. 2의8승=256가지 값을 표현할 수 있다는 뜻이지256가지 모두가 배정된 정상 메시지라는 뜻은 아닙니다. 첫 바이트 오프셋0의 Type을 먼저 읽고, 오프셋1의 Code를 그 Type의 표에서 찾습니다. 오프셋은 시작점으로부터 몇 바이트 떨어졌는지를 세며 첫 위치는0입니다.

IANA의 Type3 표에서 Code0부터15까지는16개 번호입니다. “15까지”와 “15개”를 혼동하지 마세요. Code0 하나를 보고 “정상 응답”이라고 이름 붙일 수 없지요. Type8의0은 요청, Type0의0은 응답, Type11의0은 오류입니다. IPv6에서는 Echo의128/129부터 번호가 다르므로 IP 버전도 검색 기준에 넣습니다. ICMPv6의 공통4바이트 뒤도 Type별로 해석하며 Echo의8바이트 형식을 모든 메시지에 복사하지 않습니다.

IANA 등록표에서 Unassigned는 미배정, Deprecated는 폐기된 용도를 뜻합니다. 예를 들어 ICMPv4 Source Quench Type4는 RFC6633으로 폐기되었고, 정보 요청/응답15·16과 주소 마스크 요청/응답17·18도 RFC6918에 따라 폐기된 항목입니다. 오래된 캡처를 해독할 수 있다는 것과 새 기능으로 사용을 권장한다는 것은 다릅니다. 등록된 번호라는 사실만으로 안전함이나 현재 지원 여부를 확정하지 않습니다.

4. Type을 읽은 뒤 나머지 필드의 뜻을 정합니다

ICMP의 첫 바이트는 Type, 두 번째는 Code, 다음 두 바이트는 체크섬입니다. Type이 큰 분류라면 Code는 그 안의 세부 사유입니다. Code만 따로 떼면 의미가 정해지지 않습니다. 이후 필드의 구조는 메시지 종류에 따라 달라집니다. 모든 ICMP를 Echo의 식별자·순서 구조로 해석하면 안 됩니다.

Echo의 기본 8바이트에는 Identifier와 Sequence가 각각 2바이트씩 있습니다. 가상 요청의 ID가 120, SEQ가 5라면 대응 응답에서 같은 값과 페이로드를 확인합니다. IP 주소는 요청과 응답에서 반대가 됩니다. 여러 호스트가 같은 ID를 사용할 수도 있으므로 그 숫자만으로 한 프로그램을 세계적으로 식별할 수는 없습니다.

5. 15바이트 요청에서 여섯 필드를 직접 끊어 봅시다

기존 표의 TEST-0005와 별개로 작은 계산 예제를 만들겠습니다. A=192.0.2.10에서 B=192.0.2.20으로 보낸 Echo의 Identifier는120, Sequence는5, 데이터는 ASCII 문자열 PING-42입니다. ASCII는 문자와 바이트 값을 대응하는 부호 체계이고 여기서는7문자가7바이트입니다. 다음은 실제 PCAP 출력이 아닌 합성 ICMP 메시지입니다.

16진수78은7×16+8=120입니다. 두 바이트00 78을 네트워크 바이트 순서, 큰 자리 바이트 먼저로 읽습니다. 순서를 뒤집어7800으로 읽으면120×256=30720이 되어 다른 ID처럼 보입니다. Wireshark는 Identifier/Sequence를 BE(Big Endian)와 LE(Little Endian)로 따로 보여줄 수 있으니 표시 필드와 원시 바이트를 먼저 맞추세요.

Echo의 Identifier·Sequence는 각각16비트이며 65535 다음에0으로 순환할 수 있습니다. Sequence가0으로 돌아왔다는 사실만으로 새 프로세스가 시작됐다고 단정하지 않습니다. 이 Sequence는 TCP의 바이트 위치 번호도 아니고 모든 ICMP에 공통으로 있는 순서 번호도 아닙니다.

6. 데이터 크기와 ICMP 길이와 IP 길이는 세 숫자입니다

합성 예제의 데이터는7바이트, Echo 헤더는8바이트라 ICMP 전체는8+7=15바이트입니다. IPv4 기본 헤더20바이트와 옵션·단편이 없다는 조건이면 IP Total Length는20+15=35바이트입니다. 같은 ICMP에 IPv4 옵션4바이트가 추가되면 IHL6, 헤더6×4=24바이트가 되어 IP 전체는24+15=39바이트입니다. ICMP 데이터가4바이트 늘어난 것이 아니에요.

일부 ping 명령의 size는 데이터 크기이고 tcpdump의 Echo length는 ICMP 전체 길이일 수 있습니다. 데이터56이면 ICMP64, IPv4 IP전체84바이트라는 계산과, 데이터32이면 ICMP40·IP전체60이라는 계산을 구분하세요. Ethernet 패딩·링크 헤더·FCS와 캡처 길이는 다시 다른 기준입니다. 화면에64가 나왔다고64바이트 페이로드라고 자동 번역하지 않습니다.

ICMP 자체에 UDP Length 같은 공통 길이 필드가 있는 것도 아닙니다. IP 선언 길이, IHL, 실제 저장 길이·단편 재조립 상태에서 메시지 범위를 확인합니다. IPv4 Total Length35를 선언했지만 IP 시작부터30바이트만 저장했다면5바이트가 부족합니다. 전체 데이터를 보지 못하고 “응답 데이터가 달라졌다”거나 “체크섬 검증 완료”라고 할 수 없습니다.

7. ICMPv4와 v6의 체크섬 범위를 구별합니다

ICMPv4 체크섬은 ICMP 메시지 자체를 대상으로 합니다. TCP·UDP처럼 IPv4 주소가 든 가상 헤더를 넣지 않습니다. ICMPv6는 IPv6 가상 헤더도 계산에 포함합니다. “IP 버전이 바뀌어도 체크섬 계산은 완전히 같다”는 가정을 주의하세요.

체크섬이 맞는다고 송신자가 정당하다는 뜻은 아닙니다. 체크섬은 암호학적 인증이 아니므로 값을 맞춘 위조 메시지도 가능합니다. 필드 검증, 실제 요청과 응답의 연결, 경로와 로그 대조를 함께 해야 합니다.

8. 요청 f9bd와 응답01be를 계산해 봅니다

ICMPv4 체크섬은 Type부터 메시지 끝까지의16비트1의보수 합을 뒤집어 만듭니다. 계산할 때 체크섬 두 바이트를0으로 두고, 홀수 길이면 계산용00을 끝에 붙입니다. 이00은 실제 데이터가 아니므로 메시지를16바이트로 늘리지는 않습니다.

체크섬을0으로 둔 요청 워드 · 모두16진수
0800 0000 0078 0005 5049 4e47 2d34 3200
합계 0x10641
자리올림 되먹임 0x0641 + 0x0001 = 0x0642
16비트 반전 0xffff - 0x0642 = 0xf9bd

응답은 첫 워드만0000으로 변경하여 다시 계산
합계/접힌 합 0xfe41
16비트 반전 0xffff - 0xfe41 = 0x01be

첫 워드0800은 Type08과 Code00을 묶은 값입니다. Type이8에서0으로 바뀌면 데이터가 같아도 체크섬을 다시 계산합니다. f9bd를 그대로 복사한 응답은 이 예제의 올바른 체크섬과 맞지 않습니다. 수신 시에는 저장된 체크섬을 포함해 더한 접힌 합이ffff인지 별도로 확인할 수 있어요.

IPv4 가상 헤더가 없으므로 이 ICMP 바이트 자체의 계산에는 A·B 주소가 들어가지 않습니다. 주소가 바뀌어도 메시지 바이트가 같다면 ICMPv4 체크섬이 같을 수 있습니다. IPv4 헤더의 체크섬은 별도입니다. 이것이 “ICMP 체크섬이 맞으니 발신 주소도 인증됐다”가 성립하지 않는 이유 중 하나입니다.

실제 체크섬 실패 표시를 볼 때는 원시 값과 검증 설정, 캡처 길이·재조립을 먼저 봅니다. 부분 캡처나 도구가 검증하지 않은 상태를 실제 손상으로 단정하지 않으며, 모든 잘못된 표시를 오프로딩 탓으로 돌리지도 않습니다. 이번 계산은 합성 메시지를 별도 계산기로 검산한 결과이고 실제 종단의 수용 시험은 아닙니다.

9. IPv6에는 주소와58이 든 가상 헤더도 더합니다

ICMPv6 Echo Request는 Type128, Code0이고 응답은129/0입니다. ICMPv6 체크섬은 IPv6 출발지16바이트·목적지16바이트·상위 계층 길이4바이트·0 세 바이트·Next Header 한 바이트의 가상 헤더40바이트를 함께 계산합니다. 여기의 Next Header 값은 ICMPv6의58입니다. IPv6 기본 헤더 자체40바이트를 그대로 더하는 것과는 다릅니다.

자체 IPv6 예제를2001:db8::10→2001:db8::20, ID120·SEQ5·PING-42로 두면 ICMPv6 길이는15, 가상 헤더의 상위 계층 길이도15입니다. Type128을 포함해 계산한 요청 체크섬은25d2입니다. IPv4 요청의f9bd를 주소만 바꿔 그대로 사용할 수 없습니다. IPv6 확장 헤더가 있으면 상위 계층 길이를 구하는 경계도 확인해야 합니다.

ICMPv6는 주소 해석과 라우터/이웃 발견에도 쓰이며 메시지 번호와 처리 조건도 별도 표준입니다. 이번에는 Echo와 체크섬 범위의 차이를 다루고, NDP의 실제 처리·IPv6 정책 권고를 모든 환경에 한 줄 규칙으로 적용하지 않습니다. ping 응답 여부와 필수 제어 기능의 동작은 구분합니다.

10. 같은 ID를 목적지와 시각 없이 묶으면 왜 틀릴까요?

ICMP ID는 요청·응답 대응에 쓰는16비트 필드이지 TCP 포트나 전 세계에서 유일한 세션 번호가 아닙니다. 프로세스가 새로 시작할 때 다른 ID를 고르는 구현도 있고, 여러 목적지에서 같은 ID를 공유하는 구현도 있습니다. 교재의 특정 OS 캡처는 그 환경의 관측이며 오늘의 모든 버전·프로그램 동작을 보증하지 않습니다.

자체 요청 장부 · 동일 ID를 목적지와 함께 추적
요청목적지ID/SEQ분석 메모
A의 첫 요청B 192.0.2.20120/30B의 대응 응답을 찾음
A의 다음 요청B 192.0.2.20120/31새 요청 번호
A의 다른 목적지 요청C 198.51.100.20120/32ID가 같아도 별도 목적지
A의 후속 요청B 192.0.2.20120/33B만 고르면31→33으로 보임

B만 필터링했을 때 Sequence32가 빠졌다고 손실을 확정하면 C에게 보낸 정상 요청을 놓칠 수 있습니다. 반대로 다른 ID가 보이면 반드시 다른 프로세스라고 할 수도 없습니다. 도구의 ID 할당·NAT 변환·수집 시작과 병합을 고려하세요. 두 호스트의 같은 ID를 섞지 않으려면 IP 버전·요청 방향의 주소쌍·ID·SEQ·시각·페이로드를 함께 기록합니다.

NAT가 외부에서 ID를 바꾸는 경우 안쪽 캡처의120과 바깥쪽의다른 값은 같은 거래일 수 있습니다. 이때는 변환 기록과 동시 시각을 맞춰야 합니다. 헤더 숫자 한 개가 사용자·프로세스·OS를 인증하는 것은 아닙니다.

11. 응답이 먼저 돌아온 순서로 요청을 줄 세우지 않습니다

같은 A→B의 ID120 요청을SEQ51과52로 가정해 보죠. 51을1.000초에,52를1.015초에 보냈는데52 응답이1.035초에 먼저 오고51 응답은1.040초에 왔습니다. 반환 순서가 바뀌어도 주소와ID/SEQ·데이터를 맞춰 각각의 요청에 붙여야 합니다.

가상 교차 응답 · 한 센서의 경과 초
SEQ요청 시각응답 시각대응 간격
511.000초1.040초0.040초=40ms
521.015초1.035초0.020초=20ms

단순히 처음 받은 응답을 첫 요청에 붙이면 잘못된 RTT가 됩니다. 한 센서의 대응 간격에도 수집 위치·시간 정밀도·누락·중복과 호스트 처리 시간이 섞입니다. 페이로드에 시각이 보인다고 두 호스트의 시계가 자동으로 맞춰진 것도 아닙니다.

상대 요청을 보지 못한 Echo Reply는 수집 시작 전 요청·비대칭 경로·필터·위조 등 가설을 나눕니다. 요청 수보다 응답 수가 많아도 우선 원시 레코드의 중복·여러 수신자·다른 거래 혼입을 점검합니다. 도구가 연결해 주는 response frame 표시는 보조 분석이며 실제 호스트 상태를 대신하지 않습니다.

12. 한 초 안의 요청 두 개는 프로세스 두 개의 증거일까요?

가상 요청 시각1.000·1.015·2.000·2.015초라면 두 개의1초 주기가 겹친 듯 보입니다. 여러 ping 프로그램이 실행 중이라는 가설을 세울 수 있어요. 하지만 한 프로그램이 두 대상 또는 두 작업을 점검하거나, 간격 옵션을 조정했거나, 중복 수집이 있었을 수도 있습니다. “같은 초에 두 패킷”이라는 이유만으로 두 프로세스를 확정하지 않습니다.

1.015−1.000=0.015초=15ms이고,2.000−1.000=1.000초입니다. 프로그램의 기본 간격을 아는 것은 가설을 좁히는 데 유용하지만 옵션·버전·스케줄링과 수집 지연이 결과를 바꿀 수 있습니다. 프로세스 수는 단말 실행 기록·소켓/프로세스 정보·모니터링 구성을 대조해 확인하세요.

순환·누락·목적지 분산 때문에 Sequence 연속성만으로 총 요청 수를 세기도 어렵습니다. 관측한 고유 요청과 중복 레코드, 대응 응답, 응답을 못 찾은 요청을 별도로 집계하고 관측 기간을 명시합니다. Echo가 응용 수준의 확인 메시지처럼 쓰여도 ICMP가 TCP 신뢰성 기능을 제공하게 된 것은 아닙니다.

13. 낯선 데이터가 보이면 질문을 더합니다

운영체제의 기본 ping 프로그램은 일정한 문자열이나 시각 정보를 데이터에 넣을 수 있습니다. 그러나 사용자 정의 데이터, 모니터링 도구, 다른 응용이 사용하는 Echo도 있습니다. 평소의 문자열과 다르다고 곧바로 명령 제어 채널로 확정하면 오탐이 생깁니다.

가령 짧은 주기로 일정 크기 데이터가 오간다면 상태 점검일 수도 있습니다. 반대로 요청·응답 데이터가 지속적으로 변하고 명령과 결과처럼 연결된다면 추가 조사가 필요하겠지요. 빈도·크기·양방향 내용·프로세스·목적지의 평소 역할을 함께 검토합니다. 암호화되거나 압축된 데이터는 읽기 어렵다는 이유만으로 정상 또는 악성으로 분류하지 않습니다.

패턴으로 운영체제를 추정할 때도 같은 주의가 필요합니다. 사용자 정의 ping은 기본 문자열을 바꿀 수 있고 NAT 등은 일부 식별자에 영향을 줄 수 있습니다. 과거 교재의 Windows·Linux 예제는 그 캡처의 관측값이며 모든 현재 버전의 고정 서명이 아닙니다.

14. 기본 ping의 문자열은 표준의 의무 페이로드가 아닙니다

일부 iputils ping은 페이로드 앞에 송신 시각을 넣고 뒤를 일정 패턴으로 채워 RTT를 계산합니다. Windows 기본 ping의 데이터 크기와 문자 패턴은 다른 예시를 보여 줄 수 있습니다. 이런 차이는 자산의 평소 동작을 배우는 출발점이지 OS 고유 서명은 아닙니다. 같은 OS에서도 프로그램·버전·크기·패턴 옵션이 바꿀 수 있습니다.

가상 예제로 데이터56바이트 중 앞16바이트가 시각 구조라면 뒤는40바이트 패턴입니다. 다른 구현의 시각 구조가8바이트라면48바이트가 남습니다. 시각 자료구조의 크기·바이트 순서·초/마이크로초 단위를 실제 구현 확인 없이 고정하지 마세요. Wireshark의 시간 해석도 원시 바이트와 해당 디섹터의 가정에 근거합니다.

현장의 기준선(baseline)은 자산·프로세스·목적지 역할·주기·크기·내용을 묶어 만든 평소 모습입니다. 승인된 모니터링 도구가 다른 문자열을 쓴다는 사실은 기본 ping과 다른 동작이라는 뜻이지 즉시 악성이라는 뜻은 아닙니다. 반대로 기본 문자열을 그대로 복제한 공격 도구도 가능하므로 익숙한 문자열만으로 무해하다고 판정하지 않습니다.

15. 짧은 데이터, 업무 프로그램, SSH처럼 보이는 문자열을 구분합니다

교재는 기본 ping과 다른 데이터가 업무 프로그램의 자동 검색·원격 측정으로 설명된 과거 사례와, SSH 트래픽을 실어 나르는 것으로 분석한 다른 사례를 함께 소개합니다. 이번에는 그 당시 제작사 조사나 실제 PCAP을 재실행하지 않았습니다. 따라서 과거 특정 프로그램·목적지의 설명을 오늘 같은 문자열을 가진 모든 패킷의 정체로 옮기지 않습니다.

독립 사례로 Echo 데이터가 두 바이트 OK라면 ICMP 전체는8+2=10바이트, 옵션 없는 IPv4 전체는20+10=30바이트입니다. 짧은 길이나 작은 IP TTL은 조사할 단서지만 그 자체로 명령 제어 비콘은 아닙니다. 선언된 IP 길이 밖의Ethernet 패딩이나 잘못 정렬된 덤프를 ICMP 데이터로 세지 않는 것도 중요해요.

다른 자체 사례의 데이터에서 SSH-2.0-Example 같은 문자열이 보이면 SSH 식별 문자열과 닮은 내용을 ICMP가 운반한다는 가설을 세울 수 있습니다. 그 바이트가 실제 협상의 일부인지 단순 테스트 문자열인지, 이어지는 길이·양방향 교환·프로세스·목적지와 맞는지를 봅니다. 문자열 하나가 터널 성립·SSH 인증 성공·침해를 증명하지는 않습니다.

요청 데이터가 명령처럼 보이고 응답이 결과처럼 달라진다면 Echo의 단순 반환 규칙과 다른 동작을 조사합니다. 새 애플리케이션 요청, 중간 장비, 세션 잘못 묶기, 캡처 손상도 구분해야 합니다. 평문을 못 읽는 압축·암호화 데이터는 추가 분석이 필요하다는 뜻이며, 바로 악성 또는 정상이라는 결론이 아닙니다. 단말 프로세스와 서버·경계 장비 기록에 연결하세요.

16. 시각 데이터도 그대로 반환하고 IP 옵션은 따로 다룹니다

정상적인 완전한 Echo 요청/응답 쌍에서 응답은 요청 데이터를 돌려줍니다. 요청의 PING-42가 응답에서도 같고,ID120·SEQ5가 유지되는지 확인합니다. Type은8에서0, Code는 정상 요청·응답 모두0이고, 달라진 메시지의 체크섬을 다시 계산합니다. IPv4 주소는 방향이 반대로 되지만 IP TTL·IP 식별자·옵션·헤더 체크섬까지 모두 그대로 복사한다는 뜻은 아닙니다.

페이로드에 들어 있는 송신 시각은 Echo 응답자가 자신의 현재 시각으로 고쳐 쓰는 필드가 아닙니다. iputils가 보낸 시각을 그대로 돌려받아 자신의 시각과 비교하는 방식과 연결해 생각해 보세요. 여기서 교재의 페이로드 시각 갱신 설명은 수정합니다.

RFC1122의 Record Route·Time Stamp 옵션 갱신은 IP 헤더 옵션에 관한 설명입니다. Echo 데이터의 임의 타임스탬프, Type13/14의별도 ICMP Timestamp 메시지와 섞지 않습니다. 같은 “시간”이라는 단어가 나와도 위치와 프로토콜 규칙이 달라요. RFC1122에는 의도적 단편화 미지원과 크기 제한에 따른 예외도 있으므로 크기·잘림 문제가 있는 사례는 완전한 작은 Echo 쌍과 따로 검토합니다.

데이터 불일치를 발견했다면 우선 같은 요청을 붙였는지, 양쪽이 모두 완전하게 저장됐는지와 재조립·변환·도구 설정을 확인합니다. 그 뒤 실제 수신 구현과 응용의 동작을 조사하세요. 관측 불일치를 설명하기 전에 모든 기본 Echo가 원래 데이터를 바꿔 반환한다고 가정하면 중요한 차이를 놓칩니다.

17. 요청보다 응답이 많거나 적으면

응답 수가 적으면 손실·속도 제한·필터링·캡처 누락을 먼저 고려합니다. 요청보다 많으면 중복 수집, 여러 목적지, 브로드캐스트·멀티캐스트 조건, 서로 다른 세션을 잘못 묶었는지 확인합니다. 단순히 ID 하나로 세면 관계없는 통신이 섞일 수 있습니다.

Echo 요청의 Code가 표준적인 0이 아닌 경우에는 잘못된 메시지와 구현별 처리를 구별합니다. 교재의 특정 호스트가 어떻게 응답했다는 관측을 표준의 정상 형식과 혼동하지 마세요. “수신 구현이 수용했다”와 “표준적인 요청이다”는 별도의 판단입니다.

18. 비표준 Code에 대한 반응은 표준과 분리해 기록합니다

정상 Echo Request와 Reply의 Code는0입니다. Type8에 Code7을 넣은 자체 입력을 생각해 보죠. Code7은 여기서 시험용으로 고른 비표준 조합이지 새 종류의 정상 ping이 아닙니다. 오류용 Type3의Code7 등과도 다른 조합입니다.

가상 처리 후보 · 실제 OS 실행 결과가 아님
입력가정한 처리관측 후보말할 수 없는 것
Type8/Code7무시·폐기응답 미관측방화벽이 반드시 차단함
Type8/Code7Type만0으로 변경Type0/Code7정상 표준 Echo Reply임
Type8/Code7Type·Code를0으로 처리Type0/Code0특정 OS/버전으로 확정

과거 교재는 일부Linux와Windows의 특정 시험에서 Code 보존과0처리 차이를 관측한 사례를 제시합니다. 이것은 실제 구현을 비교하는 학습 재료이지 모든 현재Linux/Windows의 계약이 아닙니다. 표준적인0코드 형식, 구현이 비표준 입력을 수용했는지, 그것을 수집한 위치를 분리해서 적습니다. 폐기·속도 제한·중간 장비 때문에 응답 자체가 안 보일 수도 있습니다.

Scapy 구성 예시 · 송신/실행 결과가 아님
from scapy.all import IP, ICMP, Raw
packet = IP(src="192.0.2.10", dst="192.0.2.20") / ICMP(type=8, code=7, id=120, seq=5) / Raw(load=b"LAB-ECHO")
raw_bytes = bytes(packet)

IP는IPv4 계층,ICMP는메시지,Raw는임의 데이터입니다. /는계층을쌓는연산이고,src/dst는주소,id/seq는식별자와순서입니다. b 접두어는문자열이아닌바이트열,bytes는직렬화된바이트로만드는함수입니다. 이예제에는송신함수를넣지않았습니다. 실제교재의특정호스트반응을재현했다고하지않습니다.

같은 ID120·SEQ5·LAB-ECHO에서 수동 계산한 요청8/7의 체크섬은db7a, 가정한 응답0/7은e37a,0/0은e381입니다. 체크섬이 맞아도 Code7 형식이 표준이 되는 것은 아닙니다. Scapy 구성 예시는 실제 실행·송신 결과가 아닙니다. 별도의 바이트 계산으로 확인한 수치와 실제 종단의 응답 관측을 구분합니다.

19. 필터와 길이 옵션의 뜻을 하나씩 확인합니다

iputils ping 절차 예시 · 실제 송신하지 않음
ping -4 -c 3 -s 32 192.0.2.20
Windows ping 절차 예시 · 실제 송신하지 않음
ping /4 /n 3 /l 32 /w 1000 192.0.2.20
저장된 파일 읽기 절차 예시 · 실제 필터 엔진 실행 아님
tcpdump -nn -tttt -r investigation.pcap 'icmp and host 192.0.2.10'
tshark -n -r investigation.pcap -Y 'icmp.type == 8 || icmp.type == 0' -T fields -e ip.src -e ip.dst -e icmp.type -e icmp.code -e icmp.ident -e icmp.seq

iputils의 -4는 IPv4, -c 3은 요청3개, -s 32는 Echo 데이터32바이트입니다. Windows의 /4와 /n 3은 버전/횟수, /l 32는 데이터 크기, /w 1000은 대기1000ms입니다. 같은 기호가 모든 운영체제에서 같은 뜻인 것은 아니며, 실제 사용 전 설치 버전의 매뉴얼을 맞춥니다. 데이터32에 Echo 헤더8과 IPv4 기본20을 더한 IP 전체는60바이트라는 계산도 연결하세요.

tcpdump의 -r은 파일 읽기, -nn은 주소와 서비스 이름 변환 생략, -tttt는 날짜 포함 시각입니다. 따옴표 안의 icmp는 ICMPv4, and는 두 조건 동시 만족, host는 출발지 또는 목적지 주소 조건입니다. -t로 시각을 없애면 짧게 읽을 수 있지만 이번의 시간 대응에는 불리합니다. -X는16진수/ASCII로 패킷 내용을 보는 옵션이며 표시 시작점과 IP 헤더 길이를 먼저 맞춰야 합니다. IPv6용 ICMP와 IPv4용 필터를 혼용하지 않습니다.

TShark의 -n도 이름 해석 생략, -r은 파일, -Y는 표시 필터입니다. ||는 둘 중 하나, ==는 같음이라 요청8 또는 응답0을 남깁니다. -T fields는 필드 출력, -e는 이어지는 필드 이름 하나를 선택합니다. ip.src/dst는 바깥 주소와 인용 계층의 여러 값이 함께 보일 수 있고, icmp.ident/seq는 BE 필드입니다. 실제 도구 설정과 계층을 펼쳐 보세요. 이 명령의 출력은 실행한 것처럼 만들지 않았습니다.

Wireshark의 icmp.type, icmp.code, icmp.ident, icmp.seq와 원시 바이트를 대조하고, 4.6.0 이후의 icmp.data 같은 새 필드도 버전을 확인합니다. 이전 화면의 data.data를 모든 페이로드가 항상 노출되는 필드로 가정하지 않습니다. 디섹터가 시간이나 다른 상위 구조로 해석하면 데이터 표시도 달라질 수 있습니다. icmp.resp_to/resp_in/resptime은 도구의 대응 분석이지 헤더 안의 새 필드가 아닙니다.

20. 보고할 때는 관측 사실과 추가 증거를 나눕니다

“A→B의8/0,ID120,SEQ5,데이터7바이트와 반대 방향의0/0·동일ID/SEQ·동일데이터를 관측했다”는 사실입니다. “해당 단말의 모니터링 프로그램이 보냈을 수 있다”는 가설이고, “같은 시각의 프로세스·모니터링 구성·단말 및 방화벽 기록을 확인한다”는 다음 단계입니다. 기본 문자열이나 포트가 없다는 이유로 응용 정체를 추측해 빈칸을 채우지 않습니다.

수집 지점·방향·시작/종료 시각·누락·중복·필터·캡처 길이·IP 단편과 재조립·암호화를 함께 남기세요. 낯선페이로드·응답부재·비표준Code만으로 공격·침해성공·회피·숙련도·무해함을 확정하지 않습니다. 리졸버 이름 해석이 관련됐다면 실제 목적지주소와서버역할도 확인합니다.

이번에는 교재14쪽을 직접 읽고 렌더 그림을 대조했으며 새 바이트·번호·길이·시간 계산을 검산했습니다. 과거 워크북/PCAP 검토 기록은 이번 직접 실행과 구분합니다. 원본 실습 파일·워크북 전체 재대조, 실제ping 송신·수신호스트·필터엔진·비표준입력의종단반응은 수행하지 않았습니다. 전체 워크북 최종 누락 검토의 잔여도 유지합니다.

21. 복습 · 조건을 바꾸어 생각하기

질문 1. ICMP에는 TCP 포트처럼 목적지 포트가 있나요?

ICMP 자체는 Type·Code로 분류합니다. 오류 메시지 안에 인용된 원래 TCP/UDP 포트가 보일 수는 있습니다.

질문 2. ping 데이터가 평소 문자열과 다르면 악성인가요?

응용별 정상 변형도 있습니다. 빈도·내용·종단 프로세스·정책을 대조합니다.

질문 3. 같은 ID의 응답은 모두 하나의 요청에 속하나요?

주소·Sequence·시각·데이터까지 함께 맞춰야 합니다.

질문 4. Identifier00 78을 역순으로 읽으면 무엇이 달라지나요?

네트워크 순서로는120입니다. 역순7800은30720이 됩니다. BE/LE 표시와 원시 바이트를 맞춰야 하며 같은 바이트를 다른 세션으로 오인하지 않습니다.

질문 5. ICMP15바이트·IPv4헤더20과24이면 IP 전체는?

각각35바이트와39바이트입니다. 헤더가4 늘어도 Echo 데이터7바이트는 그대로입니다. 링크 패딩과 캡처 길이는 별도 기준입니다.

질문 6. PING-42 요청과 응답의 체크섬을 복사해도 되나요?

Type이8에서0으로 바뀌므로 다시 계산합니다. 자체 예제는f9bd와01be입니다. 데이터 마지막32 뒤의00은 계산용이고 실제 메시지는15바이트입니다.

질문 7. ICMPv4에서 주소만 바꾸면 메시지 체크섬도 바뀌나요?

메시지 바이트가 같으면 반드시 바뀌는 것은 아닙니다. IPv4 가상 헤더가 없기 때문입니다. ICMPv6는 주소 등이 든 가상 헤더를 함께 계산한다는 차이가 있습니다.

질문 8. ID120의B 대상 Sequence31 다음이33이면32가 손실됐나요?

자체 장부의32는C 대상 요청입니다. 목적지 필터를 풀고 전체 범위를 확인해야 합니다. ID 하나만으로 세션과 프로세스를 고정하지 않습니다.

질문 9. SEQ52의응답이51보다 먼저 오면 어떻게 RTT를 구하나요?

각각 대응 요청과 붙입니다. 자체51은1.040−1.000=40ms,52는1.035−1.015=20ms입니다. 수신 순서대로 붙이면 잘못된 계산입니다.

질문 10. 한 초에 요청 두 개면 ping 프로세스도 두 개일까요?

두 주기가 겹친 가설은 가능하지만 단일 프로그램·간격 설정·중복 수집도 가능합니다. 실제 프로세스 기록과 모니터링 구성을 확인해야 합니다.

질문 11. 시각이 들어 있는 Echo 데이터는 응답자가 현재값으로 고치나요?

정상적인 완전한 Echo 쌍에서는 요청 데이터를 반환합니다. IP Timestamp 옵션의 갱신이나 별도의ICMP Timestamp 메시지와 혼동하지 않습니다. 크기·잘림 예외는 따로 검토합니다.

질문 12. Type8/Code7에Type0/Code7이 오고 체크섬도 맞으면 정상인가요?

산술적으로 일치하는 것과 표준적인Echo 형식은 다릅니다. 정상Code는0이고 과거 구현의 수용 차이는 오늘 모든OS의 동작이나 정체를 보장하지 않습니다.

질문 13. 두 바이트 데이터와SSH같은문자열은 무엇을 증명하나요?

각각 길이·내용의 관측입니다. 짧은 데이터는비콘의증명이 아니고 문자열은터널·인증성공의증명이 아닙니다. 양방향구조·시간·프로세스·서버기록을 추가로 확인합니다.

질문 14. Source Quench가 등록표에 있으면 지금도 사용 권장인가요?

아닙니다. Type4는폐기된용도이며 과거패킷해독과 현재사용권고를 구분합니다. 미배정·폐기·정상배정과 실제안전성은 각각 다른 질문입니다.

질문 15. ping의데이터32와ICMP length40은 모순인가요?

Echo 헤더8+데이터32=40바이트라 조건이 맞습니다. IPv4기본헤더20까지 더하면IP전체60입니다. 어떤계층의길이인지 먼저 표시합니다.
