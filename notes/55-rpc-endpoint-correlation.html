학습 범위

셋째 날 16강에서는 승인된 서비스의 가상 RPC 연결을 시간순으로 맞추고, 어떤 단서가 호출이나 업무 결과를 뒷받침하는지 살펴봅니다. 주소, 포트, 호출 번호와 시각은 독립적인 정상 교육 예제입니다.

1. 낯선 높은 포트를 보면 어떤 가설을 세울까요?

파일 서버 옆에서 수집한 트래픽에 관리 단말이 TCP 49620으로 연결한 기록이 있습니다. 번호만 보고 평소와 다른 서비스라고 단정하기 쉽지요. 바로 앞에 같은 서버의 TCP 135와 왕복이 있었다면 원격 프로시저 호출(RPC) 서비스의 주소를 알아낸 연결일 가능성을 살펴볼 수 있습니다. 실제 응답 속 포트와 후속 연결의 인터페이스가 이어지는지 확인해야 합니다.

전화 교환원이 담당 부서의 내선 번호를 알려 주면 발신자는 그 번호로 다시 전화합니다. 엔드포인트 매퍼(EPM)는 서비스가 연결을 받을 위치를 알려 준다는 점에서 닮았습니다. 다만 알려 준 주소로 새 연결이 만들어져도 그 위의 권한 검사가 성공했거나 업무 처리가 끝났다고 볼 수는 없습니다. 매핑, 연결, 인터페이스 연결, 호출, 업무 결과를 차례로 구분합니다.

2. RPC가 어떤 수송에 실렸는지 먼저 봅니다

RPC는 클라이언트가 서버의 특정 인터페이스에 있는 작업을 호출하는 방식입니다. 인터페이스는 작업 묶음이며 UUID라는 식별자와 버전이 붙습니다. 인터페이스 안에서 어떤 작업인지 가리키는 값이 opnum입니다. 같은 번호라도 인터페이스가 달라지면 뜻이 달라질 수 있습니다. 서비스의 네트워크 위치와 작업의 이름을 따로 확인하세요.

RPC 호출을 담는 경로와 관측 조건
수송 경로확인할 단서가시성의 조건
직접 TCP동적 위치가 필요한 경우 EPM 매핑과 실제 포트, 이후 RPC 바인드·호출미리 알려진 위치를 쓰거나 매핑이 수집 범위에 없을 수도 있습니다.
SMB의 이름 있는 파이프SMB 세션·공유와 파이프, 그 안의 RPCTCP 445 또는 공유 연결만으로 특정 RPC 작업을 알 수 없습니다.
HTTP/HTTPS를 매개로 한 RPC프록시·게이트웨이의 역할, 제품 설정과 응용 기록암호화 구간에서는 본문과 RPC 호출을 읽을 수 없는 경우가 있습니다.

DCOM은 Windows 분산 객체 호출에 RPC를 사용하는 경우입니다. RPC 직접 TCP 연결을 모두 DCOM이라고 부르지 않습니다. 이전 문헌의 여러 수송이나 등록 포트 예를 지금 모든 Windows 배포의 기본값으로 옮기지 말고, 해당 서비스의 사양과 실제 구성, 캡처 위치를 확인하세요.

3. 매핑 응답과 새 연결의 바인드를 시간순으로 이어 봅니다

가상 관리 단말은 192.0.2.55, 서비스는 198.51.100.55입니다. A·B는 다른 TCP 연결이고, 시각은 첫 매핑 요청부터 지난 밀리초입니다. 이 예제는 승인된 상태 조회가 관측됐다고 가정합니다.

매핑 응답에서 엔드포인트 정보를 펼치면 인터페이스·수송·포트 같은 값이 계층별로 표현되는 경우가 있습니다. 이 예제에서는 응답을 받은 시각 7에서 후속 바인드 15까지 15 − 7 = 8ms입니다. 두 흐름의 호스트와 반환된 포트가 같고, 바인드가 같은 인터페이스를 제안했으며 응답이 해당 컨텍스트를 받아들였다는 점이 함께 맞으면 매핑과 후속 연결이 관련됐다는 근거가 됩니다.

후속 RPC 요청의 Call ID가 9, 시각이 22ms이고 반대 방향의 일반 응답이 29ms라고 합시다. 같은 연결에서 Call ID와 컨텍스트를 대조하면 요청부터 응답까지 7ms입니다. 같은 번호라도 실패를 뜻하는 FAULT라면 해석이 달라집니다. 정상 RPC 응답 안에도 애플리케이션 오류가 들어갈 수 있습니다. 보호된 데이터나 누락이 있으면 서버에서 실제로 일어난 업무는 응답 종류만으로 확정하지 못합니다.

4. 프로토콜 필드와 규칙으로 증거의 범위를 좁힙니다

tcp.stream == 7 && dcerpc.cn_call_id == 9

Wireshark에서 해석이 된다면 이 표시 필터로 후속 연결의 호출 후보를 찾을 수 있습니다. 7은 해당 캡처에서 확인한 연결 번호를 가정한 값이고, cn_call_id는 연결 지향 DCE/RPC의 호출 ID입니다. ==는 같음, &&는 두 조건 모두입니다. 바인드·응답의 수락 컨텍스트를 먼저 찾고, 호출·응답 및 프래그먼트 재조립 상태를 확인하세요. 같은 ID가 다른 연결에 있을 수 있고, Bind ACK는 포함된 모든 컨텍스트를 받아들였다는 뜻이 아니므로 결과 목록을 읽어야 합니다.

Snort 3의 DCE/RPC 검사기는 인터페이스를 보는 dce_iface, 작업 번호의 dce_opnum, 검사할 RPC 스텁 데이터 버퍼를 선택하는 dce_stub_data 같은 조건을 제공합니다. 스텁은 호출 인자나 응답 데이터가 인코딩된 부분입니다. 규칙을 검증할 때는 정상 인터페이스와 다른 인터페이스, 기대한 작업과 다른 작업, 보이는 방향과 누락된 방향을 각각 비교하세요. 설치한 엔진에서 수송별 검사기가 실제로 적용되고 재조립된 버퍼가 전달되는지도 확인합니다. 기준점이나 바이트 순서를 확인하지 않은 원시 검색은 응용 필드 조건과 같은 의미를 보장하지 않습니다.

후속 연결이 다른 IP에서 보이거나 매핑과 멀리 떨어진 시각이라면 같은 업무였다는 가설이 약해집니다. 다중 서버, NAT, 캡처 위치를 확인하고 연결 요청과 바인드의 인터페이스를 다시 비교하세요. 관측에 그치는 결론은 “두 흐름의 매핑 포트와 바인드 인터페이스가 일치했다”입니다. 실제로 승인된 관리 작업이었는지, 어떤 데이터에 접근했는지는 인증·서버 작업·프로세스 로그를 같은 시간대에서 확인합니다.

5. 두 조사 장부를 하나의 결론으로 연결합니다

종합 연습으로 15강의 SMB 읽기와 이 강의의 가상 RPC 흐름을 각각 카드 한 장에 적어 보세요. SMB 카드에는 연결, 메시지 번호, 명령, 요청량·응답량을 적고, RPC 카드에는 매핑과 바인드의 주소·포트, 호출과 응답의 ID, 시각을 적습니다. 두 사례는 서로 다른 가상 호스트를 사용하므로 같은 사건으로 묶지 않습니다. 13강에서처럼 기록 줄 수와 독립 연결 수를 구별하고, 14강의 포트 가설이 어떤 증거에서 확인되는지 표시해 보세요.

해설. SMB의 ID 20은 16바이트를 요청하고 서버가 12바이트를 반환했습니다. RPC는 A와 B 두 연결을 쓰고 매핑과 바인드 사이가 8ms, 이어진 가상 호출의 응답까지가 7ms입니다. 같은 역할의 단말처럼 보여도 주소·시간·응용 작업이 다르면 별도의 조사 항목입니다. 보고서에는 센서에서 관측한 내용을 쓰고, 두 사례 모두 업무 목적과 종단의 결과를 확인할 서버 기록을 따로 적습니다.

복습과 해설

1. TCP 49620 기록 하나로 RPC라고 확정할까요?
포트만 관측했습니다. 앞선 매핑, 후속 바인드, 인터페이스와 컨텍스트를 확인합니다.
2. 7ms에 매핑이 돌아오고 15ms에 바인드 요청이 왔습니다.
간격은 8ms입니다. 근접한 시각은 단서이고 호스트·포트·인터페이스도 비교해야 합니다.
3. Bind ACK가 보이면 모든 컨텍스트가 승인됐나요?
각 항목의 결과를 펼쳐 승인·거절을 구분합니다. 이후 작업 호출의 성공과도 구별합니다.
4. Call ID 9 응답이 29ms인데 요청은 22ms였습니다.
같은 연결과 호출에 맞는 응답이라면 7ms입니다. 오류와 정상 응답의 내부 상태도 살핍니다.
5. RPC 탐지에서 인터페이스와 작업 번호가 맞으면 업무가 성공했나요?
일치 조건을 보았습니다. 업무 처리 여부는 응답과 승인된 서비스·종단 기록에서 확인합니다.

공식 자료와 확인일

2026-11-20에 Microsoft의 RPC 전송 규격·직접 TCP 수송, Wireshark의 DCE/RPC 필드, Snort 3의 DCE/RPC 규칙 옵션을 확인했습니다. 시간·번호는 가상 사례에서 검산했고 실제 패킷 분석기나 탐지 엔진을 실행하지 않았습니다.
