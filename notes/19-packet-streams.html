1. 경고를 본 뒤, 어느 센서의 어느 시간 자료를 읽을까

앞선 회차에서는 텍스트를 추출하고 집계했습니다. 이번에는 그 앞단으로 돌아가겠습니다. 경고를 중앙 화면에서 발견했더라도, 실제 패킷은 다른 위치의 센서에 저장되어 있을 수 있습니다. 센서는 통신을 관측하는 장치나 소프트웨어이고, 중앙 콘솔은 여러 관측 결과를 모아 조사하는 지점입니다.

조사자는 경고의 시각·시간대·관련 자산·센서를 확인한 뒤 필요한 구간의 패킷을 요청합니다. 모든 센서가 모든 경로를 보거나, 지나간 패킷을 손실 없이 영구 보관한다고 가정하지 않습니다. 필터·암호화·저장 기간·수집 손실·비대칭 경로 때문에 관측 범위가 달라질 수 있습니다.

예를 들어 지점의 센서가 실시간 경고를 중앙 콘솔이나 SIEM으로 보내더라도, 경고와 패킷 전체가 같은 곳에 보관된다는 뜻은 아닙니다. SIEM은 보안 이벤트를 모으고 연관 분석하는 시스템입니다. 원문 VM은 이런 분산 관측과 중앙 조사의 관계를 단순화한 환경이므로, 센서에서 저장 자료를 회수하는 단계와 중앙의 경고를 읽는 단계를 구별합니다.

이번 목표는 패킷을 가져오는 과정 → 바이너리 스트림 해석 → 정확한 계수 → 텍스트 검색과 치환을 연결하는 것입니다. 같은 파이프 기호를 사용해도 흐르는 데이터가 다르면 연결할 도구도 달라집니다.

자료와 실제 실행의 구분

첫째 날 워크북과 PCAP 여섯 개·621개 기록의 기존 오프라인 검증 기록을 확인했습니다. 이번에는 그 원본 실습을 재실행하지 않았으며, 전용 VM과 analyze의 센서 회수 환경에도 접근하지 않았습니다. 따라서 센서 목록·조회 시각·실제 패킷 수·tcpdump/capinfos 결과를 이번에 확인했다고 주장하지 않습니다. 패킷 명령은 사용법 예시이고, 문서용 주소로 만든 가상 텍스트에 대해서만 grep·sed의 검색·치환을 실제 실행해 검산했습니다.

“경고는 여기 있는데, 왜 패킷은 없죠?”

중앙 경고 화면에서 지점 서버의 통신을 발견했다고 해 볼게요. 화면에는 주소와 탐지 시각이 있지만, 패킷 전체를 여는 버튼에서는 아무 자료도 나오지 않습니다. 이때 바로 “오탐이었나 보다”라고 판단하면 조사를 너무 빨리 끝낼 수 있습니다. 경고의 저장 위치와 패킷의 저장 위치, 각각의 보관 기간이 다를 수 있기 때문입니다.

여러 건물의 CCTV를 관리하는 상황을 떠올려 보세요. 중앙 상황실에는 움직임 알림이 모이고, 원본 영상은 각 건물의 녹화기에 남아 있을 수 있습니다. 알림 한 줄을 읽는 일과 특정 카메라의 특정 시각 영상을 가져오는 일은 별도 작업이겠죠. 네트워크에서도 경고가 가리키는 센서와 시간 범위를 먼저 확인합니다. 다만 패킷 센서는 연속 영상을 녹화하는 카메라와 달라서, 수집 지점·필터·저장 길이·손실에 따라 개별 통신의 일부만 남을 수 있습니다.

이번에 인쇄 155~158쪽 네 페이지의 그림과 설명을 직접 읽고 대조했습니다. 전용 도구의 원리를 보편적인 회수·해석·검산 과정으로 연결하되, 그 도구를 직접 실행한 결과로 소개하지 않습니다. 이전 워크북 검증은 기존 기록이고, 이번 직접 실행은 아래의 독립 텍스트 검색·치환입니다.

2. 전용 analyze 도구의 문맥과 옵션을 읽는다

원문의 analyze는 실습 환경에서 센서의 패킷을 회수하는 전용 도구입니다. 일반 Linux에 항상 설치된 표준 명령이나 같은 이름의 다른 프로그램과 동일한 것으로 이해하면 안 됩니다. 원문은 인수 없이 실행하면 이용 가능한 센서를 보여 주고, 센서를 지정하면 자료를 가져오는 환경을 설명합니다. 현재 이 VM의 목록을 조회한 것은 아닙니다.

# 전용 환경의 문법 설명 — 그대로 복사할 실행 명령이 아님
analyze [-s 시작시각] [-e 끝시각] 센서

# 전용 도구가 실제 존재하는 환경에서의 연결 예시
analyze sensor-a | tcpdump -r - -n -c 100
원문 전용 도구의 입력과 패킷 해석 단계
표현역할확인할 조건
sensor-a회수할 센서의 설명용 이름현재 환경에 존재한다고 확인한 이름이 아님
-s / -e원문 환경의 시작 / 종료 시각 선택허용 시각 형식·시간대·경계 포함 여부를 실제 도움말로 확인
tcpdump -r -표준 입력에서 캡처 형식을 읽고 해석상류가 올바른 캡처 스트림을 내보내는지 확인
-n / -c 100이름 변환 억제 / 처리 패킷 수 제한전체 자료 수·출력 줄 수와 구별

대괄호는 선택 항목이라는 문법 표기입니다. 실제 시각 형식이 제공되지 않았는데 임의의 날짜 문자열이 동작한다고 꾸미지 않습니다. 실무에서는 센서와 콘솔의 시간대·시계 차이, 경고 전후 구간과 응답 방향까지 고려해 조회 범위를 정합니다.

자료를 회수하는 도구와 해석하는 도구를 나누면 각 단계의 책임이 명확해집니다. 회수 실패, 빈 시간 구간, 캡처 형식 오류, 해석 실패는 서로 다른 문제입니다. 끝의 명령이 아무것도 출력하지 않았다고 곧바로 ‘활동 없음’이라고 기록하지 않습니다.

센서 이름을 고르기 전에 시각의 기준을 맞춥니다

UTC는 여러 지역의 시각을 비교할 때 사용하는 공통 시간 기준입니다. 가령 경고 시각이 2026년 11월 2일 17:00이고 화면이 UTC+11을 사용한다고 합시다. 같은 순간은 UTC 기준 06:00입니다. 17에서 11시간을 빼면 6이 됩니다. 센서가 UTC를 쓰는데 변환 없이 17:00을 요청하면 11시간 뒤의 자료를 찾게 됩니다. 이는 시계가 11시간 틀린 것이 아니라 같은 순간을 서로 다른 시간대로 적은 경우입니다. 실제 시계 오차는 시간대를 맞춘 뒤 따로 확인해야 합니다.

“그럼 몇 분 전후로 넓혀 읽으면 되나요?” 경고가 흐름의 시작 시각인지 탐지 조건을 만족한 시각인지부터 확인해 보세요. 연결 시작이 경고보다 앞설 수도 있고 응답이 뒤에 올 수도 있습니다. 조회 경계가 시작 포함·끝 제외인지, 같은 패킷이 인접 구간에 중복 포함되는지에 따라서도 개수가 달라집니다. 전용 analyze의 허용 시각 문자열은 실제 도움말을 확인하지 않았으므로, 이 시각 예제를 실행 명령으로 꾸미지는 않습니다.

3. 바이너리 캡처와 사람이 읽는 텍스트는 다른 자료형이다

캡처 파일에는 패킷 바이트와 시각·저장 길이 같은 기록 정보가 들어 있습니다. 이것은 화면에 보이는 IP … 문장 자체가 아닙니다. 바이너리는 정해진 파일 구조에 따라 바이트를 해석해야 하는 데이터라고 이해하면 됩니다.

전용 회수 도구는 이 캡처 데이터를 표준 출력으로 내보내는 것으로 설명되어 있습니다. 반면 일반적인 tcpdump -r sample.pcap -n의 표준 출력은 패킷을 읽어서 만든 텍스트 설명입니다. 후자를 capinfos에 넣는다고 원래 패킷 파일이 되지는 않습니다.

tcpdump의 -w는 캡처 데이터를 파일로 쓰는 옵션이고, -w -는 그 캡처 출력을 표준 출력으로 보내는 사용법입니다. 기본 텍스트 요약을 출력하는 것과 구분합니다. -X로 16진수 문자열을 보았다고 바이너리 캡처를 그대로 전달한 것도 아닙니다. [1]

따라서 바이너리 캡처를 바로 sed로 치환하거나 일반 텍스트용 grep에 넣어 ‘패킷 필터’를 만든다고 생각하지 않습니다. 캡처 구조가 손상되거나 우연한 바이트 일치만 얻을 수 있습니다. 먼저 형식을 읽는 패킷 도구로 선택·해석하고 그 결과가 텍스트일 때 텍스트 처리 도구를 연결합니다.

표의 NAT는 네트워크 주소 변환입니다. 장치를 지나는 동안 주소나 포트가 바뀔 수 있어, 센서가 변환 전과 후 중 어디를 보는지 확인해야 합니다.

같은 통로로 보냈다고 같은 자료가 되지는 않습니다

표준 출력은 운반 통로의 이름이고, PCAP은 그 안에 담긴 자료의 형식입니다. 택배 차량이 같아도 상자 속 물건과 사용 설명서가 같지는 않은 것처럼, 캡처 바이트와 사람이 읽는 설명은 구별해야 합니다. 이 비유에서 실제 파이프가 운반하는 것은 바이트이며 파일 형식에 맞는 해석 규칙이 있어야 내용의 의미를 읽을 수 있습니다.

예를 들어 tcpdump의 기본 텍스트 출력에는 원래 헤더의 모든 바이트·저장 길이·파일 메타데이터가 그대로 남는다고 보장할 수 없습니다. 그 출력을 summary.pcap이라는 이름으로 저장해도 이름만 바뀌지 캡처 형식이 만들어지지는 않습니다. 반대로 -w로 만든 캡처를 단순 텍스트 파일처럼 치환하면 구조를 손상시킬 수 있습니다. 파일 확장자, 통로 이름, 실제 형식이라는 세 가지를 따로 확인하세요. [1]

4. 하이픈 하나는 프로그램이 정한 입력 약속이다

tcpdump -r -에서 첫 -r은 옵션이고, 뒤의 단독 -는 읽을 파일 대신 표준 입력을 사용하라는 인수입니다. 공식 매뉴얼은 이 동작을 명시합니다. 파이프의 앞 명령이 쓰는 캡처 스트림을 파일 경로 없이 읽을 수 있는 이유입니다. [1]

하지만 단독 하이픈이 모든 명령에서 운영체제가 보장하는 특별한 파일이라는 뜻은 아닙니다. 각 프로그램이 그 의미를 구현해야 합니다. 어떤 도구는 일반 파일이 필요하고, 어떤 분석은 이전 위치로 되돌아가 읽어야 하므로 파이프에서 지원되지 않을 수 있습니다.

예를 들어 TShark의 -2는 두 번 해석하는 분석 방식인데 입력을 되돌아 읽을 수 있어야 하므로 파이프·FIFO 입력에 사용할 수 없다고 공식 문서가 설명합니다. 이름만 -로 바꾸면 모든 파일 기반 분석이 스트리밍으로 바뀌는 것은 아닙니다. [4]

또한 -c 100으로 tcpdump가 먼저 읽기를 멈추면 상류 회수 도구는 닫힌 파이프를 만날 수 있습니다. 이는 표본 확인과 전체 회수 완료를 구별해야 할 이유입니다. 원본의 전체 크기·개수나 성공적인 보존을 이 제한된 출력으로 증명하지 않습니다.

왜 어떤 분석은 먼저 파일로 받아야 할까요?

FIFO는 이름을 가진 파이프처럼 프로그램 사이에 데이터를 전달하는 통로입니다. 파일처럼 보이는 경로가 있어도 일반 저장 파일과 읽기 조건이 같지는 않습니다. 한 번 지나간 입력을 다시 읽을 수 있는지가 다릅니다. 저장 파일은 읽는 위치를 앞뒤로 옮길 수 있지만, 일반 파이프는 이미 소비한 바이트를 임의로 다시 요청하는 파일과 같지 않습니다. 도구가 내부에서 일부를 저장하더라도 모든 형식·모드가 지원된다는 보장은 없습니다. 두 번 분석하는 TShark 모드의 제한은 바로 이런 입력 조건과 연결됩니다. [4]

처음 100개가 정상 해석되었다면 확인한 사실은 “그 범위는 읽을 수 있었다”입니다. 나머지 구간의 완전성이나 끝부분 손상까지 검사한 것은 아닙니다. 전체 회수와 반복 분석이 목적이면 회수 결과·오류·완료 상태를 확인하고, 보존한 파일의 식별값과 수집 조건을 함께 남깁니다. 다만 파일 해시가 일치해도 애초 수집하지 못한 패킷이 생기지는 않습니다.

5. 텍스트 여섯 줄과 패킷 여섯 개는 같지 않다

원문의 계수 예제를 먼저 분해해 보겠습니다. 전용 도구에서 받은 캡처를 tcpdump로 텍스트화하고 wc -l에 넘기면, 마지막 도구가 세는 것은 출력의 줄바꿈입니다. 패킷의 바이트 구조를 읽어 개수를 센 것이 아닙니다.

# 원문 환경의 연결 원리를 설명하는 예시 — 이 환경에서 실행하지 않음
analyze sensor-a | tcpdump -r - -n | wc -l

가상으로 P1의 설명이 1줄, P2의 설명이 3줄, P3의 설명이 2줄이었다고 하겠습니다. 패킷 기록은 3개인데 줄바꿈은 1+3+2=6개입니다. 이 숫자는 설명을 위한 가정이며, 특정 프로토콜이나 tcpdump 버전에서 실제로 이 줄 수를 출력한다고 재현한 결과가 아닙니다.

상세 프로토콜 설명이나 덤프 옵션은 한 패킷을 여러 줄로 표시할 수 있습니다. 반대로 줄 구분 방식과 출력 옵션도 달라질 수 있습니다. ‘대부분 비슷한 개수일 것’이라는 기대를 정확한 계수 근거로 사용하지 않습니다.

원문은 해석하지 못한 프로토콜의 16진수 덤프와 SMB의 여러 줄 설명을 사례로 듭니다. SMB는 파일·프린터 공유 등에 사용하는 프로토콜입니다. 학습 포인트는 특정 프로토콜 이름을 외우는 것이 아니라, 디코더의 표현 방식이 줄 수에 영향을 준다는 점입니다. 현재의 모든 버전과 옵션이 해당 패킷을 항상 같은 줄 수로 출력한다고 일반화하지 않습니다.

6. capinfos로 세는 것은 확보한 캡처의 기록이다

capinfos는 Wireshark 도구 모음에 속하며 캡처 파일을 읽어 기록 수·시각 범위·길이 등의 정보를 보여 줍니다. 기본 실행은 이용 가능한 통계를 출력하고, -c는 패킷 기록 수를 선택합니다. 여기서 -c 뒤에 100 같은 제한값을 넣는 tcpdump와 옵션 의미가 다릅니다. [2]

# 파일과 도구가 준비된 환경에서의 사용법 예시
capinfos -c sample.pcap
capinfos -c -a -e -u sample.pcap

# 바이너리 캡처 스트림을 받는 연결 예시
analyze sensor-a | capinfos -c -

-a는 가장 이른 패킷 시각, -e는 가장 늦은 시각, -u는 두 시각 차이로 계산하는 기간을 보여 줍니다. 시각 순서가 뒤섞여 있으면 파일의 첫 기록과 가장 이른 시각은 다를 수 있습니다. 기간이 길다는 것만으로 그 사이의 수집이 끊김 없이 완전했다고 확정하지 않습니다.

현재 공식 소스에서 capinfos는 순차 읽기를 요청하고, 공통 캡처 읽기 계층은 파일명 -를 표준 입력으로 처리합니다. 다만 모든 캡처 형식이 파이프의 제한된 되돌아 읽기에 대응하는 것은 아니므로 실제 버전·파일 형식·오류를 확인해야 합니다. 이 설명은 공식 소스를 읽어 확인한 것이며 이 환경에서 capinfos를 실행한 결과가 아닙니다. [3]

입력 파일이 손상되었거나 읽기가 중단되면 완전한 계수를 주장하지 않습니다. 공식 매뉴얼도 열기·읽기 오류를 표준 오류로 알리고 실패 상태를 반환하는 동작을 설명합니다. 성공 상태와 전체 입력을 읽었는지까지 확인해야 합니다. 스트림은 재조회·파일 해시·보존의 조건도 일반 파일과 다를 수 있습니다.

정상적으로 읽은 파일에 패킷 기록 3개가 있다고 확인해도 그것은 그 입력에서 확보한 기록 수입니다. 실제 회선의 총패킷 수·고유 연결 수·사용자 수·공격 횟수와 같지 않습니다. 중복 미러링은 같은 패킷을 여러 기록으로 담을 수 있고, 수집 손실은 기록을 빠뜨립니다. pcapng의 모든 블록을 단순히 더한 값과도 구별합니다.

정확한 숫자에도 조사 범위라는 울타리가 있습니다

자체 가정으로 센서 A에서 기록 100개, 센서 B에서 80개를 회수했다고 합시다. 둘을 합치면 저장된 기록은 180개입니다. 그런데 같은 통신을 두 지점에서 본 기록이 섞였다면 180을 고유 패킷 수라고 부를 수 없습니다. 반대로 한쪽에 응답 경로가 안 보였다면 작은 개수가 곧 응답 부재를 뜻하지도 않습니다. 중복 제거 기준에는 시각 정밀도·주소 변환·패킷 내용과 수집 위치가 영향을 줍니다.

시간도 작은 예제로 확인해 볼게요. 기록 순서가 06:00:02, 06:00:00, 06:00:05라면 가장 이른 시각은 둘째 기록의 00초이고 가장 늦은 시각은 05초입니다. 차이는 5−0=5초입니다. 첫 기록과 마지막 기록만 빼서 얻는 3초와 다르죠. 그 5초 사이에 자료가 몇 초 비었는지는 이 두 끝값만으로 알 수 없습니다. 이는 실제 capinfos 출력이 아닌 시각 계산을 위한 가정입니다. [2]

그래서 보고서에는 “센서 A에서 지정 구간으로 회수한 파일을 오류 없이 끝까지 읽었을 때 N개 기록을 확인했다”처럼 범위와 조건을 붙입니다. 수집 손실·중복·저장 길이와 회수 성공은 별도 근거로 검토합니다. 기록 수 검증이 중요한 이유와 그 숫자만으로 사건의 결과를 확정할 수 없는 이유가 함께 보이실 겁니다.

7. egrep만 쓰라는 권고는 현재 방식으로 고친다

grep는 기본적으로 패턴에 맞는 텍스트 줄을 선택하는 도구입니다. 이름은 줄 편집기의 global / regular expression / print와 관련됩니다. 정규표현식은 문자열의 모양을 표현하는 규칙이며, 단순한 단어 검색보다 넓은 조건을 표현할 수 있습니다.

공식 사용 지침 대조 — 2026년 11월 2일 재확인

원문은 egrep을 기본으로 쓰거나 grep을 egrep으로 연결하는 별칭을 제안합니다. 현재 GNU 문서는 egrep·fgrep을 오래된 명칭으로 설명하며, GNU Grep 3.8부터 2022년에 경고를 내도록 변경한 사실을 명시합니다. 새 명령과 스크립트에서는 grep -E와 grep -F처럼 의도한 모드를 직접 선택합니다. grep을 몰래 다른 문법으로 바꾸는 전역 별칭을 기본 지침으로 제안하지 않습니다. [5]

검색할 내용에 맞는 grep 모드 선택
명령의미이번 학습의 용도
grep / grep -G기본 정규표현식(BRE)기본 모드와 문법을 명시
grep -E확장 정규표현식(ERE)선택·반복 등 확장 표기 사용
grep -F고정 문자열점을 포함한 주소 문자열 등을 문자 그대로 찾음

‘기본은 불완전하고 확장은 모든 정규식을 지원한다’는 설명도 피합니다. GNU grep의 BRE와 ERE는 주로 연산자를 적는 문법이 다르며, 문자 클래스·반복·역참조의 동작과 이식성은 구현·모드별로 확인해야 합니다. ERE라고 PCRE의 모든 기능을 지원하는 것도 아닙니다. 다음 회차에서는 실제 연산자를 예제로 구별합니다. [6]

왜 검색 모드를 명령에 드러내 둘까요?

내 컴퓨터에서만 grep이 별칭으로 바뀌어 있다면, 같은 명령을 받은 동료의 결과가 달라질 수 있습니다. 검색 모드를 명시하면 어떤 정규식 문법을 요청했는지 기록에 남습니다. 단순 주소 문자열을 찾는 데 굳이 정규식 연산자의 의미까지 끌어올 필요는 없고, 대안 조건이 필요할 때는 그 문법을 지원하는 모드를 고르면 됩니다.

“확장이니까 항상 더 정확한가요?” 정확성은 검색 질문과 패턴·입력이 맞는지에 달려 있습니다. 고정 문자열은 점을 문자 그대로 찾지만 필드 경계를 자동으로 검증하지 않습니다. 확장 정규식도 잘못 쓰면 너무 넓거나 좁게 찾습니다. 뒤 두 강의에서는 구체적인 연산자를 풀고, 이번에는 어떤 프로그램이 어떤 규칙으로 문자열을 읽는지 구분하는 데 집중합니다.

8. 가상 텍스트에서 검색 결과와 종료 상태를 검산한다

다음은 직접 만든 텍스트 events.txt의 전체입니다. 센서명·주소·포트·결과라는 네 항목을 콜론으로 나누었습니다. 실제 센서 로그나 패킷의 해석 결과가 아닙니다.

sensor-a:192.0.2.10:443:ALLOW
sensor-b:198.51.100.20:53:DENY
sensor-c:203.0.113.30:8443:ALLOW
grep -E 'ALLOW|DENY' events.txt
grep -F '192.0.2.10' events.txt

첫 명령의 |는 작은따옴표 안의 정규표현식에서 ‘또는’을 뜻하므로 ALLOW 또는 DENY가 있는 줄을 선택합니다. 따옴표 밖에서 명령을 연결하는 셸 파이프와 다릅니다. 자체 텍스트에서는 세 줄 모두 선택됩니다. 두 번째는 점을 정규식의 연산자로 해석하지 않고 고정 문자열을 찾아 첫 줄을 선택합니다.

하지만 고정 문자열이 있다는 것과 정확히 그 주소 필드가 일치한다는 것까지는 다릅니다. 예를 들어 더 긴 주소 문자열의 일부로 포함될 수도 있습니다. 구분자와 필드 경계를 확인해야 합니다. ALLOW라고 적혀 있는 줄을 찾았다고 실제 방화벽 허용·서비스 처리 성공을 확인한 것도 아닙니다.

GNU grep의 통상적인 종료 상태는 선택한 줄이 있으면 0, 없으면 1, 오류면 2입니다. 이번 합성 입력에서 grep -F 'ABSENT' events.txt는 출력 없이 1을 반환했습니다. 이를 파일 읽기 오류와 같은 것으로 다루지 않습니다. 반대로 파일 누락 같은 오류로 빈 출력이 생겼을 때 ‘관심 활동이 없다’고 결론 내리지 않습니다. 조기 종료 옵션 등 예외가 있으므로 자동화에서는 사용한 옵션과 오류도 함께 확인합니다. [6]

줄을 선택하는 검색 결과는 매치 횟수나 패킷 수와 다릅니다. 한 줄에 단어가 여러 번 있어도 기본 출력은 그 줄 하나입니다. 이 점은 앞선 행 수와 기록 수의 차이와 연결됩니다.

부분 문자열, 필드 값, 일치 횟수를 나누어 봅시다

기존 세 줄에 sensor-d:192.0.2.100:443:ALLOW를 더해 extended.txt라고 하겠습니다. grep -F '192.0.2.10' extended.txt는 두 줄을 고릅니다. 192.0.2.100 안에도 그 문자열이 들어 있기 때문입니다. 이번에 아래 명령을 실제 실행해 차이를 확인했습니다.

# 독립 가상 텍스트 네 줄을 대상으로 한 검산
grep -F ':192.0.2.10:' extended.txt
# 선택: sensor-a:192.0.2.10:443:ALLOW 한 줄

printf 'ALLOW ALLOW\nDENY\n' | grep -c -F 'ALLOW'
# 출력: 1
printf 'ALLOW ALLOW\nDENY\n' | grep -o -F 'ALLOW'
# 출력: ALLOW 두 줄

앞뒤 콜론을 넣은 첫 패턴은 이 자체 입력의 값 양옆 구분자까지 요구합니다. 그래서 .100을 제외합니다. 하지만 같은 문자열이 다른 필드에 들어갈 수 있는 형식이라면 정확히 둘째 필드인지까지 보장하지는 않습니다. 이번 입력은 정해진 네 필드·IPv4 표기라는 전제를 두었습니다. IPv6 주소처럼 값 안에 콜론이 있는 자료에 이 규칙을 그대로 적용하지 않습니다.

-c는 선택한 줄 수를 출력합니다. 첫 줄에 ALLOW가 두 번 있어도 그 줄 하나를 셉니다. -o는 일치한 비어 있지 않은 부분만 각각 출력하므로 이 입력에서는 ALLOW 두 줄이 나옵니다. 검색 옵션을 바꾸면 오른쪽 wc -l이 세는 단위도 달라질 수 있습니다. 둘 중 어느 숫자도 실제 허용 통신·고유 연결 수를 뜻하지 않습니다. [10]

빈 결과도 원인을 구분해 보세요. ABSENT 검색의 상태 1과 입력 파일 누락의 상태 2를 이번 환경에서 직접 확인했습니다. 뒤에 wc를 연결하면 마지막 명령의 성공 상태만 보일 수 있으므로 앞선 파이프 오류 점검도 적용합니다. 또한 GNU grep의 -q는 일반 출력을 생략하고 일치 여부를 확인하는 옵션입니다. 이 옵션은 일치를 발견하면 오류가 있었어도 0으로 끝날 수 있는 예외가 있으므로 전체 입력 검증을 대신하는 옵션으로 보지 않습니다. [11]

9. sed는 흐르는 텍스트를 편집하고 결과를 출력한다

sed는 Stream Editor, 즉 스트림 편집기입니다. 데이터가 거의 원하는 형태인데 구분자 등을 조금 바꿔야 할 때 사용할 수 있습니다. 원문의 시스템 계정 파일 예제 대신 개인정보가 없는 위의 자체 텍스트를 사용하겠습니다. 실제 시스템의 계정 파일을 읽거나 수정하지 않습니다.

sed -e 's/:/,/g' events.txt
# 앞 명령에 연결하는 형태의 사용법
cat events.txt | sed -e 's/:/,/g'

-e는 sed에 실행할 편집 프로그램을 전달하는 옵션입니다. s/:/,/g는 ‘콜론을 찾아 쉼표로 바꾸되 한 줄 안의 모든 해당 위치에 적용’하는 프로그램입니다. cat은 파일 내용을 표준 출력으로 보내며, 위 두 방식은 이 입력을 편집기에 전달하는 경로가 다릅니다. sed가 직접 파일을 읽을 수 있어 cat이 반드시 필요한 것은 아닙니다.

치환식 s/:/,/g의 구성
부분역할오해하지 않을 점
s치환(substitute) 명령검색만 하고 끝내는 명령과 다름
첫 / 뒤의 :찾을 정규표현식여기서는 콜론 하나라는 단순 패턴
다음 / 뒤의 ,대체할 문자열검색 패턴과 다른 역할
마지막 / 뒤의 g패턴 공간 안의 모든 일치에 적용보통의 한 줄 처리에서 줄 전체의 반복 일치

기본적인 이 예제에서는 sed가 입력을 한 줄씩 패턴 공간이라는 작업 영역에 놓고 편집한 뒤 출력합니다. 파일 전체를 하나의 거대한 줄로 보고 딱 한 번 치환하는 것이 아닙니다. g가 없으면 각 줄의 첫 일치만 바꾸고, 있으면 그 줄의 모든 일치를 바꿉니다. 고급 명령으로 여러 줄을 다루는 경우의 범위는 별도로 이해해야 합니다. [7]

출력 양식을 조금 바꾸는 이유부터 정합니다

다음 분석 도구가 간단한 쉼표 구분 입력만 받는데 현재 자료는 콜론으로 나뉘어 있다고 해 보겠습니다. 이미 필요한 값은 있고 구분자만 바꾸면 되는 좁은 상황이라면 sed가 유용할 수 있습니다. 다만 검색할 때 쓰는 원본과 전달용 파생 결과는 구별해 두어야, 변환 뒤 결과가 달라졌을 때 이유를 되짚을 수 있습니다.

작은따옴표는 s/:/,/g를 셸에 흩어지지 않는 하나의 프로그램 인수로 전달합니다. 첫 슬래시 뒤부터 다음 슬래시 전까지가 검색식, 그다음 구간이 대체 문자열, 마지막 뒤가 수정 플래그입니다. 이 구조를 먼저 읽으면 콜론·쉼표를 다른 단순 문자로 바꾼 식도 어디가 달라졌는지 따라갈 수 있습니다. 대체 문자열에도 별도 특수 문법이 있으므로 아무 문자열이나 무검토로 끼워 넣는 일반 변환기로 확대하지 않습니다. [7]

10. g 하나가 바꾸는 범위를 눈으로 비교한다

가상 입력의 첫 줄에는 콜론이 세 개 있습니다. 첫 일치만 바꾸면 다음처럼 첫 콜론 하나만 쉼표가 됩니다. 자체 텍스트를 GNU sed 4.9에 넣어 검산한 결과입니다.

sed -e 's/:/,/' events.txt
# 첫 줄의 결과
sensor-a,192.0.2.10:443:ALLOW

g를 더하면 같은 줄의 세 콜론이 모두 쉼표로 바뀝니다. 세 입력 줄 모두를 처리한 전체 검산 결과는 다음과 같습니다.

sensor-a,192.0.2.10,443,ALLOW
sensor-b,198.51.100.20,53,DENY
sensor-c,203.0.113.30,8443,ALLOW

각 줄의 필드 네 개 사이에는 구분자 세 개가 있으므로, 이 입력에서는 전체 9곳이 바뀝니다. g 없이도 모든 입력 줄은 처리되지만 각 줄의 첫 위치만 바뀌어 총 3곳입니다. ‘global’이라는 단어를 보고 파일 전체에서 첫 줄만 처리하거나 파일 전체에서 한 번만 치환한다고 읽지 않습니다.

이 명령은 편집 결과를 표준 출력으로 보냅니다. 원본 파일을 제자리 수정하는 -i를 사용하지 않았으므로 원래 텍스트를 바꿨다는 뜻이 아닙니다. 기본적으로 치환되지 않은 줄도 출력할 수 있어 grep처럼 ‘매치된 줄만 고르는 도구’와 다릅니다. [8]

콜론을 쉼표로 바꾸는 것이 일반적인 CSV 변환기를 완성하는 것도 아닙니다. 원래 값 안에 쉼표·따옴표·줄바꿈이 있으면 CSV의 인용·이스케이프 규칙이 필요합니다. 이번에는 그런 문자가 없는 간단한 자체 입력으로 범위를 제한합니다. 실제 증거에서는 변환 전 원문을 보존하고 결과와 사용 명령을 구별합니다.

바꿀 문자가 없는 줄은 사라질까요?

note only라는 줄을 추가한 입력을 같은 sed 치환식에 넣으면 그 줄은 그대로 출력됩니다. 이 기본 실행에서는 각 줄을 읽고 치환을 시도한 뒤 현재 작업 내용을 출력하기 때문입니다. grep의 “일치한 줄을 선택한다”와 달라요. sed가 성공 종료하고 세 줄을 출력했다고 세 줄 모두 바뀌었다고 판단할 수도 없습니다.

예를 들어 sed -e 's/ABSENT/X/g' events.txt는 찾는 문자열이 없어서 결과가 원래 세 줄과 같지만 정상 종료했습니다. 성공 상태는 이 예제에서 편집 프로그램을 처리했다는 의미이지, 치환이 한 번 이상 일어났다는 보장은 아닙니다. 이번에는 실행 전후 원본 파일의 해시, 즉 파일 바이트에서 계산한 식별용 요약값도 비교해 -i 없는 명령이 입력을 바꾸지 않았음을 확인했습니다. [8]

검색과 치환의 순서를 바꾸어도 차이가 납니다. 원본에서 :192.0.2.10:을 찾으면 한 줄이지만, 먼저 콜론을 모두 쉼표로 바꾸고 같은 문자열을 찾으면 0줄입니다. 주소가 사라진 것이 아니라 경계의 문자가 바뀌었습니다. 파이프 중간의 자료형뿐 아니라 문자열 형식도 다음 단계와 맞는지 확인해야 합니다.

11. 검색 문법을 도구 사이에 무조건 복사하지 않는다

원문은 정규표현식을 sed·awk·탐지 시스템에도 연결합니다. 여러 도구에서 비슷한 문자열 모양을 찾을 수 있다는 관점은 유효합니다. 그러나 셸의 파일명 패턴, grep BRE·ERE, sed의 검색식, 침입 탐지 규칙의 정규식이 모두 같은 문법과 처리 범위를 가진 것은 아닙니다.

도구에 따라 일치 단위가 한 줄·필드·버퍼·재조립한 메시지일 수 있습니다. 대소문자·인코딩·역참조·반복·여러 줄의 의미도 달라질 수 있습니다. 문자열을 찾은 맥락과 실제 바이트 범위를 확인해야 ‘로그 한 줄에서 일치했다’를 ‘수신 호스트가 그 명령을 처리했다’로 과장하지 않습니다.

과거 이름인 Bro는 현재 Zeek라는 이름으로 이어집니다. 공식 프로젝트는 2018년 이름 변경을 설명합니다. 이 변경을 2021년 이후에 새로 일어난 일로 소개하지 않고, 현재 문서·도구를 찾을 때 이름을 대응시키는 보충으로 사용합니다. 이름이 바뀌었다고 검색 문법이나 탐지 결과를 자동으로 같은 것으로 가정하지 않습니다. [9]

실제 워크플로에서는 먼저 센서·시간·입력 형식을 확인하고, 캡처를 읽는 도구로 범위를 검토하며, 기록 수와 오류를 확인합니다. 그 다음 해석된 텍스트나 명시적으로 추출한 필드를 검색·치환합니다. 명령이 성공했다고 수집과 해석의 모든 전제가 충족된 것은 아니므로 각 단계의 중간 결과와 종료 상태를 남깁니다.

12. 계수와 문자열 일치에서 실제 판단으로 넘어가기

패킷으로 확인 가능한 사실

실제 캡처가 있을 때 확보한 기록·주소·시각·길이·바이트와 보이는 프로토콜 정보입니다. 이 노트에서는 캡처를 실행하지 않았으므로 실제 패킷 수나 센서 활동을 확인하지 않았습니다. 확인한 것은 공식 문법·소스와 자체 텍스트 변환입니다.

단독으로 확정할 수 없는 부분

파일 기록 수만으로 회선 전체 개수·고유 연결·공격 횟수, 빈 출력만으로 무해함·차단 성공, 특정 도구 이름만으로 숙련도, ALLOW라는 문자열만으로 처리 성공, 암호화된 본문의 의미입니다.

함께 확인할 로그와 자료

원본 캡처·센서 보존 범위·수집 손실·중복, 회수 도구와 디코더의 오류·버전·옵션, 시간대와 관측 위치, 방화벽·서버·단말 프로세스·인증 로그와 필요한 복호화 정보입니다.

다음은 가상 텍스트 검증 메모의 예입니다.

자체 정의한 세 줄에서 grep -E의 선택 조건은 세 줄을, 고정 주소 문자열 검색은 한 줄을 선택했다. sed의 첫 일치 치환은 총 3곳, 전역 치환은 총 9곳의 구분자를 바꾸며 원본은 수정하지 않았다. 실제 캡처·센서와 관련 없는 문법 검증이므로 이 결과에서 허용·공격·패킷 수를 판단하지 않는다.

현대에도 패킷 분석은 관측한 통신과 조사할 범위를 검증하는 데 중요합니다. 그러나 VPN·TLS로 보호된 데이터를 일반 문자열 치환으로 평문으로 만들 수 없습니다. IP 재조립·상위 프로토콜 해석·복호화·응용의 실제 처리는 서로 다른 단계입니다. 내용이 보이지 않는 경우에는 관측 가능한 특징과 양단 로그를 함께 사용합니다.

문법 검증 뒤에는 실제 처리 기록으로 돌아갑니다

센서에서 관련 기록을 찾았다면 방화벽의 정책 결정 시각과 서버 수신·처리 결과, 단말 프로세스 및 인증 기록을 연결합니다. 주소 변환이나 리졸버를 거친 통신이면 주소·도메인 대응도 해당 시각의 기록으로 확인합니다. 패킷의 요청과 ALLOW 표기가 함께 보여도 서버 작업이 성공했는지는 별도 질문입니다. 응답이 안 보이면 먼저 비대칭 경로·수집 누락·암호화·재조립 설정을 검토합니다.

13. 복습 — 자료형, 계수, 검색, 치환

질문 1: analyze는 어떤 Linux에서도 같은 옵션으로 실행할 수 있나요?

해설: 원문의 전용 VM 도구입니다. 이 환경에는 제공되지 않았고 실제 센서나 시각 문법도 검증하지 않았습니다. 표준 도구와 전용 도구의 이름·버전·형식을 구별합니다.

질문 2: tcpdump -r -의 마지막 하이픈은 무엇인가요?

해설: 해당 프로그램이 표준 입력을 읽도록 정한 인수입니다. 모든 프로그램이 자동으로 지원하는 마법의 파일명은 아닙니다. 파이프에서 되돌아 읽기가 필요한 분석은 제한될 수 있습니다.

질문 3: tcpdump가 출력한 IP 문장을 capinfos에 넣으면 캡처를 셀 수 있나요?

해설: 텍스트 설명은 원래 바이너리 캡처 형식과 다릅니다. capinfos에는 캡처를 입력해야 합니다. 16진수 덤프 문자열도 원래 파일을 그대로 전달한 것은 아닙니다.

질문 4: 가상 기록 3개가 1·3·2줄을 출력했다면 wc -l 값은?

해설: 각 줄에 줄바꿈이 있다는 전제에서 6입니다. 기록 3과 다른 단위입니다. 실제 패킷 계수는 캡처 구조를 읽는 도구로 확인합니다.

질문 5: capinfos의 정확한 기록 수가 실제 회선의 전 패킷 수인가요?

해설: 완전히 읽은 입력 캡처의 기록 수입니다. 수집 손실·중복·추출 범위는 별도 검증입니다. 읽기 오류가 있는데 완전한 계수라고 보고하지도 않습니다.

질문 6: 현재도 grep을 egrep으로 무조건 별칭 처리할까요?

해설: 새 명령에서는 grep -E로 확장 정규식, grep -F로 고정 문자열을 명시합니다. GNU의 오래된 명칭 경고와 문법 차이를 반영합니다. ERE를 모든 정규식 기능의 보장으로 해석하지 않습니다.

질문 7: 'ALLOW|DENY'의 세로 막대는 셸 파이프인가요?

해설: 따옴표 안에서 grep -E가 읽는 대안 연산자입니다. 따옴표 밖의 명령 연결과 역할이 다릅니다. 문법을 해석하는 주체를 먼저 확인합니다.

질문 8: grep의 출력이 없고 종료 상태 1이면 오류인가요?

해설: 기본적인 GNU grep 사용에서는 선택된 줄이 없다는 의미입니다. 일반 오류의 2와 구별하며 옵션별 예외도 확인합니다. 일치하지 않았다는 것과 조사 대상 활동이 실제로 없었다는 결론은 다릅니다.

질문 9: sed에서 g를 빼면 파일의 첫 줄만 바뀌나요?

해설: 이번 기본 처리에서는 각 줄의 첫 일치가 바뀝니다. 세 줄에 콜론 3개씩이면 g 없이 3곳, g를 쓰면 9곳입니다. 결과는 stdout으로 가며, -i 없는 명령이 원본을 제자리 수정한 것은 아닙니다.

질문 10: 콜론을 모두 쉼표로 바꾸면 모든 자료가 올바른 CSV가 되나요?

해설: 필드 안에 쉼표·따옴표·줄바꿈이 있는 경우 인용 규칙이 필요합니다. 이번 단순 입력의 결과를 일반 변환기로 확대하지 않습니다. 원본 보존과 변환 명령·실행 결과를 함께 남깁니다.

추가 연습: 자체 세 줄에 sensor-d:192.0.2.100:443:ALLOW를 더하고 고정 문자열 192.0.2.10을 검색해 보세요. 더 긴 주소의 일부에도 일치할 수 있습니다. 다음 회차에서 배울 경계·문자 집합·반복 조건을 이용해 ‘값이 들어 있다’와 ‘정확한 필드가 일치한다’를 구별할 준비입니다. 이 연습은 실제 센서 로그의 정답이 아닙니다.

조건을 바꾼 추가 복습

질문 11: UTC+11 화면의 17:00을 UTC 센서의 17:00으로 조회하면 같은 구간인가요?

해설: 같은 순간은 UTC 06:00입니다. 시간대 변환과 시계 오차를 나누어 확인하고, 경고 시각의 의미와 조회 경계도 맞춥니다. 예제 시각을 전용 도구의 검증된 문자열 문법으로 취급하지 않습니다.

질문 12: 기록 시각이 02초·00초·05초 순이면 관측 범위는 3초인가요?

해설: 가장 이른 00초부터 늦은 05초까지 5초입니다. 파일 첫·마지막 위치와 시각의 최솟값·최댓값은 다를 수 있습니다. 그 사이 연속 수집 여부까지 증명하지는 않습니다.

질문 13: .10을 고정 문자열로 검색했는데 .100도 나왔습니다. grep 오류인가요?

해설: 지정한 부분 문자열에 정상적으로 일치했습니다. 이번 형식에서는 양쪽 콜론까지 요구하면 구분되지만 정확한 필드 위치나 다른 주소 형식까지 자동 검증되는 것은 아닙니다.

질문 14: ALLOW가 한 줄에 두 번 있으면 grep -c는 2인가요?

해설: 그 줄 하나를 세어 1입니다. -o는 이번 비어 있지 않은 일치 둘을 각각 출력합니다. 줄 수·일치 수·패킷 수·연결 수를 구별해야 합니다.

질문 15: sed가 성공했으니 치환도 반드시 있었을까요?

해설: 아닙니다. ABSENT가 없는 입력에서 해당 치환을 요청해도 기본 출력은 원문과 같고 정상 종료할 수 있습니다. 변경된 내용과 명령 상태를 따로 확인하며 원본 보존도 검증합니다.

질문 16: 콜론을 쉼표로 바꾼 뒤 원래의 콜론 경계 검색이 0건이면 주소가 없어진 걸까요?

해설: 문자열 형식이 바뀌어 패턴이 맞지 않을 수 있습니다. 각 단계의 출력과 검색 조건을 비교합니다. 빈 결과 하나로 활동 부재·안전함을 결론 내리지 않습니다.
