1. 링크의 배달 주소에서 IP의 목적지로

오늘의 출발점 — 같은 숫자 64가 왜 다른 뜻일까요?

동료가 “이 패킷은 64바이트야”라고 말했는데, IPv4의 Total Length에는 84가 적혀 있다고 해 볼까요? 둘 중 하나가 틀렸다고 먼저 고르지 말고, 어디서부터 어디까지 센 숫자인지 물어보면 됩니다. ICMP 영역 전체가 64이고, 그 앞의 IPv4 헤더가 20이면 두 설명은 함께 맞을 수 있습니다. 이번 강의는 이런 질문을 바이트에서 직접 풀어내는 연습입니다.

생활 비유로는 물건 상자와 배송 서류를 떠올려 보세요. 물건 무게만 적은 칸과 포장까지 합친 무게 칸은 숫자가 달라도 모순이 아니죠. 네트워크에서는 무게 대신 길이를 바이트로 셉니다. 다만 이 비유에는 한계가 있습니다. IPv4 헤더는 사람이 참고하는 종이만이 아니라 수신 장비가 다음 바이트의 의미를 결정하는 구조입니다. 헤더 길이를 네 바이트 잘못 잡으면 단순한 합계 오류를 넘어 다른 프로토콜을 읽게 됩니다.

“그럼 IP가 끝까지 배송을 책임지나요?” 경로를 따라 전달하는 기능과 수신 확인·재전송은 나누어 생각해야 합니다. 어떤 패킷이 사라졌다는 사실을 IP 자체가 해결해 준다고 기대하면 안 됩니다. 반대로 TCP의 재전송이 보인다고 IP만의 결함이 증명된 것도 아닙니다. 수집 누락·경로 변화·수신 지연까지 같은 시간축에서 확인해야 합니다.

앞선 회차에서는 같은 링크에서 누구에게 프레임을 보낼지, ARP가 그 MAC을 어떻게 알아내는지 살펴보았습니다. 이제 그 프레임 안의 IPv4 패킷을 읽습니다. Ethernet 목적지 MAC이 현재 링크의 다음 전달 지점을 가리킨다면, IPv4 헤더의 목적지 주소는 IP 패킷을 보낼 대상을 나타냅니다. 두 주소는 같은 질문에 답하는 값이 아닙니다.

가령 단말 192.0.2.10이 외부 서버 198.51.100.20에 보낸다고 가정하겠습니다. 단말은 선택한 게이트웨이의 MAC으로 프레임을 보내고, 라우터는 IP 경로를 조회해 다음 링크로 전달합니다. 단순한 일반 라우팅에서는 링크마다 Ethernet 헤더가 새로 구성되어도 최종 IP 목적지는 유지됩니다. NAT·터널·프록시가 있다면 어느 지점의 어떤 헤더인지 추가로 구분해야 합니다.

여기서 홉, hop은 경로상의 한 전달 단계를 말합니다. IP는 패킷을 홉을 거쳐 목적지로 옮기는 역할을 하며, 같은 출발지와 목적지의 패킷도 경로 변경이나 다중 경로 구성에 따라 다른 길을 지날 수 있습니다. 패킷 번호가 앞선 것이 반드시 먼저 도착한다고 가정하면 안 됩니다. 전달 경로의 변화와 누락·순서 변화는 서로 관련될 수 있지만, 관측 하나만으로 원인을 확정하지 않습니다.

IP는 최선형 전달, best effort을 제공합니다. 도착·순서·중복 방지를 자체적으로 모두 보장하거나 손실된 패킷을 다시 보내 주는 서비스가 아닙니다. 신뢰성은 TCP 또는 해당 응용·전송 프로토콜이 필요한 방식으로 보완합니다. ‘신뢰성을 보장하지 않는다’는 말은 모든 패킷이 불안정하거나 분석할 가치가 없다는 뜻이 아니라, 어느 계층에서 무엇을 확인해야 하는지 구분하라는 뜻입니다. [1]

이번 회차는 헤더의 구조와 앞부분 필드, 서비스 표시, 길이, 식별 번호를 다룹니다. 단편화는 큰 IP 패킷을 여러 IP 조각으로 나누는 동작이며 이후 회차에서 자세히 계산합니다. 전체 그림에 나오는 필드는 이번에 위치와 역할을 소개하되, 다음 회차의 상세 분석까지 끝났다고 보지는 않습니다.

예시와 자료의 범위

저장소의 2026년 11월 1일 검토에는 워크북과 첫째 날 PCAP 여섯 개·621기록의 오프라인 대조가 남아 있습니다. 이번 개정에서는 그 검토 기록과 본 교재 인쇄 91~100쪽을 직접 대조했으며, 원본 PCAP이나 워크북을 재실행하지 않았습니다. 아래 바이트·주소·시각·표는 문서용 주소를 사용해 자체 구성한 가상 예시입니다. 원본 도구 실행 결과가 아니며, 명령어도 제공된 실제 파일에 실행한 것으로 주장하지 않습니다.

2. DNS는 IP 주소와 MAC을 바꾸는 도구가 아니다

사람은 숫자 주소보다 이름을 기억하기 쉬워 DNS를 사용합니다. DNS, Domain Name System은 이름과 여러 종류의 자원 정보를 연결하는 체계입니다. IPv4 주소를 알아낼 때는 A 레코드를, IPv6 주소에는 AAAA 레코드를 사용합니다. [18] 역방향 조회에는 PTR 같은 별도 레코드와 이름 공간이 쓰입니다. 이름 조회가 끝나면 프로그램은 얻은 주소 등을 이용해 통신합니다. [2]

‘DNS가 주소를 번역한다’는 표현 때문에 매 패킷마다 DNS가 IP를 MAC으로 바꾸거나 IP 헤더에 호스트 이름을 넣는다고 이해하면 곤란합니다. IPv4 헤더의 출발지·목적지는 32비트 숫자 주소입니다. MAC 대응은 현재 링크의 ARP 등 다른 단계의 문제입니다. DNS 응답이 캐시되어 있을 수도 있고 애초에 숫자 주소를 사용했을 수도 있으므로, 접속 직전에 DNS 패킷이 보이지 않는다는 이유만으로 비정상이라고 하지 않습니다.

또한 역방향 이름은 접속 당시 사용한 이름의 증명서가 아닙니다. 같은 IP를 여러 이름과 서비스가 공유할 수 있고 주소가 시점에 따라 바뀔 수도 있습니다. 따라서 ‘이 IP의 역방향 이름이 이것이므로 사용자가 이 사이트에 접속했다’는 결론에는 추가 증거가 필요합니다. 단말의 이름 조회·프로세스 기록, 프록시·서버 로그와 관측 가능한 응용 정보를 함께 봅니다.

이름표·최종 주소·이번 배달 창구를 따로 적어 보세요

가상 이름 training.example을 조회해 198.51.100.20을 얻었고, 단말이 선택한 다음 홉이 192.0.2.1이라고 합시다. DNS에서 얻은 것은 서버 주소이고, ARP로 알아낼 대상은 이번 링크의 다음 홉 주소입니다. 보통 이 상황의 IP 목적지는 서버이고 Ethernet 목적지 MAC은 게이트웨이입니다. DNS·라우팅·ARP가 서로 이어지지만 같은 변환을 세 번 하는 것은 아닙니다.

조건을 바꿔 서버를 같은 서브넷의 192.0.2.20으로 옮기면 어떨까요? 선택 경로가 직접 연결이라면 ARP 대상이 서버 자체로 바뀔 수 있습니다. DNS를 사용했다는 사실만으로 다음 홉이 정해지는 것은 아닙니다. 실제 경로표·마스크·정책을 확인해야 하며, PTR 이름이 그럴듯하다는 이유로 통신의 허가 여부를 확정하지 않습니다.

3. 헤더 그림의 한 줄은 4바이트다

IPv4 헤더 그림은 보통 한 줄을 32비트, 즉 32 ÷ 8 = 4바이트로 그립니다. 기본 헤더는 다섯 줄이므로 5 × 4 = 20바이트입니다. 실제 패킷이 종이에 그린 직사각형으로 전송된다는 뜻은 아닙니다. 이어진 바이트를 일정한 폭으로 접어 놓으면 필드의 비트 수와 위치를 비교하기 쉬워집니다.

오프셋은 어떤 기준점에서 떨어진 바이트 위치이며 0부터 셉니다. 아래 표는 모두 IPv4 헤더 시작을 0으로 둡니다. 태그 없는 Ethernet II 프레임 시작을 0으로 보면 IPv4는 14바이트 뒤에서 시작하지만, VLAN·다른 링크 형식·터널에서는 달라질 수 있습니다. 기준점을 바꾸지 않고 숫자만 외우면 엉뚱한 바이트를 읽게 됩니다.

한 줄의 맨 왼쪽 비트가 0이고 맨 오른쪽이 31입니다. 그 다음 줄은 새로운 표가 아니라 이어지는 다음 네 바이트입니다. 따라서 두 번째 줄 왼쪽 Identification은 IP 시작에서 4바이트 떨어져 있고, 세 번째 줄 왼쪽 TTL은 8바이트 떨어져 있습니다. 비트 위치와 바이트 위치를 오가려면 8비트 = 1바이트라는 단위를 붙이면 덜 헷갈립니다.

뒤에 붙는 TCP·UDP 등의 영역을 IP 페이로드라고 부릅니다. 페이로드는 “내가 지금 보고 있는 헤더 뒤에 실은 것”이라는 상대적인 말입니다. IP 페이로드에는 TCP 헤더가 들어갈 수 있고, TCP 데이터는 그 TCP 헤더를 다시 제외한 영역입니다. 앞으로 “데이터 길이”를 적을 때도 어느 계층을 기준으로 했는지 함께 적어 주세요.

4. 첫 바이트를 둘로 나누어 Version을 읽는다

바이트 하나는 8비트이며 위쪽 4비트와 아래쪽 4비트를 각각 니블이라고 부릅니다. IPv4 헤더의 첫 바이트가 0x45라면 2진수는 0100 0101입니다. 앞의 0100 = 4가 Version, 뒤의 0101 = 5가 IHL입니다. 0x45 전체를 버전 69라고 해석하거나 5를 헤더 5바이트라고 읽지 않습니다.

일반 Ethernet II에서 EtherType 0x0800은 IPv4, 0x86dd는 IPv6를 가리킵니다. 바깥 종류 표시와 내부 Version이 맞는지 확인해야 합니다. IPv4 처리기로 들어간 데이터그램의 Version이 4가 아니면 RFC 1122는 조용히 폐기하도록 요구합니다. ‘조용히’는 상대에게 오류 응답을 보내지 않는다는 뜻이지, 로컬 로그·카운터에도 반드시 아무 흔적이 없다는 뜻은 아닙니다. [3]

패킷 분석기가 잘못된 Version을 표시하면 먼저 링크 유형·캡슐화·오프셋·수집 손상·디코딩 설정을 확인합니다. 실제로 잘못 만들어진 패킷일 수 있지만 ‘컴플라이언스 시험일 뿐이므로 의미가 없다’고 단정할 수는 없습니다. 비정상 입력·우회 시도 등의 가설은 실제 바이트와 대상 구현·후속 기록으로 검증해야 합니다. 응답이 캡처에 없다는 것만으로 폐기 준수나 무해함을 확정하지 않습니다.

버전 번호 5는 일반적인 다음 세대 IPv4라는 뜻이 아닙니다. IANA는 ST 계열 실험의 역사와 관련된 5를 역사적 예약 값으로 분류하며 4·6 외에도 역사적·미할당 범주를 구분합니다. 원문의 오래된 번호 설명은 이러한 등록 현황과 연결해 읽고, ‘그 번호를 보았으니 최신 IP가 설치됐다’거나 ‘관련 실험 구현은 전혀 없었다’고 확대하지 않습니다. [4]

0x45를 보는 것보다 먼저 할 일이 있습니다

가상 덤프에서 45라는 바이트를 찾았다고 IPv4 시작을 발견한 것은 아닙니다. 응용 데이터에도 같은 값이 얼마든지 등장합니다. 링크 형식과 바깥 EtherType, VLAN·터널의 경계를 따라 실제 IP 시작점을 먼저 정한 뒤 상위 니블을 읽습니다. 0x는 뒤 숫자가 16진수라는 표시이며 회선에 x 문자가 실린다는 뜻은 아닙니다.

바깥 Ethernet Type은 0800인데 정해진 IP 시작점의 상위 니블이 6이라면 어떻게 기록할까요? 우선 “이 경계에서 바깥 종류 표시와 내부 버전이 맞지 않는다”가 관측입니다. 손상·의도적 비정상 입력·잘못된 해석 설정은 가설입니다. 실제 수신 호스트가 폐기했는지는 호스트 측 수집이나 카운터·로그가 더 있어야 확인됩니다. 버전 불일치와 악성 여부를 한 문장으로 합치지 않는 이유입니다.

5. IHL은 바이트 수가 아니라 4바이트 묶음 수다

IHL, Internet Header Length은 IPv4 헤더 길이를 32비트 단위로 나타냅니다. 32비트는 4바이트이므로 실제 길이는 IHL × 4입니다. IHL 5는 20바이트, 6은 24바이트, 15는 60바이트입니다. 4비트로 0~15를 표현할 수 있지만 정상 IPv4 기본 헤더에 필요한 최소치는 5입니다. 표현 가능한 숫자 범위와 유효한 헤더 길이 범위는 다릅니다.

단위를 이렇게 정하면 4비트 안에 60바이트까지의 헤더 길이를 표현할 수 있습니다. 바이트 단위로 60을 직접 담으려면 2⁵ = 32로는 부족하고 2⁶ = 64여야 하므로 6비트가 필요합니다. 32비트 단위 표현은 두 비트를 절약하면서 헤더를 4바이트 경계에 맞추는 구조와 연결됩니다. 오늘날에도 이 필드의 의미는 그대로이므로 단위를 생략하지 않는 습관이 중요합니다.

IHL은 IP 헤더만 셉니다. TCP·UDP·ICMP의 헤더나 데이터는 포함하지 않습니다. 옵션이 없다면 IP 시작에서 20바이트 뒤가 IP 페이로드의 시작이고, IHL이 6이면 24바이트 뒤입니다. 헤더를 항상 20바이트로 가정하면 추가된 옵션 4바이트를 내부 프로토콜의 시작으로 잘못 읽을 수 있습니다.

패킷을 해석할 때는 IHL 계산과 실제 확보 범위를 함께 확인합니다. 첫 바이트가 0x46인데 IP 헤더 전체를 담기에 바이트가 부족하다면, 우선 캡처 잘림인지·길이 값이 부정확한지 조사해야 합니다. 계산된 끝 위치를 실제 확보 바이트 밖까지 무조건 따라가서는 안 됩니다.

숫자 6을 세 군데에 적용해 볼까요?

IHL이 6이라면 IP 헤더는 6묶음 × 4바이트/묶음 = 24바이트입니다. 기본 20바이트를 빼면 옵션·패딩 영역은 24 - 20 = 4바이트이고, IP 페이로드는 IP 시작 기준 오프셋 24부터입니다. 서로 관련된 계산이지만 “24바이트 헤더”, “4바이트 추가 영역”, “시작 위치 24”는 다른 질문의 답입니다.

반대로 첫 바이트가 44라면 Version은 여전히 4이지만 IHL은 4라서 헤더가 16바이트라고 주장합니다. 기본 주소 필드까지 담을 20바이트보다 작으므로 유효한 IPv4 헤더로 받아들일 수 없습니다. 값이 4라는 이유로 버전과 길이를 함께 정상이라고 판단하면 안 됩니다. 프로그램을 만들 때도 길이를 검사하기 전에 주소나 옵션을 확보 범위 밖에서 읽지 않도록 순서를 정해야 합니다.

6. 20바이트와 24바이트 헤더를 바이트로 비교한다

다음은 자체 계산한 가상 IPv4 헤더입니다. 첫 예제는 총 84바이트인 ICMP 패킷 중 IP 헤더 20바이트만 표시합니다. ICMP 영역 64바이트는 아래에 싣지 않았습니다. 두 번째는 총 32바이트 중 옵션을 포함한 IP 헤더 24바이트이며 ICMP 영역 8바이트는 생략했습니다. 실제 캡처나 tcpdump 출력이 아니고, 계산 예제를 위한 헤더 바이트입니다.

# 가상 예제 A: IPv4 헤더만 20바이트
45 00 00 54 00 00 40 00 40 01 4e 57 c0 00 02 0a
c6 33 64 14

# 가상 예제 B: IPv4 헤더만 24바이트
46 00 00 20 00 01 00 00 40 01 82 87 c0 00 02 0a
c6 33 64 14 07 03 04 00

A의 0번 바이트 45에서 Version 4와 IHL 5를 읽습니다. 출발지는 12~15번의 c0 00 02 0a로, 각 바이트를 10진수로 바꾸면 192.0.2.10입니다. 16~19번 c6 33 64 14는 198.51.100.20입니다. IP 기준 9번 값 01은 ICMP를 가리킵니다. 체크섬 값도 헤더 바이트에 맞게 계산했지만, 그것이 송신자의 소유권이나 실제 전송 사실을 인증하는 것은 아닙니다.

B는 첫 바이트가 46이므로 6 × 4 = 24바이트입니다. 출발지와 목적지 주소는 A와 같은 위치에 있고, 20번부터 추가 영역 07 03 04 00이 있습니다. 따라서 ICMP를 찾으려면 IP 시작에서 24바이트를 지나야 합니다. 태그 없는 Ethernet II 프레임 시작을 기준으로 바꾸면 A는 14 + 20 = 34, B는 14 + 24 = 38에서 ICMP 영역이 시작합니다.

이 4바이트 차이가 왜 중요한지 생각해 보세요. B를 A처럼 읽으면 07을 ICMP Type으로 오해할 수 있습니다. 실제로는 IP 옵션의 Type입니다. 값이 낯설다는 이유로 공격이라고 하기 전에, 그 값을 어느 헤더의 어느 위치에서 읽었는지 확인해야 합니다.

기준점을 바꾼 세 번째 계산

예제 B에 VLAN 태그 하나가 붙은 Ethernet II를 가정해 보겠습니다. 태그 없는 헤더 14바이트에 태그 4바이트가 더해져 IP 시작은 프레임 기준 18입니다. IHL6의 IP 헤더 24를 지나면 ICMP 시작은 18 + 24 = 42입니다. IP 기준 출발지 위치12는 프레임 기준 18 + 12 = 30으로 옮겨갑니다. IP 자체의 IHL 값이 태그 때문에 증가하는 것은 아닙니다.

가상 예제의 기준점을 바꾸었을 때 시작 위치 — 단위: 바이트, 0부터 계산
조건IP 시작IP 헤더 길이IP 페이로드 시작
A · 태그 없음145 × 4 = 2014 + 20 = 34
B · 태그 없음146 × 4 = 2414 + 24 = 38
B · VLAN 태그 하나14 + 4 = 186 × 4 = 2418 + 24 = 42

이 표는 해당 형식의 가상 프레임에만 적용합니다. 무선 캡처·Linux cooked 캡처·터널의 안쪽 IP를 같은 14나 18로 시작시키면 안 됩니다. 수집 메타데이터와 실제 디코딩 계층을 먼저 확인하세요. 표시된 헤더 두 개만으로 실제 ICMP 메시지의 체크섬이나 수신 결과까지 검증한 것은 아닙니다.

7. Record Route — 옵션의 길이와 패딩을 구별한다

IPv4 옵션은 기본 20바이트 뒤에 놓입니다. IANA의 옵션 목록에서 7, 0x07은 Record Route로, 패킷이 지나가는 과정에서 라우터 주소를 기록할 공간을 제공하는 기능입니다. Loose Source Route·Strict Source Route처럼 경로 선택에 관여하는 옵션과는 구분해야 합니다. ‘경로’라는 단어가 같아도 목적이 다릅니다. [5]

Record Route의 기본 제어부는 Type·Length·Pointer 각 1바이트로 3바이트입니다. Length는 이 옵션의 전체 바이트 수이고 Pointer는 다음 주소를 넣을 위치를 옵션 시작 기준의 1부터 세는 값입니다. 일반 IP 헤더 오프셋의 0부터 세기와 혼동하지 마세요. 기록한 IPv4 주소 하나는 4바이트이며 공간에 주소를 넣으면 Pointer가 4만큼 진행합니다. [1]

앞의 07 03 04 00을 순서대로 읽으면 Type 7, Length 3, Pointer 4이고 마지막 00은 뒤 영역을 끝내거나 정렬하는 데 쓰인 바이트로 읽습니다. Length가 3인 이 옵션에는 주소를 넣을 공간이 없습니다. Pointer 4는 Length 3을 이미 넘습니다. 따라서 Record Route가 있다는 것만으로 이 패킷에 경로 주소가 실제 저장되어 있다고 할 수 없습니다. 원문의 24바이트 예제도 이 점을 구별해서 읽어야 합니다.

최대 주소 수를 계산하면 더 분명해집니다. 최대 헤더 60에서 기본 20을 빼면 옵션·패딩에 40바이트가 남습니다. Record Route만 있다고 가정하면 제어부 3을 뺀 40 - 3 = 37바이트에서 완전한 주소는 37 ÷ 4 = 9개, 나머지 1바이트입니다. 주소 9개를 담은 옵션은 3 + 9 × 4 = 39바이트이고 정렬용 1바이트를 더하면 40이 됩니다. ‘옵션 자체가 고정 4바이트 제어부’라기보다 3바이트 제어부와 정렬이 합쳐진 결과라고 설명해야 정확합니다.

주소를 기록할 때마다 네트워크를 지나는 헤더가 무한히 4바이트씩 길어지는 것도 아닙니다. 처음 마련한 공간 안에서 기록하며 공간이 차면 더 기록할 수 없습니다. 다른 옵션이 차지하는 공간이 있으면 기록 가능한 수는 줄어듭니다. 옵션 0과 1은 한 바이트 형식이고 나머지에는 길이 필드가 있으므로, 모든 옵션을 똑같은 구조로 잘라 읽지도 않습니다. [5]

현재 환경의 경로 관측 한계 · 2026년 11월 2일 확인

Record Route를 쓰면 모든 인터넷 라우터를 빠짐없이 알아낼 수 있다는 가정은 피합니다. RFC 7126은 옵션별 처리·필터링과 운영 영향을 다루며 Record Route의 기본 처리로 폐기를 권고하는 조건도 설명합니다. 기록 공간과 실제 장비 정책을 확인해야 합니다. traceroute도 결과를 경로 단서로 삼지만 TTL이 다른 탐침과 ICMP 응답 등을 사용하는 방식이며 Record Route와 같은 절차가 아닙니다. 응답이 없는 홉을 곧바로 장애·차단·공격으로 분류하지 않습니다. [6] [7]

주소 한 칸을 예약하면 포인터가 어떻게 움직일까요?

주소를 실제로 담을 수 있는 독립적인 옵션 예시로 07 07 04 00 00 00 00 00을 생각해 보겠습니다. 처음 07은 Type7, 다음 07은 Length7, 04는 Pointer4입니다. 옵션의 4~7번째 바이트 네 개가 주소 한 칸이고, 끝의 00 하나는 IP 헤더를 4바이트 경계에 맞추는 추가 영역입니다. 기본20+추가8=28바이트이므로 이 경우 IHL은 28 ÷ 4 = 7입니다.

라우터가 자기 주소 192.0.2.1을 넣도록 처리했다는 가상 조건에서는 그 한 칸이 c0 00 02 01로 바뀌고 Pointer는 4 + 4 = 8이 됩니다. Length7을 넘었으므로 그 옵션 안에는 더 쓸 주소 칸이 없습니다. 옵션 길이나 IHL이 홉마다 증가한 것이 아니라 미리 예약된 칸의 내용과 다음 위치가 변한 것입니다. 실제 장비가 옵션을 허용·처리했는지는 별도 검증 대상입니다. [1]

택배의 빈 경유지 칸 비유가 여기에는 유용합니다. 칸이 있다는 것과 칸이 채워졌다는 것은 다르고, 칸이 아홉 개라고 실제 경유지가 아홉 개라는 뜻도 아닙니다. 더구나 실제 IP 옵션은 장비의 정책으로 폐기될 수 있으므로 인터넷 전체를 빠짐없이 기록하는 보증서로 쓰지는 않습니다.

8. Type of Service의 옛 의미를 현재 필드와 구분한다

IP 기준 1번 바이트는 초기 설명에서 ToS, Type of Service라고 부릅니다. 역사적으로 앞 3비트 Precedence는 우선도, 이어지는 비트들은 지연 최소화·처리량 확대·신뢰성 선호 등을 나타내려 했습니다. 이후 RFC 1349에서는 비용 최소화 의미도 다뤘습니다. 원문의 오래된 회선 비용과 느린 대체 회선 이야기는, 서로 다른 전송 요구를 구별하려던 배경으로 이해하면 됩니다. [8]

예를 들어 대화형 음성은 지연이 적기를 원하고, 큰 백업은 즉각 응답보다 많은 데이터를 옮기는 데 관심이 있을 수 있습니다. 회선 용량이 부족할 때 이 차이를 전혀 구별하지 않으면 한 작업의 대기열이 다른 작업의 품질을 해칠 수 있습니다. QoS, Quality of Service는 이런 처리 요구에 맞춰 분류·큐·스케줄링·대역 제한 등을 구성하는 관점입니다. 표시 비트 하나가 자동으로 좋은 품질을 만들어 주는 것은 아닙니다.

원문의 ‘대부분 무시되었다’거나 특정 방식은 사용된 적이 없다는 표현을 현재 모든 네트워크의 사실로 받아들이지 않습니다. 오늘날의 패킷에서는 같은 바이트를 DSCP 6비트와 ECN 2비트로 읽습니다. 옛 Delay 비트 위치에 1이 있다고 곧바로 지연 최소화 요청이라고 해석하지 말고, 적용되는 현재 필드 정의와 장비 정책을 확인합니다.

9. DSCP — 숫자보다 처리 정책을 읽는다

DSCP, Differentiated Services Codepoint는 패킷에 서비스 처리 분류를 표시하는 6비트 값입니다. 2⁶ = 64가지가 표현됩니다. 라우터가 이를 정책에 따라 큐나 전달 동작에 연결할 수 있지만, 값이 크면 인터넷 어디서나 더 먼저 전달한다는 단순 순위표는 아닙니다. 어떤 처리에 매핑되는지는 관리 도메인의 설정과 경계 정책이 중요합니다. [9]

보안 조사에서는 높은 DSCP가 붙었다는 이유만으로 중요 업무라 믿지 않습니다. 단말이 값을 설정했을 수 있고 경계 장비가 다시 표시했을 수도 있습니다. 두 지점의 DSCP가 다르면 정책에 따른 재표시인지 조사하고, 어떤 프로세스의 어떤 통신이 해당 큐를 사용했는지 단말·QoS 기록과 대조합니다. 이 필드는 콘텐츠의 정체나 허가 여부를 인증하지 않습니다.

분류 표시는 우선 통행증의 진위 확인이 아닙니다

물건에 “급송” 스티커를 붙였다고 모든 배송사가 같은 요금제와 순서를 보장하는 것은 아니죠. DSCP도 장비가 그 표시를 어떤 처리 행동에 연결했는지가 중요합니다. 이때 PHB, Per-Hop Behavior는 한 홉에서 적용하는 전달 처리 행동을 뜻합니다. 수신 분류, 큐 선택, 전송·폐기 정책과 실제 혼잡 상태가 이어져야 결과가 나옵니다. [9]

가상 사례에서 사내 입구에서는 EF46인데 출구에서는 0이 보였다면, 우선 두 센서가 같은 통신과 같은 안팎 헤더를 보았는지 맞춰야 합니다. 그다음 경계에서 값을 다시 설정하는 정책을 확인합니다. “공격자가 표시를 지웠다”는 것은 아직 가설입니다. 반대로 EF가 유지되어도 실제 지연이 낮았다는 증거는 아니므로 큐 통계·시각·응용 지연 기록을 함께 봅니다.

10. ECN — 혼잡을 버리지 않고 알릴 수 있지만 손실이 사라지는 것은 아니다

ECN, Explicit Congestion Notification은 네트워크 혼잡을 명시적으로 알리는 체계입니다. 패킷을 버려 손실로 혼잡을 알리는 대신, 지원되는 흐름의 패킷에 표시를 해서 송신자가 전송을 조절하도록 도울 수 있습니다. 큐가 너무 길어지기 전에 표시나 폐기를 결정하는 AQM, Active Queue Management과 연결되지만, 모든 라우터가 같은 알고리즘을 쓰거나 ECN이 항상 패킷 손실을 없애는 것은 아닙니다. [11]

고전적인 ECN 흐름에서는 송신자가 ECN 가능 패킷으로 표시하고, 혼잡을 알리려는 장비가 지원 조건에 맞게 이를 CE로 표시할 수 있습니다. 수신자는 전송 프로토콜의 피드백으로 송신자에게 상황을 알리고, 송신자는 혼잡 제어에 반영합니다. IP 필드와 그 위의 피드백이 연결되어야 하므로 패킷 하나의 ECT 값만 보고 양 끝의 협상·피드백·속도 조절이 모두 정상 작동했다고 확정하지 않습니다. TCP의 상세 피드백은 이후 해당 계층에서 다룹니다. [12]

2021년 이후 보충 · L4S

2023년의 실험 RFC 9331은 L4S의 ECN 식별에 ECT(1)을 사용하도록 정의합니다. L4S는 낮은 지연·낮은 손실·확장 가능한 처리량을 지향하는 혼잡 제어 체계와 연결됩니다. 따라서 오늘날 01과 10을 모든 문맥에서 완전히 같은 표시라고 뭉뚱그리지 않습니다. 다만 ECT(1) 하나를 보았다고 해당 경로 전체가 L4S를 지원하거나 모든 전제 조건이 충족되었다고 검증한 것은 아닙니다. 단말 구현과 큐·피드백을 확인합니다. [13]

CE는 ‘공격이 있었다’는 표시가 아닙니다. 업무량 증가·병목·장비 큐 정책 등의 상황일 수 있으며 패킷만으로 표시한 정확한 장비를 단정하기도 어렵습니다. 관측 위치별 값, 인터페이스 큐·폐기 통계, 연결의 재전송·지연과 호스트의 전송 변화를 연결합니다.

혼잡 표시, 피드백, 반응을 세 단계로 나누세요

패킷에서 CE를 읽었다는 것은 그 관측 지점에서 ECN 비트가 11이었다는 뜻입니다. “수신자가 이를 피드백했다”, “송신자가 전송을 조절했다”는 뒤 단계의 주장입니다. TCP를 예로 들면 같은 연결의 피드백과 송신 측 상태·전송 추이를 더 확인해야 합니다. 한 패킷에 표시가 있다는 이유로 세 단계를 모두 완료했다고 쓰지 않습니다.

조건을 바꿔 요청 방향만 캡처했다면 반대 방향 피드백은 원래 안 보일 수 있습니다. 터널 밖과 안의 IP 헤더도 ECN 전달 규칙과 수집 위치를 구분해야 합니다. CE가 없다는 사실만으로 혼잡이 전혀 없었다고 단정하지도 않습니다. ECN 대신 폐기로 알렸거나, 다른 경로·시점에서 혼잡이 있었거나, 해당 흐름이 ECN을 쓰지 않았을 수 있습니다.

11. 같은 한 바이트에서 DSCP와 ECN을 따로 계산한다

IP 기준 1번 바이트가 0xb9인 가상 패킷을 보겠습니다. 16진수 b는 11이므로 10진수 값은 11 × 16 + 9 = 185입니다. 2진수로 쓰면 10111001입니다. 앞 6비트 101110과 뒤 2비트 01로 나눕니다.

앞 6비트를 풀면 32 + 8 + 4 + 2 = 46으로 EF입니다. 뒤 2비트는 1이므로 ECT(1)입니다. 연산식으로는 DSCP가 185 ÷ 4의 정수 몫 = 46, ECN이 185를 4로 나눈 나머지 = 1입니다. 반대로 합치려면 46 × 4 + 1 = 185입니다.

ECN이 CE로 바뀌고 DSCP가 그대로라면 전체 바이트는 46 × 4 + 3 = 187 = 0xbb가 됩니다. 0xb9와 0xbb가 다르다고 서비스 분류까지 바뀌었다고 하지 않습니다. 두 필드를 분리해야 어떤 의미의 변화가 있었는지 설명할 수 있습니다.

12. Total Length는 IP 헤더와 그 뒤의 데이터를 합친 값이다

Total Length는 IP 시작 기준 2~3번 바이트의 16비트 값으로, 단위가 바이트입니다. IHL처럼 4를 곱하지 않습니다. 두 바이트는 네트워크 바이트 순서로 읽으므로 큰 자릿값이 먼저입니다. 00 54는 0 × 256 + 0x54 = 84이고, 0x54를 다시 풀면 5 × 16 + 4 = 80 + 4 = 84입니다. 54 00으로 뒤집어 읽으면 21,504가 되어 전혀 다른 값이 됩니다.

A의 전체 IP 길이 84에는 IP 헤더 20과 ICMP 영역 64가 포함됩니다. ICMP Echo의 기본 헤더 8을 더 구분하면 Echo 데이터는 84 - 20 - 8 = 56바이트입니다. 일반 ICMP의 모든 메시지가 같은 세부 구조라는 뜻은 아니며, 여기서는 Echo를 가정합니다. B는 0x0020 = 32, IP 헤더 24이므로 ICMP 영역 8, Echo 데이터는 32 - 24 - 8 = 0바이트입니다.

즉, 계산에서 뺄 대상은 Total Length 안에 들어 있는 헤더들입니다. Ethernet 헤더는 원래 IP Total Length에 없으므로 다시 빼지 않습니다. UDP의 Length는 UDP 헤더와 데이터 길이를 별도로 담지만, TCP와 ICMP Echo에는 이와 똑같은 전체 길이 필드가 없어 IP 길이·헤더 경계와 실제 구조를 연결해 계산합니다. TCP에서는 가변 헤더 길이도 읽어야 합니다.

16비트 전체 길이의 표현상 최대는 2¹⁶ - 1 = 65,535바이트입니다. 이것은 각 Ethernet 링크가 그만한 IP 패킷을 그대로 운반한다는 뜻이 아닙니다. MTU와 단편화·경로 조건은 별도입니다. 또한 단편화된 패킷의 Total Length는 그 개별 조각의 IP 길이이지 원래 응용 데이터 전체 길이가 아닙니다. 뒤 조각에 TCP 헤더가 없을 수 있으므로 모든 조각에서 TCP 헤더를 빼는 공식도 사용하지 않습니다.

길이 이상을 발견했을 때

IHL이 6이라 헤더가 24인데 Total Length가 20이면 구조가 맞지 않습니다. 계산·바이트 순서·디코딩 기준과 실제 바이트를 다시 확인하세요. 반대로 Total Length 84인데 수집 파일에 IP 시작 이후 40바이트만 있다면, 헤더 20 이후 확보 데이터는 20바이트입니다. 나머지가 회선에서 사라졌다고 하기 전에 캡처 저장 한도·잘림을 확인합니다. 헤더의 예상 길이와 파일에 남은 길이를 구분합니다.

예상 길이·저장 길이·회선 길이를 함께 적어 보세요

가상 A를 태그 없는 Ethernet에서 온전히 저장했다면 IP84에 Ethernet14를 더해 FCS를 제외한 98바이트가 됩니다. FCS4까지 회선 프레임에 포함하면102바이트입니다. 이것은 프리앰블이나 프레임 사이 간격을 더한 회선 점유량과는 또 다릅니다. 반대로 작은 B는 IP32+Ethernet14=46바이트여서 Ethernet 최소 프레임을 채우는 패딩 조건이 따로 생깁니다. 패딩은 IP Total Length를 늘리는 응용 데이터가 아닙니다.

수집 파일에서 IP 시작 뒤100바이트가 보이는데 IP Total Length가84라면 어떻게 할까요? 남은16바이트를 곧바로 ICMP 데이터에 더하지 마세요. 링크 패딩·트레일러·수집 형식·디코딩 오류 등 그 위치의 의미를 먼저 확인합니다. 반대로 IP40바이트만 저장되었다면 보이지 않는44바이트의 내용을 추정해 채우지 않습니다.

잘림과 손실도 다릅니다. 패킷 기록 하나의 앞부분만 저장하는 snaplen 제한은 한 기록 안의 바이트를 줄일 수 있습니다. 수집 손실은 패킷 기록 자체가 빠지는 상황일 수 있습니다. captured length와 original length 비교는 잘림을 찾는 데 도움이 되지만 두 값이 같다고 회선의 모든 패킷을 수집했다는 증명은 아닙니다.

-ntx는 n·t·x 세 옵션을 묶은 것입니다. 이 기본 IPv4/Ethernet 예제의 -x 덤프에서는 IP 시작을 기준으로 읽을 수 있지만, 옵션·다른 링크와 캡슐화를 만났다면 실제 출력 범위를 먼저 확인합니다. 반대로 링크 헤더까지 포함하는 옵션으로 바꾸었다면 같은 오프셋 0을 무조건 IP 시작으로 쓰면 안 됩니다. [14]

tcpdump가 ICMP Echo 요약에서 length 64라고 표시한 원문 사례는 IP 전체 길이 84와 모순되지 않습니다. 그 요약의 ICMP 영역 길이와 IP 헤더 안 Total Length가 기준을 달리하기 때문입니다. 64가 Echo 데이터만의 길이라고도 단정하지 않습니다. 도구 요약에서 숫자 하나를 떼어 ‘패킷 크기’라고 적기보다 무엇을 포함한 값인지 헤더·바이트와 대조합니다.

Wireshark에서는 IPv4를 펼쳐 Header Length와 Total Length를 비교할 수 있습니다. 공식 필드 ip.hdr_len, ip.len, ip.dsfield.dscp, ip.dsfield.ecn, ip.id를 활용할 때도 표시 단위와 범위를 확인하세요. 원래 IHL 니블 값 5와 바이트로 환산된 헤더 길이 20을 같은 숫자로 기대하지 않습니다. [15]

필터를 쓰기 전에 무엇을 고르는지 말로 풀어 보세요

ip.hdr_len > 20
ip.len < ip.hdr_len
ip.dsfield.dscp == 46 && ip.dsfield.ecn == 3

위 식은 Wireshark의 표시 필터 예시이며 이번 실행에서 캡처에 적용한 결과는 아닙니다. 첫 식의 ip.hdr_len은 바이트로 표시되는 IPv4 헤더 길이이고 >는 “크다”입니다. 20보다 큰 헤더 후보를 고르지만, 옵션 처리 성공이나 악성을 판정하지 않습니다. 두 번째의 <는 “작다”로, 전체 길이가 헤더 길이보다 작은 것으로 해석된 후보를 찾습니다. 손상·잘림·해석 조건을 다시 확인할 출발점입니다.

세 번째는 ==로 값이 같은지 비교하고 &&로 두 조건을 모두 요구합니다. DSCP46과 ECN3이 함께 있는 후보를 보려는 식입니다. DS 바이트가185인 앞 예제는 ECN1이므로 이 식에 맞지 않고,187인 변경 예제는 조건을 만족합니다. 숫자185와 DSCP46을 비교하는 식으로 바꾸면 목적 자체가 달라집니다. 공식 참조에서 필드 이름·형식·지원 버전 범위를 확인했으며, 실제 설치 버전과 재조립·중첩 IP 처리 설정도 기록해야 합니다. [15]

tcpdump의 출력도 먼저 필터 없이 소수 기록을 읽는 것과 특정 조건으로 줄이는 것을 구분하세요. -c 1은 분석할 표본을 하나로 제한할 뿐, 그 하나가 전체 사건을 대표한다는 뜻은 아닙니다. -n으로 숫자 주소를 보존하고 시각을 남겨 두면 다른 기록과 대조하기 쉽지만, 어떤 프로그램이 보냈는지까지 주소가 말해 주지는 않습니다.

14. IP ID는 전 세계 패킷의 일련번호가 아니다

Identification, IP ID는 IP 기준 4~5번의 16비트 값입니다. 중심 용도는 단편화·재조립 문맥에서 같은 데이터그램의 조각을 구분하는 것입니다. 이름에 식별이라는 말이 있어도 전 세계 모든 패킷을 유일하게 구별하거나 사용자·프로세스를 가리키는 값은 아닙니다. 재조립에서는 주소·프로토콜 등 다른 문맥도 함께 봅니다.

16비트는 65,536가지 값만 가지므로 순차 증가하는 구현도 언젠가 65,535 다음에 0으로 돌아갑니다. 모든 목적지에 걸친 하나의 카운터, 목적지별 상태, 임의성 있는 생성, 고정 값 등 관측 가능한 동작이 다를 수 있습니다. 원문의 운영체제별 경향을 현재 모든 버전의 고정 지문으로 사용하지 마세요. 두 패킷의 ID가 같다고 같은 패킷의 중복이라 하거나, 값이 뛰었다고 그 사이 전송 수를 바로 계산하지 않습니다.

RFC 6864의 적용 조건 · 2026년 11월 2일 확인

이 표준은 2013년에 이미 IP ID 해석을 보완했습니다. DF=1, MF=0, Fragment Offset=0인 atomic 데이터그램에서는 재조립용 ID에 의미를 부여하지 않으며 송신자가 임의 값으로 설정할 수 있습니다. DF는 단편화 금지, MF는 뒤 조각이 더 있는지, Offset은 조각 위치입니다. 이번 A처럼 ID가 0이어도 이 조건에서 그것만으로 오류나 공격을 뜻하지 않습니다. 반대로 단편화가 허용되거나 이미 조각인 경우의 제약까지 사라지는 것은 아닙니다. 단편화되지 않았다는 관찰 하나와 atomic 조건도 구분합니다. [16]

원문의 ‘일부 운영체제는 부호 있는 수처럼 취급한다’는 주의는 숫자의 표시 방식을 점검하라는 의미로 연결할 수 있습니다. 예를 들어 원시 0xffff는 부호 없는 16비트로 65,535이고, 같은 비트를 부호 있는 16비트 2의 보수로 표시하면 -1입니다. 회선에 음수 바이트가 추가된 것이 아닙니다. 도구·로그의 형식과 원시 바이트를 대조해야 하며, 이 표시만으로 특정 운영체제를 확정하지 않습니다.

‘조각이 아니다’와 ‘atomic이다’를 표로 구별합니다

IP ID 해석에 먼저 필요한 단편화 조건
DF / MF / Offset뜻ID 해석의 출발점

0 / 0 / 0지금은 조각이 아니지만 단편화 가능현재 비단편이라는 이유로 atomic 규칙을 적용하지 않음

DF는 Don't Fragment, 즉 단편화를 금지하는 비트입니다. MF는 More Fragments, 즉 뒤에 조각이 더 있다는 비트입니다. Offset은 원래 IP 데이터 안에서 이 조각이 놓일 위치이며 세부 단위 계산은 단편화 강의에서 이어집니다. 처음 두 행 모두 지금 보이는 패킷에는 조각 표시가 없지만 단편화 가능성의 조건이 다릅니다. 그래서 “ID0이어도 괜찮다”는 문장에도 조건을 붙여야 합니다. [16]

또한 예제 A의 IP ID0과 ICMP Echo의 식별자라는 말은 서로 다른 헤더의 필드입니다. 원문 도구 요약의 id라는 짧은 이름이 어느 계층을 가리키는지 확인하세요. 이번 A/B에는 IP 헤더만 제시했으므로 ICMP 식별자의 실제 값은 읽을 수 없습니다.

15. Idle scan 사례는 왜 생성 규칙의 전제를 요구할까

원문은 예측 가능한 IP ID가 간접적인 통신 관찰에 악용될 수 있다는 사례를 소개합니다. Idle scan은 비교적 조용한 중간 호스트 Z의 ID 변화에서, 대상 T가 Z에게 응답을 보냈는지 추정하려는 방식입니다. 아래는 원리를 이해하기 위한 가상 수치이며 실제 스캔 결과·실행 절차가 아닙니다.

Z가 모든 관련 응답마다 공유 ID를 정확히 1씩 증가시키고 다른 트래픽은 없다고 가정해 보겠습니다. 관측한 ID가 1,000이고, T가 Z에서 온 것처럼 보이는 SYN을 받았다고 합시다. T가 SYN-ACK을 Z에게 보내면 Z는 자신이 시작한 연결이 아니므로 RST를 보낼 수 있습니다. 이 추가 응답이 ID 하나를 소비한다면 다음 관측은 1,002가 될 수 있습니다. 추가 응답이 없었다면 다음 관측은 1,001일 수 있습니다. 변화량은 각각 1002 - 1000 = 2, 1001 - 1000 = 1입니다. 공식 설명은 RST 응답의 역할을 다루며, RST에 언제나 ACK가 함께 있다고 고정하지 않습니다. [17]

여기서 중요한 것은 숫자 2라는 마법의 기준이 아니라 생성 규칙과 추가 트래픽이 없다는 전제입니다. 목적지별 카운터·임의화·고정 ID·다른 업무·방화벽·응답 제한·경로 차이가 있으면 변화의 원인이 달라집니다. 닫힌 포트와 필터링도 이 간접 관찰만으로 항상 구분되지 않습니다. ‘최신 스택이면 무조건 임의화되어 불가능’이라는 일반화도 피하고 실제 관측 조건으로 판단합니다.

방어 분석에서는 ID 변화 하나로 이 기법이나 특정 도구를 확정하지 않습니다. Z에 도착한 예기치 않은 SYN-ACK과 Z의 RST, T가 본 출발지, 관련 수집·방화벽 기록을 시간상 연결합니다. T의 패킷에 Z가 출발지로 적혔다는 사실이 Z의 사용자가 직접 탐색했다는 증거는 아닙니다. 이 방식이 조건부로 원래 송신 주소를 숨길 수 있다는 것과 모든 로그·다른 지점에서 추적할 수 없다는 주장은 구별해야 합니다.

차이가 2라면 추가 패킷 하나가 반드시 증명될까요?

공유 카운터라는 전제를 실험으로 확인하지 않았다면 아닙니다. Z가 다른 서버에 정상 응답 하나를 보내도 같은 차이가 나올 수 있습니다. “관측한 두 ID의 차이는2”와 “그 원인은 대상의 열린 포트 응답이었다”는 별개의 문장입니다. 대상·중간 호스트·방화벽의 같은 시간대 기록을 연결해야 두 번째 주장에 가까워집니다.

카운터가 끝을 넘어가는 조건도 바꿔 볼까요? 이전 값65535에서 다음 관측이1이면 단순 뺄셈은 음수지만, 순차16비트 카운터의 한 번 감김을 가정한 모듈러 차이는 (1 - 65535) mod 65536 = 2입니다. 여기서 mod는 나눈 나머지로 값을 한 바퀴 범위에 맞추는 연산입니다. 이 계산조차 중간에 여러 바퀴 돌지 않았다는 전제를 요구하므로 전송 수를 복원하는 만능 공식은 아닙니다.

16. 이번 회차의 증거 구분

이번 필드들은 암호화된 통신에서도 헤더의 형식·길이·표시·패킷 변화 등을 조사하는 데 도움이 됩니다. 다만 IP 목적지·DSCP·ID를 읽은 것만으로 암호화 본문이나 실제 프로그램을 알아낸 것은 아닙니다. 패킷 분석은 여전히 중요하며, 그 중요성은 확인 가능한 사실의 경계를 정확하게 유지할 때 커집니다.

패킷으로 확인 가능한 사실

관측 지점의 IP 주소·Version·IHL·Total Length·DSCP·ECN·ID, 확보된 옵션과 바이트 경계, 여러 패킷의 값·시각 변화입니다. 원시 값과 계산한 길이를 나누어 기록합니다.

단독으로 확정할 수 없는 부분

실제 사용자·프로세스·도메인, 모든 홉의 경로, QoS 처리 성공, ECN 협상·속도 조절 성공, ID만으로 특정 운영체제·생성 도구·공격자의 수준, 암호화 본문의 내용과 공격의 최종 성공입니다.

함께 확인할 자료

단말의 연결·프로세스·DNS 기록, 수집 위치·링크 형식·잘림·손실 정보, 라우팅·QoS 정책과 큐 통계, 방화벽 처리, 서버·프록시 로그 및 필요하면 여러 지점의 동기화된 캡처입니다.

가상 예제 A의 IP 시작에서 Version 4, IHL 5, Total Length 84를 읽었다. IP 헤더 20바이트와 ICMP 영역 64바이트로 구분되며, Echo를 전제로 데이터는 56바이트이다. 제시된 자료는 헤더만 포함하므로 실제 Echo 바이트·수신 결과는 확인한 것이 아니다. ID 0의 의미는 DF·MF·Offset 조건과 함께 판단한다.

17. 복습 — 필드 값에서 결론까지 설명해 보기

본 교재의 이번 페이지 묶음에는 별도 워크북 연습 지시가 없지만, 기존 워크북 검토 기록에는 IPv4 필드 학습 목표가 있습니다. 아래 연계 실습과 함께 읽어 주세요. 아래는 독립적으로 구성한 복습이며 실제 PCAP 실행 결과를 대신하지 않습니다.

질문 1: 첫 바이트가 0x46이면 Version과 헤더 길이는 무엇일까요?

해설: 0100 0110으로 나누면 Version 4, IHL 6입니다. 길이는 6×4=24바이트이며 IP 시작 이후 24바이트가 지나야 다음 프로토콜이 시작합니다. 6바이트도 46바이트도 아닙니다.

질문 2: IHL은 4비트인데 왜 0~15바이트라고 하지 않을까요?

해설: 단위가 32비트, 즉 4바이트입니다. 정상 기본 헤더 최소가 5×4=20, 표현 가능한 최대가 15×4=60입니다. 숫자가 표현 가능하다고 모든 값이 유효하지는 않습니다.

질문 3: 07 03 04 00을 보았다면 라우터 주소가 하나 기록되었을까요?

해설: Type7·Length3·Pointer4인 Record Route 제어부에는 주소 공간이 없습니다. 남은 00을 라우터 주소로 읽지 않습니다. 최대 예제에서도 제어부3+주소36+정렬1=40으로 계산해야 합니다.

질문 4: DS 바이트 0xbb는 DSCP 187일까요?

해설: 전체 바이트가 187이며 DSCP는 187÷4의 몫 46, ECN은 나머지 3입니다. EF 분류와 CE 혼잡 표시를 별도로 읽습니다. 이것이 QoS 성공이나 공격을 증명하지는 않습니다.

질문 5: ECT(1)이 보이면 2021년 표처럼 ECT(0)과 늘 같은 의미로 읽어도 될까요?

해설: 기본 ECN 가능 표시를 이해하되 현재 L4S 식별 문맥을 확인해야 합니다. 필드 하나만으로 단말·경로·혼잡 제어 전체의 작동을 확인했다고 하지 않습니다.

질문 6: IP Total Length 84, IHL5인 ICMP Echo의 데이터는 64바이트일까요?

해설: IP 헤더20을 빼면 ICMP 전체64입니다. Echo 헤더8을 더 빼면 데이터56입니다. Ethernet14는 IP 전체 길이에 없으므로 이 계산에서 다시 빼지 않습니다.

질문 7: ID가 0이거나 반복되면 공격 패킷일까요?

해설: 그 값만으로는 알 수 없습니다. atomic 조건에서는 임의 값이 가능하고, 다른 상황에서도 생성 규칙·수집 중복·단편화 문맥을 확인해야 합니다. ID를 사용자나 운영체제의 확정 지문으로 쓰지 않습니다.

질문 8: IP Version이 이상하고 응답도 없으면 무해한 시험이라고 종결할까요?

해설: 먼저 실제 오프셋·링크 형식·손상·디코딩을 확인하고 대상·전후 활동을 조사합니다. 응답 부재만으로 폐기 준수·무해함·공격 실패를 확정하지 않습니다.

질문 9: Total Length84인데 IP 시작 뒤40바이트만 확보했다면 IP 페이로드64를 모두 분석한 것일까요?

해설: IHL5라면 헤더20 이후 확보한 IP 페이로드는40-20=20바이트뿐입니다. 헤더가 예고한64와 실제 확보20을 나누어 기록하고 저장 한도·잘림을 확인합니다.

추가 연습: 가상 예제 B에서 ICMP 영역의 시작을 태그 없는 Ethernet 기준으로 설명해 보세요. Ethernet14+IP24=38입니다. IP 전체32이므로 IP 밖 헤더14를 더한 데이터 단위는46바이트이며 회선의 최소 Ethernet 프레임에는 별도 패딩·FCS 조건이 있습니다. 수집 파일의 앞부분 길이를 실제 회선 프레임 전체로 오해하지 않는 것이 목표입니다.

조건을 바꾸는 추가 복습

질문 10: 첫 바이트44는 IPv4이므로 정상인가요?

해설: 상위니블4는 Version만 설명합니다. 하위니블4는16바이트 헤더를 주장해 기본20보다 작습니다. 기준점·실제 확보 바이트를 확인하고 구조 불일치로 조사해야 합니다. 정상 여부와 악성 여부도 별도 판단입니다.

질문 11: VLAN 태그 하나가 있는 예제 B에서 ICMP 시작이38인가요?

해설: 이 가정에서는 Ethernet18+IP24=42바이트입니다.38은 태그 없는 경우입니다. IP 기준으로는 두 경우 모두24이므로 기준점을 함께 써야 답의 의미가 분명해집니다.

질문 12: Record Route의 주소 한 칸 예시에서 Pointer가4→8이면 IHL도1 증가하나요?

해설: 아닙니다. Length7인 옵션의 예약 주소 칸을 채운 것입니다. 추가영역8을 포함한 IP헤더28·IHL7은 유지됩니다. 새 주소 칸이 자동으로 생기지도 않습니다.

질문 13: DSCP46은 그대로인데 DS 바이트가185→187입니다. 무엇이 바뀌었나요?

해설:185=46×4+1이고187=46×4+3이므로 ECN이ECT(1)에서CE로 변했습니다. 같은 통신·같은 헤더인지 대조한 뒤 혼잡 표시의 경로·피드백·호스트 반응을 추가 확인합니다. QoS 성공이나 공격을 단정하지 않습니다.

질문 14: DF0/MF0/Offset0이고 ID0이면 atomic의 임의 값 허용만으로 설명해도 될까요?

해설: 이 패킷은 현재 조각은 아니지만 DF0이라 단편화가 가능합니다. atomic의DF1 조건을 만족하지 않으므로 해당 예외를 그대로 적용하면 안 됩니다. 생성 규칙과 단편화 가능 데이터그램의 ID 요구사항을 검토해야 합니다.

질문 15: IP84바이트를 예고했는데 IP시작 뒤40바이트만 저장됐습니다. Echo데이터를56바이트 읽었나요?

해설: IHL5라면 실제 확보 IP페이로드는40-20=20바이트입니다. Echo헤더8까지 온전히 있다면 그 뒤 확보 데이터는12바이트뿐입니다. 예상 데이터56과 확보12를 구분하고, 캡처 잘림과 누락·실제 입력 오류를 조사합니다.

질문 16: IP ID65535 다음1이면 Idle scan이 입증되나요?

해설: 공유 순차16비트 카운터의 한 번 감김이라는 가정하에서 차이가2라고 계산할 수 있을 뿐입니다. 정상 추가 트래픽·카운터 정책·수집 간격이 다른 설명일 수 있습니다. 관련SYN-ACK·RST와 종단 기록이 더 필요합니다.
