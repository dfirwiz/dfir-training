1. IP 주소가 있는데 MAC 주소는 왜 필요할까

브라우저가 다른 네트워크의 서버에 접속한다고 생각해 보겠습니다. IP 주소는 IP 계층에서 목적지를 표현하지만, 지금 연결된 링크에서 실제로 누구에게 프레임을 보낼지도 정해야 합니다. Ethernet에서는 그 전달에 MAC 주소를 사용합니다. IP 패킷을 Ethernet 프레임에 담을 때 두 종류의 주소가 함께 등장하는 이유입니다.

멀리 있는 서버로 가는 경우 현재 링크의 프레임 목적지는 다음 전달 지점인 라우터일 수 있습니다. 그러면 IP 목적지와 Ethernet 목적지 MAC이 같은 장비를 가리키지 않습니다. 프레임의 바로 다음 수신자와 IP 통신의 목적지를 구분해야 패킷을 잘못 연결하지 않습니다.

네트워크 접근 계층, 또는 링크 계층을 배우는 이유가 여기에 있습니다. IPv4에서 다음 전달 지점의 IP 주소와 링크 주소를 대응시키는 데에는 ARP가 사용됩니다. IPv6는 ARP를 그대로 사용하지 않고 Neighbor Discovery를 사용합니다. 이웃 주소 확인에 멀티캐스트 등이 관여하며 자세한 절차는 후속 학습으로 연결하겠습니다. [1]

이번 회차는 Ethernet 프레임을 읽는 기초입니다. 목적지·출발지 MAC, 다음 프로토콜의 식별, 길이와 패딩, VLAN 태그가 바이트 위치를 어떻게 바꾸는지 설명합니다. 아래 덤프와 주소·수치는 독립적으로 구성한 학습용 예시이며, 제공되지 않은 실습 PCAP을 실행한 결과가 아닙니다.

2. Ethernet II와 IEEE 802 계열을 구분한다

IEEE는 네트워크 등 여러 기술의 표준을 다루는 단체이고, IEEE 802는 LAN 등의 기술을 다루는 표준 계열입니다. Ethernet은 802.3, 무선 LAN은 802.11과 연결됩니다. 여기서는 서버와 스위치 사이 등에서 자주 분석하는 Ethernet II 형식에 집중하겠습니다.

이름을 읽을 때 주의할 점이 있습니다. ‘Ethernet II 대 IEEE 802.3’을 모든 현대 표준이 서로 배타적인 두 기술이라는 뜻으로 이해하면 곤란합니다. 실제 분석에서는 특히 출발지 MAC 다음의 2바이트를 프로토콜 종류로 읽는지, 길이로 읽는지가 중요합니다.

Ethernet II 형식은 그 자리에 EtherType을 둡니다. 길이 기반 형식에서는 그 값 뒤의 LLC·SNAP 같은 구조를 더 따라가 프로토콜을 식별할 수 있습니다. LLC는 Logical Link Control, SNAP은 Subnetwork Access Protocol의 약자이며, 여기서는 추가적인 프로토콜 식별 정보를 제공하는 구조라고 이해하면 됩니다. LLC 3바이트와 SNAP 5바이트를 사용하는 전형적인 조합에서는 추가 8바이트가 필요하므로 같은 데이터 공간에서 IP 등에 쓸 수 있는 양이 줄어듭니다. 모든 프레임에 이 8바이트가 있다는 뜻은 아닙니다. [2]

학습 범위와 보안 중요성은 구분

이번에 무선 분석을 깊게 다루지 않는 것은 범위를 정한 것입니다. 단말에는 중요한 정보가 없거나 서버만 보면 충분하다는 전제로 확대하지 않습니다. 무선 단말·접근점·스위치도 관측과 보안 관리 대상입니다. NIST의 WLAN 지침 역시 구성요소 전반의 보안과 모니터링을 다룹니다. 이 지침은 2012년 문서이므로 무선의 중요성이 최근에야 생긴 변화라는 설명도 피해야 합니다. [3]

클라우드·가상 네트워크에서는 실제 관측 링크 형식이 다르거나 바깥 캡슐화가 붙을 수 있습니다. IP 계층 이상의 원리는 이어지더라도 모든 수집 자료가 같은 Ethernet 헤더로 시작한다고 가정하지 않습니다. 캡처의 링크 유형을 먼저 확인하세요.

3. 기본 Ethernet II 프레임의 구조

VLAN 태그가 없는 기본 Ethernet II를 가정하면 헤더는 목적지 MAC 6바이트 + 출발지 MAC 6바이트 + EtherType 2바이트 = 14바이트입니다. 그 뒤에 상위 데이터를 운반하는 페이로드와 필요한 패딩이 오고, 프레임 끝에는 4바이트 FCS가 붙습니다. [4]

프레임이 회선에서 시작될 때는 수신 동기화를 위한 프리앰블과 시작 구분 정보도 사용됩니다. 일반적인 패킷 캡처에는 이런 물리 전송 정보가 그대로 올라오지 않으며, Ethernet 최소 64바이트라는 계산에도 포함하지 않습니다. 패킷 분석 화면의 시작과 물리 신호의 시작을 같은 것으로 보지 마세요.

목적지 MAC이 맨 앞에 있으면 수신 측이 현재 링크에서 누구에게 향한 프레임인지 빠르게 판단할 수 있습니다. 그러나 주소가 맞는다고 무조건 응용 프로그램까지 전달되는 것은 아닙니다. 필터·드라이버·프레임 검증과 상위 프로토콜 처리 등 여러 조건이 뒤따릅니다.

또한 MAC 주소는 실제 사람이나 프로그램을 인증한 신원 정보가 아닙니다. 가상 인터페이스·주소 변경·수집 위치 등에 따라 해석이 달라질 수 있습니다. 관측한 MAC과 실제 자산의 관계는 스위치·단말·자산 정보와 함께 확인합니다.

4. 유니캐스트·브로드캐스트·멀티캐스트

유니캐스트는 특정한 한 수신자를 대상으로 하는 전달입니다. 브로드캐스트는 같은 링크의 브로드캐스트 범위에 있는 장치들을 대상으로 하며, Ethernet의 대표 주소는 ff:ff:ff:ff:ff:ff입니다. 멀티캐스트는 특정 그룹을 대상으로 하는 전달입니다. 각각 ‘하나·해당 범위 전체·그룹’이라는 차이가 있습니다.

브로드캐스트 MAC을 IP 서브넷의 브로드캐스트 주소와 같은 값이라고 설명하면 안 됩니다. 하나는 링크 계층의 6바이트 주소이고 다른 하나는 IP 계층의 주소입니다. IPv4 ARP 요청처럼 링크 전체에 물어볼 때 브로드캐스트 MAC이 사용될 수 있지만, IP 계층의 모든 주소와 일대일로 같은 의미가 되는 것은 아닙니다.

멀티캐스트도 그룹 주소를 보았다는 것과 모든 단말이 실제 처리했다는 것은 다릅니다. 스위치의 전달 설정, 그룹 가입 상태, 수신 필터 등이 영향을 줄 수 있습니다. 분석 센서가 복사본을 받는 상황과 실제 목적지 단말의 수신도 구별합니다.

가상 상황으로 192.0.2.10이 외부 서버 198.51.100.20에 접속하면서 프레임 목적지에 기본 게이트웨이의 MAC을 쓰는 경우를 생각해 보세요. 이 MAC을 외부 서버의 주소라고 기록하면 경로를 잘못 해석하게 됩니다. 같은 링크의 주소 역할을 먼저 확인하고 IP 통신과 연결해야 합니다.

5. EtherType을 읽어 다음 구조로 들어간다

EtherType은 헤더 다음의 데이터를 어떻게 해석할지 알려 주는 2바이트 식별값입니다. 태그 없는 Ethernet II에서는 프레임 시작 기준 오프셋 12~13에 있습니다. 해당 값으로 IPv4·IPv6·ARP 등을 구분하고 그 프로토콜의 형식과 길이를 따라갑니다.

자주 만나는 식별값과 다음 확인 지점
값의미읽을 때의 주의점
0x0800IPv4그 뒤에서 버전과 IHL 등 IPv4 구조를 확인합니다.
0x86DDIPv6IPv4 길이 필드를 그대로 적용하지 않습니다.
0x0806ARP이 위치부터 곧바로 IP 헤더가 나온다고 보지 않습니다.
0x8100일반적인 802.1Q 고객 VLAN 태그 식별태그 정보를 더 읽고 안쪽 Type/Length를 따라갑니다.

2바이트 정수는 바이트 순서도 확인합니다. 08 00은 이 필드에서 0x0800이지 0x0008이 아닙니다. 프로토콜 번호를 발견하는 것과 그 프로토콜의 정상 동작을 검증하는 것도 다른 단계입니다. 주소·길이·상태와 실제 데이터를 더 확인해야 합니다.

Type/Length 경계값 바로잡기

‘0x0600보다 작으면 전부 길이’라는 단순 구분은 보완해야 합니다. 0~1500은 길이, 1536 이상은 Type으로 구분하고, 1501~1535를 일반적인 유효 길이로 분류하지 않습니다. 1500은 0x05DC이고 1536은 0x0600입니다. IEEE의 공개 프로토콜 식별 기술 자료도 이 두 경계를 구분합니다. 해당 자료는 2020년 초안이며 최종 표준 그 자체로 소개하지 않습니다. [2]

길이로 해석하는 형식이라면 그 뒤의 LLC·SNAP 등의 식별 구조를 더 봐야 합니다. SNAP을 만났다고 모두 공격이나 매우 오래된 통신이라고 판단하지 않습니다. 또한 현대 802.3 전체를 ‘Ethernet II와 달리 항상 LLC/SNAP이 필요한 형식’으로 일반화하지 않습니다. 실제로 어떤 Length/Type 인코딩과 프로토콜을 사용했는지가 판단 기준입니다.

6. 64·1518·1500이라는 숫자의 기준을 구분한다

다음 계산은 VLAN 태그가 없는 일반 Ethernet 프레임을 기준으로 합니다. FCS를 포함한 최소 프레임 길이는 64바이트이므로 헤더 14바이트와 FCS 4바이트를 빼면 데이터·패딩 영역의 최소 길이는 46바이트입니다. [4]

최소 데이터·패딩 영역 = 64 - 14 - 4 = 46바이트
최소 프레임 = 헤더 14 + 데이터·패딩 46 + FCS 4 = 64바이트

일반적인 최대 프레임 = 14 + 1500 + 4 = 1518바이트
Ethernet 페이로드의 일반적인 최대 = 1518 - 14 - 4 = 1500바이트

여기서 46바이트 전부가 실제 IP 데이터라는 뜻은 아닙니다. 상위 데이터가 짧으면 패딩을 넣어 최소 길이를 맞춥니다. 예를 들어 상위 데이터가 28바이트라면 46 - 28 = 18바이트의 패딩이 필요하고, 프레임은 14 + 28 + 18 + 4 = 64바이트가 됩니다. 이 18바이트를 응용 메시지나 IP 패킷의 일부로 자동 해석하면 안 됩니다.

MTU는 그 링크에서 운반할 수 있는 데이터 단위의 최대 크기와 관련된 값입니다. 일반 Ethernet의 IP MTU 1500이라는 말은 IP 패킷 전체가 들어가는 Ethernet 페이로드 공간을 가리키며, Ethernet 헤더와 FCS까지 더한 1518과는 다릅니다. 1500은 파일 다운로드 전체 크기의 제한도 아닙니다. 큰 응용 데이터는 여러 패킷으로 운반할 수 있습니다. [5]

태그·터널·장비의 jumbo frame 설정 등에서는 전제가 달라집니다. 1518보다 크게 보인다는 사실 하나만으로 손상이나 공격이라고 분류하지 않습니다. 링크 형식, 태그, 수집 위치, 오프로딩과 장비 MTU를 확인한 뒤 기준과 비교합니다.

7. 최소 길이의 배경과 오늘날의 전이중 통신

초기의 공유 매체·반이중 Ethernet에서는 여러 장치가 같은 매체를 사용했습니다. CSMA/CD는 매체의 사용 상태를 확인하면서 송신하고 충돌을 검출하는 방식입니다. 충돌하면 송신을 중단하고 일정 시간 뒤 다시 시도하는 과정이 필요했습니다. 반이중은 한 시점에 송신 또는 수신하는 방식이고, 전이중은 양쪽이 동시에 송수신할 수 있는 방식입니다.

왜 최소 길이가 필요했을까요? 먼 곳의 다른 장치가 송신을 시작해 충돌이 생기면 그 영향이 원래 송신자에게 돌아오는 데 시간이 걸립니다. 송신자가 너무 짧은 프레임을 이미 다 보내 버린 뒤 충돌을 알게 되면 정상적인 충돌 검출·재시도의 시간 조건이 깨질 수 있습니다. 여기서 네트워크의 지름은 같은 공유 LAN에서 가장 멀리 떨어진 두 장치 사이의 거리를 뜻합니다. 이 거리의 전파 지연과 충돌이 돌아오는 시간, 송신 시간의 관계가 중요했던 것입니다.

비트 시간은 한 비트를 전송하는 데 드는 시간입니다. 가상의 단순 계산으로 10 Mb/s에서 1비트는 1 ÷ 10,000,000초 = 0.1마이크로초이고, 64바이트는 64 × 8 = 512비트이므로 512비트의 전송 시간은 51.2마이크로초입니다. 이 계산만으로 케이블의 실제 허용 길이를 정할 수는 없습니다. 실제 반이중 규칙에는 매체·장비 지연과 속도별 조건이 포함됩니다.

정상 충돌 검출 시간 범위를 벗어난 late collision은 케이블·거리·duplex 불일치 등의 문제를 조사할 단서입니다. 이를 곧바로 공격으로 보지 않습니다. 또 링크 계층에서 해결되지 않은 손실을 반드시 IP가 재전송한다고 설명해서도 안 됩니다. IP 자체는 TCP와 같은 신뢰성 있는 재전송을 제공하지 않으며, 복구는 TCP나 응용 프로토콜의 기능과 조건에 따라 달라집니다.

‘기가비트 이상은 모두 전이중만 가능’이라는 일반화 보완

오늘날 일반적인 스위치 기반 전이중 링크에서는 공유 매체의 CSMA/CD 충돌을 전제로 운영하지 않습니다. 다만 Gigabit Ethernet의 표준 역사까지 모두 전이중만 있었다고 하면 부정확합니다. Cisco 공식 설명도 IEEE 802.3z의 반이중 지원과 자사 장비의 전이중 지원을 구분합니다. 현대 장비의 실제 지원 속도·duplex와 포트 상태는 모델·구성 문서로 확인해야 합니다. 충돌이 없어진 구성에서도 기본 프레임 길이 규칙은 남습니다. [6]

8. FCS가 안 보이는 것과 오류가 없다는 것은 다르다

FCS는 Frame Check Sequence의 약자이며 Ethernet에서는 CRC 계산을 이용한 4바이트 오류 검출 값을 담습니다. 수신 측은 계산 결과와 비교해 프레임 손상 여부를 검사할 수 있습니다. 하지만 CRC는 발신자 인증이나 악성 여부 판정 기능이 아닙니다. CRC가 맞는 프레임에도 악성 통신이 실릴 수 있습니다.

일반적인 NIC와 드라이버는 FCS를 분석 프로그램에 전달하지 않는 경우가 많습니다. 따라서 FCS를 제외한 캡처에서 최소 프레임이 64 - 4 = 60바이트로 보일 수 있습니다. 최대 1500바이트 데이터를 담은 태그 없는 프레임도 1518 - 4 = 1514바이트로 보일 수 있습니다. 이것은 원래 프레임 규칙을 위반했다는 뜻이 아닙니다. [4]

반대로 일부 환경은 FCS를 제공할 수 있습니다. ‘tcpdump에는 FCS가 절대로 들어오지 않는다’고 일반화하지 않습니다. 캡처 형식·인터페이스·드라이버와 실제 바이트 정보를 확인해야 합니다. 하드웨어가 손상 프레임을 버려 PCAP에 남지 않았을 수도 있으므로, 캡처에서 FCS 오류가 안 보인다는 사실만으로 회선에 오류가 전혀 없었다고 결론 내리지 않습니다.

스위치 포트의 CRC·FCS 오류와 드롭 카운터, NIC 상태와 캡처 손실 기록을 함께 보세요. Ethernet FCS와 IP·TCP 체크섬은 서로 다른 계층의 검사입니다. 어느 값이 어떤 데이터에 대해 계산되었는지 구분해야 오류 원인을 제대로 좁힐 수 있습니다.

9. Wireshark와 tcpdump에서 같은 헤더를 확인하기

Wireshark에서 Ethernet II 항목을 펼치면 Destination·Source·Type을 확인할 수 있습니다. 실제 헤더의 순서는 목적지 MAC부터입니다. 화면의 요약 줄에 출발지부터 보이는 형식과 바이트 배치 순서를 혼동하지 마세요.

다음은 문서용 MAC 주소 범위를 사용해 새로 구성한 헤더의 앞부분입니다. 전체 프레임이나 실제 덤프 출력이 아닙니다. 태그 없는 Ethernet II이고 EtherType 뒤에서 IPv4가 시작한다고 가정합니다. 문서용 MAC 주소 사용은 RFC 9542도 참고했습니다. [7]

00 00 5e 00 53 20  00 00 5e 00 53 10  08 00  45 00 ...

프레임 기준 오프셋
0~5   목적지 00:00:5e:00:53:20
6~11  출발지 00:00:5e:00:53:10
12~13 EtherType 0x0800
14    IPv4 첫 바이트

오프셋은 0부터 셉니다. 0~13이 기본 헤더이므로 그 다음 위치 14에서 IP가 시작합니다. IP 첫 바이트가 45라면 버전 4와 IHL 5를 읽을 수 있지만, 이 한 값만 배열에서 검색해 헤더 경계를 정해서는 안 됩니다.

실제 파일이 준비되었다면 아래 명령으로 링크 정보를 확인할 수 있습니다. 예시 파일명이며 이번 노트에서 실행한 결과는 아닙니다. [8]

tcpdump -nn -e -r sample.pcap -c 1
tcpdump -nn -r sample.pcap -c 1 -xx
tcpdump -nn -r sample.pcap -c 1 -XX
wireshark sample.pcap &
옵션과 읽는 기준점
표현의미주의할 점
-r sample.pcap저장 파일을 읽음라이브 수집 명령과 구분합니다.
-nn주소·포트 이름 변환을 하지 않음실제 숫자와 표시 이름을 구별하기 좋습니다.
-c 1처리 패킷을 하나로 제한전체 활동을 검증한 표본은 아닙니다.
-e링크 계층 정보를 해석해 출력원시 바이트 덤프 옵션과 다릅니다.
-x / -X링크 헤더를 제외한 16진수 / 16진수와 ASCII그 출력의 0은 프레임의 0과 다를 수 있습니다.
-xx / -XX링크 헤더도 포함한 16진수 / 16진수와 ASCIIEthernet이면 목적지 MAC부터 대조합니다. 다른 링크 형식은 별도 확인합니다.
wireshark 파일명 &파일을 GUI로 열고 셸에서 백그라운드 실행&는 여기서 셸 표기이며 Wireshark 수집 옵션이 아닙니다.

같은 패킷을 비교할 때는 파일·패킷 번호·시각·길이와 링크 유형을 맞춥니다. -xx 출력에 MAC이 보인다는 이유만으로 모든 물리 전송 정보나 FCS까지 보장되는 것은 아닙니다. 도구에 전달된 자료의 범위 안에서 링크 헤더를 보여 주는 옵션입니다.

10. VLAN 태그는 어디에 무엇을 추가할까

VLAN은 링크 계층의 논리적 네트워크 구분입니다. 802.1Q 태그는 프레임이 어느 VLAN과 관련되는지 등을 표현하는 방법입니다. 모든 링크에서 모든 프레임이 태그를 달고 보이는 것은 아니므로, 태그의 부재와 VLAN의 부재를 같은 사실로 취급하지 않습니다.

일반적인 802.1Q 고객 태그는 출발지 MAC과 기존 Type/Length 사이에 4바이트를 추가합니다. 앞의 2바이트는 태그를 식별하는 TPID이고 흔한 값이 0x8100입니다. 다음 2바이트 TCI에는 우선순위 등의 정보와 VLAN ID가 들어갑니다. 태그 뒤에는 다시 안쪽 Type/Length가 있어 실제 상위 프로토콜을 가리킵니다. [9]

TCI 16비트의 기본 구성
필드폭역할
PCP3비트Priority Code Point. 우선순위 분류에 사용합니다.
DEI1비트Drop Eligible Indicator. 혼잡 시 폐기 적격성 등의 처리와 관련됩니다.
VID12비트VLAN Identifier. VLAN 식별값을 담습니다.

합계는 3 + 1 + 12 = 16비트 = 2바이트입니다. 12비트에는 2¹² = 4096개 조합이 있지만 예약값과 특별 용도가 있으므로 4096개가 모두 일반 VLAN 번호로 사용 가능하다는 뜻은 아닙니다. 오래된 화면의 CFI는 역사적 명칭이며, 현재 문맥에서는 DEI라는 정의와 구별해서 읽습니다. [10]

자체 구성 예시에서 TCI가 00 2a이면 상위 PCP·DEI는 0이고, VID는 0x02A = 2 × 16 + 10 = 42입니다. 앞선 예제의 두 MAC 다음이 81 00 00 2a 08 00 45 ...가 되었다면, 12~13은 TPID, 14~15는 TCI, 16~17은 안쪽 EtherType, IPv4는 18에서 시작합니다. 태그 없는 경우보다 18 - 14 = 4바이트 뒤입니다.

1500바이트 데이터를 운반하는 단일 태그 예시라면 헤더는 14 + 4 = 18바이트이고 FCS 포함 길이는 18 + 1500 + 4 = 1522바이트입니다. FCS를 제공하지 않는 캡처에서는 1518바이트일 수 있습니다. 여기서 태그가 MTU 안의 IP 공간을 항상 4바이트 줄인다고 단정하지 않습니다. 태그를 지원하는 링크의 프레임 한도와 IP MTU를 구분합니다. [5] [9]

802.1Q 태깅과 VTP는 다른 개념

원문에서 802.1Q를 VTP와 같은 이름으로 부르는 부분은 수정해야 합니다. 802.1Q 태그는 프레임에 VLAN 관련 정보를 담는 구조이고, VTP는 Cisco의 VLAN Trunking Protocol로 VLAN 구성 정보를 배포·관리하는 별도 프로토콜입니다. 802.1Q 태그가 보였다고 VTP 메시지가 보였다는 뜻은 아닙니다. [11]

11. IDS 앞에서 VLAN 태그를 반드시 제거해야 할까

원문은 처리량과 특수 태그 지원 문제를 줄이기 위해 센서 도달 전에 태그를 제거하라고 권합니다. 특정 수집 장비나 탐지기의 제약에 대응할 선택일 수 있지만, 현재 환경의 보편적 기본값으로 적용해서는 안 됩니다. 지원 문제를 줄이는 효과와 관측 맥락을 잃는 비용을 함께 검토해야 합니다.

가령 서로 분리된 VLAN에서 같은 사설 IP·포트 조합을 쓰는데 센서로 보낼 때 태그만 지웠다고 가정해 보세요. 다른 출처의 통신을 구별할 정보가 사라질 수 있습니다. 센서가 별도 인터페이스·수집 소스 같은 다른 식별 정보로 이를 유지하는지 확인해야 합니다. 같은 주소가 보인다는 이유로 같은 단말이나 같은 연결로 합쳐서는 안 됩니다.

현재 Suricata 8.0.1 공식 문서는 VLAN 추적과 관련한 vlan.use-for-tracking 설정 및 eBPF/XDP 처리 조건을 설명합니다. 이는 VLAN 문맥이 흐름 처리에 쓰일 수 있음을 보여 줍니다. 그렇다고 특정 설정을 모든 환경에 그대로 적용하라는 뜻은 아닙니다. 실제 탐지기 버전·수집 방식·태그 지원·성능·동일 주소 재사용 여부를 확인하고, 필요한 식별 정보를 보존하는 설계를 선택합니다. [12]

반대로 캡처에서 태그가 안 보이는 경우에도 ‘태그를 쓴 적이 없다’고 확정하지 않습니다. VLAN 가상 인터페이스, NIC·드라이버 처리, 스위치 미러링 방식에 따라 수집 지점에 전달되는 형태가 달라질 수 있습니다. Wireshark 공식 문서도 VLAN에서 수집해도 태그가 반드시 보이지는 않는다고 설명합니다. [13]

여러 태그를 사용하는 구성도 있을 수 있으므로 0x8100 하나를 무조건 제거한 뒤 14바이트 오프셋으로 읽는 방식은 피합니다. 원본 구조를 해석하고 수집 지점에서 어떤 변환이 있었는지 확인하세요. VLAN 번호의 관측은 논리적 구분의 단서이며, 접근 제어가 안전하게 구현되었거나 다른 VLAN과 절대 통신하지 못한다는 보증은 아닙니다.

12. 링크 계층에서 관측한 사실과 남는 질문

패킷으로 확인 가능한 사실

확보된 링크 형식, MAC 주소와 Type/Length, 실제로 보이는 태그·VID, 데이터 시작 위치와 길이 관계입니다. FCS 포함 여부와 잘림을 함께 기록합니다.

단독으로 확정할 수 없는 부분

실제 사용자·프로그램 신원, 프레임이 최종 응용에 처리되었는지, 태그가 안 보이는 이유, 보이지 않은 회선 오류와 공격 성공입니다. 암호화된 본문의 의미도 링크 헤더만으로 알 수 없습니다.

함께 확인할 자료

스위치 MAC·VLAN·포트 구성, 링크 속도·duplex와 오류·드롭 카운터, 미러링·NIC·드라이버 설정, 센서 VLAN 추적과 수집 손실, 단말·서버·인증 로그입니다.

암호화된 통신에서도 링크 정보는 ‘어디에서 어떤 형태로 관측했는가’를 검증하는 데 도움이 됩니다. 다만 MAC은 현재 링크의 정보이며 암호화된 내용을 풀거나 전체 경로를 증명하지는 않습니다. 필요한 단말·스위치·서버 기록과 연결해야 패킷 분석의 의미가 분명해집니다.

해설: 다른 네트워크로 가는 정상 전달에서 가능한 구조입니다. IP 목적지와 현재 링크의 다음 전달 지점을 구분합니다. MAC 하나로 최종 서버나 사용자를 확정하지 않습니다.

질문 2: 태그 없는 프레임에 상위 데이터 28바이트가 들어갑니다. 최소 길이에 필요한 패딩과 전체 길이는 얼마일까요?

해설: 데이터·패딩 최소는 46바이트이므로 패딩은 18바이트입니다. 헤더 14 + 데이터 28 + 패딩 18 + FCS 4 = 64바이트입니다. FCS가 없는 캡처에는 60바이트로 보일 수 있습니다.

질문 3: Type/Length가 1520입니다. 0x0600보다 작으니 길이라고 하면 될까요?

해설: 일반 길이 범위는 1500 이하이고 Type 범위는 1536 이상입니다. 그 사이 값을 정상적인 길이로 확정하지 않고 형식·손상·해석 기준 등을 검토합니다.

질문 4: -x 출력의 처음과 -xx 출력의 처음을 같은 기준으로 비교하면 될까요?

해설: 링크 헤더 포함 여부가 다릅니다. Ethernet의 -xx는 목적지 MAC부터 대조할 수 있지만, -x는 그 링크 헤더를 제외합니다. 링크 유형과 덤프 기준점을 기록하고 비교해야 합니다.

질문 5: 81 00 00 2a 08 00이 출발지 MAC 뒤에 옵니다. 어디에서 IPv4가 시작할까요?

해설: 단일 802.1Q 태그 예시라면 TPID 0x8100, TCI 0x002a, 안쪽 유형 0x0800입니다. VID는 42이고, IPv4는 프레임 기준 18에서 시작합니다. 이 여섯 바이트를 모두 IP 헤더로 읽지 않습니다.

질문 6: 태그가 있는 최대 프레임이 1522바이트라면 IP MTU도 1522일까요?

해설: 이 예시는 헤더 18 + 데이터 1500 + FCS 4입니다. IP 공간과 링크 전체 길이는 다릅니다. 장비의 MTU 표기와 태그 포함 기준도 확인합니다.

질문 7: IDS 처리량을 위해 태그를 항상 지워야 할까요?

해설: 지원·성능과 문맥 보존을 함께 봅니다. 같은 주소를 다른 VLAN에서 쓰면 태그 제거가 통신 구별에 영향을 줄 수 있습니다. 센서의 VLAN 추적과 별도 수집 소스 식별을 확인한 뒤 설계해야 합니다.

질문 8: CRC 오류가 PCAP에 없으면 회선에 손상이 없었다고 해도 될까요?

해설: FCS가 제공되지 않았거나 하드웨어에서 먼저 버렸을 수 있습니다. 캡처에 없는 사실을 오류 부재로 바꾸지 않고 포트·NIC 카운터와 수집 조건을 대조합니다. 정상 CRC도 악성 여부의 판정은 아닙니다.
