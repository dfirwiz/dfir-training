1. 경고 이름만으로 순위를 정할 수 있을까

Ping Sweep, SYN 스캔, ICMP 터널이라는 세 가지 경고가 있습니다. 터널은 위험하고 Ping Sweep은 가볍다고 바로 순위를 매겨도 될까요? 경고 이름은 조사할 방향을 알려 주지만, 실제 위험도를 결정할 증거는 더 필요합니다. 자산의 중요도, 정상 업무 여부, 전후 활동과 관측 범위를 함께 봐야 합니다.

이번에는 경고에서 시작해 패킷의 주소·시간·필드·데이터를 확인하고, 가설을 검증하는 과정을 배웁니다. 아래 출력과 주소는 이해를 돕기 위해 새로 구성한 가상 예시입니다. 원본 실습 PCAP을 실행한 결과가 아닙니다.

2. 조사를 진행하는 네 단계

경고가 발생했을 때 ‘공격 같다’는 느낌을 바로 결론으로 적으면, 나중에 새로운 증거가 나와도 처음 판단에 끌려가기 쉽습니다. 그래서 이번 회차에서는 관찰과 분석 → 가설 → 검증과 종합 → 보고를 구분해서 연습합니다. 네 단계를 반드시 한 번씩만 거치는 것은 아닙니다. 가설이 맞지 않으면 다시 패킷을 읽고 다른 설명을 검토합니다.

Ping Sweep 의심 사례를 조사하는 사고 과정
단계무엇을 하는가기록 예시
관찰과 분석패킷을 주소·시간·종류·필드로 나누어 읽습니다.짧은 간격으로 여러 목적지에 Echo Request가 관측되었다.
가설관측을 설명할 가능한 원인을 세웁니다.자동화된 호스트 탐색일 수 있다. 승인된 자산 점검일 가능성도 있다.
검증과 종합예상되는 다른 증거를 찾고 반대 가능성도 확인합니다.점검 일정과 실행 프로세스를 대조하고, 응답 경로와 수집 필터를 확인한다.
보고확인한 사실, 판단의 근거, 남은 의문을 나누어 적습니다.자동 탐색 정황이 있다. 실행 주체와 승인 여부는 아직 확인되지 않았다.

특히 ‘내 가설이 맞다면 무엇이 더 보여야 할까’를 생각하는 것이 도움이 됩니다. 승인된 스캐너라고 생각한다면 자산 목록과 점검 일정이 맞아야 하고, 특정 프로그램이 만든 통신이라고 생각한다면 실행 기록이나 재현 조건이 맞는지 확인해야 합니다.

3. Ping Sweep에서 볼 것은 주소와 시간

먼저 ping을 ‘상대에게 보낸 확인 요청에 응답이 오는지 살펴보는 진단 도구’라고 이해하면 됩니다. IPv4의 ICMP Echo Request는 요청이고, Echo Reply는 그 요청에 대한 응답입니다. ICMP는 TCP처럼 연결을 맺는 프로토콜은 아니지만, 주소와 식별 정보로 관련 요청·응답을 묶어 조사할 수 있습니다.

ICMP Echo Request는 흔히 ping에 사용됩니다. 하나의 호스트가 여러 목적지 주소를 빠르게 바꿔 가며 요청을 보내면, 살아 있는 장치를 찾으려는 자동화된 탐색을 가설로 세울 수 있습니다.

# 가상 출력: 문서용 주소와 임의의 시각
10:00:00.000100 IP 192.0.2.10 > 198.51.100.11: ICMP echo request, id 4200, seq 1, length 64
10:00:00.000600 IP 192.0.2.10 > 198.51.100.12: ICMP echo request, id 4200, seq 1, length 64
10:00:00.001100 IP 192.0.2.10 > 198.51.100.13: ICMP echo request, id 4200, seq 1, length 64

출력을 왼쪽부터 읽어 보겠습니다. 10:00:00.000100은 패킷 시각이고, 192.0.2.10은 출발지, 화살표 오른쪽의 198.51.100.11은 목적지입니다. 다음 줄에서는 목적지가 .12로 바뀌었습니다. 시각의 차이는 0.000500초, 즉 0.5밀리초입니다. 사람이 목적지를 매번 바꾸어 입력했다고 보기보다는 자동화된 처리를 먼저 검토할 만한 패턴입니다.

ICMP Echo에서 ID와 순번을 읽는 방법 [5]
정보기본 의미분석 시 주의
Identifier 또는 ID요청과 응답을 대응시키는 데 사용하는 식별 값같은 값이라고 반드시 같은 프로그램이나 사용자라는 뜻은 아닙니다.
Sequence Number 또는 seq여러 요청과 각각의 응답을 구분하는 데 사용하는 순번구현에 따라 사용 방식이 다릅니다. 반드시 증가해야 한다고 단정하지 않습니다.
Echo의 Data진단을 위해 요청에 실어 보낸 데이터표준 Echo Reply에서는 요청의 데이터를 돌려줍니다. 내용·길이·대응 관계를 함께 봅니다.

여기서는 목적지가 바뀌고, 요청 간격이 짧고, ID와 sequence가 반복됩니다. 이 조합은 자동화된 생성 가능성을 뒷받침합니다. 그러나 특정 도구나 공격자의 숙련도를 확정하지는 못합니다. 여러 대상을 한 번씩 검사하는 프로그램이라면 sequence가 같은 것도 구현에 따라 설명될 수 있습니다.

관측과 판단 분리

‘캡처에 Echo Reply가 없다’는 관측입니다. ‘대상이 꺼져 있다’, ‘모두 차단됐다’, ‘위험하지 않다’는 별도 검증이 필요한 판단입니다. 비대칭 경로, 필터, 캡처 누락과 ICMP 응답 정책을 확인하세요.

4. tcpdump로 가설에 필요한 정보 확인

전체 흐름을 볼 때는 요약 출력을 먼저 보고, 의미 있는 패킷을 골라 바이트와 문자열을 살펴보면 효율적입니다. 처음부터 모든 데이터를 16진수로 출력하면 주소 변화나 요청 간격 같은 패턴을 놓치기 쉽습니다.

분석용 PCAP이 준비되었다면 다음처럼 특정 주소의 ICMP만 읽을 수 있습니다. sample.pcap은 예시 파일명이며, 실제 파일과 조사 대상 주소로 바꿔 사용합니다.

tcpdump -nn -tttt -r sample.pcap 'icmp and host 192.0.2.10'
tcpdump -nn -r sample.pcap -X -c 3 'icmp and host 192.0.2.10'
이번에 사용하는 옵션과 필터 [1]
표현의미
-r sample.pcap라이브 캡처 대신 저장된 파일을 읽습니다.
-nn주소와 포트 번호를 이름으로 변환하지 않습니다.
-tttt날짜를 포함한 시각을 표시합니다. 출력 시간대도 확인하세요.
-X링크 계층 헤더를 제외한 데이터를 16진수와 ASCII로 표시합니다.
-c 3필터에 일치하는 패킷 세 개를 처리한 뒤 종료합니다.
icmp and host …해당 IPv4 주소가 출발지 또는 목적지인 ICMP 패킷을 선택합니다.

첫 명령은 icmp와 host 조건을 모두 만족하는 패킷을 선택합니다. host는 출발지와 목적지 양쪽에 적용되므로 해당 주소가 요청을 보내는 경우와 응답을 받는 경우를 함께 살펴볼 수 있습니다. 두 번째 명령은 그중 세 개만 자세히 출력하는 예시입니다. 세 개를 봤다는 이유로 전체 활동을 판단하지는 않습니다. 필요한 시간 구간과 관련 패킷으로 범위를 넓혀야 합니다.

ASCII 영역의 점은 사람이 읽을 수 있는 문자로 표시하기 어려운 바이트일 수 있습니다. 점이 많다고 그 데이터가 암호화되었다고 확정할 수는 없습니다. 바이트의 위치와 프로토콜 구조를 함께 확인합니다.

명령어 설명 바로잡기

-x는 16진수, -X는 16진수와 ASCII를 함께 보여 줍니다. -t는 시각을 숨기고, -n은 호스트 주소의 이름 변환을 막습니다. 시간 간격을 조사할 때 시각을 숨기지 않는 편이 좋습니다. IPv6 ICMP를 조사할 때는 이번의 icmp 필터를 그대로 재사용하지 말고 icmp6 등 분석 대상에 맞는 필터를 선택합니다. [1]

5. 도구 이름은 검증할 가설

운영체제의 ping, 관리용 스크립트, 보안 점검 프로그램은 서로 다른 필드와 간격을 사용할 수 있습니다. 알려진 기본 출력과 비슷한 것은 단서가 될 수 있지만, 기본 출력을 흉내 내거나 옵션을 바꾸는 것도 가능합니다. ‘내가 아는 모양’과 ‘확인된 생성 도구’를 구분해야 합니다.

‘이 패턴은 Nmap 같다’고 생각했다면, 버전·운영체제·권한·옵션·같은 링크인지 여부를 맞춰 비교해야 합니다. 한 번의 기본 설정 실험과 다르다는 이유로 그 도구를 배제하면 안 됩니다.

Nmap 공식 문서에는 호스트 탐색의 -sn이 예전에 -sP로 불렸다고 설명되어 있습니다. 같은 이더넷 링크에서는 권한과 옵션에 따라 ICMP 대신 ARP 탐색이 이루어질 수 있습니다. 또한 페이로드를 바꾸는 옵션이 있으므로, 길이 하나만으로 생성 도구를 단정해서도 안 됩니다. [2] [3]

현대적 해석

기본 도구를 사용한다고 위협 수준이 낮은 것은 아닙니다. LOTL은 시스템에 원래 있는 도구와 기능을 악용해 정상 활동 속에 섞이는 방식입니다. 도구의 희귀성보다 실행 주체, 권한, 대상, 목적과 후속 활동을 봅니다. ACSC 등의 공동 지침도 이런 활동의 탐지를 위해 정상 기준과 로그 분석을 강조합니다. [4]

6. SYN 스캔은 연결 시도의 패턴으로 읽기

TCP의 SYN은 연결 설정을 시작할 때 사용합니다. 같은 목적지의 여러 포트에 SYN을 보내면 어떤 서비스가 응답하는지 확인하려는 활동일 수 있습니다. 승인된 취약점 점검과 침해 후 탐색 모두 비슷한 형태를 만들 수 있습니다.

정상적인 TCP 연결 설정에서는 시작하는 쪽의 SYN, 상대의 SYN-ACK, 시작한 쪽의 ACK가 이어지는 기본 흐름을 배웁니다. 포트 탐색에서는 이 연결을 끝까지 만들지 않고 상대의 반응만 관찰하는 경우도 있습니다. 그러므로 ‘SYN이 보였다’는 사실만으로 응용 서비스에 로그인하거나 명령을 실행했다고 설명할 수는 없습니다. [6]

호스트 탐색과 포트 탐색도 구별합니다. 여러 IP에 확인 요청을 보내는 활동은 어느 장치가 반응하는지 알아보려는 것일 수 있고, 한 IP의 여러 포트에 SYN을 보내는 활동은 어떤 서비스가 반응하는지 알아보려는 것일 수 있습니다. 어느 쪽이든 승인된 업무인지와 후속 활동을 확인해야 합니다.

출발지 포트나 sequence가 반복되면 조사할 특징이 되지만, 그 사실 자체가 스푸핑이나 특정 도구를 증명하지는 않습니다. 먼저 출발지가 등록된 스캐너인지 확인하고, SYN-ACK·RST·ICMP 오류 등 응답과 후속 접속을 찾아보세요.

응답에 대한 신중한 해석
관측가능한 해석추가 확인
SYN에 SYN-ACK응답 주체가 연결을 받아들일 준비가 되었을 수 있음목적지 서버인지 중간 장비인지, 연결 이후 활동
SYN에 RST닫힌 포트 또는 장비의 거부 응답 가능성응답 생성 위치와 정책
응답이 캡처에 없음차단, 무응답, 경로 차이, 수집 누락 등방화벽 기록, 양방향 수집 여부

7. ICMP 안에서 다른 통신의 흔적 찾기

터널은 한 통신을 다른 통신 안에 담아 운반하는 방식을 말합니다. 일반적인 ping의 데이터 영역을 단순한 진단 데이터 대신 다른 통신의 운반 공간으로 이용한다면, 바깥에서는 ICMP Echo처럼 보이면서 안에서는 다른 정보가 오갈 수 있습니다. 그래서 ICMP의 종류만 확인하고 지나가면 중요한 차이를 놓칠 수 있습니다.

여기서는 먼저 정상적인 Echo 요청과 응답의 대응 관계를 봅니다. 주소가 뒤바뀌는지, ID와 순번이 대응되는지, 요청 데이터가 응답에 돌아오는지 확인합니다. 특정한 유니캐스트 진단 사례에서 요청보다 응답이 훨씬 많거나 데이터가 다르게 이어진다면 추가 조사할 단서입니다. [5]

그러나 응답 개수만으로 터널이라고 결론 내리면 안 됩니다. 같은 패킷을 여러 수집 지점에서 중복으로 담았거나, 요청 일부가 누락되었거나, 여러 응답 주체가 있을 가능성도 먼저 확인해야 합니다. ‘이상해 보인다’는 관찰을 설명할 다른 원인이 없는지 살펴보는 과정입니다.

ICMP Echo의 데이터 영역에서 일반적인 진단 패턴과 다른 내용이 보이고, 요청·응답 개수나 크기도 예상과 다르다면 더 자세히 살펴볼 이유가 있습니다. 특히 SSH-2.0-... 같은 식별 문자열이 ICMP 데이터에 반복적으로 포함된다면, 다른 통신을 담아 전달하는 터널 가설을 검토할 수 있습니다.

SSH 식별 문자열을 발견했다는 것은 SSH 통신의 시작 부분이 보이는 정황일 수 있습니다. 그 뒤의 명령과 파일까지 모두 읽을 수 있다는 뜻은 아닙니다. 내부 통신이 암호화되어 있어도 바깥쪽 ICMP의 양·방향·시점과 관측 가능한 구조는 여전히 조사할 수 있습니다.

문자열 하나만으로 악성 터널이나 데이터 유출을 확정하지는 않습니다. 정상 진단 도구도 임의의 데이터를 넣을 수 있습니다. 페이로드가 여러 패킷에서 어떻게 이어지는지, 해당 호스트의 프로세스와 연결 기록이 맞는지, 허용된 사용인지 대조해야 합니다.

8. 경고 시각 이전으로 조사 범위 넓히기

내부 서버가 외부 주소를 스캔했다는 경고가 처음 발생했습니다. 그것이 사건의 시작일까요? 관리자가 진단을 시작했을 수도 있고, 이미 침해된 서버가 다른 대상을 찾는 단계일 수도 있습니다. 경고 하나로 어느 쪽인지 결정할 수 없습니다.

여기서 중요한 것은 경고 발생 시각과 실제 사건 시작 시각이 같다고 가정하지 않는 것입니다. 처음 발견한 경고보다 앞에 관련 통신이 있었을 수 있습니다. 반대로 공격의 전형적인 단계를 알고 있다는 이유로, 관측하지 않은 초기 침해나 정보 유출을 연표에 넣어서도 안 됩니다.

가상 조사 연표에서 사실과 미확인을 나누는 예시
시점확보한 자료기록할 수 있는 내용
경고 이전아직 자료 없음최초 침해 여부와 시작 시각은 미확인
02:00인증 로그해당 계정의 로그인 기록이 있음. 실제 사용자와 정당성은 추가 확인
02:05네트워크 캡처여러 주소·포트로 접속 시도가 관측됨
02:06IDS 경고탐지 조건에 일치해 경고가 발생함

자산 식별과 시간대를 맞춘 뒤 이전의 로그인, 프로세스 실행, 외부 연결, 다른 내부 장비와의 접속을 연결해 보세요. 의심스러운 순서가 보이더라도 실제 증거가 없는 단계를 사건 연표에 사실처럼 채워 넣으면 안 됩니다.

조사 메모 예시

‘여러 내부 주소로 짧은 간격의 ICMP Echo Request가 관측되었다. 자동 탐색 가능성이 있다. 현재 캡처에서 응답은 확인되지 않았으며, 승인된 점검 여부와 응답 경로를 추가 확인한다.’

9. 세 경고의 우선순위를 다시 판단하기

이제 처음의 세 경고로 돌아가 보겠습니다. 터널이라는 단어가 항상 최우선이고 Ping Sweep은 항상 후순위인 것이 아닙니다. 예를 들어 중요 서버에서 갑자기 시작된 미승인 탐색은 빠른 확인이 필요할 수 있습니다. 반면 등록된 점검 장비가 승인된 시간에 수행한 스캔은 정상 작업으로 설명될 수 있습니다.

다음 질문을 함께 검토하면 경고 이름에만 끌려가지 않는 데 도움이 됩니다.

  • 어떤 자산인가? 중요 시스템이나 민감한 데이터에 접근할 수 있는 장치인가?
  • 승인된 활동인가? 점검 일정·담당자·스캐너 목록과 맞는가?
  • 어디까지 진행됐는가? 요청만 있었는지, 응답과 연결 이후 활동까지 있는가?
  • 다른 증거가 이어지는가? 의심스러운 로그인·프로세스·외부 전송이 같은 시간대에 있는가?
  • 관측이 충분한가? 양방향 트래픽과 필요한 시간 구간을 확보했는가?

우선순위 판단에는 근거와 불확실성을 함께 적습니다. ‘터널 경고라서 높음’보다 ‘중요 서버에서 승인되지 않은 프로세스와 연결되는 ICMP 데이터 교환이 관측되어 우선 확인’처럼 설명하는 편이 다음 대응으로 이어집니다.

10. 이번 회차의 증거 구분

패킷으로 확인

목적지 변화, 시간 간격, 보이는 ID·sequence·크기, 관측된 응답, 캡처된 페이로드.

패킷만으로 확정 불가

공격자 신원·실력, 특정 도구의 단정, 캡처 밖 응답, 침해나 유출의 성공 여부.

함께 확인할 로그

스캔 승인·자산 목록, EDR 프로세스 기록, 방화벽 허용·차단 기록, 인증과 서버 로그.

11. 복습과 조사 메모

질문: 응답 없는 SYN 스캔은 무해하다고 종결해도 될까요?

해설: 아직 어렵습니다. 우선 캡처에 응답이 없다는 사실과 실제 응답이 없었다는 판단을 구별합니다. 양방향 수집 여부, 방화벽 기록, 승인된 점검인지, 다른 성공한 접속이나 관련 행위가 있는지를 확인해야 합니다.

질문: 기본 ping과 비슷한 페이로드라면 공격자의 수준이 낮을까요?

해설: 그렇게 판단할 수 없습니다. 숙련된 공격자도 기본 도구를 사용합니다. 도구가 익숙한지보다 실행 주체·권한·대상·목적·후속 행동을 봅니다. 페이로드 하나는 이런 맥락을 대신하지 못합니다.

질문: 실험한 도구와 필드가 다르면 그 도구를 배제해도 될까요?

해설: ‘실험한 버전과 옵션에서는 동일한 패턴이 재현되지 않았다’고 조건을 명시합니다. 다른 버전·옵션·운영체제·권한에 따른 가능성을 검토하고 확정적인 배제를 피합니다.

다음 문장은 관찰과 가설, 다음 확인 사항을 구별한 보고 예시입니다.

여러 목적지로 0.5밀리초 간격의 ICMP Echo Request가 관측되었다. 자동화된 탐색 가능성이 있다. 현재 캡처에서 대응 응답은 확인되지 않았으며, 실행 프로세스와 승인 여부, 수집 경로를 추가 확인한다.
