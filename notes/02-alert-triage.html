Ping Sweep, SYN 스캔, ICMP 터널을 비교하며 관찰·가설·검증의 순서를 익힙니다.

이번 강의는 본 교재 인쇄 12~21쪽에 해당합니다. 1강에서 배운 ‘경고는 조사의 출발점’이라는 원칙을 Ping Sweep, SYN 스캔, ICMP 터널 의심 사례에 적용해 보겠습니다. 패킷의 주소·시각·필드·데이터를 읽고, 가설을 검증한 뒤 우선순위와 조사 메모로 연결하는 것이 목표입니다.

아래 주소·시각·출력·관측표는 독립적으로 구성한 가상 학습 예시입니다. 원문의 실습 파일을 이번 작업에서 tcpdump나 Wireshark로 실행한 결과가 아닙니다. 본 교재와 기존 해설·실습 검토 기록을 대조했으며, 기존 워크북·첫째 날 캡처 검증과 이번 예제 검산을 구별합니다. 실제 파일을 읽을 때는 파일명·관측 위치·시간대·도구 버전과 설정을 함께 남겨야 합니다.

1. 세 경고가 동시에 뜨면 무엇부터 볼까요?

당직 중에 다음 세 경고를 받았다고 생각해 볼게요.

여러 주소를 향한 Ping Sweep 의심, 여러 포트를 향한 SYN 스캔 의심, ICMP 터널 의심.

‘터널’은 위험해 보이고 ‘ping’은 평범해 보이죠. 그러면 터널부터 처리하고 ping은 뒤로 미루면 될까요?

아직 그렇게 정하기는 어렵습니다. 경고 이름은 책의 제목과 비슷합니다. 어떤 내용일지 짐작하는 데는 도움이 되지만, 제목만으로 책 속에서 실제로 벌어진 일을 모두 설명할 수는 없으니까요.

예를 들어 Ping Sweep이 중요한 내부 서버에서 갑자기 시작됐다면, 승인된 자산 점검인지 아니면 다른 장비를 찾는 미승인 활동인지 빨리 확인할 필요가 있습니다. 반대로 터널 의심 경고가 승인된 시험 환경에서 발생했다면 담당자가 설명할 수 있는 정상 실험일 수도 있죠.

용어를 먼저 가볍게 연결해 보겠습니다. Ping Sweep은 여러 주소를 대상으로 응답 여부를 확인하는 탐색 활동을 가리킵니다. 포트는 TCP나 UDP 통신에서 서비스와 통신 끝점을 구분하는 번호입니다. SYN 스캔은 TCP 연결을 시작하는 신호를 여러 포트에 보내 반응을 살펴보는 탐색입니다. 터널은 다른 통신을 어떤 통신의 데이터 안에 담아 운반하는 방식입니다.

세 경고의 조사 출발점
경고먼저 떠올릴 수 있는 활동실제로 확인해야 할 것
Ping Sweep여러 주소 중 응답하는 장치 찾기출발지의 역할, 대상 범위, 시간 간격, 응답과 승인 여부
SYN 스캔한 장치의 여러 서비스 탐색목적지 포트 변화, 응답 종류, 후속 연결과 실행 주체
ICMP 터널 의심진단 메시지 안에서 다른 데이터 운반요청·응답 대응, 데이터 구조, 프로세스와 허용된 사용 여부

세 경고에 공통으로 던질 질문은 같습니다. 누가 누구에게 무엇을 보냈는지, 자동화 정황은 있는지, 응답은 어떻게 이어졌는지, 어느 사실까지 확인했는지, 지금 무엇을 더 조사해야 하는지입니다.

출발지 주소를 찾았다고 곧바로 ‘공격자’를 알아낸 것은 아닙니다. 지금은 관측한 송신 주소와 수신 주소라고 적는 편이 정확합니다. 실제 사용자·프로세스와 의도는 다른 근거를 연결해서 확인해야 합니다.

2. ping의 요청과 응답은 어떻게 짝을 찾을까요?

먼저 한 대에 보내는 ping부터 보겠습니다. ping은 상대에게 확인 요청을 보내고 돌아오는 응답을 살펴보는 진단 도구입니다. IPv4에서는 흔히 ICMP Echo Request라는 요청과 Echo Reply라는 응답을 사용합니다. ICMP는 통신의 오류나 진단 정보를 전달하는 프로토콜이며 TCP처럼 연결을 맺는 방식은 아닙니다.

사무실에서 “김 대리님, 들리세요? 확인 번호 17번입니다”라고 부르고, 상대가 “17번, 들립니다”라고 답한다고 생각해 보세요. 여러 확인 요청이 오가면 어느 답이 어느 질문에 대한 것인지 구별할 표시가 필요하겠죠.

ICMP Echo에도 Identifier(ID)와 Sequence Number(seq)가 있습니다. ID는 관련 요청과 응답을 연결하는 식별 값이고, seq는 그 안에서 개별 요청을 구분하는 데 사용할 수 있는 순번입니다. 표준 Echo 응답은 요청의 ID·순번과 데이터를 돌려줍니다. [1]

ICMP Echo 요청과 응답의 대응
정보가상 요청대응하는 가상 응답무엇을 읽을까요?
주소 방향192.0.2.10 → 198.51.100.11198.51.100.11 → 192.0.2.10요청을 받은 쪽에서 보낸 쪽으로 돌아오는가?
Echo 종류RequestReply요청과 응답의 역할이 맞는가?
ID42004200연결할 수 있는 식별 값인가?
seq11같은 요청에 대응하는 순번인가?
Datacheck-01check-01요청 데이터가 그대로 돌아오는가?

비유와 실제 동작이 달라지는 점도 있습니다. ICMP의 ID는 전 세계에서 유일한 접수 번호가 아닙니다. 서로 다른 프로그램이 같은 값을 사용할 수 있고, 값을 다시 사용할 수도 있습니다. 주소 변환 장비가 값을 바꾸는 환경도 있을 수 있습니다. 따라서 주소·방향·시각·데이터까지 함께 읽어야 합니다.

순번이 늘어나는 ping 출력을 자주 보겠지만, 모든 구현이 모든 상황에서 같은 방식으로 순번을 증가시켜야 한다고 외우면 안 됩니다. 한 대상에 연속으로 보내는 경우와 여러 대상에 한 번씩 보내는 경우도 다릅니다. [1]

이 강의에서 ICMP ‘대화’를 묶어 본다는 말은, TCP와 같은 연결이 만들어졌다는 뜻이 아닙니다. 서로 관련된 요청과 응답을 분석자가 함께 살펴본다는 뜻입니다.

3. Ping Sweep의 주소와 시각을 함께 읽어 봅시다

이제 한 대상이 아니라 여러 주소로 보낸 경우입니다. 다음은 직접 만든 요약 출력 예시입니다.

# 가상 출력: 문서용 주소와 임의의 시각
10:00:00.000100 IP 192.0.2.10 > 198.51.100.11: ICMP echo request, id 4200, seq 1, length 64
10:00:00.000600 IP 192.0.2.10 > 198.51.100.12: ICMP echo request, id 4200, seq 1, length 64
10:00:00.001100 IP 192.0.2.10 > 198.51.100.13: ICMP echo request, id 4200, seq 1, length 64

왼쪽의 시각부터 읽어 볼까요? 세 줄의 출발지는 같고 목적지는 .11, .12, .13으로 바뀝니다. 세 요청의 ID와 seq, 표시 길이는 같습니다.

첫 요청과 두 번째 요청의 시각 차이는 다음과 같습니다.

0.000600초 − 0.000100초 = 0.000500초
0.000500초 × 1000 = 0.5밀리초
첫 요청부터 세 번째 요청까지: 0.001100 − 0.000100 = 0.001000초 = 1밀리초

밀리초(ms)는 1초의 1000분의 1입니다. 사람이 주소를 바꾸어 명령을 세 번 입력하기에는 매우 짧은 간격이죠. 그래서 자동화된 처리를 가설로 검토할 수 있습니다.

그렇다고 짧은 간격 하나만으로 특정 프로그램을 알아낸 것은 아닙니다. 운영체제 도구를 스크립트에서 반복 실행했을 수도 있고, 별도의 점검 프로그램일 수도 있습니다. 캡처 장치의 시계 정밀도와 패킷을 모아서 처리하는 방식도 고려해야 합니다. 정밀한 숫자가 표시된다고 회선에서의 실제 간격을 무조건 그 정확도로 안다는 뜻은 아닙니다.

한 대상에게 반복하는 진단과 여러 대상에게 한 번씩 보내는 탐색은 목적지의 변화에서 차이가 드러납니다. ID와 순번도 함께 보되, 그 값 하나를 ‘정상·공격’ 판정기로 사용하지는 마세요.

그런데 응답은 어떻게 찾을까요? 출발지만 고정해서 보면 돌아오는 방향을 놓칠 수 있습니다. 같은 주소가 출발지 또는 목적지인 기록을 함께 살펴보고, 앞 절에서 배운 ID·순번·데이터와 시간 관계로 대응시켜야 합니다.

여기서 Echo Reply가 안 보인다면 “현재 확인한 캡처 범위에는 대응 응답이 없다”고 기록합니다. 대상이 꺼져 있거나 정책상 응답하지 않았을 수도 있지만, 한 방향만 수집했거나 응답 경로가 달랐거나 필터·누락 때문에 빠졌을 수도 있습니다. 응답 부재는 무해함을 증명하지 않습니다.

4. tcpdump에서 요약과 바이트를 오가며 확인하기

많은 패킷을 볼 때는 먼저 주소와 시간의 흐름을 읽고, 의미 있는 패킷을 골라 내부를 자세히 보는 편이 좋습니다. 책을 처음부터 확대경으로 글자 하나씩 읽기보다 목차와 문단의 흐름을 파악한 뒤 필요한 부분을 확대하는 것과 비슷하죠.

tcpdump는 명령줄에서 패킷을 수집하거나 저장된 캡처를 읽는 도구입니다. Wireshark는 그래픽 화면에서 목록·상세 필드·바이트를 연결해 탐색하기에 편리합니다. 두 도구 모두 요약과 자세한 데이터를 다룰 수 있으므로 ‘tcpdump는 내용 분석을 못 한다’고 구분할 필요는 없습니다.

다음은 저장된 예시 파일을 읽는 사용법입니다. sample.pcap은 파일명 예시이며 아래 명령을 원본 실습에 실행한 것은 아닙니다.

tcpdump -nn -tttt -r sample.pcap 'icmp and host 192.0.2.10'
tcpdump -nn -tttt -X -c 3 -r sample.pcap 'icmp and host 192.0.2.10'

첫 명령의 -r sample.pcap은 네트워크를 새로 수집하는 대신 그 파일을 읽으라는 뜻입니다. -nn은 주소와 포트 번호를 이름으로 변환하지 않게 합니다. 조사 중에는 숫자 자체를 보존하면 다른 로그와 대조하기도 편합니다.

-tttt는 날짜를 포함한 시각을 표시합니다. 날짜가 없으면 자정을 지난 두 구간을 잘못 연결할 수도 있으므로, 여러 날의 자료를 조사할 때 유용합니다. 출력의 시간대가 무엇인지도 함께 기록하세요. [2]

작은따옴표 안의 icmp and host 192.0.2.10은 선택 조건입니다. icmp와 host 조건을 모두 만족해야 하며, host는 출발지와 목적지 양쪽을 대상으로 합니다. 따라서 이 주소에서 나간 요청과 이 주소로 돌아오는 응답을 함께 찾는 데 적합합니다. 이 문법은 흔히 BPF라고 부르는 tcpdump/libpcap 필터 문법입니다. [3]

두 번째 명령은 여기에 -X와 -c 3을 추가했습니다. -X는 링크 계층 헤더를 제외한 패킷 바이트를 16진수와 읽을 수 있는 문자로 함께 보여 주고, -c 3은 필터에 맞는 기록 세 개를 처리한 뒤 끝냅니다. 세 개를 골라 자세히 읽는 것과 전체 통신을 검토하는 것은 다릅니다. 범위를 제한한 이유와 이후 확장한 범위를 남겨야 합니다. [2]

소문자 -n은 호스트 주소의 이름 변환을 막고, -t는 시각을 숨기는 옵션입니다. 시각을 숨긴 상태에서는 요청 간격을 계산할 수 없으니, 현재 조사 목적에 맞게 골라야겠죠. 이번 설명은 tcpdump 공식 매뉴얼과 libpcap 필터 문서를 기준으로 확인했습니다. [2] [3]

5. 페이로드가 익숙해 보여도 시간과 길이를 다시 봅니다

바이트를 확대하면 숫자가 길게 나와 처음에는 복잡해 보일 수 있습니다. 지금은 모든 헤더를 해독하려 하지 않아도 됩니다. 어느 부분이 진단 데이터이고, 길이와 반복 패턴이 어떤 의미인지부터 연결해 보겠습니다.

16진수는 숫자 하나로 0부터 15까지를 나타내는 표기법이고, 바이트는 8비트의 데이터 단위입니다. 16진수 두 자리로 바이트 하나를 표현할 수 있습니다. ASCII는 일부 문자와 숫자에 바이트 값을 대응시킨 문자 체계입니다. 자세한 진법 변환은 4강에서 배웁니다.

# 독립적인 데이터 예시: 아래 두 줄은 같은 8바이트
16진수: 61 62 63 64 65 66 67 68
문자:   a  b  c  d  e  f  g  h

일부 ping 구현은 규칙적인 데이터나 시간 정보를 넣습니다. 그래서 익숙한 문자열이 보이면 특정 운영체제의 기본 ping과 닮았다고 생각할 수 있습니다. 하지만 사용자가 패턴과 크기를 바꿀 수 있고, 다른 프로그램이 같은 내용을 만들 수도 있습니다. 특정 시기의 기본 크기나 문자열을 모든 운영체제·버전에 적용하지 마세요.

앞의 가상 출력에서 length 64는 이 예시의 tcpdump ICMP 요약에서 ICMP 메시지 전체 길이를 나타내는 것으로 구성했습니다. Echo 헤더가 8바이트라면 그 뒤의 Data는 64−8=56바이트입니다. IPv4 헤더가 옵션 없이 20바이트라면 IP 전체 길이는 20+64=84바이트가 됩니다.

계층별 길이 계산
계산 단계계산무엇의 길이인가?
Echo 데이터64 − 8 = 56바이트ICMP Echo 헤더 뒤 Data
ICMP 메시지8 + 56 = 64바이트Echo 헤더와 Data 전체
IPv4 패킷20 + 64 = 84바이트옵션 없는 IPv4 헤더와 ICMP 메시지

여기에 이더넷 프레임의 헤더 등을 더한 길이는 또 다른 단위입니다. 모든 화면의 length가 같은 경계를 가리키는 것은 아니므로 어느 계층의 시작부터 어디까지인지 확인하세요. 예제에서 가정한 20바이트도 IP 옵션이 있으면 달라질 수 있습니다.

ASCII 영역에 점이 많다면 암호화일까요? 그것만으로는 알 수 없습니다. 출력 도구는 읽을 수 있는 문자로 표현하기 어려운 바이트를 점으로 표시할 수 있습니다. 이진 구조나 패딩도 점처럼 보일 수 있고, 실제 마침표 문자와도 구별해야 합니다. 먼저 16진수 값과 위치를 봅니다.

여기서 주소·시각을 다시 연결해 보세요. 데이터가 기본 ping과 비슷해도, 여러 목적지로 아주 짧은 간격에 보냈다면 자동화된 탐색일 수 있습니다. 익숙한 데이터 모양이 전후 행동의 의미를 대신하지는 않습니다.

6. “Nmap 같네요”를 검증할 가설로 바꾸기

패턴을 보고 “이건 Nmap 같네요”라는 생각이 들 수 있습니다. Nmap은 호스트와 서비스를 탐색하는 데 널리 사용하는 도구입니다. 이런 추측은 조사의 출발점이 될 수 있지만 아직 결과는 아닙니다.

이제 질문을 바꿔 보세요. “Nmap이라면, 어떤 버전과 옵션·권한·네트워크 조건에서 이런 패킷을 만들까요?”

다음은 호스트 탐색 옵션을 설명하는 사용법 예시입니다. 실제로 실행하지 않았으며, 주소는 문서용 주소입니다. 재현할 때는 자신이 관리하고 허가받은 격리 실습망의 실제 주소와 경로로 바꾸어 조건을 기록합니다.

nmap -sn -PE -n 198.51.100.11-13

-sn은 포트 스캔을 하지 않고 호스트 탐색을 수행하는 옵션입니다. 과거 문서의 -sP와 연결되는 현재 명칭입니다. -PE는 ICMP Echo 방식의 탐색을 지정하고, -n은 이름 해석을 끕니다. 마지막 표현은 끝 주소가 11부터 13인 세 대상을 지정합니다. [4]

그런데 이 명령을 같은 이더넷 링크에서 실행하면 언제나 ICMP가 나올까요? 그렇지는 않습니다. Nmap 공식 문서는 권한과 환경에 따라 로컬 이더넷 대상에 ARP 탐색을 사용하며, -PE를 지정해도 이러한 동작이 개입할 수 있다고 설명합니다. ARP는 같은 링크에서 IP에 대응하는 링크 주소를 알아보는 통신으로, 10강에서 자세히 다룹니다. [4]

따라서 원격 경로의 ICMP와 같은 링크의 ARP를 비교해 놓고 “패킷이 다르니 다른 도구다”라고 말하면 전제부터 맞지 않는 것이죠. 비관리자 권한에서 사용 가능한 탐색 방식이 달라지는 점도 고려해야 합니다.

Nmap에는 패킷 데이터나 길이를 바꾸는 옵션도 있습니다. 그러므로 기본 설정의 예제와 길이가 다르다는 이유만으로 Nmap 가능성을 배제할 수는 없습니다. 특정 ID나 순번의 조작 여부도, 문서에서 보지 못했다는 이유만으로 모든 버전과 변형 도구에 대해 불가능하다고 단정하지 않습니다. [5]

도구 비교 실험의 조건
비교할 조건왜 맞춰야 할까요?

적절한 보고 문장은 “실험한 버전과 옵션에서는 관측 패턴이 재현되지 않았다”입니다. 조건을 명시하면 나중에 다른 옵션이나 도구가 확인됐을 때 무엇을 다시 검토해야 하는지도 분명해집니다.

7. 관찰 → 가설 → 검증과 종합 → 보고

앞의 과정을 네 단계로 정리해 보겠습니다. 분석은 자료를 주소·시각·필드·데이터처럼 구성 요소로 나누어 읽는 일입니다. 가설은 관측을 설명할 가능한 원인입니다. 종합은 개별 근거를 연결해 일관된 설명을 만드는 일이며, 필요한 경우 실험으로 가설을 검증합니다.

예를 들어 관찰은 “여러 목적지에 짧은 간격으로 Echo Request가 보였다”입니다. 가설은 “자동화된 호스트 탐색일 수 있다”이고, 검증은 승인된 점검 일정·프로세스 기록·도구 조건을 대조하는 것입니다. 보고에서는 확인한 사실과 여전히 남은 의문을 구분합니다.

그림의 되돌아가는 화살표를 봐 주세요. 검증 결과가 가설과 맞지 않으면 관측을 다시 읽고 다른 설명을 검토합니다. 처음 생각한 답을 지키기 위해 맞는 근거만 골라내는 과정이 아닙니다.

‘승인된 스캐너일 것이다’라고 생각했다면 등록된 장비인지, 해당 시간의 점검 계획과 대상이 일치하는지 확인합니다. ‘침해된 서버일 것이다’라고 생각했다면 어떤 로그인·프로세스·후속 통신이 그 설명을 지지하는지 찾아야 합니다. 어느 쪽도 먼저 결론으로 적고 시작하지 않습니다.

도구 비교 실험도 마찬가지입니다. 네트워크에서 관측한 결과와 실험 환경의 결과를 구분하고, 맞지 않는 부분을 숨기지 않습니다. 재현하지 못했다면 그 조건에서 확인하지 못했다고 보고하면 됩니다.

8. 도구의 이름으로 사람의 실력을 평가할 수 있을까요?

익숙한 기본 도구는 초보자도 사용할 수 있습니다. 그렇다고 그 도구를 사용한 사람이 모두 초보자인 것은 아니겠죠. 숙련된 관리자가 단순한 도구를 선택하는 이유가 있듯, 숙련된 공격자도 기본 기능을 사용할 수 있습니다.

낯선 도구가 보인다고 반드시 고급 공격인 것도 아닙니다. 분석자가 모르는 프로그램일 수 있고, 정상 업무 도구가 새로 도입됐을 수도 있습니다. 알려진 도구인지 알아보는 일은 유용하지만, 그 결과를 사람의 능력이나 실제 피해와 같은 것으로 취급해서는 안 됩니다.

현재 보안 지침에서는 LOTL(Living Off the Land)도 중요하게 다룹니다. 시스템에 원래 있는 도구와 기능을 악용하면 정상적인 관리 활동과 비슷한 흔적을 남길 수 있습니다. 그래서 도구 이름 하나보다 평소 기준과의 차이, 실행 계정과 권한, 부모·자식 프로세스, 대상과 목적을 연결해서 조사합니다. [6]

예를 들어 승인된 점검 서버가 예정된 시간에 실행한 탐색과, 문서 편집 프로그램에서 시작된 알 수 없는 프로세스가 민감한 서버를 찾는 활동은 같은 ping을 사용해도 조사 맥락이 다릅니다. 이 예시만으로 뒤쪽 사례를 침해로 확정하는 것은 아니지만, 추가 확인할 근거가 무엇인지는 더 구체적이 되겠죠.

9. SYN 스캔은 무엇을 찾고 있을까요?

Ping Sweep이 ‘어느 주소에서 반응이 오는가’를 살펴보는 경우라면, 한 대상의 여러 포트에 보내는 SYN 스캔은 ‘어떤 서비스가 반응하는가’를 알아보려는 활동일 수 있습니다.

SYN은 TCP 연결 설정을 시작할 때 사용하는 제어 표시입니다. ACK는 확인을 나타내며, RST는 연결을 재설정하거나 거부할 때 관련되는 표시입니다. 기본 연결 설정에서는 시작한 쪽의 SYN, 상대의 SYN과 ACK, 시작한 쪽의 ACK가 이어집니다. 이것을 세 단계의 연결 설정이라고 부릅니다. [7]

TCP 기본 연결 설정
순서기본적인 연결 설정 예시아직 뜻하지 않는 것
1클라이언트 → 서버: SYN로그인 성공이나 명령 실행
2서버 → 클라이언트: SYN-ACK응용 요청의 정상 처리
3클라이언트 → 서버: ACK사용자 인증이나 업무상 승인

스캔은 상대 반응만 살펴보고 연결을 끝까지 진행하지 않을 수 있습니다. 따라서 SYN이 보였다는 것과 실제로 응용 서비스에 접속해 작업했다는 것을 구분해야 합니다.

# 가상 SYN 탐색 요약: Flags [S]는 SYN, length 0은 이 TCP 데이터 길이가 0이라는 뜻
192.0.2.20.53000 > 198.51.100.30.22:  Flags [S], seq 9000, win 4096, length 0
192.0.2.20.53000 > 198.51.100.30.80:  Flags [S], seq 9000, win 4096, length 0
192.0.2.20.53000 > 198.51.100.30.443: Flags [S], seq 9000, win 4096, length 0

주소 뒤의 마지막 숫자는 포트입니다. 목적지 IP는 같은데 포트가 22·80·443으로 달라집니다. 출발지 포트와 seq는 반복됩니다. win은 상대에게 알리는 TCP 수신 창과 관련된 값으로, 흐름 제어를 배울 때 자세히 다룹니다. 여기서의 length 0은 패킷 자체가 없거나 길이가 0이라는 뜻이 아니라 TCP 응용 데이터가 없다는 뜻입니다.

이 출력의 TCP seq와 앞에서 읽은 ICMP seq는 이름이 비슷하지만 다른 프로토콜의 다른 필드입니다. ICMP Echo의 순번 해석을 TCP에 그대로 가져오면 안 됩니다.

같은 출발지 포트나 TCP seq가 반복된다는 것은 자동 생성 방식 등을 조사할 특징입니다. 그러나 그것만으로 Nmap이나 주소 위조를 확정할 수는 없습니다. 일반 연결에서 기대하는 동작과 비교하고, 버전·옵션·시각·포트 선택·후속 통신을 함께 확인해야 합니다.

# 저장된 파일에서 가상 주소와 포트에 관련된 TCP를 양방향으로 선택하는 사용법
tcpdump -nn -tttt -r sample.pcap 'tcp and host 192.0.2.20 and port 53000'

tcp는 TCP를 고르고, host는 해당 주소가 어느 방향에 있든 선택합니다. port 53000도 출발지·목적지 양쪽에 적용되므로 돌아오는 응답을 함께 읽을 수 있습니다. 실제 조사에서 출발지 포트가 바뀌었다면 이 조건 밖으로 빠질 수 있으니 주소와 시간 범위로 다시 넓혀 봅니다. [3]

10. ICMP 터널은 요청과 응답의 관계에서 시작합니다

이번에는 바깥 표시가 ICMP라는 이유로 모두 일반 ping이라고 생각하지 않는 연습입니다.

터널은 다른 통신을 실어 나르는 운반 수단이라고 했죠. 편지 봉투 안에 진단 확인 문구 대신 다른 업무 문서를 넣는 모습을 떠올려 보세요. 겉봉투의 종류가 같아도 안에 담긴 내용과 주고받는 방식은 달라질 수 있습니다.

다만 네트워크 터널이 언제나 완성된 IP 패킷 하나를 통째로 안에 넣는 것은 아닙니다. 터널 도구가 자체 제어 정보와 데이터 조각을 담을 수도 있습니다. 실제 구조는 해당 프로토콜과 도구에 따라 확인해야 합니다.

먼저 단순한 유니캐스트 Echo를 기준으로 보겠습니다. 유니캐스트는 한 목적지를 향한 전달입니다. 요청의 ID·순번과 데이터가 응답에서 대응되는지 확인합니다. 그 뒤에 응답 수·크기·내용·순서를 함께 비교합니다.

A와 B는 단순한 요청·응답으로 대응됩니다. C가 같은 모양으로 한 번 더 나타났다면 수집 중복인지, 실제로 반복 전송된 것인지 먼저 확인합니다. 여러 수집 지점의 파일을 합쳤다면 같은 패킷을 두 번 담을 수도 있겠죠.

D는 데이터의 길이와 내용도 다릅니다. 정말 A에 대한 표준 Echo 응답인지, 같은 ID·순번을 다시 쓰는 다른 교환인지, 요청 일부를 놓쳤는지, 별도의 운반 방식인지 조사할 이유가 있습니다. 표의 네 줄만으로 한 가지 원인을 확정하지는 않습니다.

방송·멀티캐스트 요청이나 여러 응답 주체를 포함한 경우에는 단순한 ‘요청 하나에 응답 하나’의 전제도 다시 검토해야 합니다. 응답 개수를 셀 때는 선택한 필터와 시간 구간, 중복 수집, 누락부터 확인하세요.

그림에서는 바깥쪽 IP·ICMP가 같아도 데이터 영역의 용도가 달라질 수 있다는 점을 읽으면 됩니다. 특정 터널 제품의 바이트 배열이나 상대적인 길이 비율을 나타낸 그림은 아닙니다.

그런데 왜 단순한 문자열 규칙만으로는 부족할까요? 어떤 규칙은 패킷 안의 특정 데이터에만 반응할 수 있습니다. ‘한 요청과 관련된 응답이 여러 개다’라는 관계는 여러 패킷을 묶어 봐야 드러납니다. 상태와 관계를 분석하는 기능이 있는 도구도 있으므로, 모든 IDS가 이런 행위를 탐지할 수 없다고 일반화하지는 마세요. 실제 규칙이 무엇을 보고 울렸는지 확인하는 것이 중요합니다.

11. ICMP 안의 SSH 문자열은 어디까지 말해 줄까요?

SSH는 원격 접속 등을 보호하는 프로토콜입니다. SSH 연결의 시작에는 자신이 사용하는 프로토콜과 소프트웨어를 알리는 식별 문자열이 오갈 수 있습니다. 예를 들어 아래는 새로 만든 식별 문자열입니다. 실제 제품 버전이나 원본 실습 출력이 아닙니다. [8]

SSH-2.0-demo_1.0
시작 8바이트: 53 53 48 2d 32 2e 30 2d

53은 대문자 S, 48은 H, 2d는 하이픈입니다. 이 바이트를 문자로 읽으면 SSH-2.0-가 됩니다. ICMP Data에서 이런 구조를 발견하면, 일반적인 진단 외에 다른 통신을 운반하는지 조사할 수 있습니다.

SSH 식별 줄은 CR과 LF라는 두 줄 끝 문자로 끝납니다. 각각의 바이트는 0d와 0a이며, 위 식별 문자열의 문자 16바이트에 이를 더하면 16+2=18바이트입니다. 문자로 보기 좋은 화면에서는 줄 끝 바이트가 눈에 잘 보이지 않을 수 있으므로 바이트 길이와 화면 글자 수를 구분합니다. [8]

그렇다고 ‘문자열이 있으니 SSH 접속 성공’이라고 쓸 수는 없습니다. 임의의 문자열을 넣은 진단 데이터일 수도 있고, 통신의 시작만 보였을 수도 있습니다. 문자열은 송신자가 보낸 주장일 뿐, 설치된 프로그램의 실제 버전까지 보장하지도 않습니다.

교재는 ICMP로 TCP 통신 데이터를 운반하는 도구의 사례를 통해 이러한 차이를 보여 줍니다. 여기서 배울 핵심은 특정 도구 이름을 외우는 것이 아니라 바깥 프로토콜의 정상적인 역할과 안쪽 데이터·교환 관계가 맞는지 확인하는 방법입니다. 데이터 유출이나 원격 제어 통로일 가능성은 조사할 가설이며, 정당한 사용 여부와 실제 전달 내용을 더 확인해야 합니다.

SSH 식별 부분을 읽었다고 뒤의 명령과 파일을 전부 볼 수 있는 것도 아닙니다. 후속 통신이 암호화되면 본문 해석이 제한됩니다. 그래도 외부 ICMP의 시간·크기·방향과 요청·응답 관계는 여전히 조사할 수 있죠. 1강의 암호화 가시성 설명과 연결되는 부분입니다.

Wireshark에서 같은 주소의 ICMP를 살펴보는 표시 필터 예시는 다음과 같습니다.

icmp && ip.addr == 192.0.2.10

icmp는 해당 프로토콜이 있는지 확인하고, &&는 두 조건을 모두 만족해야 한다는 뜻입니다. ip.addr == 192.0.2.10은 IPv4 주소 필드 중 이 값과 같은 것이 있는 패킷을 고릅니다. 출발지와 목적지 양쪽을 대상으로 할 수 있으므로 관련 양방향 교환을 찾는 데 쓸 수 있습니다. [9]

이것은 Wireshark 표시 필터입니다. 앞에서 사용한 tcpdump/libpcap의 icmp and host …를 같은 입력 칸에 그대로 넣는 문법이 아닙니다. 표시 필터를 적용하면 화면에 보이는 범위가 줄어들므로, 후속 조사에서 이전 필터가 남아 있지 않은지도 확인하세요. 패킷 바이트 검색과 도구가 해석한 필드 검색, 재조립된 데이터 검색도 같은 입력이 아닙니다.

데이터가 IP 조각이나 여러 메시지에 나뉘었다면 필요한 부분을 모아 읽는 재조립 조건도 확인합니다. 바이트가 한 패킷 안에 연속해서 없다는 이유로 전체 통신에도 문자열이 없다고 단정할 수는 없습니다. 반대로 터널 형식을 해석하지 않은 채 모든 ICMP Data를 단순 연결하면 제어 정보와 중복 데이터를 잘못 섞을 수 있습니다. 필요한 패킷의 확보 여부와 도구가 실제로 해석하는 범위를 구분하세요.

터널 가설을 검증할 때는 양 끝 호스트의 프로세스와 연결 기록, 실행 파일·서비스 설정, 방화벽의 허용·차단, 작업 승인 여부를 대조합니다. 문자열 하나나 패킷 개수만으로 감염·유출 성공을 확정하지 않는 이유입니다.

12. 첫 경고보다 앞의 시간을 조사하고 우선순위를 정합니다

내부 서버에서 외부 주소를 향한 스캔 경고가 처음 발생했습니다. 이때가 사건의 시작일까요?

관리자가 진단을 막 시작한 순간일 수도 있습니다. 반대로 이미 침해된 서버에서 후속 탐색이 시작됐고, 그제야 탐지했을 수도 있습니다. 처음 경고한 시각은 처음 탐지한 시각이지 언제나 최초 활동 시각은 아닙니다.

택배 배송 기록을 보다가 마지막 이동 기록을 처음 발견했다고 해서, 물건이 그때 만들어진 것은 아니겠죠. 앞선 흔적을 찾아보는 이유가 여기에 있습니다. 다만 가능한 사건의 단계를 안다는 이유로 실제로 보지 않은 활동을 연표에 사실처럼 채워 넣어서는 안 됩니다.

내부 이동은 다른 내부 시스템으로 접근 범위를 넓히는 활동을 말합니다. 가능한 가설로 조사할 수 있지만, 이 표가 그런 활동을 관측했다는 뜻은 아닙니다. 마찬가지로 데이터 반출이나 권한 상승도 실제 근거가 있을 때만 발생 사실로 기록합니다.

연표를 만들 때는 시간대와 시계 차이, IP를 사용한 장비의 변경, 주소 변환을 고려합니다. 인증 기록 하나와 같은 IP의 통신이 가깝게 나타났다는 이유만으로 특정 사용자가 만들었다고 확정하지 않고, 세션·프로세스·장비 식별 근거를 연결합니다.

필요한 자료는 경고를 일으킨 패킷만이 아닐 수 있습니다. 경고 이전과 이후의 네트워크 기록, 단말·서버·인증·방화벽 기록을 찾아 범위를 넓힙니다. 다만 수집이 없었던 구간의 내용을 복원했다고 주장해서는 안 됩니다.

이제 첫머리의 세 경고로 돌아가 보겠습니다. 우선순위는 경고 이름만으로 고정하지 않고 다음 조건을 함께 봅니다.

관측의 충분성시간·양방향·필터·누락 조건이 맞는가?수집 설정과 다른 지점의 관측

중요 서버에서 승인되지 않은 프로세스가 만드는 ICMP 데이터 교환이 관측됐다면 우선 확인할 이유를 설명할 수 있습니다. 등록된 장비의 예정된 SYN 점검은 정상 작업일 수 있죠. 반대로 응답 없는 Ping Sweep도 침해 정황과 연결된다면 조사를 뒤로 미룰 근거가 되지는 않습니다.

‘터널이라 높음’이라는 메모보다 ‘중요 서버의 미승인 프로세스와 ICMP 데이터 교환이 연결되어 영향 확인을 우선한다’는 메모가 다음 행동으로 이어집니다. 확인된 영향과 아직 조사 중인 가설을 함께 적어 주세요.

13. 이번 회차의 증거와 복습

이번 회차의 증거 구분
구분이번 강의에서 남길 내용
패킷으로 직접 관측주소·방향·시각·간격·ID·순번·길이·캡처된 응답과 데이터
관측이 지지하는 가설자동 탐색, 특정 생성 방식, ICMP를 이용한 다른 데이터 운반
단독으로 확정하기 어려운 결론실제 사용자·도구의 단정·공격자 숙련도·관측 밖 응답·침해와 유출의 성공
함께 대조할 자료승인과 자산 목록, 프로세스·서비스·인증·서버·방화벽 기록, 추가 캡처

다음은 관찰과 가설, 다음 확인을 나누어 적은 가상 보고 예시입니다.

여러 목적지로 0.5밀리초 간격의 ICMP Echo Request가 관측되었다. 자동화된 탐색 가능성이 있다. 현재 캡처에서 대응 응답은 확인되지 않았다. 실행 프로세스와 승인 여부, 수집 방향·시간·필터와 응답 경로를 추가 확인한다.

문제 1. 여러 목적지에 0.5밀리초 간격의 Echo Request가 있습니다. 어떤 설명을 먼저 검토할까요?

해설: 사람이 목적지를 바꾸며 일일이 입력했다는 설명보다 자동화된 처리 가능성을 먼저 검토할 만합니다. 하지만 어떤 도구인지, 악성인지까지 증명된 것은 아닙니다. 실행 기록과 업무 맥락, 수집 시각의 정밀도도 확인합니다.

문제 2. 시각이 0.000100초와 0.000850초라면 간격은 얼마인가요?

해설: 0.000850−0.000100=0.000750초입니다. 1000을 곱하면 0.75밀리초입니다. 출력의 소수 자릿수와 초·밀리초의 단위를 혼동하지 않아야 합니다.

문제 3. ICMP seq가 모두 1이면 비정상이라고 확정할까요?

해설: 아닙니다. 여러 대상에 한 번씩 확인하는 프로그램 등 구현과 목적에 따라 설명될 수 있습니다. 주소·시각·ID·데이터와 프로그램 조건을 함께 봅니다. ICMP 순번의 관행을 반드시 지켜야 하는 단일 규칙처럼 다루지 않습니다.

문제 4. Echo 메시지가 64바이트이고 Echo 헤더가 8바이트라면 Data와 IP 전체 길이는 얼마인가요?

해설: Data는 64−8=56바이트입니다. IPv4 헤더가 옵션 없이 20바이트라는 조건에서는 IP 전체가 20+64=84바이트입니다. 이 값은 이더넷 프레임 전체 길이가 아니며 헤더 조건이 달라지면 다시 계산해야 합니다.

문제 5. -x를 사용했는데 문자 표시가 기대와 다릅니다. 무엇을 확인할까요?

해설: 16진수와 ASCII를 함께 보려는 목적이라면 대문자 -X인지 확인합니다. 소문자 -x와 구별하고, 시간 간격도 조사한다면 -t로 시각을 숨기지 않았는지 확인합니다. 어떤 계층부터 출력하는지도 함께 봅니다.

문제 6. 한 번 실행한 Nmap 출력과 길이가 다르면 Nmap을 배제할 수 있을까요?

해설: 그 실험 조건에서는 같은 패턴이 재현되지 않았다고 적는 것이 맞습니다. 버전·권한·운영체제·경로·옵션·데이터 길이 설정을 맞춰 봐야 하며 기본 출력 하나로 모든 가능성을 배제하지 않습니다.

문제 7. -PE를 지정했는데 같은 링크에서 ARP가 보였습니다. 명령이 실패한 걸까요?

해설: 꼭 그렇지는 않습니다. Nmap은 로컬 이더넷 대상에서 권한과 옵션에 따라 ARP 탐색을 사용할 수 있습니다. 대상과의 경로, 실행 권한과 실제 옵션을 확인해야 합니다. ARP를 ICMP의 실패 결과로 해석하지 않습니다.

문제 8. SYN의 length 0은 전송된 패킷이 없다는 뜻인가요?

해설: 이 예시에서는 TCP 데이터 길이가 0이라는 뜻입니다. IP·TCP 헤더와 SYN 표시는 존재합니다. 따라서 어떤 계층의 길이인지 먼저 확인하며 연결 시도와 응용 데이터 교환을 구분합니다.

문제 9. 응답이 없는 SYN 스캔은 무해하다고 종결해도 될까요?

해설: 캡처의 응답 부재와 실제 응답 부재를 먼저 구별합니다. 양방향 수집·방화벽 처리·필터·시간 범위·승인 여부와 다른 통신을 확인합니다. 실패한 탐색 정황이 있어도 다른 침해 가능성이 자동으로 사라지는 것은 아닙니다.

문제 10. 한 요청에 같은 응답 두 개가 보이면 터널인가요?

해설: 개수만으로는 부족합니다. 중복 수집·누락된 요청·실제 반복 전송·응답 주체와 요청 방식 등을 먼저 확인합니다. 길이·데이터의 대응과 여러 패킷의 연속성, 단말 기록이 다른 데이터 운반 가설을 지지하는지도 조사합니다.

문제 11. ICMP에서 SSH-2.0-를 찾으면 명령과 유출 파일을 모두 알 수 있나요?

해설: 아닙니다. 식별 문자열은 통신의 시작을 의심할 단서이며 인증·명령 실행·유출 성공을 증명하지 않습니다. 임의 데이터일 가능성과 실제 프로토콜 구조를 확인해야 하고, 후속 통신이 암호화되면 그 내용의 가시성은 제한됩니다.

문제 12. 내부 서버의 외부 스캔이 첫 경고라면 연표는 어디서 시작할까요?

해설: 경고보다 앞의 통신·인증·프로세스 기록을 찾되, 최초 침해가 있었다고 미리 채워 넣지 않습니다. 확인한 최초 관측 시점과 실제 시작 시각이 미확인이라는 점을 구분합니다. 정상 점검과 침해 후 탐색 같은 경쟁 가설을 근거로 비교합니다.

문제 13. 기본 ping을 썼다는 이유로 공격자의 실력이 낮다고 판단할 수 있을까요?

해설: 어렵습니다. 숙련된 공격자도 기본 기능을 악용할 수 있습니다. 도구의 희귀성보다 실행 주체·권한·대상·목적·정상 기준과의 차이·후속 활동을 확인합니다. 평소와 다르다는 사실도 실제 피해와는 구분합니다.
