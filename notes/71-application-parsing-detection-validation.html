학습 범위

넷째 날 16강에서는 DHCP 옵션, HTTP 요청과 응답, 메일 첨부를 예로 듭니다. 같은 데이터라도 화면에 표시된 문자열, 센서가 검사한 필드, 종단 프로그램이 처리한 값이 달라질 수 있습니다. 정상 합성 표본으로 보고서에 어떤 근거를 남길지 연습합니다.

1. 검색 전에 어느 필드의 어떤 값을 읽는지 정합니다

메일 담당자는 의심 첨부가 들어왔다고 하고, 네트워크 담당자는 같은 시간에 경보가 없었다고 합니다. 무엇부터 맞춰야 할까요? 먼저 둘 다 같은 메시지와 같은 표현을 읽었는지 확인합니다. 우편 봉투에 적힌 주소, 상자에 붙은 라벨, 안에 들어 있는 설명서의 단어는 서로 다른 정보입니다. 네트워크에서도 주소·경로·옵션·본문은 역할이 다릅니다. 다만 소포에 비해 네트워크 데이터는 분할·압축·인코딩되거나, 암호화 뒤에 숨을 수 있습니다.

파서는 바이트를 프로토콜 구조와 필드로 나눕니다. 디코딩은 정해진 표현을 다른 표현으로 읽는 과정이고, 정규화는 여러 표현을 일정한 방식으로 정리하는 일입니다. 검사 버퍼는 규칙이 검색할 데이터를 담은 공간입니다. 처음 단계에서 본 문자열이 어디의 어떤 데이터인지 남겨야 다음 단계의 판단을 설명할 수 있습니다.

2. DHCP에서는 옵션의 역할과 수신 프로그램을 함께 봅니다

DHCP는 단말에 주소와 네트워크 설정을 자동으로 알려주는 프로토콜입니다. 옵션은 그 안에서 개별 설정을 뜻합니다. RFC 2132에서 옵션 12는 클라이언트 호스트 이름, 옵션 15는 이름 해석에 쓰는 도메인 이름입니다. 이때 길이 필드는 값의 바이트 수를 나타냅니다. 문서용 정상 값 lab.example은 lab 3바이트, 점 1바이트, example 7바이트를 합쳐 11바이트입니다. 옵션 코드 1바이트와 길이 1바이트를 포함하면 이 옵션 전체는 13바이트입니다.

만약 배포 변경 직후 여러 단말에서 예상하지 못한 도메인 설정이 들어왔다면 해당 값과 DHCP 응답 방향, 트랜잭션 ID, 임대 기록을 맞춥니다. 릴레이를 쓰는 환경에서는 센서가 보는 출발 주소와 원래 서비스의 관계도 확인합니다. 패킷에 설정이 있다는 사실은 종단이 그 값을 적용했다는 판단의 출발점입니다. 적용 결과는 클라이언트와 승인 DHCP 서버의 기록에서 확인합니다.

과거 Bash 취약점인 Shellshock은 외부 입력이 환경 변수를 거쳐 취약한 Bash로 전달될 때 생길 수 있는 문제였습니다. Red Hat은 일부 DHCP 클라이언트 구성도 영향 경로로 설명합니다. 검증할 것은 대상 자산의 패키지 보안 업데이트, DHCP 처리 경로와 종단 프로세스 이벤트입니다. 규칙 경보를 확인했더라도 실제 실행 여부는 따로 판단합니다. 교재에 등장하는 특정 문자 조합을 쓰는 과거 시그니처는 오늘의 패치·자산 확인이나 필드 검증까지 대신해 주지 못합니다.

3. HTTP의 경로·헤더·본문마다 관찰 범위가 다릅니다

가상 단말 192.0.2.24가 문서용 서비스 https://status.example/health를 읽는다고 합시다. /health는 경로, status.example은 호스트 이름입니다. Snort 3에서 http_uri는 정규화된 요청 URI 검사 버퍼, http_raw_uri는 정규화 전의 요청 URI 검사 버퍼입니다. http_client_body는 요청 본문에 대한 검사 버퍼입니다. 경로를 읽는 규칙과 폼의 내용을 읽는 규칙은 같은 요청에서도 서로 다른 부분을 봅니다. 실제 인스펙터 설정과 로그에 남은 필드를 확인해야 하는 이유입니다.

Content-Type은 데이터의 매체 형식, Content-Encoding은 표현에 적용한 코딩을 나타냅니다. 본문이 gzip으로 압축된 응답이라면 압축된 바이트와 풀린 텍스트는 각기 다른 단계의 증거입니다. 센서가 암호화 구간 밖에 있으면 HTTP 경로나 본문이 미관측일 수 있습니다. 승인된 TLS 종료 지점의 요청 로그와 응용 요청 ID를 사용해 행위를 검증합니다.

4. 정상 표본으로 표현과 결과를 짝지어 봅니다

MIME은 메일을 파트별로 나누고 첨부의 형식과 전송 표현을 설명하는 규격입니다. 예를 들어 평문 OK는 ASCII로 2바이트이고, 같은 값을 MIME Base64로 표현하면 T0s= 4문자가 됩니다. =는 이 예에서 그룹 끝을 채우는 패딩입니다. Base64는 전송용 표현이며 누구나 규칙에 따라 원래 바이트를 읽을 수 있습니다. 설명서 대신 문자가 적힌 상자를 받았다고 가정해 보면, 읽는 단계에서 안에 무엇이 적혔는지 알 수 있지만 그 내용을 실행할 필요는 없습니다.

조건을 바꿔 한국을 UTF-8로 저장하면 두 글자가 각각 3바이트를 사용해 총 6바이트입니다. Base64는 3바이트를 4문자로 바꾸므로 6바이트는 2그룹, 총 8문자입니다. 값은 7ZWc6rWt입니다. 한글 검색이 예상과 다르다면 파트의 문자 집합과 인코딩, 로그 필드에서 값이 잘리지 않았는지부터 살펴보세요. 언어 자체에는 위협이나 신뢰 점수를 부여하지 않습니다.

원문       OK      (ASCII 2바이트)
전송 표현  T0s=    (Base64 4문자)
해석 결과  OK      (ASCII 2바이트)

검사 기록에 원시 파트의 해시, 선언된 형식, 디코딩 성공 여부, 분석기가 검사한 필드를 남기세요. 첨부 안에 다른 객체가 있으면 승인된 오프라인 환경에서 개체별로 보존하고, 용량·중첩 제한에 닿았으면 검사된 범위를 표시합니다. 오래된 탐지 예제가 다룬 실행 가능 첨부의 문자열은 여기서 일반적인 파싱 검증 목표로 바꿨습니다.

5. 주말이나 트래픽 급증 구간에서도 확인할 근거를 남깁니다

평소 1분당 100건이던 수집기 입력이 행사 중 900건으로 늘었다고 합시다. 증가량은 800건/분, 평소 대비 배율은 900 ÷ 100 = 9배입니다. 배율만으로 보안 사고를 발표할 수는 없습니다. 패킷 드롭, 로컬 엔진 출력, 중앙 적재 오류, 분석 대기열과 알림 전달 시간을 나란히 비교하세요. 평소 적던 오류의 절대 건수가 늘어났다면 전체 건수 대비 비율도 함께 계산합니다.

보고에는 해당 환경의 시간대, 교대 담당자가 확인할 정렬 기준, 첫 관측 시각 및 다음 조치를 넣습니다. 이해하기 어려운 언어나 인코딩이라면 쓰인 문자 집합을 기록하고 필요 시 해당 언어를 읽을 수 있는 검토자에게 전달합니다. 이벤트가 평소보다 많은 구간에는 센서에서 기록된 근거와 실제로 분석가에게 도착한 경보를 비교합니다. 재현용 검증에는 정상 요청, 정상 인코딩 첨부, 짧은 캡처를 각각 준비하고, 기대한 관측과 검사 한도를 장부에 씁니다.

복습과 바로 읽는 해설

1. DHCP 옵션 15가 보이면 단말이 설정을 적용했나요?
패킷에 값이 있다는 사실을 먼저 적습니다. 승인 서버인지와 어떤 임대인지 확인하고 단말 설정이나 임대 기록을 대조합니다.
2. 같은 정상 문자열을 영어 2바이트에서 UTF-8 6바이트로 바꾸면 Base64 길이는 어떻게 변하나요?
2바이트는 한 그룹으로 4문자, 6바이트는 두 그룹으로 8문자입니다. 문자의 수와 바이트 수를 구분합니다.
3. TLS 연결 기록만 남았는데 HTTP 경로를 확정할 수 있나요?
승인된 종료 지점 또는 응용 서버의 요청 기록을 확보합니다. 센서에서 관측한 TLS 연결 정보는 시각과 방향을 맞추는 근거로 사용합니다.
4. 피크 시간 경보 적재가 줄면 가장 먼저 살필 자료는 무엇인가요?
같은 시간 창에서 센서 로컬 출력과 중앙 입력·드롭·지연을 비교합니다. 어느 단계에서 관측 차이가 발생했는지 확인한 뒤 원인을 조사합니다.

2026-11-25에 확인했습니다. 정상 문서용 데이터와 오프라인 산술·인코딩을 사용했습니다. 원본 첨부·센서 룰·실제 네트워크 입력은 실행하지 않았습니다.
