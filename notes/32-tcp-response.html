학습 범위와 예제

둘째 날 10강 · 교재 인쇄 107~114쪽의 학습 주제를 자체 예제와 해설로 풀었습니다. 아래 주소·숫자·흐름은 별도 표시가 없으면 가상 학습 예시입니다. 명령은 분석 절차이며 실제 실행 출력으로 제시하지 않습니다.

1. 초인종을 눌렀는데 대답이 없습니다

초인종을 눌러도 대답이 없으면 무엇을 알 수 있을까요? 집이 비었을 수도 있고, 초인종이 고장 났거나, 소리를 듣지 못했을 수도 있습니다. “응답이 없다”는 사실 하나로 어느 원인인지 확정할 수는 없습니다. TCP 연결 시도도 마찬가지입니다. 송신한 SYN을 자극으로 두고 응답과 무응답의 가능한 원인을 나눠 보겠습니다.

분석 전에 센서가 어디에 있는지 표시합니다. 클라이언트 옆인지, 방화벽 바깥인지, 서버 옆인지에 따라 보이는 패킷이 다릅니다. 센서에서 보았다는 것과 서버가 받았다는 것은 동일한 문장이 아닙니다. 양방향을 볼 수 있는지도 먼저 확인하세요.

2. 같은 자극이라는 말에는 비교 조건이 들어 있습니다

어제는 접속되던 웹 서비스가 오늘 열리지 않는다고 해 봅시다. 담당자가 “서버는 켜져 있습니다”라고 답해도 연결이 성공한다는 뜻은 아닙니다. 전원, IP 도달, TCP 수신 대기, 방화벽 허용, HTTP 처리, 사용자 인증은 서로 다른 단계입니다. 이번에는 그중 TCP 시작 요청이 어디까지 갔는지를 읽습니다.

자극(stimulus)은 상대에게 보낸 입력, 응답(response)은 그 뒤에 돌아온 반응입니다. 초인종 비유는 대답의 여러 원인을 떠올리는 데 도움이 되지만, 네트워크에는 초인종을 대신 받아 주는 프록시와 왕복의 서로 다른 길이 있습니다. 센서가 들은 대답의 주소가 같다고 원래 서버의 응용이 답했다고 할 수 없는 이유입니다.

자체 비교 조건을 정하겠습니다. 클라이언트 A는 192.0.2.40의 포트 53000, 서버 후보 B는 198.51.100.60의 포트 80입니다. IPv4/TCP, 데이터 없는 최초 SYN, 원시 SEQ 42000으로 두고, 각 경우는 독립적인 가상 실험입니다. 실제로 같은 5튜플을 동시에 재사용하여 시험한 기록이 아닙니다. 프로토콜·출발지 IP/포트·목적지 IP/포트 다섯 요소가 5튜플이며, 실무에서는 시작 시각과 연결 재사용까지 함께 적습니다.

포트 80은 여기서 HTTP를 설명하기 위해 고른 번호입니다. 그 번호만으로 HTTP 프로그램이라고 증명하지 않습니다. TLS로 암호화된 서비스라면 TCP 이후 내용을 못 읽을 수 있지만 시작 교환과 정책 실패의 구간을 좁히는 일은 여전히 가능합니다.

3. 응답 형태를 먼저 기록하고 해석을 붙입니다

일반적인 수신 대기 상태라면 SYN/ACK가 돌아올 수 있습니다. 닫힌 포트라면 RST/ACK가 올 수 있습니다. 경로에서 도달 불가나 정책 거절이 발생하면 ICMP 오류를 볼 수도 있습니다. 그러나 방화벽과 프록시가 종단을 대신해 응답할 수 있으므로 응답 주소만으로 실제 프로그램의 상태를 확정하지 않습니다.

4. SYN/ACK는 연결의 초대장이지 업무 완료 영수증이 아닙니다

LISTEN은 TCP가 해당 포트에서 시작 요청을 기다리는 상태입니다. 경로와 정책이 허용되고 요청을 받아들이는 조건이면 B가 SYN/ACK를 돌려줄 수 있습니다. SYN은 자기 번호 공간의 시작을 알리고, ACK 플래그는 확인 번호 필드가 유효함을 뜻합니다. 플래그와 숫자 ACK를 같은 것으로 읽지 마세요.

가상 번호 추적 · 옵션과 재전송은 생략 · 데이터 길이 0바이트
A 192.0.2.40:53000 → B 198.51.100.60:80   SYN      SEQ=42000
B:80 → A:53000                          SYN/ACK  SEQ=91000 ACK=42001
A:53000 → B:80                          ACK      SEQ=42001 ACK=91001

왜 42001일까요? 데이터가 0바이트여도 SYN은 순서 번호 공간에서 1을 소비합니다. 42000+1+0=42001입니다. B의 시작 번호 91000도 독립적인 값이라 마지막 ACK는 91000+1=91001입니다. B의 SEQ에 A의 시작 번호를 더하는 계산은 하지 않습니다. tcpdump의 [S.]에서 S는 SYN이고 점은 ACK 플래그를 뜻합니다. 화면의 상대 번호가 0과 1로 바뀌면 원시 번호와 섞지 말고 표시 설정부터 맞춥니다.

그렇다면 SYN/ACK만 보면 접속 성공일까요? A가 마지막 ACK를 보내지 않았거나 그 ACK가 B에 도착하지 않았을 수 있습니다. SYN 프록시라면 방화벽이 먼저 응답하고 실제 백엔드 연결은 따로 시도할 수 있어요. 양끝의 시작 완료, 후속 데이터, 서버 로그를 차례로 맞춰야 합니다. HTTP 200조차 사용자 업무나 인증 성공과 같은 뜻은 아닙니다.

관측을 바꿔 SYN/ACK 뒤에 A의 RST가 보이면 정상 응용 접속이 완료된 흐름인지 다시 살핍니다. 포트 조사 도구의 동작, 클라이언트 취소, 상태 불일치 등도 가능합니다. 응답이 빨랐다는 사실만으로 백엔드가 정상이라는 결론을 붙이지 않습니다.

5. 닫힌 상태의 RST/ACK를 번호로 맞춰 봅니다

B까지 SYN이 갔지만 그 포트에서 받아 줄 TCP 연결 상태나 수신 대기가 없다면, 일반적인 CLOSED 처리에서는 RST/ACK가 돌아옵니다. RST는 reset, 연결 상태를 즉시 거절하거나 중단하는 제어입니다. FIN처럼 정상 종료 교환을 계속하는 신호와 다릅니다.

가상 비교 · 데이터 없는 SYN에 대한 CLOSED 응답
A → B  SYN      SEQ=42000  ACK 플래그=0  데이터=0
B → A  RST/ACK  SEQ=0      ACK=42001
RST에 다시 RST를 보내는 왕복은 만들지 않습니다.

ACK 비트가 없는 입력에 대한 CLOSED 응답은 SEQ=0, ACK=입력 SEQ+세그먼트의 번호 공간 길이로 구성됩니다. 이 예제의 길이는 SYN 1+데이터 0=1이므로 42001이지요. Window 0이나 옵션 부재가 함께 보일 수 있어도 그 한 필드로 모든 RST를 식별하거나 OS를 확정하지 않습니다.

중요한 조건 변경이 있습니다. CLOSED 상태가 ACK 플래그가 있는 입력을 받으면 생성 규칙은 입력 ACK를 RST의 SEQ에 쓰는 형태입니다. 예를 들어 ACK=91001인 입력이라면 SEQ=91001인 RST를 생각할 수 있습니다. 따라서 “모든 RST에 ACK 플래그가 있어야 한다”는 암기는 틀립니다. 들어온 RST에는 다시 RST를 만들지 않는 규칙도 구분하세요. 이미 연결된 상태의 RST 검증은 별도의 순서 번호·상태 규칙을 따릅니다.

RST/ACK가 보이면 누군가 능동적으로 응답했다는 단서는 늘어납니다. 그러나 방화벽의 reject 정책도 서버 주소를 사용해 거절 응답을 만들 수 있습니다. 서버 측 캡처·방화벽 거절 기록·수신 소켓 상태를 비교하기 전에는 “서버 프로그램이 내려갔다”는 결론을 보류합니다. 주소·TTL·도착 시간의 차이는 가설의 재료이며 단독 발신 인증 수단이 아닙니다.

6. 호스트 부재와 경로 실패를 나눠 봅니다

같은 링크의 목적지에 보내려는데 MAC을 찾지 못하면 ARP 실패가 먼저 나타날 수 있습니다. 이런 경우 실제 SYN 프레임이 선로에 나가지 않았을 수도 있습니다. 반면 원격 목적지라면 로컬 게이트웨이까지는 전달되고 그 뒤 경로에서 실패할 수 있겠지요.

ICMP 오류가 있다면 바깥 IP 주소는 오류를 보낸 장비이고, ICMP 안의 인용 패킷은 무엇을 보내다가 실패했는지 알려주는 자료입니다. 이 둘을 섞지 마세요. Code와 인용된 원래 목적지·포트가 해당 SYN에 맞는지도 확인합니다. “Host Unreachable”이라는 문구를 보고 호스트가 영구적으로 존재하지 않는다고 확대 해석하지 않습니다.

7. 같은 링크에서는 서버 MAC, 원격이면 게이트웨이 MAC을 찾습니다

주소를 안다고 바로 Ethernet으로 보낼 수 있는 것은 아닙니다. 같은 링크의 IPv4 목적지라면 보통 ARP(Address Resolution Protocol)로 그 목적지의 MAC 주소를 찾습니다. 반면 라우팅 표가 원격 목적지를 가리키면 다음 홉인 게이트웨이의 MAC을 찾습니다. 원격 서버의 MAC을 로컬 링크 전체에서 직접 찾는 것이 아닙니다.

같은 링크에서 ARP 요청만 반복되고 해석이 실패했다면, IP 계층이나 호스트 내부에서 SYN이 준비됐더라도 실제 Ethernet SYN 프레임은 아직 나가지 않았을 수 있습니다. 캡처 지점이 호스트 내부인지 외부 선로인지에 따라 “보냈다”의 뜻이 달라집니다. ARP 실패도 호스트 부재뿐 아니라 VLAN 불일치·포트 상태·잘못된 마스크·응답 손실을 검토해야 합니다.

동일한 접속 실패라도 먼저 찾아야 하는 이웃은 다릅니다
라우팅 판단로컬에서 찾는 MAC관측과 한계
B가 같은 링크B의 MACARP 미해결이면 선로 SYN 부재 가능
B가 원격 링크다음 홉 게이트웨이 MAC게이트웨이 전달 후 실패는 다른 구간
경로 자체 없음해당 경로의 다음 홉을 선택 못함로컬 소켓 오류일 수 있음; 외부 ICMP 필수 아님

운영체제의 “No route to host” 같은 오류 문구는 조사 시작점입니다. 라우팅 표에 항목이 없다는 원인 하나만 뜻한다고 읽지 않습니다. 이웃 해석 실패나 전달받은 오류가 응용에 비슷하게 표현될 수 있어요. 그 시점의 라우팅·이웃 테이블·인터페이스·스위치 기록을 같이 보세요.

8. ICMP 봉투 바깥과 안쪽의 실패 대상을 분리합니다

라우터 R=203.0.113.1이 전달 실패를 알린다고 정하겠습니다. ICMP(Internet Control Message Protocol)는 IP 전달 상태 등을 알리는 제어 메시지입니다. 이 예제에서 바깥 IPv4는 R→A이고, ICMP 안에는 실패한 A→B 패킷의 일부가 인용됩니다. 바깥 목적지가 A라고 해서 A의 포트 80이 실패했다는 뜻이 아닙니다.

합성 ICMP 인용의 구조 · IPv4 옵션 없음이라는 조건
바깥 IP: 203.0.113.1 → 192.0.2.40, Protocol=1
ICMP: Type=3, Code=1
인용 IP: 192.0.2.40 → 198.51.100.60, Protocol=6, IHL=5
인용 TCP 앞 8바이트: cf 08 00 50 00 00 a4 10
해독: 출발지 포트=53000, 목적지 포트=80, SEQ=42000

Type은 메시지 종류, Code는 그 종류 안의 세부 이유입니다. IPv4의 Type 3은 Destination Unreachable입니다. Code 0은 network unreachable, 1은 host unreachable, 3은 port unreachable, 13은 관리 정책상 통신 금지의 단서입니다. 예전 화면에 나타난 “unreachable” 한 단어를 읽는 대신 이 두 숫자와 인용을 확인합니다. TCP 닫힌 포트의 보통 응답인 RST와, ICMP Type 3 Code 3을 무조건 같은 TCP 동작으로 취급하지 않습니다.

인용 바이트의 cf08은 207×256+8=53000, 0050은 0×256+80=80입니다. 0000a410은 164×256+16=42000입니다. 첫 두 포트가 각각 2바이트, SEQ가 4바이트라 합계 8바이트입니다. 인용 IP의 IHL=5는 5×4=20바이트 IP 헤더이므로 TCP 시작은 인용 IP 시작에서 20바이트 뒤입니다. IHL이 6이면 24바이트 뒤로 이동해야 합니다.

최소 인용이 원래 IP 헤더와 그 뒤 8바이트뿐이면 TCP의 플래그·ACK·체크섬까지 모두 들어 있지 않습니다. 따라서 이 인용만 보고 원래 SYN 비트를 직접 확인했다고 쓰면 안 됩니다. 원래 패킷의 5튜플·SEQ·시각과 대조해 요청을 연결합니다. 더 많은 내용을 인용하는 장비도 있으므로 실제 길이를 읽어야 하고, 잘림과 비첫 IP 단편에서는 TCP 헤더가 없을 수도 있습니다.

이 단순 예제의 크기도 검산해 보죠. 바깥 IP 20+ICMP 앞머리 8+인용 IP 20+인용 TCP 8=IP 전체 56바이트입니다. Ethernet 헤더나 FCS를 더한 프레임 길이와 다릅니다. 56이라는 값은 옵션·추가 인용·확장 없는 자체 조건의 결과이며 모든 ICMP 길이가 아닙니다.

9. 정책 거절은 ICMP일 수도, RST일 수도, 침묵일 수도 있습니다

접속이 허용되지 않을 때 장비가 이유를 알려 주면 문제 구간을 찾기 쉬워집니다. 예를 들어 인용이 맞는 Type 3 Code 13이 R에서 돌아왔다면 “R이 정책 거절을 알렸다”는 가설이 강해집니다. 그래도 실제 정책 이름과 당시 적용 여부는 장비 로그와 구성으로 확인합니다. ICMP 출발지 주소는 메시지에 적힌 값이지 암호학적으로 검증된 발신자 신분이 아닙니다.

같은 차단 정책이라도 구현·설정에 따라 TCP RST, ICMP, 조용한 폐기 중 무엇이 나오는지가 다릅니다. 반대로 ICMP host unreachable은 그 시점의 전달 실패 보고이지 B가 영원히 존재하지 않는다는 자산 판정이 아닙니다. NAT 전후 인용에는 변환된 주소·포트가 반영될 수 있으므로 어느 쪽 캡처와 어느 변환 기록을 맞추는지도 명시하세요.

ICMP가 없다는 이유로 정책 장비가 없다고 하지 않습니다. 오류 메시지의 속도 제한이나 생성 억제, 역방향 경로의 손실, 수집 필터도 가능합니다. IPv6 ICMPv6는 다른 Type/Code 체계를 쓰므로 이 IPv4 숫자 표를 그대로 대입하지 않습니다. IPv6의 이웃 탐색도 ARP와 별도 절차입니다.

10. 조용한 차단은 유일한 무응답 원인이 아닙니다

방화벽이 아무 응답 없이 버리면 클라이언트는 재전송하다가 포기할 수 있습니다. 하지만 같은 모습은 응답 경로가 다른 곳으로 흐르거나 캡처 필터가 응답을 제외했을 때도 보입니다. 첫 확인은 필터를 풀어 원본 범위를 점검하는 것입니다.

방화벽 로그가 차단을 보여준다면 시각과 다섯 요소가 맞는지 확인합니다. 서버 캡처에서 SYN이 보이지 않는다면 경로 중 어디에서 사라졌는지 관측 지점을 늘릴 수 있습니다. 서버에 SYN이 있고 응답도 나갔는데 클라이언트에 없다면 응답 경로를 조사합니다. 한 번에 “방화벽 문제”라고 쓰기보다 관측 가능한 구간을 한 단계씩 좁혀 가세요.

11. 같은 SYN 세 번과 세 번의 새 연결 시도는 다릅니다

조용한 폐기 조건을 숫자로 읽어 봅시다. 다음은 자체 시간표이며 실제 캡처 출력이 아닙니다. 같은 A:53000→B:80, 같은 SYN SEQ 42000을 세 번 관측했다고 정합니다. 시각은 한 센서의 경과 초입니다.

가상 재시도 후보의 관측 시각 · 단위 초
관측경과 시각직전과 차이비교할 내용
첫 SYN0.250기준5튜플·SEQ42000
두 번째 SYN1.2501.250−0.250=1.000같은 SYN 번호의 재시도 후보
세 번째 SYN3.2503.250−1.250=2.000간격 증가; 응답 누락도 점검

첫 관측부터 마지막까지는 3.250−0.250=3.000초이고, 간격은 1초와 2초입니다. 1+2+3=6초로 더하거나 세 번째 시각을 재전송 간격 3.25초라고 부르면 기준점을 섞은 셈입니다. 세 패킷을 봤다고 응용의 전체 타임아웃이나 최종 포기를 관측한 것은 아닙니다. 수집이 그 전에 끝났을 수도 있습니다.

같은 번호와 5튜플·비슷한 옵션은 재시도 가설의 근거입니다. Timestamp나 IP 식별자 등은 바뀔 수 있으므로 전체 바이트가 같아야만 재전송인 것은 아닙니다. 반대로 SPAN 중복·병합한 캡처의 중복도 비교해야 합니다. 새 출발지 포트와 새 시작 번호면 새 시도 가능성을 살피고, 포트 재사용과 애플리케이션 재시도도 구분합니다.

운영체제의 재시도 횟수·간격·응용 제한 시간은 설정과 상태에 따라 다릅니다. 이 자체 1초·2초 예제를 모든 OS의 규칙이라고 외우지 않습니다. Wireshark의 TCP Retransmission 같은 분석 표시는 패킷 순서와 이전 관측에 의존하는 추론입니다. SYN/ACK가 수집 밖에서 돌아갔다면 한쪽 센서의 표시만으로 실제 종단이 무엇을 알았는지 확정할 수 없습니다.

12. 응답을 지운 필터로 무응답을 증명하지 않습니다

tcpdump -nn -tttt -S -r investigation.pcap 'tcp port 80 or icmp or arp'

tcp.flags.syn == 1 && tcp.flags.ack == 0
tcp.flags.syn == 1 && tcp.flags.ack == 1
tcp.flags.reset == 1
icmp.type == 3

첫 줄은 파일 읽기 절차 예시이며 이 파일을 실행했다고 제시하는 출력이 아닙니다. -r 뒤는 읽을 파일명, -nn은 호스트명과 서비스명 변환을 막아 주소·포트를 숫자로 보려는 옵션, -tttt는 날짜를 포함한 시각, -S는 절대 TCP 순서 번호 표시입니다. 따옴표 안은 캡처 필터 문법입니다. tcp port 80은 양방향의 TCP 출발지 또는 목적지 포트 80, or는 어느 하나가 맞아도 포함, icmp는 ICMPv4, arp는 ARP입니다.

왜 TCP만 고르지 않았을까요? port 80만 남기는 식은 ICMP 오류와 ARP를 제외할 수 있기 때문입니다. 심지어 SYN만 저장하면 SYN/ACK·RST를 관측하지 못한 것이 필터의 당연한 결과일 수 있습니다. -t로 시각을 숨기면 읽기는 짧아져도 이번의 간격·상관 분석에는 불리합니다. 처음부터 저장하지 않은 응답은 나중에 표시 필터를 풀어도 복구되지 않습니다.

뒤 네 줄은 Wireshark의 표시 필터로 첫 줄과 문법이 다릅니다. tcp.flags.syn과 tcp.flags.ack는 각 비트, reset은 RST, ==는 비교, 1은 설정·0은 미설정, &&는 두 조건의 동시 만족입니다. 첫 식은 SYN을 포함하고 ACK가 없는 후보이며 다른 모든 비트가 0이라는 정확 0x02 검사는 아닙니다. 두 번째는 SYN/ACK 후보, 세 번째는 모든 RST 후보, 마지막은 ICMPv4 도달 불가 종류를 고릅니다. Code를 추가로 읽고 인용 안의 TCP까지 펼쳐 보세요.

이 필터 묶음은 전체 증거의 대체품이 아닙니다. IP 단편·터널·VLAN·IPv6·캡처 길이와 디섹터 설정에 따라 단순 포트 조건이 필요한 레코드를 놓칠 수 있습니다. 원본의 더 넓은 범위를 보존하고 목적에 맞게 좁히세요. 설치한 도구 버전과 실제 필터 적용 결과도 따로 남겨야 합니다.

13. 보고서는 확인한 범위로 씁니다

“서버가 죽었습니다” 대신 “이 센서의 10초 관측 구간에서 동일 연결의 SYN 세 번을 확인했으며 대응 응답은 관측하지 못했습니다”라고 적으면 증거 범위가 분명해집니다. 이어서 차단·호스트 부재·경로·수집 문제를 가설로 적고 필요한 자료를 제시합니다.

워크북에서 외부 SYN/ACK만 다수 들어오는 상황도 같은 방식으로 봅니다. 출발지 위조에 따른 반사 응답, 비대칭 경로, 수집 누락을 구별해야 합니다. 위조 가설을 검토하더라도 SYN을 직접 보지 못한 상태에서 공격자를 특정하지 않습니다. 동일 ACK 값·대상 분포 같은 단서는 결론의 재료입니다.

14. 두 관측 지점으로 실패 구간을 좁히는 연습

시계가 정렬된 A측과 B측 센서가 있다고 해 봅시다. A측에는 SYN 송신, B측에는 그 SYN 수신과 SYN/ACK 송신이 보이는데 A측에 SYN/ACK가 없다면, “B가 전혀 응답하지 않았다”는 가설과 맞지 않습니다. B 이후의 반환 경로·A측 수집·로컬 방화벽을 우선 조사할 근거가 생긴 것입니다.

반대로 A측 SYN만 있고 B측에 없다면 두 지점 사이의 경로를 좁힙니다. 다만 B측 캡처가 올바른 NIC인지, 오프로딩·드롭·비대칭 라우팅·필터로 빠진 것은 아닌지 먼저 검증합니다. 모든 지점에서 안 보였다는 것을 증명하려면 각 지점의 관측 신뢰도도 설명해야 합니다.

가상 양단 대조 · 관측과 조사 대상을 분리
A측B측좁힐 구간과 추가 자료
SYN만같은 SYN 없음전달 경로·정책·B측 수집 신뢰도
SYN만SYN 수신·SYN/ACK 송신반환 경로·A측 수집과 로컬 정책
SYN/ACK 수신·ACK 송신마지막 ACK 없음ACK의 전달·상태·시각 정렬
시작 완료 후 데이터시작 완료·응용 오류TCP 이후 서버·응용·인증 기록

암호화로 데이터 본문을 못 읽어도 전송 구간과 시간·연결 수를 볼 수 있습니다. 반대로 패킷이 읽힌다고 사용자 인증·업무 성공을 모두 알 수 있는 것도 아닙니다. 실제 조사에서는 방화벽의 허용/차단 시각, NAT 매핑, 서버 수신 소켓과 응용 로그, 단말 연결 오류를 함께 요청합니다. DNS로 이름을 찾은 경우에는 리졸버 응답의 실제 목적지가 의도한 서버인지도 점검합니다.

15. SYN을 못 봤는데 SYN/ACK만 들어오면 무엇을 묻나요?

여러 외부 주소가 내부의 한 주소로 SYN/ACK를 보낸다고 가정합시다. 첫 가설은 내부 주소를 출발지로 위조한 SYN에 대한 반사 응답, 흔히 backscatter라고 부르는 현상입니다. 그러나 센서가 송신 경로를 보지 못했거나 수집 시작이 늦었거나 필터가 SYN을 제외했을 가능성도 남아 있습니다. 지문이 같은 응답을 봤다는 이유만으로 공격자를 특정할 수는 없습니다.

자체 숫자로 더 살펴보죠. 서로 다른 외부 응답이 모두 ACK=42001이라면, 데이터 없는 SYN을 확인한 응답이라는 조건에서 원래 SYN의 SEQ 후보는 42001−1=42000입니다. 이것은 공통 입력 번호 가설의 단서이지 위조 주체를 증명하는 서명이 아닙니다. SYN 데이터·번호 순환·구현·가짜 응답 여부가 다르면 이 단순 역산도 다시 검토해야 합니다.

내부 단말이 그 연결을 실제 시작했는지는 양방향 원본, 단말 소켓/프로세스 기록, 경계 장비의 송신·변환 기록으로 확인합니다. 응답의 출발지 분포·포트·ACK·시각·RST 반응을 함께 기록하고, “위조에 따른 반사 가능성”과 “그 내부 단말이 공격했다”를 분리하세요. 위조 주소는 피해자 주소일 수도 있습니다.

16. 신뢰성의 비용과 분석기의 재조립을 연결합니다

TCP는 연결 상태와 바이트 순서를 관리하고 손실에 대응해 신뢰성 있는 바이트 스트림을 제공합니다. 데이터가 여러 세그먼트로 나뉘면 받는 쪽은 순서대로 이어야 하며 분석기나 IDS/IPS도 스트림을 복원해야 내용을 비교할 수 있습니다. 순서 번호와 확인 번호, 버퍼·타이머·재전송이 이 기능의 비용입니다. TCP의 전달 확인은 응용이 데이터를 읽거나 저장했다는 별도 업무 확인을 대신하지 않습니다.

예를 들어 다음 기대 번호가 1001인데 [1501,1801) 300바이트가 먼저 보이면 앞의 [1001,1501) 500바이트가 비어 있습니다. 뒤에 데이터가 있어도 누적 ACK는 1001에 머물 수 있고 SACK은 뒤 구간 정보를 보탤 수 있습니다. 나중에 앞 500바이트가 도착하면 연속 구간은 [1001,1801) 800바이트, 다음 ACK는 1801로 이어집니다. 중복 ACK 하나를 무조건 원본 전체 패킷의 손실 증거로 읽지 않습니다.

센서와 종단이 겹친 바이트·잘못된 체크섬·옵션·시간 초과를 다르게 처리한다면 복원 결과가 달라질 수 있습니다. 이것이 탐지 우회 가능성을 검토하는 이유지만, 복잡한 패킷 하나를 봤다고 회피가 성공했다고 결론 내리지는 않습니다. 저장 바이트, 센서 재조립 설정, 종단 실제 수용과 응용 결과를 단계별로 대조해야 합니다. 이번에는 실제 IDS·대상 VM을 실행하지 않았습니다.

앞선 8강의 체크섬·길이·윈도와 9강의 MSS·옵션을 이번 응답 관측과 연결하면, “필드가 있다”→“패킷이 전달됐다”→“TCP가 수용했다”→“응용이 처리했다”의 증거 단계를 구분할 수 있습니다. 기존 워크북의 응답·생성 필드 요구와 연결하되 원본 문항 전체의 최종 대조와 실제 대상 수용 검증은 남겨 둡니다.

17. 복습 · 조건을 바꾸어 생각하기

질문 1. RST/ACK가 보이면 실제 서버 프로그램이 닫혔다고 확정하나요?

중간 장비의 능동 거절일 수도 있습니다. 응답 주체와 서버 상태를 대조합니다.

질문 2. ICMP가 없으면 방화벽이 없나요?

아닙니다. 정책·속도 제한·손실·비대칭 경로로 ICMP가 안 보일 수 있습니다.

질문 3. SYN/ACK만 들어오는 현상을 어떻게 기록하나요?

관측 범위를 명시하고 반사 응답·경로 차이·수집 누락 등의 가설을 자료로 검증합니다.

질문 4. SEQ가42000인 데이터 없는 SYN에 ACK42001이 오는 이유는?

SYN의 번호 공간1을 확인하므로42000+1+0=42001입니다. 실제 데이터1바이트가 있었다는 뜻은 아닙니다.

질문 5. SYN/ACK만으로 HTTP 성공을 말할 수 있나요?

시작 교환의 일부를 응답한 사실입니다. 마지막ACK·후속전달·실제응용응답과로그를 확인해야 하며 프록시 응답도 구분합니다.

질문 6. 모든RST가 RST/ACK여야 하나요?

아닙니다. CLOSED의 ACK없는입력에 대한RST/ACK와 ACK있는입력에 대한RST생성은 다릅니다. 입력RST에다시RST를보내지않는 규칙도 있습니다.

질문 7. 원격B에 보내는A가ARP로찾는MAC은?

라우팅표가선택한로컬다음홉의MAC입니다. 같은링크의B라면B의MAC을찾습니다. ARP실패는 선로SYN부재의한원인이지 호스트영구부재의확정이아닙니다.

질문 8. 최소ICMP인용의TCP8바이트에서SYN플래그를읽나요?

포트2+2와SEQ4까지만있다면 플래그위치까지들어있지않습니다. 원본요청과대조하고 인용길이·IP헤더길이를확인해야합니다.

질문 9. IHL이5에서6으로바뀌면인용TCP시작은?

인용IP시작+20에서+24바이트로4바이트이동합니다. 고정20으로읽으면옵션바이트를포트로오인할수있습니다.

질문 10. 세SYN시각0.250/1.250/3.250의간격과관측기간은?

직전차이는1.000초와2.000초, 첫관측부터마지막까지3.000초입니다. 전체접속타임아웃은관측종료만으로확정하지않습니다.

질문 11. 서버측SYN/ACK송신은보이는데클라이언트측은없다면?

서버무응답이라는결론과맞지않습니다. 반환경로·클라이언트정책·센서누락을점검하고 두센서시각과인터페이스의신뢰도를확인합니다.

질문 12. 여러SYN/ACK의ACK가42001이면위조주체를알수있나요?

조건부원래SYN번호후보42000을역산할수있을뿐입니다. 비대칭경로·늦은수집·필터·반사응답을함께검토하고 단말/경계기록으로확인합니다.

질문 13. 누적ACK1001에서뒤300바이트와앞500바이트가모두모이면?

뒤[1501,1801)와앞[1001,1501)의연속합은800바이트입니다. 다음기대번호는1801이며 응용처리성공과는별도입니다.
