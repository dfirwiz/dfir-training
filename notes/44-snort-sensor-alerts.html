학습 범위

셋째 날 5강에서는 탐지 센서가 트래픽을 읽고 경보를 남기는 과정부터 살펴봅니다. 1강에서 만든 정상 UDP 캡처는 입력 예시로 다시 사용합니다. 아래 경보 행은 읽는 법을 설명하기 위한 가상 기록입니다.

1. 경보 한 줄을 받으면 어디서부터 확인할까요?

대시보드에 같은 규칙의 경보가 여러 건 올라왔다고 해 봅시다. “침해가 여러 번 있었다”라고 바로 쓰기 전에 무엇을 세었는지부터 확인합니다. 센서가 몇 패킷을 보았는지, 그중 어느 규칙이 몇 번 일치했는지, 실제 단말에서 어떤 앱이 통신했는지는 서로 다른 질문입니다. 오늘은 입력이 어디에서 빠질 수 있고, 남은 경보 한 줄을 어떻게 원래 바이트에 연결하는지 봅니다.

건물 출입구의 카메라에 비유해 볼게요. 화면을 얻고, 사람과 출입 방향을 식별하고, 확인이 필요한 장면에 표시한 뒤, 관제 담당자가 출입 기록을 대조합니다. 카메라가 보지 못한 구역은 보고서에 나타나기 어렵죠. 네트워크에서는 한 요청이 여러 패킷에 나뉘고, 센서가 규격을 해석해 이어 읽으며, 암호화된 정보는 평문을 복원할 수 있는 조건이 있어야 분석할 수 있습니다.

2. 패킷 입력에서 결과까지 네 단계로 봅니다

IDS는 관측한 트래픽에서 조건에 맞는 사건을 찾는 침입 탐지 시스템입니다. 센서에 복제된 트래픽을 읽는 수동 배치에서는 경보와 기록을 남길 수 있습니다. IPS는 트래픽을 통과시키는 경로에 배치되고 엔진·입력 모듈·정책이 지원할 때 처리 여부에 관여합니다. 화면의 alert 항목을 차단 기록으로 읽으려면 실제 배치와 동작을 확인해야 합니다.

Snort의 입력 모듈을 설명할 때 DAQ라는 이름을 만납니다. DAQ는 엔진에 패킷을 전달하는 인터페이스 계층입니다. 예를 들어 -r로 저장 파일을 읽는 실습과, 운영 인터페이스의 복제 트래픽을 받는 배치는 출발점이 다릅니다. 캡처에 없는 방향이나 프레임 길이를 DAQ와 규칙이 복구할 수는 없습니다.

다음은 링크·IP·전송 헤더를 식별하는 디코더와, 패킷을 연결 단위로 다루는 구성 요소입니다. IP 조각이나 TCP 세그먼트를 이어 읽고 응용 서비스를 식별하면, 검사기(inspector)가 HTTP 경로 등 구조화된 검사 영역을 규칙에 제공할 수 있습니다. 모든 패킷의 모든 응용 데이터를 같은 방법으로 읽는다고 생각하지 마세요. 서비스가 식별됐는지, 필요한 설정이 켜져 있는지, 그 시점의 평문을 볼 수 있는지가 중요합니다.

3. 구성 파일은 어느 트래픽을 어떻게 볼지 정합니다

Snort 3의 대표 구성 파일은 snort.lua입니다. Lua는 구성에 쓰이는 언어이며 파일의 실제 경로는 배포 방법과 설치 위치마다 달라집니다. 기본 변수와 모듈 설정이 함께 제공되는 예제에서는 snort_defaults.lua를 불러오고, 자체 규칙과 정책을 별도로 관리할 수 있습니다. 교재의 고정 경로를 운영 환경의 실제 경로로 가정하지 마세요.

센서 위치에 따라 확인할 구성

예를 들어 안쪽 센서에서는 192.0.2.10이 보이지만 바깥쪽 센서에서는 주소 변환 이후의 다른 값만 보일 수 있습니다. 두 센서가 같은 규칙 파일을 쓰더라도 입력 주소와 HOME_NET이 달라지면 대상 집합이 달라질 수 있습니다. 정책 변수가 업무 구역 이름과 같아도, 엔진이 실제로 어떤 주소 집합으로 평가하는지 구성을 확인하세요.

설치 구성에 따라 기본값, 규칙 분류와 참조, 로깅, 이벤트 빈도 제어를 별도 파일로 포함할 수 있습니다. 공급 규칙 묶음을 가져온 뒤에도 대표 긍정·부정 샘플을 반복 점검하세요. 공급사 권고나 CVE 기록에서 보호 제품·서비스·공격 관측 범위를 읽고, 방어 규칙이 실제 센서에서 볼 수 있는 단서로 표현됐는지 검토합니다. 여기서 CVE는 공개 취약점에 부여되는 식별자입니다. 경보 제목에 CVE가 있어도 해당 시스템이 취약하거나 공격이 성공했다는 결론은 자산·패치·종단 자료가 필요합니다.

4. Snort와 Suricata는 같은 질문을 다른 구성으로 풉니다

예전 교재에서 Snort 2의 preprocessor라는 표현을 보더라도 Snort 3의 검사기 역할과 일대일로 대응시키지 마세요. Snort 3에서는 흐름과 서비스 식별을 바탕으로 연결에 필요한 검사기를 붙이는 구성이 쓰입니다. 정규화는 검사 대상의 일정한 표현을 만드는 과정입니다. 예를 들어 구조화된 URI 검사 영역과 수집 파일의 원래 바이트는 서로 다를 수 있습니다. 출력에서 어느 대상을 봤는지 구분해야 규칙이 일치한 이유를 설명할 수 있습니다.

Suricata도 탐지·프로토콜 분석과 구조화된 로그를 제공하는 별도의 엔진입니다. 두 엔진 사이에 비슷해 보이는 헤더와 옵션이 있지만 검사 영역의 이름, 서비스 식별, 구성 방식과 로깅은 버전별로 확인해야 합니다. Suricata의 EVE는 경보와 흐름, DNS·HTTP 등 서로 다른 이벤트를 JSON 레코드로 출력할 수 있습니다. Snort의 alert_json과 필드 이름이나 식별자가 같다고 가정하지 않습니다.

패킷 탐지 규칙은 그 엔진의 지원 필드와 수집 범위에서 판단합니다. 하루 동안 여러 내부 단말이 같은 이름을 찾았는지 확인하려면 기간과 호스트 단위로 DNS·흐름·경보를 묶고, 단말 기록과 연결합니다. Zeek 같은 프로토콜 관측 도구의 로그나 중앙 분석 시스템은 이 작업의 다른 근거를 제공합니다. 규칙 하나에 여러 호스트와 시간대의 결론을 전부 맡기지 않습니다.

5. 오프라인에서는 구성, 입력, 출력을 따로 확인합니다

1강의 정상 UDP 표본과 자체 규칙 파일을 사용할 때의 Snort 3 명령 예시입니다. practice.lua는 설치본과 맞춰 준비한 오프라인 실습 구성이고 local.rules는 같은 폴더의 교육용 규칙 파일입니다. 이름만 입력해서 이 파일들이 자동 생성되지는 않습니다.

snort -V
snort -T -c practice.lua -R local.rules
snort -c practice.lua -R local.rules -r signature-check.pcap -A alert_fast
snort -c practice.lua -R local.rules -r signature-check.pcap -A alert_json

-V는 버전 확인, -T는 설정 확인용 모드, -c는 구성 파일, -R은 추가 규칙 파일입니다. -r은 저장된 패킷 입력이고, -A 뒤에는 경보 출력 방식을 적습니다. alert_fast는 사람이 빠르게 읽을 수 있는 행, alert_json은 설정한 필드를 구조화해 처리하는 출력입니다. 아래 두 명령은 같은 입력을 서로 다른 출력 방식으로 비교하는 개별 실행입니다. 두 실행의 경보를 합해 고유 사건으로 세지 마세요.

현재 제작사 안내에서 두 로거의 표준 출력 방식과 파일 설정을 구분합니다. 예를 들어 JSON을 파일에 남기려면 로거의 파일 설정을 확인합니다. 표준 출력에 실행 진단이 함께 보일 수 있으므로, 전체 콘솔을 곧바로 JSON 데이터로 간주하지 않습니다. 옛 출력 예에 나온 Unified2 같은 형식은 그 도구·버전과 함께 읽고, 현재 설치본이 제공하는 로거와 저장 형식을 확인하세요. 이 페이지의 Snort 명령은 제작사 문법을 대조한 예이며, 이 환경에서는 엔진을 실행하지 않았습니다.

6. 경보의 식별자와 패킷으로 돌아가는 단서를 읽습니다

아래는 alert_json에서 쓸 수 있는 일부 필드의 의미를 설명하는 가상 기록입니다. 실제 출력의 필드 선택·순서와 시간 표기는 설정과 실행 파일에서 확인합니다.

{"pkt_num":1,"proto":"UDP","src_ap":"192.0.2.10:53000","dst_ap":"198.51.100.20:5514","rule":"1:1000040:1","action":"allow"}
{"pkt_num":5,"proto":"UDP","src_ap":"192.0.2.10:53000","dst_ap":"198.51.100.20:5514","rule":"1:1000040:1","action":"allow"}

pkt_num은 그 실행에서 패킷을 찾아갈 단서입니다. 다른 파일의 프레임 번호와 자동으로 같다고 판단하지 마세요. src_ap와 dst_ap는 각각 출발·목적 주소와 포트입니다. rule의 세 값은 순서대로 생성기 ID, 규칙 ID, 개정 번호입니다. 위 예는 같은 규칙과 개정이 두 레코드에 걸린 상황을 설명합니다. 분류·우선순위·메시지도 규칙과 구성의 설명이며, 그 값 자체가 감염 확인을 뜻하지 않습니다.

가상 행은 경보 2건, 고유 규칙 개정 1개, 고유 방향별 주소·포트 쌍 1개입니다. 이 숫자 어디에도 사용자 한 명이 공격했다거나 애플리케이션이 두 번 손상됐다는 근거는 없습니다. 실제 조사에서는 캡처와 로거의 시각·파일 식별자, 규칙 개정, 관련 패킷, 재조립 범위, 암호화와 수집 누락을 함께 확인합니다. 이어서 단말 프로세스·DNS·방화벽·서버 기록을 대조합니다.

복습 · 경보 유무를 어떻게 설명할까요?

1. 구성 검사만 통과했습니다. 규칙의 탐지도 검증됐나요?

구성 검사와 대상 입력을 평가하는 실행은 별개입니다. 의도한 파일과 규칙 개정을 쓰고 긍정·부정 표본에서 실제 결과를 확인합니다.

2. 같은 규칙 개정의 두 행이면 고유 사건도 두 개인가요?

두 경보 행을 봤다는 뜻입니다. 패킷·흐름·대상·시각으로 묶는 기준을 정한 뒤 어떤 단위를 세는지 보고합니다.

3. 센서 위치만 바뀌면 왜 경보가 달라지나요?

수집 방향, NAT 전후 주소, 캡처 누락, 복호화 가시성이 달라질 수 있습니다. 같은 구성이라도 입력이 달라지면 평가 결과도 달라질 수 있습니다.

4. 출력이 비었습니다. 먼저 무엇을 확인하나요?

파일과 설정이 로드됐는지, 읽은 패킷 수와 오류가 어떤지, 규칙이 활성인지, 출력·억제 설정이 무엇인지 봅니다. 이후 원래 바이트에서 조건을 대조합니다.

5. 수동 센서의 경보를 차단 성공으로 보고할 수 있나요?

경보는 해당 규칙의 관측을 기록합니다. 실제 차단을 말하려면 인라인 경로·동작·정책과 처리 기록을 함께 확인합니다.

6. 규칙 제목이 악성 DNS라고 적혀 있습니다. 무엇을 검증하나요?

실제 규칙이 고른 쿼리나 응답의 필드와 방향을 읽고, 해결자 로그와 단말 행위를 대조합니다. 분류 문자열만으로 활동 목적이나 침해를 결론내리지 않습니다.
