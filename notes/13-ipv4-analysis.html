1. 남은 헤더 필드로 어떤 질문에 답할까

12강에서 IPv4 헤더의 시작·길이·서비스 표시·IP ID를 읽었습니다. 이번에는 패킷이 어디까지 전달될 수 있는지, 내부 데이터를 어느 프로토콜로 해석할지, 헤더의 검사합이 맞는지, 주소와 옵션이 관측 환경에 어울리는지를 살펴봅니다. 필드를 외우는 데서 끝내지 않고 관측한 값 → 가능한 설명 → 추가로 확인할 증거를 연결하는 것이 목표입니다.

예를 들어 TTL이 1인 요청과 ICMP 오류가 함께 보인다면 ‘상대 서버가 응답하지 않는다’는 막연한 설명보다, 어느 라우터에서 전달 수명이 끝났는지 조사할 수 있습니다. 체크섬 경고가 있다면 실제 회선 오류인지 호스트에서 수집한 위치의 영향인지 구분해야 합니다. 사설 주소가 보이면 어느 인터페이스·NAT·VPN 단계인지부터 확인해야 합니다.

자료와 예시의 범위

별도 실습 PCAP과 워크북은 제공되지 않았습니다. 아래 주소·바이트·계산·도식은 문서용 주소 등을 사용한 자체 가상 예시입니다. 원본 실습을 실행한 결과가 아니며, 명령과 필터는 준비된 실제 자료에 적용할 때의 읽기 방법을 설명합니다. 확인하지 않은 결과를 만들어 채우지 않습니다.

2. 6~7번 바이트의 세 비트와 열세 비트

IPv4 시작을 0으로 센 6~7번 바이트는 16비트입니다. 앞 3비트는 Flags이고 뒤 13비트는 Fragment Offset입니다. Flags는 순서대로 예약 비트, DF, Don't Fragment, MF, More Fragments입니다. DF는 전달 중 단편화를 금지하는 표시, MF는 뒤에 더 이어지는 조각이 있음을 나타냅니다.

Offset은 재조립할 때 이 조각의 데이터를 어디에 놓을지 나타내며 단위가 8바이트입니다. 예를 들어 Offset 값이 100이면 원래 IP 데이터 영역의 100 × 8 = 800바이트 위치에서 시작합니다. 앞의 IP 헤더 길이를 이 값에 더해 원래 데이터 위치를 바꾸는 것은 아닙니다. 각 조각의 헤더와 원래 데이터 영역의 위치를 구별해야 합니다. 단편 크기·MTU·재조립 계산은 다음 회차에서 자세히 다룹니다.

단순 가상 값 0x4000 = 0100 0000 0000 0000을 나누면 예약0·DF1·MF0·Offset0입니다. DF와 Offset이 함께 들어 있다는 이유로 0x4000 전체를 조각 위치라고 읽으면 안 됩니다. 먼저 세 비트를 떼어 해석하고 나머지를 위치로 읽습니다. 이 조건은 지난 회차의 atomic 데이터그램 설명과도 연결됩니다.

예약 비트를 악성을 나타내는 ‘Evil Bit’로 소개한 RFC 3514는 만우절 농담입니다. 실제 공격 탐지 기능이나 정상적인 보안 인증 비트가 아닙니다. 드물거나 재미있는 필드 이름을 만났을 때도 표준의 성격과 실제 처리 규칙을 구분하세요. [1] [2]

3. TTL은 패킷이 끝없이 도는 것을 막는다

TTL, Time to Live은 IP 기준 8번 바이트의 8비트 필드입니다. 라우팅 루프가 생겨 패킷이 같은 장비 사이를 계속 돌더라도 영원히 남지 않도록 전달 수명을 제한합니다. 송신자가 초기 값을 넣고 라우터가 전달할 때 줄입니다.

실무에서는 보통 라우터를 지날 때 1씩 줄어드는 홉 제한으로 이해합니다. RFC 1812는 전달 시 적어도 1 감소해야 하고, 1초 이상 보유했다면 보유 시간에 따라 더 줄일 수 있다고 설명합니다. 역사적 단위가 초라고 해서 ‘TTL64는 캡처 시점부터 정확히 64초 뒤에 사라진다’고 계산해서는 안 됩니다. [3]

원문은 시간 측정의 어려움을 설명하면서 시계 동기화 문제를 언급하지만, 라우터가 자기 장비에서 보유한 시간을 재는 데 전 세계 장비의 시계가 같을 필요는 없습니다. 핵심은 이 필드가 절대 만료 시각이나 송신 시각을 담지 않는다는 점입니다. TTL 값만으로 실제 경과 초를 복원하지 않습니다.

TTL1인 패킷을 받은 라우터가 이를 다음 링크로 전달하려고 하면, 감소 후 0이 되므로 그 원래 패킷을 더 전달하지 않고 폐기합니다. 일반적인 조건에서는 송신자에게 ICMP Time Exceeded를 돌려보냅니다. 0인 TTL의 원래 데이터그램이 다음 라우터까지 정상 전달된다는 그림으로 이해하면 안 됩니다. 목적지가 라우터 자신인 경우와 그 너머로 전달하는 경우도 구별합니다.

TTL은 초기 값이 구현·설정·소켓·터널 처리에 따라 달라질 수 있습니다. 관측 TTL61에서 초기 값을64라고 가정하면 감소량은3이지만, 초기 값과 처리 경로를 확인하지 않았다면 실제 라우터 수를 확정할 수 없습니다. 특정 값이 익숙한 운영체제와 비슷하다는 것만으로 생성 OS나 공격자를 단정하지 않습니다.

4. ICMP 오류 안에 IP와 ICMP가 또 보이는 이유

원문 캡처는 TTL1인 ICMP Echo Request 뒤에 ICMP Type11·Code0, 즉 전송 중 수명 초과 오류가 돌아오는 사례입니다. TIMEX라는 약어를 보더라도 Time Exceeded를 줄인 표현으로 이해하면 됩니다. Type11의 다른 Code와 모두 같은 원인으로 묶지 않습니다. Code1은 단편 재조립 시간 초과의 경우입니다. [4]

오류의 바깥 IP 주소는 일반적으로 오류를 보낸 라우터와 원래 송신자 사이의 관계를 보여 줍니다. 그 안에는 오류를 일으킨 원래 패킷의 IP 헤더와 데이터 일부가 인용됩니다. 송신자가 자신이 보낸 어떤 통신 때문인지 연결할 수 있게 하는 정보입니다. 인용된 정보의 길이는 적용 규격·생성 장비·패킷·확장 등에 따라 확인해야 하며, 언제나 원래 패킷 전체가 들어 있다고 가정하지 않습니다.

따라서 Wireshark에서 IP와 ICMP 계층이 한 번 더 나온다고 곧바로 터널이나 이중 공격이라고 해석하지 않습니다. 인용된 원래 패킷인지 확인하고, 어느 계층의 주소·체크섬을 보고 있는지 기록합니다. 원래 요청의 식별 정보·길이·주소와 오류 인용을 대조하면 관계를 확인하는 데 도움이 됩니다.

TTL이 만료되었는데 캡처에 오류가 없다고 라우터가 무조건 규격을 어겼다고 할 수는 없습니다. ICMP 오류에는 생성하지 않아야 하는 경우가 있고, 빈도 제한·방화벽·비대칭 회신 경로·수집 누락도 영향을 줍니다. 응답 부재는 단독으로 차단 성공·무해함·목적지 부재를 증명하지 않습니다.

원문의 wireshark 파일명 & 형태는 저장 파일을 GUI로 열고 셸에서 백그라운드로 실행하는 예시입니다. 아래 명령의 sample.pcap은 예시 파일명이며, &는 Wireshark의 분석 옵션이 아닙니다.

wireshark sample.pcap &

# 아래는 Wireshark 표시 필터 예시
ip.ttl == 1
icmp.type == 11 && icmp.code == 0

첫 필터는 관측 TTL1을, 둘째는 전송 중 수명 초과 오류를 찾습니다. 인용된 패킷에도 IP 필드가 있을 수 있으므로 일치한 필드의 계층을 직접 펼쳐 확인합니다. 필터 일치만으로 원래 요청과 오류의 대응이 끝난 것은 아닙니다. [5]

5. Protocol 번호는 포트 번호가 아니다

IPv4 시작 기준 9번 바이트의 Protocol은 8비트로, IP가 운반하는 다음 프로토콜의 종류를 가리킵니다. TCP 목적지 포트80과 IP Protocol6은 다른 계층의 정보입니다. 모든 IP 내부 프로토콜에 TCP·UDP 같은 포트가 있는 것도 아닙니다.

IANA는 IPv4의 Protocol과 IPv6의 Next Header가 공유하는 번호 공간을 설명합니다. 그래서 같은 목록에 ICMPv6와 IPv6 확장 헤더 관련 값이 있어도 IPv4 패킷 안에 항상 그런 구조가 정상적으로 온다는 뜻은 아닙니다. IPv6에서는 다음 헤더 체인을 따라야 합니다. 목록의 이름과 실제 IP 버전·캡슐화를 함께 확인하세요. [6]

등록 범위를 고정하지 않기 · 2026년 11월 1일 확인

‘정의된 값은0~143’이라는 원문의 범위는 현재 등록 현황을 설명하기에 부족합니다. 현재 IANA에는146 Homa,147 BIT-EMU 같은 항목도 있습니다. 번호가 낯설다는 이유만으로 공격이라고 하지 않고, 미할당·실험·예약의 구분과 실제 장비의 지원·정책을 확인합니다. 레지스트리는 기능 등록부이지 우리 네트워크의 허용 목록은 아닙니다.

또한 IP Protocol을 보고 내부 헤더가 각 패킷의 바로 다음 바이트에 완전히 있다고 가정하지 않습니다. 단편의 뒤 조각이면 원래 TCP 헤더가 없을 수 있습니다. IHL·조각 위치·확보 길이를 확인한 뒤 내부 해석으로 들어갑니다.

6. 프로토콜 탐색과 방화벽 응답을 해석한다

여러 Protocol 값을 바꾸어 보낸 패킷은 어떤 IP 프로토콜이 허용·지원되는지 탐색하는 정황일 수 있습니다. 포트를 바꾸는 TCP·UDP 포트 탐색과 구별합니다. 정상 진단·승인된 점검과 공격이 모두 비슷한 패턴을 만들 수 있으므로 출발 장비·승인·대상·전후 활동을 확인해야 합니다.

대상에서 지원하지 않는 프로토콜을 받으면 조건에 따라 ICMP Destination Unreachable Type3·Code2, Protocol Unreachable이 돌아올 수 있습니다. 이것은 UDP의 Port Unreachable Code3과 다릅니다. 중간 장비가 먼저 폐기했거나 오류 생성 제한이 있으면 응답이 없을 수 있습니다. 응답 없음은 그 프로토콜이 열려 있다는 확정 증거도, 모두 차단됐다는 증거도 아닙니다. 공식 Nmap 설명도 응답과 ICMP 오류별 해석을 구분합니다. [7]

tcpdump -r sample.pcap -nt
tcpdump -nn -tttt -r sample.pcap

첫 명령은 원문 형태처럼 저장 파일을 읽는 -r, 주소 이름 변환을 막는 -n, 시각을 숨기는 -t입니다. 둘째는 포트 등도 숫자로 표시하는 -nn과 날짜·시각을 보여 주는 -tttt를 사용합니다. 시간과 오류를 대응시킬 때는 시각을 보존하고, 실제 시간대와 수집 위치도 기록합니다. 이 명령은 스캔을 실행하지 않습니다. [8]

Windows와 IPv6에 관한 정정

‘Windows의 IPv4 방화벽은 잠겼지만 IPv6 방화벽은 완전히 열려 있다’는 설명을 현재 일반 규칙으로 사용하지 않습니다. Microsoft 공식 문서는 Windows Firewall이 기본 활성화되며, 요청된 통신이나 허용 규칙에 해당하지 않는 수신을 기본 차단한다고 설명합니다. ICMP와 ICMPv6의 규칙을 별도로 구성해야 하는 경우도 안내합니다. 실제 프로필·주소 범위·규칙·정책과 처리 로그를 확인해야 합니다. [9] [10]

허용 여부를 시험했다면 확인한 주소 계열·프로토콜·방향·인터페이스·프로필을 한 문장에 명시하세요. IPv4의 결과를 IPv6 전체로 옮기거나 제품 기본값을 조직의 실제 설정이라고 가정하지 않습니다.

7. 체크섬은 어떤 바이트를 검사하는가

체크섬, checksum은 정해진 범위의 바이트로 계산한 오류 검출 값입니다. IPv4의 Header Checksum은 IP 시작 10~11번 바이트에 있으며, 옵션까지 포함한 IPv4 헤더만 검사합니다. IP 뒤의 TCP·UDP·ICMP 데이터까지 이 값으로 검증하지 않습니다.

목적지 주소 등이 우연히 손상된 패킷을 그대로 전달하면 잘못된 경로로 보내게 될 수 있습니다. IPv4 수신 처리에서 잘못된 헤더 검사합은 폐기 대상이며, 정상 전달을 위해 TTL을 바꾸면 헤더가 달라져 검사합도 갱신해야 합니다. 모든 홉에서 패킷 전체를 다시 암호화한다는 뜻은 아닙니다.

검사합이 맞는다고 바이트가 전혀 바뀌지 않았거나 신뢰할 송신자가 보냈다고 증명되지는 않습니다. 서로 다른 데이터가 같은 검사합을 만들 수 있고, 의도적으로 내용을 바꾼 사람이 다시 계산할 수도 있습니다. 이는 인증 서명이나 암호학적 무결성 검증과 다른 목적입니다. 원문의 ‘변하지 않았음을 보장’하는 표현은 오류 검출의 제한된 의미로 읽어야 합니다.

8. 1의 보수 합을 중간 단계부터 계산한다

인터넷 체크섬을 계산할 때는 해당 체크섬 필드를0으로 놓고 데이터를16비트 묶음으로 읽습니다. 묶음들을 더한 뒤 상위로 넘친 자리올림을 하위16비트에 다시 더하는 end-around carry를 처리하고, 마지막16비트 합의 비트를 반전한 값이 체크섬입니다. RFC1071은 이를 1의 보수 합으로 설명합니다. [11]

12강의 가상 헤더 A를 이어 쓰겠습니다. 실제 PCAP에서 얻은 출력이 아니라, 문서용 주소192.0.2.10→198.51.100.20인 IP 헤더20바이트입니다. 아래는 계산할 때 체크섬 자리를0000으로 둔16비트 단어입니다.

4500 0054 0000 4000 4001 0000 c000 020a c633 6414

일반 정수 합 = 0x2b1a6
하위 16비트 0xb1a6 + 넘친 값 0x2 = 0xb1a8
16비트 반전 = 0xffff - 0xb1a8 = 0x4e57

체크섬을 포함한 헤더
45 00 00 54 00 00 40 00 40 01 4e 57 c0 00 02 0a
c6 33 64 14

0x2b1a6에서 앞의2가16비트를 넘어간 부분입니다. 이것을 버리지 않고0xb1a6에 더해0xb1a8로 접습니다. 다시 넘친 값이 있으면 같은 처리를 반복합니다. 그 결과를 반전해4e57을 넣습니다. 원문의 각 묶음을 먼저 뒤집는 설명보다, 합산→자리올림 되돌림→최종 반전으로 계산하면 순서를 일관되게 따라가기 쉽습니다.

수신 검증은 체크섬까지 포함해 같은 합을 구합니다. 이 예제는 접힌 합 0xb1a8 + 0x4e57 = 0xffff이므로 검사에 맞습니다. 구현이 마지막 반전까지 해 결과0인지 검사하는 방법도 같은 관계입니다. ‘생성 결과가ffff여야 한다’와 ‘검증에서 체크섬을 포함한 합이ffff’라는 문장을 혼동하지 마세요.

원문의 주석은 이를 실제로는2의 보수 연산이라고 설명하지만, RFC1071이 말하는 것은 2의 보수 기계에서도 자리올림을 되돌려1의 보수 합을 구현한다는 것입니다. 알고리즘을2의 보수 체크섬으로 바꾸지 않습니다. 또한 이 예제의 체크섬이 유효하다는 것은 헤더 계산을 검증했다는 뜻이며, 원래 회선에서 실제 전달되었다는 뜻은 아닙니다.

9. TTL을 하나 줄이면 무엇을 갱신할까

앞 헤더에서 TTL64는0x40, Protocol1은0x01로 연달아 있으므로16비트 묶음이 0x4001입니다. TTL을63으로 줄이면0x3f01이 됩니다. 차이는 0x4001 - 0x3f01 = 0x0100입니다. 헤더가 변했으므로 기존4e57을 그대로 두면 검사합이 맞지 않습니다.

다른 필드가 모두 같은 이 예제에서는 새 접힌 합이 0xb1a8 - 0x0100 = 0xb0a8, 반전 값이 0xffff - 0xb0a8 = 0x4f57입니다. 따라서 TTL63·검사합4f57의 헤더를 검증하면 다시ffff가 됩니다. 이것은 이 값에서의 계산 예시이며, 모든 변경을 단순 덧셈 하나로 일반화할 때는 자리올림과0 표현 등 규칙을 확인해야 합니다.

TTL만 바뀐 일반 라우팅에서 TCP 체크섬까지 반드시 바뀌는 것은 아닙니다. TCP의 검사 범위에 IP TTL이 들어 있지 않기 때문입니다. 반대로 NAT로 IP 주소나 포트를 바꾸면 IP 헤더뿐 아니라 관련 TCP·UDP 검사합에도 영향을 줄 수 있습니다. 어떤 바이트를 바꾸었는지 먼저 정하고 각 계층의 범위를 따라갑니다.

IPv6와 UDP 예외도 범위를 지켜 읽기

IPv6 기본 헤더에는 IPv4와 같은 헤더 체크섬이 없습니다. 그렇다고 오류 검출이 모두 사라지는 것은 아니며 TCP·UDP·ICMPv6 등의 검사와 링크 계층 처리는 별도입니다. IPv4 UDP에서 체크섬0은 검사합 미사용을 나타낼 수 있습니다. IPv6 UDP는 일반적으로 체크섬이 필요하지만, RFC6936처럼 제한된 터널 환경의0 체크섬 적용 조건도 별도로 존재합니다. ‘모든 프로토콜·모든 계층이 언제나 같은 방식으로 검사한다’고 묶지 않습니다. [12] [13] [14]

10. 체크섬 경고와 IDS·IPS의 무경고를 조사하는 순서

캡처에서 체크섬 오류가 보이면 첫 질문은 ‘공격인가’보다 어디에서 어떤 상태의 바이트를 수집했는가입니다. 송신 호스트의 운영체제가 체크섬 계산을 NIC에 위임하면, 캡처는 NIC가 최종 값을 넣기 전의 데이터를 볼 수 있습니다. 이를 checksum offloading이라고 합니다. 실제 회선에서 잘못된 값이 전송되었다는 뜻과 다릅니다. [15]

가령 단말 수집본에서는 오류가 보이는데 외부 관측 지점의 대응 패킷에서는 정상이라면, 수집 위치와 오프로딩으로 설명할 가설이 생깁니다. 하지만 이 역시 대응 패킷·시각·처리 설정을 확인한 뒤 판단해야 합니다. 모든 오류를 오프로딩이라고 일괄 무시하거나, 반대로 모두 실제 손상으로 분류하지 않습니다. 잘린 캡처에서는 내부 데이터 전체의 검사합을 검증할 바이트가 부족할 수도 있습니다.

Wireshark의 validation disabled는 검증이 꺼졌다는 상태이지 정상 검증을 통과했다는 뜻이 아닙니다. 어떤 계층이 검증되었는지와 계산 범위를 따로 확인합니다. ICMP 오류 화면에 나오는 바깥 IPv4·ICMP·인용 IPv4의 검사 상태도 서로 구분합니다.

원문이 강조한 ‘대상과 탐지기의 처리 차이’는 중요한 분석 관점입니다. 대상은 버리는 입력을 탐지기는 정상으로 해석하거나, 대상이 처리한 통신을 센서가 버리면 결과가 달라질 수 있습니다. 다만 수동 IDS가 네트워크 전달 자체를 차단한다는 뜻은 아닙니다. IDS의 분석 제외, 인라인 IPS의 폐기, 대상 호스트의 수신 폐기는 서로 다른 조치입니다.

Suricata 공식 문서와 설정 예시에도 체크섬 검증과 수집 방식별 설정이 있습니다. 실제 버전·설정·수집 모드에 따라 해석해야 하며, ‘모든 IDS/IPS가 무조건 같은 기본값으로 폐기한다’고 하지 않습니다. 검증을 끄는 것을 만능 해결책으로 삼기보다 필요한 관측 정확성과 대상 처리의 일치를 확인합니다. [16]

규칙에 맞는 것 같은데 경고가 없다면 검사합과 저장 길이, 센서의 도달·수집 여부, 필터, 재조립, 규칙 조건·방향과 실제 처리 로그를 차례로 대조합니다. 검사합이 맞다고 규칙이 반드시 일치하는 것도 아니고, 경고가 없다고 공격이 실패하거나 무해한 것도 아닙니다.

11. 주소의 이상 여부는 ‘어느 경계인가’에서 시작한다

IPv4 출발지는 IP 기준12~15, 목적지는16~19번의 각4바이트, 즉32비트입니다. 192.0.2.10 같은 표기는 각 바이트를10진수로 읽어 점으로 나눈 형태입니다. 이 주소만으로 실제 사용자·호스트 소유권·실행 프로그램을 확정하지 않습니다.

원문은 외부에서 내부 주소를 출발지로 주장하는 패킷이나, 내부에서 자기 조직 것이 아닌 주소를 출발지로 내보내는 패킷을 주의하라고 설명합니다. 이는 주소 위조와 잘못된 경로를 조사하는 유용한 출발점입니다. 그러나 먼저 관측 지점이 공용 인터넷 경계인지, 사내 링크인지, VPN 안쪽인지, NAT 전후인지 정해야 합니다.

예를 들어 VPN 장비에서 안쪽 사설 주소를 본 것과, 공용 인터넷 인터페이스에서 예상하지 않은 사설 출발지를 본 것은 같은 경고 조건이 아닙니다. 후자는 누출·위조·경로 오류를 조사할 이유가 되지만 전자까지 무조건 공격으로 표시하면 정상 연결을 오탐할 수 있습니다. 문서용 예제 주소 역시 실제 운영 인터넷의 정당한 주소로 배포하라는 뜻이 아닙니다.

목적지가 우리 주소가 아닌데 들어왔다면 원문처럼 조사할 이유가 있습니다. 다만 트랜짓 라우팅·부하분산·DNAT·캡슐화·미러링 구성이 있는지 확인해야 합니다. 여러 조직의 트래픽을 전달하는 장비와 단일 서버는 기대되는 주소 집합이 다릅니다.

12. 출발지 검증은 중요하지만 모든 DDoS를 막지는 않는다

출발지 주소 검증은 해당 링크나 고객·조직에서 나올 수 있는 주소를 기준으로 부적절한 출발지를 제한하는 방식입니다. BCP38은 이런 필터링으로 출발지 위조를 사용하는 공격의 영향을 줄이는 원칙을 설명합니다. 외부에서 내부 주소를 사칭하는 유입뿐 아니라, 내부에서 허용되지 않은 주소로 나가는 유출 방향도 운영 경계에 맞게 검토합니다. [19]

예를 들어 같은 시각의 자산·할당·경로 정보를 보면 그 인터페이스에서 관측한 출발지가 가능한지 검증할 수 있습니다. 불일치가 있으면 공격 외에도 NAT 위치 착각, 잘못된 할당·라우팅, 공급자 연결·트랜짓 설정 등을 조사합니다. 가능한 원인을 나열하는 데서 끝내지 않고 DHCP·인터페이스·라우팅·방화벽 기록으로 어느 설명이 맞는지 확인해야 합니다.

다중 회선이나 비대칭 경로에서는 출발지로 돌아가는 최선 경로가 수신 인터페이스와 다를 수 있습니다. 그래서 역방향 경로 검사 같은 기능을 엄격하게 적용하면 정상 트래픽까지 거절할 수 있습니다. 실제 토폴로지·경로와 적용 방식의 전제를 맞추는 일이 중요합니다. [20]

이런 검증을 했다고 모든 DDoS 참여가 차단되지는 않습니다. 위조하지 않은 실제 출발지로도 악성 요청이나 대량 통신이 가능하기 때문입니다. 원문의 ‘위조 주소를 막으면 DDoS 참여를 방지한다’는 설명은 위조 기반 공격을 줄이는 효과로 한정합니다. 통신량·응용 요청·단말 프로세스·서비스 영향의 검증은 계속 필요합니다.

13. 끝자리가0·255라는 이유만으로 판단하지 않는다

네트워크 주소와 브로드캐스트 주소를 구분하려면 주소만이 아니라 프리픽스 길이·서브넷 마스크가 필요합니다. 가상 네트워크192.0.2.0/24에서는 호스트 비트가8개입니다. 모두0이면192.0.2.0, 모두1이면192.0.2.255이며 일반적인 이 서브넷에서 각각 네트워크·브로드캐스트 주소로 해석합니다.

반면 RFC3021을 적용하는 가상 지점 간 링크192.0.2.254/31은 두 주소192.0.2.254와192.0.2.255를 끝점에 사용할 수 있습니다. 이 문맥에서는 192.0.2.255를 /24의 브로드캐스트라고 처리하면 안 됩니다. 192.0.2.0/31의 지점 간 링크에서도 끝자리0인 주소를 같은 전제로 끝점에 사용할 수 있습니다. 마지막 한 바이트만 보고 결론을 내리면 잘못된 경보를 만들 수 있습니다.

특수한 /31 지점 간 링크처럼 전제가 다른 사용도 있습니다. 모든 프리픽스에 같은 호스트·브로드캐스트 공식을 기계적으로 적용하지 않습니다. 외부 주소의 실제 프리픽스를 모른다면 패킷에 쓰이지 않은 마스크를 임의로 가정해 ‘브로드캐스트 공격’이라고 확정하지 마세요. [21]

14. 옵션은 길이를 따라 읽고 종류별로 판단한다

IP 옵션은 기본 헤더20바이트 뒤에 있고, IHL로 정해진 헤더 끝까지만 읽습니다. 한 옵션의 Type·Length·내부 값을 확인하고 그 Length로 다음 경계를 찾습니다. Type0인 End of List와 Type1인 NOP는 한 바이트 형식이며 일반적인 길이 필드가 없습니다. 전체 헤더가4바이트 경계에 맞도록 정렬하는 것과, 각 옵션 하나하나가 반드시4바이트 길이라는 주장은 다릅니다.

End of List는 옵션 목록의 끝이고, NOP는 한 바이트를 건너뛰며 정렬 등에 사용할 수 있습니다. 헤더 끝까지의 남은 패딩을 새로운 다중 바이트 옵션처럼 해석하지 않습니다. 옵션의 길이가 남은 헤더 범위를 넘거나 필요한 제어부보다 작다면 잘림·손상·잘못된 생성·디코딩을 대조해야 합니다.

15. Loose·Strict Source Route에서 확인할 것

일반 경로에서는 라우터가 목적지와 정책으로 다음 홉을 정합니다. Source Route 옵션은 송신자가 경로에 관한 정보를 제공한다는 차이가 있습니다. Loose는 지정된 지점들을 거쳐야 하되 그 사이에 다른 라우터가 있을 수 있고, Strict는 지정 다음 지점에 대한 직접 연결 등 엄격한 조건을 요구합니다. 다만 이를 모든 물리 장비·터널 내부의 실제 홉까지 완전하게 통제한다는 뜻으로 확대하지 않습니다.

바이트를 읽을 때 중요한 정정이 있습니다. 주소 목록이0x83이나0x89 바로 다음 바이트부터 시작하는 것은 아닙니다. 그 뒤에는 Length와 Pointer 제어부가 먼저 옵니다. Type·Length·Pointer의3바이트 다음에 주소 데이터를 해석합니다. 12강의 Record Route처럼 Pointer 기준과 길이를 먼저 읽어야 합니다. 형식 정의를 건너뛰면 길이·포인터 값을 라우터 주소의 일부로 오인합니다. [1]

경로 정보가 되돌아가는 응답에 반영될 수 있다는 원문의 설명은 역사적 처리 규칙의 문맥으로 읽습니다. 실제 회신에서 옵션이 유지·거절·무시되었는지와 경로 정책을 확인하지 않고 ‘응답도 반드시 공격자가 정한 경로로 돌아갔다’고 가정하지 않습니다.

이런 옵션을 악용해 경로 정책의 전제를 흔들거나 원치 않는 지점을 거치게 하려는 시도는 조사할 가치가 있습니다. 그러나 옵션이 보였다는 이유만으로 경로 장악·본문 변조·높은 공격자 숙련도를 입증한 것은 아닙니다. 정상 점검·사전 제작 자료·자동 도구도 가능합니다. 실제 장비 수용·전달·회신·단말 활동을 검증해야 합니다.

RFC7126은 Source Route 등 옵션별 필터링과 운영 영향을 다룹니다. ‘인터넷에서는 전부 무시하고 내부에서는 전부 받아들인다’는 보편 규칙은 없습니다. 해당 장비의 설정·지원·로그와 실제 경로를 확인하세요. 암호화가 정상이라면 우회 경로에 있다는 사실만으로 TLS 본문을 평문으로 읽거나 임의 변조할 수 있는 것도 아닙니다.

16. 관측과 판단을 나누어 기록한다

현대에도 IP 필드는 중요합니다. 암호화된 본문을 읽지 못해도 TTL·ICMP 오류·프로토콜·주소·옵션과 관측 지점별 변화로 전달 문제를 좁힐 수 있습니다. 다만 오류 검출 값이나 주소 표시는 실제 프로그램과 사용자의 정체, 메시지의 의미를 대신하지 않습니다.

패킷으로 확인 가능한 사실

관측 TTL·Protocol·주소·Flags·Offset·검사합과 계산 범위, ICMP Type/Code와 인용 바이트, 옵션의 Type/Length/Pointer, 여러 지점의 대응 패킷 변화입니다.

단독으로 확정할 수 없는 부분

초기TTL·전체 경로·오류 응답 부재의 원인, 실제 회선 손상과 오프로딩의 구분, 주소 소유권·사용자·프로세스, 방화벽 전체 정책, 공격자 숙련도·암호화 본문의 의미·최종 침해 영향입니다.

함께 확인할 자료

수집 위치·잘림·오프로딩·손실 설정, 라우팅·NAT·VPN·주소 할당, 방화벽·IDS/IPS 실제 처리, 인터페이스·프로필·옵션 정책, 단말·서버·프로세스 로그와 시각을 맞춘 다른 지점의 캡처입니다.

가상 요청의 TTL은1이며 R이 보낸 ICMP Type11/Code0이 원래 요청의 일부를 인용한다. 이 자료는 R에서 전달 수명이 끝난 흐름을 설명한다. 목적지 서버의 응용 처리나 사용자 활동은 확인하지 않았다. 별도 가상 헤더의 검사합4e57은 헤더 계산에 맞지만 실제 회선 전송·송신자 신뢰를 인증하지 않는다.

17. 복습과 독립적인 분석 연습

원문의 마지막 페이지는 별도 IPv4 워크북 연습을 안내합니다. 워크북 문제·PCAP이 이번에 제공되지 않아 해당 실습의 수행과 정답을 검증하지 못했습니다. 아래는 같은 범위의 필드·계산·증거 판단을 점검하는 자체 문제입니다.

질문 1: 6~7번 바이트가0x4000이면 조각 위치가16,384바이트일까요?

해설: 아닙니다. 예약0·DF1·MF0·Offset0으로 나눕니다. 세 비트를 제외한13비트가 조각 위치이며, 원래 데이터 영역 기준8바이트 단위입니다.

질문 2: TTL1인 원래 패킷은 첫 라우터를 지나 TTL0으로 다음 라우터에 갈까요?

해설: 일반 전달 상황에서는 감소 후0이 되어 더 전달하지 않고 폐기됩니다. 조건에 맞으면 별도의 ICMP 오류가 돌아옵니다. 목적지가 장비 자신인 경우와 전달 동작은 구별합니다.

질문 3: 오류 안에 IP와 ICMP가 다시 보이면 터널일까요?

해설: 원래 오류 유발 패킷의 인용일 수 있습니다. 바깥 오류의 주소·Type/Code와 안쪽 원래 주소·식별 정보를 구별해 대응시킵니다. 인용에 언제나 전체 원본이 있다고 보지 않습니다.

질문 4: Protocol17은 UDP의 목적지 포트17이라는 뜻일까요?

해설: IP가 다음 데이터를 UDP로 넘기라는 종류 표시입니다. UDP 헤더에 있는 포트와 다른 값입니다. 17은16진수0x11이며 단편 상태·IHL도 확인해야 합니다.

질문 5: 체크섬이 맞으면 본문과 송신자도 신뢰할 수 있을까요?

해설: IPv4 검사합은 헤더만 검사하고, 값이 맞아도 충돌·재계산 가능성이 있어 인증이 아닙니다. 본문·상위 프로토콜·인증 검증은 별도입니다.

질문 6: 합0x2b1a6에서0xb1a6만 남기고 반전해도 될까요?

해설: 넘친2를 되돌려0xb1a8로 만든 뒤 반전해야4e57이 됩니다. TTL64→63이면 이 예제의 새 검사합은4f57이며 체크섬을 포함한 접힌 합은ffff입니다.

질문 7: 단말 캡처의 checksum bad는 회선 손상일까요?

해설: 실제 손상일 수 있지만 NIC 오프로딩 전 수집일 수도 있습니다. 대응 패킷을 다른 지점과 비교하고 잘림·검증 상태를 확인합니다. validation disabled는 검증 성공이 아닙니다.

질문 8: 목적지192.0.2.255는 언제나 브로드캐스트일까요?

해설:192.0.2.0/24에서는 그렇지만 RFC3021을 적용한 지점 간192.0.2.254/31에서는 끝점 주소로 쓸 수 있습니다. 마스크·프리픽스와 링크 조건을 확인해야 합니다.

질문 9: Source Route 옵션이 보이면 공격 성공과 높은 숙련도를 확정할까요?

해설: 옵션 존재·형식·실제 수용·전달 경로·응용 영향은 다른 증거 단계입니다. Type 다음의 Length·Pointer를 먼저 읽고 실제 장비 정책·이력을 검증합니다.

추가 연습: 원문 덤프의 남은 헤더를 해석하는 목표에 맞춰, 8절의 가상 헤더를 처음부터 읽어 보세요. 45는 Version4/IHL5, 0054는 전체 길이84, 0000은 ID0, 4000은 DF1/Offset0, 40은 TTL64, 01은 ICMP, 4e57은 헤더 검사합입니다. 뒤의 각4바이트는 문서용 출발지·목적지 주소입니다. 이렇게 읽은 결과에 실제 ICMP 본문이나 수신 성공을 덧붙이지 않는 것이 연습의 마지막 단계입니다.
