이번 실습 범위

셋째 날 3강에서는 HTTP 응답 본문과 메일 첨부에서 파일 바이트를 꺼내는 과정을 봅니다. 아래 주소·이름·문구는 독립적인 가상 예제입니다. 분석할 캡처와 그로부터 추출한 파일은 서로 다른 증거로 관리합니다.

1. 화면에서 파일명이 보였으면 파일도 확보했을까요?

“단말이 어떤 파일을 받았는지 확인해 주세요.” 이런 요청을 받으면 먼저 다운로드 요청을 찾고 싶겠죠. 요청 경로가 /status/note.txt라고 해서 실제 답변에 그 파일의 본문이 있었다는 뜻은 아닙니다. 서버가 오류를 보냈을 수도 있고, 응답은 있었지만 그 구간을 센서가 놓쳤을 수도 있습니다. 오늘은 요청, 응답, 추출된 바이트, 단말에 저장된 파일을 차례로 확인해 봅니다.

우편함에서 여러 장으로 나뉘어 온 안내장을 모아 읽는다고 생각해 보세요. 표지의 제목, 배달 기록, 각 장의 내용, 최종으로 묶은 사본은 각각 다른 정보입니다. 다만 TCP는 문서의 페이지 번호가 아니라 바이트 위치를 관리합니다. 같은 바이트가 재전송될 수 있고, 그 위의 HTTP가 본문의 구간을 다시 나눕니다. 패킷의 경계만 보고 파일의 경계를 정하면 머리말을 내용에 붙이거나 내용 일부를 놓치기 쉽습니다.

2. 패킷, 스트림, HTTP 객체에는 서로 다른 경계가 있습니다

재조립은 나뉘어 저장된 데이터를 프로토콜 규칙에 따라 이어 읽는 작업입니다. 먼저 TCP의 두 방향에서 순서 번호를 보고 각각의 바이트 흐름을 구성합니다. 이어서 HTTP의 요청과 응답을 읽어 헤더와 본문을 구분합니다. 객체는 여기서 응용 프로토콜의 해석기가 추출 대상으로 식별한 바이트 묶음을 뜻합니다.

예를 들어 헤더가 가리키는 본문 길이가 14바이트라면, 헤더가 끝난 바로 다음부터 그 길이를 읽습니다. 데이터의 TCP 순서 번호가 501부터라면 바이트 범위는 [501,515)이고, 끝 515는 포함하지 않습니다. 8바이트와 6바이트로 나뉘어 와도 연속 범위가 전부 있으면 본문은 14바이트입니다. 앞쪽 8바이트가 재전송된 경우 관측된 페이로드를 더하면 22바이트처럼 보이지만 재조립한 본문은 여전히 14바이트입니다.

3. HTTP 객체를 선택하고 원래 교환을 다시 확인합니다

Wireshark에서 저장 캡처를 열고 File → Export Objects → HTTP로 들어갑니다. 목록에서 패킷 번호, 호스트명, 콘텐츠 유형, 크기, 파일명을 보고 후보를 고릅니다. 패킷 번호는 추출 결과를 원래 패킷 목록으로 되돌아가 확인하는 실마리입니다. 본문이 여러 프레임에 걸쳐 있다는 점을 함께 기록하세요. 파일 이름이 같은 결과가 여러 개라면 디렉터리를 분리하거나 프레임 번호를 포함한 이름을 써서 구별합니다.

가상 사례에서 클라이언트가 docs.example에 보낸 요청과 서버 응답의 일부는 아래와 같습니다. 표시를 쉽게 하려고 요청과 응답을 따로 적었습니다. 빈 줄은 HTTP 헤더가 끝난 자리이고, 본문의 마지막 줄바꿈은 LF 1바이트입니다.

GET /status/note.txt HTTP/1.1
Host: docs.example

HTTP/1.1 200 OK
Content-Type: text/plain
Content-Length: 14

training-only

GET은 그 경로의 표현을 요청하는 메서드입니다. 200은 이 응답에서 읽은 상태 코드이고, Content-Type은 서버가 주장하는 본문 형식입니다. Content-Length는 이 예제의 단순한 HTTP/1.1 응답에서 전송할 본문 바이트 수입니다. training 8 + 하이픈 1 + only 4 + LF 1 = 14바이트입니다. 스크린샷에서 줄바꿈이 보이지 않아도 마지막 바이트가 빠지면 파일은 13바이트가 됩니다.

조건을 바꿔 볼까요? 206 Partial Content면 해당 HTTP 응답은 범위의 일부일 수 있고, Content-Range로 어느 구간인지 확인합니다. Transfer-Encoding: chunked로 전달한다면 각 조각 크기 표기와 구분 줄은 재조립된 본문이 아닙니다. Content-Encoding: gzip은 표현에 압축이 적용됐다는 뜻입니다. 압축된 전송 바이트와 풀린 파일의 크기·해시가 다를 수 있으므로 어떤 표현을 내보냈는지 기록합니다.

4. 목록이 비어 있거나 파일이 깨졌을 때

실패처럼 보이는 화면에서 확인할 다음 근거
관측가능한 설명되돌아갈 지점
HTTP 목록이 비어 있음암호화, 해석기 미적용, 지원하지 않는 형식, 응답 미수집 가능성수집 위치와 방향, TLS 여부, 실제 응답 프레임과 프로토콜 해석
내보낸 길이가 기대와 다름TCP 공백·짧게 저장된 프레임, HTTP 범위 응답 또는 표현 변환스트림의 누락 표시, 본문 경계, 길이·범위·인코딩 헤더
정렬 뒤 고른 행과 결과의 내용이 어긋남행·파일명이 비슷하거나 도구 동작이 기대와 다를 수 있음원래 프레임·스트림, 내보낸 바이트, 설치 버전 재확인
이름은 PDF지만 내용이 다르게 보임이름이나 MIME 유형이 실제 형식과 다를 수 있음파일 시작 바이트, 길이, 형식 검사 결과와 응답 헤더

오래된 교재의 추출 프로그램 오류 사례가 오늘의 도구에도 그대로 있다는 뜻은 아닙니다. 그 사례에서 가져올 원칙은 행을 고른 뒤에도 원래 프레임과 내보낸 파일이 대응하는지 확인하는 것입니다. TCP 재조립과 HTTP 해석 설정, 중복·중첩 데이터의 처리 방식도 기록하세요. HTTPS의 앱 본문은 캡처에 충분한 데이터와 권한 있는 복호화 자료가 있을 때만 확인할 수 있습니다. 443번 포트만으로 파일이나 프로토콜 버전을 확정하지 않습니다.

설치한 TShark에서 지원되는 객체 유형과 내보내기 옵션을 먼저 확인합니다. 아래는 공식 문법을 대조한 파일 읽기 예입니다. practice-http.pcap은 학습자가 준비한 캡처를 가리키는 예시 이름입니다.

tshark --export-objects help
tshark -r practice-http.pcap --export-objects http,review-http

-r은 저장 파일을 읽는 옵션입니다. --export-objects 뒤의 쉼표 왼쪽은 추출할 프로토콜, 오른쪽은 결과 폴더입니다. 여기서는 별도 작업 폴더에 저장하는 용도입니다. TShark가 이 예시 파일을 실제 읽었다고 가정하지 말고, 설치 환경에서는 버전과 출력 파일 수, 선택한 원래 프레임을 함께 기록하세요.

5. 객체 목록에서 못 찾으면 메일의 MIME 경계를 읽습니다

메일 교환이 캡처에 있지만 첨부가 객체 목록에 없다고 합시다. 먼저 해당 TCP 흐름에서 Follow → TCP Stream으로 대화를 살펴봅니다. 메일 본문을 보낸 방향과 관심 구간을 골라 작업용 사본으로 저장합니다. 바이너리 값을 유지해야 하는 내보내기에서는 GUI의 표시용 문자열을 복사하는 것과 별도 저장을 구별하세요. SMTP 명령·서버 응답과 DATA의 메시지 영역도 서로 다릅니다. 이 예제는 SMTP 프레이밍이 이미 제거된 메시지 사본을 사용합니다.

MIME은 메일 메시지에서 본문과 첨부 같은 여러 부분의 형식·인코딩을 나타내는 규격입니다. multipart/mixed는 여러 부분이 하나의 메시지에 들어 있음을 뜻합니다. boundary는 그 부분을 갈라 주는 문자열입니다. 헤더에 쓴 값이 sample-boundary라면 각 경계 줄은 --sample-boundary, 마지막 경계 줄은 뒤에도 두 하이픈을 붙입니다. 경계 줄과 각 부분의 헤더는 첨부의 데이터가 아닙니다.

MIME-Version: 1.0
Content-Type: multipart/mixed; boundary="sample-boundary"

--sample-boundary
Content-Type: text/plain

Training message
--sample-boundary
Content-Type: text/plain
Content-Disposition: attachment; filename="note.txt"
Content-Transfer-Encoding: base64

dHJhaW5pbmctb25seQo=
--sample-boundary--

Content-Disposition은 이 부분이 첨부임을 표시하고 filename은 보낸 쪽이 제공한 이름입니다. Content-Transfer-Encoding: base64는 바이너리 값을 전송 가능한 문자로 표현한 방식입니다. 암호화가 아니고, 복원할 때 헤더의 빈 줄 뒤에서 다음 경계 전까지만 뽑습니다. 실제 메시지에 부분이 여러 겹이라면 같은 경계가 속한 수준부터 구분하고, 중첩이 복잡할 때는 MIME 파서의 결과와 원래 메시지의 경계를 비교하세요.

SMTP의 일반 DATA 대화에서는 수신 측에서 점으로 시작하는 줄의 전송용 이스케이프 처리를 고려하고, 메시지 끝 표식을 본문에 넣지 않습니다. STARTTLS 뒤가 암호화됐거나 캡처가 메시지 중간부터 시작하면 추출에 필요한 평문이나 MIME 헤더가 없을 수 있습니다. 그럴 때는 캡처에서 보인 정보와 메일 서버가 보관한 권한 있는 메시지 사본을 나누어 기록합니다.

6. 본문만 디코딩하고 길이·형식·해시를 남깁니다

위의 한 줄짜리 가상 Base64 데이터만 빈 작업 폴더의 part.b64에 저장합니다. 헤더, 경계, 전송 명령은 넣지 않습니다. 실제 메시지의 원본 바이트를 바꾸지 말고, 텍스트 사본에서 CRLF와 LF의 차이를 확인하세요. CRLF는 두 바이트, LF는 한 바이트입니다. 남은 CR 때문에 쓰는 도구가 입력을 거부한다면, Base64로 분리한 작업용 텍스트의 줄 끝을 정리한 다음 처음부터 다시 확인합니다. 디코딩된 바이너리 파일의 줄 끝까지 바꾸면 해시와 내용이 달라집니다.

base64 -d part.b64 > decoded.bin
wc -c < decoded.bin
file -- decoded.bin
sha256sum -- decoded.bin

-d는 디코딩, >는 표준 출력을 새 결과 파일로 보내는 기호입니다. 출력 경로가 이미 있다면 덮어쓸 수 있으니 빈 작업 폴더에서 예제를 실행합니다. 실패한 디코딩이 부분 파일을 남길 수 있으므로 종료 상태를 확인한 다음에 나머지 명령을 실행하세요. wc -c는 바이트 수, file은 파일 형식의 단서, sha256sum은 파일의 SHA-256 해시를 계산합니다. --는 뒤의 이름을 옵션으로 해석하지 않도록 구분합니다.

가상 첨부를 실제로 디코딩해 14바이트를 확인했습니다. 예제 HTTP 본문과 같은 값을 쓰므로 두 바이트 묶음의 SHA-256은 같습니다. 같은 해시는 두 사본의 내용이 일치한다는 근거로 쓸 수 있지만, 어느 단말에서 그 파일을 열었는지는 증명하지 않습니다.

운영 자료의 추출물은 먼저 바이트와 해시를 점검합니다. 확장자나 아이콘을 믿고 열거나 미리보기·썸네일 기능이 켜진 일반 환경에 두면 의도치 않게 분석 대상이 처리될 수 있습니다. 특히 알 수 없는 실행 파일이나 문서는 격리된 승인 분석 환경에서 취급합니다. 보고에는 캡처 식별자, 시각과 방향, 원래 프레임, 추출 방식, 길이·해시, 예상 구간이 빠진 이유를 남기세요.

복습 · 추출을 확인하고 관측의 한계를 적어 보세요

1. TCP의 두 프레임에 8바이트와 6바이트가 있고 8바이트가 다시 보였습니다. 객체 길이는?

재전송이 이미 있던 위치를 채운 것이면 고유 본문 길이는 14바이트입니다. 세 프레임 길이의 합은 수집한 데이터량일 수 있어도 객체 길이가 아닙니다.

2. 응답이 206이고 14바이트만 저장됐습니다. 파일 전체를 얻었나요?

응답의 범위와 전체 길이를 함께 봅니다. 14바이트가 어떤 부분인지 Content-Range로 확인하고, 다른 구간이 빠졌다면 부분이라고 기록합니다.

3. MIME 헤더와 경계까지 넣고 디코딩하면 되나요?

그 문자열들은 전송 구조를 설명합니다. 첨부 부분의 헤더 뒤에서 경계 전까지만 분리해 Base64를 복원합니다.

4. 유형이 PDF라고 표시되면 무엇을 더 확인하나요?

헤더의 주장, 실제 시작 바이트와 형식 검사, 크기·해시를 맞춰 봅니다. 특히 새로 확보한 운영 자료는 격리된 방식으로 분석합니다.

5. 같은 해시의 파일이 두 추출 경로에서 나왔습니다. 실행도 확인했나요?

확보한 두 사본의 바이트가 일치한다는 근거입니다. 단말에 저장하거나 실행한 사실은 프로세스, 파일 이벤트, 앱 로그 등에서 확인해야 합니다.

6. 객체가 하나도 없었습니다. 다음에는 무엇을 하나요?

수집한 위치·방향·시각과 응답 구간이 포함됐는지 먼저 확인합니다. 그다음 TCP 재조립, 응용 해석, 암호화 여부, 앱·서버 로그를 대조합니다.
