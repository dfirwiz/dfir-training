1. 작은 통신은 되는데 파일 전송은 왜 멈출까

VPN 연결은 살아 있고 짧은 요청도 성공하는데, 큰 파일을 받기 시작하면 전송이 멈춥니다. 이때 곧바로 암호화 오류나 공격을 의심하기보다 패킷을 감싸면서 늘어난 길이가 경로의 전송 한도에 맞는지 확인할 필요가 있습니다. 작은 패킷은 지나가고 큰 패킷만 문제가 생기는 조건을 MTU와 연결해 설명할 수 있기 때문입니다.

VPN은 떨어진 네트워크 사이에 논리적인 통신 경로를 만드는 기술입니다. 이번에는 원래 IP 패킷을 보호해 다른 IP 패킷 안에 담는 IPsec 터널 모드를 중심으로 봅니다. 모든 VPN이 같은 헤더·암호화·전송 방식을 사용하는 것은 아닙니다. 원문의 워크스테이션·라우터·VPN 게이트웨이·전달망·반대편 게이트웨이·파일 서버 그림의 학습 포인트는, 양단이 보는 원래 패킷과 중간망이 운반하는 패킷의 크기가 다르다는 것입니다.

학습 범위와 실습의 한계

터널의 안팎 헤더, MTU·DF·MSS, 손실·재조립 시간 초과를 설명하고 단편화 학습을 종합합니다. 워크북과 첫째 날 PCAP 여섯 개·621기록의 대조는 이전 검토 기록에서 확인했습니다. 이번에는 본 교재의 해당 네 페이지 이미지·OCR과 공식 자료를 직접 대조했으며, 원본 PCAP과 워크북 실습을 재실행하지 않았습니다. 아래 주소·수치·도식·관측 상황은 자체 구성한 가상 예시이며, 실제 VPN이나 운영체제에서 실행한 결과가 아닙니다. 마지막 실습 안내 페이지에는 문제 본문이 없어 원래 실습의 정답이나 완료를 주장하지 않습니다.

로그인 화면은 열리는데 다운로드만 멈춘다면

원격 근무자가 “VPN 로그인도 되고 서버 첫 화면도 열려요. 그런데 자료만 받으면 멈춰요”라고 알려왔다고 해 보겠습니다. 연결 여부를 묻는 질문에는 이미 답했지만, 어떤 크기의 데이터를 어느 방향으로 보냈는지는 아직 모릅니다. 로그인 성공과 큰 파일 전송 성공은 다른 시험입니다. 작은 제어 메시지가 지나간 사실은 그보다 큰 모든 패킷이 지나간다는 보장이 되지 않습니다.

여행 가방을 보호 케이스에 넣는 장면을 떠올려 보세요. 가방 자체는 규격에 맞아도 케이스를 씌우면 바깥 치수가 늘어납니다. “원래 가방은 규격에 맞았는데요?”라는 말은 맞지만, 운반 구간은 케이스를 포함한 크기를 검사합니다. 터널도 비슷합니다. 다만 실제 네트워크는 케이스를 잘라 보내기만 하면 끝나는 구조가 아닙니다. 조각을 다시 모아야 하고, 분할 금지 조건과 오류 피드백·암호화 검증도 있습니다. 비유로 크기 관계를 잡은 뒤 실제 헤더와 처리 순서로 돌아오겠습니다.

이번 회차의 목표는 특정 장비의 MTU 값을 외우는 것이 아닙니다. “어느 계층의 길이를 계산했는가, 어느 방향의 설정이 적용되었는가, 개선을 어떤 증거로 확인할 것인가”를 설명하는 것입니다. 앞선 조각 계산을 장애 원인과 변경 결과를 검증하는 도구로 써 보세요.

2. 안쪽 패킷은 그대로여도 바깥쪽 길이는 늘어난다

터널에 넣기 전 패킷을 안쪽 패킷, 터널 구간을 건너기 위한 새 IP 패킷을 바깥쪽 패킷이라고 부르겠습니다. 안쪽 주소는 원래 통신 상대를 나타내고, 바깥쪽 주소는 VPN 게이트웨이 사이 전달에 사용될 수 있습니다. 바깥쪽 주소를 곧바로 파일 전송을 시작한 프로그램이나 원래 서버의 주소로 기록하지 않습니다.

예를 들어 문서용 단말 192.0.2.10과 서버 198.51.100.20 사이의 통신을, 바깥쪽 게이트웨이 203.0.113.10과 203.0.113.20 사이에서 운반한다고 가정합니다. IPsec의 ESP는 보호된 내용을 운반하는 형식입니다. 바깥 IP 헤더, ESP 관련 정보, 사용 조건에 따른 초기화 값·인증 태그·패딩, NAT 통과를 위한 UDP 캡슐화 등이 추가 길이를 만들 수 있습니다. 정확한 구성은 실제 모드와 암호화 방식에 따라 확인해야 합니다. [1] [2]

배송 상자에 보호 포장을 덧씌우는 상황과 비슷합니다. 원래 상자가 한도에 정확히 맞았다면 포장 후에는 한도를 넘을 수 있습니다. 다만 네트워크에서는 넘친 부분을 임의로 잘라 버릴 수 없습니다. 분할·폐기·크기 조정 중 어떤 처리를 할지는 IP 버전, DF, 터널 정책과 PMTU 처리에 달려 있습니다.

수집 위치가 달라지면 같은 통신의 주소도 달라집니다

캡슐화는 원래 데이터를 다른 전달 형식 안에 담는 처리입니다. IPsec은 IP 통신에 보호 기능을 제공하는 체계이고, ESP는 Encapsulating Security Payload의 약자입니다. 여기서는 안쪽 IP 패킷 전체를 터널의 보호 대상으로 삼습니다. 평문 측에서 보던 단말·서버 주소와 터널 구간에서 보이는 게이트웨이 주소는 역할이 다릅니다. 암호화된 안쪽 주소·포트가 중간 수집에 그대로 보인다고 가정하지 마세요. [1] [2]

관측 B에서 보이는 바깥 출발지203.0.113.10은 보호 패킷을 내보내는 게이트웨이의 역할입니다. 원래 파일 요청자는192.0.2.10일 수 있습니다. 그렇다고 시간상 가까운 두 기록을 크기만으로 일대일 대응시켜도 된다는 뜻은 아닙니다. 여러 안쪽 흐름이 같은 터널을 공유할 수 있으므로 양쪽 캡처의 시각·방향과 게이트웨이의 처리 문맥을 함께 봐야 합니다.

패딩은 알고리즘이나 정렬 조건 등에 맞추어 덧붙이는 바이트입니다. 인증 태그는 보호된 내용의 무결성 검증 등에 쓰이는 값이고, 초기화 값은 암호 처리에 사용하는 입력입니다. 어떤 항목이 얼마나 전송되는지는 선택한 방식에 따라 달라집니다. ESP라는 이름만 보고 고정 길이를 더하거나, “암호화했으니 무조건 원래 데이터 길이가 일정 비율로 늘어난다”고 계산하지 않습니다. [2]

3. 길이 예산 계산: 1500에 80을 더하면

MTU는 해당 링크에서 단편화 없이 운반할 수 있는 IP 패킷 크기의 한도이고, PMTU는 경로에서 제약이 되는 IP 전송 크기입니다. 이번 가상 모델에서는 바깥쪽 경로 한도를 1500바이트, 안쪽 패킷을 감쌌을 때의 총 추가 길이를 80바이트로 고정합니다. 80은 계산을 위한 가정이며 IPsec의 공통 상수나 권장값이 아닙니다. 실제 패딩과 전송 방식에 따라 길이는 달라질 수 있습니다.

안쪽 IP 전체 1500 + 가정한 추가 길이 80 = 바깥 IP 전체 1580
바깥쪽 경로 한도 1500보다 1580−1500 = 80바이트 큼
이 모델에서 허용할 안쪽 IP 전체 = 1500−80 = 1420바이트

안쪽 1500이 이미 IP 헤더를 포함한다는 점이 중요합니다. 여기에 안쪽 IP 헤더 20을 또 더하지 않습니다. 반대로 바깥 IP 헤더를 포함한 추가 길이를 80으로 정했으면 그 바깥 헤더를 다시 한 번 더해서도 안 됩니다. 어떤 범위를 더하고 빼는지 먼저 정의하면 중복 계산을 피할 수 있습니다.

만약 이 1580바이트의 바깥 IPv4 패킷을 헤더20·DF0 조건에서 최대한 채워 단편화한다고 가정하면, 바깥 IP 데이터는 1580−20=1560입니다. 첫 조각 데이터1480, 끝 조각 데이터80으로 나뉘어 IP 전체1500과100이 됩니다. 끝 조각의 원시 Offset은 1480÷8=185, MF는0입니다. 합계1600은 원래 바깥1580보다 새 IP 헤더20만큼 큽니다.

이 계산은 가능한 처리 하나를 설명할 뿐입니다. 실제 게이트웨이가 반드시 이 두 조각을 보낸다고 예측하는 결과가 아닙니다. 터널에 넣기 전 안쪽을 분할하는지, 보호 후 바깥쪽을 분할하는지, 폐기·ICMP 피드백을 하는지와 추가 길이의 변화를 실제 자료에서 확인해야 합니다.

길이 예산을 네 칸으로 나누면 중복 계산을 줄일 수 있습니다

바깥 한도를 P, 안쪽 IP 전체를 L, 바깥 IP 헤더까지 포함한 총 추가 길이를 O라고 적어 보겠습니다. 세 값의 단위는 모두 바이트입니다. 이 단순 모델에서 L+O≤P이면 크기 한도 안에 들어갑니다. ≤는 작거나 같다는 기호입니다. 따라서 허용할 안쪽 전체의 상한은 P−O입니다. 실제 O가 패딩 등으로 달라지면 그 조건까지 확인해야 하며, 한 패킷에서 구한 O를 모든 길이에 무조건 재사용하지 않습니다.

항목추가80 가정추가96 가정
바깥 경로 한도 P1500바이트1500바이트

기본 IPv4/TCP 데이터 예산1420−20−20=1380바이트1404−20−20=1364바이트
안쪽1500을 그대로 감싼 전체1580바이트, 80 초과1596바이트, 96 초과

첫 행의1500과 안쪽1500은 숫자는 같아도 검사 대상이 다릅니다. 모든 물리 링크가1500이어도 그 위에 터널을 씌우면 안쪽 예산은 더 작아질 수 있습니다. 반대로 실제 바깥 경로에 충분한 여유가 있거나 이미 안쪽 크기를 줄였다면 같은 형태의 장애가 나타나지 않을 수 있습니다. “VPN을 쓰면 반드시 단편화된다”라는 결론으로 바꾸지 마세요.

바깥1580을 두 조각으로 나누는 예제에서 마지막100은 헤더20과 데이터80을 합친 값입니다. 누락된80바이트를 마지막 조각의 전체100과 혼동하지 않아야 합니다. 조각 구간은 [0,1480)과 [1480,1560), 원래 바깥 IP 데이터 끝은1560입니다. 보호된 데이터의 이 좌표를 안쪽 TCP 데이터의 위치로 바로 읽지 않습니다.

4. 안쪽 DF와 바깥쪽 DF를 따로 읽어야 한다

DF(Don’t Fragment)는 IPv4에서 해당 패킷의 전달 중 단편화를 금지하는 비트입니다. 안쪽 IPv4 헤더와 바깥쪽 IPv4 헤더가 각각 있으면 DF도 서로 다른 헤더에 존재합니다. 안쪽 DF1 하나를 보았다는 이유만으로 바깥 구간에서 단편이 절대 생기지 않는다고 결론 내릴 수 없습니다.

원문의 일반화 보완 — 2026년 11월 2일 확인

그렇다고 ‘VPN에서는 안쪽 DF가 아무 의미 없다’고 일반화해서도 안 됩니다. RFC4301 §8.1은 안팎이 IPv4인 터널 모드 SA에서 DF를 설정·해제·안쪽에서 복사하는 처리의 구성을 설명합니다. SA는 보호 통신에 사용할 알고리즘·키·처리 조건 등을 정하는 보안 연결의 문맥입니다. 어떤 정책이 실제로 적용되었는지 확인해야 합니다. [1]

가상 안쪽 DF1·바깥 길이 초과 상황의 조건부 해석

두 번째 행에서도 원래 송신자까지 피드백이 반드시 잘 전달된다고 보장하지 않습니다. 터널 종단은 바깥 경로의 문제를 안쪽 통신의 크기 문제와 연결해야 하고, ICMP가 필터링되거나 전달 경로가 달라질 수도 있습니다. 안쪽·바깥쪽 캡처와 게이트웨이의 PMTU·폐기 기록을 함께 봅니다.

IPv6에는 IPv4와 같은 DF 비트가 없습니다. 바깥이 IPv6라면 ‘DF를 끄면 라우터가 나눠 주겠지’라는 접근이 맞지 않습니다. RFC8200의 송신 측 단편화와 경로 크기 처리로 돌아가 확인해야 합니다. [3]

DF를 묻기 전에 어느 헤더인지 적어 두세요

안쪽 단말은 자신의 IPv4 패킷에서 DF를 설정할 수 있고, 게이트웨이는 새 바깥 IPv4 헤더를 만듭니다. RFC4301이 설명하는 복사 정책이라면 안쪽 DF1이 바깥 DF1로 이어질 수 있습니다. 바깥 DF를 해제하는 정책이라면 결과가 달라질 수 있습니다. 두 조건을 섞어 “원래 DF는 중요하지 않다” 또는 “DF1이면 어느 층에서도 조각이 없다”라고 말하지 않는 것이 핵심입니다. 실제 SA와 장비 정책을 먼저 확인합니다. [1]

DF1인 바깥1580을 한도1500 구간에 보낸 가상 조건에서는 경유 라우터가 그 패킷을 나누어 전달할 수 없습니다. 폐기와 단편화 필요 알림을 검토해야 합니다. 하지만 이 조건 계산은 실제 알림이 어느 지점에서 생성·허용·수집되는지를 보장하지 않습니다. IPv6 바깥 터널이라면 DF 필드 자체가 없으며, 경유 라우터가 단편화하지 않는 규칙과 송신 터널 종단의 처리를 따로 봅니다.

5. PMTUD는 단편을 만들기보다 크기를 맞추기 위한 과정

PMTUD(Path MTU Discovery)는 경로에 맞는 전송 크기를 알아내는 접근입니다. 고전적인 IPv4 방식에서는 DF를 설정한 패킷이 경로 한도를 넘을 때, 라우터가 버리고 ICMP Destination Unreachable Type3·Code4로 단편화가 필요하다는 정보를 알릴 수 있습니다. 송신 측은 받은 정보를 바탕으로 이후 크기를 줄입니다. DF 자체가 경로의 한도를 자동으로 계산하는 것은 아닙니다. [4]

작은 요청은 성공하지만 큰 전송에서 응답이 멈추는 가상 사례에서는, 크기 초과와 ICMP 전달 실패로 인한 PMTU 블랙홀을 가설로 둘 수 있습니다. 블랙홀은 필요한 전달·피드백이 관측되지 않아 통신이 진행되지 않는 상황을 뜻합니다. 하지만 서버 부하·정책·수집 누락 등도 가능하므로 이 패턴만으로 원인을 확정하지 않습니다.

예제의 바깥1500 한도와 추가80이 맞다면 안쪽1420으로 줄이는 계산이 출발점이 됩니다. 실제로는 안쪽 송신자가 올바른 한도를 학습했는지, 터널 종단에서 바깥 피드백을 처리했는지, 방향별 경로가 같은지, 재연결·경로 변경 뒤에도 값이 유효한지를 봅니다. ICMP를 보았다는 사실과 PMTU 학습 성공은 다른 결론입니다.

현재의 데이터그램 전송에서는 RFC8899의 DPLPMTUD도 함께 이해할 수 있습니다. 패킷을 만드는 계층에서 탐색과 전달 확인을 통해 적절한 크기를 찾는 방법입니다. UDP 위 프로토콜·응용에 맞는 지원이 필요하며 모든 UDP 프로그램이 자동으로 이 기능을 제공하는 것은 아닙니다. 이 표준은2020년 문서이므로2021년 이후 새로 생긴 기술로 소개하지 않습니다. [5]

피드백을 받은 뒤 크기가 달라졌는지까지 확인합니다

고전적인 IPv4 PMTUD의 ICMP3/4에는 Next-Hop MTU라는 다음 링크의 한도 정보가 실릴 수 있습니다. 이 값도 IP 헤더와 데이터를 합친 크기이며 Ethernet 헤더까지 합친 회선 길이는 아닙니다. 오류에 인용된 원래 IP 헤더와 데이터를 연결해, 이번 흐름에 대한 피드백인지부터 확인하세요. 오래된 형식은 한도 값이0일 수도 있으므로0을 “MTU0으로 보내라”는 지시로 읽지 않습니다. [4]

관측 B에서 바깥 패킷에 대한 오류를 보았다면 그 수신자는 터널 게이트웨이일 수 있습니다. 게이트웨이가 그 정보를 안쪽 경로의 유효 크기로 반영했는지, 안쪽 송신자가 이후 크기를 조정했는지는 추가 확인입니다. 오류가 한 번 보인 사실만으로 전체 피드백 연결이 성공했다고 말하지 않습니다. 반대 방향은 다른 경로를 지날 수 있어 한 방향의 성공을 그대로 복사할 수도 없습니다.

크기를 줄인 뒤 전송이 진행되었다면 PMTU 가설을 지지하는 관측이 됩니다. 그래도 같은 시각에 정책·경로·부하가 달라졌는지 확인해야 합니다. DPLPMTUD 역시 적절한 탐색과 전달 확인을 지원하는 프로토콜 문맥이 필요합니다. 임의의 UDP 데이터그램 하나를 보냈고 응답이 없다는 사실만으로 경로 한도를 알아냈다고 보고하지 않습니다. [5]

6. MTU를 낮추는 방법과 적용 범위

첫 번째 대응 방향은 터널에 넣기 전부터 안쪽 패킷을 적절한 크기로 만드는 것입니다. 인터페이스 MTU나 경로 설정을 조정하면 TCP만이 아니라 그 인터페이스를 사용하는 IP 전송의 크기 판단에 영향을 줍니다. 예제에서는1420을 검토할 수 있지만, 이는 실제 터널 조건을 측정하기 전 모든 단말에 배포할 권장값이 아닙니다.

원문이 소개한 DHCP를 통한 MTU 전달도 이런 접근입니다. DHCP는 주소와 관련 네트워크 설정을 전달하는 프로토콜이며, RFC2132의 옵션26(Interface MTU)은 인터페이스에서 사용할 MTU를16비트 값으로 전달합니다. 값의 길이는2바이트입니다. 예를 들어1420은 5×256+140=1280+140이므로16진수 0x058c입니다. 이 값은 설정 정보이지 실제 터널의 측정 결과가 아닙니다. [6]

서버에 옵션을 넣었다고 모든 장치에 적용되는 것은 아닙니다. 클라이언트가 해당 옵션을 지원하고 수용했는지, 갱신이 이루어졌는지, 정적 설정·다른 인터페이스·관리 정책이 우선하는지를 확인합니다. IPv4 DHCP 옵션 하나가 IPv6나 모든 경로의 설정을 대신하지도 않습니다.

인터페이스 전체 한도를 낮추면 VPN을 쓰지 않는 트래픽에도 작은 패킷을 만들게 할 수 있습니다. 같은 데이터에 필요한 패킷 수와 헤더 비중이 늘어날 수 있지만 실제 성능 변화는 업무·경로·장비에 따라 측정해야 합니다. 무조건 빠르거나 느리다고 단정하는 대신, 적용 범위를 결정하고 변경 전후의 크기·손실·처리량을 비교합니다.

DHCP 옵션의 숫자와 적용 여부를 따로 읽습니다

옵션26에서26은 옵션 종류를 나타내는10진수 코드입니다. 바이트로 적으면0x1a이고, 뒤의 길이2는 MTU 값이2바이트라는 뜻입니다. 따라서1420을 전달하는 독립 필드 예시는 1a 02 05 8c입니다. 앞의1a·02는 MTU 값 자체가 아닙니다. 전체 DHCP 메시지를 만든 것이 아니라 이 옵션의 형식만 설명한 예제입니다. [6]

“서버 설정에서 보았으니 적용됐겠지요?”라는 질문에는 한 단계가 더 필요합니다. 클라이언트가 받은 설정과 실제 사용하는 인터페이스·경로의 값이 일치하는지 보세요. DHCP 응답이 캡처에 있다는 사실, 클라이언트가 옵션을 수용했다는 사실, 그 경로의 큰 전송이 개선되었다는 사실은 별도입니다. 실제 장치의 상태와 변경 전후 트래픽을 함께 확인해야 합니다.

전체 인터페이스의 MTU를 낮추는 경우 비VPN 목적지로 가는 흐름도 영향을 받을 수 있습니다. 패킷 수와 헤더 비중의 변화는 계산할 수 있지만 처리량·지연의 최종 변화는 별도 측정입니다. 과거의 “효율이 낮아진다”는 설명을 모든 업무가 반드시 느려진다는 예측으로 확대하지 않습니다.

7. MSS는 ‘TCP용 MTU’와 정확히 같은 값이 아니다

MSS(Maximum Segment Size)는 TCP에서 수신할 세그먼트의 TCP 데이터 크기를 알리는 값입니다. IP 전체 길이인 MTU와 달리 IP·TCP 헤더를 제외합니다. 비슷한 크기 제약과 관련되어 있어도 두 숫자를 그대로 서로 바꿔 쓰면 안 됩니다.

TCP는 연결을 시작할 때 SYN 비트를 사용하는 세그먼트에서 MSS 옵션을 전달할 수 있습니다. SYN-ACK도 SYN이 설정된 응답이므로 반대 방향의 MSS 정보를 담을 수 있습니다. 한쪽이 광고하는 MSS는 그쪽이 받을 크기와 관련되며, 두 방향을 따로 확인해야 합니다. MSS가 실제 모든 세그먼트의 데이터 길이를 고정하는 것은 아닙니다. 송신 측은 경로와 다른 조건도 고려합니다. [7]

가상 안쪽 IPv4 MTU 1420, 기본 IP 헤더20, 기본 TCP 헤더20
MSS 계산의 출발점 = 1420−20−20 = 1380바이트
TCP 옵션12가 실제 세그먼트에 더 있으면 데이터 예산 = 1380−12 = 1368
확인: IP20 + TCP32 + 데이터1368 = 1420

같은 안쪽 한도에서 기본 IPv6 헤더40·TCP20이라면
기본 헤더를 뺀 값 = 1420−40−20 = 1360바이트

TCP MSS 옵션의 광고값 계산과 실제 세그먼트에 넣을 데이터의 계산도 구별합니다. 현재 TCP 명세 RFC9293은 기본 IP·TCP 헤더를 빼 MSS를 산정하고, 실제 IP/TCP 옵션이 있으면 송신 데이터 양을 추가로 줄이는 관계를 설명합니다. 예제에서 옵션12가 있다고 MSS 광고값을 언제나1368로 바꾸라는 뜻은 아닙니다. IPv6 확장 헤더 등이 있으면 실제 길이 예산에 추가 반영해야 합니다. [7]

MSS clamping은 게이트웨이 등이 연결 시작 패킷의 MSS 옵션을 정책에 맞게 낮추어, 상대가 너무 큰 TCP 데이터를 보내지 않도록 유도하는 방법입니다. 장비가 어떤 방향의 SYN·SYN-ACK을 보고 값을 수정했는지, 체크섬 등 필요한 처리를 했는지, 새 연결에서 실제 크기가 줄었는지 확인합니다. 기존 연결이 모두 즉시 고쳐진다고 가정하지 않습니다.

누가 광고했는지 알아야 어느 방향을 제한하는지 보입니다

가상 단말이 SYN에서 MSS1380을 광고했다고 해 보겠습니다. 이는 단말이 받을 TCP 데이터 크기와 관련된 값이므로 서버가 단말로 보내는 방향을 볼 때 중요합니다. 서버의 SYN-ACK에 담긴 MSS는 서버가 받는 반대 방향과 관련됩니다. SYN은 연결 시작에 사용하는 TCP 제어 비트이고 ACK는 확인 응답 비트입니다. 두 방향의 헤더를 놓고 어느 광고가 어느 쪽의 송신에 영향을 주는지 화살표로 읽어 보세요. [7]

MSS가1380이어도 데이터가 매번1380이어야 하는 것은 아닙니다. 응용이 조금만 보냈거나 경로·송신 제어 조건 때문에 더 작은 세그먼트가 생길 수 있습니다. 반대로 TCP 옵션12바이트를 더 보낼 때 헤더가32가 된다면 데이터는1368로 줄여야 같은1420 예산에 맞습니다. 20+32+1368=1420에서20은IP 헤더,32는TCP 헤더,1368은TCP 데이터입니다. 광고값과 실제 보낸 길이를 같은 열에 적지 마세요.

연결 시작 구간을 수집하지 않았다면 그 파일에서 실제 MSS 광고와 변경 전후를 직접 확인하기 어렵습니다. 길이가 작다는 결과만으로 clamping 장비가 수정했다고 확정할 수 없습니다. 정책과 양쪽 SYN을 대조하고, 변경 뒤 새 연결에서 적용되었는지 확인해야 합니다. 파일 전송 중인 기존 연결에 설정을 넣은 뒤 즉시 모든 세그먼트가 바뀐다고 기대하지 않습니다.

8. MSS 조정으로 해결할 수 있는 것과 없는 것

예제에서 TCP가1380바이트의 데이터와 기본 헤더40으로 안쪽1420을 만들고, 추가80으로 바깥1500에 맞으면 길이 초과를 피할 수 있습니다. 그러나 이 결론은 해당 경로·헤더·추가 길이·적용 방향이라는 전제 위에서 성립합니다. 모든 VPN 장애의 해결책이나 향후 경로 변경에 대한 보장은 아닙니다.

UDP에는 TCP SYN과 MSS 옵션이 없습니다. 따라서 MSS clamping으로 UDP 기반 전송의 큰 데이터그램을 직접 작게 만들 수 없습니다. 원문의 UDP 기반 NFS 사례도 이 구분을 위한 예입니다. NFS라는 이름만 보고 실제 전송이 UDP인지 확정하지 말고 캡처와 서버 구성을 확인합니다.

UDP를 사용하는 현대 전송에서도 터널 오버헤드와 크기 문제는 남습니다. 해당 프로토콜의 PMTU 처리와 메시지 크기 조정을 검토해야 합니다. TCP 조정 후 웹 전송이 좋아졌다고 UDP까지 해결되었다고 보고하지 않습니다. 반대로 UDP 자체가 TCP와 같은 재전송을 제공하지 않는다는 사실을 ‘UDP 위에서는 신뢰성 있는 응용을 만들 수 없다’로 확대하지 않습니다.

TCP가 좋아졌다면 UDP는 새 질문으로 시작하세요

UDP는 TCP와 다른 전송 프로토콜이며 SYN의 MSS 옵션을 사용하지 않습니다. 안쪽 IPv4 전체1420을 기본IP20·UDP헤더8로 구성하는 가상 예산이라면 UDP 데이터는 1420−20−8=1392바이트입니다. 이 값에 응용 자체의 헤더까지 포함되는지 다시 확인해야 합니다. TCP 데이터 예산1380을 UDP의 MSS라고 부르지 않으며, 이 계산을 특정 응용의 권장 전송 크기로 제시하지 않습니다.

파일 서비스가 NFS라는 이름을 쓴다는 사실만으로 UDP라고 판단할 수 없습니다. 실제 캡처의 전송 프로토콜과 서버 구성을 확인한 뒤 적용 대상을 정합니다. UDP 기반 업무라면 응용의 데이터그램 크기·탐색·재시도 지원을 확인하고, TCP 기반 업무라면 MSS와 경로 크기를 연결합니다. 서비스 이름보다 실제 입력과 구성이 판단을 정합니다.

9. 조각 손실은 IP의 자동 재전송을 의미하지 않는다

IP는 다음 홉으로 패킷을 전달하지만 배달을 보장하는 프로토콜은 아닙니다. 목적지는 필요한 조각을 모두 모아 원래 데이터그램을 구성해야 하고, 하나가 빠지면 그 데이터그램을 완성하지 못할 수 있습니다. 여기서 IP가 빠진 조각을 알아서 다시 보내 달라고 요청하고 송신한다는 절차가 자동으로 생기지는 않습니다.

상위 프로토콜이 손실을 처리합니다. TCP라면 확인 응답과 재전송 등의 메커니즘으로 누락된 바이트를 복구할 수 있습니다. 재전송 시 원래와 똑같은 IP ID·조각 경계·묶음이 다시 만들어져야 하는 것은 아닙니다. UDP 응용은 별도 재시도·복구를 구현했을 수도 있고, 복구 없이 손실로 끝날 수도 있습니다. [7] [8]

바깥 IPsec 패킷이 단편화된 경우에는, 터널 반대편 종단에서 바깥 조각을 모아 보호 패킷을 처리한 뒤 안쪽 패킷을 전달할 수 있습니다. 바깥 조각 하나가 없으면 안쪽 내용이 보안 처리 단계까지 도달하지 못할 수 있습니다. 이때도 일반적인 IPsec 보호가 TCP처럼 모든 잃어버린 데이터 패킷을 자동 재전송해 준다고 가정하지 않습니다.

일반적인 경유 라우터가 매 홉마다 조각을 전부 재조립하는 것이 기본 IP 전달 절차는 아닙니다. 그러나 터널 종단은 바깥 패킷의 목적지이며, 보안 장비도 검사·정규화를 위해 재조립 상태를 관리할 수 있습니다. ‘중간에 있는 장치는 어떤 경우에도 재조립하면 안 된다’는 말로 VPN 게이트웨이와 IDS/IPS의 역할까지 지우지 않습니다. [1] [9]

누가 복구하는지와 무엇을 다시 보내는지 구분합니다

바깥 조각의 목적지는 게이트웨이 B입니다. B가 조각을 모두 모아야 원래 보호 패킷을 처리하고 그 안쪽 패킷을 전달할 수 있습니다. 이 경우 B는 원래 단말과 서버 사이에서는 중간 장치이지만, 바깥 IP 패킷에 대해서는 목적지입니다. “목적지에서 재조립한다”는 말의 목적지를 어느 IP 헤더로 판단하는지 적으면 모순이 사라집니다.

안쪽 TCP는 바이트 순서와 확인 응답을 기준으로 복구할 수 있습니다. 그러나 새 전송이 이전과 같은 IP 조각 집합을 재현해야 하는 것은 아닙니다. 경로 크기가 바뀌거나 송신이 다르게 묶이면 조각 개수·ID·경계가 달라질 수 있습니다. 따라서 이전 조각의ID를 재전송 검색의 유일한 열쇠로 삼지 않습니다. TCP의 바이트 관계와 시간·주소·포트를 함께 대조해야 합니다.

센서 파일에 끝 조각80바이트가 없으면 이 모델의 바깥 데이터1560 중1480만 확보한 것입니다. 목적지에서도 빠졌는지는 아직 모릅니다. 송신·수신 위치의 캡처, 센서 저장 누락과 인터페이스 손실 통계가 필요합니다. 그림의 점선은 학습 모델에서 미확보인 구간을 뜻하며 실제 네트워크의 폐기를 관측한 표식은 아닙니다.

10. 재조립 시간 초과와 ICMP는 조건을 붙여 해석한다

수신 측은 미완성 조각을 영원히 보관할 수 없으므로 재조립 대기에 시간 한도를 둡니다. 이 타이머는 패킷의 TTL 숫자를 그대로 초로 바꾼 것과 다릅니다. RFC1122 §3.3.2는 고정된 재조립 시간과60~120초의 권고를 설명합니다. 실제 OS·센서·장비의 값과 자원 제한은 다를 수 있으므로 모든 제품의 현재 고정값으로 옮기지 않습니다. [10]

IPv4 ICMP Time Exceeded Type11·Code1은 조각 재조립 시간 초과를 나타냅니다. Type11·Code0의 전달 중 TTL 초과, Type3·Code4의 단편화 필요·DF 설정과 구별합니다. 같은 ICMP라도 조사할 조건과 생성 위치가 다릅니다. [8]

원문의 ‘수신자는 반드시 송신자에게 알려 모든 조각을 재전송하게 한다’는 설명에는 조건이 필요합니다. RFC1122는 시간 초과 시 미완성 데이터그램을 버리고, 첫 조각(fragment zero)을 받았다는 조건에서 ICMP 알림을 규정합니다. ICMP 오류 생성의 다른 제한과 실제 전달·필터링도 고려해야 합니다. 알림은 상태 통지이지 IP 자동 재전송 명령이 아닙니다. [10]

따라서 ‘Type11·Code1이 보이지 않는다’만으로 재조립 성공을 증명하지 않습니다. 첫 조각이 없었거나, 오류 생성이 제한되었거나, 응답 경로가 수집되지 않았을 수 있습니다. 오류가 보였다면 인용된 헤더와 주소·Protocol·ID를 연결해 어느 안쪽/바깥쪽 묶음인지 확인합니다. 오류 발신 주소 하나를 실제 응용 서버의 최종 처리 결과로 해석하지 않습니다.

TTL64와 재조립 대기64초는 같은 말이 아닙니다

TTL은 IPv4 전달 과정의 수명을 제한하는 필드이고, 재조립 타이머는 수신 측이 미완성 묶음을 얼마나 유지할지를 정하는 상태입니다. TTL이64라는 이유로 조각을64초 기다린다고 계산하지 마세요. 과거 자료의 제품별 대기 범위와 RFC1122의60~120초 권고도 현재 설치의 실제 값으로 확인한 것이 아닙니다. 실제 분석에서는 첫 도착·마지막 관측 시각과 장비의 재조립 만료·자원 폐기 기록을 대조합니다. [10]

Type과 Code는 ICMP 메시지 종류와 그 세부 상황을 구분하는 필드입니다. 11/1을 관측했다면 오류에 인용된 원래 헤더가 안쪽인지 바깥쪽인지부터 확인합니다. 외부 게이트웨이에서 보낸 오류라는 이유만으로 파일 서버가 요청을 처리하지 않았다고 확정할 수 없습니다. 또한 첫 조각을 받았다는 조건을 확인할 수 없고 오류도 수집하지 못했다면, “오류 없음”을 “정상 재조립”으로 바꾸지 않습니다.

11. 단편화 학습을 실제 조사 순서로 연결하기

먼저 관측 위치를 정합니다. VPN 앞의 평문 측인지, 터널 중간의 보호 패킷인지, 복호화 뒤의 내부 측인지에 따라 주소·Protocol·크기·가시성이 달라집니다. 바깥쪽의 ESP·UDP와 안쪽의 TCP·UDP를 같은 계층으로 혼동하지 않습니다.

다음에는 해당 계층의 IP 헤더에서 버전·IHL·Total Length·DF/MF·Offset을 읽고, 출발지·목적지·Protocol·ID와 시간 문맥으로 묶습니다. 데이터 길이=전체 길이−헤더 길이, 시작=원시 Offset×8, 끝=시작+데이터 길이로 빈틈·중복·충돌을 구분합니다. 첫 조각이나 마지막 조각 하나만으로 전체 확보를 선언하지 않습니다.

IPv4 헤더 체크섬은 그 헤더의 오류 검출에 쓰입니다. 전체 데이터나 송신자의 진위를 인증하는 값이 아닙니다. TCP·UDP·ICMP의 전체 검증과 대상 수신·응용 처리 성공은 별도 증거가 필요합니다. 잘린 캡처와 오프로딩 때문에 보이는 값도 실제 회선과 대조합니다. [9]

보통의 분할에서는 첫 조각에 상위 헤더가 있고 뒤에는 그 이후 데이터가 옵니다. 하지만 작은 IPv4 조각은 TCP 헤더 일부를 나눌 수도 있습니다. 포트 같은 필드로 고르는 원시 캡처 필터와 재조립 후 Wireshark 표시 필터는 단계가 다르므로, ‘포트 필터로 안 보였다’를 ‘조각이 없었다’로 옮기지 않습니다. 이 예외와 실제 필터 설명은 앞선 16강의 필터 절과 연결해 복습하세요.

이후 MTU·추가 길이·DF 처리·PMTU 피드백·MSS 적용을 같은 통신 문맥에서 확인합니다. 개선 후에는 새 TCP 연결과 양방향, UDP 업무를 따로 살펴봅니다. 한 번의 작은 ping 성공만으로 파일 전송이나 모든 응용이 정상이라고 결론 내리지 않습니다.

변경 전후 비교에서도 같은 기준을 유지해야 합니다

먼저 수집 지점·방향·시각과 저장 길이를 기록하고, 평문 측과 터널 측을 분리해 장부를 만드세요. 안쪽에서는 원래 흐름의 IP·TCP 길이를, 바깥에서는 캡슐화 뒤 IP 길이와 조각을 계산합니다. 암호화 구간에서 안쪽 TCP 포트가 안 보인다는 사실을 필터 실패나 다른 프로토콜의 증거로 단정하지 않습니다. 잘린 저장과 실제 전송 길이를 구분하고, 호스트 수집의 오프로딩 영향도 확인합니다.

그다음은 변경의 적용 범위입니다. MTU 변경이라면 어느 인터페이스·경로가 바뀌었는지, MSS 변경이라면 어느 방향의 새 연결이 대상인지 확인합니다. 마지막으로 작은 요청뿐 아니라 문제를 일으켰던 큰 전송과 관련 UDP 업무도 비교합니다. 검증할 입력·수집 위치·성공 기준을 유지해야 “무엇이 개선됐는가”를 설명할 수 있습니다.

12. 패킷으로 확인한 사실과 남은 의문

패킷으로 확인 가능한 사실

관측한 계층의 주소·길이·DF/MF·Offset·시각, 확보된 조각 구간과 오류 메시지, 보이는 SYN의 MSS 옵션, 관측 지점 사이 크기·필드 변화입니다. 암호화와 수집 범위를 함께 기록합니다.

단독으로 확정할 수 없는 부분

전체 경로의 실제 MTU, 모든 장치의 DF 정책, 누락의 원인, ICMP 부재만으로 성공·차단, 경고 부재만으로 무해함, 생성 도구·공격자 숙련도, 암호화된 내용과 최종 응용의 성공 여부입니다.

함께 확인할 로그와 자료

게이트웨이 SA·터널 MTU·DF 처리·폐기·재조립·PMTU 기록, DHCP 클라이언트 반영 상태, MSS 수정 정책과 연결 양방향, 송수신·미러링 손실 통계, 단말 프로세스와 서버 응용 로그입니다.

다음은 가상 조사 메모입니다. 실제 파일 전송을 수행한 보고가 아닙니다.

안쪽1500바이트 패킷과 추가 길이80을 가정하면 바깥 길이는1580이며, 경로 한도1500을 초과한다. 안팎IPv4의 DF 및 터널 정책을 확인하기 전에는 단편화 또는 폐기를 확정하지 않는다. 이 모델의 안쪽 한도1420·기본TCP 데이터 한도1380을 계산했으며, 실제 적용과 UDP·양방향 영향은 미검증이다. 수집 지점·게이트웨이 기록·PMTU 피드백과 새 연결의 패킷을 추가 대조한다.

현대에도 패킷 분석이 중요한 이유는 내용을 읽는 것 외에 길이·손실·경로와 설정의 관계를 검증할 수 있기 때문입니다. 그러나 VPN이나 TLS로 보호된 본문을 수집 파일만으로 자동 복호화할 수 있다고 기대하지 않습니다. IP 재조립·VPN 복호화·TCP 스트림·TLS 복호화·응용 처리의 증거를 단계별로 연결해야 합니다. 적절한 비밀정보와 양단 로그가 필요한 경우를 분명히 남깁니다. [11]

장애 가설과 침해 결론을 따로 유지합니다

관측 가능한 사실은 “이 지점에서 이 길이·DF·Offset을 가진 패킷을 이만큼 저장했다”입니다. “터널 오버헤드와 경로 한도의 불일치가 장애를 만들었다”는 그 자료와 장비 기록으로 검증할 가설입니다. “누군가 고의로 장애를 만들었다”거나 “암호화된 요청이 침해에 성공했다”는 별도 증거가 필요한 결론입니다. 크기·응답 부재·도구 이름만으로 그 사이를 뛰어넘지 않습니다.

단말의 프로세스·소켓 기록과 서버의 전송 완료·오류 로그를 연결하면 실제 업무 영향을 확인하는 데 도움이 됩니다. 방화벽은 어떤 방향의 데이터·ICMP가 허용 또는 폐기되었는지, 게이트웨이는 SA·PMTU·재조립 상태를 보완합니다. 이름 해석과 로그인 결과까지 문제 범위에 포함된다면 리졸버와 인증 기록도 따로 봅니다. 작은 VPN 로그인 성공을 파일 서버의 인증·전송 완료로 대신하지 않습니다.

13. 종합 복습과 독립 연습

질문 1: 안쪽 DF1이면 VPN 바깥에서 조각이 절대로 생기지 않을까요?

해설: 안팎IPv4의 DF를 따로 확인합니다. 바깥 DF 처리에는 설정·해제·복사 등의 정책이 있고, 한도와 터널 처리에 따라 결과가 달라집니다. 안쪽 DF가 무의미하다고 일반화하는 것도 옳지 않습니다.

질문 2: 안쪽1500, 추가80, 바깥 한도1500일 때 넘친 길이와 안쪽 예산은 얼마일까요?

해설: 바깥1580으로80 초과, 안쪽 예산은1500−80=1420바이트입니다.80은 총 추가 길이를 고정한 가정이며 실제 IPsec 공통값이 아닙니다.

질문 3: 바깥1580을 IP헤더20·DF0·MTU1500 조건에서 최대로 채워 나누면?

해설: 데이터1560을1480과80으로 나눕니다. IP전체는1500과100, 끝 조각 원시Offset185·MF0입니다. 합1600의 추가20은 새 IP헤더입니다. 실제 장비의 출력이라고 주장하지 않습니다.

질문 4: MTU1420이면 TCP MSS도1420일까요?

해설: MSS는TCP 데이터 기준입니다. 기본IPv4헤더20과TCP헤더20을 빼1380입니다. 실제TCP옵션12가 있으면 데이터1368로 안쪽 총1420에 맞추는 관계를 검토합니다. 광고값과 실제 전송 데이터 양을 구별합니다.

질문 5: MSS 조정 후 UDP 기반 파일 전송도 고쳐졌을까요?

해설: UDP에는TCP MSS가 없습니다. 해당 응용의 메시지 크기·PMTU 처리와 터널 조건을 따로 확인합니다. NFS라는 이름만으로 전송 프로토콜도 확정하지 않습니다.

질문 6: DHCP 옵션을 설정했으면 모든 호스트가 새 MTU를 쓰나요?

해설: 클라이언트 지원·수용·갱신과 실제 인터페이스·관리 설정을 확인해야 합니다. 정적 설정이나 다른 경로의 장치는 같은 결과를 보장하지 않습니다.

질문 7: 조각 하나를 잃으면 IP가 전체 조각을 자동으로 다시 보낼까요?

해설: IP에는 그런 자동 손실 복구가 없습니다. TCP·응용이 재시도할 수 있으며 새 전송의IP ID나 조각 경계가 같아야 하는 것도 아닙니다. ICMP 알림을 IP 재전송 명령으로 읽지 않습니다.

질문 8: ICMP11/1을 못 봤으면 재조립이 성공했을까요?

해설: 첫 조각 수신 조건과 오류 생성 제한·경로·필터·수집 손실을 확인합니다.11/1은재조립시간초과,11/0은TTL초과,3/4는단편화필요·DF설정으로 구별합니다.

질문 9: 중간 장비인 VPN 게이트웨이는 절대로 재조립하면 안 될까요?

해설: 일반 경유 라우터의 IP 전달과 터널 종단의 역할을 구별합니다. 터널 종단은 바깥 패킷의 목적지이며 보안 장비도 검사 상태를 관리할 수 있습니다. 어느 계층과 관측 위치인지 먼저 정합니다.

질문 10: 작은 요청이 되고 큰 전송이 멈추면 공격 또는 MTU 문제를 확정할까요?

해설: 길이 초과·PMTU 피드백 실패는 검증할 가설입니다. 부하·정책·경로·수집 누락을 함께 조사합니다. 응답 부재나 익숙한 도구 이름만으로 무해함·숙련도·공격 성공을 단정하지 않습니다.

독립 연습: 같은 바깥 한도1500에서 가상의 총 추가 길이가96으로 바뀌었다고 가정해 보세요. 안쪽 예산은1500−96=1404, 기본IPv4/TCP의 MSS 계산 출발점은1404−40=1364입니다. 이전의1380을 그대로 적용하면20+20+1380+96=1516으로16바이트 넘칩니다. 값의 암기보다 캡슐화 조건을 바꾸어 다시 계산하는 연습입니다.

원문의 마지막 페이지는 별도 워크북의 단편화 실습을 안내하며 문제 본문을 싣지 않습니다. 여기의 복습은 그 실습을 실행하거나 정답을 복원한 것이 아니라, 확인한 본문을 바탕으로 만든 독립 연습입니다. 워크북 문제·기재 해설과 첫째 날 PCAP의 조각 위치·플래그·데이터·응답을 오프라인으로 대조한 이전 검토 기록을 읽고 연계 실습 가이드를 유지했습니다. 이번 개정에서 원본 PCAP을 다시 분석한 결과는 아닙니다. 실제 VPN 장비의 재현 결과를 뜻하지는 않습니다. 다음 회차부터는 명령줄에서 분석을 반복 가능하게 구성하는 방법으로 이어갑니다.

조건을 바꾸어 한 번 더 설명해 보세요

질문 11: 단말이 SYN에서 MSS1380을 광고했습니다. 주로 어느 방향의 TCP 데이터 크기와 연결할까요?

해설: 단말이 받을 데이터와 연결하므로 서버→단말 방향을 봅니다. 반대 방향은 서버의 광고와 경로 조건을 따로 확인합니다.1380이 모든 세그먼트의 고정 길이라는 뜻은 아니며 실제 옵션과 다른 송신 조건도 확인합니다.

질문 12: 추가 길이가96이 되었는데 이전1380 데이터와 기본IP/TCP헤더40을 유지하면 어떻게 될까요?

해설: 안쪽1420에96을 더하면1516이므로 바깥 한도1500을16바이트 넘습니다. 안쪽 예산1404·기본TCP 데이터1364로 다시 계산합니다. 실제TCP옵션12가 있으면 데이터1352·TCP헤더32로1404를 맞추는 관계입니다.96도 독립 가정이지 제품 공통값은 아닙니다.

질문 13: DHCP 옵션 예시1a 02 05 8c에서 MTU 값은 어느 부분일까요?

해설: 1a는옵션26,02는값의길이2바이트,05 8c는MTU1420입니다.5×256+140=1420으로 읽습니다. 이 옵션을 보았다는 것만으로 클라이언트 수용과 실제 경로 적용까지 확인한 것은 아닙니다.

질문 14: 바깥 조각을 받은 게이트웨이가 중간 장치이므로 재조립하면 잘못일까요?

해설: 안쪽 흐름에서는 중간 장치여도 바깥IP헤더의 목적지일 수 있습니다. 바깥 재조립→보호 처리→안쪽 전달의 역할을 구별해야 합니다. 일반 경유 라우터가 매 홉에서 재조립한다는 뜻은 아닙니다.

질문 15: 안쪽IPv4 한도1420에서 기본UDP헤더8이면 UDP 데이터 예산은 얼마이며 MSS조정과 같을까요?

해설: 1420−20−8=1392바이트입니다. UDP 데이터 안의 응용 헤더 예산은 다시 확인해야 합니다. UDP에는TCP의SYN/MSS가 없으므로 이 계산을 UDP MSS라고 부르거나 TCP clamping의 효과로 설명하지 않습니다.

질문 16: ICMP3/4를 관측했으니 안쪽 송신자가 PMTU를 배웠다고 보고해도 될까요?

해설: 오류가 이번 바깥 패킷을 인용하는지, 터널 종단이 수신·처리했는지, 안쪽 유효 크기에 반영되었는지와 이후 전송 크기를 대조해야 합니다. 오류 관측·학습·업무 회복은 별도 단계입니다. 반대 방향과 수집 누락도 확인합니다.

워크북 연계 실습

기재 해설을 바탕으로 실패 조건을 점검하고 IPv6 단편화와도 비교합니다. 재조립 실패와 중첩 종합 실습에서 단계별 설명과 복습을 읽을 수 있습니다. 이 페이지의 기존 자체 예시는 그대로 유지하며, 원본 PCAP을 실행한 출력으로 제시하지 않습니다.
