1. 반송 봉투 안에는 원래 보낸 봉투의 정보가 있습니다

라우터가 오류를 보낼 때 “안 됩니다” 한마디만 있으면 어느 통신의 문제인지 모릅니다. 그래서 ICMP 오류에는 원인이 된 원래 패킷의 일부가 들어갑니다. 바깥 IP 헤더는 오류 메시지의 전달 경로이고, 안쪽 IP 헤더는 실패한 원래 통신의 정보입니다. 같은 패킷 안의 두 주소 쌍을 따로 읽는 것이 핵심입니다.

전통적인 ICMPv4 오류 형식은 원래 IP 헤더와 그 뒤 최소 8바이트를 인용합니다. 실제로는 더 많은 내용을 포함하는 메시지도 있습니다. 인용 범위를 확인하면 원래 TCP·UDP 포트 또는 ICMP 식별자를 연결할 수 있지만, 짧거나 잘린 인용에 없는 필드를 억지로 해석하지 않습니다.

업무용 진단 프로그램이 “응답 없음”을 보고했는데 수집 파일에는 라우터가 보낸 ICMP만 있다고 해 볼게요. 바깥 목적지를 서버 주소로 착각하면 엉뚱한 흐름을 조사하게 됩니다. 먼저 누가 알림을 배달했는지와 어느 원래 패킷을 문제 삼았는지를 두 줄에 나누어 적어 보세요.

반송 봉투 비유에는 한계도 있습니다. 원래 패킷 전체가 돌아오는 것은 아니고 일부가 인용됩니다. 인용은 전자서명된 원본 증명서도 아닙니다. 조작된 오류일 가능성, NAT가 주소를 바꾼 지점, 캡처가 잘린 경우를 따져야 해요. 인용된 포트가 보이면 대응 후보를 찾을 수 있지만 그 오류를 단말이 받아들였다고까지 말할 수는 없습니다.

2. 64비트와 8바이트, 어디서부터 셀까요?

오프셋(offset)은 기준점에서 몇 바이트 떨어졌는지를 뜻하고 첫 바이트의 번호는0입니다. 링크 헤더·바깥 IP·ICMP·인용 IP의 기준점은 서로 달라요. 64비트는64÷8=8바이트입니다. 전통적인 인용은 원래 IP 헤더 전체에 그 뒤8바이트를 더한 것이지, 원래 IP 패킷의 맨 앞8바이트만 가져온 것이 아닙니다.

기본 IPv4 헤더를 가정한 오류 경계 · 단위 바이트
ICMP 시작 기준 범위길이역할
[0,4)4Type1 + Code1 + Checksum2
[4,8)4종류별 정보·예약 영역
[8,28)20인용 IPv4 헤더 · IHL5 가정
[28,36)8원래 IP 데이터의 첫8바이트

[8,28)은8번부터27번까지이고28은 포함하지 않는 범위 표기입니다. IHL(Internet Header Length)은IPv4 헤더 길이를4바이트 단위로 담습니다. IHL5이면5×4=20바이트여서 인용 상위 헤더는8+20=28에서 시작하죠. IHL6이면6×4=24이고8+24=32로 옮겨갑니다. “무조건28에서 포트를 읽자”는 방식은 옵션이 붙는 순간 잘못된 값을 만듭니다.

바깥IPv4 헤더도20바이트라 정하면 전체IP 시작 기준 인용IP는20+8=28, 인용 상위 헤더는20+8+20=48입니다. 이더넷까지 섞으면 기준점이 또 달라지므로 어떤 계층에서 세는지 반드시 표시해 주세요.

RFC1812는 라우터가 더 많은 원래 내용을 돌려주는 조건을 설명하고, RFC4884는 일부 오류의 인용 길이와 확장 구조를 정의합니다. “8바이트보다 많으니 비정상”, “4~7은 언제나0”, “나머지는 전부 원래 패킷”이라고 단정하지 마세요. 확장 구조·잘림·디섹터(dissector, 바이트를 프로토콜 필드로 해석하는 기능)의 지원과 설정을 함께 봅니다.

3. 시간 초과와 도달 불가의 세부 사유

Type 11 Code 0은 전달 중 TTL 소진, Code 1은 조각 재조립 시간 초과를 알립니다. 두 메시지는 같은 “시간 초과”라는 말이 있어도 원인이 다릅니다. 경로 추적의 정상 탐사에서 보이는 TTL 소진을 곧바로 장애나 공격으로 해석하지 마세요.

Type 3은 Destination Unreachable입니다. 네트워크·호스트·프로토콜·포트·정책 등 여러 세부 Code가 있습니다. 특히 Code 4는 IPv4에서 DF가 설정되어 단편화가 필요한 경우의 경로 MTU 탐색과 연결됩니다. 단순히 오류를 지우기 위해 전부 막으면 큰 데이터 전송의 문제 해결 신호를 잃을 수 있습니다.

TTL(Time To Live)은IPv4의 남은 수명이며 실제 경로에서는 홉을 지날 때 줄어드는 한도로 읽습니다. 11/0의0은 초 단위 타이머 값이 아니라 Code입니다. 반대로11/1은 목적지에서 조각을 합치려다 대기 시간이 끝난 상황입니다. 조각을 합치는 재조립(reassembly)과 홉을 넘는 전달(forwarding)을 나누면 두 사유를 구분하기 쉬워요.

4. 같은 도달 불가도 무엇이 없다는 말인지 다릅니다

Type은 큰 분류, Code는 그 안의 세부 사유입니다. Type3 Code에는0도 포함됩니다. 0~15는16개 번호이지 “1~15만 있다”는 뜻이 아닙니다. 과거 명칭 중 요즘 자주 보이지 않는 것도 있지만 오래된 파일을 읽을 때 뜻을 알아야 해요. 배정된 번호가 모두 같은 빈도나 권장 상태라는 뜻은 아닙니다.

가상 패킷의IP Protocol이253이면 그 숫자는UDP 목적지 포트253이 아닙니다. IP Protocol은IP 다음을 해석할 한 바이트이고, UDP 포트는UDP 헤더 안의 두 바이트입니다. Protocol Unreachable(3/2)와Port Unreachable(3/3)을 섞으면 서비스 지도부터 틀어지죠. 253은 이 독립 예제의 실험용 프로토콜 번호이며 특정 실제 도구나 공격을 뜻하지 않습니다.

알림 출발지가 원래 목적지와 같아도 실제 서비스 상태는 독립적으로 확인합니다. 방화벽이 대신 만들거나 출발지가 위조될 수 있고, 인용이 현재 흐름과 맞지 않을 수도 있어요. 오류는 경로·상태의 단서이지 장비 신원을 인증하는 장치는 아닙니다.

5. 작은 인용 하나로 UDP와 TCP를 어디까지 알까요?

아래는 실제 PCAP 출력이 아닌 자체 장부입니다. 송신자A는192.0.2.10, 목적지B는198.51.100.20입니다. A가UDP 출발53000에서B의33440으로 보낸 요청을 중간R의203.0.113.1이11/0으로 알려 줬다고 정해요.

가상 오류의 바깥·안쪽 대응
위치구성한 값뜻
바깥IPv4203.0.113.1 → 192.0.2.10 · Protocol1R→A ICMP 알림
ICMPType11 · Code0전달 중 TTL 소진
인용IPv4192.0.2.10 → 198.51.100.20 · Protocol17 · IHL5원래UDP 통신
인용UDP8바이트cf08 82a0 0020 000053000 → 33440 · 길이32 · IPv4 예제 체크섬 생략

16진수cf08은207×256+8=53000,82a0은130×256+160=33440입니다. 0020은16진수20이므로 십진수32바이트예요. UDP 길이32에서헤더8을 빼면 원래 데이터는24바이트라고 길이 필드가 주장합니다. 인용에는UDP8바이트만 있어서 그24바이트 내용은 읽을 수 없어요. UDP 체크섬0000은 이IPv4 예제에서는 생략이며IPv6 일반UDP에 그대로 적용하지 않습니다.

인용은IPv420+UDP8=28바이트, ICMP는헤더8+인용28=36바이트, 바깥IP는20+36=56바이트입니다. 원래IP Total Length가52(20+32)여도 오류가 원래 패킷 전체를 복사하지 않으므로 인용28바이트가 될 수 있습니다. 이 차이만으로 캡처 손실을 확정하지 않아요.

가상 UDP 인용 8바이트
cf 08 82 a0 00 20 00 00
가상 TCP 인용 8바이트
cf 08 01 bb 12 34 56 78

두 번째는TCP 출발53000·목적443·SEQ0x12345678(305419896)을 구성한 예제입니다. 첫8바이트에는 두 포트4바이트와Sequence4바이트만 있습니다. ACK·플래그·윈도·TCP 체크섬은 그 뒤여서 SYN이었다거나 ACK번호가 얼마였다고 채울 수 없어요. 목적443도TLS 성공의 증거는 아닙니다. Echo라면Type/Code/Checksum/ID/Sequence가첫8바이트에 있으므로12강의 대응법을 적용합니다.

조건을 바꿔 인용IHL을6으로 만들면 옵션4바이트 뒤에UDP가 시작합니다. 인용은24+8=32,ICMP40,바깥IP60바이트가 됩니다. 실제 저장된 인용이24바이트뿐인데IHL5이면 상위 데이터는24−20=4바이트뿐이에요. 포트 후보는 읽어도UDP 길이·체크섬과TCP의완전한SEQ는없습니다. IHL6인데24바이트뿐이면 상위 헤더는 하나도 없죠. 필드의 주장 길이와 실제 저장된 바이트 수를 따로 기록하세요.

6. 큰 전송만 실패하면 MTU 숫자를 따라가 봅니다

MTU(Maximum Transmission Unit)는 링크로 한 번에 운반할IP 패킷의 크기 한도입니다. 경로의 작은 한도를 알아내는 것이PMTUD(Path MTU Discovery)이고, DF(Don’t Fragment)는IPv4 단편화를 하지 말라는 플래그예요. DF가 켜져 있고 다음 링크보다 패킷이 크면3/4로 크기 문제를 알릴 수 있습니다.

자체 조건은IPv4전체1500바이트, 다음 홉MTU1400바이트입니다. 1500>1400이라 그대로 전달할 수 없습니다. RFC1191의3/4에서는ICMP오프셋6~7에Next-Hop MTU가 실립니다. 1400=0x0578=5×256+120이고 이형식의4~5는0입니다. “Type3의4~7은모두안쓴다”는 오래된 단순 도식이면 중요한1400을 버리게 되죠.

IPv4기본헤더20과TCP기본헤더20을 가정하면1400−20−20=1360바이트가 이조건의TCP데이터상한입니다. TCP옵션12를붙이면헤더32가되어1400−20−32=1348입니다. 광고MSS·터널오버헤드·추가IP옵션·다른경로한도까지 보아야 실제송신량을 정할 수 있어요.

인용이 현재 흐름에 맞는지 확인하고 단말의PMTU추정 변화와 재전송길이를 대조합니다. MTU필드0인 옛형식도 있으니0바이트링크라고 판정하지 않습니다. 작은 요청은 성공하고 큰 데이터만 재전송된다면 오류차단·비대칭수집·터널MTU등을 분리해 확인해요. 3/4가안보인다는 것만으로 크기 문제가 없다고 말할 수 없습니다.

7. tcpdump와 표시 필터가 다른 개수를 낼 수 있습니다

가상 ICMP 오류의 바깥 주소는 공인 대역이고 인용된 원래 주소가 사설 대역이라고 합시다. BPF의 일반 host/net 조건은 기본 바깥 IP 헤더를 대상으로 할 수 있는 반면, Wireshark 표시 필터의 ip.addr는 해석된 여러 IP 주소 필드를 대상으로 매칭할 수 있습니다. 두 도구의 결과가 다르다고 한쪽이 무조건 틀린 것이 아닙니다.

이럴 때는 파일·시간·패킷 번호·필터 종류를 맞추고, 선택된 패킷의 바깥 주소와 안쪽 주소를 각각 기록합니다. 캡처 필터와 표시 필터의 문법·해석 계층 차이를 확인하는 연습입니다. 인용된 내부 주소가 밖으로 보인다면 정보 노출의 단서일 수 있지만 현재 내부 호스트가 직접 외부와 연결했다는 뜻으로 확대하지 않습니다.

BPF(Berkeley Packet Filter)는libpcap계열의캡처/선택 표현식이고, 표시필터는Wireshark가 해석해 만든 필드에 조건을 거는 언어입니다. 같은 파일이라도 질문이 다르면 개수도 달라져요. 다음은 실행 출력이 아니라 필터의 질문 범위를 비교하는 절차입니다.

tcpdump -n -r investigation.pcap 'icmp and net 192.0.2.0/24'
tshark -n -r investigation.pcap -Y 'icmp and ip.addr == 192.0.2.0/24'
tshark -n -r investigation.pcap -Y 'icmp and ip.addr#1 == 192.0.2.0/24'
tshark -n -r investigation.pcap -Y 'icmp and ip.addr#2 == 192.0.2.0/24'
tshark -n -r investigation.pcap -Y 'icmp' -T fields -e frame.number -e ip.src -e ip.dst -E occurrence=a

-n은이름해석을끄고숫자로보려는옵션,-r은저장파일읽기입니다. 작은따옴표는셸이특수문자를먼저해석하지않도록필터를한인자로묶어요. icmp는ICMP조건,and는두조건모두만족입니다. net 192.0.2.0/24는첫24비트가같은대역의출발/목적지를고르는일반IPv4질문이고, 기본바깥IPv4를보는조건이인용안까지자동탐색한다고가정하지않습니다.

표시필터의ip.addr는출발/목적지주소필드,==는여러출현중하나라도같은지비교,/24는접두사입니다. 해석된IP가여럿이면인용주소도후보가될수있어요. 현행공식문서의#1은첫번째IP계층,#2는두번째IP계층을선택합니다. 다른터널IP가앞에있으면#2가원하는인용이아닐수있으니트리를먼저확인합니다. 오래된설치본에서는이연산자지원여부를확인하고지원하지않으면세부트리에서위치를읽으세요.

-Y는표시필터,-T fields는필드출력방식,-e는출력필드추가입니다. frame.number는파일내프레임번호,ip.src와ip.dst는출발/목적지입니다. -E occurrence=a는반복필드를모두출력하도록정하며f는첫번째,l은마지막입니다. 요약행주소두개와필드출력주소네개가다를수있죠. 출현순서를독립적인흐름으로세지말고한프레임안의계층으로분류합니다.

8. 주소 노출과 NAT 변환을 구분하는 장부

오류바깥에주소가있는지 인용안에만있는지 분리하면 정보노출을 찾기 쉽습니다. 공개용 자체예제에서는 내부영역A를192.0.2.10, 외부변환주소를198.51.100.10, 수신영역B를203.0.113.20으로 정해요. 모두 문서용대역이며 실제사설대역이라는뜻은아닙니다. 내부·외부는 이예제에서 정한역할입니다.

NAT(Network Address Translation)는경계에서주소·경우에따라포트를변환합니다. 오류에는인용된주소가더있으므로바깥주소만보면변환이제대로됐는지알수없어요. 경계안팎의같은흐름을시각·원래포트·ID/SEQ·인용길이와맞추고NAT세션로그·정책을봅니다. 주소를수정하면관련헤더와ICMP체크섬의일관성도확인해야합니다.

외부에서내부역할주소가인용안에보였다면“그수집위치에서해당바이트가노출됐다”가관측입니다. 어느장비가왜그대로보냈는지,내부호스트가현재살아있는지,그주소로직접접속할수있는지는별도질문이에요. “NAT는언제나숨긴다”도“인용주소가보이면NAT전체가무력화됐다”도피합니다. 공개보고에는실제내부주소를그대로옮기지않고정해진마스킹정책을적용하세요.

9. 오류에 오류로 답하지 않는 이유

ICMP 오류에 다시 ICMP 오류를 보내면 서로 오류를 주고받는 고리가 생길 수 있습니다. 그래서 오류 메시지에 대한 오류 생성에는 제한이 있습니다. 브로드캐스트·멀티캐스트 대상과 비초기 IP 조각 등에도 오류 생성 제한이 적용됩니다. Echo Reply처럼 정보 응답과 ICMP 오류를 같은 것으로 묶어 외우지 마세요.

조각 재조립 시간 초과의 경우 초기 조각의 수신 여부도 고려합니다. 첫 조각이 없으면 원래 상위 통신을 식별할 정보가 부족할 수 있습니다. 메시지가 안 왔다고 재조립이 성공했다는 뜻은 아닙니다. 생성 금지 조건·속도 제한·정책·손실로 오류를 못 볼 수도 있습니다.

IPv6에는 별도의 ICMPv6 규칙과 예외가 있습니다. 예를 들어 Packet Too Big은 멀티캐스트 관련 예외를 포함하므로 IPv4 억제 표를 그대로 복사하면 안 됩니다. 필요한 제어 메시지는 유지하면서 메시지 종류와 정책을 구별하는 방식으로 검토합니다.

오류알림이배달되지않았다고다시오류를보내면반송에대한반송이이어질수있습니다. 방송주소하나에여러호스트가모두오류를반환하면트래픽도불어나죠. 다만이것은ICMP오류생성의제한입니다. 모든ICMP나Echo처리를똑같이금지한다는뜻은아닙니다.

10. 첫 조각을 받은 재조립 시간 초과는 어떻게 다를까요?

가상원래IP데이터2400바이트가두조각으로나뉘었다고합시다. 첫조각은데이터1200·Fragment Offset0·MF1, 둘째는데이터1200·Offset150·MF0입니다. MF(More Fragments)는뒤에조각이더있다는표시예요. Offset단위가8바이트라150×8=1200바이트위치에서둘째데이터가시작합니다. 각기본IP헤더20까지더하면각조각은1220바이트입니다.

목적지가첫조각만받고기다리다시간이끝나면11/1의조건을검토합니다. RFC792는첫조각이없을때알림을보낼필요가없다고설명하고,RFC1122의재조립절은조각0을받은경우의응답요구를구체화합니다. 앞절의다른생성금지조건은우선해요. 첫조각에는상위헤더앞부분이있어인용과원래흐름을연결할수있습니다.

둘째조각만보이는센서에서11/1이없다면재조립성공일까요? 첫조각이실제로없었는지,다른경로로갔는지,수집이늦게시작됐는지부터모릅니다. 수신측재조립카운터·방화벽조각처리·송신기록을연결하고타임아웃값을모든OS에서같다고가정하지않습니다.

11. 오류를 서비스 지도와 연결할 때의 한계

여러 포트에 대한 Port Unreachable이 짧은 시간에 몰리면 탐사 가설을 세울 수 있습니다. 그러나 잘못된 설정의 응용도 비슷한 오류를 반복합니다. 대상을 얼마나 넓게 훑는지, 요청이 어떤 프로세스에서 나왔는지, 정상 업무 시각과 맞는지를 함께 봅니다.

보고서는 “11/0을 관측했다”, “인용 목적지가 이 주소였다” 같은 사실을 먼저 적고 라우팅 루프·탐사 등의 가설과 필요한 라우팅·방화벽·단말 자료를 이어 적습니다. 오류의 존재는 진단 단서이지 그 자체가 공격자의 의도를 증명하지는 않습니다.

Echo응답은주소응답의단서,3/1은호스트경로문제단서,3/2는IP프로토콜처리단서,3/3은포트상태단서입니다. 11/0과3/4는중간전달장비·MTU의단서가될수있어요. 하지만“답하지않은주소만살아있다”는역방향지도는생성억제·속도제한·손실을살아있는호스트와혼동합니다. 방송대상Echo를능동적으로보낼필요도없고,허가된수집자료에서관계를읽는것부터시작합니다.

프로토콜번호나포트가순차변하는요청과인용오류가맞으면스캔가설을세울수있습니다. 관리점검·오동작인지구분하려면자산목록·작업일정·프로세스실행·인증기록을보세요. 응답주소개수만세면다중인터페이스·NAT·중복수집때문에호스트수를과대평가할수있습니다.

12. tracert의 별표는 끊어진 선일까요?

Windows tracert는TTL을늘려Echo탐사를보내고중간의11/0과끝의Echo Reply로경로단서를얻습니다. 가상경로A→R1→R2→B에서TTL1이면R1에서소진,TTL2이면R2에서소진,TTL3이면이조건에서B에도달해요. 탐사와A로돌아오는오류의방향은반대지만돌아오는실제경로까지같다는뜻은아닙니다.

한홉에여러탐사를보내더라도응답들을하나의패킷으로읽지않고인용Echo의ID·Sequence와시각을맞춥니다. 자체시각으로탐사0.500초,대응오류0.527초이면차이는0.027초=27ms예요. R1의10ms를빼면17ms지만R1~R2구간만의지연이라고확정하지않습니다. 서로다른탐사의왕복경로·제어메시지처리·혼잡이다를수있기때문입니다.

tracert /d /h 5 /w 1000 198.51.100.20

실행하지않은허가된환경용절차예제입니다. /d는주소이름해석생략,/h 5는최대홉5,/w 1000은대기1000밀리초입니다. 1000ms=1초죠. 별표는대기시간내에그탐사의응답을관측하지못했다는표시입니다. 그홉뒤의모든전달이중단됐다는증명이아니에요. Microsoft문서도응답하지않는라우터가경로에보이지않을수있다고설명합니다.

13. ICMPv6의 맨 왼쪽 비트는 허용표가 아닙니다

ICMPv6는Type한바이트의최상위비트로오류와정보영역을나눕니다. 8비트에서가장큰자리값은2의7제곱=128입니다. Type과128(16진수0x80)을비트AND로비교해0이면0~127영역,그렇지않으면128~255영역이에요. AND는같은자리의두비트가모두1일때만1을남깁니다. Type3은00000011이므로결과0,Type135는10000111이므로128입니다. 이것은번호영역계산이며모든번호가배정됐다는뜻은아닙니다.

이웃·라우터·그룹관리ARP·IGMP등별도역할과연계NDP·MLD가ICMPv6사용

NDP(Neighbor Discovery Protocol)는같은링크의주소해석뿐아니라라우터발견·도달성확인·중복주소검사등과연결됩니다. MLD(Multicast Listener Discovery)는멀티캐스트수신자를알아보는기능이에요. IPv4의ARP·IGMP이름을그대로ICMPv6패킷이름으로쓰지않습니다. 다음14~15강에서헤더·주소범위와NDP메시지를이어읽습니다.

128이상이라는이유로정보메시지를전부막으면NDP같은필수기능을깨뜨릴수있어요. 128미만이라는이유로오류를검증없이전부신뢰하는것도위험합니다. RFC4890의필터링지침처럼메시지종류·링크범위·방향·필수역할을구별하고,종단상태·연결된흐름·방화벽기록을맞춰정책을검토합니다.

ICMPv6오류는최소IPv6MTU를넘지않는범위에서가능한원래패킷을포함합니다. 확장헤더가길거나ESP로암호화되면상위포트까지인용되지않거나해독할수없습니다. v4의“IP헤더+8바이트”와고정오프셋표를v6에복사하지마세요. 체크섬에도IPv6가상헤더가포함됩니다.

오류에대한오류·Redirect에대한오류·단일노드를특정하지못하는출발지등의제약을보되멀티캐스트에는예외가있습니다. RFC4443에서는Packet Too Big과특정알수없는IPv6옵션에대한Parameter Problem Code2가예외입니다. 후자는옵션유형의상위두비트가10인조건까지확인해요. “v6멀티캐스트는언제나무응답”이면크기조정과오류처리경로를놓칩니다.

14. 실제 조사는 한 프레임에서 끝나지 않습니다

수집위치·인터페이스·시간대·시계오차·snaplen(저장할패킷최대길이)·드롭통계·표시필터·재조립설정을적습니다. 이어바깥주소/Type/Code와인용주소/Protocol/포트/ID/SEQ·저장범위를나눕니다. 한프레임의주소출현수·프레임수·흐름수는서로다른수예요.

“R주소의11/0 4건이A로수집됐고인용은A→B의UDP53000→33440과일치한다”는관측입니다. “경로탐사또는루프가능성”은가설이에요. “요청의TTL단계·반복경로·라우팅변경·작업일정·단말프로세스확인”이추가증거입니다. 오류를단말이수용했는지,응용이재시도했는지도단말·서버로그로확인해야합니다.

필터에서 시작한 둘째 날의 흐름도 여기서 연결됩니다. 표시 필터는 해석된 필드로 질문하고, BPF는 헤더 값·비트 마스크와 시작 위치로 질문합니다. TCP의 재전송·순서·확인은 신뢰성 기능이지만 응용 처리 성공까지 보장하지 않습니다. UDP 자체에는 같은 보장이 없어도 응용이 재시도·복구를 구현할 수 있어요. ICMP는 오류뿐 아니라 정보 전달을 하고, IPv6에서는 NDP 같은 제어 기능까지 맡습니다. 그래서 프로토콜 이름 하나보다 실제 헤더·상태·상위 로그를 연결하는 연습이 필요합니다.

원래워크북문항·PCAP의재실행출력을이본문에제시하지않습니다. 과거검토의오프라인확인과이번독립예제계산은구별합니다. 인용의계층·필터질문·오류사유·억제조건을설명하는것이이번연습목표이고,실제필터엔진·대상VM반응과원본문항전체대조는별도검증항목으로남깁니다.

15. 복습 · 조건을 바꾸어 생각하기

질문 1. ICMP 안의 사설 주소가 보이면 그 호스트가 직접 보낸 ICMP인가요?

인용된 원래 패킷의 주소일 수 있습니다. 바깥 발신자와 분리해 읽습니다.

질문 2. 11/0과 11/1은 같은 원인인가요?

전달 중 TTL 소진과 조각 재조립 시간 초과로 다릅니다.

질문 3. ICMP 오류가 없으면 통신이 성공했나요?

생성 억제·필터·손실·수집 범위 때문에 안 보일 수 있어 성공의 증거가 아닙니다.

질문 4. IHL6의인용상위헤더는ICMP몇번부터인가요?

6×4=24바이트의IP헤더가오프셋8뒤에옵니다. 8+24=32입니다. IHL5의28을고정하면옵션을포트로오인해요.

질문 5. UDP길이32를인용했는데데이터가없으면틀린오류인가요?

UDP헤더8바이트만인용될수있어요. 원래데이터24는길이필드의주장이며내용을읽었다는뜻은아닙니다.

질문 6. TCP첫8바이트의SEQ를보면SYN도확인됐나요?

아닙니다. 플래그는포트와SEQ뒤에있어요. 원래패킷이나더긴인용이필요합니다.

질문 7. 3/4의4~7바이트는항상0인가요?

RFC1191형식의6~7에는Next-Hop MTU가옵니다. 자체1400은0578입니다. 종류와확장형식을먼저정하세요.

질문 8. MTU1400,IP20,TCP옵션포함32라면데이터상한은?

1400−20−32=1348바이트입니다. 광고MSS·터널·다른경로제한은별도로확인합니다.

질문 9. ip.addr와ip.addr#1은같은개수를내야하나요?

일반필드는인용IP에도매칭할수있고#1은첫IP계층을고릅니다. 지원문법·디섹터·프레임번호를맞추고다른터널여부도확인해요.

질문 10. Offset150은150바이트위치인가요?

단위가8바이트이므로150×8=1200바이트입니다. Offset0·MF와수집범위를함께봅니다.

질문 11. 일시적인장애에는절대로ICMP오류가없나요?

그렇게일반화하지않습니다. 구체적인오류조건·생성금지·속도제한을따로봅니다. 오류하나로영구장애를확정할수도없어요.

질문 12. Type135는정보영역이므로막아도되나요?

최상위비트가1이라정보영역인것과정책허용여부는별도예요. NDP역할·링크범위·방향·상태를확인해야합니다.

질문 13. v6멀티캐스트에는절대로오류가없나요?

Packet Too Big과특정옵션조건의Parameter Problem Code2예외가있습니다. v4억제표를그대로쓰지않습니다.

질문 14. 27ms에서10ms를빼면링크지연17ms인가요?

차이는17ms이지만단독구간지연확정값은아닙니다. 서로다른탐사의왕복경로·처리부하·혼잡이섞여요.

질문 15. 인용주소노출의보고는어떻게시작하나요?

위치·시각·바깥/안쪽주소·저장바이트를관측으로적습니다. NAT설정문제·탐사는가설로두고경계양쪽수집·세션로그·정책을연결해요.
