1. 숫자를 바꾸어 쓰는 공부가 패킷 분석에 필요한 이유

앞 강의에서는 헤더 길이와 데이터 시작 위치를 계산했습니다. 이번에는 그 헤더에 적힌 숫자를 바이트에서 직접 읽어 보겠습니다. Wireshark가 길이를 57이라고 표시했는데 원시 데이터에는 0039가 보인다면, 두 값이 같은 것인지 확인할 수 있어야 합니다.

이진수·십진수·16진수는 서로 다른 데이터가 아니라 같은 값을 표현하는 서로 다른 방식입니다. 사람이 익숙한 크기를 이해할 때는 십진수가 편하고, 비트 하나의 설정을 볼 때는 이진수가 편합니다. 긴 바이트 배열을 읽고 정확히 복사할 때는 16진수가 유용합니다. 어느 표현을 쓰는지 구별하는 것이 도구의 결과를 검증하는 첫 단계입니다.

이번 회차의 목표

비트와 바이트의 크기를 구분하고, 자리값으로 진법을 변환하며, 패킷의 기준점·오프셋·필드 길이를 확인해 실제 값을 읽습니다. 예시는 독립적으로 구성한 학습용 데이터이며, 실습 PCAP을 실행한 결과로 제시하지 않습니다.

2. 비트와 니블과 바이트를 구별하기

비트는 0 또는 1이라는 두 값 중 하나를 표현합니다. 비트 네 개를 묶으면 니블, 여덟 개를 묶으면 바이트입니다. 네 비트의 가능한 조합은 16개이므로, 니블 하나를 16진수 한 자리로 표현할 수 있습니다.

패킷을 읽을 때 필요한 기본 크기
단위크기표현 예시
비트0 또는 11
니블4비트1010 ↔ 16진수 A
바이트 또는 옥텟8비트 = 2니블1010 0110 ↔ A6
2바이트16비트 = 16진수 4자리02 3B
4바이트32비트 = 16진수 8자리00 00 02 3B
8바이트64비트 = 16진수 16자리비트 폭이 큰 정수 등의 표현에 사용

여기서 바이트는 네트워크에서 사용하는 8비트입니다. 부호 없는 정수로 해석하면 한 바이트는 0부터 255, 두 바이트는 0부터 65,535까지 표현할 수 있습니다. 8비트에는 2의 8승인 256가지 조합이 있지만, 0을 포함하므로 최댓값은 255입니다. 가능한 조합 수와 최댓값을 혼동하지 마세요.

용어 보충

교재에서 쓰는 word 16비트, double word 32비트, quad word 64비트라는 묶음은 해당 문맥의 용어입니다. 모든 네트워크 문서에서 word가 16비트라는 규칙은 아닙니다. Windows의 WORD·DWORD 같은 타입명은 각 문서의 정의를 따르고, IPv4 IHL과 TCP Data Offset은 32비트 단위를 사용합니다. CPU가 64비트라는 이유로 모든 자료형이나 패킷 필드가 64비트가 되는 것도 아닙니다. 이름보다 실제 비트 수와 명세를 확인하세요. [1] [2] [3]

3. 십진수에서 익숙한 자리값을 다시 보기

십진수 2,047은 숫자 네 개를 이어 놓은 것 이상의 의미가 있습니다. 오른쪽부터 일·십·백·천의 자리라는 위치가 정해져 있기 때문입니다. 오른쪽 끝을 0번째 자리라고 하면 각 자리의 크기는 10의 0승, 1승, 2승, 3승입니다.

2047 = 2 × 10³ + 0 × 10² + 4 × 10¹ + 7 × 10⁰
     = 2000 + 0 + 40 + 7
     = 2047

진법의 밑은 사용할 숫자의 종류 수를 알려 줍니다. 십진수에는 0부터 9까지 열 종류가 있고, 한 자리의 최댓값은 9입니다. 9에 1을 더하면 그 자리는 0이 되고 왼쪽 자리에 1이 올라가서 10이 됩니다.

이 원리를 이진수와 16진수에도 그대로 적용합니다. 달라지는 것은 밑과 한 자리에 쓸 수 있는 숫자뿐입니다. 0번째 자리의 값은 어느 진법에서든 밑의 0승인 1입니다.

4. 이진수는 두 종류의 숫자로 같은 규칙을 쓴다

이진수에서 한 자리에 사용할 숫자는 0과 1입니다. 1에 1을 더하면 해당 자리는 0으로 돌아가고 왼쪽으로 1이 올라가서 이진수 10이 됩니다. 이 10은 십진수의 열이 아니라 둘입니다.

한 바이트의 자리값을 왼쪽부터 쓰면 128, 64, 32, 16, 8, 4, 2, 1입니다. 비트가 1인 자리의 값을 더하면 십진수 값을 구할 수 있습니다. 예를 들어 1010 0110은 다음처럼 계산합니다.

이진수 1010 0110의 자리값
자리값1286432168421
비트10100110
더할 값12803200420
1010 0110₂ = 128 + 32 + 4 + 2 = 166₁₀

거꾸로 십진수 166을 이진수로 바꾸려면 큰 자리값부터 확인합니다. 128을 넣으면 38이 남고, 64는 넣을 수 없으므로 0입니다. 32를 넣으면 6이 남습니다. 16과 8은 넣지 못하고, 4와 2를 넣으면 0이 됩니다. 각 자리에 넣었는지를 적으면 1010 0110이 됩니다.

패킷의 플래그는 이런 비트 단위로 의미가 정해지는 경우가 있습니다. 값 전체를 십진수 하나로 보는 것보다 어떤 자리가 1인지 보는 편이 설정된 조건을 이해하기 좋습니다. 다만 비트의 의미와 개수는 해당 필드의 명세를 따릅니다.

5. 16진수에서 A부터 F까지 사용하는 이유

16진수에는 0부터 15까지 열여섯 종류의 한 자리 값이 필요합니다. 0부터 9까지만으로는 부족하므로 나머지 여섯 값을 A·B·C·D·E·F로 씁니다. 대소문자가 달라도 같은 숫자를 뜻합니다.

F는 16이 아니라 15입니다. F에 1을 더하면 자리올림하여 16진수 10이 됩니다. 십진수에서 9 다음에 10이 되는 것과 같은 원리입니다.

이 글에서는 혼동을 줄이기 위해 16진수에 0x 접두어를 붙입니다. 0x10은 십진수 16이고, 10을 십진수로 읽으면 십입니다. 숫자를 복사할 때는 진법까지 함께 기록하세요.

6. 네 비트씩 묶으면 십진수를 거치지 않아도 된다

16은 2의 4승입니다. 그래서 16진수 한 자리와 이진수 네 자리 사이에는 정확한 대응이 있습니다. 1010 0110을 왼쪽 니블과 오른쪽 니블로 나누면 1010 → A, 0110 → 6이므로 바로 A6이 됩니다.

중요한 점은 니블을 한 자리로 바꿀 때는 각각 0~15 범위의 값으로 읽되, 바이트 전체의 크기를 계산할 때는 상위 니블에 16의 가중치를 준다는 것입니다. 상위 니블 A와 하위 니블 6을 단순히 10 + 6으로 더하면 틀립니다.

반대로 0xB3을 이진수로 바꾸려면 B를 1011, 3을 0011로 옮겨 1011 0011이라고 쓰면 됩니다. 전체를 십진수 179로 바꾸었다가 다시 이진수로 바꿀 필요가 없습니다.

12비트 값 1010 0110 0011도 같은 방법으로 A63이 됩니다. 하지만 실제 필드가 16비트라면 너비를 유지해 0A63이라고 적는 것이 위치를 확인하기 좋습니다. 선행 0은 수치의 크기를 바꾸지 않지만 필드의 폭을 보여 줍니다.

7. 여러 바이트의 값을 십진수로 바꾸기

16진수도 오른쪽부터 16의 0승·1승·2승·3승이라는 자리값을 사용합니다. 두 바이트 02 3B를 하나의 부호 없는 값으로 읽으면 다음과 같습니다.

0x023B = 0 × 16³ + 2 × 16² + 3 × 16¹ + 11 × 16⁰
       = 0 + 512 + 48 + 11
       = 571

여기서 B를 11로 바꾸는 단계를 빼먹지 마세요. 또 바이트마다 나누어 계산할 수도 있습니다. 첫 바이트 02는 2, 두 번째 3B는 3 × 16 + 11 = 59입니다. 높은 바이트의 자리값은 256이므로 2 × 256 + 59 = 571이 됩니다.

숫자로 표시된 바이트가 문자 데이터일 수도 있다는 점도 구분합니다. 바이트 31을 정수로 읽으면 십진수 49이지만, ASCII로 해석하면 문자 ‘1’입니다. 화면에 보이는 문자 두 개 ‘31’을 숫자 31이나 원시 바이트 한 개와 자동으로 동일시하지 않습니다. 해석에는 필드 형식과 문자 인코딩이 필요합니다.

8. 먼저 필드 위치를 찾고 그 다음에 값을 변환한다

숫자 변환을 정확하게 해도 다른 필드의 바이트를 읽었다면 분석 결과는 틀립니다. 따라서 순서는 기준점 확인 → 필드 위치와 길이 확인 → 바이트 추출 → 값 변환 → 의미 해석입니다.

예를 들어 다음 네 바이트를 IPv4 헤더의 시작 부분이라고 가정합니다. 학습용으로 구성한 별도 예시입니다.

46 00 00 68

오프셋은 0부터 시작합니다. 오프셋 0의 46은 IPv4 버전과 헤더 길이를 담고 있고, 오프셋 1은 서비스 관련 필드입니다. Total Length는 IP 헤더 시작 기준 오프셋 2와 3의 두 바이트입니다. 따라서 읽을 값은 00 68입니다. [2]

0x0068 = 6 × 16 + 8 = 96 + 8 = 104바이트

0x46 = 0100 0110₂
상위 4비트 0100 → 버전 4
하위 4비트 0110 → IHL 값 6 → 헤더 길이 6 × 4 = 24바이트

Total Length 104바이트와 IP 헤더 24바이트는 다른 값입니다. 이 예시에서 IP 헤더 뒤의 데이터 길이는 104 - 24 = 80바이트입니다. 그 80바이트 안에 어떤 전송 계층 헤더와 데이터가 있는지는 해당 프로토콜 필드 등을 더 읽어야 합니다.

9. tcpdump의 16진수 덤프를 읽는 방법

저장된 패킷을 16진수로 보려면 다음 명령을 사용할 수 있습니다. sample.pcap은 실제 분석할 파일명으로 바꿉니다. -r은 파일을 읽고, -nn은 주소와 포트의 이름 변환을 막으며, -x는 링크 계층 헤더를 제외한 데이터를 16진수로 출력합니다. -X는 ASCII도 함께 표시하고, -xx는 링크 계층 헤더까지 16진수로 표시합니다. 옵션이 바뀌면 기준점도 다시 확인합니다. [4]

tcpdump -nn -r sample.pcap -x

일반적인 요약 줄에는 시각, IP 주소와 포트, 방향, 프로토콜 해석 등이 나옵니다. 그 아래의 덤프 왼쪽 숫자는 시각이 아니라 해당 출력의 바이트 오프셋입니다. 흔히 한 줄에 16바이트를 보여 주므로 다음 줄은 0x0010, 그다음은 0x0020으로 시작합니다. 십진수로 각각 16과 32입니다. 네 자리 묶음 하나는 16진수 네 글자, 즉 두 바이트이지 네 바이트가 아닙니다.

다음은 문서용 주소와 예시 도메인으로 새로 구성한 IPv4/UDP/DNS 데이터입니다. 원본 실습 파일의 출력이 아닙니다. 혼동을 줄이기 위해 Ethernet 헤더를 넣지 않고 IPv4에서 시작하는 바이트만 표시합니다.

0x0000: 4500 0039 023b 0000 4011 f42f c000 0214
0x0010: c000 0235 cf08 0035 0025 0000 2345 0100
0x0020: 0001 0000 0000 0000 036c 6162 0765 7861
0x0030: 6d70 6c65 0000 0100 01

첫 바이트 45에서 버전 4와 IHL 5를 읽으므로 IP 헤더는 20바이트입니다. 따라서 오프셋 0부터 19까지가 IPv4 헤더이고, UDP는 오프셋 20부터 시작합니다. 오프셋 16에서 시작하는 두 번째 줄 안에도 IP 헤더의 마지막 네 바이트가 들어 있으므로, 한 줄 전체를 같은 계층으로 묶으면 안 됩니다.

20~21cf 08UDP 출발지 포트: 53,000
22~2300 35UDP 목적지 포트: 53
24~2500 25UDP 길이: 37바이트. 헤더 8바이트와 데이터 29바이트 포함
28부터23 45 01 00 …DNS 메시지 시작. DNS 필드의 자세한 해석은 이후에 다룹니다.

이 예시의 관계는 IP 20 + UDP 8 + DNS 29 = 57입니다. 이처럼 필드 값과 실제 배열의 길이를 대조하면 엉뚱한 위치를 읽거나 단위를 잘못 적용한 실수를 찾을 수 있습니다.

10. Identification 필드를 직접 찾고 검증하기

이번에는 덤프에서 Identification을 찾아 보겠습니다. 먼저 IPv4 헤더 배치에서 시작 기준 오프셋 4, 길이 2바이트임을 확인합니다. 그다음 덤프의 첫 줄에서 세 번째 두 바이트 묶음인 023b를 고릅니다. [2]

앞에서 계산한 것처럼 0 × 4096 + 2 × 256 + 3 × 16 + 11 × 1 = 571입니다. 도구의 Identification 표시와 비교한다면 같은 값이 나와야 합니다. 일치하지 않으면 진법, 선택한 패킷, 기준 오프셋과 필드 길이를 먼저 재확인합니다.

Identification은 IP 단편화·재조립과 관계된 필드이지 사용자 이름이나 장치의 인증된 신원 번호가 아닙니다. 값 하나가 같다는 이유로 같은 사용자나 같은 사건이라고 확정하지 않습니다. IPv4 ID의 의미와 요구사항은 RFC 6864에서도 보완되어 있으므로, 이후 단편화 분석에서 조건을 함께 다룹니다. [5]

11. 현재 도구에서 특히 조심할 표현과 바이트 순서

이진수와 16진수의 수학적 관계는 2021년 이후에도 같습니다. 현재 도구에 적용할 때 보완할 부분은 접두어의 해석, 필드의 폭과 바이트 순서, 화면 표시와 원시 데이터의 차이입니다.

2026년 11월 1일 확인

앞에 0이 있다고 항상 8진수는 아닙니다. 진법 표기 규칙은 도구와 언어마다 다릅니다. Wireshark 표시 필터는 십진수·8진수·16진수·이진수 표기를 지원하지만 다른 프로그램에 그대로 적용해서는 안 됩니다. 재현 코드에서는 int("0068", 16)처럼 밑을 명시하면 의도가 분명합니다. [6] [7]

두 바이트를 어느 순서로 읽는지도 확인합니다. IPv4의 여러 바이트 정수 필드는 높은 자리 바이트가 먼저 오는 방식입니다. 02 3B를 big-endian으로 읽으면 571이지만 little-endian으로 읽으면 0x3B02 = 15106입니다. 바이트 순서를 뒤집는 것과 바이트 안의 비트를 뒤집는 것은 다릅니다. 모든 파일 형식과 모든 응용 프로토콜에 같은 순서를 강제하지 않습니다. [2] [7]

ASCII 화면의 점은 암호화 판정이 아닙니다. 표시할 수 없는 바이트가 점으로 나올 수 있습니다. Wireshark의 바이트 표시 형식은 ASCII·UTF-8·Hex Dump 등으로 바꿀 수 있으므로, 표시 형식과 실제 바이트를 구별합니다. [8]

다음은 실제로 실행하여 산술 결과를 확인한 Python 예시입니다. 패킷을 네트워크에 보내지 않고 숫자와 바이트 변환만 합니다. PCAP 분석 결과가 아닙니다.

raw = bytes.fromhex("02 3b")
print(int("0068", 16))                         # 104
print(int.from_bytes(raw, byteorder="big"))    # 571
print(int.from_bytes(raw, byteorder="little")) # 15106
print(format(0xA6, "08b"))                     # 10100110

예를 들어 Wireshark 표시 필터에서 십진수 10, 16진수 0xa, 이진수 0b1010, 8진수 012는 같은 정수입니다. 반면 int("010", 10)은 명시한 십진수 규칙에 따라 10입니다. 서로 다른 도구의 숫자를 옮길 때는 접두어와 해석 규칙을 확인합니다. 0x의 첫 글자는 알파벳 O가 아니라 숫자 0입니다. [6] [7]

도구로 값을 확인하는 일과 원리를 이해하는 일은 함께 필요합니다. 자동 변환의 결과가 맞아도 잘못된 필드를 골랐다면 조사 결론은 여전히 틀릴 수 있습니다. 기준점과 길이를 기록하는 습관을 유지하세요.

12. 숫자를 읽은 사실과 보안 판단을 구별하기

패킷으로 확인 가능한 사실

확보된 바이트, 필드 위치와 폭, 진법과 바이트 순서에 따른 값, 길이 필드와 실제 캡처 분량의 관계입니다.

패킷만으로 확정할 수 없는 부분

특이한 숫자 하나만으로 악성 여부·사용자 신원·공격 성공을 확정하지 않습니다. 암호화된 본문의 의미나 확보하지 못한 바이트도 변환만으로 복원되지 않습니다.

함께 확인할 자료

프로토콜 명세, 링크 유형과 캡처 길이, 같은 패킷의 도구 해석, 단말 연결·프로세스 기록과 서버 로그입니다. 숫자 변환은 이런 조사에 쓰는 기초 도구입니다.

13. 복습과 단계별 해설

질문: 0xB3은 이진수와 십진수로 각각 무엇일까요?

해설: B는 1011, 3은 0011이므로 이진수는 1011 0011입니다. 십진수로는 11 × 16 + 3 = 179입니다. B를 12로 잘못 읽지 않도록 니블 표와 대조합니다.

질문: IP 헤더의 첫 네 바이트가 46 00 00 68일 때 IP 전체 길이와 IP 헤더 길이는 각각 얼마일까요?

해설: Total Length는 오프셋 2~3인 00 68이므로 104바이트입니다. IHL은 첫 바이트의 하위 니블 6이고 32비트 단위이므로 헤더는 24바이트입니다. 단순히 두 숫자를 읽는 것에 그치지 않고 서로 다른 필드라는 점을 확인합니다.

질문: 위 덤프의 Identification은 어디에 있으며 값은 얼마일까요?

해설: IP 시작 기준 오프셋 4~5의 02 3B입니다. 2 × 256 + 3 × 16 + 11 = 571입니다. Ethernet 헤더부터 세고 있다면 먼저 IP 시작 위치를 더해야 합니다.

질문: 덤프의 줄 시작에 0x0020이 보이면 20번째 바이트일까요?

해설: 16진수 0x20은 십진수 32입니다. 그 줄의 첫 바이트는 해당 출력 기준점에서 32바이트 떨어진 위치입니다. 기준점이 프레임인지 IP인지도 확인해야 합니다.

IPv4 시작 기준 오프셋 4의 2바이트를 확보했다. 바이트는 02 3B이며 명세의 바이트 순서로 해석한 값은 571이다. 이 값의 존재만으로 통신의 악성 여부나 발신자의 신원을 판단하지 않는다.

워크북 연계 실습
