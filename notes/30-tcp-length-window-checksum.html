1. 데이터가 몇 바이트인지 먼저 계산해 봅시다

파일 전송이 느리다는 신고를 받아 패킷을 열었는데, 어떤 줄에는 길이가 수천 바이트이고 어떤 줄에는 체크섬 오류가 보인다고 해 봅시다. 바로 네트워크 장애나 공격으로 분류하고 싶어지지요. 그런데 세 숫자가 서로 다른 질문에 답하고 있습니다. 데이터 길이는 “이 세그먼트에 무엇이 얼마나 실렸나”, 윈도는 “반대편이 앞으로 얼마까지 받을 수 있나”, 체크섬은 “정해진 범위의 비트가 계산과 맞나”를 말합니다. 먼저 각 숫자의 기준점을 맞춰야 해요.

이번에는 같은 패킷을 봉투의 경계, 받는 사람의 여유, 계산 검증이라는 세 관점에서 따라가겠습니다. 앞 강의의 SEQ·ACK와 이어지지만 처음 등장하는 기호부터 다시 풉니다. 본문의 자체 예제는 원본 실습의 실행 출력이 아니며, 산술과 합성 바이트만 독립적으로 검산했습니다.

상자 전체 무게만으로 내용물 무게를 알 수는 없지요. 포장 무게를 빼야 합니다. IPv4 패킷에서 TCP 데이터 길이를 구할 때도 IP 헤더와 TCP 헤더를 빼야 합니다. 두 헤더 모두 옵션 때문에 길이가 달라질 수 있으므로 늘 20바이트씩 빼면 틀릴 수 있습니다.

IPv4 IHL은 ip[0]의 아래 네 비트이고, TCP Data Offset은 tcp[12]의 위 네 비트입니다. 각각 4를 곱합니다. 가상 예시에서 IP Total Length가 120, IHL이 6, TCP Data Offset이 8이면 IP 헤더 24바이트, TCP 헤더 32바이트입니다. 데이터는 120-24-32=64바이트입니다.

2. TCP의 12번 바이트에서 위쪽 네 비트를 읽습니다

오프셋(offset)은 기준점에서 떨어진 위치입니다. 첫 바이트를 0번으로 세므로 tcp[12]는 TCP 헤더가 시작한 곳에서 12바이트 뒤, 사람의 순서로는 열세 번째 바이트예요. 프레임 전체의 열세 번째 바이트를 읽는다는 뜻이 아닙니다. IPv4 옵션이나 VLAN 태그가 있으면 프레임 안의 TCP 시작점도 움직입니다.

그 바이트의 상위 4비트, 즉 니블(nibble)이 Data Offset입니다. 이름은 데이터의 시작 위치이지만 저장 단위는 바이트가 아니라 32비트 워드의 개수입니다. 32비트는 8비트짜리 바이트 네 개이므로 필드 값에 4바이트를 곱합니다. 기본 TCP 헤더는 20바이트라 값이 5이고, 이 4비트 필드로 표현하는 일반 헤더 길이는 20~60바이트입니다. 0~4를 정상적인 짧은 헤더로 해석하면 안 됩니다.

TCP 시작점 기준 12번 바이트 = 0x80 = 1000 0000 (2진수)
상위 네 비트만 보존: 0x80 & 0xf0 = 0x80
오른쪽으로 4비트 이동: 0x80 >> 4 = 8
TCP 헤더 길이: 8 × 4바이트 = 32바이트
TCP 옵션과 패딩: 32 - 기본 20 = 12바이트

0x는 뒤 숫자가 16진수라는 표시입니다. &는 양쪽에서 모두 1인 비트만 남기는 AND 연산이고, >> 4는 네 칸 오른쪽으로 옮긴다는 뜻입니다. 0xf0는 위 네 비트가 1인 마스크예요. 위 예제에서는 마스크 후 이동해도, 먼저 이동해도 같은 상위 니블을 얻습니다. 아래 네 비트까지 헤더 길이로 읽으면 엉뚱하게 큰 값이 나옵니다.

IPv4의 IHL도 4바이트 단위지만 위치가 다릅니다. ip[0]의 하위 네 비트가 IHL이고 상위 네 비트는 IP 버전입니다. 0x46이면 버전은 4, IHL은 6, IP 헤더는 24바이트입니다. IPv4와 TCP의 “헤더 길이”라는 이름이 비슷해도 서로 다른 헤더 안의 별도 필드라는 점을 꼭 잡고 가세요.

3. 같은 120바이트를 세 기준점으로 표시해 봅시다

앞의 120바이트 예제를 그대로 좌표에 놓겠습니다. IPv4 시작점을 0으로 정하면 IP 헤더는 0~23번, TCP 헤더는 24~55번, TCP 데이터는 56~119번입니다. 컴퓨터의 구간 표기 [24,56)는 24는 포함하고 56은 포함하지 않는다는 뜻이에요. 따라서 길이는 56-24=32바이트입니다. 마지막 바이트 번호와 길이를 혼동하는 1바이트 오차를 피할 수 있지요.

이제 링크 헤더까지 붙이면 어떻게 될까요? Ethernet II 헤더가 14바이트이고 VLAN 태그가 없다는 조건에서는 IP가 프레임 오프셋 14에서 시작합니다. 위의 TCP 시작은 14+24=38, 데이터 시작은 14+56=70입니다. 태그 하나가 4바이트를 더하면 각각 42와 74로 이동합니다. 원시 IP 캡처나 Linux cooked 캡처에 Ethernet의 14를 무조건 더하면 안 됩니다.

기준점이 바뀌면 같은 필드의 절대 위치도 바뀝니다
확인 대상IPv4 시작 기준Ethernet II 14바이트VLAN 태그 하나 추가
TCP 시작2414+24=3818+24=42
TCP Data Offset이 든 바이트24+12=3614+36=5018+36=54
TCP 데이터 시작24+32=5614+56=7018+56=74

덤프가 두 바이트씩 묶여 있어도 한 묶음이 한 바이트가 되는 것은 아닙니다. 8018은 80과 18이라는 두 바이트입니다. 위쪽 니블 8은 헤더 길이이고, 다음 바이트에는 플래그가 들어 있습니다. 화면의 열 간격보다 저장된 바이트 수와 시작점을 우선하세요.

4. 옵션 뒤의 정렬 공간까지 헤더 길이에 들어갑니다

“TCP는 20바이트라고 외웠는데 왜 32나 40바이트인가요?” 20은 고정 부분입니다. 옵션은 그 뒤에 붙고, 헤더 전체가 4바이트 배수가 되도록 정렬 공간도 포함합니다. 예를 들어 10바이트 Timestamp 옵션 앞에 1바이트 NOP 두 개를 놓으면 옵션 영역은 1+1+10=12바이트, 전체 헤더는 20+12=32바이트가 됩니다. Data Offset은 8이지, 옵션 길이 12나 전체 길이 32를 그대로 넣는 필드가 아닙니다.

NOP는 No-Operation, 즉 그 바이트에서 별도 동작을 요구하지 않는 한 바이트 옵션입니다. 옵션 사이 정렬에 쓸 수 있어요. EOL은 End of Option List로 목록의 끝을 알리고, EOL 뒤에서 Data Offset 경계까지 남은 헤더 패딩은 0으로 채우는 규칙입니다. “패딩은 언제나 마지막 NOP”라고 외우면 실제 옵션을 잘못 읽습니다. 각 옵션의 Kind와 Length, 헤더의 끝을 함께 봐야 합니다.

옵션 순서와 초기 윈도는 운영체제 추정의 단서로 쓰이기도 합니다. 다만 같은 계열도 설정·버전·중간 장비에 따라 달라지고, 필드는 임의로 만들 수도 있습니다. 특정 순서 하나를 보고 OS나 공격 도구를 확정하지 마세요. SYN도 옵션이 있을 수 있고, 조건에 따라 데이터가 있을 수 있으므로 “SYN이어서 데이터 0” 대신 전체 길이에서 두 헤더를 빼서 확인합니다. MSS·Timestamp·스케일의 협상 의미는 다음 9강에서 더 이어갑니다.

5. 헤더를 바꾸어도 데이터 길이를 다시 구할 수 있나요?

페이로드(payload)는 그 계층이 운반하는 내용물입니다. IP 페이로드에는 TCP 헤더도 들어가지만, TCP 페이로드에는 TCP 헤더가 들어가지 않습니다. 여기서 구하는 것은 TCP 데이터 길이입니다. IP 전체 - IP 헤더까지만 계산하고 TCP 데이터라고 부르면 헤더까지 내용물로 세게 됩니다.

독립적인 길이 계산 예제 · 모든 숫자는 바이트 또는 명시한 필드 단위
IP 전체IHL → IP 헤더Data Offset → TCP 헤더계산과 해석
885×4=205×4=2088-20-20=48바이트 데이터
1046×4=248×4=32104-24-32=48바이트 데이터
645×4=2011×4=4464-20-44=0바이트 데이터
606×4=2410×4=4060-24-40=-4. 유효한 데이터 길이가 아니라 모순된 입력

첫 두 행은 총 길이가 달라도 데이터가 같은 48바이트입니다. 두 번째는 IP 옵션 4바이트와 TCP 옵션·패딩 12바이트가 더 있지요. 세 번째는 헤더만 들어갑니다. “데이터 0이니까 아무 의미도 없다”는 결론은 틀립니다. ACK·윈도·상태 변화처럼 데이터 없이 전달하는 정보도 있습니다.

직접 풀 때는 먼저 버전과 Protocol=6(TCP)을 확인하고, IHL로 TCP 시작점을 찾고, 그곳의 Data Offset으로 데이터 시작점을 찾으세요. 0x0058은 16진수 자리값으로 5×16+8=88입니다. 헤더 길이 필드는 워드 수이고 Total Length는 이미 바이트 수라는 단위 차이도 놓치지 마세요.

IP 전체 길이       120바이트
IP IHL              6 × 4 = 24바이트
TCP Data Offset     8 × 4 = 32바이트
TCP 데이터         120 - 24 - 32 = 64바이트

6. 계산식에 넣기 전에 유효한 입력인지 봅니다

이 계산은 완전한 비단편 IPv4/TCP 패킷을 전제로 한 기본식입니다. IP 조각마다 TCP 헤더가 있는 것은 아닙니다. 캡처가 snaplen 때문에 잘렸다면 헤더에 쓰인 전체 길이와 파일에 실제로 저장된 길이도 다를 수 있습니다. 헤더가 주장하는 데이터 길이와 확보한 데이터 바이트 수를 구별합니다.

헤더 길이가 최소 길이보다 작거나 전체 길이보다 길면, 바로 음수 데이터를 보고할 것이 아니라 손상·잘못된 기준점·불완전 수집·비정상 패킷을 점검합니다. Ethernet의 패딩이나 링크 계층 헤더를 IP Total Length에 다시 더하는 실수도 피합니다. 먼저 시작점을 그림으로 표시하고 길이끼리 관계가 맞는지 검사하세요.

7. 헤더가 주장한 64바이트와 실제 확보한 34바이트

snaplen은 캡처할 때 패킷마다 저장할 최대 바이트 수입니다. 앞의 IP 120바이트에 링크 헤더 14바이트를 붙이면 프레임 길이는 134바이트입니다. 이 예제는 FCS와 VLAN이 저장되지 않았다고 가정합니다. 저장 길이가 104바이트로 잘렸다면 확보한 IP 바이트는 104-14=90, 데이터 부분은 90-24-32=34바이트뿐입니다. 헤더로 계산한 64바이트 중 나머지 30바이트는 이 레코드에 없습니다.

그렇다고 송신자가 34바이트만 보냈거나 수신자가 30바이트를 잃었다고 바로 적을 수는 없어요. 저장이 짧아진 것과 선로에서 패킷이 손실된 것은 다른 사건입니다. 반대로 원래 길이 메타데이터 자체가 부정확할 가능성도 조사 문맥에 따라 남겨 둡니다. 선언 길이, 원래 레코드 길이, 저장 길이를 보고서에서 구분하세요.

단편에서는 첫 조각에만 TCP 헤더가 있을 수 있고, 그 첫 조각조차 헤더 전체를 포함하지 않을 수 있습니다. 완전한 IP 데이터그램을 재조립하기 전 각 조각의 Total Length를 넣어 전체 TCP 데이터 길이를 구하지 않습니다. 재전송이나 겹침이 있으면 각 세그먼트의 길이 합도 고유한 응용 데이터 길이와 달라집니다. 암호화된 TCP 데이터 길이를 알았다는 것 역시 평문 내용을 읽었다는 뜻은 아닙니다.

8. 수신 윈도는 “지금 더 받을 수 있는 범위”입니다

식당 창구에서 “주문을 다섯 개 더 받을 수 있습니다”라고 말하는 장면을 떠올려 보세요. TCP의 수신 윈도는 이와 비슷하게 상대에게 수신 여유를 알립니다. 자신의 송신 속도를 직접 적는 필드가 아닙니다. 연결 양방향의 윈도는 따로 읽어야 합니다.

윈도 0은 상대가 당분간 새 데이터를 보내지 않도록 알리는 상태입니다. 곧바로 공격이나 연결 종료를 뜻하지 않습니다. 응용이 읽기를 멈췄거나 처리 속도가 부족할 수 있습니다. 이후 윈도 갱신과 프로브를 보면서 회복 여부를 확인합니다.

수신 윈도만으로 실제 전송 속도가 결정되는 것은 아닙니다. 송신자는 혼잡 제어, 링크 용량, 애플리케이션의 데이터 생성 속도 등의 제한도 받습니다. 수신 흐름 제어와 네트워크 혼잡 제어를 분리해서 생각해야 원인을 정확히 좁힐 수 있습니다.

9. 윈도는 방향을 정한 바이트 범위로 읽습니다

식당 비유에서 조심할 부분이 있습니다. 윈도 필드는 컴퓨터의 전체 메모리 용량이나 응용 버퍼 전체 크기를 그대로 덤프한 숫자가 아닙니다. 이 연결의 수신 측이 현재 광고하는 바이트 범위입니다. 받는 쪽의 정책·버퍼와 이미 받은 데이터, 스케일 협상 등을 반영합니다. A가 보낸 패킷의 윈도는 대개 B→A 데이터에 대한 A의 수신 여유이지 A→B 전송 한도가 아닙니다.

자체 예제로 B가 ACK=5001, 유효 윈도=4000바이트를 광고했다고 합시다. ACK는 다음에 기대하는 A의 번호입니다. 범위는 [5001,9001), 즉 데이터 번호 5001~9000입니다. A가 그 범위에서 이미 1500바이트를 보냈고 아직 확인받지 못했다면, 다른 제한이 없을 때 남는 공간은 4000-1500=2500바이트입니다. 윈도를 볼 때마다 4000바이트를 새로 보내도 된다는 뜻이 아니지요.

B의 다음 ACK가 6001이고 유효 윈도가 3000이면 오른쪽 경계는 여전히 9001입니다. ACK는 1000 전진했고 윈도 숫자는 1000 작아졌지만, 둘을 더한 경계는 같습니다. 이후 응용이 읽어 윈도를 5000으로 광고하면 오른쪽 경계는 11001로 이동합니다. 숫자 하나보다 ACK와 함께 움직이는 범위를 보세요. 여기서는 32비트 번호 순환이 없는 작은 수를 골랐습니다.

10. 윈도 0에서도 프로브와 제어 교환은 남을 수 있습니다

받는 응용이 잠시 읽기를 멈추면 수신 측이 윈도 0을 광고할 수 있습니다. “새로운 일반 데이터의 수용 여유가 없다”는 흐름 제어이지, RST처럼 연결을 강제 중단하겠다는 뜻은 아닙니다. “0이니까 이후 패킷은 전부 이상하다”는 오해도 피해야 해요.

보내는 쪽은 다시 받을 수 있게 됐는지 확인하는 zero-window probe, 즉 영 윈도 탐색을 수행할 수 있습니다. 표준은 새 데이터나 재전송을 이용한 프로브를 규정하므로 작은 데이터 세그먼트가 보일 수 있어요. 받는 쪽은 기대 ACK와 현재 윈도를 알립니다. 열렸다는 갱신이 유실되어도 영원히 멈추지 않게 만드는 장치입니다. 정확한 타이밍·표시는 구현과 도구 설정을 함께 봅니다.

가상 흐름에서 B의 ACK=9001, Window=0이 이어지다가 ACK=9001, Window=2048이 오면 ACK가 그대로여도 새 수신 여유를 광고한 것입니다. ACK 번호가 안 움직였다는 이유만으로 모두 손실 신호라고 세지 마세요. 응용 처리 지연, CPU·메모리·디스크 지표, 수신 큐와 서버 로그를 같은 시간축에 놓으면 일시 정체와 지속 장애를 좁힐 수 있습니다.

11. 16비트 필드와 실제 윈도 사이의 배율을 확인합니다

원시 Window는 부호 없는 16비트라 0~65535를 표현합니다. 같은 16비트를 유지하면서 더 큰 범위를 광고하려고 Window Scale 옵션을 협상합니다. 스케일 값 s에 대해 원시 값 × 2의 s제곱으로 해석해요. s=7이면 7배가 아니라 128배입니다. 원시 값 2000은 2000×128=256000바이트가 됩니다.

여기에는 두 가지 조건이 붙습니다. 협상은 SYN 교환에서 확인해야 하며, SYN 비트가 설정된 세그먼트의 Window 자체에는 배율을 적용하지 않습니다. 또 양쪽 배율은 각각의 수신 윈도에 적용되므로 방향별로 다를 수 있어요. 중간부터 수집해 SYN을 놓쳤다면 원시 값만으로 배율을 확정하지 않습니다. OS 추정값으로 빈칸을 확정 채우는 것은 위험합니다.

Wireshark의 tcp.window_size_value는 저장된 원시 Window, tcp.window_size는 도구가 계산한 윈도, tcp.window_size_scalefactor는 분석에 사용한 배율 관련 정보입니다. 값과 추론을 구분하고, 패킷 상세의 협상 상태를 함께 읽으세요. 이 필드 이름에서의 factor와 SYN 옵션 안의 shift count를 무조건 같은 숫자로 취급하지 않습니다. 다음 강의에서 양방향 협상 예제로 다시 확인하겠습니다.

12. 빠른 링크도 왕복 시간을 기다리면 느릴 수 있습니다

한 번에 배송 상자를 많이 보낼 수 있어도 확인 전화를 기다리느라 멈추면 전체 운송량은 줄어듭니다. TCP도 미확인 상태로 유지할 수 있는 데이터 양이 작으면 빠른 링크를 채우지 못할 수 있어요. RTT(Round-Trip Time)는 나갔다가 응답이 돌아오는 왕복 시간입니다. 아래 식의 지연은 편도 시간이 아니라 RTT입니다.

유효 윈도가 일정하고 손실·다른 제한을 무시하는 단순 모델에서 윈도에 따른 전송률 상한은 윈도 바이트 × 8비트/바이트 ÷ RTT 초입니다. 이것은 정확한 측정 속도를 예언하는 공식이 아닙니다. 혼잡 윈도, 병목 링크, 헤더 오버헤드, ACK 동작, 응용·저장장치 성능을 따로 봐야 합니다.

65535바이트 유효 윈도에서 RTT만 바꾸기
조건단위 변환과 중간 계산단순 모델의 결과
RTT 4ms4÷1000=0.004초; 65535×8=524280비트; 524280÷0.004131070000bit/s = 131.07Mbit/s
RTT 20ms20÷1000=0.020초; 524280÷0.02026214000bit/s = 26.214Mbit/s

링크가 1Gbit/s여도 첫 행의 조건에서는 단일 연결이 1Gbit/s를 채우기 어렵다는 뜻입니다. 반대로 여러 연결의 합계, 더 큰 실제 윈도, 다른 RTT에는 그 결론을 그대로 적용할 수 없습니다. “링크 속도가 얼마든 무조건 이 속도”가 아니라 가정을 붙인 한 연결의 모델이에요.

이번에는 목표 속도에서 필요한 전송 중 데이터 양을 거꾸로 구해 보죠. 대역폭-지연 곱 BDP(Bandwidth-Delay Product)는 bit/s × RTT 초입니다. 1Gbit/s=1000000000bit/s이고, RTT 4ms이면 1000000000×0.004=4000000비트, 이를 8로 나누면 500000바이트입니다. RTT가 20ms면 20000000비트=2500000바이트입니다. 경로를 채우는 데 필요한 규모의 참고값이지 모든 서버에 같은 버퍼 값을 설정하라는 지시가 아닙니다.

MB는 여기서 1000000바이트, KiB는 1024바이트를 뜻합니다. 500000바이트는 약 488.28KiB, 2500000바이트는 2.5MB입니다. “64k”라는 말도 정확히 65535인지 65536인지 분명히 적으세요. 작은 차이지만 계산의 전제와 단위를 습관적으로 확인하는 연습이 됩니다.

13. MTU보다 큰 세그먼트가 파일에 보인다면

TSO는 큰 송신 데이터를 나누는 일을 네트워크 장치 쪽에 맡기는 기능입니다. 호스트 안에서 그 처리 전에 캡처하면 실제 선로에서 보낼 프레임보다 큰 단위가 보일 수 있습니다. 반대로 수신 집약 기능은 여러 수신 단위를 합친 모습으로 관측되게 할 수 있습니다. 파일의 한 레코드가 항상 선로의 한 프레임이라는 가정을 주의하세요.

따라서 길이가 유난히 크면 점보 프레임·오프로딩·캡처 지점을 확인합니다. 운영 서버의 설정을 무조건 바꾸기보다, 분석용 수집 지점과 센서 구성의 적합성을 검토하고 필요한 비교 캡처를 얻습니다. 교재의 센서 권고를 운영 서버 전체의 즉시 변경 지시로 받아들이지 않습니다.

14. 송신 분할 전과 수신 집약 후를 구별합니다

TSO는 TCP Segmentation Offload로, 큰 송신 버퍼를 선로에 맞는 세그먼트로 나누는 작업을 장치에 맡기는 기능입니다. GSO(Generic Segmentation Offload)는 소프트웨어 분할 경로를 제공하고, GRO(Generic Receive Offload)는 수신한 여러 단위를 더 큰 내부 단위로 모을 수 있습니다. 송신 분할과 수신 집약은 반대 방향의 동작이지 같은 기능명이 아닙니다.

이 예제는 TCP 옵션이 없어서 1500-20-20=1460바이트를 담습니다. 5840÷1460=4개이고, 선로의 IP 전체 길이는 각 1500바이트입니다. TCP 헤더가 32바이트로 바뀌면 데이터 한도는 1448바이트가 되므로 같은 분할표를 재사용할 수 없습니다. 큰 내부 단위 하나의 헤더가 실제 선로 네 패킷의 모든 메타데이터를 보존하는 것도 아닙니다.

따라서 IDS 수집 경로에서는 실제 프레임 경계가 보존되는지 확인해야 합니다. 다만 TSO 설정 하나를 끄면 수신 GRO/LRO와 모든 가상화 계층의 영향까지 사라진다고 보장할 수는 없어요. 수집 인터페이스·방향·드라이버·미러링 위치·분석 엔진 요구를 확인하고 비교 캡처로 검증합니다. 운영 서버의 오프로딩을 일괄 해제하면 CPU·처리량이 달라질 수 있으므로 전용 수집기의 설계 문제와 구별하세요.

ethtool -k enp1s0

ethtool은 네트워크 장치 기능을 조회·제어하는 Linux 도구이고, 소문자 -k는 기능 상태 조회입니다. enp1s0는 예시 인터페이스 이름이라 실제 수집 장치 이름으로 바꿔야 합니다. 대문자 -K는 설정 변경이라 의미가 다릅니다. 여기서는 조회 구문만 제시하며 실행 결과나 설정 변경을 했다고 주장하지 않습니다. 기능이 on이어도 해당 트래픽이 반드시 그 경로를 거쳤다는 증거는 아니고, fixed 표시·장치 지원·수집 방법도 확인해야 합니다.

15. 체크섬은 IP 주소의 영향도 받습니다

TCP 체크섬은 TCP 헤더와 데이터만으로 계산하지 않습니다. 출발지·목적지 IP 주소, 프로토콜, TCP 길이 같은 가상 헤더 정보도 계산에 참여합니다. 가상 헤더는 독립적인 실제 TCP 앞머리로 전송되는 것이 아니라 계산용 구성입니다. 주소를 바꾸는 NAT나 패킷 편집에서 TCP 체크섬도 고려해야 하는 이유입니다.

체크섬 오류 표시를 보면 실제 손상과 체크섬 오프로딩을 구별합니다. 송신 호스트에서 장치가 최종 값을 채우기 전에 수집했을 수 있습니다. 다른 지점의 같은 트래픽, 수집 방향, 오프로딩 설정, 캡처 잘림을 대조하세요. 실제 와이어의 잘못된 체크섬을 수신 호스트가 어떻게 처리했는지는 유효성 검사와 로그를 함께 확인합니다. 체크섬은 암호학적 무결성이나 송신자 인증 수단도 아닙니다.

16. 가상 헤더는 계산에만 붙이는 12바이트입니다

택배 상자 안 물건의 개수만 맞아도 엉뚱한 주소로 가면 문제지요. TCP 체크섬은 데이터와 TCP 헤더뿐 아니라 IP 주소 일부도 계산에 넣습니다. 다만 이 비유에는 한계가 있습니다. 체크섬이 맞는다는 것이 믿을 만한 발신자가 보냈다는 인증은 아니고, 우연한 오류를 모두 검출하는 보장도 아닙니다. 비밀키 없이 다시 계산할 수 있는 산술 검사입니다.

IPv4 TCP 가상 헤더 · 선로에 별도 헤더로 붙지 않는 계산용 구성
구성 요소길이역할
출발지 IPv4 주소4바이트송신 주소를 계산에 포함
목적지 IPv4 주소4바이트목적 주소를 계산에 포함
0으로 채우는 자리1바이트정의된 0 값
프로토콜 번호1바이트TCP는 6

IP 전체가 120바이트이고 IP 헤더가 24바이트이면 가상 헤더에 넣는 TCP 길이는 120-24=96바이트입니다. TCP 데이터 64바이트만 넣는 것도, IP 전체 120을 넣는 것도 틀립니다. TCP 헤더의 체크섬 필드 두 바이트는 새 값을 계산할 때 0으로 두고 계산합니다. IPv4 헤더 체크섬은 IP 헤더만 보호하므로 검사 범위가 다릅니다. IPv6의 가상 헤더 형식은 별도이니 위 12바이트 표를 그대로 복사하지 않습니다.

데이터가 홀수 바이트이면 마지막 바이트 오른쪽에 0을 붙여 16비트 계산 단위를 맞춥니다. 이 0은 계산용이며 TCP 데이터 뒤에 실제로 전송하는 추가 데이터가 아닙니다. 옵션 정렬용 패딩과 이 계산용 0을 같은 것으로 취급하면 길이가 한 바이트씩 어긋납니다.

17. 더하고, 자리올림을 접고, 비트를 뒤집습니다

16비트 1의 보수 합은 우선 두 바이트씩 묶은 수를 더하고, 16비트 밖으로 넘은 자리올림을 아래로 다시 더합니다. 그 뒤 16비트를 뒤집은 값이 체크섬입니다. 계산 규칙만 작은 숫자로 연습해 볼게요. 여기의 세 워드는 완전한 TCP 패킷이 아니라 산술 원리 예제입니다.

0xffff + 0x0001 + 0x0002 = 0x10002
하위 16비트 0x0002 + 넘친 자리 0x0001 = 0x0003
16비트 반전: 0xffff - 0x0003 = 0xfffc
검사 시 0x0003 + 0xfffc = 0xffff

홀수 데이터 41 42 43을 계산할 때는 0x4142와 0x4300으로 읽습니다. 둘의 합은 0x8442, 반전은 0x7bbd입니다. 이 값은 그 데이터 두 워드만의 연습 결과이고 TCP 체크섬 답은 아닙니다. TCP에서는 반드시 가상 헤더와 실제 TCP 헤더까지 합쳐야 해요.

이번에는 별도로 만든 완전한 TCP 세그먼트로 범위를 확인합니다. 문서용 주소 192.0.2.10→198.51.100.20, 포트 40000→443, SEQ=1001, ACK=5001, ACK 플래그, 원시 윈도=4096, TCP 헤더=20바이트, 데이터=ABC 3바이트를 정했습니다. 443이라는 포트가 실제 TLS나 정상 서비스를 입증하지는 않습니다. 이것은 바이트 계산을 위한 합성 예제입니다.

가상 헤더 12바이트: c0 00 02 0a c6 33 64 14 00 06 00 17
TCP 길이: 20 + 3 = 23바이트 = 0x0017
TCP 체크섬 필드를 0으로 둔 전체 합: 0x3862d
자리올림을 접은 16비트 합: 0x8630
반전해 넣는 TCP 체크섬: 0x79cf
체크섬을 넣은 TCP 23바이트:
9c 40 01 bb 00 00 03 e9 00 00 13 89 50 10 10 00 79 cf 00 00 41 42 43

위 수치는 독립적인 Python 바이트 계산으로 확인했습니다. 표준 TCP 수신기나 Wireshark를 실행해 이 세그먼트를 수신·수용시킨 결과는 아닙니다. 체크섬 필드를 포함하여 같은 범위를 합치면 접힌 합이 0xffff가 되는지 다시 검사했습니다. 원본 PCAP의 실제 출력과 섞지 않습니다.

18. 주소만 바꾸어도 TCP 계산이 달라집니다

합성 예제의 출발지만 192.0.2.10에서 192.0.2.11로 바꿔 보겠습니다. TCP 데이터와 포트가 그대로여도 가상 헤더가 달라집니다. 새 체크섬은 0x79ce가 되어야 합니다. 예전 체크섬을 둔 채 계산하면 유효한 합 0xffff가 나오지 않습니다. 주소를 바꾸는 NAT와 패킷 편집에서 TCP 체크섬도 갱신하는 이유지요. 구현은 매번 모든 바이트를 재계산하는 대신 증가분 방식으로 갱신할 수도 있습니다.

가상 상황에서 중간 장비가 목적 주소를 잘못 바꾸고 IP 헤더 체크섬만 새 주소로 맞췄다고 합시다. 새 목적지의 IP 검사는 통과할 수 있어도, 이전 주소로 계산된 TCP 체크섬과 현재 가상 헤더가 맞지 않을 수 있습니다. IP 체크섬 정상과 TCP 체크섬 정상은 별도 질문이라는 뜻입니다. 단, 체크섬은 충돌이 가능하므로 모든 주소 오류를 반드시 검출한다고 일반화하지 않습니다.

19. 체크섬 통과는 응용 전달을 위한 조건 중 하나입니다

TCP 체크섬이 실제로 유효하지 않은 세그먼트는 정상 TCP 처리에서 조용히 버리는 것이 기본입니다. 그 잘못된 패킷에 꼭 RST나 ICMP를 보내 주는 진단 교환으로 이해하지 마세요. 그러나 분석 파일의 “오류 표시”와 종단이 실제로 받은 “오류 세그먼트”는 같지 않을 수 있습니다. 오프로딩·수집 잘림·재조립·도구 설정을 확인한 다음 결론을 좁혀야 합니다.

반대로 계산이 맞아도 해당 포트가 닫혀 있거나, 연결의 순서 범위에서 벗어나거나, 호스트 정책이 거부할 수 있습니다. ACK가 보이더라도 응용이 내용을 읽고 업무 처리를 완료했는지는 서버 로그나 단말 기록이 필요합니다. 무응답 역시 캡처 방향 누락·반환 경로 차이·손실과 함께 검토합니다.

20. Wireshark의 미검증·부분값·오류를 같은 색으로 묶지 않습니다

송신 호스트 안에서 잡은 패킷에는 장치가 최종 체크섬을 채우기 전 값이나 가상 헤더의 부분 합이 저장될 수 있습니다. 이때 분석 도구의 버전과 설정이 중요합니다. Wireshark 4.2.0 이후에는 인식 가능한 TCP·UDP 부분 체크섬을 유효한 부분값으로 구별할 수 있습니다. 모든 오프로딩 값이 항상 인식된다는 뜻은 아닙니다.

프로토콜 환경설정에서 체크섬 검증이 꺼져 있으면 “오류 표시가 없다”는 것을 “모든 체크섬이 맞다”로 해석하지 않습니다. 반대로 체크섬 검증을 켰을 때 유효하지 않다고 판정된 패킷이 재조립에 사용되지 않아 스트림 분석 결과가 달라질 수 있습니다. 검증 설정을 바꾸어 얻은 결과에는 그 설정을 기록하고, 설정 변경을 실제 패킷 손상의 치료라고 부르지 마세요.

체크섬 표시를 본 다음의 조사
관측 사실가능한 설명추가 확인
송신 호스트에서 부분값/오류, 외부 수집에서 정상송신 오프로딩 전후 차이방향·SEQ 범위·시간·캡처 위치가 대응하는지 확인

잘못된 체크섬 뒤에도 데이터/ACK가 보임후속 정상 데이터 또는 다른 경로·추론 가능각 세그먼트를 개별 계산하고 실제 수용 결과와 분리

직전 강의의 워크북 검토에는 잘못된 RST 체크섬과 뒤따르는 데이터·ACK를 저장 바이트로 검산한 기록이 있습니다. 그것은 그 당시 특정 파일에 대한 확인입니다. 이번 실행에서 해당 원본 PCAP이나 피해 호스트를 다시 실행한 결과로 재포장하지 않습니다. 공격 회피 성공 여부는 센서 정책과 수신 종단 동작의 차이까지 추가 검증해야 합니다.

21. 명령과 표시 필터를 한 항목씩 풀어 읽습니다

tcpdump -r capture.pcap -nn -t -vvv

tcp && tcp.len > 0
tcp && tcp.window_size_value == 0
frame.cap_len < frame.len

첫 줄은 셸에서 실행하는 읽기 지침입니다. tcpdump는 패킷 해석 도구, -r capture.pcap은 저장 파일에서 읽기, -nn은 주소와 포트 번호를 이름으로 바꾸지 않기, -t는 각 줄의 타임스탬프 생략, -vvv는 자세한 해석 수준입니다. 파일명은 예시이며 이 명령을 실제 원본 파일에 실행했다고 주장하지 않습니다. 패킷의 길이 표시가 IP 전체인지 TCP 데이터인지 출력 문맥도 확인하세요.

나머지 세 줄은 Wireshark 표시 필터이므로 셸의 tcpdump 뒤에 그대로 붙이지 않습니다. &&는 양쪽 조건을 모두 만족, >는 큼, ==는 같음, <는 작음을 뜻합니다. tcp.len은 도구가 해석한 TCP 데이터 길이, tcp.window_size_value는 원시 Window 값, frame.cap_len과 frame.len은 저장 길이와 원래 프레임 길이입니다. 마지막 식은 저장 길이가 짧은 레코드를 찾는 후보 조건이지, 모든 종류의 누락을 찾는 완전한 검사식이 아닙니다.

확인 순서는 패킷 목록에서 방향과 흐름을 고른 뒤, 패킷 상세에서 IP 길이·TCP 헤더 길이·윈도·체크섬을 읽고, 바이트 패널에서 원시 위치를 대조하는 것입니다. ip.hdr_len과 tcp.hdr_len은 해석된 바이트 길이이므로 원시 니블처럼 다시 4를 곱하지 않습니다. 잘림이나 재조립이 개입하면 해당 표시가 어떤 원본 바이트와 추론에서 나왔는지도 확인합니다.

22. 분석 결론에는 숫자와 수집 조건을 함께 씁니다

예를 들어 “A→B에서 IP 전체120, IP 헤더24, TCP 헤더32로 선언 데이터64바이트가 계산되며, 이 레코드에는 데이터34바이트만 확보됐다”는 관측을 적을 수 있습니다. 이어 “캡처 잘림이 후보이며 실제 선로 손실과 종단 수용 여부는 별도 확인이 필요하다”고 구분하면 다음 분석자가 같은 근거에서 출발할 수 있지요.

“B가 윈도 0을 광고했고 2초 뒤 같은 ACK 번호로 수신 여유를 다시 알렸다”는 시간·방향의 기록도 유용합니다. 이것을 바로 악성 행위라고 부르지 말고 B의 응용 처리·수신 큐·시스템 지표를 연결하세요. 반대 방향이 누락된 파일에서는 윈도 갱신이나 ACK가 없다고 확정하지 않습니다. 암호화·재조립·미러링 손실·시간 동기화도 결론의 범위에 넣습니다.

자료의 역할도 구분합니다. 이번에는 본 교재의 해당12쪽을 직접 읽고 그림과 대조했으며, 이 노트의 자체 길이·체크섬 예제를 독립 검산했습니다. 과거 워크북·PCAP 검토 기록은 참고했지만 그 원본 전체를 이번에 다시 실행하지 않았습니다. 워크북의 남은 체크섬·패킷 생성 문제와 대상 호스트의 수용 결과를 모두 완료한 것으로 처리하지 않습니다.

가상 헤더에 주소가 포함되므로 TCP 체크섬에도 영향을 줍니다.

질문 4. 큰 세그먼트와 체크섬 오류가 함께 보이면 공격인가요?

오프로딩 전후의 수집 차이도 후보입니다. 수집 조건과 다른 관측 지점을 대조합니다.

질문 5. tcp[12]가 0xa0이면 TCP 헤더는 몇 바이트인가요?

상위 니블 0xa는 10입니다. 10×4=40바이트이고 기본20을 뺀 옵션·패딩 영역은20바이트입니다. 프레임 기준12번 바이트라고 읽지 않습니다.

질문 6. Ethernet14, IP24, TCP32이면 데이터는 프레임 어디서 시작하나요?

14+24+32=70번 오프셋입니다. IP 기준으로는56입니다. VLAN 태그 하나가 실제 저장돼 있다면 프레임 기준은74가 됩니다.

질문 7. IP104, IHL6, TCP Data Offset8이면 데이터는?

IHL6×4=24바이트, TCP8×4=32바이트입니다. 104-24-32=48바이트입니다. 옵션 영역도 헤더에 포함됩니다.

질문 8. IP120인데 링크14 포함 저장길이가104라면 데이터64바이트를 전부 확보했나요?

아닙니다. 저장한IP는90바이트이고 IP24+TCP32를 빼면 확보한데이터34바이트입니다. 선언길이64와30바이트 차이가 나지만 그것만으로 선로 손실을 증명하지 않습니다.

질문 9. ACK5001, 유효윈도4000에서 미확인1500, cwnd2000이면 단순 송신 여유는?

min(4000,2000)-1500=500바이트입니다. rwnd만 빼면2500이지만 혼잡 제어가 더 작게 제한합니다. 실제 전송에는 추가 조건이 있습니다.

질문 10. 같은 원시윈도2000, 협상 shift7이면 SYN과 이후 패킷을 똑같이128배 하나요?

아닙니다. SYN비트가 설정된 패킷의 Window는 스케일하지 않습니다. 협상된 방향의 후속 원시2000은2000×128=256000바이트로 해석할 수 있습니다.

질문 11. 윈도65535바이트와 RTT20ms를 속도로 바꾸면?

65535×8=524280비트,20ms=0.020초이므로524280÷0.020=26214000bit/s,26.214Mbit/s입니다. 다른 제한을 무시한 한 연결의 윈도 기반 모델입니다.

질문 12. 1Gbit/s, RTT4ms의 대역폭-지연 곱은 몇 바이트인가요?

1000000000×0.004=4000000비트,8로 나누면500000바이트입니다. 약488.28KiB이며 모든 호스트에 같은 버퍼를 강제 설정하라는 뜻은 아닙니다.

질문 13. IPv4 TCP 가상헤더에 IP전체120과 TCP데이터64 중 무엇을 넣나요?

둘 다 그대로 넣지 않습니다. IP헤더24를 뺀 TCP길이96바이트를 넣습니다. TCP헤더32와 데이터64의 합이며 링크헤더는 제외합니다.

질문 14. 홀수 데이터 ABC의 계산용 마지막0은 선로에서 한 바이트 더 보내나요?

아닙니다. 41 42 43을16비트 워드4142/4300으로 계산하기 위한0입니다. 데이터 길이는 여전히3이고 체크섬 계산용 패딩과 헤더 정렬을 구분합니다.

질문 15. TCP 체크섬이 맞으면 해당 응용이 데이터를 읽은 것인가요?

체크섬은 검사 조건 중 하나입니다. 연결·순서·포트·정책과 응용 읽기는 별도입니다. ACK와 서버·단말 로그를 확인해도 각각이 입증하는 단계까지만 보고합니다.

질문 16. 송신 호스트에서 오류, 외부 센서에서 정상이면 무엇을 먼저 확인하나요?

오프로딩 전후 차이를 후보로 두고 같은 방향·번호 구간·시간인지 대조합니다. 부분값 인식, 검증 설정, 잘림과 수집 위치를 확인하며 공격이나 전송 실패를 곧바로 확정하지 않습니다.
