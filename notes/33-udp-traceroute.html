1. UDP는 전달 절차를 어디까지 맡을까요?

TCP는 바이트 순서와 재전송을 전송 계층에서 관리합니다. UDP는 주소·포트·길이·체크섬을 가진 개별 데이터그램을 전달하지만 TCP와 같은 연결 수립과 순서 복구를 자체 제공하지 않습니다. 그렇다고 UDP 위의 모든 응용이 손실을 방치한다는 뜻은 아닙니다. 필요한 재시도·순서·혼잡 제어를 상위 프로토콜이 맡을 수 있습니다.

따라서 UDP가 무조건 빠르고 TCP가 무조건 느리다는 비교는 지나치게 단순합니다. 메시지 크기·왕복 시간·손실·응용 구현에 따라 결과가 달라집니다. UDP를 쓰는 암호화 전송도 있으므로 UDP 페이로드를 항상 평문으로 볼 수 있다는 가정도 피합니다.

2. 빠른 메모 전달과 등기 우편의 차이를 생각해 봅시다

음성 통화가 잠깐 끊길 때와 계좌의 거래 기록이 한 글자 빠질 때는 필요한 대응이 다르겠지요. 제때 도착하지 못한 음성 조각을 나중에 다시 틀어 주는 것보다 다음 소리를 빨리 듣는 편이 유용할 수 있습니다. 반면 기록에는 순서와 완전성이 중요합니다. UDP를 이해하는 출발점은 “빠른 프로토콜”이라는 이름표가 아니라 누가 어떤 전달 책임을 맡는가입니다.

UDP는 User Datagram Protocol입니다. 데이터그램(datagram)은 경계를 가진 개별 전송 단위예요. 메모 한 장씩 보낸다는 비유가 도움이 됩니다. TCP 바이트 스트림처럼 앞뒤 조각의 순서와 빠진 부분을 UDP가 직접 추적하지는 않습니다. 메모 비유와 달리 실제 네트워크에는 포트·길이·체크섬이라는 정해진 이진 형식과 IP 경로가 있다는 한계도 기억하세요.

UDP 헤더에는 TCP의 SYN/ACK, SEQ/ACK 번호, 수신 윈도가 없습니다. UDP 자체가 연결 시작 교환·도착 확인·재전송·메시지 순서 복구·흐름 제어를 제공하지 않는다는 뜻입니다. 그렇다고 방화벽에 UDP 흐름 상태가 없거나 응용이 연결 상태를 가질 수 없다는 뜻은 아닙니다. connect라는 소켓 API를 사용해도 선로에 TCP 같은 세 단계 시작 교환이 생기는 것은 아닙니다.

흐름 제어는 수신자의 처리 여유를, 혼잡 제어는 공유하는 경로의 과부하를 다룹니다. UDP에 둘 다 내장되어 있지 않다고 마음껏 보내도 된다는 뜻은 아니에요. RFC 8085는 응용과 상위 프로토콜에 혼잡 제어·크기·신뢰성 등의 설계 책임을 설명합니다. 상위 계층이 손실 복구와 암호화를 제공할 수도 있으므로 UDP라는 이름만으로 전송 품질이나 내용을 예측하지 않습니다.

3. 하나에게, 같은 링크의 여러 장치에게, 그룹에게

유니캐스트(unicast)는 한 목적지, 브로드캐스트(broadcast)는 해당 IPv4 브로드캐스트 범위의 여러 장치, 멀티캐스트(multicast)는 그룹을 대상으로 보내는 방식입니다. UDP는 IP의 이런 전달 방식을 사용할 수 있습니다. 일반적인 TCP 연결은 두 종단 사이의 유니캐스트입니다. UDP가 그룹 전달에 쓰인다고 모든 그룹 구성원이 받았다는 확인까지 생기지는 않습니다.

IPv6에는 IPv4식 브로드캐스트가 없고 필요한 여러 노드 전달에 멀티캐스트 등을 사용합니다. IPv4 UDP의 브로드캐스트 사례를 주소만 바꿔 IPv6에 그대로 적용하면 틀립니다. 그룹 가입·스위치/라우터 처리·정책 때문에 같은 센서에서 그룹 주소를 봤다고 모든 수신자를 나열할 수는 없어요.

IPv4 헤더의 Protocol 값17은 그 IP 페이로드가 UDP임을 나타냅니다. IPv6에서는 Next Header 연결을 따라 최종적으로17에 도달할 수 있습니다. 확장 헤더가 있으면 기본 IPv6 헤더 바로 다음이 UDP가 아닐 수 있습니다. 여기의17은 서비스 포트17이 아니라 상위 프로토콜 식별 번호입니다.

4. 한 번 묻고 답하는 일도 프로토콜별 규칙이 다릅니다

짧은 질의와 응답이라면 연결 시작 교환의 비용을 줄이는 이점이 있습니다. 그러나 “요청 하나에 응답 하나”는 이해를 위한 전형적인 거래 모습이지 모든 메시지가 반드시 일대일로 끝난다는 규칙은 아닙니다. 여러 응답·알림·재시도·캐시·전송 방식 변경이 있을 수 있습니다.

DNS는 Domain Name System, NTP는 Network Time Protocol, SNMP는 Simple Network Management Protocol, DHCP는 Dynamic Host Configuration Protocol입니다. 이름을 외우는 것보다 리졸버, 시간 원천, 관리 장비, 설정 제공자 중 누구에게 어떤 질문을 보냈는지 구분해 보세요. 같은 포트 번호나 패킷 수만으로 정상 거래나 성공을 확정하지 않습니다.

NTP의 시각은 로그를 서로 맞추거나 시간에 민감한 인증을 조사할 때도 중요합니다. SNMP는 짧은 질의만이 아니라 비동기 알림도 가능하고, DHCP의 초기 주소 배정은 여러 메시지 단계를 거칩니다. 잘못된 DHCP 게이트웨이·DNS 설정은 트래픽의 경로와 이름 해석에 영향을 줄 수 있지만, 패킷 하나의 옵션만 보고 중간자 공격 성공을 단정하지 않습니다. 실제 임대·단말 설정·스위치·리졸버 기록으로 수용 여부를 확인합니다.

오래된 “DNS는 UDP, 큰 데이터만 TCP”라는 이분법도 피하세요. DNS의 TCP 지원은 현재 표준의 기본 요구이며 실제 질의도 TCP로 갈 수 있습니다. DNSSEC는 DNS 데이터의 진위와 무결성 검증을 위한 기능이지 UDP 체크섬을 강하게 만드는 기능이나 질의를 암호화하는 기능이 아닙니다. 거래의 전송과 인증·암호화 계층을 분리합니다.

NFS(Network File System)는 과거 UDP 사용 사례로 등장하지만 오늘 모든 NFS를 “주로 UDP”라고 소개하면 부정확합니다. 버전과 마운트·전송 설정을 확인해야 하며 NFSv4는 TCP 같은 신뢰성 있는 전송을 전제로 설명합니다. OpenVPN도 UDP 또는 TCP 전송을 구성할 수 있습니다. UDP1194나 TCP443만 보고 특정 VPN이나 HTTPS라고 확정하지 마세요. 교재의 응용 예시는 낮은 기본 전송 비용과 상위 계층의 책임을 보여 주는 사례로 읽으면 됩니다.

5. 네 필드, 여덟 바이트

UDP 헤더는 출발지 포트, 목적지 포트, 길이, 체크섬이 각각 2바이트씩 차지합니다. Length는 헤더를 포함합니다. 예를 들어 Length가 48이면 기본 계산상 데이터는 48-8=40바이트입니다. TCP의 Data Offset처럼 가변 UDP 헤더 길이를 곱하는 필드는 없습니다.

일반 데이터그램에서 8보다 작은 길이는 유효성을 점검해야 합니다. 길이 0을 모든 IP 패킷에서 정상이라고 읽어서는 안 됩니다. IPv6 jumbogram의 특수 조건이 있으며 그 조건을 검증해야 합니다. 일반 IPv4 UDP 길이 0을 곧바로 점보그램으로 분류하지 않습니다.

6. 실제 바이트를 네 칸으로 끊어 읽습니다

아래는 표의48바이트 예시와 별개로 만든 작은 UDP 예제입니다. IPv4 출발지192.0.2.40, 목적지198.51.100.60, 출발지 포트53000, 목적지 포트53을 사용합니다. 데이터는 ASCII 문자 ABC의 세 바이트입니다. 이것은 DNS가 아니라 헤더 계산용 데이터예요. 목적지 포트53이라고 유효한 DNS 질의가 되는 것은 아닙니다.

합성 UDP 전체 11바이트
cf 08 00 35 00 0b bf bf 41 42 43
출발지 포트 cf08 = 207×256+8 = 53000
목적지 포트 0035 = 0×256+53 = 53
Length 000b = 11바이트 = 헤더8 + 데이터3
Checksum bfbf · 데이터 41 42 43 = ABC

네트워크 바이트 순서는 큰 자리 바이트가 먼저입니다. 두 자리16진수 하나가1바이트이고,0b는16진수11입니다. 체크섬의 bf bf는 문자 데이터가 아니라 숫자 필드입니다. 바이트 위치0·2·4·6이 각16비트 필드의 시작이며 데이터는8부터입니다.

RFC 768에서 출발지 포트는 사용하지 않는 경우0으로 표현할 수 있습니다. 이를 TCP의 모든 포트 규칙과 똑같이 암기하지 않습니다. 보통 요청·응답 대응에는 출발지 포트가 매우 유용하지만, 응답 대상과 실제 소켓 처리는 응용·구현의 문맥도 확인해야 합니다.

7. 길이는 데이터, UDP, IP 중 무엇을 센 값인가요?

Length=8이면 데이터가0바이트인 UDP입니다. 헤더가 없다는 뜻이 아닙니다. Length=72면72−8=64바이트 데이터입니다. 반대로 데이터40바이트라면 UDP 전체는8+40=48바이트이고, IPv4 기본 헤더20바이트를 붙인 IP 전체는68바이트입니다. Ethernet 프레임에는 링크 헤더 등 다른 비용도 들어가므로 이68을 그대로 프레임 길이라고 쓰지 않습니다.

UDP Length는16비트라 일반 필드의 최대 표현값은65535입니다. 그래서 UDP만의 길이 표현으로는65535−8=65527바이트 데이터를 생각할 수 있어요. 그러나 IPv4 Total Length도 IP 헤더를 포함해65535까지이므로 IP 헤더20이라는 조건에서 실제 이론상 최대 UDP 데이터는65535−20−8=65507바이트입니다. 이 최대값이 경로 MTU에 안전하게 들어간다는 뜻은 아닙니다.

자체 길이 검산 · 옵션·터널 없는 기본 헤더 조건
조건계산해석
UDP Length4848−8=40바이트데이터 길이
IPv4 MTU15001500−20−8=1472바이트한 IP 패킷에 넣는 데이터 예산
IPv6 MTU15001500−40−8=1452바이트확장 헤더 없다는 조건
IPv4 IP길이68,헤더2468−24=44바이트UDP가48이라고 하면4바이트 불일치

마지막 줄에서 “40바이트 데이터”를 자동으로 출력하지 마세요. IP 선언·실제 저장 길이·UDP 선언을 대조해야 합니다. 캡처가 잘린 경우, IP 단편의 일부만 읽은 경우, 재조립이나 오프로딩 상태, 원본 필드 모순을 구분합니다. 실제 데이터가 모두 저장되지 않았다면 선언 길이만으로 체크섬 검증까지 완료할 수 없습니다.

IPv4 단편화가 있으면 UDP 헤더는 첫 단편에만 있을 수 있고, UDP Length는 재조립할 전체 UDP를 가리킵니다. 비첫 단편을 새로운 UDP 헤더처럼 해독하면 임의의 데이터가 포트로 보입니다. 큰 UDP를 보내면 단편 하나의 손실로 전체 데이터그램을 못 복원할 수도 있어요. IPv6 라우터는 지나가는 패킷을 직접 단편화하지 않는다는 차이도 있습니다. 실제 경로 크기와 응용의 메시지 분할을 별도로 고려합니다.

8. 길이0 두 곳과 실제 길이65536을 구분합니다

일반 IPv4 UDP의 Length=0을 “점보그램 표시”로 받아들이지 않습니다. IPv6 jumbogram은 IPv6 페이로드가65535바이트를 초과하고 Jumbo Payload 옵션 등 규격 조건을 만족하는 경우입니다. 흔히 말하는 Ethernet jumbo frame과 같은 말도 아닙니다. MTU9000인 링크라는 사실만으로 IPv6 jumbogram이 되는 것은 아니에요.

자체 조건을 하나 정하겠습니다. IPv6 기본 헤더 뒤에 Hop-by-Hop 확장 헤더8바이트, 그 뒤 UDP 전체65536바이트가 있습니다. IPv6 페이로드는8+65536=65544바이트입니다. 기본 IPv6 Payload Length 필드는0, Jumbo Payload 옵션의 길이 값은65544, UDP의 Length 필드도0으로 표현하는 조건입니다. 하지만 UDP의 실제 길이는65544−8=65536, 실제 데이터는65536−8=65528바이트입니다.

첫 번째8은 IPv6 확장 헤더, 두 번째8은 UDP 헤더라 역할이 다릅니다. IPv6 가상 헤더의 상위 계층 길이에는 실제 UDP 길이65536을 사용하며0을 넣고 체크섬을 계산하지 않습니다. UDP 자체가65535를 넘는 경우의0 규칙과 IPv6 전체 페이로드의0 규칙을 구분하세요. 옵션·확장 헤더·실제 저장 길이를 확인하기 전에는0 하나를 근거로 정상 점보그램이라고 판정하지 않습니다. 이 예제는 이론 검산이며 실제 점보 전송 시험이 아닙니다.

9. 체크섬 0의 의미는 IP 버전에 따라 다릅니다

IPv4 UDP에서는 체크섬 필드 0이 체크섬을 사용하지 않는다는 의미로 쓰입니다. 계산 결과가 0일 때의 전송 표현과 “미사용 0”도 구별해야 합니다. 일반 IPv6 UDP는 체크섬이 필요하며 제한적인 터널 예외를 평범한 UDP 전체에 일반화하지 않습니다.

UDP 체크섬도 IP 주소 등의 가상 헤더 정보를 포함합니다. 캡처에서 잘못된 값처럼 보이면 TCP 때처럼 오프로딩·수집 위치·잘림과 실제 손상을 비교합니다. UDP 헤더에 체크섬이 있다고 데이터를 자동으로 재전송하는 것은 아닙니다. 오류 검출과 신뢰성 복구는 서로 다른 기능입니다.

10. 세 바이트 ABC의 체크섬을 끝까지 계산합니다

체크섬은 오류를 찾는 작은 합계이지 발신자를 인증하는 서명이 아닙니다. 같은 합계를 만드는 다른 데이터가 있을 수 있고, 올바른 합계가 응용 문법이나 권한을 보장하지도 않습니다. 이번 합성 예제에서는 가상 헤더12바이트, UDP 헤더8바이트, 데이터3바이트를 계산 범위로 둡니다. 가상 헤더는 계산을 위해 IP의 정보를 빌린 구조이지 UDP 앞에 추가로 전송하는12바이트가 아닙니다.

체크섬을 0000으로 둔 16비트 워드 · 모두16진수
가상 헤더: c000 0228 c633 643c 0011 000b
UDP 헤더:  cf08 0035 000b 0000
데이터:    4142 4300
합계: 0x3403d
자리올림 되먹임: 0x403d + 0x0003 = 0x4040
16비트 반전: 0xffff − 0x4040 = 0xbfbf

가상 헤더의 앞 네 워드는 두 IPv4 주소입니다.0011은0바이트와 프로토콜17을 붙인 값,000b는 UDP 길이11입니다. UDP 헤더의000b도 별도 필드이므로 이 길이 값이 계산에 두 번 나타나는 것이 오류가 아닙니다. 체크섬 필드만0으로 놓고 더합니다.

데이터41 42 43은 홀수 길이라 계산할 때만 마지막43 뒤에00을 붙여4300으로 만듭니다. 그00은 전송 데이터에 추가하지 않습니다. 따라서 UDP Length는12가 아니라11입니다. 합계가16비트를 넘으면 상위 자리올림3을 낮은16비트403d에 더하고, 모든 비트를 뒤집어bfbf를 얻습니다. 수신 시 체크섬까지 포함한 접힌 합은ffff가 되는지 확인할 수 있습니다.

조건을 바꿔 마지막 문자C(43)를D(44)로 바꾸면 마지막 워드는4400입니다. 합계가0100 증가해 접힌 합4140, 체크섬bebf가 됩니다. 원본 체크섬bfbf를 그대로 붙인 변경 데이터라면 검산 결과가 맞지 않습니다. 이 예제는 별도 계산기로 검산했지만 실제 NIC나 UDP 수신기가 폐기하는 동작을 시험한 결과는 아닙니다.

11. 계산 결과0은 전송 필드ffff와 연결됩니다

IPv4에서 체크섬 필드0000은 체크섬 미사용을 나타냅니다. 그러면 실제 계산 결과가0000인 정상 계산은 어떻게 보낼까요? 그때는ffff로 전송해 미사용과 구분합니다. “0이라 계산이 잘됐다”와 “0이라 계산하지 않았다”를 같은 뜻으로 읽으면 안 됩니다.

같은 주소·포트에서 데이터만44 04 두 바이트로 바꾼 자체 예제는 UDP 길이10입니다. 가상 헤더와 UDP 헤더의 길이도 모두000a로 바꾸고 체크섬을0으로 두면 접힌 합ffff, 반전0000이 됩니다. 전송할 체크섬은ffff입니다. 길이를11로 그대로 놓고 데이터만 바꾼 계산이 아니라는 점을 보세요.

일반 IPv6 UDP는 체크섬을 계산해야 하며0인 수신 패킷은 기본 규칙상 폐기 대상입니다. 특정 터널의 지정 포트에 적용하는 zero-checksum 모드는 규정된 조건과 별도 구성의 예외입니다. “IPv6도 선택”이라는 일반 규칙으로 바꾸지 않습니다. IPv6에는 IP 헤더 체크섬이 없다는 구조 차이가 있지만, UDP 체크섬이 있다고 암호학적 인증이 생기는 것은 아닙니다.

Wireshark의 체크섬 검증 설정·캡처 위치·오프로딩도 확인하세요. 송신 전 캡처에서는 NIC가 완성할 체크섬이 아직 보일 수 있습니다. 공식 필드 사전의 udp.checksum.partial은4.2.0 이후의 부분 체크섬 관련 표시이며, 옛 udp.checksum_bad와 현재 udp.checksum.bad의 이름과 버전도 다릅니다. “검사 안 함”과 “검사 실패”를 같은 빨간 표시로 추측하지 말고 원시 값·검사 상태·설정·수신 측 증거를 대조합니다.

12. UDP 포트가 조용하면 열려 있는 걸까요?

DNS 요청이 정상 서버에 도착하면 질의에 맞는 응답을 기대할 수 있습니다. 닫힌 UDP 포트에서는 ICMP Port Unreachable이 돌아올 수 있습니다. 그러나 열려 있어도 응용 형식이 잘못되어 응답하지 않을 수 있고, 닫혀 있어도 필터나 속도 제한 때문에 ICMP를 못 볼 수 있습니다.

거래를 연결할 때는 양 끝 주소·포트, 시간, DNS 거래 ID와 질문 이름처럼 응용 정보를 함께 봅니다. 포트가 53이라는 사실은 DNS 후보라는 단서입니다. 실제 DNS로 해석되고 요청·응답 관계가 맞는지 확인해야 합니다. 반복 질의도 TCP 재전송과 동일한 전송 계층 동작으로 부르지 말고 응용의 재시도일 수 있음을 구별합니다.

13. DNS 응답과 ICMP 오류는 서로 다른 봉투입니다

자체 정상 질의를 A=192.0.2.40:53000→B=198.51.100.60:53, DNS 거래 ID0x4a21, 질문example.net의A레코드라고 정합시다. 정상 후보 응답은 B:53→A:53000 방향에 대응 ID와 질문을 가집니다. ID가16비트라 반복될 수 있으므로 ID 하나만으로 모든 거래를 묶지 않습니다. 응답 코드와 실제 답, 질의 시간·재시도를 함께 봅니다. 앞의ABC 세 바이트 계산 예제와는 다른 데이터입니다.

B의 UDP 포트가 닫혀 있으면 ICMPv4 Type3 Code3, Port Unreachable이 돌아올 수 있습니다. 바깥 IP는 오류를 보고하는 장비→A이고 안에는 실패한 A→B의 IP·UDP 일부가 인용됩니다. UDP는 헤더 전체가8바이트라 최소한 그8바이트가 온전히 인용되면 양쪽 포트·길이·체크섬을 읽을 수 있습니다. TCP의 첫8바이트에는 플래그가 없었던10강과 비교하면 차이가 분명해집니다.

인용 UDP가 cf08 0035 000b bfbf라면 포트53000→53, 길이11, 체크섬bfbf입니다. 그러나 그 인용만으로 데이터ABC까지 들어 있다고 말할 수는 없습니다. 실제 인용 길이와 IHL, 단편·NAT 변환 여부를 확인하고 원래 요청에 연결합니다. ICMP 출발지 주소만으로 발신자를 인증하지도 않습니다.

아무 응답도 없다면 포트 열림·닫힘을 확정하지 않습니다. 응용이 잘못된 질의를 조용히 버렸거나, 방화벽이 요청/오류를 막았거나, ICMP 속도 제한·왕복 경로·수집 필터가 원인일 수 있습니다. 리졸버·서버 로그와 양단 캡처, 방화벽 기록을 대조하세요. UDP 반복 질의는 응용의 재시도일 수 있으며 TCP의 SEQ 기반 재전송과 같은 필드로 분류하지 않습니다.

14. TTL을 늘리며 오류의 발신자를 관찰합니다

전형적인 UDP traceroute는 TTL을 1부터 늘려 목적지로 탐사 패킷을 보냅니다. 중간 라우터에서 TTL이 소진되면 ICMP Time Exceeded가 올 수 있습니다. 마지막 목적지의 닫힌 UDP 포트에 도착하면 Port Unreachable이 경로 완료를 알려줄 수 있습니다. UDP를 보냈는데 ICMP를 읽어야 하는 이유입니다.

각 홉의 왕복 시간은 출발지에서 그 응답까지의 시간입니다. 인접 홉의 전송 지연을 직접 측정한 값이 아니므로 뒤 홉의 값이 더 작아 보일 수 있습니다. 응답 패킷은 다른 경로로 돌아올 수 있고 라우터는 응답에 낮은 우선순위를 줄 수도 있습니다.

별표는 해당 탐사에 대한 응답을 시간 안에 못 받았다는 표시입니다. 반드시 그 홉에서 모든 일반 통신이 막힌 것은 아닙니다. ICMP 기반 tracert, TCP 기반 탐사 등도 있으므로 도구 이름만 외우지 말고 실제 프로토콜·TTL·응답을 봅니다. 세 번씩 보낸다는 횟수도 구현·옵션의 기본값일 뿐 보편 규칙은 아닙니다.

15. TTL은 남은 시간의 밀리초가 아니라 경로 진행 조건입니다

TTL(Time To Live)은 IPv4 헤더의 필드입니다. 경로 추적에서는 라우터를 지날 때 줄어드는 홉 제한으로 이해하면 편합니다. TTL1인 탐사를 받은 첫 라우터는 전달할 수명 값이 소진되면 원래 탐사를 폐기하고 ICMPv4 Type11 Code0, Time Exceeded in transit를 보낼 수 있습니다. UDP 응용이 “TTL 초과”를 답한 것이 아닙니다.

다음에는 새 탐사 패킷을 TTL2로 보냅니다. 첫 라우터를 지나 TTL1이 되고 두 번째에서 소진되는 단순 경로를 생각할 수 있어요. 원래 TTL1 패킷을 첫 라우터가 TTL2로 올려 재전송하는 과정이 아닙니다. 목적지 주소는 계속B이고 TTL만 바꿔 도달 가능한 깊이를 늘립니다. 터널·특수 경로·장비 정책에서는 이 단순 모형과 표시가 달라질 수 있습니다.

아래의 기존 단계 그림도 서로 다른 탐사 묶음을 위에서 아래로 비교하는 그림으로 읽습니다. 화살표는 같은 UDP 패킷의 전달이나 되돌아온 ICMP를 다음 홉으로 재사용한다는 뜻이 아닙니다. 마지막 목적지의 UDP 포트가 닫혀 있고 정상적으로 전달되면 Type3 Code3을 받아 종료할 수 있습니다. 목적지 포트가 열렸거나 차단되면 그 종료 조건이 생기지 않을 수 있습니다.

16. 탐사9개를 보냈다면 TTL과 포트를 두 축으로 추적합니다

독립적인 가상 모형을 새로 만들겠습니다. A에서 R1·R2를 지나B로 가는 경로이고, TTL마다3개 탐사를 보낸다고 정합니다. 출발지 포트54000, 목적지 포트40000부터 탐사마다1씩 증가하도록 설정한 모형입니다. 특정 도구의 기본 시작 번호를 재현한 출력이 아닙니다.

가상 탐사 장부 · 각 행의 세 패킷은 독립 UDP 데이터그램
탐사 번호송신 TTL목적지 UDP 포트가정한 응답
1·2·31·1·140000·40001·40002R1→A,Type11 Code0
4·5·62·2·240003·40004·40005R2→A,Type11 Code0
7·8·93·3·340006·40007·40008B→A,닫힌 포트에서Type3 Code3

보낸 UDP는3홉×3개=9개이고, 모두 각각 ICMP 하나를 되돌린다는 모형이면 ICMP도9개입니다. 이18은 가정한 두 종류의 IP 패킷 수이지 Ethernet 프레임 총수·고정 실측값이 아닙니다. ARP·손실·재시도·추가 제어 트래픽은 제외했어요. 도구 설정에 따라 홉당 탐사 수와 포트 변경 방식도 달라집니다.

ICMP 오류 속의 인용 UDP 목적지 포트40004는 이 장부에서 TTL2의 두 번째 탐사 후보와 맞습니다. 실제 분석에서는 출발지/목적지 주소, 포트, IP 식별자와 시각·데이터까지 확인해야 합니다. 여러 탐사가 동시에 대기하면 응답 순서가 뒤바뀌어도 장부의 해당 탐사로 연결해야 합니다. 같은 ICMP 종류라고 모두 첫 요청의 응답으로 세지 마세요.

교재 그림과 짧은 본문을 대조하면 다음 단계의TTL이나 포트가 앞 단계 숫자로 남은 듯한 표기가 있습니다. 숫자를 그대로 외우는 대신 “새 탐사의TTL은 단계별로 증가, 그 묶음의 세TTL은 같음, 포트는 택한 방식대로 탐사마다 증가”라는 일관된 규칙으로 검산했습니다. 원본 출력의 주소·시각을 재게시하지 않습니다.

17. RTT 열은 옆 링크의 지연 시간이 아닙니다

자체 시간 예제에서 한 탐사를10.000초에 보내고10.012초에 대응 ICMP를 받았다면 관측 왕복 시간은0.012초입니다. 1초=1000ms이므로12ms입니다. 이 값에는 보내는 길·응답 장비의 처리·돌아오는 길이 섞이며, 그 라우터의 바로 앞 링크만의 지연이 아닙니다.

가상 화면 값을 해석하는 연습 · 실행 출력 아님
홉세 탐사의 관측 RTT읽을 내용
12ms·3ms·2ms각기 다른 탐사의 왕복
218ms·*·21ms한 탐사는 제한 시간 안에 응답 없음
311ms·12ms·10ms홉2보다 작아도 모순 아님

홉3의11에서 홉2의18을 빼−7ms 링크라고 보고하면 서로 다른 경로·시각의 측정을 잘못 뺀 것입니다. 장비의 ICMP 처리 우선순위·역방향 경로·부하가 다를 수 있고 라우터는 제어 응답을 제한할 수 있습니다. 같은 행의 세 숫자도 자동으로 최소·평균·최대라는 뜻이 아니라 각 탐사 값일 수 있습니다.

별표는 정해진 대기 시간에 대응 응답을 못 받았다는 표시입니다. 홉2에 별표가 있어도 뒤의홉3에서 응답을 받았다면 모든 전달이 홉2에서 막혔다고 단정할 수 없습니다. NAT·정책·비대칭 경로·응답 제한과 수집 위치를 함께 봅니다. 라우터 주소를 지도상의 도시나 물리 케이블 위치로 바꾸려면 별도 증거가 필요합니다.

18. 포트가 바뀌면 지나가는 길도 바뀔 수 있습니다

ECMP(Equal-Cost Multi-Path)는 비용이 같은 여러 경로로 전달을 분산하는 방식입니다. 장비가5튜플 등을 사용해 경로를 선택한다면, UDP 목적지 포트를 바꾸는 탐사들은 서로 다른 길로 갈 수 있습니다. 한 행에 여러 응답 주소가 보이는 것과 라우터가 순간 이동했다는 해석은 다릅니다. 각 탐사에 어떤 주소가 대응하는지 기록하세요.

UDP 방식은 보통 중간의Time Exceeded와 끝의Port Unreachable을 연결합니다. Windows tracert는 ICMP Echo 요청/응답을 사용하므로 마지막에 Echo Reply가 오는 방식입니다. TCP 기반 탐사도 가능하지만 종료를 판단하는 응답이 다릅니다. ICMPv6의 숫자 체계도 IPv4와 다르므로Type11·Type3을 IPv6에 그대로 붙이지 않습니다.

traceroute는 특정 시각·출발지·프로토콜·설정의 탐사 결과입니다. 다른 업무의TCP443 경로도 반드시 같다고 보장하지 않습니다. 관측한 응답 인터페이스가 라우터의 모든 인터페이스나 정방향·역방향 전체 경로를 뜻하는 것도 아닙니다. 결과와 함께 입력 조건을 보존해야 비교가 가능합니다.

조회한 FreeBSD 매뉴얼은 TCP 탐사를 보낼 수 있어도 그 구현이 목적지의 RST·SYN/ACK를 종료 응답으로 인식하지 못할 수 있다고 명시합니다. “TCP로 탐사하면 항상 SYN/ACK로 깔끔하게 끝난다”는 식으로 구현 차이를 지우지 마세요. 실행한 도구의 매뉴얼과 실제 패킷을 함께 확인합니다.

19. 명령의 목적과 버전을 함께 적습니다

FreeBSD traceroute 매뉴얼에 맞춘 절차 예시 · 실행하지 않음
traceroute -n -m 6 -q 3 -w 1 198.51.100.60
Windows tracert 절차 예시 · 실행하지 않음
tracert /d /h 6 /w 1000 198.51.100.60
저장된 캡처 읽기 예시 · 실행하지 않음
tcpdump -nn -tttt -r investigation.pcap 'udp or icmp'

첫 줄의-n은 이름 조회 대신 숫자 주소,-m 6은 최대TTL6,-q 3은 TTL당 탐사3개,-w 1은 응답 대기1초를 뜻합니다. 이는 조회한FreeBSD 매뉴얼의 예시이며 모든 Linux/macOS 구현의 동일 기본값을 주장하지 않습니다. 두 번째의/d는 이름 조회 생략,/h 6은 최대홉6,/w 1000은 대기1000ms입니다. 1000ms=1초이므로 두 명령의 숫자1과1000은 단위부터 다릅니다. 대상은 문서용 주소이며 실제 실행할 때는 허가된 시험 목적지와 도구 매뉴얼을 사용합니다.

세 번째는-r 뒤 파일을 읽고,-nn으로 호스트/서비스 이름 변환을 하지 않으며,-tttt로 날짜를 포함한 시각을 봅니다. 따옴표 안의or는 UDP 또는ICMPv4를 남기는 캡처 필터 문법입니다. udp만 남기면 경로 추적의 중요한 ICMP 응답을 제외할 수 있습니다. 원래 저장하지 않은 패킷은 표시 필터를 풀어 복구할 수 없어요. IPv6·터널·단편은 이 단순 필터의 관측 범위 밖으로 빠질 수 있어 원본을 넓게 보존합니다.

Wireshark 표시 필터 예시 · 실제 필터 엔진 실행 아님
udp
udp.length == 11
udp.checksum == 0
icmp.type == 11 && icmp.code == 0
icmp.type == 3 && icmp.code == 3

udp는 프로토콜 존재,udp.length는 헤더 포함 길이,udp.checksum은 원시 필드입니다. ==는 같음,&&는 두 조건의 동시 만족입니다. 체크섬0 검색은 후보 찾기일 뿐 IPv4 미사용·IPv6 예외·잘림을 분류하지 않습니다. ICMP 안에 인용된 UDP도 해석되어 필터에 걸릴 수 있으므로 바깥 프로토콜과 인용 계층을 펼쳐 확인합니다. udp.checksum.status와 분석 설정·설치 버전도 기록하세요.

20. 관측, 가설, 추가 증거를 한 문단에 섞지 않습니다

“이 센서에서A→B:53 요청 두 개와 대응 응답 하나를 관측했다”는 사실입니다. “응용이 첫 요청을 재시도했을 수 있다”는 가설이고, “리졸버 질의 기록과 양단 캡처를 맞춘다”는 다음 확인입니다. 요청이 더 많다고 즉시DDoS나 오류를 확정하거나, 암호화되어 내용을 못 읽는다고 무해하다고 하지 않습니다.

IPv4 UDP 체크섬 미사용이나 비정상 길이는 수집 설정·종단 수용·원본 바이트를 점검할 단서입니다. 열린 포트·응답 부재·traceroute 별표·프로토콜 이름만으로 침해나 회피 성공을 확정하지 않습니다. 센서 시각·방향·드롭·캡처 길이·재조립·암호화와 단말/서버/방화벽/리졸버 기록을 연결하세요.

이번 개정은 교재13쪽의 설명·그림과 자체 바이트·계산·관측 장부를 대조한 범위입니다. 과거 여섯 실습 파일과 워크북 검토 기록은 별도 자료로 참고했으며, 원본 워크북·PCAP이나 실제 traceroute·필터 엔진을 이번에 실행한 결과가 아닙니다. 원본문항 최종 대응과 실제 수신·경로 시험은 미해결 범위로 유지합니다.

21. 복습 · 조건을 바꾸어 생각하기

질문 1. UDP Length 72면 데이터는 몇 바이트인가요?

일반 조건에서는 72-8=64바이트입니다.

질문 2. UDP에서 응답도 ICMP 오류도 없으면 열린 포트인가요?

그것만으로 확정할 수 없습니다. 필터·손실·응용 요구 조건 등도 검토합니다.

질문 3. traceroute의 뒤 홉 RTT가 앞 홉보다 작으면 모순인가요?

각 탐사와 돌아오는 경로·처리 지연이 다를 수 있습니다. 인접 링크 지연으로 단순 빼지 않습니다.

질문 4. UDP에 순서 번호가 없으면 응용도 신뢰성을 구현할 수 없나요?

응용과 상위 프로토콜이 번호·확인·재시도·혼잡 제어를 설계할 수 있습니다. UDP 자체의 기능과 그 위의 기능을 구분합니다.

질문 5. Protocol17과 목적지 포트17은 같나요?

아닙니다. 전자는 IP가 UDP를 식별하는 번호이고 후자는 UDP 서비스 필드입니다. IPv6 확장 헤더가 있으면 Next Header 연결을 따라 읽습니다.

질문 6. Length8과48의 데이터 길이는?

각각0바이트와40바이트입니다. UDP 헤더8을 포함하는 값이므로8을 빼며, 0바이트 데이터도 헤더는 있습니다.

질문 7. IPv4 MTU1500에서 UDP 데이터 예산은?

IP20·UDP8·옵션 없음 조건에서1500−20−8=1472바이트입니다. IPv6 기본 헤더40이면1452바이트이며 터널·확장 헤더는 예산을 더 줄일 수 있습니다.

질문 8. ABC의 마지막00 패딩을 보내면 Length도12인가요?

예제의00은16비트 체크섬 계산용입니다. 전송 데이터 ABC는3바이트라 UDP 길이는11입니다. 패딩을 실제 데이터로 추가한 별도 전송과 구분합니다.

질문 9. UDP 체크섬 계산이0000이면 어떤 값으로 전송하나요?

ffff로 표현합니다. IPv4에서 전송 필드0000의 미사용 표현과 구분하기 위함입니다. 일반 IPv6 UDP의 체크섬0은 기본 규칙상 허용되지 않습니다.

질문 10. Jumbo값65544·확장 헤더8이면 실제 UDP와 데이터 길이는?

실제 UDP는65544−8=65536, 데이터는65536−8=65528바이트입니다. 두8의 역할은 확장 헤더와 UDP 헤더로 다릅니다. 가상 헤더에는 실제 UDP 길이를 씁니다.

질문 11. TTL1 탐사가 만료되면 그 패킷이 TTL2로 다시 전달되나요?

아닙니다. 송신자가 새 TTL2 탐사를 보냅니다. 만료된 원래 탐사와 오류 응답, 다음 탐사는 서로 다른 IP 패킷입니다.

질문 12. 가상 장부에서 인용 UDP 목적지40004는 어느 탐사인가요?

TTL2 묶음의 두 번째 탐사 후보입니다. 실제로는 주소·출발지 포트·시각·식별 정보까지 맞춰야 하고 응답 순서가 탐사 순서와 같을 필요는 없습니다.

질문 13. 세 홉에 세 탐사와 각각 한 ICMP이면 총 몇 개인가요?

가정한 UDP9개와 ICMP9개로18개 IP 패킷입니다. ARP·손실·추가 제어·재시도는 제외했으며 고정 실측값이나 Ethernet 프레임 총수가 아닙니다.

질문 14. 10.000초 송신·10.012초 수신과 홉 RTT18/11ms는 어떻게 읽나요?

첫 왕복은0.012초=12ms입니다. 서로 다른 홉의18과11을 빼−7ms 링크라고 하지 않습니다. 경로·응답 처리·측정 시각이 다릅니다.

질문 15. DNS 후보 응답은 ID 하나만 맞으면 끝인가요?

주소·포트·시각·질문과 응답 코드를 함께 맞춥니다. 16비트 ID는 반복될 수 있으며 응용 성공이나 위조 방지까지 ID 하나가 보장하지는 않습니다.
