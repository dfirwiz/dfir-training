이벤트가 TSV 로그로 남는 과정을 이해하고 zeek-cut, UID 피벗, 로그 생성 조건과 바이트 계산을 증거 범위에 맞게 해석합니다.

학습 범위

넷째 날 7강에서는 Zeek의 이벤트가 로그로 남는 흐름, TSV 로그의 머리말과 필드, zeek-cut으로 필요한 열을 읽는 방법, 여러 로그를 uid로 연결하는 원리를 배웁니다. 모든 값은 문서용 주소로 만든 정상 합성 예제이며 실제 캡처나 운영 로그를 실행한 결과가 아닙니다.

1. 이벤트는 경보가 아니라 기록할 기회입니다

센서가 DNS 질의를 보았다고 해서 그 질의가 곧 공격이라는 뜻은 아닙니다. Zeek의 이벤트는 “분석 과정에서 의미 있는 상태나 데이터가 도착했다”는 알림입니다. 기본 스크립트는 그 정보를 dns.log 같은 구조화 로그에 남길 수 있고, 사이트 스크립트는 조건을 더 살펴 notice를 만들 수도 있습니다. 사건 조사자는 이벤트 발생, 로그 기록, 위험 판단을 서로 다른 단계로 봐야 합니다.

병원 접수표를 떠올려 보세요. 접수표는 환자가 왔다는 사실과 시간·창구를 기록하지만 진단 결과는 아닙니다. Zeek 로그도 비슷합니다. 다만 이 비유의 한계는 패킷 누락·암호화·분석기 비활성화 때문에 접수 자체가 기록되지 않을 수 있고, 한 연결에서 여러 프로토콜 로그가 생길 수 있다는 점입니다.

2. TSV 로그는 머리말이 데이터 사전입니다

Zeek의 기본 텍스트 로그는 TSV, 즉 탭(tab) 문자로 열을 구분하는 형식입니다. 파일 위쪽의 #separator, #fields, #types 같은 머리말은 구분자, 필드 이름, 자료형을 알려 줍니다. 스크립트와 버전에 따라 필드가 늘거나 달라질 수 있으므로 외운 열 번호보다 현재 파일의 머리말을 먼저 읽는 습관이 안전합니다.

합성 conn.log를 읽을 때 먼저 확인할 요소
요소뜻해석할 때 주의할 점
#fields각 열의 이름과 순서로컬 스크립트가 필드를 추가할 수 있으므로 파일마다 확인
ts관측 시각을 나타내는 epoch 기반 값센서 시간대·동기화·수집 지연을 별도로 확인
uid해당 Zeek 실행에서 연결을 잇는 식별자해시나 영구 장치 ID가 아니며 다시 처리하면 달라질 수 있음
id.orig_h/p연결을 시작한 쪽의 주소와 포트항상 내부 클라이언트라는 뜻은 아니며 방향·NAT를 확인
id.resp_h/p응답한 쪽의 주소와 포트서비스 성공이나 애플리케이션 결과를 보장하지 않음
service분석기가 식별한 응용 프로토콜포트 추측과 다르며 분석기·암호화·누락의 영향을 받음

예를 들어 id.resp_p의 점은 중첩된 id 레코드 안의 응답 포트를 뜻합니다. orig는 originator, 즉 이 연결을 시작한 쪽이고 resp는 responder입니다. “서버”와 “클라이언트”라는 역할을 주소 위치만 보고 고정하지 않고 실제 연결 방향과 자산 기록으로 확인합니다.

3. zeek-cut은 필요한 열을 이름으로 고릅니다

zeek-cut은 Zeek TSV의 머리말을 읽어 지정한 필드만 출력하는 도구입니다. 예시 명령 zeek-cut -m -d ts uid id.orig_h id.resp_h service에서 -m은 선택한 열 이름도 함께 표시하고, -d는 epoch 시각을 사람이 읽기 쉬운 날짜로 바꿉니다. 뒤의 항목들은 출력할 필드 이름입니다. 입력은 파이프나 리디렉션으로 전달합니다.

# 형식 설명용 예시이며 이번 실행에서 실행하지 않았습니다.
zeek-cut -m -d ts uid id.orig_h id.resp_h service < conn.log

조건을 바꿔 JSON 로그를 쓰거나 머리말이 없는 임의 TSV에 이 명령을 적용하면 같은 방식으로 동작하지 않습니다. 또한 사람이 읽는 날짜가 나왔다고 센서 시계가 정확하다는 뜻은 아니에요. NTP 상태, 시간대, 캡처 인터페이스와 수집 지연을 함께 기록합니다.

4. uid는 같은 연결의 로그를 잇는 외래 키처럼 씁니다

conn.log에서 합성 UID Cdemo7A2를 찾았고 같은 값이 http.log와 weird.log에도 있다고 합시다. 이는 한 Zeek 실행 안에서 그 기록들이 같은 연결과 관련됐다는 강한 연결 고리입니다. 데이터베이스의 외래 키처럼 다른 표를 잇는다고 생각하면 편합니다.

하지만 UID는 패킷의 5-튜플을 해시한 값이나 장치의 영구 식별자가 아닙니다. 같은 캡처를 다시 처리하면 UID가 달라질 수 있고, 서로 다른 센서에서 우연히 같은 문자열이 보여도 같은 연결이라고 자동 보장하지 않습니다. 센서 ID, 캡처 시간, 주소 변환과 자산·서버 요청 ID를 함께 보존해야 합니다.

구분내용판단 범위
관측conn.log·http.log·weird.log에 Cdemo7A2가 존재현재 Zeek 실행에서 같은 연결 관련 기록

5. 로그 이름보다 생성 조건과 필드가 더 중요합니다

conn.log는 연결 요약, dns.log는 DNS 활동, http.log는 해석된 HTTP 메시지, weird.log는 분석기가 예상 밖이라고 본 상태를 담습니다. loaded_scripts.log는 시작 때 불러온 스크립트 검증에, reporter.log는 분석·스크립트 문제를 확인하는 데 도움이 됩니다. 특정 로그가 없으면 먼저 그 프로토콜이 관측됐는지, 분석기가 로드·활성화됐는지, 트래픽이 암호화됐는지 확인합니다.

교재의 오래된 고정 경로·매시간 회전 설명을 현재 모든 배포의 기본값으로 일반화하지 않습니다. 현재 Zeek 로그 프레임워크에서 독립 실행의 파일 로그는 기본적으로 현재 작업 디렉터리를 쓰며, ZeekControl과 사이트 설정이 디렉터리·회전·압축을 바꿀 수 있습니다. 스트림은 필드 집합을, 필터는 어떤 기록과 열을 쓸지, writer는 TSV 같은 실제 출력 형식을 담당합니다.

6. 바이트 합계도 방향과 누락을 붙여 계산합니다

정상 합성 연결 세 개의 orig_bytes가 1,200B, 850B, 50B라면 합은 1,200 + 850 + 50 = 2,100B입니다. resp_bytes가 400B, 1,500B, 120B라면 400 + 1,500 + 120 = 2,020B입니다. originator 기준 차이는 2,100 - 2,020 = 80B입니다.

이 80B 차이만으로 업로드나 유출을 말할 수 없습니다. 값은 응용 페이로드 기준일 수 있고 링크·IP·TCP 오버헤드와 재전송 계산 방식이 다르며, missed_bytes가 있으면 관측 자체가 불완전할 수 있습니다. 조건을 바꿔 한 연결에 50MB 송신이 추가돼도 승인된 백업일 수 있으므로 단말 프로세스·사용자 작업·목적지 서버 수신 기록을 연결합니다.

복습과 해설

1. dns.log 한 줄이 있으면 악성 DNS 활동인가요?
아닙니다. DNS 분석 이벤트가 기록됐다는 관측입니다. 질의·응답·자산 기준선과 리졸버·단말 기록으로 의미를 판단합니다.
2. #fields를 먼저 읽는 이유는 무엇인가요?
버전과 사이트 스크립트가 열을 바꿀 수 있기 때문입니다. 고정 열 번호보다 현재 파일이 선언한 이름과 자료형이 신뢰할 기준입니다.
3. zeek-cut -m -d에서 두 옵션은 무엇을 하나요?
-m은 필드 이름을 표시하고 -d는 epoch 시각을 사람이 읽는 날짜로 바꿉니다. 시간 정확성 자체를 보증하지는 않습니다.
4. UID가 같으면 서로 다른 센서에서도 같은 연결인가요?
자동으로 그렇지 않습니다. UID는 한 Zeek 실행 안의 피벗 키입니다. 센서·시간·주소 변환과 다른 공통 식별자를 함께 확인합니다.
5. 로그가 없으면 프로토콜도 없었다고 결론 내려도 될까요?
안 됩니다. 캡처 누락, 암호화, 분석기 비활성화·실패, 저장 필터와 회전·전송 문제를 먼저 확인합니다.

공식 자료와 확인일
