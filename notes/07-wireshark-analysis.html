1. 패킷 하나를 열기 전에 조사할 범위를 정한다

가상의 조사 상황을 하나 더 붙여 볼까요? 사용자는 “10시14분쯤 메일 링크를 눌렀다”고 기억하고, 분석가에게는 수십만 패킷이 담긴 파일 하나가 전달됐습니다. 지금 필요한 것은 가장 진한 색의 줄을 누르는 일이 아니라, 이 자료가 그 시각·단말·경로를 볼 수 있는 자료인지부터 확인하는 일입니다. 범위가 다른 자료를 아무리 자세히 읽어도 사건의 빈칸을 채우기 어려울 수 있죠.

도서관에서 책을 찾는 일과 비슷합니다. 서가가 어느 분야인지 확인하고 목차를 훑은 뒤 필요한 장을 읽으면 효율적입니다. 파일 속성은 자료의 범위, 계층 통계는 구성, 대화 통계는 자세히 볼 통신을 고르는 데 도움을 줍니다. 다만 책의 목차와 달리 이 통계는 센서가 확보하고 도구가 해석한 부분만 설명합니다. 네트워크의 모든 사실이 이미 색인돼 있다는 뜻은 아닙니다.

피싱은 사용자를 속여 링크 접근이나 정보 제공 같은 행동을 유도하는 방식입니다. 의심 메일을 받았다는 사실과 악성 파일을 실행했다는 사실 사이에는 확인해야 할 단계가 있습니다. 파일명·요청 문자열은 그 연결을 조사할 단서이며, 정상 파일명으로 다른 내용을 보내거나 요청이 실패하는 경우도 생각해야 합니다. 본문에서는 실제 악성 파일이나 원본 통신을 공개하지 않고 독립적인 예시로 조사 질문을 만듭니다.

6강에서는 패킷 목록에서 한 줄을 골라 상세 정보와 바이트를 대조했습니다. 이번에는 그 한 줄을 어떤 근거로 고를 것인가를 배웁니다. 패킷이 수십만 개라면 처음부터 끝까지 같은 비중으로 읽기 어렵습니다. 먼저 자료의 시간 범위와 구성을 파악하고, 확인할 통신을 좁혀 가야 합니다.

출발점으로 피싱 의심 신고를 생각해 보겠습니다. 사용자가 메일의 링크를 눌렀고 다운로드 페이지에 접속했을 가능성이 있다는 정보와, HTTP 요청에서 찾을 만한 파일 관련 표식이 전달되었다고 가정합니다. 이때 바로 ‘악성 파일을 내려받아 실행했다’고 적으면 여러 단계를 건너뛰게 됩니다. 메일 전달, 링크 접근, 응답 데이터 수신, 파일 저장, 실행은 각각 다른 증거로 확인해야 하는 활동입니다.

원문의 사례도 피싱과 관련된 HTTP 표식을 조사 단서로 제공합니다. 다만 해당 실습 PCAP은 제공되지 않았으므로 이 노트에서는 원문 파일을 직접 분석한 결과를 제시하지 않습니다. 아래 주소·시각·숫자·요청 예시는 학습을 위해 새로 만든 가상 자료입니다. 원문의 화면에서 읽은 정보와 실제 파일을 실행해 확인한 결과를 혼동하지 않겠습니다.

예를 들어 https://download.example/report?filename=notice.pdf는 문서용 도메인으로 구성한 가상 단서입니다. 파일명처럼 보이는 값은 요청의 의미를 조사할 출발점이지, 내려받은 바이트의 실제 형식이나 악성 여부를 증명하지 않습니다. HTTPS라면 복호화 정보 없이 이 전체 경로가 네트워크 패킷에 평문으로 보인다고 기대해서도 안 됩니다.

2. Statistics에서 큰 그림을 먼저 본다

자료를 열었다면 Statistics 메뉴에서 세 창을 먼저 확인해 보세요. Capture File Properties는 지금 가진 자료가 무엇인지, Protocol Hierarchy는 어떤 계층과 프로토콜이 해석되었는지, Conversations는 어떤 종단 사이에 얼마나 통신했는지 묻는 창입니다. 세 창을 같은 통계의 반복으로 보지 말고 서로 다른 질문에 대응시켜야 합니다.

원문에서 시작하는 파일 열기 명령도 특정 파일을 분석 대상으로 선택하는 단계입니다. 실제 자료가 준비되었다면 다음처럼 사용할 수 있습니다. case.pcap은 예시 이름이며 이 명령을 실행한 결과를 뜻하지 않습니다. 명시적인 -r 없이 파일명을 인자로 주는 방식도 지원됩니다. [1]

wireshark -r case.pcap

패킷 목록 옆에 색이 있는 작은 지도 형태의 영역이 보일 수도 있습니다. 원문 화면의 이 영역은 캡처 안에서 다른 패킷 위치로 이동하는 보조 수단입니다. 색은 패킷 표시 규칙과 연결되므로 빨간색이나 진한색이라는 이유만으로 공격이라고 읽지 않습니다. 도구 모음이나 큰 아이콘을 숨겨 공간을 확보한 화면도 있을 수 있습니다. 배치 차이와 파일 내용의 차이를 구분하세요. 이 기능의 세부 모양보다 지금 선택한 파일·필터·패킷이 무엇인지 확인하는 일이 우선입니다.

세 창은 같은 자료를 서로 다른 단위로 묻습니다

Statistics는 통계 메뉴입니다. Properties는 파일 자체의 속성, Hierarchy는 포함 관계를 가진 계층 구조, Conversations는 종단 사이 통신 묶음이라는 뜻으로 연결해 보세요. 같은 숫자 표가 세 번 나오는 것이 아닙니다. 날짜가 맞지 않는 파일에서 수상한 대화부터 찾거나, 한 주소의 대화만 보고 전체 프로토콜 구성을 설명하면 질문과 자료의 단위가 어긋납니다.

예시 명령의 wireshark는 실행 프로그램이고 -r은 뒤 파일을 읽도록 하는 옵션입니다. case.pcap은 실제 분석할 파일명으로 바꾸는 인자입니다. 두 번째 줄은 파일명을 위치 인자로 주는 같은 목적의 사용법입니다. 새 캡처를 시작하거나 그 파일이 사건 전체를 담았다고 보증하는 명령은 아닙니다. GUI를 사용할 수 있는 환경과 파일 접근이 필요하며 이번 실행 결과로 제시하지 않습니다. [1]

화면의 지도나 색은 이동을 돕는 표시입니다. 같은 파일이어도 색상 규칙·열·프로필·숨긴 도구 모음이 다르면 화면이 달라질 수 있습니다. 프로필(profile)은 여러 분석 설정을 묶어 관리하는 단위입니다. 스크린샷의 위치를 외우기보다 현재 파일명·선택 필터·메뉴 이름과 기능을 기준으로 따라가세요.

3. 파일 속성에서 시간과 관측 조건을 확인한다

Capture File Properties에서는 파일 경로·크기·해시·형식과 캡슐화 정보, 첫 패킷과 마지막 패킷 시각, 가능한 경우 수집 환경과 인터페이스 정보를 확인합니다. 해시는 파일의 바이트에 대응하는 값으로, 같은 자료를 다루는지 확인하는 데 도움이 됩니다. 해시가 있다는 것만으로 수집이 완전하거나 사건 해석이 맞다는 뜻은 아닙니다. [2]

여기서 캡슐화 정보는 파일 속 패킷을 어떤 링크 형식으로 읽어야 하는지와 연결됩니다. Ethernet 캡처와 다른 링크 형식의 캡처에 같은 바이트 오프셋을 적용하면 해석이 틀어질 수 있습니다. 인터페이스 정보도 통신의 실제 경로를 모두 보증하지는 않으므로, 센서 위치와 수집 설정을 따로 기록하는 편이 좋습니다.

가상 사건의 클릭 의심 시각이 2026년 11월 1일 10:14:00 UTC라고 가정하겠습니다. 캡처의 첫 시각이 10:00:00 UTC, 마지막이 10:20:00 UTC라면 해당 시각은 파일의 전체 시간 범위 안에 있습니다. 그 차이는 20분 × 60 = 1,200초입니다. 하지만 ‘사건 시각이 범위 안에 있다’는 것과 ‘그 단말의 해당 통신이 확보되어 있다’는 것은 다른 판단입니다. 수집 지점과 대상, 필터도 맞아야 합니다.

반대로 캡처가 10:15부터 시작했다면 클릭 직후 요청이 빠졌을 수 있습니다. 이것이 속성을 먼저 보는 이유입니다. 한참 검색한 뒤 결과가 없다는 사실만으로 접속 자체가 없었다고 결론 내리는 일을 줄여 줍니다. 시작과 끝 사이에도 수집 중단이나 패킷 누락이 있을 수 있어, 경계 시각만으로 연속 수집을 확정하지 않습니다.

메일 로그와 단말 로그의 시간대도 맞춰야 합니다. 목록의 Time이 14.2라고 보인다고 시계 시각 14시 2분으로 읽지 마세요. Wireshark는 절대 시각, 첫 패킷 이후 초, 직전 패킷과의 차이 등 여러 표시 형식을 지원합니다. 표시 기준을 확인하고 비교할 로그의 시간대와 시계 오차를 함께 검토합니다. 표시 소수 자릿수가 많아졌다고 원본 시각의 정확도가 좋아지는 것도 아닙니다. [3]

현재 문서로 확인한 보완 · 2026년 11월 2일

수집 환경 정보는 라이브 수집이거나 저장 파일에 그 정보가 있을 때 표시됩니다. 공식 가이드는 pcapng가 수집 환경 정보를 지원한다고 설명합니다. 항목이 비어 있다고 사건 당시 장비가 없었다거나, 파일 형식만으로 필요한 메타데이터가 반드시 들어 있다고 단정하지 않습니다. 통계의 Captured·Displayed·Marked 열도 구분해서 읽습니다. [2]

메타데이터도 질문에 맞게 읽습니다

메타데이터(metadata)는 여기서 패킷 기록을 언제·어떤 형식으로 저장했는지 같은 부가 정보를 뜻합니다. 파일 경로는 현재 파일의 위치이며 사건 당시 서버의 파일 경로와 다릅니다. 파일 형식은 PCAP·PCAPNG 같은 저장 규칙이고, 캡슐화는 그 안의 패킷을 어떤 링크 구조로 읽을지와 관련됩니다. 인터페이스 정보는 수집 접점의 설명이지 최종 사용자의 신원을 알려 주는 값이 아닙니다.

해시(hash)는 파일 내용에서 계산한 값입니다. 같은 알고리즘의 해시를 비교하면 같은 바이트의 자료를 다루는지 확인하는 데 도움이 됩니다. 그러나 원본에서 패킷을 추출하거나 주석·메타데이터를 바꾸어 새로 저장하면 패킷 내용이 겹쳐도 파일 해시는 달라질 수 있습니다. 해시가 다르다는 사실과 사건이 다르다는 결론도 구분해야 합니다.

Captured는 수집·파일 범위의 기록, Displayed는 현재 표시 조건에 맞는 기록, Marked는 분석가가 표시해 둔 기록을 보는 열입니다. Marked라고 악성으로 판정된 것은 아닙니다. 예를 들어1,000개 중25개를 표시하고 그중3개에 표시를 해 뒀다면, 현재 표시 비율2.5%와 표시된25개 중 마킹 비율12%는 다른 분모입니다. 같은 창 안에서도 어느 열을 읽었는지 반드시 적어 두세요. [2]

시간 범위가 맞아도 수집이 완전하다는 뜻은 아닙니다

처음과 마지막 시각의 차이는 그 두 기록 사이의 경과 시간입니다. 10:00과10:20 사이에 기록이 있다고 해도 중간5분 동안 센서가 중단됐을 수 있습니다. 반대 방향이 다른 경로를 지났거나 특정 VLAN·인터페이스만 수집했다면 조사할 요청·응답이 일부만 남을 수 있죠. 시각 범위·대상·방향·경로·누락을 함께 확인해야 합니다.

또 상대 시각14.2는 기준점에서14.2초라는 뜻일 수 있습니다. 첫 패킷이10:00:00 UTC라면10:00:14.2 UTC이지14시2분이 아닙니다. 표시 형식 중 ‘직전 표시 패킷 이후’와 ‘직전 수집 패킷 이후’도 다릅니다. 필터로 중간 기록을 숨기면 직전 표시 패킷은 더 앞의 기록일 수 있습니다. 표시 자릿수·기준점·시간대와 원래 타임스탬프의 정밀도·시계 오차를 나누어 보세요. [3]

4. 파일 크기와 패킷 바이트 합계는 다르다

파일 속성의 파일 크기를 그대로 네트워크 전송량이라고 기록하면 안 됩니다. 캡처 파일에는 패킷 데이터뿐 아니라 패킷을 구분하고 시각이나 수집 정보를 저장하기 위한 형식상의 정보도 들어갑니다. 디스크에 저장된 파일의 크기, 저장된 패킷 데이터의 합계, 원래 회선에서 관측된 프레임 길이, 응용 프로그램의 파일 내용은 서로 다른 양입니다.

가상의 압축하지 않은 캡처 파일 크기가 120,000바이트이고, 실제 저장된 패킷 데이터 합계가 100,000바이트라고 가정하겠습니다. 두 값의 차이는 120,000 - 100,000 = 20,000바이트입니다. 이것은 캡처 파일 형식의 부가 정보 등 저장 구조와 대조할 차이이지, 상대에게 추가로 20,000바이트를 보냈다는 뜻이 아닙니다. 실제 파일에서 차이의 원인을 따질 때는 형식·주석·압축과 길이 집계 기준을 확인해야 합니다.

한 패킷을 앞부분만 저장했다면 원래 길이와 캡처된 길이도 다릅니다. 재전송이 있었다면 같은 응용 바이트가 여러 패킷에 포함될 수 있습니다. 따라서 패킷 합계를 가지고 ‘문서 파일이 정확히 몇 바이트 유출되었다’고 바로 쓰지 않습니다. 어떤 길이 필드를 합산했는지와 헤더·재전송·잘림의 영향을 따로 확인해야 합니다.

가상 자료의 저장 패킷이 1,000개라면 이 기준의 평균 크기는 100,000 ÷ 1,000 = 100바이트입니다. 평균은 모든 패킷이 100바이트였다는 뜻이 아니며, 파일 부가 정보까지 합친 평균과도 다릅니다.

단위 표기도 남기세요. 십진수 기준이면 120,000 ÷ 1,000 = 120 kB이고, 1 KiB를 1,024바이트로 두면 120,000 ÷ 1,024 = 117.1875 KiB입니다. 바이트 수가 다른 것이 아니라 표시 단위가 다릅니다. 화면의 KB 표기만으로 단위를 추측하기보다 가능한 경우 원래 바이트 수와 사용한 기준을 함께 적습니다.

봉투 묶음의 무게와 편지 내용의 무게는 다릅니다

편지 여러 통을 상자에 넣어 보관하면 상자·봉투·분류표의 무게도 함께 잽니다. 캡처 파일의 저장 크기에는 패킷 외의 형식 정보가 포함될 수 있다는 점을 이해하는 비유입니다. 다만 실제 파일에는 압축이나 여러 메타데이터 구조도 있으므로 “두 값의 차이는 언제나 같은 크기의 헤더다”라는 공식으로 바꾸지는 마세요.

바이트(byte)는8비트입니다. 바이트 수를 합한 양과 초당 비트 수는 다른 단위입니다. 가상의 저장 패킷 데이터100,000바이트를1,200초 동안 관측했다고 가정하면, 이 집계의 평균은 100,000 × 8 ÷ 1,200 ≈ 666.67비트/초입니다. 분자는 같은 관측 기준의 데이터 양이고 분모는 경과 시간입니다. 이것은 파일의120,000바이트를 쓴 계산과 다르며 실제 회선의 최대 전송 속도를 뜻하지도 않습니다.

평균은 짧은 집중 전송을 가릴 수도 있습니다. 별도의 가상 예시에서90패킷이 각각100바이트,10패킷이 각각1,000바이트라면 합계는 90 × 100 + 10 × 1,000 = 19,000바이트이고 평균은 19,000 ÷ 100 = 190바이트입니다. 실제로190바이트인 패킷이 하나도 없어도 평균은190이 됩니다. 평균만으로 패킷 크기 분포나 큰 파일 존재를 확정할 수 없는 이유입니다.

잘린 캡처라면 헤더에 남은 원래 프레임 길이와 실제 저장 바이트 길이도 다를 수 있습니다. 같은 바이트가 재전송되었다면 여러 번 합산될 수도 있습니다. 어떤 값이 프레임 전체인지, IP 길이인지, TCP 데이터인지, 중복을 제거한 응용 내용인지 구별한 뒤 통계를 연결하세요. 표의 단위·분모·길이 기준이 조사 결론의 일부입니다.

5. Protocol Hierarchy는 계층을 겹쳐 세는 표다

Statistics → Protocol Hierarchy는 해석된 프로토콜을 트리로 보여 줍니다. 한 행은 한 프로토콜의 패킷 수와 바이트 수, 비율 등을 나타냅니다. 이는 목록의 Protocol 열에서 가장 눈에 띄는 이름만 세는 것과 다릅니다. 하나의 Ethernet 프레임 안에 IP와 TCP, 응용 데이터가 함께 들어갈 수 있기 때문입니다. [4]

가상의 파일에 패킷 100개가 있고, 전부 Ethernet과 IPv4를 포함하며 그중 80개에 TCP가 있다고 가정해 보겠습니다. 패킷 기준 비율은 Ethernet 100%, IPv4 100%, TCP 80%입니다. 이를 더하면 280%지만 오류가 아닙니다. 같은 패킷을 서로 다른 계층의 행에서 다시 세기 때문입니다. 각 행은 전체에서 그 프로토콜이 포함된 비율을 묻지, 서로 겹치지 않는 조각으로 나눈 것이 아닙니다.

주요 열도 구분합니다. Packets는 해당 프로토콜을 포함하는 패킷 수, Percent Packets는 그 비율입니다. Bytes와 Percent Bytes는 바이트 양의 집계와 비율입니다. 작은 패킷이 많이 있는 프로토콜과 큰 데이터가 적은 횟수로 오가는 프로토콜은 패킷 비율과 바이트 비율이 다를 수 있습니다. Bits/s처럼 속도를 나타내는 값은 바이트 수 자체와 다른 단위입니다. [4]

TCP가 80개인데 그 아래 HTTP가 5개라고 해서 나머지 75개를 곧바로 수상한 미확인 데이터로 분류하지 않습니다. 연결 제어, 재조립 위치, 암호화, 다른 상위 프로토콜과 해석되지 않은 데이터 등이 영향을 줄 수 있습니다. 위 계층 패킷 수가 아래 행들의 단순 합계와 반드시 일치하는 것은 아닙니다.

이제 피싱 의심 사례로 돌아가 보세요. SMTP와 HTTP는 각각 메일 전달과 웹 접근을 조사할 단서가 됩니다. 그러나 SMTP가 존재한다고 피싱 메일이 실제로 포함되었다는 뜻은 아닙니다. TLS가 많다면 암호화된 연결을 조사할 필요가 있고, 기대한 HTTP가 없다면 해당 통신이 암호화되었거나 수집되지 않았는지 검토합니다. 프로토콜의 유무와 비율은 조사 방향을 정하는 자료이며 사건의 결론 자체는 아닙니다.

평소 내부망에서 거의 사용하지 않는 프로토콜이 보이면 추가 확인할 이유는 생깁니다. 다만 새 업무나 정상 관리 기능일 수도 있으므로 자산 역할과 승인 내역을 대조합니다. 반대로 흔한 HTTPS라는 이유로 안전하다고 종결할 수도 없습니다. 정상 기준은 프로토콜 이름에 더해 그 자산의 역할과 실제 동작을 포함합니다.

포함된 계층과 마지막으로 해석된 계층은 다릅니다

트리(tree)는 한 항목 안에 다른 항목이 포함된 구조를 펼쳐 보는 표시입니다. Ethernet 안에 IPv4, 그 안에 TCP가 있으면 같은 패킷이 세 행의 수에 들어갈 수 있습니다. 피자 한 판을 서로 겹치지 않는 조각으로 나누는 비율과 다르죠. 그래서 이 표를 그대로 “모든 행을 더해100%가 되는 구성비”로 읽으면 안 됩니다.

공식 문서의 End Packets는 그 프로토콜이 해석된 스택의 가장 위쪽, 즉 마지막으로 해석된 프로토콜이었던 패킷 수를 뜻합니다. Packets와 End Packets를 같은 열로 읽지 마세요. TCP가 포함된 기록과 TCP까지만 해석된 기록은 다른 질문입니다. 높은 계층으로 해석되지 않은 원인은 암호화·재조립·누락·설정·형식 등에서 검토해야 하며, 곧바로 숨은 공격으로 채우지 않습니다. [4]

Percent Packets와 Percent Bytes도 같은 비중을 말하지 않습니다. 짧은 제어 패킷은 많이 보이지만 바이트 합계는 작을 수 있고, 적은 수의 큰 데이터 패킷이 바이트 비중을 크게 만들 수도 있습니다. Bits/s는 속도이고 Bytes는 양입니다. 숫자가 큰 행을 찾았으면 어느 열의 값이 큰지부터 말해 보세요.

SMTP는 Simple Mail Transfer Protocol로 메일 전달에 쓰이고, HTTP는 웹 요청·응답을 위한 규칙입니다. TLS는 통신을 보호하는 프로토콜이므로 응용 내용을 감출 수 있습니다. 이런 프로토콜 이름은 사건 가설과 비교할 단서이지 정상·악성의 이름표가 아닙니다. 예를 들어 메일이 웹메일의 HTTPS로 전달됐다면 SMTP가 관측되지 않아도 사용자가 메일을 보지 않았다고 단정할 수 없습니다.

반대로 평소 없던 프로토콜이 나왔다면 먼저 어떤 자산·버전·업무 변경과 연결되는지 확인합니다. 가상화·터널·중첩 헤더가 있으면 같은 패킷에 같은 계층이 여러 번 보일 수도 있으니, 트리의 어느 위치를 보는지도 남기세요. 통계는 도구가 해석한 범위를 설명하며, 해석에 필요한 바이트가 없으면 실제 통신 전체와 차이가 날 수 있습니다.

6. Conversations에서 주소와 포트의 묶음을 읽는다

Statistics → Conversations에서 conversation은 두 종단 사이에 관측된 통신을 묶은 것입니다. IP 탭은 주소 쌍을 보는 반면 TCP·UDP 탭은 포트 정보도 보여 줍니다. 탭을 바꾸면 같은 파일이라도 집계하는 묶음이 달라집니다. 주소 쌍 하나 안에 여러 포트 조합의 통신이 들어갈 수 있으므로 행 수가 같을 필요가 없습니다. [5]

다음은 TCP 탭의 기본 개념을 설명하는 가상 표입니다. 문서용 주소를 사용했고, 실제 PCAP에서 추출한 행이 아닙니다. 예시의 A는 조사 단말로 가정했지만 실제 화면의 A·B라는 글자 자체가 내부·외부, 클라이언트·서버를 보증하지는 않습니다.

첫째 행과 둘째 행은 IP 주소 쌍이 같지만 출발지 포트가 다릅니다. IP 수준의 묶음으로 보면 함께 보일 수 있는 활동을 TCP 포트 조합으로 나누어 보는 것입니다. 443번이나 25번이라는 번호는 예상 서비스를 생각할 단서지만 실제 응용 프로토콜의 확정 근거는 아닙니다. 목록과 상세 패킷으로 돌아가 해석과 바이트를 확인해야 합니다.

Address A와 Address B는 묶음의 양쪽 주소이고 Port A와 Port B는 각 주소 쪽 포트입니다. Packets A → B와 Packets B → A는 방향별 패킷 개수이며, Bytes A → B와 Bytes B → A는 방향별 바이트 양입니다. 같은 방향이라도 패킷 개수와 데이터 양은 다른 질문에 답합니다.

Packets는 패킷 개수이고 Bytes는 바이트 양입니다. 방향 열은 어느 종단에서 어느 종단으로 관측된 바이트가 집계되었는지 구분합니다. 첫째 행의 합계는 6,000 + 54,000 = 60,000바이트이며, B → A 비율은 54,000 ÷ 60,000 × 100 = 90%입니다. 내려받기 형태를 검토할 단서가 될 수 있지만, 이 숫자를 그대로 ‘악성 파일 54,000바이트를 받았다’로 바꾸면 안 됩니다. 헤더와 제어·재전송 등의 포함 기준, 실제 응용 내용과 처리 결과를 더 확인해야 합니다.

반복된 주소·포트 조합의 행을 보는 것도 도움이 됩니다. 다만 TCP 통신의 정확한 분리와 집계는 도구의 상태 추적·설정에도 영향을 받을 수 있습니다. 한 행을 곧바로 하나의 사용자가 한 번 실행한 작업이나 파일 한 개라고 대응시키지 마세요. 단말 프로세스와 실제 스트림, 응용 로그가 필요합니다.

탭 표시 방식 보완

오래된 화면 설명처럼 ‘탭이 없으면 해당 프로토콜 데이터도 반드시 없다’고 일반화하지 않습니다. 현재 공식 문서는 Protocol 선택으로 표시할 통계 종류를 정하고 프로필에 설정을 저장할 수 있다고 설명합니다. 탭이 보이지 않을 때는 버전·표시 설정·프로필도 확인합니다. 데이터 존재 여부는 계층 통계와 관련 패킷으로 교차 확인하세요. [5]

종단 두 개를 묶는 기준을 먼저 적습니다

종단(endpoint)은 선택한 계층에서 통신의 한 끝을 뜻합니다. IP라면 주소, TCP·UDP라면 주소와 포트를 함께 보게 됩니다. 포트(port)는 통신 접점을 구분하는 번호입니다. A와 B는 표의 양쪽을 구분하는 기호이지 “A는 공격자, B는 피해자”라는 뜻이 아닙니다. 방향 열을 외부 유출이나 내부 수신으로 옮기려면 각 주소의 실제 역할을 먼저 알아야 합니다. [5] [7]

기존 가상 표의 첫 두 행을 같은 IP 주소 쌍의 범위로 묶으면 바이트 합계는 60,000 + 5,000 = 65,000입니다. TCP 포트 조합으로 나누면 각각60,000과5,000바이트입니다. 이 집계 관점이 달라졌다고 데이터가 새로 생기거나 사라진 것은 아닙니다. 다만 실제 도구의 행 구분은 상태 추적과 설정도 반영하므로 단순히 주소가 같다는 이유로 서로 다른 연결의 응용 의미를 합치지는 않습니다.

세 행 전체를 합치면 A→B는 6,000 + 3,000 + 8,000 = 17,000바이트이고, B→A는 54,000 + 2,000 + 4,000 = 60,000바이트입니다. 이 세 행의 합계는77,000바이트입니다. 첫 행의 B→A 비중90%를 세 행 전체의 비중이라고 복사하면 분모가 바뀌어 틀립니다. 각 행의 관측량과 선택한 집계 범위를 함께 남겨야 합니다.

문자열로 표시된 호스트 이름이나 서비스 이름은 이름 변환 설정의 결과일 수 있습니다. 같은 숫자 주소·포트를 보고 있는지 확인하고, 이름 하나를 실제 사용자나 특정 프로세스의 증명으로 사용하지 않습니다. DNS 리졸버 기록, 단말의 연결·프로세스 기록과 서버 로그가 필요한 이유입니다. 리졸버는 이름 질의를 처리해 주소 등의 답을 찾는 구성 요소입니다.

또 Endpoints의 행 수는 종단 수이고 Conversations의 행 수는 통신 묶음 수입니다. 종단10개가 서로 통신한다고 해서 대화도10개여야 하는 것은 아닙니다. IP주소 수를 실제 컴퓨터·사용자 수와 곧바로 같다고 놓는 것도 피하세요. 프록시·주소 변환·하나의 장비의 여러 주소 같은 조건이 있을 수 있습니다. [7]

7. 정렬은 결론을 내리는 버튼이 아니라 후보를 고르는 방법이다

Conversations의 열 머리글을 눌러 패킷 수나 바이트 수 순으로 정렬하면 많은 통신을 빠르게 찾을 수 있습니다. 오름차순·내림차순 표시를 확인하고 필요하면 다시 눌러 순서를 바꿉니다. 하지만 큰 값이 항상 가장 위험한 것은 아닙니다. 정상 백업은 클 수 있고, 계정 탈취나 명령 전달은 작은 통신으로도 이루어질 수 있습니다.

피싱 사례라면 양만 보지 않고 신고된 시각, 조사 단말, 목적지와 연결 지속시간을 함께 비교합니다. 앞의 가상 표에서 첫째 행의 수신량이 많다는 이유만으로 그것을 사건 통신으로 확정하지 않습니다. 클릭 의심 시각과 겹치는지, 목적지가 메일 단서와 이어지는지, 단말의 브라우저 연결 기록과 일치하는지 확인한 뒤 자세히 볼 후보로 올립니다.

Limit to display filter도 중요합니다. 공식 문서상 이 설정은 현재 표시 필터에 맞는 통신으로 범위를 제한하며, 필터가 적용된 채 창을 열면 자동으로 설정될 수 있습니다. ‘전체 파일의 상위 통신’이라고 썼는데 실제로는 특정 주소의 필터 결과만 보았다면 보고 범위가 잘못됩니다. 탭·정렬 열·필터와 제한 설정을 함께 기록합니다. [5]

시작 시각이 절대 시각인지 파일 시작 기준 상대 시각인지도 확인하세요. 가상의 파일 시작이 10:00:00 UTC이고 통신의 Rel Start가 840초라면, 840 ÷ 60 = 14분이므로 해당 통신 시작은 10:14:00 UTC입니다. Duration이 12초라면 그 관측 구간은 대략 10:14:12까지입니다. 이는 첫·마지막 관측 패킷에 근거한 통신 구간이지 사용자가 프로그램을 실행한 전체 시간이라는 뜻은 아닙니다.

방향별 큰 바이트 수는 유출 조사에서도 단서가 됩니다. 그러나 A → B가 외부 방향인지 알려면 실제 자산·경로를 알아야 하고, 큰 양이 반출 금지 자료인지 알려면 내용과 업무 허용 여부가 필요합니다. 암호화된 통신에서는 특히 방향·양·시간을 근거로 가설을 세우고, 파일 접근·업로드 기록과 프록시·서버·단말 로그로 검증해야 합니다.

같은 표를 정렬해도 질문이 다르면 후보가 달라집니다

Packets 내림차순은 많이 오간 패킷을, Bytes 내림차순은 집계 바이트가 많은 통신을 먼저 보여 줍니다. B→A만 정렬하면 특정 방향의 양을 보게 됩니다. 어느 방식도 악성 점수를 자동 계산하는 것은 아닙니다. 가상 신고 시각과 맞는 작은 연결이, 시간대가 다른 큰 백업보다 먼저 조사할 이유가 있을 수 있습니다.

Limit to display filter는 “현재 표시 필터로 제한”이라는 뜻입니다. 창을 열기 전에 필터를 적용했는지, 제한 옵션이 켜졌는지, 표에 Total Packets나 Percent Filtered 같은 별도 값이 표시되는지 확인하세요. 현재 문서는 필터가 먼저 적용됐으면 제한 설정이 자동 활성화될 수 있다고 설명합니다. 열마다 어떤 범위의 값인지 확인하고, 제한된 후보 순위를 전체 파일 순위라고 쓰지 않습니다. [5]

Rel Start는 relative start, 즉 상대 시작이고 Abs Start는 absolute start, 즉 절대 시작입니다. Duration은 관측된 지속 시간입니다. 앞 예시의840초를 파일 시작에 더하면10:14:00이고,12초를 더한 끝은10:14:12입니다. 하지만 사용자가 그 전에 프로그램을 열었는지나 마지막 패킷 뒤에도 작업을 계속했는지는 이 구간만으로 알 수 없습니다.

첫 가상 행의 양방향60,000바이트가12초의 같은 관측 구간에 걸쳤다고 추가로 가정하면 평균 합산 속도는 60,000 × 8 ÷ 12 = 40,000비트/초입니다. 방향별로는 A→B가 6,000 × 8 ÷ 12 = 4,000비트/초, B→A가 54,000 × 8 ÷ 12 = 36,000비트/초입니다. 초당 바이트로 계산한 수를 그대로 Bits/s 열과 비교하지 마세요. 이것은 해당 집계의 평균이지 회선 용량이나 순간 최고 속도가 아닙니다.

8. 통계에서 구체적인 조사 계획으로 넘어간다

지금까지의 흐름을 가상 피싱 신고에 적용해 보겠습니다. 처음에는 ‘사용자가 링크를 눌렀을 가능성’만 있습니다. 파일 속성에서 조사 시각과 수집 지점이 맞는지 확인하고, 계층 통계에서 해석 가능한 메일·웹·암호화 통신을 파악합니다. 그런 다음 주소·포트 쌍과 시각·방향·양을 이용해 관련 통신 후보를 고릅니다.

이렇게 고른 후보는 다음 단계에서 패킷 흐름과 스트림을 읽을 대상입니다. 통계만으로는 메일에 담긴 링크, 웹 요청의 실제 내용, 응답 파일과 실행 결과를 모두 연결할 수 없습니다. 다음 회차에서는 TCP 스트림과 HTTP 객체를 분석하는 방법으로 이어갑니다. 이번 회차를 마쳤다는 것은 상세 분석할 후보와 그 선택 이유를 설명할 수 있다는 뜻입니다.

조사 메모는 다음처럼 관측과 미확인을 함께 남길 수 있습니다. 실제 사건 보고가 아닌 작성 예시입니다.

캡처의 시간 범위는 신고된 시각을 포함한다. 현재 수집 위치에서 조사 단말과 외부 주소 사이의 TCP 통신 후보를 확인했으며, 그중 한 통신에서 상대 측 방향의 바이트가 많다. 파일 범위·필터·통계 탭과 정렬 조건을 기록했다. 해당 통신이 신고된 링크 접근인지, 어떤 파일을 받았고 실행했는지는 아직 확인되지 않았다. 관련 패킷과 브라우저·메일·단말 로그를 추가 대조한다.

현대에도 이런 패킷 분석은 유효합니다. 암호화되어 있어도 관측된 주소·시각·양과 연결 흐름을 근거로 조사 대상을 정할 수 있습니다. 다만 복호화 조건 없이 암호화된 본문을 읽을 수 있다고 기대하지 않으며, 본문이 안 보인다는 이유로 정상이라고 종결하지도 않습니다. Wireshark의 TLS 분석도 적절한 비밀정보 등 복호화 조건을 구분합니다. [6]

통계의 결과는 다음 증거를 고르는 이유가 됩니다

첫 후보의 방향 비대칭과 클릭 의심 시각이 맞았다면, 다음에는 실제 요청·응답과 앞뒤 연결을 읽습니다. 링크의 도메인과 연결 주소가 어떻게 이어졌는지, 프록시가 대신 연결했는지, 브라우저의 다운로드 기록과 단말 파일 활동이 있는지를 확인할 수 있겠죠. 후보 선정은 상세 분석의 시작이며 완료 판정이 아닙니다.

조건을 바꾸어 같은 양의 통신이 신고보다 한 시간 앞에 있었거나 승인된 업데이트 작업과 연결됐다고 해 보겠습니다. 큰 숫자는 같아도 우선순위 근거는 달라집니다. 반대로 작은 연결이 의심 시각의 새 프로세스·비정상 인증과 이어지면 우선 조사할 이유가 생길 수 있습니다. 통계는 시간·자산·내용·실제 활동 증거와 함께 판단합니다.

원하는 응답이 없을 때도 원본 파일과 수집 범위를 되짚습니다. 한 방향만 보였는지, 캡처가 일찍 끝났는지, 비대칭 경로와 표시 필터·재조립 설정이 영향을 줬는지 확인하세요. 방화벽 차단 기록이 있으면 같은 연결·시점과 연결하고, 서버가 요청을 처리한 기록이 있으면 처리 결과까지 구분합니다. 관측 부재를 실패·차단·무해함 중 하나로 곧바로 바꾸지 않습니다.

관련 로그를 대조할 때도 시각이 비슷하다는 이유만으로 묶지 마세요. 시간대·시계 오차와 실제 계정·프로세스·요청 식별자 같은 연결 근거를 찾습니다. 암호화된 통신의 반복 주기·방향·양은 가설을 세우는 단서가 되지만, 읽지 못한 명령이나 반출 파일 내용을 그 숫자로 채워 넣을 수는 없습니다.

9. 이번 회차의 증거 구분

패킷으로 확인 가능한 사실

파일에 확보된 시간 범위, 해석된 계층, 조건에 맞는 주소·포트 쌍과 패킷·바이트 집계입니다. 선택한 필터·탭·길이 기준을 명시해야 합니다.

단독으로 확정할 수 없는 부분

모든 경로의 완전한 수집, 실제 사용자와 실행 프로세스, 파일 내용과 저장·실행, 암호화 본문의 의미, 공격 성공과 반출의 정당성입니다. 응답 부재만으로 차단 성공이나 무해함을 확정하지 않습니다.

함께 확인할 자료

센서 위치·필터·손실과 시계 정보, 메일 전달·클릭 기록, 브라우저·프록시·DNS·서버 로그, 단말 프로세스와 파일 활동, 업무 승인과 자산 역할입니다.

보고서의 숫자 옆에는 “어느 파일·계층·필터·방향·기간·길이 기준인가”를 붙입니다. 예를 들어 “큰 다운로드”라고만 적기보다 “가상 TCP통계 첫 행에서 B→A54,000바이트,양방향 합계60,000바이트 중90%;실제 응용 파일 크기와 수신·실행 결과는 미확인”처럼 관측과 결론의 경계를 남길 수 있습니다.

한 통계가 다른 통계와 다르면 오류라고 결정하기 전에 기준을 맞춥니다. 저장 파일 크기와 패킷 합계,IP주소 쌍과TCP포트 조합,전체 파일과필터 결과는 같은 분모가 아닙니다. 서로 다른 숫자가 각자의 질문에 맞게 정확할 수도 있습니다.

10. 복습 — 숫자 옆에 판단의 조건을 적기

다음 문제는 학습을 위해 새로 구성했습니다. 실습 PCAP의 실제 결과를 묻는 문제가 아닙니다.

질문 1: 사건은 10:14에 발생했을 가능성이 있고 캡처는 10:00~10:20입니다. 사건 패킷이 들어 있다고 확정할 수 있을까요?

해설: 시간 범위에 들어갈 수 있다는 조건은 맞지만 수집 지점·대상·필터·누락을 확인해야 합니다. 시간대와 시계 오차도 맞춥니다. 시작과 끝의 시각만으로 중간이 완전하다는 보증은 없습니다.

질문 2: 파일이 120,000바이트인데 저장 패킷 합계는 100,000바이트입니다. 20,000바이트가 유실되었나요?

해설: 두 값은 집계 대상이 다릅니다. 캡처 저장 형식에는 부가 정보가 들어가므로 차이를 곧바로 통신 유실로 보지 않습니다. 형식·압축·주석과 실제 길이 집계 기준을 확인합니다. 응용 파일 크기와도 따로 구분합니다.

질문 3: Ethernet 100%, IPv4 100%, TCP 80%를 더하면 280%입니다. 도구 오류일까요?

해설: 같은 패킷이 여러 계층에 포함되어 중복 집계될 수 있습니다. 서로 겹치지 않는 범주를 나눈 표가 아닙니다. TCP 80개 중 상위 HTTP로 표시되는 수가 적더라도 암호화·제어·재조립 등 다른 설명을 검토합니다.

질문 4: B → A가 54,000바이트이고 반대 방향은 6,000바이트입니다. 무엇을 말할 수 있을까요?

해설: 해당 기준의 합계는 60,000바이트이고 B → A는 90%입니다. 방향 비대칭을 관측했지만 악성 파일의 수신 크기나 성공적인 침해까지 확정한 것은 아닙니다. A·B의 실제 역할과 바이트 집계 기준, 내용·단말 증거를 더 확인합니다.

질문 5: TCP 통계 탭이 없거나 어떤 응용 프로토콜이 보이지 않으면 관련 활동이 없었다고 해도 될까요?

해설: 버전·통계 표시 설정·프로필과 수집 범위, 프로토콜 해석 조건을 확인합니다. 통계 화면에서 보이지 않는 것과 네트워크에서 실제 발생하지 않은 것은 다릅니다. 암호화되어 응용 이름이 드러나지 않을 수도 있습니다.

질문 6: Bytes가 가장 큰 통신을 첫 조사 대상으로 삼으면 항상 적절할까요?

해설: 큰 통신은 좋은 탐색 기준 중 하나지만 정답은 아닙니다. 신고 시각·자산·목적지·방향·업무 맥락을 함께 봅니다. 작은 계정 악용 통신을 놓치지 않도록 하고, 현재 표시 필터에 제한된 순위인지도 확인합니다.

조건을 바꾼 추가 복습

문제 7. Captured 1,000·Displayed 25·Marked 3인 가정에서 두 비율은요?

해설: 표시 비율은 25 ÷ 1000 × 100 = 2.5%입니다. 표시된 25개 중 3개를 마킹했다는 조건에서 마킹 비율은 3 ÷ 25 × 100 = 12%입니다. 전체 1,000개 중 3개의 비율은 0.3%로 다릅니다. 마킹은 악성 판정이 아닙니다.

문제 8. 타임스탬프의 소수 자리를 늘리면 수집 시계가 더 정확해지나요?

해설: 표시 정밀도가 달라져도 원래 시계 오차나 기록 정밀도가 개선되는 것은 아닙니다. 시간 표시 기준·원본 정밀도·시간대·시계 오차를 나누어 확인합니다.

문제 9. 평균 패킷 크기 190바이트면 모든 패킷이 190바이트인가요?

해설: 아닙니다. 90 × 100 + 10 × 1000 = 19000바이트를 100개로 나누면 평균 190이지만, 그 크기의 패킷이 없을 수 있습니다. 평균과 분포를 구별합니다.

문제 10. 파일 시작 10:00:00에서 Rel Start 14.2는 언제인가요?

해설: 기준이 첫 패킷 이후 초라면 10:00:14.2입니다. 14시 2분이 아닙니다. 시간 참조점과 표시 형식이 무엇인지도 확인해야 합니다.

문제 11. 같은 IP 주소 쌍의 두 TCP 행이 60,000·5,000바이트라면 IP 관점 합계는요?

해설: 동일 관측 범위의 그 두 행만 묶는 가정에서 65,000바이트입니다. 포트 조합별로 보면 두 후보입니다. 집계 단위가 달라도 바이트가 새로 생긴 것은 아니며, 두 통신의 업무 의미까지 같다고 합치지는 않습니다.

문제 12. 첫 행 60,000바이트를 12초로 계산하면 속도는요?

해설: 60,000 × 8 ÷ 12 = 40,000비트/초입니다. 방향별은 4,000과 36,000비트/초입니다. 같은 바이트 기준과 관측 구간을 쓴 평균이며 회선 용량·순간 최고 속도가 아닙니다.

문제 13. End Packets와 Packets는 같은 열인가요?

해설: Packets는 해당 프로토콜을 포함하는 패킷 수이고, End Packets는 해석된 스택에서 그 프로토콜이 마지막인 패킷 수입니다. 상위 해석이 없다고 바로 공격으로 분류하지 않고 암호화·재조립·누락·설정을 검토합니다.

문제 14. SMTP가 없으므로 메일을 읽지 않았다고 결론내릴까요?

해설: 웹메일의 HTTPS처럼 다른 방식이 있을 수 있습니다. 수집 위치·시간·방향·암호화·프로토콜 해석과 메일·브라우저 로그를 함께 확인합니다. 관측한 프로토콜 이름만으로 사용자 행위를 확정하지 않습니다.

문제 15. Limit to display filter가 켜진 Bytes 순위를 전체 파일 순위라 써도 될까요?

해설: 현재 제한 범위와 열별 집계 기준을 확인해야 합니다. 필터·탭·정렬 열·제한 설정을 기록하고 전체와 필터 결과의 분모를 구별합니다.

문제 16. 파일 해시가 다르면 서로 다른 사건인가요?

해설: 파일 바이트가 달라졌다는 단서이며 사건 관계는 별도입니다. 추출·다른 저장 형식·주석 변경 등으로 일부 같은 패킷이 있어도 파일 해시가 달라질 수 있습니다. 원본·파생 관계와 실제 패킷을 대조합니다.

워크북 연계 실습

주소 수·연결 수·바이트·지속 시간의 단위를 분리해 기록합니다. 통계에서 대화로 좁히기에서 단계별 설명과 복습을 읽을 수 있습니다. 이 페이지의 기존 자체 예시는 그대로 유지하며, 원본 PCAP을 실행한 출력으로 제시하지 않습니다.

교재는 통계로 후보를 좁히는 원리를 설명하고,워크북은 도구에서 확인할 순서를 연결하며,PCAP은 실제 저장된 관측 바이트를 제공합니다. 기존 검토 기록에는 첫째 날 여섯 캡처·621개 기록의 오프라인 대조가 있습니다. 이 사실을 이번 피싱 사례의 별도 HTTP 캡처를 직접 분석했다는 뜻으로 바꾸지 않습니다. 이번 실행에서는 원본 워크북·PCAP을 다시 분석하지 않았습니다.

연계 실습에서는 먼저 파일 속성의 범위와 단위를 적고,계층별 패킷·바이트 비중을 비교한 뒤,대화의 주소·포트·방향·시작·지속시간을 읽어 보세요. 통계 결과를 적을 때는 필터 제한과 프로필도 함께 남깁니다. 이름·연결·객체·실행이라는 서로 다른 단위를 혼합하지 않는 것이 이번 연습의 중심입니다.
