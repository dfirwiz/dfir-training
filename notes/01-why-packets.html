보안 장비가 있는데도 패킷을 공부하는 이유

경고를 검증하는 과정부터 암호화 환경에서의 분석 가치까지, 사례와 함께 차근차근 설명합니다.

이번 강의는 본 교재 인쇄 4~11쪽에 해당합니다. 학습 자료의 역할, 전체 학습 흐름, 기초와 반복 실습이 필요한 이유, 보안 경고를 검증하는 방법을 다룹니다. 기존 강의의 TLS·QUIC·ECH 보충 설명도 함께 연결합니다.

자료는 구분해서 사용했습니다. 이번에는 본 교재의 해당 페이지와 그림, 최신 사이트 본문을 직접 확인했습니다. 저장소에는 전자 워크북 연계와 첫째 날 PCAP 여섯 개의 기존 검증 기록도 있습니다. 다만 이번 세션에서 워크북 원본과 그 여섯 파일을 다시 열어 분석한 것은 아닙니다. 아래 사건과 관측표는 별도로 만든 가상 학습 예시입니다.

1. 보안 장비가 “공격입니다”라고 알려주면, 조사가 끝난 걸까요?

보안 업무를 시작했다고 생각해 볼게요. 화면에는 여러 서버의 상태가 보이고, 갑자기 다음과 같은 경고가 올라옵니다.

웹 서버를 대상으로 명령 실행 공격 의심 통신이 탐지되었습니다.

‘명령 실행’이라는 말부터 무섭게 느껴지죠. 외부에서 보낸 요청 때문에 서버가 원하지 않는 프로그램이나 명령을 실행할 수 있다는 뜻이니까요.

그런데 여기서 곧바로 “서버가 해킹당했습니다”라고 보고해도 될까요?

아직은 어렵습니다. 경고는 분명 중요한 신호지만, 어떤 조건에 해당하는 통신을 발견했다는 것과 서버가 실제로 침해되었다는 것은 서로 다른 사실이기 때문입니다.

건물의 화재경보기를 떠올려 보세요. 경보가 울렸다면 확인하러 가야 합니다. 하지만 경보음만 듣고 화재의 위치와 규모, 피해까지 모두 알 수는 없겠죠. 실제 불이 났을 수도 있고, 다른 원인으로 감지기가 반응했을 수도 있습니다.

네트워크 보안 경고도 비슷합니다. 분석가는 경고를 출발점으로 삼아 다음 질문을 이어가야 합니다.

“무슨 통신 때문에 울렸을까요?”

“그 통신이 서버까지 도달했을까요?”

“서버는 어떤 응답을 했을까요?”

“서버 안에서 실제로 무슨 일이 일어났을까요?”

이 질문에 근거를 붙여 답하는 것이 이번 과정의 목표입니다. 도구의 화면을 잘 다루는 능력에 더해, 화면에 나온 판단이 어떤 증거에서 나왔는지 검증하는 능력을 기르는 것이죠.

2. 그 증거를 찾으려면 왜 패킷을 알아야 할까요?

회사에서 고객 정보가 담긴 데이터베이스를 운영한다고 해 봅시다. 데이터가 서버 안에 안전하게 저장되어 있어도, 직원이 고객 정보를 조회하거나 프로그램이 보고서를 만들려면 그 정보에 접근하는 과정이 필요합니다.

프로그램과 데이터베이스가 서로 다른 컴퓨터에 있다면, 요청과 결과가 네트워크를 통해 오가겠죠.

웹사이트를 열 때도 마찬가지입니다. 내 컴퓨터가 서버에 무언가를 요청하고, 서버가 필요한 데이터를 돌려줍니다. 네트워크에서는 이러한 데이터를 전달하기 위해 일정한 형식의 전송 단위를 사용합니다. 이 과정에서 우리가 읽게 되는 중요한 단위가 패킷입니다.

배송 상자를 생각하면 감을 잡기 쉽습니다.

상자 겉에는 어디에서 어디로 보내는지 적혀 있고, 안에는 전달할 물건이 들어 있습니다. 패킷에도 전달과 처리를 위한 정보와 운반할 데이터가 있습니다.

  • 헤더(header)는 주소나 처리 방법처럼 해당 단계의 통신을 다루는 데 필요한 정보입니다.
  • 페이로드(payload)는 그 단계에서 운반하는 데이터입니다.

여기서 “해당 단계”라는 표현을 기억해 주세요. 실제 통신은 여러 단계의 포장이 겹치기 때문입니다.

예를 들어 일반적인 HTTPS 통신 중 TCP를 사용하는 경우에는, 이더넷 프레임 안에 IP 패킷이 들어 있고, 그 안에 TCP 헤더와 데이터가 이어질 수 있습니다. HTTPS는 웹 통신을 암호화해 보호하는 방식이고, 이더넷·IP·TCP는 각각 다른 범위의 전달과 처리를 담당합니다. 각 역할은 3강부터 자세히 살펴봅니다.

계층별 헤더와 운반하는 데이터
읽는 위치그 위치의 헤더가 알려주는 정보의 예그 뒤에 실리는 것
이더넷 프레임해당 링크에서 전달할 주소와 종류IP 패킷 등
IP 패킷출발지·목적지 IP 주소, 다음 프로토콜TCP 헤더와 데이터 등
TCP 부분포트, 순서와 확인에 필요한 정보TLS 데이터 등

IP 입장에서 보면 TCP 헤더도 자신이 운반하는 데이터의 일부입니다. 따라서 어떤 계층을 기준으로 읽느냐에 따라 헤더와 페이로드의 경계가 달라집니다.

배송 상자 비유에도 한계는 있습니다. 웹 요청 하나가 패킷 하나에 딱 맞아 들어가는 것은 아닙니다. 하나의 요청이 여러 패킷에 나뉠 수도 있고, 하나의 패킷에 응용 메시지의 일부나 여러 메시지가 들어갈 수도 있습니다.

그래서 분석할 때는 “이 패킷의 내용이 무엇인가?”와 함께 “앞뒤 패킷과 어떤 관계인가?”를 물어야 합니다.

주소가 보인다고 실제 사용자를 바로 알아낸 것도 아닙니다. IP 주소는 관측한 통신의 주소이지, 그 자체가 사람의 신분증은 아니니까요. 포트 번호도 서비스의 단서가 되지만, 번호 하나만으로 프로그램을 확정할 수는 없습니다.

패킷 정보와 판단의 범위
패킷에서 살펴볼 정보답할 수 있는 질문바로 확정하기 어려운 것
출발지·목적지 IP어떤 주소 사이의 통신이 보였는가?실제 사용자와 실행 프로그램
TCP·UDP, 포트어떤 전송 방식과 포트를 사용했는가?실제 응용 프로그램의 정체
시각·크기·방향언제, 어느 방향으로, 얼마나 전송했는가?데이터의 의미와 업무상 정당성
관측 가능한 페이로드어떤 요청·응답 데이터가 실렸는가?암호화되거나 수집되지 않은 내용

TCP와 UDP는 IP 위에서 데이터를 전달하는 데 사용하는 서로 다른 프로토콜입니다. 프로토콜은 통신 상대가 따라야 하는 형식과 처리 규칙이라고 이해하면 됩니다.

이 과정에서 배우는 TCP/IP도 TCP 하나만 뜻하지 않습니다. IP와 TCP, UDP를 비롯해 서로 협력하는 여러 통신 규칙을 묶어 부르는 말입니다.

3. 앞으로 무엇을 어떤 순서로 배우게 될까요?

처음부터 공격 이름을 많이 외우면 더 빨리 실무에 도움이 되지 않을까 싶을 수 있습니다.

그런데 공격 사례만 외워 두면, 처음 보는 통신이 나왔을 때 판단이 막히기 쉽습니다. 반대로 통신의 구조를 이해하면 익숙하지 않은 도구나 공격을 만나도 “어떤 정상 동작이 어떻게 달라졌는가?”부터 따져 볼 수 있습니다.

외국어 공부와 비슷합니다. 자주 쓰는 문장을 통째로 외우는 것도 도움이 되지만, 단어와 문장 구조를 알아야 새로운 문장도 읽을 수 있죠.

패킷의 필드와 값은 단어에, 요청·응답과 프로토콜의 동작은 문장 구조에 비유할 수 있습니다. 필드(field)는 헤더 안에서 정해진 의미를 갖는 항목입니다. 출발지 주소나 길이 같은 것이죠.

행위와 관계 분석여러 연결과 이벤트의 연관성개별 경고를 넘어 어떤 활동이 이어졌을까?
많은 데이터에서 조사 대상 찾기통계, 시각화, 이상 징후 분석수많은 통신 중 무엇부터 살펴봐야 할까?
종합 조사여러 자료를 연결한 사건 분석어떤 일이 있었고, 어느 결론까지 증명할 수 있을까?

Wireshark는 패킷을 사람이 읽기 좋게 해석하고 탐색하는 도구입니다. 이후에는 Snort·Suricata처럼 탐지 규칙을 사용하는 도구와, 통신을 분석해 기록하는 Zeek도 연결해서 이해하게 됩니다.

필요한 패킷을 직접 구성해 동작을 확인하는 방법도 등장합니다. 예를 들어 Scapy는 파이썬에서 패킷을 구성하고 다루는 데 사용하는 도구입니다. 실제로 사용할 때 각 항목을 설명할 것이므로 지금 이름을 외울 필요는 없습니다.

규칙 기반 탐지를 배운 뒤에는 그 한계도 살펴봅니다. 정해진 문자열이나 조건을 잘 잡는 규칙이라도, 표현이 달라지거나 여러 통신에 행위가 나뉘면 놓칠 수 있기 때문입니다.

그다음에는 “공격자가 목표를 이루려면 어떤 행동을 해야 할까?”를 생각하고 관측할 흔적으로 연결합니다. 이런 식으로 위협과 가능한 행동을 구조화하는 접근이 위협 모델링입니다.

데이터가 많아지면 통계와 머신러닝도 도움이 될 수 있습니다. 다만 어떤 기법이 “이상하다”고 표시했다고 해서 자동으로 공격이 증명되는 것은 아닙니다. 평소와 다른 이유를 조사하는 과정은 여전히 필요합니다.

이 모든 단계의 바탕에 패킷과 프로토콜 기초가 놓여 있습니다.

4. 본 교재와 워크북, 실습 파일은 각각 어떻게 사용해야 할까요?

설명 책을 읽는 것과 실제 캡처를 분석하는 것은 다른 작업입니다. 어느 하나만으로 나머지를 전부 대신하기는 어렵습니다.

본 교재에서는 개념과 동작을 이해합니다. 워크북에서는 그 개념을 어떤 질문으로 확인할지 배웁니다. 실제 실습 파일에서는 예상한 구조와 값이 정말 나타나는지 관측합니다.

학습 자료의 역할
자료주된 역할사용할 때 확인할 점
본 교재개념·원리·학습 범위 이해그림과 본문을 함께 읽었는가?
워크북·실습 안내서실습 목적과 조사 순서 연결어떤 파일과 환경을 전제로 하는가?
PCAP 등 캡처 파일실제 저장된 통신 관측수집 위치·시간·포함 범위는 무엇인가?
실습용 가상머신도구와 환경 제공안내서와 도구 버전이 맞는가?
빠른 참조표·색인필드와 문법을 빠르게 찾기의미를 이해한 뒤 찾아 쓰는가?
공식 문서·정오표·유지관리 자료변경 사항과 오류 확인적용 버전과 갱신 시점은 무엇인가?

PCAP은 패킷을 저장하는 데 널리 쓰이는 캡처 파일 형식입니다. 관련 형식으로 PCAPNG도 있습니다. 파일에는 저장 당시 수집한 기록이 들어 있지만, 네트워크에서 일어난 모든 일이 반드시 담겨 있는 것은 아닙니다.

가상머신은 실습용 컴퓨터 환경을 소프트웨어로 마련한 것입니다. 교재의 명령이 어떤 프로그램과 파일을 전제로 하는지 맞춰 보는 데 도움이 됩니다.

오래된 교재의 실습 환경을 사용할 때는 전자 워크북과 도구의 변경 사항도 확인해야 합니다. 종이 안내서의 출력과 현재 화면이 조금 다르다는 이유만으로 분석이 틀렸다고 볼 수는 없겠죠. 반대로 프로그램이 최신이라고 해서 과거 예제의 결과가 그대로 재현된다고 가정해서도 안 됩니다.

학습 중 질문이 생기면 관련 공식 문서나 유지관리되는 저장소를 확인하는 습관도 좋습니다. 다만 교재에 적힌 옛 주소나 지원 채널이 현재도 같은 방식으로 운영되는지는 별도로 확인해야 합니다.

현재 사이트의 첫째 날 실습 가이드는 기존 강의와 실습 주제를 연결합니다. 이번 1강에서는 실습의 답을 미리 외우기보다, 이후 실습에서 무엇을 증거로 남겨야 하는지부터 익히겠습니다.

5. 읽을 때는 알겠는데, 혼자 하면 막히는 이유

설명을 읽으면서 “IP 헤더가 여기 있구나”라고 이해하는 것과, 처음 보는 바이트에서 IP 헤더의 경계를 직접 찾는 것은 다릅니다.

운전 강의를 보는 것과 실제로 차선을 바꾸는 것이 다른 것처럼요.

따라서 학습은 작은 순환으로 진행하는 것이 좋습니다.

먼저 원리를 읽고, 작은 예제에 적용합니다. 결과가 예상과 같으면 왜 같은지 설명하고, 다르면 어디에서 전제가 달라졌는지 확인합니다. 시간이 조금 지난 뒤 같은 원리를 다른 예제에 다시 적용합니다.

예를 들어 오늘 “패킷을 어디에서 수집했는지가 중요하다”고 배웠다면, 다음 실습에서 파일을 열 때 스스로 물어보는 것입니다.

“이 파일은 서버 앞에서 수집했을까요, 방화벽 바깥에서 수집했을까요?”

나중에 응답이 보이지 않는 사례를 만나면 다시 그 질문으로 돌아옵니다. 배운 내용을 다른 상황에서 꺼내 쓰면서 분석 습관이 되는 것이죠.

그래서 뒤에 나오는 종합 실습도 의미가 있습니다. 앞에서 배운 지식을 실제 자료에 적용하면서, 자신의 조사 순서를 만들어 보는 과정입니다.

시험에 나오는 항목만 따로 떼어 외우면 개별 문제에는 답할 수 있어도, 여러 조건이 겹친 실제 통신을 설명하기는 어려울 수 있습니다. 학습 목표는 정답을 알아보는 능력에서 근거를 찾아 설명하는 능력으로 나아가는 것입니다.

처음부터 모든 숫자가 익숙할 필요는 없습니다. 다만 이해되지 않는 용어를 계속 쌓아 두지는 마세요. 뒤의 설명이 그 용어를 바탕으로 진행되므로, 정의와 작은 예제로 돌아가 확인하는 편이 좋습니다.

6. IDS와 IPS는 무엇을 알려주고, 무엇까지 알려주지는 않을까요?

이제 처음의 경고 화면으로 돌아가 보겠습니다.

IDS는 Intrusion Detection System, 즉 침입 탐지 시스템입니다. 의심스러운 활동을 탐지하고 알리는 역할을 합니다.

IPS는 Intrusion Prevention System, 즉 침입 방지 시스템입니다. 통신 경로에서 동작하며, 설정과 정책에 따라 통신을 차단하는 조치도 수행할 수 있습니다.

IDS와 IPS의 역할
구분기본 역할경고를 본 뒤 확인할 것
IDS의심스러운 통신 탐지·알림어떤 조건을 보고 경고했는가?
IPS탐지와 정책에 따른 차단어떤 조치를 했고 실제 결과는 어땠는가?

둘을 화재경보기와 자동 방재장치에 비유할 수 있습니다. 다만 실제 제품은 기능이 겹치기도 하고, 같은 장비도 운영 모드에 따라 다르게 동작합니다. 제품 이름만 보고 “이 경고는 차단까지 끝났다”고 판단하면 안 됩니다.

장비가 통신을 탐지할 때 사용하는 조건을 탐지 규칙, 또는 문맥에 따라 시그니처(signature)라고 부릅니다.

예를 들어 특정 방향의 웹 요청에서 어떤 문자열이 나타났는지, 어떤 프로토콜 필드가 특정 값을 가졌는지 등을 조건으로 삼을 수 있습니다.

그런데 모든 규칙이 모든 공격을 아는 것은 아닙니다. 규칙이 없거나, 조건이 맞지 않거나, 장비가 통신을 제대로 해석하지 못하면 중요한 활동을 놓칠 수 있습니다. 반대로 정상 통신이 규칙과 겹쳐 불필요한 경고가 발생할 수도 있습니다.

따라서 경고가 있다는 사실도, 경고가 없다는 사실도 각각 해석이 필요합니다.

처음의 ‘명령 실행 공격 의심’ 경고에는 적어도 다음 가능성이 있습니다.

동일한 경고의 네 가지 가능성
가능한 상황실제로 일어났을 수 있는 일구별하는 데 필요한 근거
공격 시도 후 실패요청은 전달됐지만 대상이 취약하지 않음요청 내용, 대상 버전·설정, 처리 기록
중간에서 차단IPS 등이 전달을 막음조치 기록, 관측 위치, 다른 지점의 기록
정상 통신과 조건 일치정상 요청이 탐지 조건에 해당규칙의 의미, 요청 목적, 업무 맥락
공격 성공요청으로 원하지 않는 동작 발생응답과 서버의 프로세스·파일·감사 기록

여기서 흔히 헷갈리는 부분이 있습니다.

“공격이 실패했으면 오탐 아닌가요?”

반드시 그렇지는 않습니다. 오탐(false positive)은 탐지하려던 사건이 아닌 것을 그런 사건으로 잘못 판단한 경우입니다. 규칙의 목적이 공격 시도를 찾는 것이라면, 실패한 공격을 정확히 찾은 것도 올바른 탐지일 수 있습니다.

반대로 탐지해야 할 활동을 놓치는 것은 미탐(false negative)이라고 합니다.

‘탐지가 맞았는가’, ‘공격이 도달했는가’, ‘공격이 성공했는가’를 나누어 보면 혼동이 줄어듭니다.

또한 경고의 우선순위 숫자가 조직의 실제 대응 우선순위와 항상 같지는 않습니다. 동일한 요청이라도 외부에 노출된 중요 서버를 대상으로 했는지, 사용하지 않는 테스트 환경을 대상으로 했는지에 따라 조사의 긴급성이 달라질 수 있습니다.

패킷의 특징에서 자동화 여부나 사용한 기법을 추정할 수는 있습니다. 그러나 그것만으로 공격자의 실제 신원·의도·숙련도까지 확정해서는 안 됩니다.

7. 실제로는 어떤 순서로 조사하면 좋을까요?

아래는 경고에서 조사 결론으로 나아가는 흐름입니다. 화살표는 판단이 진행되는 방향이며, 증거가 부족하면 추가 수집 후 다시 검토합니다.

이 그림에서 중요한 부분은 가운데의 ‘관측 위치’와 마지막의 ‘증거가 충분한가’입니다.

패킷을 봤다는 이유만으로 모든 경계를 확인한 것은 아니기 때문입니다.

다음은 가상의 관측 기록입니다. 주소는 학습용 문서 주소입니다.

가상의 요청·응답 관측 기록
순서확보한 자료확인한 내용
1보안 장비 경고외부 주소 198.51.100.20에서 서버 192.0.2.10을 향한 공격 의심 경고
2외부 관측 지점의 캡처경고와 관련된 요청 데이터 확인
3같은 캡처해당 통신의 응답은 현재 자료에서 찾지 못함

여기까지 읽으면 “응답이 없으니 공격이 실패했겠네요”라고 생각할 수 있습니다.

그런데 잠깐만요. ‘현재 캡처에 응답이 없다’와 ‘서버가 응답하지 않았다’는 같은 문장이 아닙니다.

캡처가 시작되거나 끝난 시간이 적절하지 않았을 수 있습니다. 한 방향만 수집됐을 수도 있고, 응답이 다른 경로로 나갔을 수도 있습니다. 패킷이 수집 과정에서 누락됐거나, 분석 필터가 응답을 숨겼을 가능성도 있죠.

무엇보다 외부 관측 지점에서 요청을 봤다면, 그 요청이 중간 방화벽을 지나 서버까지 도달했는지도 아직 모릅니다.

여기에 조건을 하나 추가해 보겠습니다.

방화벽 기록에 해당 통신의 차단 조치가 남아 있습니다.

이제 ‘차단됐다’는 설명을 지지하는 증거가 늘었습니다. 그래도 정확한 통신을 연결한 것인지, 조치가 어느 시점에 적용됐는지 확인해야 합니다. 이미 일부 데이터가 전달된 뒤 조치했을 가능성까지 따져야 하는 상황도 있기 때문입니다.

조건을 또 바꿔 보겠습니다.

서버의 접근 기록에도 관련 요청이 남아 있습니다.

그렇다면 서버 측 처리 경로까지 요청이 전달되었다는 설명을 검토할 수 있습니다. 그러나 이것만으로 명령 실행 성공까지 증명되지는 않습니다. 서버가 요청을 받았지만 거부했을 수도 있으니까요.

성공 여부를 판단하려면 요청과 관련된 응답, 응용 프로그램 기록, 프로세스 실행, 파일 생성 등 추가 근거가 필요합니다.

조사 중에는 다음 다섯 질문을 반복해서 사용해 보세요.

조사에서 반복할 다섯 질문

이때 시간도 맞춰야 합니다. 서로 다른 장비의 기록이 같은 시간대와 시계 기준을 쓰는지 확인하지 않으면, 관계없는 사건을 연결하거나 관련 사건을 놓칠 수 있습니다.

보고서에는 관측·가설·남은 의문을 나누어 적으면 좋습니다.

관측: 외부 관측 지점에서 공격 의심 요청을 확인했다.

가설: 요청 내용은 해당 공격 시도와 일치할 가능성이 있다.

미확인: 서버 도달 여부와 명령 실행 성공 여부는 현재 자료로 확인되지 않는다.

추가 확인: 방화벽 조치 기록, 서버 접근 기록, 관련 프로세스 실행 기록을 대조한다.

이렇게 쓰면 무엇을 알고 있는지뿐 아니라, 무엇을 더 알아봐야 하는지도 분명해집니다.

8. 그런데 요즘은 암호화되어 있는데, 패킷을 읽을 수 있나요?

좋은 의문입니다. 여기서 과거 설명을 현재 환경에 맞게 보완해야 합니다.

통신이 패킷으로 전달된다는 원리는 여전히 유효합니다. 하지만 패킷을 확보하면 모든 통신 내용을 복원할 수 있다는 설명에는 조건이 필요합니다.

암호화 여부, 수집한 범위, 누락, 재조립 가능 여부, 복호화에 필요한 정보가 있는지에 따라 읽을 수 있는 내용이 달라집니다.

이 절의 공식 자료 확인일은 2026년 11월 1일입니다.

① HTTPS 본문은 Wireshark로 열기만 하면 보이는 것이 아닙니다.

HTTPS에서는 일반적으로 HTTP 요청의 경로나 본문 등이 암호화됩니다. HTTP는 웹에서 요청과 응답을 주고받는 규칙이고, TLS는 그 통신을 암호화해 보호하는 데 사용하는 프로토콜입니다.

배송 상자 비유로 돌아가면, 운송에 필요한 일부 정보는 볼 수 있어도 안의 내용물은 잠긴 상태인 셈입니다.

Wireshark가 TLS 통신이라고 알아보는 것과 암호화된 내용을 읽는 것은 다릅니다. 해당 세션의 비밀정보와 필요한 캡처가 있으면 복호화할 수 있는 경우가 있지만, 서버 인증서의 개인키만으로 TLS 1.3 통신을 복호화할 수는 없습니다. Wireshark 공식 문서도 개인키를 사용하는 방식의 제한과 세션 키 로그 방식을 구분합니다. [1]

따라서 “내용이 안 보인다”는 상황을 만나면 암호화 때문인지, 필요한 패킷이 빠졌는지, 해석 설정이나 재조립에 문제가 있는지부터 구별해야 합니다.

② UDP라고 해서 연결이나 신뢰성 있는 전송이 불가능한 것은 아닙니다.

이후 UDP를 배우면 TCP와 같은 연결 설정이나 재전송 기능을 UDP 자체가 제공하지 않는다는 설명을 접하게 됩니다.

그런데 그 위에 동작하는 다른 프로토콜이 필요한 기능을 구현할 수는 있습니다.

QUIC이 그 예입니다. QUIC은 UDP 위에서 연결과 스트림을 제공하고, 손실 복구와 암호화된 전송을 지원합니다. 따라서 UDP를 봤다는 이유만으로 연결 상태나 복구 기능이 전혀 없는 통신이라고 확대 해석하면 안 됩니다. [2]

지금은 “아래 계층에 없는 기능을 위 계층에서 제공할 수 있다”는 점을 기억하면 충분합니다.

③ 접속하려는 실제 도메인도 항상 보이지는 않습니다.

도메인은 사람이 사용하는 서버 이름입니다. 예를 들어 training.example 같은 이름이죠.

TLS 통신을 시작할 때 보내는 ClientHello에는 사용할 통신 조건이 담깁니다. 그 안의 SNI는 접속하려는 서버 이름을 전달하는 정보입니다.

일부 환경에서는 이 정보를 통해 대상 이름을 볼 수 있습니다. 그러나 모든 TLS 통신에서 실제 대상 이름이 그대로 보인다고 가정하면 안 됩니다.

ECH, 즉 Encrypted Client Hello는 실제 대상 이름 등이 포함된 내부 ClientHello를 암호화하는 방식입니다. 2026년 3월 RFC 9849로 표준화되었습니다. 적용된 통신에서는 외부에서 보이는 이름과 실제 내부 대상 이름을 구분해야 합니다. [3]

그렇다고 ECH 하나가 모든 흔적을 숨기는 것도 아닙니다. IP 주소나 시간·크기 같은 정보가 남을 수 있고, 다른 위치의 기록에서도 단서를 얻을 수 있습니다. 반대로 IP 주소 하나가 여러 서비스를 함께 가리킬 수도 있어, 그 주소만으로 정확한 접속 사이트를 확정하기도 어렵습니다.

9. 내용을 못 읽어도 패킷 분석이 중요한 이유

잠긴 상자의 내용물을 못 본다고 배송 기록까지 사라지는 것은 아니겠죠.

누가 어디로 보냈는지, 언제 보냈는지, 얼마나 자주 보냈는지, 어느 정도의 물량이 오갔는지는 여전히 조사에 도움이 됩니다.

네트워크에서도 내용을 해독하는 작업과 통신의 특성을 분석하는 작업을 구분할 수 있습니다. NIST도 암호화된 통신의 관측 가능한 특성에서 정보를 얻는 트래픽 분석을 설명합니다. [4]

다음은 가상 사례입니다.

평소 외부 통신이 거의 없는 서버가 새벽부터 처음 보는 외부 주소에 30초 간격으로 연결했습니다. 이후 외부 방향 전송량이 크게 증가했습니다.

암호화 때문에 실제 내용을 읽지 못했다고 해 보겠습니다. 그래도 평소와 다른 접속 대상, 반복 주기, 전송량 변화는 발견할 수 있습니다.

다만 “악성코드가 기밀 파일을 유출했다”고 바로 결론내려서는 안 됩니다. 새 백업 작업이나 승인된 모니터링 프로그램일 수도 있으니까요.

여기서 할 일은 정상 업무와 비교하고, 해당 연결을 만든 프로그램과 작업 기록을 확인하는 것입니다.

Zeek는 이러한 분석을 연결해 이해하기 좋은 도구입니다. conn.log에는 통신 주소·프로토콜·지속시간·방향별 바이트 등 연결 분석에 유용한 정보가 남고, ssl.log에는 관측 가능한 TLS 관련 정보가 기록됩니다. 구체적으로 남는 항목은 통신과 분석 조건에 따라 달라집니다. 내용을 복호화하지 않아도 활용할 정보가 있다는 예입니다. [5] [6]

여기에 다른 기록을 연결하면 조사가 더 구체적이 됩니다.

EDR은 단말의 활동을 관측하고 대응하는 도구입니다. 수집 설정에 따라 어떤 프로세스가 연결을 만들었는지 확인하는 데 도움이 될 수 있습니다. 웹 서버 기록에서는 요청 처리 상황을, 방화벽 기록에서는 통신 정책과 조치를, 인증·클라우드 감사 기록에서는 로그인과 관리 활동을 확인할 수 있습니다.

클라우드의 API는 프로그램이 서비스 기능을 호출하는 인터페이스입니다. 사용자가 관리 화면에서 수행한 작업뿐 아니라, 프로그램이 API로 수행한 작업도 조사 대상이 될 수 있습니다. ACSC 등의 공동 지침도 환경에 맞는 단말·네트워크·클라우드 기록의 확보를 권고합니다. [7]

이 기록들을 연결할 때도 시간과 주소만 대충 맞추면 안 됩니다. 실제 계정, 프로세스, 요청 식별자 등 연결 가능한 근거를 찾아야 합니다.

10. 도구가 보여주는 설명은 어디까지 믿어야 할까요?

Wireshark가 어떤 패킷을 HTTP라고 표시했다면, 편리한 출발점이 됩니다. 하지만 그 표시가 어떤 조건과 바이트를 근거로 나왔는지는 필요할 때 확인할 수 있어야 합니다.

도구에는 해석 규칙과 설정이 있고, 프로그램 오류도 있을 수 있습니다. 필요한 패킷이 빠졌거나, 중간부터 수집했거나, 사용 중인 버전이 해당 형식을 충분히 지원하지 않을 수도 있죠.

따라서 이상한 결과를 만나면 다음 순서로 되짚어 보는 것이 좋습니다.

먼저 실제 바이트와 길이를 확인합니다. 다음으로 도구의 설정과 재조립 조건을 살펴봅니다. 그 뒤 적용되는 표준과 공식 문서, 필요하면 다른 도구의 결과와 비교합니다.

단, 서로 다른 도구 두 개가 같은 말을 했다고 해서 무조건 증명된 것은 아닙니다. 같은 전제나 유사한 해석 방식을 사용했을 수도 있으니까요.

이것이 패킷 구조를 직접 배우는 또 다른 이유입니다. 도구의 도움을 충분히 받으면서도, 결과가 이상할 때 근거로 돌아갈 수 있게 만드는 것입니다.

11. 복습 — 조건이 달라지면 판단도 달라질까요?

문제 1. IPS에서 공격 경고가 발생했습니다. “공격이 차단됐다”고 바로 보고해도 될까요?

해설: 경고만으로는 부족합니다. IPS가 실제 차단 모드로 동작했는지, 해당 통신에 어떤 조치를 적용했는지, 어느 지점까지 데이터가 전달됐는지 확인해야 합니다. 장비의 역할과 이번 사건의 실제 처리 결과를 구별해야 합니다.

문제 2. 공격 요청이 있었지만 서버가 취약하지 않아 실패했습니다. 그러면 오탐인가요?

해설: 실패했다는 이유만으로 오탐이 되지는 않습니다. 공격 시도를 찾는 규칙이 실제 공격 요청을 탐지했다면 올바른 탐지일 수 있습니다. 규칙이 찾으려던 대상과 실제 통신을 먼저 대조해야 합니다.

문제 3. 캡처에서 요청은 보이지만 응답은 없습니다. 확실하게 쓸 수 있는 문장은 무엇인가요?

해설: “현재 확인한 캡처 범위에서는 해당 응답을 찾지 못했다”입니다. 서버가 응답하지 않았다는 결론에는 수집 시간·방향·경로·누락·필터 조건 등에 대한 추가 확인이 필요합니다.

문제 4. 목적지 포트가 443이면 HTTPS가 확실한가요?

해설: 포트 443은 HTTPS를 의심할 단서지만, 포트 번호만으로 응용 프로토콜을 확정할 수는 없습니다. 가능한 범위에서 실제 프로토콜 구조와 서버·단말 기록을 함께 확인해야 합니다.

문제 5. HTTPS 내용을 읽을 수 없습니다. 패킷 분석을 중단해야 할까요?

해설: 아닙니다. 관측 가능한 주소·시각·방향·빈도·전송량과 연결 진행 상황을 분석할 수 있습니다. 다만 그 정보로 실제 본문이나 전송 파일을 알아냈다고 표현해서는 안 됩니다.

문제 6. TLS 1.3 통신과 서버 인증서의 개인키가 있습니다. 이것만으로 본문을 읽을 수 있을까요?

해설: 서버 개인키만으로 TLS 1.3 통신을 복호화할 수는 없습니다. 해당 세션에 필요한 비밀정보와 캡처 조건을 확인해야 합니다. Wireshark에서 프로토콜 이름이 보인다는 사실도 복호화 성공과는 다릅니다.

문제 7. 서버가 외부 주소에 정확히 30초마다 연결합니다. 악성코드의 제어 통신이라고 확정할 수 있을까요?

해설: 반복 주기는 조사할 단서입니다. 하지만 모니터링·백업·상태 확인 프로그램도 주기적으로 통신할 수 있습니다. 평소 동작, 목적지 역할, 연결을 만든 프로세스와 작업 기록을 대조해야 합니다.

문제 8. 보안 경고가 하나도 없었습니다. 그러면 침해가 없었다고 결론내릴 수 있을까요?

해설: 어렵습니다. 탐지 규칙이 해당 활동을 다루지 않거나, 수집 위치에서 통신을 보지 못했거나, 해석 조건 때문에 놓쳤을 수 있습니다. 경고가 없다는 사실의 의미도 탐지·관측 범위를 기준으로 판단해야 합니다.

문제 9. 워크북의 예상 결과와 내 도구의 출력이 다릅니다. 무엇부터 확인해야 할까요?

해설: 같은 파일·같은 범위·같은 설정인지부터 확인합니다. 그다음 도구 버전, 이름 변환, 표시 단위, 필터와 재조립 조건을 살펴봅니다. 조건을 맞추지 않은 상태에서 자신의 결과나 안내서 중 하나가 틀렸다고 단정하면 원인을 놓치기 쉽습니다.

문제 10. 패킷 분석을 공부하는 목적을 자신의 말로 설명해 보세요.

해설: “네트워크에서 관측한 통신을 읽고, 도구의 판단을 검증하며, 다른 기록과 연결해 어떤 일이 있었는지 근거로 설명하기 위해서”라고 답할 수 있습니다. 여기에 확인하지 못한 부분도 구분해 남긴다는 점이 포함되면 좋습니다.

다음 개정 대상은 2강 ‘경고 이름보다 중요한 패킷의 맥락’입니다. 이번에 배운 관측·가설·검증의 구분을 실제 통신 유형에 적용하며 이어갑니다.
