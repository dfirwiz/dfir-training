## 현재성 보완과 근거

RFC826·1122·5227·4861·9542, Apple 비공개 Wi-Fi 주소 안내, Linux ARP 수신 설정, Cisco의 ARP 및 MAC 전달 표 문서, tcpdump 공식 매뉴얼과 Wireshark Ethernet 문서를 조회했습니다. 실제 확인 날짜와 링크는 본문에 기록했습니다.

- MAC은 NIC 교체 외에도 바뀔 수 있고 가상 MAC이 매 부팅마다 반드시 바뀌지도 않음을 설명했습니다.
- 기본 예제의 마스크 비교와 실제 경로 선택을 구분하고, 기존 캐시가 있으면 매 통신마다 새 ARP가 필요하지 않음을 명시했습니다.
- 일반 라우팅의 다음 링크 프레임은 출발지·목적지 MAC 모두 출력 링크에 맞게 구성함을 설명했습니다.
- 수신한 모든 장치가 무조건 새로운 대응을 캐시에 추가한다고 일반화하지 않습니다. 기존 항목 갱신·자신이 대상인 조건·구현 정책을 구분했습니다.
- 요청 Target MAC의 0을 모든 ARP 요청의 유일한 정상값으로 강제하지 않습니다. RFC5227의 Probe에서 Sender IP가0인 합법적 문맥도 보충했습니다.
- ARP 내부 Protocol type0800과 바깥 Ethernet Type0806을 구분했습니다. ARP 캐시와 L2 MAC·VLAN·포트 표, L3 장비의 별도 ARP 기능도 구분했습니다.
- 유니캐스트 응답을 모든 관측자가 볼 수 있다고 가정하지 않습니다. 응답 관측·캐시 반영·실제 소유자·응용 결과를 분리했습니다.
- NDP를 단일 ICMPv6 타입이라고 하지 않고 NS135·NA136 등으로 연결했습니다.

## 자체 예제 검증

문서용 IP와 RFC9542 문서용 MAC을 사용했습니다. 바이트 배열과 요약은 실제 PCAP 출력이 아닙니다. 원본 실습 PCAP은 제공되지 않아 실행 결과를 꾸며내지 않았습니다.

- 6×8=48, IPv4 4×8=32, IPv6 16×8=128.
- 192.0.2.10/24의 마스크255.255.255.0·네트워크192.0.2.0, 192.0.2.20의 포함과 198.51.100.20의 비포함을 검증했습니다.
- ARP 고정부분2+2+1+1+2=8, 주소6+4+6+4=20, 합계28.
- Ethernet14+ARP28=42, 42×8=336. 패딩46-28=18, FCS까지14+28+18+4=64. 42바이트 예제는 패딩·FCS 없는 부분 배열이며 최소 회선 프레임이라고 하지 않았습니다.
- 필드 위치12~13 Type, 14~21 ARP 고정부분, 22~27 SHA, 28~31 SPA, 32~37 THA, 38~41 TPA를 실제 배열에서 검증했습니다.
- Protocol type0x0800·Opcode1과 주소192.0.2.10/20, THA0을 바이트 해석으로 대조했습니다.

## 게시 검증과 다음 실행

홈페이지와 노트10개, 로컬 링크·자산498개, 새 본문14절·참고문헌11개·복습8문항·SVG와 표를 확인했습니다. 중복 ID·누락 앵커·없는 내부 대상이 없고, 전체17회차 범위가167쪽까지 연속됩니다. 기존 폰트·어두운 배경·민트 강조·반응형 스타일을 유지합니다.

미리보기 인프라 제한으로 실제 브라우저의 시각 검증은 수행하지 못했습니다. 구조 검사를 시각 검증 완료로 보고하지 않습니다.

다음은 새11강 인쇄84~90쪽입니다. 이 범위는 미완료입니다. 다음 실행에서 원문을 다시 읽고 캐시 수신 정책, 양방향 경로와 실제 중간자 영향, CAM 포화의 조건, BPDU Guard·포트 보안·ARP 검증 기능의 차이와 암호화 한계를 검토해야 합니다. 이번 기초 회차의 완료를 그 공격·방어 분석의 완료로 간주하지 않습니다.
