## 현재성·정확성 검토

- TTL의 루프 제한·Protocol 종류·헤더 검사합·주소·옵션 경계 원리는 계속 유효합니다. TTL0의 원래 패킷이 다음 라우터로 전달되는 것처럼 설명하지 않습니다. 초기TTL·전체 경로를 값 하나로 확정하지 않습니다.
- ICMP 오류 인용과 바깥 헤더를 구분하고, 생성 금지·빈도 제한·회신 경로·수집 누락 때문에 응답이 없을 수 있음을 명시했습니다.
- 현재 IANA Protocol 등록부를 조회해0~143이라는 범위를 고정하지 않았습니다. IPv6-ICMP와 IPv4의 일반 ICMP, 포트와 Protocol을 혼동하지 않습니다.
- Microsoft 문서로 현재 기본 활성화·수신 기본 차단과 ICMP/ICMPv6 규칙을 확인했습니다. IPv6 방화벽이 무조건 열려 있다는 원문 주장을 일반 규칙으로 사용하지 않습니다.
- 체크섬은 인증·내용 불변의 보장이 아니며 IPv4 범위는 헤더만입니다.1의 보수 합을2의 보수 기계에서 구현한다는 RFC1071 설명을 알고리즘이2의 보수라는 말로 바꾸지 않았습니다.
- 호스트 오프로딩 전 수집과 실제 회선 오류, validation disabled와 검증 성공, IDS의 분석 제외·IPS의 차단·대상 수신 폐기를 구분했습니다. Suricata 설정 문서가 개발 버전일 수 있으므로 배포 환경 버전/모드 확인으로 제한하고 새 버전의 일반 기본값을 단정하지 않습니다.
- IPv4 UDP0의 합법적 문맥과 IPv6 일반 요구·제한된 터널 예외를 구분했습니다. 모든 계층이 같은 체크섬을 쓴다고 일반화하지 않았습니다.
- 사설·루프백·멀티캐스트·특수 목적 주소를 경계·NAT·VPN·프리픽스와 연결했습니다. 출발지 검증으로 모든 DDoS를 막는다고 설명하지 않습니다. 비대칭 경로와 엄격한 역방향 검사의 전제를 연결했습니다.
- MTU Probe/Reply는 RFC1191에서 이미 폐기되었으며 RFC6814가 이를 재확인한다는 점을 정확히 구분했습니다. 다른 등록 옵션·공식 폐기·장비 정책은 별개입니다. LSRR/SSRR는3바이트 제어부 뒤 주소 데이터를 읽습니다.
- 공식 RFC·IANA·Microsoft·Wireshark·tcpdump·Nmap·Suricata 자료를2026년11월1일 확인하고24개 참고 항목에 링크를 남겼습니다.

## 자체 예제·계산·게시 검증

모든 가상 통신 주소는 문서용 범위로 구성했습니다. 주소 범주 표의 사설·루프백·멀티캐스트는 실제 송수신 예시가 아니라 개념 설명입니다. 원본 실습 PCAP·워크북 결과를 만들지 않았습니다.

- 본문에 실제 표시된 헤더20바이트를 추출해450000540000400040014e57c000020ac6336414와 일치함을 확인했습니다. 검사합 포함 합ffff, 체크섬0일 때 일반 합2b1a6→접힌합b1a8→반전4e57을 검산했습니다.
- TTL64→63일 때4001→3f01, 차0100, 새 검사합4f57을 직접 재계산하고 검증했습니다.
- 4000을 예약0/DF1/MF0/Offset0으로 분해, Offset100×8=800을 확인했습니다.
- 192.0.2.0/24의 브로드캐스트192.0.2.255, RFC3021 지점 간192.0.2.254/31의 두 끝점254/255와192.0.2.0/31의 두 끝점0/1을 검증했습니다.
- 홈페이지+노트13개, 로컬 링크/자산711개와 앵커, 태그 균형·중복ID·각 페이지h1을 검사했습니다. 새 본문18절·표5개·SVG1개·참고24개·바로 보이는 주요 복습9개와 추가 연습을 확인했습니다.
- 표·코드의 가로 스크롤과 SVG 최소폭·반응형 및 접근성 제목을 유지했습니다. 기존 폰트·어두운 배경·민트 강조·생성 스크립트는 수정하지 않았습니다. 실제 브라우저 시각 검증은 수행하지 못했으며 구조 검사와 구분합니다.
