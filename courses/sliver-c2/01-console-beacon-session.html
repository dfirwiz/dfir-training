Sliver 콘솔·Beacon·Session

콘솔이 알려주는 상태와 Windows 로그가 증명하는 동작을 연결해 봅니다.

1강 학습 목표
  • Sliver 콘솔, C2 서버, Windows 단말에서 실행되는 구성 요소의 역할을 설명합니다.
  • Beacon의 체크인과 Session의 대화형 연결을 구분합니다.
  • Sysmon의 프로세스·DNS·네트워크 이벤트를 묶고, 조사 결과를 세 문장으로 작성합니다.

실제 콘솔 읽기 · Windows 로그 실습

1. C2 서버와 콘솔의 역할

Sliver는 Bishop Fox의 오픈소스 레드팀 프레임워크입니다. C2는 Command and Control의 약칭입니다. 콘솔은 사람이 상태를 확인하는 인터페이스이고, 서버는 작업과 통신을 관리합니다. 단말 쪽 실행 구성 요소는 Sliver 문서에서 implant라고 부릅니다. 서버에 내장된 콘솔과 별도의 운영자 클라이언트는 모두 서버와 상호작용합니다. Bishop Fox 아키텍처 설명

구성 요소역할이 기록이 답하는 질문
운영자 콘솔사람이 작업과 상태를 확인하는 텍스트 화면운영자 또는 서버가 어떤 상태를 표시했나?
C2 서버단말과의 통신과 작업을 관리하는 구성 요소언제 체크인했고, 작업의 어떤 상태가 기록됐나?
단말의 Implant서버와 통신하는 단말 측 프로그램어떤 프로세스가 실행되고 어떤 네트워크 활동이 관측됐나?

레드팀 기초의 Cobalt Strike 장에서도 도구가 표시하는 상태와 단말에서 확인한 결과를 나눠 봤습니다. Sliver에서도 서버 콘솔이 열렸다는 사실만으로는 어느 Windows 단말에서 실행이 있었는지 알 수 없습니다. 단말에서 프로세스가 생성됐다는 기록이 있다면, 이어서 그 프로세스의 연결과 실행 문맥을 확인합니다.

2. 실제 Sliver 서버 콘솔 읽기

Virus Bulletin의 C2 탐지 연구에 실린 그림 2를 엽니다. 공개 원본은 Sliver v1.5.34가 Kali에서 열린 실제 콘솔 화면입니다. 연구 자료의 해당 화면에서 아래 항목만 짚어봅니다. 실제 콘솔 원본 열기

  1. 화면 가운데 아래의 서버 버전에서 v1.5.34를 찾습니다. 이는 보고 있는 서버 화면의 버전입니다. 버전이 다른 교육 자료를 비교할 때 기준으로 쓰세요.
  2. 맨 아랫줄의 [server] sliver >를 찾습니다. 텍스트를 입력하는 콘솔 프롬프트이고, [server] 표시는 서버 콘솔 문맥을 알려줍니다.
  3. 증거로 기록할 내용은 ‘Sliver 서버 콘솔이 열려 있음’입니다. 이 화면에 단말명, 체크인 시각, 작업 결과는 표시되어 있지 않습니다. 그 정보가 필요하면 별도의 상태 기록이나 단말 로그를 확인합니다.

3. Beacon과 Session의 차이

구분통신 방식조사할 때 볼 점
Beacon단말이 주기적으로 서버에 체크인하고, 대기 중인 작업을 받아 결과를 돌려주는 비동기 방식동일한 프로세스와 목적지의 연결 반복 여부, 기록 시각, 정상 소프트웨어에서 알려진 패턴
Session지속 연결 또는 롱 폴링 등 통신 방식에 따라 대화형 상호작용을 제공연결 시작 시각, 흐름 지속 시간, 단말의 실행 기록. 지속 시간은 흐름·방화벽·프록시 로그에서 확인

대기 중인 작업, 단말에서 실행된 작업, 서버가 결과를 받은 작업은 각각 별도의 상태입니다. 그리고 백업·업데이트 서비스도 정기적으로 서버를 확인합니다. 반복 연결이 보이면 누가 연결했고, 목적지가 업무상 기대되는 곳인지부터 조사합니다. Sliver의 Beacon과 Cobalt Strike의 Beacon은 각 제품의 용어이므로 해당 제품 문서에서 의미를 확인합니다. Bishop Fox 모드 설명

4. 시나리오 실습. 연결을 만든 프로세스 찾기

가상 회사의 SOC가 WS-FIN-07에서 반복적인 외부 연결 경보를 받았습니다. 정상 업데이트 프로그램도 같은 시간에 TCP 443을 사용했습니다. 다음 표와 합성 Sysmon CSV를 이용해 둘을 가려냅니다. 이 자료는 수업용으로 작성했으며 실제 Sliver 실행이나 Windows 수집 결과는 포함하지 않습니다. 시각은 UTC이며, 표의 A·B는 실제 ProcessGuid를 대신하는 예제 표시입니다.

시각 (UTC)Sysmon ID프로세스 키관측 내용
09:13:021BC:\Program Files\ExampleCorp\updater.exe 시작
09:14:011AC:\Users\training\Downloads\invoice-viewer.exe 시작. 부모는 explorer.exe
09:14:0722Async-telemetry.example DNS 조회. 응답 203.0.113.25
09:14:083A203.0.113.25:443 연결
09:14:093B198.51.100.41:443 연결
09:15:083A203.0.113.25:443 재연결
09:16:093A203.0.113.25:443 재연결

직접 확인하는 순서

  1. CSV를 열어 EventID가 3이고 DestinationIp가 203.0.113.25인 행을 찾습니다. 세 행의 Computer와 ProcessGuid를 적습니다.
  2. 목적지와 EventID 필터를 해제하고, 방금 기록한 Computer와 ProcessGuid로 다시 필터링합니다. 이벤트 1에서 Image와 ParentImage, 이벤트 22에서 QueryName과 QueryResults를 읽습니다.
  3. 09:14:08→09:15:08과 09:15:08→09:16:09 사이 간격을 계산합니다. 같은 포트를 쓴 프로세스 B의 ProcessGuid와 DestinationIp도 비교합니다.
  4. 티켓에 관찰한 사실 한 문장, 가설 한 문장, 다음 확인 한 문장을 씁니다.

실제 Windows에서는 이벤트 뷰어의 응용 프로그램 및 서비스 로그 → Microsoft → Windows → Sysmon → Operational에서 현재 로그 필터링을 열고 이벤트 ID에 1,3,22를 넣습니다. 개별 이벤트의 자세히 → XML 보기에서 해당 필드를 확인합니다. Sysmon의 이벤트 3은 기본적으로 비활성화되어 있으므로 보이지 않으면 수집 설정과 필터를 먼저 확인합니다. DNS 조회 이벤트 자체는 TCP 연결이나 데이터 전송을 증명하지 않습니다. Microsoft Sysmon 이벤트 설명

실습 해설과 티켓 예시

  1. 관찰. WS-FIN-07에서 invoice-viewer.exe 프로세스 A가 sync-telemetry.example을 조회한 후 응답 IP의 TCP 443으로 세 차례 연결했습니다. 두 간격은 60초와 61초입니다.
  2. 가설. 다운로드 폴더의 프로그램이 약 1분 간격으로 같은 목적지에 접속해 C2 체크인 가능성을 조사합니다. 해당 패턴의 원인과 도구 식별은 미확정입니다.
  3. 다음 확인. EDR에서 파일 해시·서명·최초 실행 이력을 확인하고, 프록시나 방화벽 기록에서 같은 시각과 목적지를 대조합니다. 프로세스 B는 GUID와 목적지가 다르므로 별개 연결로 기록합니다.

5. 복습과 즉시 해설

  1. 서버 콘솔이 열려 있으면 단말도 연결된 상태인가요? 화면으로 확인한 것은 서버 콘솔 문맥입니다. 단말 접속 상태를 판단하려면 체크인 기록이나 통신 증거가 필요합니다.
  2. 어떤 필드로 세 종류의 이벤트를 묶나요? 이 사례에서는 Computer와 ProcessGuid를 함께 사용합니다. PID만 쓰면 시간이 흐른 뒤 재사용된 PID와 혼동할 수 있습니다.
  3. 443번 연결이 1분마다 발생하면 Sliver인가요? 반복은 조사 단서입니다. 포트만으로 애플리케이션 프로토콜이나 도구를 식별할 수 없으며, 정상 업데이트에도 반복 통신이 발생합니다.
  4. DNS 조회는 있고 이벤트 3은 없으면 어떻게 쓰나요? ‘DNS 조회 관측, 네트워크 연결 여부 미확인’으로 적습니다. Sysmon의 수집 범위를 확인하고, 네트워크 기록과 대조합니다.
